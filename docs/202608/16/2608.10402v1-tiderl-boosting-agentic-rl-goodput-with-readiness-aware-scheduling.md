## 摘要
用于大型语言模型的强化学习（RL）正朝着多轮智能体工作负载发展，在此类负载中，回放任务会反复因外部环境而暂停，在上下文不断增长的情况下恢复，并在高度可变的时刻完成。在这种场景下，RL训练的有效吞吐（以训练吞吐量衡量）比原始GPU占用率更为重要：GPU等待和重复的预填充重计算均为纯粹开销。我们提出TideRL，一个具有连续任务批处理、资源感知的Ref-Actor流水线和弹性资源伸缩的就绪感知弹性RL系统。CTB保留有用的回放状态，$\textrm{RA}^2\textrm{P}$根据就绪积压和到达间隔在解耦流式与同地聚合之间进行选择，而ERS利用相同的就绪信号在回放与训练之间移动资源。在纯文本和多模态智能体工作负载上，与同步基线相比，TideRL将RL训练有效吞吐提升了高达5.6倍，与异步基线相比提升了超过33%，同时实现了相似的任务性能。它还使KV缓存命中率提升了1.58倍，将每步训练时间减少了高达44.3%，并将总等待时间削减了高达77.6%。

## Abstract
Reinforcement learning (RL) for large language models is moving toward multi-turn agentic workloads, where rollout tasks repeatedly pause for external environments, resume with growing contexts, and finish at highly variable times. In this setting, RL training goodput, measured by training throughput, matters more than raw GPU occupancy: GPU waiting and repeated prefill recomputation are pure overhead. We present TideRL, a readiness-aware elastic RL system with Continuous Task Batching, Resource-Aware Ref-Actor Pipelining, and Elastic Resource Scaling. CTB preserves useful rollout state, $\textrm{RA}^2\textrm{P}$ selects between decoupled streaming and colocated aggregation from the ready backlog and arrival interval, and ERS moves ranks between rollout and training using the same readiness signals. Across text-only and multi-modal agentic workloads, TideRL improves RL training goodput by up to 5.6$\times$ over synchronous baselines and over 33% over asynchronous baselines, while reaching similar task performance. It also improves KV cache hit rate by 1.58$\times$, reduces per-step training time by up to 44.3%, and cuts total waiting time by up to 77.6%.

### 1. 核心问题与研究动机

- **背景**：大语言模型（LLM）正从单轮文本生成器演变为多轮智能体（Agent），通过与浏览器、手机、操作系统等外部环境迭代交互来完成复杂任务。强化学习（RL）是提升智能体自主能力的关键手段，而智能体 RL 任务呈现出多轮交互、上下文持续增长、完成时间高度可变的特点。
- **核心问题**：在多轮智能体 RL 中，传统以 GPU 占用率为导向的优化目标不再适用——GPU 等待和重复的 prefill 重计算是纯粹开销。**训练有效吞吐（goodput，即真正被 Trainer 消费并推进更新的 token 数/秒）** 才是关键指标。
- **三大系统性挑战**（论文识别出的现有架构缺陷）：
  - **C1：KV 缓存被抢占**。多轮任务的暂停等待外部反馈期间，推理引擎因 request 级连续批处理而驱逐其 KV 缓存，恢复时需对不断增长的历史上下文进行灾难性的重复 prefill 重计算。
  - **C2：训练端停滞与抖动**。现有系统在 Trainer 中共享 GPU 运行 Ref 和 Actor 模型，要么等待大全局批次导致 GPU 闲置高达 81% 的步时间，要么频繁切换模型权重造成严重 I/O 抖动。
  - **C3：静态资源分配失效**。任务复杂度差异极大，系统瓶颈在 Rollout 和 Trainer 之间动态切换，静态 GPU 划分无法同时适应初始就绪积压和稳态就绪间隔的变化。

### 2. 方法论：TideRL 的三个协同组件

#### 核心思想
**就绪感知（Readiness-Aware）**：通过统一的就绪信号（RAS——训练步开始时已就绪的微批次数量；TPRM——后续微批次的平均到达间隔）来协同调度 Rollout、Trainer 和集群资源。核心洞见是：多轮 RL 需要共享的就绪视图，内存管理需从请求级提升到任务级，DP rank 应该是可调度资源而非静态工作组成员。

#### 组件一：连续任务批处理（CTB）
- **Token 感知准入控制**：将每个 DP rank 视为 token 预算池，通过轻量探针任务估计任务初始足迹，仅在 KV 缓存余量充足时准予进入；同时执行环境并发限制、策略陈旧性限制、任务多样性约束。
- **语义感知的暂停与恢复**：当 rank 超过 token 预算时，按优先级层级（评估任务 > 组完成度 > 活动轨迹 > 上下文长度）暂停低优先级任务；容量恢复后优先恢复已暂停任务而非准入新任务，并通过组 ID 保持 worker 亲和性以保留共享前缀。

#### 组件二：资源感知 Ref-Actor 流水线（RA²P）
- **解耦流式模式**（适用于高 RAS 或短 TPRM）：Ref 和 Actor 分布于不同 GPU，形成流式微批次流水线；**通过将损失计算从前向推迟到反向**，打破 Actor 对 Ref 输出的依赖，使 Ref 前向、Actor 前向和反向可以重叠执行，零模型切换开销。
- **优化共置模式**（适用于低 RAS 且长 TPRM）：Ref 和 Actor 同驻 GPU，采用**就绪批次聚合**（一次加载 Ref 处理多个就绪批次再切换至 Actor）和**零拷贝共享内存传输**，摊还不可避免的模型切换开销。
- **分析式模式选择**：通过成本模型比较两种模式的延迟（$C_{dec}$ 与 $C_{col}$），综合 RAS 和 TPRM 两个信号动态决策。
- **微批次调度**：早期批次尽量攒满以饱和 DP rank 算力，最终批次刻意保持最小以缩短 pipeline flush 气泡；共置模式用锯齿形（最长处理时间优先）分配策略平衡负载，解耦模式则保证流水线输入的最后一个序列最小以缩短尾延迟。

#### 组件三：弹性资源缩放（ERS）
- **就绪感知计划生成**：监控全局缓冲区的 RAS 和 TPRM 信号，通过**生成亏空**（generation deficit，全局批次量 < B_ideal）和**消费亏空**（consumption deficit，队首微批次延迟超阈值）两个指标判断瓶颈方向。生成亏空→选择共置 RA²P 并将 GPU 调配给 Rollout；消费亏空→选择解耦 RA²P 并将 Rollout rank 回收为 Trainer 容量。
- **零开销弹性迁移**：利用 on-policy RL 每次同步后 KV 缓存天然失效的特性，将任务迁移与缓存刷新对齐；权重迁移与 sync_params 广播重叠，隐藏 PCIe 切换延迟，无需暂停流水线或重建 NCCL 组。
- **保护机制**：冷启动或评估阶段预先生成分配最大化 Rollout 规模；采用自适应数据保留防止缩容后出现饥饿循环。

### 3. 实验设计

#### 测试平台与工作负载
- **文本任务套件**：WebShop（电商交互）和 AlfWorld（具身家居任务混合套件），上限 20 轮、上下文 8192 token。
- **多模态任务套件**：OS-World（GUI 交互，5–9 张滑动窗口图像）和 ScienceBoard（科学工作流 GUI，8–15 张滑动窗口图像），上限 50 轮，截图分辨率 1280×720。
- **模型**：文本——Qwen-2.5（7B、14B）；多模态——Qwen-3-VL（4B）、Qwen-3.5（9B，线性注意力 + 多 token 预测）。

#### 对比基线
- **VeRL**：同步 RL 框架，严格阶段屏障。
- **AReaL**：异步 RL 框架，物理解耦 Rollout/Trainer，使用 APRIL 的主动部分回滚机制。
- **StreamRL**：先进异步框架，支持流式生成直接送入 Trainer；为公平比较，StreamRL 始终使用最大允许 GPU。
- 所有框架使用相同 GPU 预算、任务流、模型检查点、陈旧性边界、全局批次配置；固定分区异步基线在候选集中扫描最佳 rollout GPU 比例（最佳为 0.25）。

### 4. 资源与算力

- **训练集群**：4 个计算节点，每个节点 8× NVIDIA H100 GPU（共 **32 块 H100**），通过 NVLink 互联；64 核 Intel Xeon CPU，1.5 TB RAM/节点；共享 JuiceFS 后端 NFS。
- **环境集群**：独立的裸金属 Kubernetes 集群，**1024 个 CPU 核**用于运行外部环境模拟。
- **训练时长**：文本任务训练 100 步，多模态任务训练 40 步（论文未报告总墙钟时长，仅报告了相对收敛时间——如 TideRL 仅用 VeRL 的 48.9% 墙钟时间达到同等性能）。

### 5. 实验数量与充分性

- **端到端实验**（文本 4 框架 × 2 模型，多模态 4 框架 × 2 模型）：覆盖同步/异步基线和不同架构模型。
- **渐进消融**（OSWorld + Qwen-3-VL）：StreamRL 基线 → +RA²P → +ERS → +CTB，量化各组件贡献。
- **微基准 / 组件隔离实验**：
  - CTB：单 H100 上 1312 个 WebShop 任务，对比固定并发因子（1024 和 512）；
  - RA²P：4×H100 上 8 个就绪微批次，对比带/不带模型卸载的 vanilla 流式；
  - ERS：8×H100 单节点 100 步 WebShop，与静态固定比例对照。
- **补充实验**：后缀解码（SD）兼容性分析及 overhead 数据。
- **充分性评价**：实验总体设计合理、覆盖面广（不同模态、模型规模、就绪模式），对比基线选择得当且做了公平的静态比例扫描。但多模态实验仅 40 步，训练方差较大时结论稳健性略有不足；未在更大规模集群（如 100+ GPU）或更长训练周期上验证。

### 6. 主要结论与发现

- **文本任务**：TideRL 训练吞吐比 VeRL 快 5.6×，比 AReaL 快 1.8×，比 StreamRL 快 7×（14B 场景下 StreamRL 甚至无法在 6 小时内完成）；达到 VeRL 同等任务性能仅需其 48.9% 的墙钟时间（BoN 奖励差距 0.01，通过率差距 0.5%）。
- **多模态任务**：训练吞吐比 VeRL 提升 6.02×，比异步基线提升超 33%，40 步训练仅用 VeRL 37.8% 的墙钟时间。
- **组件级效果**：CTB 提升 KV 缓存命中率 1.58×、生成吞吐 1.15×、缩短步时长 15.6%；RA²P 降低每步训练时间最高 44.3%；ERS 减少总 TWT+RWT 达 77.6%（在 0.25 固定比例基础上）。
- **关键洞察**：就绪信号（RAS/TPRM）能够统一指导内存管理、执行模式选择和资源弹性分配；TideRL 以接近同步 RL 的训练质量实现了远高于同步/异步基线的好put。

### 7. 优点与亮点

- **系统性协同设计**：CTB、RA²P、ERS 三者通过统一就绪信号闭环耦合，不是孤立优化模块——CTB 控制数据何时就绪，RA²P 决定如何高效消费，ERS 根据消费代价动态调配资源。
- **零开销弹性的巧妙实现**：利用 on-policy RL 的天然同步边界（KV 缓存失效 + sync_params 广播）来隐藏角色切换和权重迁移成本，避免了传统弹性框架的暂停-迁移-重建开销。
- **计算图重构创新**：将 Actor 的损失计算从前向延迟到反向，打破 Ref→Actor 的依赖链，使流水线重叠成为可能——这是一个简洁而高效的设计。
- **务实且通用的工程实现**：约 16000 行 Python，兼容 Megatron、PyTorch FSDP、vLLM、SGLang 等主流框架；环境接口标准化，支持 /pause、/resume 端点管理任务生命周期。
- **对真实部署约束的敏感性**：考虑了生产集群固定资源配额场景，与 Pollux、AntMan 等大规模系统讨论对齐。

### 8. 不足与局限

- **多模态任务收益较小**：因 Trainer 体积增大减少了 ERS 可迁移 rank 数量，吞吐优势从文本任务的 1.8× 降至 1.33×，说明可弹性空间受模型规模制约。
- **评估任务同步瓶颈未完全解决**：评估需锚定静态模型版本，强制执行版本同步会暂时破坏异步流水线动量；论文承认这是未来工作（拟引入 Laminar 式 relay 同步），属于已知未解决问题。
- **规划偏保守**：ERS 每次最多增加一个 Trainer rank，在训练方差高的多模态场景中 Trainer 可能长期成为瓶颈，导致策略陈旧性偏移（虽然 KL 惩罚缓解了影响）。
- **与后缀解码（SD）不兼容**：在多变多轮 agentic 工作负载下 SD 接受率仅约 40%、接受长度仅 2.8 token，草稿验证开销超过投机收益，实验显示 SD 反而增加 4.9%–7.6% 的 rollout 时间——这在某些具备高接受率的工作负载上可能错失加速机会。
- **实验外部效度限制**：32 GPU 规模能否推广到数百/数千 GPU 的巨型集群未经验证；14B 是最大测试模型，更大模型（如 70B+）下显存压力和弹性空间的表现未知。
- **主机内存瓶颈**：全局轨迹缓冲区、参考模型和图像文件同时占用 CPU RAM，导致无法使用 HiCache 等分层缓存方案缓解 KV 容量压力。
