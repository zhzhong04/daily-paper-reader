## 摘要
生产环境中的分页服务引擎对KV缓存采用统一的分页粒度，尽管多智能体工作负载的两个区域具有相反的存储需求：长共享前缀要求连续性，而每个请求的后缀则要求细粒度分配。我们提出GraniKV，一种KV缓存层，将共享前缀分配在连续的HOT池中，将后缀分配在token级的COLD池中，并结合一个逐步调度器，在双后端之间为每种情况（计算密集型、内存密集型或通信密集型）选择适当的后端。据我们所知，GraniKV是首个将不对称分页粒度应用于生产分页服务引擎KV缓存的系统。在L_p=16K共享token时，与生产基线相比，GraniKV在Llama-3.1-8B/TP=1、Qwen-2.5-14B/TP=2和Qwen-2.5-32B/TP=4上的输出token吞吐量分别达到2.16倍、1.98倍和1.57倍。这一增益可分解为：级联注意力集成在饱和时贡献了大部分；不对称存储层在端到端上增加了1.05–1.15倍，同时它也是实现批量GEMM前缀后端的基础。在具有不同长度不同提示的异构多智能体服务下，贡献归因发生反转：GraniKV维持1.95倍的性能，而批量全局级联则降至持平——在激励本文的场景中，仅存储层就带来了胜利。

## Abstract
Production paged-serving engines apply uniform paging granularity to the KV cache, even though the two regions of a multi-agent workload have opposite storage requirements: a long shared prefix demands contiguity, while the per-request suffix demands fine-grained allocation.   We present \textbf{GraniKV}, a KV-cache layer that allocates the shared prefix in a contiguous HOT pool and the suffix in a token-level COLD pool, combined with a per-step dispatcher which selects the appropriate backend among dual backends for each regime (compute-, memory-, or communication-bound). To the best of our knowledge, GraniKV is the first system to apply asymmetric paging granularity to the KV cache of a production paged-serving engine.   At $L_p{=}16$\,K shared tokens GraniKV reaches $\mathbf{2.16\times}$, $\mathbf{1.98\times}$, and $\mathbf{1.57\times}$ output-token throughput over the production baseline on Llama-3.1-8B/TP=1, Qwen-2.5-14B/TP=2, and Qwen-2.5-32B/TP=4. The gain decomposes: cascade attention integration contributes the majority at saturation; the asymmetric storage layer adds $1.05$--$1.15\times$ end-to-end while being what makes the batched-GEMM prefix backend possible at all. Under heterogeneous multi-agent serving with \emph{distinct} prompts of different lengths, the attribution inverts: GraniKV sustains $\mathbf{1.95\times}$ while batch-global cascade collapses to parity --- the storage layer alone carries the win in the regime that motivates the paper.

## GraniKV 论文深度解析与总结

### 1. 核心问题与整体含义（研究动机与背景）

- **核心矛盾**：生产级 LLM 服务引擎（如 SGLang、vLLM）在管理 KV 缓存时，普遍采用**统一分页粒度**。然而，多智能体（Multi-Agent）系统的工作负载中，KV 缓存的两个区域有着**截然相反**的存储需求：
  - **共享前缀**（系统提示词、检索文档等）：长且被大量并发请求复用，需要**连续存储**，以便注意力内核能直接进行大矩阵乘法（fat-GEMM）而无需 gather 操作。
  - **请求后缀**（用户问题、生成token）：短且每个请求唯一，需要**细粒度分配**（如 token 级），以避免内部碎片和内存浪费。
- **现有方案的不足**：
  - **生产引擎默认方案**（如 SGLang）：对所有 KV 统一分页，既无法满足前缀的连续性需求，也无法实现后缀的 token 级分配。
  - **HydraGen**：提出了共享前缀的批量 GEMM 方法，但其实现依赖于连续的前缀存储，生产级分页引擎无法直接提供。
  - **Cascade Inference**：通过只读一次前缀来减少 HBM 带宽，但仍需从分散的页面中读取，且无法被不同前缀的请求利用。
- **研究意义**：GraniKV 首次在**生产级分页服务引擎**中引入**非对称粒度的 KV 缓存分页**，解决了共享前缀与独立后缀在存储和计算模式上的根本冲突，从而显著提升长共享前缀多智能体系统的推理吞吐量。

### 2. 方法论：核心思想、关键技术细节

GraniKV 的核心思想是**将具有对立需求的 KV 区域分离管理，并为不同计算场景动态选择最优内核**。其方法包含三大支柱：

- **非对称粒度存储层**：
  - **HOT 池（共享前缀）**：为每个共享前缀分配一块**连续的内存区域**（slab）。采用 bump-pointer 分配器，通过简单的跨度计算（stride math）即可定位 K/V 张量，无任何间接寻址开销，保证了前缀注意力内核能进行单次密集读取。
  - **COLD 池（请求后缀）**：实现 **token 级（页大小为1）** 的空闲列表分配器。每个生成 token 占用一个槽位，彻底消除了内部碎片。虽然在解码时引入了 token 级页表间接寻址，但实验证明其开销可忽略不计（<1%）。
- **双注意力后端（Dual Backends）**：
  - **Dense Backend（计算受限场景）**：受 HydraGen 启发，在一次运算中将所有请求的 Query 与共享前缀的 Key/Value 进行批量 GEMM（大矩阵乘法），最大化 Tensor Core 利用率。适用于大批量、长前缀的**计算密集型**场景。
  - **Cascade Backend（内存/通信受限场景）**：基于 FlashInfer Cascade，将共享前缀作为 level-0 输入，每个解码步骤只读取一次前缀，然后与每个请求的后缀分别计算，通过 log-sum-exp 合并。适用于小批量、短前缀或通信开销大的**内存/通信密集型**场景。
  - **数值等价性**：两个后端通过 log-sum-exp 技巧合并前缀和后缀的注意力输出，产生数值上等价的结果。
- **逐步调度器（Per-Step Dispatcher）**：
  - 在每个解码步骤，根据当前实际批次大小（$B_{step}$）和多查询注意力（GQA）组大小（$n_{q/kv}$）计算有效矩阵乘法维度：$M_{eff} = B_{step} \times n_{q/kv}$。
  - **调度规则**：当 $M_{eff} \ge M_{sat}$（在 A100 上经验测得为 1024）时，路由到 Dense Backend；否则路由到 Cascade Backend。
  - 这使得 GraniKV 能动态适应批次大小的波动，在不同性能区间均能保持最优或接近最优的性能，避免单一后端选择在性能曲线错误一侧造成的损失。

### 6. 主要结论与发现

- **显著的性能提升**：在长共享前缀（$L_p=16K$）和高并发（$B=256$）下，GraniKV 的输出吞吐量相比生产基线，在 Llama-3.1-8B/TP=1、Qwen-2.5-14B/TP=2 和 Qwen-2.5-32B/TP=4 上分别提升 **2.16 倍、1.98 倍和 1.57 倍**，同时 TPOT 延迟大幅下降。
- **增益归因**：
  - 在**单一共享前缀**的饱和场景下，**Cascade 注意力集成**贡献了大部分增益。
  - **非对称存储层**在端到端性能上额外贡献了 1.05–1.15 倍，并且是实现 Dense 后端的**必要前提**。
- **异构多前缀场景的逆袭**：在多个不同共享前缀同时存在的真实多智能体场景下，Cascade 因无法跨不同前缀去重而失效（与基线持平），而 GraniKV 的存储层因能按前缀类别管理，**单独贡献了 1.95 倍**的吞吐量提升。
- **根本原因**：连续的 HOT 池存储将 Dense 后端的 `QK^T` 运算从**内存受限**变为**计算受限**，内核隔离测试显示，仅存储布局的改变就带来了 **15.6 倍**的内核加速。
- **无短前缀回归**：在短前缀场景下性能与基线持平（最差为 0.97 倍），没有引入性能回退。

### 8. 不足与局限

- **高租户场景的失效**：在大量不同前缀同时存在且其总大小超过 KV 预算时（如 k=64），系统性能会急剧下降。虽然这是所有分页引擎的共同问题，但 GraniKV 在此场景下没有特殊优势，且目前缺乏基于热度的 HOT 池淘汰策略。
- **静态池比例**：HOT 和 COLD 池的比例（$f_p$）在启动时固定（默认 0.2），无法适应工作负载的动态变化（如白天长前缀多、晚间短查询多的场景）。
- **硬件与模型覆盖有限**：实验仅在 A100 GPU 上完成，调度阈值（$M_{sat}=1024$）是硬件特定的，需在新硬件上重新校准。未测试 MoE 模型、更大或更小的模型、序列并行等更广泛的部署模式。
- **特定配置下的性能回归**：在小型 $L_p$ 和高批次大小组合的极端角落（如 `Lp=512, B=512`），GraniKV 相比基线有高达 30% 的性能回退。虽然这被描述为可通过 CLI 关闭的部署时配置选择，但它确实暴露了系统在非目标场景下的脆弱性。
