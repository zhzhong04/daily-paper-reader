## 摘要
设备端大语言模型智能体在本地硬件上与用户反复交互，产生的私有轨迹对自适应很有价值，但不应发送给远程训练器。理想情况下，此类智能体应能连续学习——在不暂停或挂起面向用户的推理的情况下，从每次交互中自适应——然而现有的推理运行时假定权重稳定，现有的强化学习系统假定资源分离，因此两者都无法支持这种连续性。我们提出了LOCAL，这是首个支持智能体大语言模型设备端连续学习的单GPU运行时。关键洞察在于，GPU调度、适配器版本管理和KV缓存有效性不能由独立的子系统处理：适配器更新会使旧版本的缓存KV张量失效，而缓存保留会影响可用于训练的内存。LOCAL将适配器版本、任务优先级和缓存状态暴露给三个协同组件——协作调度器、版本感知的KV缓存管理器和多智能体模型运行时——它们共享这些状态以保持调度、执行和缓存维护相互一致。在单个24 GB GPU上使用7B级模型时，LOCAL相比FIFO将前台队列等待p95降低了3.1倍，相比不可抢占训练将p95首令牌时间（TTFT）降低了1.55倍，将发布后首次命中预填充p99降低了25.6%，跨智能体TTFT p99降低了21.9%，并在紧张的KV预算下保持后台学习持续推进。

## Abstract
On-device LLM agents interact repeatedly with users on local hardware, producing private traces that are valuable for adaptation but should not be sent to a remote trainer. Ideally, such agents would learn contiguously---adapting from every interaction without pausing or suspending user-facing inference---yet existing inference runtimes assume stable weights and existing RL systems assume separated resources, so neither can support this continuity. We present LOCAL, the first single-GPU runtime that enables contiguous on-device learning for LLM agents. The key insight is that GPU scheduling, adapter version management, and KV-cache validity cannot be handled by independent subsystems: adapter updates invalidate cached KV tensors from older versions, and cache retention affects the memory available for training. LOCAL makes adapter version, task priority, and cache state visible to three cooperating components---a cooperative scheduler, a version-aware KV-cache manager, and a multi-agent model runtime---that share this state to keep scheduling, execution, and cache maintenance mutually consistent. On a single 24 GB GPU with 7B-class models, LOCAL lowers foreground queue-wait p95 by 3.1x over FIFO, lowers p95 time-to-first-token (TTFT) by 1.55x versus non-preemptible training, cuts post-publish first-hit prefill p99 by 25.6% and cross-agent TTFT p99 by 21.9%, and keeps background learning progressing under tight KV budgets.

# 论文详细总结

## 1. 核心问题与整体含义（研究动机和背景）

- **核心问题**：设备端 LLM 智能体（on-device LLM agent）需要在本地与用户持续交互，并从交互产生的私有轨迹中不断自适应（即“连续学习”），但现有系统无法支持这种连续性。具体而言：
  - **推理运行时**（如 vLLM、SGLang）假定“权重稳定”：模型参数在服务期间不变，因此 KV 缓存条目只要 token 前缀匹配就保持有效；一旦在线训练更新 LoRA 适配器，旧适配器版本产生的 KV 张量失效，重用时会在不同适配器状态间静默混入隐藏状态。
  - **分布式 RL 系统**（如 HybridFlow、OpenRLHF、ReaL）假定“资源分离”：rollout、奖励计算、参考打分、训练等可以放在独立加速器上。但在单卡消费级 GPU 上，用户推理、评判推理、适配器训练和 KV 状态维护必须共享同一块 GPU，无法依赖集群分散负载。
- **应用背景**：本地部署 LLM 可保护隐私，且 LoRA 等参数高效微调使单设备自适应变得可行；智能体反复交互产生的用户纠正、偏好、失败工具调用等轨迹既私密又有价值，不应发送到远程训练器。
- **本文含义**：提出了 LOCAL（首个单 GPU 连续学习运行时），使设备端 LLM 智能体在不中断用户推理的情况下持续从交互中学习，为隐私敏感的自适应 LLM 系统奠定了运行时基础。

## 2. 方法论：核心思想、关键技术细节

- **核心思想**：前台延迟、适配器发布和 KV 缓存有效性三方面强耦合，不能由独立子系统管理。LOCAL 将**适配器版本、任务优先级、缓存有效性**视为共享的运行时状态，让三个组件协同工作：
  1. **协作调度器**（Cooperative Scheduler）——唯一的 GPU 准入点；
  2. **版本感知的 KV 缓存管理器**（Version-aware KV-cache Manager）——负责缓存有效性、热前缀统计、刷新与驱逐；
  3. **多智能体模型运行时**（Multi-agent Model Runtime）——执行推理和训练、感知内存压力、维护智能体身份与适配器归属。
- **关键技术细节**：

### 协作调度器（§4）
- 将所有 GPU 模型操作统一建模为任务（task），包含类别、优先级、所需适配器状态、估计耗时、估计峰值内存、最长不可让出区间、效用等元数据。
- 采用**指数移动平均（EMA）**在线校准任务耗时估计：`E_z^(i) = (1-α_z)E_z^(i-1) + α_z v_i`（当无历史时直接采用新观测值）。
- **前台严格优先**：前台推理队列非空时，不启动新的后台任务；已运行的后台任务通过**协作式中断**在安全边界（mini-step、优化器提交、适配器发布点）让出 GPU，避免任意 kernel 抢占，将前台阻塞时间限定为“距下一个安全边界”。
- **后台准入条件**：`m̂(x)+M_reserve ≤ M_free` 且 `ŷ(x)+δ ≤ W_bg`；若有工具/子任务截止时间 `D_tool`，还需满足 `t̂(x)+δ ≤ D_tool - t_now`。在所有可准入任务中，按“前台安全效用”选择最优任务。

### 版本感知的 KV 缓存管理器（§5）
- **智能体作用域 KV 身份**：缓存复用键为 `κ = (token span, context namespace, adapter, adapter version)`；只有 token 前缀、上下文命名空间、逻辑适配器、适配器版本全匹配才可复用。智能体身份作为来源元数据而非硬性键，避免无法共享完全相同的序列。
- **热前缀统计**：前缀热度 `H_P(p)` 与适配器热度 `H_A(ν)` 分别用衰减统计更新，联合热度分数：
  ```
  H_KV(e) = (ε + H_P(p)) * (ε + H_A(ν)) * (1 + α_L * min(L_e, L_max)/L_max)
  ```
  - 乘法形式保证只有前缀和适配器都热时记录才有价值；
  - 长度项奖励更长可复用跨度，但有上限。
- **保留优先级**：`Π_keep(e) = H_KV(e) · Ĉ_recompute(e) / max(1, B_e)`，值越低越适合驱逐；驱逐顺序按 `Π_keep` 升序、同值时占用更大者优先。
- **过期覆盖预填充（Stale-coverage Prefill）**：适配器新版本训练完成后先进入 staged 状态，KV 管理器选择热前缀生成有界预填充块作为后台任务；只有调度器准入才执行。目的：避免适配器发布后首个前台请求重建长前缀，降低 TTFT。
- **基于 Radix 树的索引**：分离逻辑有效性与物理驻留状态，支持共享 token 路径不重复存储。

### 多智能体模型运行时（§6）
- **跨智能体预填充（Cross-Agent Pre-Prefill）**：利用多智能体通信结构（如一个智能体的输出将被另一个智能体消费）生成投机性预填充提案。预测需求信号：
  ```
  D_ma(c) = ρ_c * (1 + β_s * log(1 + s_c)) * min(Δc, M_max)/M_max
  ```
  该信号并入前缀热度和适配器热度；最终优先级为 `Π_xpre(c) = D_ma(c) · H_KV(e_c) · Ĉ_prefill(e_c)`。
- **内存压力卸载请求**：训练等后台任务预估内存不足时，运行时向 KV 管理器发起卸载请求，由后者按保留优先级将冷条目卸载到主机内存。内存压力可见于调度器，不是局部缓存策略可解决。

## 6. 主要结论与发现

- **调度有效性**：前台优先策略相比 FIFO 将前台队列等待 p95 降低 3.1×（从 4.403s 降至 1.433s）、p99 降低 3.4×；相比轮询策略，p99 降低 2.1× 且训练提交数多 1.6×（34 vs 21）。
- **协作抢占**：与不可抢占训练相比，p95 队列等待和 TTFT 均降低 1.55×（队列 p95 从 4.140s 降至 2.676s，TTFT p95 从 4.247s 降至 2.749s），训练吞吐量仅损失 21.6%（346.8 → 271.8 步/小时），累计训练阻塞时间降低 2.6×。
- **与 vLLM 全 LoRA 睡眠/训练/唤醒路径对比**：LOCAL 将 p95 队列等待降低 5.9×（前台优先）、12.8×（轮询）、6.3×（FIFO），核心在于细粒度任务准入而非秒级睡眠/唤醒窗口。
- **过期覆盖预填充**：发布后首次命中预填充 p95 降低 22.0%、p99 降低 25.6%，缓存命中率 p50 从 0 提高到 0.210。
- **跨智能体预填充**：TTFT 均值降低 38.0%、p95 降低 12.8%、p99 降低 21.9%，且额外预填充未显著阻塞前台（阻塞时间仅 0.018s）。
- **内存压力**：在 512–1280 KV 页配置下全部完成工作负载，峰值内存 21.6–23.5 GB，未出现 OOM 或适配器发布失败；页数从 512 增到 1024 使队列 p95 从 1.312s 降至 0.850s（1.5×），说明内存配置影响延迟是通过调度准入实现的。

## 7. 优点

- **问题定义清晰**：准确地指出现有推理系统“权重稳定”假设与 RL 系统“资源分离”假设在设备端连续学习场景中的结构性失效。
- **协同设计而非局部优化**：将调度、KV 缓存、模型运行时三者解耦但共享状态，让适配器版本、任务优先级与缓存有效性全局一致，避免了独立子系统互相破坏。
- **理论/工程细节扎实**：任务模型、EMA 估计、安全边界定义、KV 有效性键、热前缀联合热度公式、预填充与跨智能体预填充的优先级计算均有明确数学形式，便于复现。
- **实验设计注重尾延迟**：不仅报告均值，还系统报告 p95/p99，并分析队列阻塞归因，能够区分“平均表现不错但尾部恶劣”的情况。
- **与工业基线对比**：加入 vLLM 全 LoRA 睡眠/训练/唤醒路径对比，证明 LOCAL 的细粒度任务可见性带来实际增益，而不仅是单点优化。
- **强调不出错性**：过期预填充不绕过调度器、训练中断不暴露部分适配器状态、KV 复用严格检查版本——在正确性约束下优化性能。

## 8. 不足与局限

- **实验覆盖单一**：仅使用 tau-bench 零售任务和 xLAM-7b-r 模型，未测试其他领域、其他模型系列（如更小模型、量化模型、更长上下文）与更大适配器数量。
- **硬件范围窄**：只在单张 RTX 3090 上验证；结论未必直接推广到更低规格设备（如手机端、边缘 CPU）或更高规格多卡环境。
- **长期稳定性未验证**：运行规模为 24 个任务，会话长度有限；论文自述“剩余工作包括更长多智能体会话、更大适配器群体和策略级学习质量”。
