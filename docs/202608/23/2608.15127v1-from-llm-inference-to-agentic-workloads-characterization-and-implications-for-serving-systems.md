## 摘要
智能体应用正在将AI服务从孤立的模型推理转变为长时间运行的工作负载，其中LLM协调工具、环境和持久状态。然而，这些工作负载的系统行为——延迟、成本和瓶颈出现的地方——仍然缺乏清晰的刻画，使得服务系统依赖于为传统推理构建的假设。我们提出了AgentSysBench，一个包含十个代表性智能体应用和统一系统级插桩的基准测试套件与测量工具。在受控部署和生产环境追踪中，我们识别出六个将智能体工作负载与传统LLM服务区分开来的属性：(1) 执行是重量级且有状态的，非LLM组件在10个应用中的5个中主导延迟，沙箱工作集内存峰值达到每个会话28 GB；(2) 应用组合了具有异构资源亲和性的组件——GPU绑定的推理、内存绑定的检索、CPU绑定的沙箱——其任务延迟差异高达32倍；(3) 瓶颈在请求、模型和部署之间转移；(4) 生产会话在活动步骤之间保持空闲状态数分钟到数小时；(5) 控制平面开销——辅助LLM调用以及工具模式和观察带来的上下文开销——排挤了生产性计算和上下文；(6) 来自三个应用的生产追踪揭示了搜索查询和网页抓取中的大量跨请求冗余，暴露了巨大的缓存机会。四项设计探索证明了这些发现是可操作的：任务感知服务将延迟降低29%–40%，通信感知放置降低高达4.5倍，状态卸载减少了4.6倍的内存使用，工具结果缓存消除了35.2%的冗余搜索调用并节省了19.3%的总搜索延迟。

## Abstract
Agentic applications are shifting AI serving from isolated model inference to long-running workloads in which LLMs coordinate tools, environments, and persistent state. However, the system behavior of these workloads---where latency, cost, and bottlenecks arise---remains poorly characterized, leaving serving systems to rely on assumptions built for conventional inference. We present AgentSysBench, a benchmark suite and measurement toolkit with ten representative agentic applications and unified systems-level instrumentation. Across controlled deployments and production traces, we identify six properties that distinguish agentic workloads from conventional LLM serving: (1) execution is heavyweight and stateful, with non-LLM components dominating latency in 5 of 10 applications and sandbox working-set memory peaking at 28 GB per session; (2) applications compose components with heterogeneous resource affinity---GPU-bound inference, memory-bound retrieval, CPU-bound sandboxes---whose task latencies diverge by up to 32x; (3) bottlenecks shift across requests, models, and deployments; (4) production sessions hold state idle for minutes to hours between active steps; (5) a control-plane tax---auxiliary LLM calls and context overhead from tool schemas and observations---crowds out productive compute and context; and (6) production traces from three applications reveal heavy cross-request redundancy in search queries and web fetches, exposing a large caching opportunity. Four design explorations demonstrate that these findings are actionable: task-aware serving reduces latency by 29--40%, communication-aware placement by up to 4.5x, state offloading reduces memory usage by 4.6x, and tool-result caching removes 35.2% of redundant search calls and saves 19.3% of aggregate search latency.

## 1. 论文的核心问题与整体含义

**研究动机与背景：**
- 智能体（Agentic）应用正将 AI 服务从孤立的单次模型推理转变为长时间运行的工作负载：LLM 不再只生成文本，而是需要调用工具、检查外部环境、更新持久化状态，并在中间结果上反复迭代。
- 一个用户请求可能触发检索、代码执行、浏览器/GUI 交互、API 调用和数十次模型调用，由此产生的会话级工作负载（称为“agentic workloads”）在延迟、成本与瓶颈来源等方面与传统 LLM 推理有本质区别。
- 但现有服务系统仍基于传统 LLM 推理的假设进行设计（以模型推理为唯一成本中心），且已有研究存在三个明显空白：一是智能体服务系统只研究少量应用（1-3个）且假设不兼容；二是能力基准（如 SWE-bench、WebArena）只测任务完成度，几乎不记录延迟分解、资源画像、状态足迹等系统级信息；三是已有的测量研究均运行在单一固定服务栈上，未将硬件分配、组件放置或生产条件视为变量。
- 核心问题：**智能体工作负载的系统行为（延迟、成本、瓶颈到底出现在哪里）缺乏系统性表征，导致服务系统无法做出有依据的设计决策。**

**整体含义：**
- 该论文首次提供了一套可复现的、覆盖十个应用并统一插桩的基准套件 AgentSysBench，结合受控实验与生产追踪，系统地揭示了智能体工作负载与传统 LLM 推理的本质差异，为下一代 Agentic Serving 系统的设计提供了经验基础与可操作的优化方向。

## 2. 论文提出的方法论

**核心思想：**
- 将智能体应用视为一个执行图（execution graph），包含链式、分支、循环和并行子任务；每个用户请求执行该图的一条路径，记录为一条执行轨迹。
- 用四元组刻画工作负载：𝑊 = ⟨𝑅, 𝑇, 𝑀, 𝑂⟩（请求分布、工具/环境集、模型选择、编排结构），用三元组刻画服务系统：𝑆 = ⟨𝐻, 𝐶, 𝐴⟩（硬件资源、组件服务机制、部署架构），测量结果视为两者交互的产物：𝑌 = Φ(𝑊, 𝑆)。
- 该建模方式的核心价值在于：只有同时指定并控制 𝑊 和 𝑆，才能正确归因瓶颈是来自工作负载还是服务基础设施。

**AgentSysBench 三大组件：**

1. **应用集合（满足需求 R1 工作负载代表性）**：选择 10 个覆盖不同执行模式的应用，横跨请求分布、工具/环境类型、模型选择与编排结构四个维度。包括：RAG、HuggingGPT、DeepResearch、Mini-SWE、Codex、WebAgent、GUIAgent、Claude Code、Openclaw、Pi-AutoR。

2. **模块化服务栈（满足需求 R2 可控的服务系统因素）**：
   - 工作负载生成器控制请求分布（一对一、泊松、追踪驱动到达）；
   - 编排器持有控制流逻辑并调用工具和模型服务；
   - 所有组件打包为 Docker 容器，支持按需改变硬件分配（𝐻）、组件服务机制（𝐶）与部署架构（𝐴）；
   - 核心原则是“因素隔离”：改变一个因素时尽量保持其他因素不变。

3. **测量工具包（满足需求 R3 统一组件级插桩）**：
   - 白盒应用通过轻量级注解采集事件；
   - 黑盒第三方应用通过 LLM/工具代理和沙箱钩子追踪；
   - 统一规范化每条操作记录（操作类型、组件、起止时间、I/O 大小、token 用量、成本）；
   - 使用 cAdvisor、DCGM Exporter 和 Prometheus 收集容器与 GPU 的 CPU/内存/网络/磁盘使用率时间序列。

**生产追踪补充（满足需求 R4）**：受控实验无法揭示真实用户思考时间、长期空闲但有状态的会话、跨请求冗余等现象，因此论文还分析了三个已部署应用的 24 小时生产日志。

## 6. 论文的主要结论与发现

论文通过受控实验和生产追踪归纳出六个区分性属性：

1. **执行重量级且有状态（非 LLM 主导）**：端到端延迟从秒级到数小时（如 Mini-SWE 任务经常超过 10 分钟，Pi-AutoR 可达数小时）；在 10 个应用中有 5 个的非 LLM 组件主导关键路径延迟；沙箱工作集内存峰值达 28GB/会话；KV cache 单会话可达 11GB；token 消耗超线性增长；单会话数据 I/O 可达数十 MB；非 LLM 基础设施在工具密集型应用中主导货币成本（如 Pi-AutoR 中沙箱成本占 99%+）。

2. **跨栈异构性**：单个应用内部，GPU 绑定推理、内存绑定检索、CPU 绑定沙箱并存；同一组件的不同任务延迟相差达 32 倍；同一任务在单个执行内也相差 30 倍以上；异构任务共享资源时产生队头阻塞、共批干扰和共享资源争用三类性能干扰（分别带来 7.1-35.7×、1.38-1.80×、1.22× 的退化）。

3. **瓶颈转移**：瓶颈随请求类型、输入大小、工具集、模型速度、编排结构、硬件分配、服务机制与部署架构而变。例如：模型从 Flash 换成 Pro 可使 DeepResearch 瓶颈从嵌入转向 LLM；批量大小从 1 调到 4 可使 GUIAgent 瓶颈从工具转向 LLM 推理；网络传输在分布式部署下可占 67.5% 的延迟。结论：静态画像无法追踪瓶颈，需要在线按请求自适应。

4. **生产会话长时间“空闲但存活”**：生产会话中位活跃执行时间仅占生命周期的 20%；70% 的会话执行时间不到生命周期的一半；空闲间隔从数秒到数小时（多在 1-10 分钟）。这些会话持有沙箱、终端上下文与 KV cache，既未完成也不消耗计算资源，需要区分“等待”与“完成”状态。

5. **LLM 控制平面开销**：工具模式、原始观察和多次用户交互的历史在 261 步会话末尾占输入的 84.3%；上下文压缩事件平均消耗 176K 输入 token、生成 5K 输出 token、耗时 156 秒；59.4% 的会话经历至少一次前缀缓存驱逐，驱逐贡献了 55.9% 的 cache-create token 与 31.5% 的货币成本。

6. **跨请求冗余**：搜索应用中 27% 的去重查询贡献了 67.3% 的搜索调用；URL 抓取中 24% 的去重 URL 贡献了 64% 的抓取调用。10 分钟 TTL 的缓存可消除 35.2% 的搜索调用并节省 19.3% 的总搜索延迟。

**设计探索的效果验证：**
- 任务感知服务：三种负载下延迟分别降低 29%、38%、40%；
- 通信感知放置：低负载 2.8×、高负载 4.5× 端到端加速；
- 状态卸载：平均内存降低 4.6×、峰值内存降低 2.1×，延迟增加小于 0.5%；
- 工具结果缓存：搜索调用减少 35.2%、总搜索延迟节省 19.3%；URL 抓取调用减少 11.65%、总抓取延迟节省 16.5%。

## 7. 优点

1. **系统化的基准设计**：用显式的工作负载模型（𝑊）和服务系统模型（𝑆）驱动应用选择与实验控制，使测量结果可以归因，避免将服务基础设施造成的瓶颈误归于工作负载结构。
2. **统一测量协议**：白盒注解与黑盒代理双路径产生统一 trace 格式，使得跨应用的延迟/成本/状态对比在方法上可比——这是现有能力基准（只测任务完成度）和单一栈测量研究都无法做到的。
3. **受控实验 + 生产追踪互补**：受控实验揭示因果机制（瓶颈转移、干扰机制），生产追踪揭示仅存在于真实部署的现象（空闲间隔、跨用户冗余、压缩与缓存驱逐），两者交叉验证了核心结论。
4. **多维测量覆盖**：延迟、token、状态（性能状态/持久状态/工作集）、I/O、货币成本五个维度都做量化，每个维度给出可操作的含义。
5. **设计探索紧贴发现**：四项优化设计都有清晰对应的表征结论（任务感知↔异构性；通信感知↔数据 I/O；状态卸载↔空闲间隔；工具缓存↔跨请求冗余），实现了从“理解”到“行动”的完整闭环，且验证了机制的有效性。

## 8. 不足与局限

1. **生产追踪覆盖面有限**：仅分析了 3 个应用的单日 24 小时快照（无可重复长时间跨度），且这些应用都来自较少类型，对更广泛的生产部署（如复杂多智能体协作、视频/音频多模态智能体）的代表性有限。
2. **模型与服务的混杂变量**：不同应用使用不同模型（自部署 DeepSeek-V4 与云端阿里 API），且云端 API 的引擎、批处理和缓存策略未知，跨应用对比可能包含模型服务配置差异的影响。
3. **受控实验环境偏理想化**：默认部署使用共享内存虚拟网络（非真实物理网络），容器通信不经过真实网卡，可能低估网络序列化/传输时延；对网络瓶颈的结论需在物理网络下进一步确认。
4. **成本估计为近似值**：货币成本基于公开云定价的估算，未考虑折扣、预留实例、真实计费粒度，沙箱和搜索的真实价格可能与估算存在偏差。
5. **部分实验规模较小**：生产追踪的核心现象（空闲间隔、冗余）虽在统计上有效，但干扰验证实验（如 8 个沙箱共享 128 核）等仅用了较小规模的并发数，尚未覆盖超大规模集群的场景。
6. **缓存策略的局限性**：工具结果缓存仅评估了精确匹配（query/URL 级），未考虑语义相似查询的近似匹配、新鲜度敏感的场景（如新闻/金融数据）以及不同租户间缓存隔离的合规问题。
7. **优化方案的完整性受限**：四项设计探索独立验证，没有组合成完整系统，未说明它们之间的相互作用；状态卸载的最优阈值依赖人为固定阈值，未建模为自适应策略。
8. **开源状态未验证**：论文声明将开源 AgentSysBench，但没有提供体验地址或仓库链接，无法独立复现验证。
