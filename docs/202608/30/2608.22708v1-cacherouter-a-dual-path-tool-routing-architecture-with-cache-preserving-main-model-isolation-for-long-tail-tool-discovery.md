## 摘要
大型语言模型系统中的工具使用面临结构性权衡。渐进式披露通过仅显示当前任务相关的工具来保持提示词简短，而提示词缓存则奖励跨调用保持固定的请求前缀；可见工具列表的任何更改都会使缓存的前缀失效。本文将这一权衡视为请求架构问题，提出了一种双路径路由设计，将工具选择与工具交付分配给不同通道。主模型始终看到一组小而固定的核心工具，因此其请求头部在多次调用中保持不变；所有其他工具通过独立的路由通道访问，其中路由器子模型搜索完整工具列表、选择一个工具、执行它并返回结果。工具注册从源代码自动完成并支持运行时更新，因此工具集可以在不修改主模型请求前缀的情况下扩展。该设计泛化了渐进式披露：能力通过路由通道披露，而主模型的前缀保持稳定。一个原型实现已在55个功能性查询和30轮对话上进行了测试；令牌级缓存命中率达到90.99%和95.2%，在DeepSeek的定价下，输入成本降至无缓存基线的约12.0%和8.0%，其中缓存命中的输入令牌成本约为缓存未命中令牌的1/30。

## Abstract
Tool use in LLM systems faces a structural trade-off. Progressive disclosure keeps the prompt small by showing only the tools relevant to the current task, while prompt caching rewards a request prefix that stays fixed across calls; every change to the visible tool list invalidates the cached prefix. This paper treats the trade-off as a problem of request architecture and proposes a dual-path routing design that assigns tool selection and tool delivery to separate channels. The main model always sees a small, fixed set of core tools, so the head of its request is unchanged across calls; all other tools are reached through an independent routing channel, in which a router sub-model searches the full tool list, selects one tool, executes it, and returns the result. Tool registration is automated from source code and supports runtime updates, so the tool set can grow without modifying the main model's request prefix. The design generalizes progressive disclosure: capabilities are disclosed through the routing channel, and the main model's prefix stays stable. A prototype implementation was exercised on 55 functional queries and a 30-turn dialogue; token-level cache hit rates reached 90.99% and 95.2%, cutting input cost to about 12.0% and 8.0% of a no-cache baseline under DeepSeek's pricing, where cache-hit input tokens cost roughly 1/30 of cache-miss tokens.

## 论文总结：CacheRouter——面向长尾工具发现的缓存保持双路径工具路由架构

### 一、核心问题与整体含义

- **研究动机**：大语言模型（LLM）作为智能体调用外部工具（如 MCP 协议下的工具）已成为常态，但当工具数量从几十个增长到成百上千时，系统面临一个**结构性冲突**：
  - **渐进式披露**（Progressive Disclosure）只向主模型展示当前任务相关的工具，以保持上下文精简，但**每次工具列表变化都会导致请求前缀变化**。
  - **提示词缓存**（Prompt Caching）依赖请求前缀的**跨调用稳定性**——前缀一旦变化，缓存即失效，导致 Token 费用大幅上升（如 DeepSeek 缓存命中 Token 价格约为未命中的 1/30）。
- **根本矛盾**：工具选择（task 需要哪些能力）与工具交付（哪些工具定义进入请求）被耦合在**同一条请求通道**中，导致“工具集越灵活，缓存越不稳定”。
- **论文立场**：应将工具选择与工具交付**解耦为两条独立通道**——主模型保持固定的小型核心工具集（前缀稳定），长尾工具通过独立路由子模型按需发现和执行——从而在不牺牲缓存效率的前提下，实现大规模动态工具生态系统的可持续扩展。

### 二、方法论：核心思想、关键技术细节与算法流程

**1. 核心思想：双路径工具路由架构（Dual-Path Tool Routing）**

- 主模型始终只看到**固定的小型核心工具集（C）**，其请求前缀跨调用保持不变。
- 长尾工具（T\C）通过**独立的 INTERNAL_ROUTER 路由子模型通道**发现、筛选、执行，并将结果以 JSON 字符串形式返回主模型。
- 动态工具的定义、描述和参数信息**永不进入主模型的请求前缀**，实现“生态系统可变，核心请求路径稳定”。

**2. 关键技术细节**

- **占位符工具（Placeholder Tool Triage）**：
  - 在第一轮意图分流阶段引入固定结构的占位符工具 `TOOL_WHICH_WOULD_BE_USED`，其定义在系统运行期间**永不改变**，且禁止实际调用（tool_choice="none"）。
  - 双重功能：**缓存锚点**（第一轮工具段前缀结构性恒定）+ **意图引导信号**（描述外部能力边界，帮助模型区分纯知识问题与需要工具的任务）。
- **INTERNAL_ROUTER 路由子模型**：
  - 定义为主模型固定工具视图中的一个伪工具，主模型判定核心工具不足时调用它。
  - 路由协议五阶段：**上下文压缩**（≤800字符任务摘要）→ **全量工具列表刷新**（不受主模型包可见性限制）→ **四阶段候选过滤** → **路由子模型一次受限工具调用**（2000 Token 生成上限）→ **结果返回**。
  - 路由子模型是**无状态、轻量、故意有损**的“快速工具调用者”。
- **四阶段过滤管线**：
  - **黑名单过滤**（硬性安全约束）→ **白名单过滤**（部署场景访问控制）→ **Top-K 语义预选**（基于查询词在工具元数据中的命中率，k=5）→ **黄名单过滤**（缓存优先策略：软避开核心工具集中的工具，但保留最相关的核心工具作为回退候选）。
  - 最终候选集：|T⁽⁴⁾| ≤ 5，满足 T⁽⁴⁾ = F_Y(F_K(F_W(F_B(T))))。
- **AST 自动注册与热重载**：
  - 启动时通过 Python AST 静态解析工具脚本中的 argparse 参数定义，自动生成统一 MCP JSON Schema；静态无法覆盖时用运行时反射补充。
  - 通过文件快照轮询（5秒）检测仓库变化，原子替换工具注册表，实现**运行时热重载**而无需重启服务。
- **技能自举（Skill Bootstrapping）**：
  - 当现有工具无法完成任务时，系统利用已有代码执行能力生成新的技能脚本和元数据，合并到独立工具包（如 `other`）中。
  - 新技能**默认不在主模型可见集内**，通过路由机制在后续任务中按需发现，不破坏缓存前缀。

**3. 算法流程（文字说明）**

- 算法 1（查询处理管线）：第一轮用压缩历史 + 占位符工具做意图分流 → 若标记为直接回答则返回；否则进入工具执行循环（主模型看到 C ∪ {INTERNAL_ROUTER}）→ 核心工具直接执行；路由伪工具触发算法 2 → 检测深度思考信号（状态异常/超60秒/≥4轮连续工具调用）→ 重规划或回退回答。
- 算法 2（路由子通道）：获取全量注册工具 → 依次执行黑名单、白名单、Top-K、黄名单四阶段过滤 → 子模型一次工具调用 → 执行并返回 JSON 结果，或返回重试信号。
- **缓存不变性保证**：三种运行时事件（运行时添加工具、生成新技能、网关重启）都不会改变主模型可见的核心工具集 C，主模型请求前缀仅随历史**追加式增长**（append-only），天然满足缓存前缀复用条件。

### 七、优点

1. **问题定位精准**：将工具调度与提示缓存的矛盾抽象为“工具选择与工具交付同通道耦合”的结构性问题，提出架构级解法而非调参式修补。
2. **架构设计优雅**：双路径 + 占位符 + 四阶段过滤 + 热重载 + 技能自举，构成完整闭环，分离了关注点（主模型专注推理，路由专注发现，网关专注注册，仓库专注持久化）。
3. **缓存意识贯穿设计**：占位符工具作为缓存锚点、黄名单作为缓存优先策略、核心工具集作为可见性边界，每一层都考虑了前缀稳定性。
4. **工程实用性强**：AST 自动注册 + 运行时热重载 + 技能自举解决了大规模工具运维中的实际痛点，且建立在 MCP 标准协议之上，可叠加于现有框架。
5. **实验设计覆盖关键路径**：路由触发对比（A/B/C 三组）、网关冷启动对比、不可回答回退、技能合并质量等实验维度较为全面。

### 八、不足与局限

1. **检索质量有限**：Top-K 预选基于关键词字面命中率，对语义相关但字面无重叠的工具召回不足（论文自认）。
2. **路由开销**：路由子模型增加了一次额外推理调用，带来延迟和推理成本；复杂任务需主模型多次调用 INTERNAL_ROUTER，产生多次主–子模型往返。
3. **封闭式知识的浪费**：30 轮实验中 14 个未命中查询即使属于可闭卷回答的常识/算术题，仍进入完整工具循环（如 Q28“一小时多少分钟”消耗 24,577 tokens），分流策略有待优化（提出“先直接回答，工具循环作为回退”的改进方向）。

5. **单提供商依赖**：仅验证 DeepSeek API 行为，未覆盖其他提供商（如 OpenAI）的缓存机制差异。
6. **缓存命中率受外部因素影响**：命中率还依赖于服务器端缓存淘汰策略和缓存生命周期，架构仅保证结构性前缀稳定，不承诺具体命中率。
7. **并发一致性未强保证**：热重载机制本身已验证，但并发更新下在途请求的一致性保证留待未来工作。
