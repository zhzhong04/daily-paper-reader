Abstract 

Agentic workloads are a major source of LLM inference demand. Existing prefill–decode (PD) disaggre-gated serving systems offer limited flexibility for runtime adaptation of compute allocation and KV cache management, and rely on coarse signals that only partly capture the diverse and dynamic agent workload. These limitations lead to load imbalance between prefill and decode nodes and eviction of KV caches that agents will reuse. We present E VOLVING INFRA , an agent-adaptive serving framework that adapts compute allocation to agent workloads and KV cache management to agent context management at runtime. We de-couple compute allocation from key–value (KV) cache management, allowing nodes to switch efficiently between prefill and decode. Building on this design, an online planner matches the PD split to workload composition, while an agent-aware distributed KV manager guides cache eviction and transfer with sig-nals from agent context management. Across coding, math, and computer-use tasks with GLM-5.2 and Kimi K2.6 on up to 256 GB300 GPUs, E VOLVING INFRA reduces mean end-to-end request latency and P95 TTFT by up to 4.1 × and 14 × over Dynamo, NVIDIA’s production framework.

# 1 Introduction 

Agentic workloads account for a large and growing share of LLM inference [9, 30], spanning software engineering [22], math research [38], and computer use [5]. Agents execute these tasks in steps, each consisting of a model request and the tool calls it triggers, with harnesses updating the context between steps. Successive requests therefore typically share long prefixes, creating opportunities for key–value (KV) cache reuse across consecutive steps. These workloads place diverse demands on prefill and decode resources. Differences in tasks, harnesses, and models lead to different amounts of uncached input and generated output per request, making some agent workloads prefill-heavy and others decode-heavy (Figure 2a). The agent workload composition, i.e., the proportions of different agent workloads served by a cluster, also varies over time. A production study of 11.7 million requests finds that user-triggered task starts follow workday rhythms, whereas automatically triggered task starts are more evenly distributed throughout the day [79]. Meanwhile, within an agent, context management changes which prefixes subsequent requests can reuse. Harnesses compact histories, fork and create sub-agents [7, 47]. Each fork or sub-agent starts a new branch , a context that has its own sequence of requests and remains active until it finishes. A branch waiting for a tool or sub-agent may reuse its existing prefix after a long pause, whereas compaction can remove recently accessed history from the subsequent requests of a branch (Figure 2c). Access recency alone thus does not reveal which cached prefixes remain useful to active branches. Serving agents efficiently thus requires adapting compute allocation to diverse agent workloads and their shifting composition, and KV cache management to agent context management. Production systems [40] serve agentic workloads with PD disaggregation [80] and manage compute and memory with three components. A planner determines the compute allocation between prefill and decode by assigning nodes to each phase [43, 69]. A cache-aware router routes each request to a node with matching prefix KV [45, 58]. A memory pool shares and evicts KV across nodes [50, 72]. However, agentic workloads expose three problems in existing systems. 

Costly phase switches. Each adaptation of the compute allocation switches nodes between phases, and such switches are expensive in existing systems. Some [43] relaunch serving workers to change their phase, which takes minutes and removes the node from service during the switch. Others switch without a restart [69] but strand the node’s cached KV, forcing later requests to recompute their prefixes. In our measurements on Claude Code traces, Dynamo takes 681 s per switch on average, while Arrow loses 55.5% of the available KV reuse over 34 in-place switches (Figure 3a). 

Misestimated compute demand. A PD split profiled offline for each agent workload is costly to obtain and cannot follow the shifting workload composition. Even the best static split loses up to 24% of throughput in some periods relative to the best split of each 10-minute window (Figure 2b). Online planners also misestimate demand. They adjust the PD split using coarse signals such as queue depth [43] or predicted time to first token (TTFT) [31]. Context management, such as spawning several sub-agents at once, can create short bursts of prefill work that perturb these signals and trigger costly phase switches without sustained throughput gains. Some planners also estimate prefill work from the full input length [69], ignoring KV reuse and overestimating the number of prefill nodes needed (Figure 3b). 

Misjudged KV reuse. Existing systems misjudge KV reuse when they route requests and evict KV. Requests of the same branch share long prefixes. Cache-aware routers [58] concentrate these requests on the few prefill nodes holding their prefixes, overloading them and raising P95 TTFT. Routers [45] that trade cache locality for load balance can route requests to nodes that must recompute their prefixes. The memory pool avoids this recomputation, but its KV fetches can delay prefill and leave duplicate copies in the pool (Figure 3c). The memory pool and node caches typically evict KV in least recently used (LRU) order [50, 78]. They thus drop the KV of branches waiting for tools, sub-agents, or users while keeping the history replaced by compaction, the contexts of finished sub-agents, and duplicate copies left by KV transfers. 2Two limitations underlie these problems. First, compute allocation and KV cache management remain coupled. Engines index cached KV in local state. Switching a node from prefill to decode thus discards or strands its cached KV. Shared KV pools avoid this coupling, but keep the allocation fixed or change it by relaunching nodes. Second, the three components rely on coarse signals, such as request latency, input lengths, and access history, which do not fully reveal the agent workload or context management. To our knowledge, 

Evolving Infra is the first agent-adaptive serving framework, adapting compute allocation to diverse agent workloads and their shifting composition, and KV cache management to agent context management at runtime. We make three contributions. 

Decoupled compute allocation and KV cache management. To reduce the cost of phase switches, 

Evolving Infra separates the phase of each node from the KV storage. Each node supports both phases, and the planner reassigns its phase at runtime without a restart. KV resides in a shared pool formed by the host memory of all nodes, and a cluster-wide KV directory records the number of active branches that reference each copy. Neither the pool nor the directory is tied to node phases, and a phase switch leaves the KV readable by all nodes. The directory updates these counts in response to agent context management and KV transfers between nodes (Section 4). 

Agent-adaptive compute allocation. To precisely size the PD split for the agent workload composition, 

Evolving Infra learns iteration-time models of prefill and decode online, without offline profiling (Section 5.1). The prefill model incorporates KV reuse, enabling accurate estimation of prefill time on agentic workloads. The planner evaluates these models on the average work of a request over each planning window. These averages characterize the workload itself rather than the momentary load of the cluster. The planner switches only when the predicted throughput gain of a new split persists across the window, which keeps short bursts from triggering switches (Section 5.2). 

Agent-adaptive KV cache management. To keep the reusable KV of active branches while balancing the load of prefill nodes, Evolving Infra routes requests and evicts KV according to agent context management. It fetches remote KV asynchronously while a request is queued, which allows the router to send each prefill request to the node with the shortest predicted TTFT. The directory shows that no active branch references replaced histories, the contexts of finished sub-agents, or duplicate copies left by transfers, and 

Evolving Infra evicts this KV first (Sections 4.2, 4.3, and 5.3). We evaluate Evolving Infra on coding, computer-use and math agents, serving GLM-5.2 and Kimi K2.6 on 36 GB300 GPUs. When serving a single agent workload at a stationary load , Evolving Infra 

achieves up to 2.7 × the throughput of Dynamo and up to 38% more than the best static split. Reduces the mean end-to-end (E2E) request latency by up to 4.1 × and P95 TTFT by up to 14 × relative to Dynamo (Figure 1). For a shifting workload composition from math to computer-use agents, Evolving Infra 

adapts the PD split online, achieving 2.1 × the throughput of Dynamo and 28% more than the best static split (Section 6.3). 

# 2 Background 

# 2.1 Diverse and dynamic agentic workloads 

Workload composition. An agent solves a task in steps orchestrated by a harness. Each LLM request appends new tokens from tools or the harness to a prefix whose KV was computed in earlier steps. The inference engine fetches the cached prefix KV, prefills the uncached tokens, and decodes the output tokens. The amounts of prefill and decode work differ across tasks, harnesses, and models. For example, the workload of a computer-use agent on OSWorld is prefill-heavy because each step appends a new screenshot to the context, whereas the workload of a math agent on Putnam is decode-heavy because each request generates a long reasoning trace (Figure 2a). The best PD split thus differs across agent workloads, and finding it requires costly offline profiling (Section 6.4). The workload composition of a cluster also changes over time. User-triggered agent tasks starts follow workday rhythms, whereas automatically triggered tasks starts are more evenly distributed throughout the day [79]. In production LLM serving, the mean input length of requests to one model rises by 13% from midnight to afternoon, while the mean output length falls by 18% [70]. The best PD split thus shifts over time (Figure 2b). The PD split must therefore change over time to avoid load imbalance between prefill and decode nodes. 3Context management. The harness typically extends the context of a branch with model outputs and tool results, and consecutive requests therefore share prefixes. Harnesses also manage context through forking, sub-agent spawning, and compaction. Forking creates new branches that reuse the current context, while spawning a sub-agent starts a separate branch with a new context. Compaction replaces the history of a branch with a summary [6, 47]. Once compaction completes, even recently accessed KV of the replaced history is no longer needed. In contrast, KV can remain idle during a long wait for tools or sub-agents, yet still be reused when the branch resumes. In GitHub Copilot, the median gap between consecutive turns is 172 s [30]. Whether KV will be reused thus depends on whether an active branch still includes it in its context, not merely on access recency. Together with the shift in workload composition, these dynamics challenge the planner, the router, and the memory pool of existing serving systems, which the rest of this section reviews. 

# 2.2 Existing PD disaggregated serving systems 

Engines. By default, vLLM and SGLang fix the phase of each engine at launch in PD disaggregation mode [53, 64]. For example, each SGLang engine builds only the scheduling loop and KV transfer path of its own phase. A prefill engine queues requests and sends their KV to decode engines, whereas a decode engine reserves KV slots, receives KV, and captures CUDA graphs for decoding. Each engine also indexes cached KV in local state, such as the prefix tree of a prefill engine. A phase switch thus requires relaunching the engine with a new configuration and discards its cached KV. 

Planners. A planner sets the PD split by switching nodes between prefill and decode as compute demand changes. Phase switches in existing planners are costly. A switch in Dynamo relaunches the engine and keeps the node out of service for minutes [43]. A switch in Arrow [69] and xLLM [31] reassigns the node to the other phase without a relaunch but strands its cached KV. The split also follows coarse signals, namely prefill queue depth and decode KV utilization in Dynamo [43], and TTFT and per-token latency targets in Arrow, xLLM, and Llumnix [32]. These planners predict TTFT from the full input length [31, 33, 69], which counts cached prefixes as prefill work and overestimates prefill demand. Sub-agents spawned at once by the harness create a short burst of requests. The burst raises queueing delay and TTFT but leaves the long-term balance between prefill and decode workloads unchanged. These signals thus misestimate demand and trigger frequent phase switches, each costing minutes of downtime or the cached KV of the switched node (Section 3). 

Routers. A router assigns each request to a prefill and decode node. For prefill, the SGLang Model Gateway and the Dynamo router weigh prefix-cache hits against node load [45, 58]. The Dynamo router keeps a cluster-wide prefix tree that records which KV blocks each node holds, and the engines update the tree through KV events [45]. For each request, the router uses this tree to count the prefix blocks that each node already holds. These routers choose where a request runs but do not move its KV. Without a memory pool, a request thus either queues at a node that holds its prefix, raising TTFT, or recomputes the prefix on another node, lowering throughput. 

Memory pools. A memory pool extends the capacity for reusable KV beyond GPU memory. HiCache caches KV in GPU memory (L1) and host memory (L2) on each node and shares KV across nodes through an optional storage tier (L3), such as Mooncake Store [50, 72]. Shared KV moves from the L2 of the source node through L3 to the L2 of the destination node, leaving copies in L3 and in the L2 of both nodes. HiCache loads the fetched KV into GPU memory only when the request starts its prefill [52]. This load therefore delays prefill and raises TTFT (Section 3.3). These pools index KV by content and typically evict KV in LRU order. LRU eviction thus cannot distinguish the KV of a branch that waits for a tool from the history that compaction has replaced. Agent-aware systems such as Continuum and ThunderAgent retain the KV of agents that wait for tools [23, 27], but assume that each context only grows and do not track the duplicate copies that KV transfers leave across nodes. In summary, these systems couple compute allocation with KV cache management, making phase switches costly. Their planners rely on coarse signals that do not fully reveal the workload composition, and their routers trade cache locality against load balance. Their memory pools load fetched KV only when prefill starts, evict KV by access recency, and leave duplicate copies after KV transfers. # 3 Motivation 

This section profiles PD-disaggregated serving systems on agentic workloads and quantifies three sources of inefficiency, namely costly phase switches, misestimated compute demand, and misjudged KV reuse. We use the testbed of Section 6.1, nine nodes of 4 ×GB300 GPUs that serve GLM-5.2 with TP4, and replay the Claude Code traces with 90 concurrent agents for one hour after a 30-minute warmup. Dynamo runs its planner at the default throughput target with the SGLang Model Gateway. Arrow’s code is not public, so we reimplement its planner and scheduler on the symmetric engines of Evolving Infra (Section 4.1). Both planners start from 6P3D, and each node runs HiCache with LRU eviction. For routing (Section 3.3), we run SGLang in its PD disaggregation mode at the best static split, 4P5D, and compare the cache-aware and sticky-session policies of the SGLang Model Gateway, the Dynamo KV router [45], and a variant of the Dynamo KV router whose nodes fetch prefixes from a shared host-memory pool (+ memory pool). 

# 3.1 Costly phase switches 

Every phase switch takes time, loses KV reuse, or both (Figure 3a), because engines fix their phase at launch and index cached KV locally (Section 2.2). The Dynamo planner relaunches the worker of a node at every switch. A switch takes 681 s on average, during which the node serves no requests. Arrow switches nodes in place without this delay, but the KV of a switched node becomes unreachable for prefill. Arrow misses 55.5% of the cache hits that it would achieve with an unlimited KV cache shared by all nodes and no phase switches, and Dynamo misses 5.1%. We call this fraction of missed hits the lost KV reuse . Avoiding both costs requires an engine that serves both phases without a relaunch and a KV pool that every node can read in either phase. 

# 3.2 Misestimated compute demand 

Both online planners size the split from coarse signals (Section 2). The Dynamo planner and Arrow thus deliver 49% and 65% less throughput than the best static split(4.9 req/s), respectively (Figure 3b). These signals misjudge the work of agents in opposite directions. Arrow predicts prefill time from the full input length, which counts cached prefixes as work, and it also reacts to short prefill bursts, such as several sub-agents that start together. Arrow thus drifts from 6P3D to 8P1D, and switches 34 times during the run, each time incurring the costs in Section 3.1. The Dynamo planner instead follows queue depth and KV utilization. Long agent contexts keep the KV utilization of decode nodes high, and the planner drifts past 4P5D to 2P7D. 5Sizing the split well requires a model of the average prefill and decode work that a request needs after KV reuse. Short bursts of sub-agents and forks raise the momentary load but barely change the average. 

# 3.3 Misjudged KV reuse 

Routers misjudge the KV reuse of agents in either direction (Figure 3c). The cache-aware and sticky policies of the SGLang Model Gateway keep an agent and its forked branches on the few prefill nodes that hold their prefixes. The P95 TTFT thus reaches 27 s and 34 s. The load-aware Dynamo KV router [45] sends more requests to nodes that lack their prefixes, which recompute them, and the P95 TTFT reaches 65 s. With the shared memory pool, these nodes fetch the prefixes instead, yet the P95 TTFT rises to 95 s. Because the pool loads the fetched KV into GPU memory only when the request begins its prefill, the load adds to the prefill time instead of overlapping with queueing (Appendix D.6). The duplicate copies that fetches leave also occupy host memory and displace the KV that agents still need. Eviction misjudges KV reuse as well. HiCache evicts the least recently used KV, whereas the reuse of agent KV depends on whether an active branch still includes it (Section 2). HiCache thus keeps histories that compaction replaced but evicts the KV of branches that wait for tools, sub-agents, or users. On the CC traces, these evictions cause 39% of the KV reuse that Dynamo loses (Appendix C.1). Reusing KV well requires a memory pool that hides fetch delays, routing that balances load, and eviction that follows agent context management and removes duplicate copies. 

# 4 Decoupled and Agent-Aware Infrastructure 

This section presents the infrastructure that enables efficient online adaptation (Figure 1). The symmetric engine (Section 4.1) allows nodes to switch phases without a relaunch, and the shared KV pool (Section 4.2) keeps KV readable by all nodes in either phase. Together, they meet the two needs in Section 3.1 and decouple compute allocation and KV cache management. The KV directory (Section 4.3) counts the active branches that reference each KV block on each node and updates these counts as branches fork, compact, or finish and as KV moves between nodes. These counts identify the KV that no active branch reuses (Section 3.3). 

# 4.1 Symmetric engines for online phase switches 

To reduce the cost of online prefill–decode phase switches (Section 3.1), we build a symmetric engine that supports both phases, so that every node can serve either phase. With this engine, the router separates prefill and decode at runtime rather than through a static deployment configuration. Unlike SGLang (Section 2), whose prefill and decode engines run different scheduling loops and fix their phase at launch by default, our engine extends SGLang with one scheduling loop that serves both phases and a KV transfer protocol that moves KV between any two nodes in either direction. The protocol reuses the RDMA transport of Mooncake [50] and keeps working after a node switches its phase. Every node of Evolving Infra runs this engine, and a single router routes prefill requests to one set of nodes and decode requests to the remaining nodes (Figure 1). When the planner reassigns the phase of a node (Section 5.2), the router changes the type of requests that it routes to the node, and the engine serves the new phase without a restart. 

# 4.2 Shared host-memory KV pool 

To keep KV readable by every node in either phase (Section 3.1), Evolving Infra pools the host memory (L2) of all nodes into a shared KV pool. Following HiCache [72], each node caches KV in GPU memory (L1) and writes it through to its L2 in both phases. A prefill node locates reusable KV through the directory (Section 4.3) and pulls it from the L2 of a peer over RDMA. Unlike the storage tier of SGLang, which stages shared KV in a separate store, the pool reads directly from the L2 of a peer and avoids this extra copy (Appendix A.2). Deduplication across the GPUs of a node further increases its effective capacity (Appendix A.5). Decode nodes only write to the pool, since a fetch from host memory would delay decoding (Appendix D.6). They receive the KV of each request from the prefill node through the faster GPU-to-GPU transfer, and the KV that they generate stays in their L2 for the next request of the branch. 6A fetch from a peer, however, delays the prefill of its request (Section 3.3). HiCache prefetches KV only into host memory while a request waits and loads it into GPU memory layer by layer during prefill. Evolving Infra instead completes the whole fetch while the request waits in the queue. The node pulls the KV from the L2 of the peer into its own L2, loads it into GPU memory, and broadcasts it to all GPUs of the node before the prefill begins. When the planner selects a new split (Section 5.2), the router moves the queued requests of each switching node to other nodes of its current phase. The running requests of the node finish in place, after which the node switches its phase. The KV of the switching node stays in the pool and remains readable by all nodes throughout the switch (Section 3.1). 

# 4.3 Agent-aware cluster-wide KV directory 

To identify the duplicate copies that KV transfers leave and the histories that context management drops (Section 3.3), the router (Figure 1) maintains a cluster-wide KV directory. Following the Dynamo KV indexer [45], the directory is a prefix tree that records KV placement in GPU and host memory of each node. The router updates this tree with the KV events that the engines publish (Section 2). The directory also records, for each block on each node, how many active branches reference it (Figure 4). The router updates these counts from two identifiers. The harness tags each request with the ID of the agent branch that issues it and reports when a branch finishes. The router maintains a version for each branch and increments it when the context of the branch is rewritten. The engine on each node then updates the eviction priority of the KV blocks in its host memory according to the counts that the router sends (Section 5.3). Both identifiers follow agent context management. When the harness forks a context or spawns a sub-agent, it sends the ID of the new branch to the router. The router then adds one count to each block that the new branch reuses on the node that serves it. For consecutive requests of the same branch, the router compares the new request with the previous request of the branch. If the new request only appends tokens, the router adds counts only to the newly appended blocks on the routed node (Figure 4a). The reused blocks keep their counts, since the branch was already counted on them in earlier steps. If the context is rewritten by compaction, the router increments the version. It then releases the counts on the blocks that the new context drops and adds counts to the blocks that it newly includes (Figure 4b). When the harness reports that a branch has finished, the router releases all counts of the branch. Counts also follow KV transfers. A transfer between two nodes of the same phase (P2P or D2D) moves the counts of the branch, since the branch reuses only the target copy in that phase. The source releases them once the target holds the current version (Figure 4c). A transfer across phases (P2D or D2P) keeps the counts on both nodes, since the next step of the branch needs the copies in both phases (Figure 4d). A node that switches from decode to prefill resets its counts to free its memory, whereas a node that switches to decode keeps them to preserve its KV. Appendix E.1 and Appendix E.2 give these rules in pseudocode. As a result, each active branch holds counts on at most one copy per phase. 

# 5 Agent-Adaptive Compute Allocation and KV Cache Manage-ment 

Based on the infrastructure in Section 4, this section presents how Evolving Infra adapts compute allocation and KV cache management to agents at runtime. We first characterize the work of each request and learn iteration-time models of each node online (Section 5.1). Section 5.2 then presents the planner, which uses these models to size the PD split for diverse agent workloads and their shifting composition. Given the split, Section 5.3 presents KV-reuse-aware eviction and routing, which preserve the KV that active branches still reuse and balance prefill work across nodes. Table 1 summarizes the notation.

The router obtains tc from the longest cached prefix that the KV directory finds for the request (Section 4.3), and tuc counts the remaining input tokens. Separating the two token lengths allows the models to predict prefill time accurately, even when agents reuse most of their context. The models rest on two premises. First, the kernels of a forward pass run one after another, and the iteration time is the sum of their execution times. Second, as in the roofline model [68], each kernel is limited either by the compute throughput or by the memory bandwidth of the GPU. A compute-bound kernel runs in time proportional to its arithmetic operations, whereas a memory-bound kernel runs in time proportional to the bytes that it reads and writes.

Under causal attention, the i-th uncached token attends to the tc cached tokens and to the first i uncached tokens, including itself. Online fitting. Evolving Infra fits both models purely online at the start of serving. During a warmup period, every node serves both phases in a collocated mode, and Evolving Infra records the prefill and decode work that each node completes in fixed windows. It fits the coefficients of both models for each node by nonnegative least squares, freezes them, and then starts PD disaggregation from the initial split. After warmup, Evolving Infra periodically remeasures only ¯ tn and fn, which change with the workload composition (Figure 2b). On controlled measurements on GB300, the model form predicts iteration time with a mean error below 7% outside the fitted settings (Figure 5).

# 5.3 KV-reuse-aware eviction and routing 

Eviction. The rules in Section 4.3 keep the count of a copy positive only while an active branch may still reuse it on that node. A block with a zero count, such as the history that compaction replaced, the context of a finished sub-agent, or the source copy left by a same-phase transfer (Figure 4), is thus KV that no active branch will reuse. Each node therefore evicts the blocks in its host memory in ascending order of the key (1[Rb > 0] , T b), where Rb is the count of block b on the node and Tb is its last access time. The node thus evicts zero-count blocks first, in LRU order, and evicts blocks with positive counts only after no zero-count block remains. # 6.2 Stationary workloads 

Low-cost online adaptation across agent workloads. Evolving Infra outperforms Dynamo in throughput, lost KV reuse, and mean E2E latency for every agent workload (Figure 6). It achieves 1.10– 2.73 × the throughput of Dynamo (Appendix C.4), reduces lost KV reuse by 81–95% , and lowers the mean E2E latency by 1.15–4.12 × and the P95 TTFT by up to 13.92 ×. At the lowest concurrency of each workload, it also achieves 0.98–1.38 × the throughput of the best static split under SGLang (Appendix D.1). Averaged over all nine settings, a phase switch of Evolving Infra completes in 6.2 s, including the wait for the running requests of the node, which the node keeps serving. This is over 100 × shorter than a Dynamo relaunch, which takes 754 s on average and keeps the node out of service throughout (Appendix C.1). The symmetric engine (Section 4.1) and the shared KV pool (Section 4.2) thus avoid the relaunch and retain the KV of the switching node, the two costs of a phase switch in Section 3.1. They stay fast when prefill and decode use different parallelism (Appendix D.4). 

Accurate compute allocation for diverse agent workloads. Evolving Infra reduces the mean E2E latency by 3.80–4.12 × on CC, 2.34–2.69 × on OSWorld, and 1.15–1.23 × on Putnam relative to Dynamo (middle row of Figure 6). The planner (Section 5.2) contributes to this gain by matching the PD split to the compute demand of each workload purely online. It selects 3P6D–4P5D for CC and 8P1D for OSWorld (Appendix C.2). These splits differ from the best static splits under SGLang in Figure 2a, 4P5D and 6P3D, since the symmetric engines shift the best split (Appendix D.1). On the decode-heavy Putnam, the planner keeps only one or two prefill nodes to maximize throughput. This choice trades P95 TTFT for throughput, raising the P95 TTFT above that of Dynamo at 224 and 288 agents while lowering the mean E2E latency. Unlike the coarse signals in Section 3.2, the iteration-time models separate cached from uncached tokens (Section 5.1), and the average work of a request barely changes during short bursts. Evolving Infra 

thus switches only 2.0 times per run on average, whereas the Dynamo planner reacts to queue depth and KV utilization, switches 3.6 times per run, and deviates from the best static split of each workload for 41–100% 

of the measurement period (Appendix C.2). Under open-loop arrivals, the planner also gives prefill more nodes as agents arrive faster, and Evolving Infra sustains twice the arrival rate of the best static split (Appendix D.3). 

Accurate KV cache management under agent context management. Since asynchronous fetches make moving KV fast (Section 4.2), the router routes each request to the node with the shortest predicted TTFT (Section 5.3) rather than to the few nodes holding its prefix (Section 3.3). Evolving Infra thus reduces the P95 TTFT by 3.25–13.92 × on CC and OSWorld relative to Dynamo (bottom row of Figure 6). On CC, the most loaded prefill node queues requests 1.75–1.85 × as long as the average node, versus

With the counts of the directory (Section 4.3), the eviction of Evolving Infra (Section 5.3) retains nearly all the KV that agents still need (top row of Figure 6). In contrast, the LRU eviction of Dynamo drops the KV of branches that wait for tools, sub-agents, or users, which accounts for 34–46% of its lost KV reuse on CC. # 6.4 Ablation study 

Sensitivity to the initial PD split. Evolving Infra achieves a similar mean E2E latency from every initial split (Figure 8a). Serving CC with 126 concurrent agents from four initial splits, from 3P6D to 6P3D, its mean E2E latency varies by at most 1.8% . In all four runs, the planner converges to 4P5D (Appendix C.2). On this workload, online phase-split adaptation thus does not need a well-chosen initial split. 

Contribution of each component. On CC with 126 concurrent agents, the infrastructure of Section 4 and the KV-reuse-aware eviction and routing of Section 5.3 alone achieve 1.37 × the throughput of the best static split at the same 4P5D split, without online phase-split adaptation (Figure 8b). With the routing of SGLang, asynchronous KV fetching alone achieves 1.12 × the throughput of upstream SGLang, because it cuts the idle time of prefill nodes from 23.6% to 14.4% (Appendix D.6). KV-reuse-aware routing and eviction contribute the rest. Compared with cache-aware routing at the same split, Evolving Infra loses 0.7% instead of 2.4% of the KV reuse and prefills 31% fewer uncached prompt tokens per request (Appendix D.5). Pausing agents as ThunderAgent does brings no such gain (0.95 ×), because KV capacity does not limit serving on GB300 nodes (Appendix D.5). 

Cost of online phase-split adaptation. Enabling online phase-split adaptation at the best static split lowers the throughput by only 0.3% (Figure 8b). Online adaptation thus costs almost no throughput even when the initial split is already the best. It also avoids offline profiling, which takes 10,752 GPU-hours for the three-hour CC trace on 256 GPUs even with a binary search and recurs for every agent workload (Appendix D.2). Online fitting is fast as well. The iteration-time models converge to a low mean error within a minute of learning (Figure 8c), far shorter than the 30-minute warmup of our runs. 

# 7 Conclusions 

We present Evolving Infra , an agent-adaptive serving framework that decouples compute allocation from KV cache management. Existing PD-disaggregated systems tie the KV cache of each node to the phase of that node. Changing the PD split thus either relaunches a node or loses its KV. Keeping KV on its node also forces routing to trade load balance against cache locality. In Evolving Infra , symmetric engines switch the phase of a node in place. A shared KV pool keeps the KV of every node readable by all other nodes. On this data plane, Evolving Infra adapts compute allocation to diverse agent workloads and their shifting composition, and KV cache management to agent context management. Its planner reassigns nodes between prefill and decode with iteration-time models that separate cached from uncached tokens and are fitted online. Its router balances predicted TTFT across prefill nodes. With the branch counts of the KV directory, each node evicts first the KV that no active branch references, such as replaced histories and the contexts of finished sub-agents. On 36 GB300 GPUs, a phase switch of Evolving Infra takes 6.2 s on average, over 100 × shorter than a Dynamo relaunch. Under stationary load, Evolving Infra delivers up to 2.73 × the throughput of Dynamo, loses 81–95% less KV reuse, and reduces the mean E2E latency by up to 4.12 ×. Under a shifting workload composition, it reduces the mean E2E latency by 2.15 × and 1.33 × relative to Dynamo and the best static split, respectively. These gains hold on 256 GB300 GPUs and, in simulation, on 3,072 GPUs (Appendix D.2). 14 References

# A.1 Prefill–decode split adaptation 

Current serving engines fix their phase at launch by default. Systems that adapt the PD split around this limit either relaunch engines, which takes minutes and empties their KV caches, or switch them in place. Those that switch in place lose the KV of a switched engine or size the pools with a coarse cost model. Others keep the roles of nodes fixed and shift only compute or KV between the phases, inside an engine or between fixed prefill and decode nodes. 

vLLM and SGLang relaunch to change phase. In SGLang, a flag at launch makes each engine a prefill or a decode engine, and the router is given separate lists of prefill and decode engines [53]. The two roles run different scheduling loops with role-specific state. A prefill engine keeps a bootstrap queue and sends KV to decode engines. A decode engine reserves KV slots for each incoming request before its prefill finishes, receives KV through its own threads and queues, and captures CUDA graphs for decoding [53, 55]. vLLM likewise configures each engine at launch to produce KV for prefill or to consume it for decode, and its proxy is given fixed lists of prefill and decode engines [64]. Changing the phase of an engine thus requires relaunching it with a new configuration. SGLang’s recent opt-in runtime switch avoids the relaunch, but it still drains the engine to idle and releases its prefix cache [55]. Systems built on these engines therefore relaunch them. The Dynamo planner changes the phase of a node by terminating its worker, without waiting for in-flight requests, and launching a worker of the other phase [43]. The new worker must load the model and starts with an empty KV cache, and Dynamo notes that spinning up a GPU worker takes minutes [43]. In the runs of Section 6.2, a Dynamo switch takes 754 s on average, from the planner decision until the relaunched worker is ready, and on CC with 108 agents Dynamo loses 4.9% of the available KV reuse over its four switches (Appendix C.1). While a node relaunches, only eight of the nine nodes serve requests, which covers 44–91% of the one-hour measurement period (Appendix C.2). 

Arrow switches in place but loses KV. Arrow [69] keeps nodes stateless, so that any node can serve both prefill and decode requests, and it moves nodes between the prefill and decode pools without a restart. Its code is not public, so Section 3 evaluates our reimplementation of its planner and scheduler on the symmetric engines of Evolving Infra . Arrow has three problems on agentic workloads. xLLM cannot switch phases and route by cached KV at once. xLLM [31] switches nodes between phases in place, but its open-source service implements this switching and KV-aware routing as alternative policies chosen at launch [73]. Only its SLO-aware policy switches phases, and it flips single nodes in reaction to individual requests instead of sizing the split with a planner. This policy predicts TTFT from the full prompt length, so it counts cached prefixes as prefill work and ignores where KV is cached. Its cache-aware policy routes by prefix hits but never switches phases. 

Llumnix adapts the split with a coarse cost model. Llumnix [60] reschedules running requests across engines by live-migrating each request together with its KV, which balances load, reduces memory fragmentation, and isolates high-priority requests. Its adaptive PD mode assigns phases to engines at runtime to meet TTFT and TPOT targets [32], using a cost model that predicts TTFT by interpolating between profiled points by the number of prefill tokens and the decode load [33]. A single token count cannot separate the uncached tokens of an agent request from the long cached prefix they attend to. Part of its KV transfer stack is also released only as a pre-built binary without source code, so we could not run Llumnix on the Arm CPUs of our GB300 nodes. In our runs on H200 GPUs, Llumnix delivers 12.2% less throughput than the best static split (Figure A.1). 

semi-PD shares KV between the phases only inside an engine. semi-PD [19] runs a prefill process and a decode process on every GPU of an engine, divides the SMs of each GPU between them through NVIDIA MPS, and keeps one copy of the weights and the KV, its unified storage, in the GPU memory of the engine. Shifting SMs restarts only these processes, while a resident process keeps the weights and the KV, so semi-PD avoids costly phase switches inside an engine. Its controller, however, shifts SMs to the phase whose TTFT or TPOT misses its target, and the prefill bursts of agents, such as sub-agents that start together, perturb both (Section 3.2). Across engines, its router weighs the KV cache hit rate of each engine against GPU utilization and queue depth, the trade-off between cache locality and load balance of Section 3.3. 

MemServe and PPD reuse multi-turn KV but keep the split fixed. MemServe [20] and PPD [28] let the later turns of a conversation reuse the KV that its previous turn left on the decode side. MemServe moves this KV to the prefill engine: the decode engine sends the KV that it produced back after each request, and a global scheduler routes each request by where its prefix is cached. PPD instead moves the prefill to the KV: it prefills the uncached tokens of a later turn on the decode node that holds the KV of the conversation, which slows decoding far less than a full prefill does, and a table profiled offline decides per request whether to take this path. Neither, however, adapts the split: MemServe’s engines are prefill-only, decode-only, or colocated, and PPD restarts its engines to change the split, so neither follows the shifting workload composition (Figure 2b). PPD’s offline table, as its authors note, becomes suboptimal when the workload drifts far from the one it was profiled on. MemServe also judges KV reuse from stale records: its scheduler learns where KV resides only from the responses that pass through it, so it misses evictions and expires its records after a fixed time-to-live. PPD keeps the KV of a conversation on one decode node, so each later turn either runs on that node or recomputes the previous response on a prefill node. 

Evolving Infra instead switches the phase of a node in place, and the shared KV pool keeps the KV of the node readable by all other nodes (Sections 4.1 and 4.2). 

# A.2 KV memory hierarchy in current serving engines 

Section 4.2 builds the shared KV pool of Evolving Infra on SGLang HiCache. This subsection describes how current engines tier KV, how they share it across nodes through Mooncake, and why this sharing adds latency. 22 Private host tiers. SGLang HiCache backs the GPU KV cache (L1) of an engine with host memory (L2) and an optional storage backend (L3) such as Mooncake Store [52, 72]. L1 and L2 are private to each engine, and every tensor-parallel rank allocates its own L2 pool. Engines therefore never read each other’s L2: KV that one engine computes becomes visible to another only after it reaches L3 [52]. 

Sharing through Mooncake. Mooncake Store pools the DRAM that nodes contribute into a cluster-wide object store. A master service keeps the metadata of each object, and clients move the data directly over RDMA with the Mooncake Transfer Engine [36, 37]. A put first asks the master to allocate space and then commits the object, and a get first asks the master where the object is stored. SGLang backs up pages from L2 to Mooncake in the background, keyed by a hash of the prefix that ends at each page. When a request is queued, an engine asks Mooncake which pages of its prefix exist, prefetches them into its own L2, and loads them into GPU memory layer by layer during prefill [52, 57]. vLLM’s Mooncake store connector instead registers GPU memory with Mooncake and moves KV blocks directly between GPU memory and the pool [49], and a newer SGLang option links its radix cache to Mooncake in the same way, without HiCache’s host tier [57]. 

Why fetching through the pool adds latency. KV takes extra hops. With HiCache, it moves from the L2 of the producing engine into a Mooncake segment, which may lie on a third node, and from there into the L2 of the consuming engine before it reaches the GPU. Every lookup, put, and get also involves RPCs to the master, and a page becomes visible only after its backup commits [36]. The prefetch starts when the request is queued but fills only L2, and the GPU loads the pages layer by layer during prefill. If the prefetch has not finished when the prefill could start, SGLang stops it under the best-effort policy and recomputes the pages that have not arrived, waits for it under the wait-complete policy, and under the default timeout policy waits until a deadline and then recomputes the rest [52, 57]. Mooncake’s own benchmark accordingly finds HiCache slightly faster with L2 alone than with Mooncake at equal hit rates in its first rounds, because L2 alone avoids fetching from remote storage [35]. The same KV can also occupy the L2 of the producer, the pool, and the L2 of each consumer at once. Evolving Infra instead lets prefill nodes read KV directly from the L2 of any peer over RDMA, restores it into GPU memory before the prefill begins, and keeps L2 across phase switches (Sections 4.1 and 4.2). 

# A.3 Dynamo KV indexer and router 

The KV directory of Evolving Infra (Section 4.3) follows the KV indexer of the Dynamo router. This subsection describes how the index is built and updated, how the router scores nodes with it, and what it does not record. 

Cluster-wide KV index. The KV router of Dynamo keeps a cluster-wide index of cached KV in a prefix tree [44]. Each entry of the tree stands for one KV block, keyed by a hash of its tokens, and records the nodes that hold the block. To route a request, the router walks the tree along the blocks of the request and finds, for every node, how many leading blocks it already holds. 

KV events. Engines keep the tree current through KV events. SGLang and vLLM publish an event over ZMQ whenever they store or evict blocks, and a publisher on each node relays the events to the routers [41]. The engine identifies each block by a prefix hash over all tokens up to and including the block. When it stores new blocks, its event carries their tokens and prefix hashes and the prefix hash of their parent block. Through a per-node table from prefix hashes to tree entries, the router finds the entry of the parent block, descends from it along the token hashes of the new blocks, creating entries as needed, and adds the node to each of these entries [40, 41, 44]. When the engine evicts blocks, its event names them by their prefix hashes, and the router removes the node from their entries. With HiCache, SGLang also names the memory tier in each event, and the router tracks host memory and disk in separate indexes beside the GPU tree [40, 42]. 

Scoring. For each candidate node, the router adds the prompt blocks of the request to the prefill blocks already assigned to the node, subtracts a credit for each leading block that the node already holds, and adds 23 the blocks that the node would be decoding. The router tracks these loads itself from the requests that it routes, not from KV events, and sends the request to the node with the lowest cost [44]. A block held in GPU memory earns a full credit, while blocks in host memory and on disk earn 0.75 and 0.25 by default [42]. The host and disk credits are constants: they depend neither on how long loading the blocks takes nor on the running requests that the loading delays on the node. Evolving Infra instead predicts the TTFT of the request on each prefill node, including the part of a KV fetch that the wait in the queue does not hide (Section 5.3 and Appendix E.3). 

What the index does not record. The index records where each block is cached, on which nodes and in which tier, but not which requests or agent branches will reuse it. KV events report only stores and evictions, not the forks, compactions, and finished sub-agents that decide this reuse. Eviction therefore stays with each engine, and SGLang evicts in LRU order by default [54]. Dynamo can also pass a per-request priority from the harness to SGLang, which can then evict the KV of the lowest-priority requests first [46]. Neither recency nor priority changes when compaction replaces a history or a KV transfer leaves a copy behind: these blocks keep their last access time, and a cached prefix keeps the highest priority among the requests that reached it [54]. Evolving Infra keeps the same event-driven tree and adds one attribute to each block, the number of active branches that reference it on each node (Section 4.3). The counts follow agent context management and KV transfers, and each node evicts the host-memory blocks with zero counts first (Section 5.3). 

# A.4 Agent-aware KV management and routers 

This subsection compares Evolving Infra with systems that use the structure of agents to manage KV. 

Program-aware scheduling. ThunderAgent [23] and Continuum [27] schedule the requests of an agent together so that its KV survives tool calls. Continuum pins the KV of a multi-turn program in GPU memory for a time-to-live that it estimates from the durations of past calls to the same tool. ThunderAgent abstracts each agent workflow as a program. When the programs on a data-parallel replica need more KV than its GPU cache holds, ThunderAgent pauses programs that wait for tools, evicts their KV, and resumes them later, possibly on another replica with free memory. Both systems thus target KV-cache thrashing, in which the KV of a waiting program is evicted from GPU memory and its whole context must be prefilled again. Both run prefill and decode on the same nodes, and both treat the context of a program as growing only by appending. 

Thrashing on current models and hardware. Thrashing occurs only when programs need more KV than a replica can hold. Current engines back GPU memory with a host-memory tier, and compact KV representations together with deduplication let this tier hold several times as much KV as GPU memory (Appendix A.5). A context evicted from GPU memory then stays in host memory and is reloaded rather than recomputed. ThunderAgent found such offloading too slow over PCIe [23], but on GB300 nodes the reload runs over the NVLink-C2C link between the Grace CPUs and the GPUs [10, 39]. In our runs, Dynamo, whose SGLang engines evict host memory in LRU order, loses at most 7.8% of the available KV reuse, and 

Evolving Infra at most 1.0%, without pausing any agent (Appendix C.1). Host memory instead keeps KV that no active branch needs: the source copies that KV transfers leave, the histories that compaction replaces, and the contexts of finished sub-agents. Evolving Infra therefore counts the branches that reference each copy (Section 4.3) instead of pausing agents. Appendix D.5 compares Evolving Infra with ThunderAgent and cache-aware routing on GB300 nodes. 

Agent-aware KV management. KVTether [17] exports runtime context operations from agent harnesses and maps them to KV lifecycle states, accounting for shared prefixes across contexts. These states guide cache admission, reclamation, and eviction in a multi-tier cache with cross-node transfers. Its presented design focuses on KV lifecycle management and does not address online adaptation of the PD split; its evaluation uses a fixed PD configuration. 24 A.5 Extending host memory with deduplication 

Section 4.2 keeps the KV that agents reuse in host memory (L2), and Appendix A.4 argues that this tier largely absorbs KV thrashing. This subsection explains why L2 is large enough. 

Compact KV. Although smaller than L3, L2 is sufficient for recent open models [18, 25]. These models increasingly adopt compact KV representations such as MQA [59] and MLA [13]. In MLA, all attention heads share one latent vector of 576 values per token and layer. With an FP8 KV cache, a token takes about 35 KB of KV in Kimi K2.6 and about 50 KB in GLM-5.2, including the keys of the sparse-attention indexer of GLM-5.2. Full multi-head attention at the same precision would need 36 × and about 50 × as much. 

Deduplication across tensor-parallel ranks. Because all heads share the latent vector, tensor parallelism does not split MLA KV: every rank holds the complete KV of each token [52]. SGLang HiCache allocates its host pool per rank and thus stores the same KV once per GPU in L2, although only one rank writes it to the storage backend [52]. vLLM’s CPU offloading instead keeps one copy of each replicated MLA block in a host region that all ranks share, so that at a tensor-parallel degree of N the host tier holds about N

times as many blocks [63]. LMCache saves MLA KV from one rank and broadcasts it to the other ranks on retrieval [34]. Our engines deduplicate L2 in the same way: L2 stores a single copy per node for all attention heads and broadcasts it to all GPUs of the node when fetched in L1. All systems in our evaluation, including the baselines, use this deduplication. When serving GLM-5.2 on NVIDIA GB300, L2 typically holds 4× as much KV as L1. A GB300 node has about 1 TB of host memory [39], which could hold about 20 million tokens of GLM-5.2 KV as a single copy, but only about 5 million if each of its four GPUs kept its own copy. Production traces of a large cloud provider show that the cache size needed for an ideal hit ratio is moderate [66]. With a deduplicated host tier, capacity thus rarely forces recomputation in our runs (Appendix A.4), and the remaining waste lies in KV that no active branch references (Section 4.3).

# B.3 MoE weights in the decode iteration-time model 

In an MoE model, a decode iteration reads the dense weights in full but reads a routed expert only when some token selects it. The dense weights, such as the attention projections and the shared experts, serve every token, and reading them is part of the fixed cost dn, 0 in Equation (2). In each MoE layer, a gate assigns every token to k of the E routed experts. The layer then reads the weights of each selected expert from GPU memory once and applies them to all tokens that select this expert. It does not read the weights of experts that no token selects. Our engines split every expert across the GPUs of a node with tensor parallelism, and each GPU reads its share of every selected expert. The time to read the routed experts thus grows in proportion to the number of selected experts. Equation (2) writes this time as dn, 1ϕ(B), where dn, 1 is the time to read all routed experts and ϕ(B) is the fraction that the iteration selects. We derive ϕ(B) under two assumptions. First, every expert receives the same share of tokens. MoE models are trained to keep the load of their experts balanced [12], and each token thus selects a given expert with probability k/E . Second, different tokens select their experts independently. Each of the B running requests feeds tfwd tokens into every MoE layer, and the layer thus routes tfwd B tokens. The probability that none of them selects a given expert is (1 − k/E )tfwd B . The expected fraction of selected experts is one minus this probability, which gives ϕ(B) = 1 − (1 − k/E )tfwd B in Section 5.1. 

# B.4 Context length in the decode iteration-time model 

The decode iteration-time model omits the KV that an iteration reads for its running requests. This KV grows with their total context but stays small next to the weights that the iteration reads, for two reasons. First, recent models store little KV per token. With MLA, a token of GLM-5.2 takes about 50 KB of KV in FP8, about 50 × less than under full multi-head attention (Appendix A.5). Second, sparse attention lets decode read only part of this KV. GLM-5.2 reads the full KV of at most 2048 selected tokens per layer and only the small indexer keys of all other tokens. DeepSeek-V4-Flash reads the full KV of its 128-token window and 512 selected entries, and of all other tokens only compressed entries or indexer keys that each cover 4 or 128 tokens (Appendix B.2). As a result, one million more context tokens lengthen a decode iteration by about 1 ms for GLM-5.2 on GB300 and by at most 1.5 ms for DeepSeek-V4-Flash on H200, whereas an iteration with 8 to 64 running requests takes 17 to 45 ms (Figure 5d and Figure B.1d).

# D.2 Scaling to Larger Clusters 

This subsection evaluates Evolving Infra on real clusters of up to 256 GB300 GPUs and on a simulated cluster of 3,072 GPUs. Both show that the aggregate PD demand varies less as the cluster grows, whereas the imbalance within the cluster grows. 31 Setup on up to 256 GPUs. We serve the Claude Code traces with GLM-5.2 on 36, 64, 128, and 256 GB300 GPUs and scale the number of concurrent agents with the GPUs, 10 agents per GPU. Static PD runs SGLang in its PD disaggregation mode at a fixed split, with the router and HiCache settings of Section 6.1. 

The aggregate split matters less at scale. On 256 GPUs, static PD keeps 81–103% of the throughput of 24P40D across P/D ratios from 0.33 to 1.29 (Figure D.1a). The demand of many agents together varies less over time, and each node holds a smaller fraction of the capacity. A mismatch between the split and the aggregate demand thus costs less throughput than on 36 GPUs. 

The imbalance among nodes grows. The P95 TTFT of static PD, however, rises about threefold from 36 to 256 GPUs, from 142 s to 418 s (Figure D.1b). With more prefill nodes, the cache-aware router concentrates the requests of more agents on the few nodes that hold their prefixes. The router and the shared KV pool of Evolving Infra spread this load across nodes. Its P95 TTFT thus stays within 10–14 s, and its mean E2E latency rises by only 16% (Figure D.1c). 

Offline profiling grows costly at scale. Finding the best static split offline also becomes expensive as the cluster grows. A cluster of N nodes with g GPUs each has N − 1 candidate splits, and evaluating one candidate replays the whole trace of length T on all N g GPUs, together with a warmup of length Tw. An exhaustive search thus costs ( N − 1)( T + Tw)N g GPU-hours, or O(N 2gT ). A binary search compares two adjacent splits at each of its ⌈log 2(N − 1) ⌉ steps and costs O(N gT log N ). For the three-hour CC trace on 256 GPUs, N = 64 and Tw = 0 .5 h, so each candidate costs 896 GPU-hours. The binary search takes 12 runs, or 10,752 GPU-hours, which is 14 × the 768 GPU-hours of serving the trace once. The exhaustive search takes 56,448 GPU-hours. Three factors raise these costs further. First, a binary search assumes that throughput first rises and then falls with the number of prefill nodes, yet the throughput in Figure D.1a rises again from a P/D ratio of 0.78 to 1.00. A binary search can thus stop at a local optimum, and a reliable search falls back to the exhaustive one. Second, adjacent splits differ by only a few percent, for example 3% between P/D ratios of 0.45 and 0.60, which is comparable to the variation between runs. Each candidate then needs repeated runs, which multiplies the cost. Third, the search must recur for every new workload composition. A best split per planning window costs even more, since the searches of different windows visit different splits and together approach all N − 1 candidates. Evolving Infra instead evaluates the N − 1 candidates with its iteration-time models on m slices at the end of each window, which takes O(N m ) arithmetic on a CPU and no extra GPU time. 

Simulation setup. We further simulate a cluster of 3,072 GB300 GPUs with Frontier [16], a discrete-event simulator for LLM serving. We profile the prefill and decode iterations of GLM-5.2 offline on our GB300 nodes and supply these profiles to the simulator. Frontier models KV caching only within GPU memory, and we extend it with the shared host-memory KV pool and the asynchronous fetches of Section 4.2. Since 

Evolving Infra fetches remote KV while a request waits in the queue, the simulator assumes that each fetch completes before the prefill of its request begins and charges the fetch no time. We replay the Claude Code and Codex traces over 24 hours with about 10 concurrent agents per GPU, or 30,720 agents in total. 

Hierarchical scheduling. A single router cannot monitor every node of a cluster with thousands of GPUs. We therefore divide the cluster into 8 partitions of 384 GPUs, each with its own router, planner, and KV directory (Figure D.2). Constraints such as region and hardware bind each user to one partition, and each partition thus serves its own subset of agents. 

Local shifts under a stable aggregate. Across all partitions, the aggregate workload stays nearly constant, and the PD ratio of the cluster varies by only 7% over the trace. A static split, however, leaves 2 of the 8 partitions severely imbalanced, with queueing times up to 13.9 × the cluster average. These imbalances rarely stem from bursts of load. While a partition is imbalanced, its total work changes by less than 12.3%, whereas its PD ratio shifts by up to 42.4%. The planner of each partition follows these shifts and improves the throughput by 1.42 × over a static split. 32 Summary. At scale, Evolving Infra corrects the imbalance at two levels. Its router and shared KV pool balance the load among the nodes of a cluster, and the planner of each partition follows the local shifts in PD demand, even when the aggregate workload of the cluster is fixed. Neither level requires offline profiling.

# D.4 Compatibility with Heterogeneous Parallelism 

The best parallelism can differ between prefill and decode. For example, Huawei’s xDeepServe serves DeepSeek with tensor parallelism (TP) in prefill and attention data parallelism (ADP) in decode, because the two phases see different sequence lengths and ADP avoids duplicating the MLA KV cache [71]. SGLang and vLLM, however, choose parallelism strategy with launch arguments [56, 65], so a node that switches between them must relaunch its engine. The symmetric engine of Evolving Infra can avoid this relaunch, because where a node places its weights can be decoupled from how it computes with them: a node can hold the union of the weights that both phases need and switch phases by changing only its computation path, without moving 33 any weights. The extra weights take a small share of GPU memory, and the KV cache of Evolving Infra 

lies mostly in abundant host memory, which holds four times as much KV as GPU memory (Section 6.1). 

Experimental Setup. We serve GLM-5.2 [18] on six 8 ×B200 nodes, with TP8 on prefill nodes and ADP8 on decode nodes, and run BrowseComp agents [67], which can only spawn sub-agents, for two hours. We compare Evolving Infra with Dynamo [40] and the best static split, and Evolving Infra and Dynamo both start from 4P2D. In this deployment, the two phases differ only in the attention layers, and the MoE layers use the same parallelism in both. Under ADP, every GPU holds all attention weights, so it also holds the slice that TP assigns to it. Each node of Evolving Infra therefore keeps the ADP layout of the attention weights in both phases: it computes attention with TP in prefill and with ADP in decode, and a switch changes only which of the two it runs. With FP8 attention weights, this layout takes about 10 GB more per GPU than TP alone, or 6% of the memory of a B200 GPU. The planner needs no change, because it fits the iteration-time coefficients of each node online, and these coefficients already depend on the parallelism of the node (Section 5.1). 

Results. As Table D.3 shows, Evolving Infra moves to 2P4D, the best static split, and reaches a mean E2E latency of 15.9 s, within 1.3% of the 15.7 s of that split, which requires profiling each split offline. Switching engines takes Evolving Infra 27 s in total over the two hours. Dynamo ends at 3P3D with a mean E2E latency of 21.9 s, 38% higher than that of Evolving Infra . Wide expert parallelism. The same decoupling carries over to wide EP, where one engine spans an EP group of several nodes and attention runs with ADP. Under wide EP, the two phases use groups of different sizes and different communication kernels. SGLang, for example, evaluates prefill on 4-node groups with kernels built for throughput, and decode on 9-node groups with low-latency kernels captured in CUDA graphs [61]. A phase switch therefore moves a node from a group of one phase to a group of the other. Elastic EP performs such a move without a restart [3], but it transfers weights: when vLLM grows a DeepSeek-V4-Pro group from 16 to 20 GB200 GPUs, the scale-up takes 92 s in total to transfer weights, warm up, and capture CUDA graphs [2]. Evolving Infra avoids most of this weight transfer by again holding the union of what both groups need. Every node already holds the non-expert weights. For the experts, each group keeps two copies of every expert on different nodes, so each GPU holds twice its share. A node can then leave a group without taking away the last copy of any expert, and it can join any group at least half as large as its old one by serving experts that it already holds. For GLM-5.2 with NVFP4 experts, the second copy takes 7% of B200 memory in a 4-node group and 3% in a 9-node group. Nor does a move reload kernels, because one engine can load the kernels of both phases, as the auto mode of SGLang does [61].

# E.3 Routing and phase-split planning 

Algorithm E.3 runs two loops. The inner loop routes each request to the prefill node with the shortest predicted TTFT, Equation (7). For each prefill node n, the router forms the work of the request on n: the cached prefix tc,n is the longest prefix that the KV directory finds on n or on another node, of which xn

tokens must be fetched from another node, and tuc ,n counts the remaining input tokens. The router reads the running batch and the queue of n from the latest state that n reports, and adds the requests that it has sent to n but that n has not reported yet. It sums the service times of Equation (3) to predict the wait ˆWn

before the request starts. The fetch runs while the request waits, so only the part of the fetch time τ (xn)that exceeds the wait adds to the prediction. The prediction ends when the prefill of the request finishes, so it leaves out the first decode iteration, which is the same on every prefill node. Our implementation evaluates the sum by replaying the chunked prefill iterations of n in arrival order, which also accounts for requests that share an iteration. The decode node is bound when the prefill starts. The outer loop is the planner of Section 5.2. 

Parameters of our runs. Each prefill node reports its state at every iteration launch, and the router uses a state only if it is at most 5 s old. The chunk size is 8,192 tokens. τ (x) = 0 .45 s + 1 μs · x for x ≥ 512 38 tokens (no fetch below 512 tokens). The router also adds to ˆTn a copy price proportional to xn, which charges the duplicate KV that a fetch creates. Tlearn = 1 ,800 s, Twin = 600 s, and 60-s slices, so m = 10 for a full window.
