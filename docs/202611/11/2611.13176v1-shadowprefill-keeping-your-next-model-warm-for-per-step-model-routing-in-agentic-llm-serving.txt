## ABSTRACT 

Per-step model routers send each LLM call of an agent to the cost-optimal model dynamically within each session. However, every model switch discards prefix-cache reuse: KV caches are per model, so the new model must prefill the relevant context before it emits a token. Across representative agentic workloads, including a production coding-agent trace with a mean context of 63K tokens, the prefix hit rate falls from 80–89% on same-model calls to 44–65% after a switch, and a switch call takes 1.5–3.2 × as long. We present S HADOW PREFILL , which prefills the session’s context on the model the router has not chosen, in capacity that instances serving normal traffic leave idle, so the next switch finds its prefix cached. S HADOW PREFILL harvests the per-iteration SLO slack of requests in flight, protects routed calls, spills shadow KV to host memory, and falls back to a cold switch whenever the shadow is incomplete. With LLMRouter routing 24 model pairs over five agentic benchmark suites, S HADOW PREFILL 

cuts switch-call latency by 8.5–21.4%, LLM-call latency by 3.7–17.7%, and routed token cost by 22.5–46.1%, while normal traffic keeps its SLO and energy per request rises by 0.4%. 

## 1 INTRODUCTION 

Motivation. Agents solve a task through a sequence of LLM calls: plan, call a tool, read the result, edit, test, and repeat. The calls differ widely in difficulty, so a single model is either too weak for the hard steps or too expensive for the easy ones. Routers address this mismatch by selecting a model for each call (Ong et al., 2024; Chen et al., 2023b; Ding et al., 2024), and recent systems make the decision per step inside an agent loop (Zhang et al., 2025; 2026a;c; Paul & Nandy, 2026). Commercial products ship the same pattern: GPT-5 routes between a fast and a reasoning model per request (Ope-nAI, 2025), and coding agents delegate subtasks to smaller models (Anthropic, 2025). Across representative agentic workloads, an LLMRouter (Feng et al., 2025) policy that routes between two models is 6.6–13.6% more accurate than always using the larger one using less tokens (Section 5.3). 

The model switch tax. Agent calls are long and grow: each call resends the session’s history plus new tool output. Serv-ing engines make this cheap through prefix caching (Kwon et al., 2023; Gao et al., 2024; Qin et al., 2024): a call whose prompt extends the previous one prefills only the new tokens, and providers bill cached input at about a tenth of the price. KV caches, however, belong to one model. When the router switches, the target model holds no copy of the recent context, or a copy that stops at the last call it served, and must prefill the gap before it emits a token (Liu et al., 2026b). ## 2 BACKGROUND AND CHARACTERIZATION 

2.1 Per-step Routing in Agent Loops Model routers. A per-step router observes each LLM call of a session and selects one of several deployed models for it. We adopt LLMRouter (Feng et al., 2025) as the router. Its benchmarks evaluate every query on every candidate model, so a routing policy can be replayed exactly; we use its accuracy-per-cost policy, which sends each step to the model with the highest score per dollar, and restrict the candidates to a two-model pair, a small model S and a large model L.Two models is the common deployment of a cheap and a capable tier (OpenAI, 2025; Anthropic, 2025).

2.2 The Model Switch Tax Prefix caching is per model. Serving engines keep the KV of recent prompts and reuse it when a new prompt shares a prefix (Kwon et al., 2023; Gao et al., 2024; Qin et al., 2024). In an agent loop each call extends the previous one, so a session that stays on one model prefills only the new tool output and input: same-model calls hit 80–89% of their prompt tokens (Figure 2c). KV is a function of the model’s weights, so the cache cannot be shared across models. A switch call finds either nothing on the target or a copy that ends where the session last left that model, and its hit rate falls to 44–65%. Switch-aware routers (Zhang et al., 2026a;c) avoid switches and give up accuracy; S HADOW PREFILL lowers their price. 

2.3 Idle Capacity in Production Deployments Deployments are provisioned for peak. The model a ses-sion switches to is already deployed and busy serving other users’ requests, which we call normal traffic. Clusters are typically sized for the peak hour to reserve buffer for bursts and avoid SLO violations, so off-peak hours leave capacity unused. We replay one week of the Azure LLM inference traces for conversation and code (Stojkovic et al., 2025) and BurstGPT (Wang et al., 2025) on a pool provisioned for its peak (Figure 3a). Load swings by 3–10 × within a day. Instances serving code traffic are completely idle for 72% of the median hour and 85% of the trough hour, but only 8% SHADOW PREFILL : Keeping Your Next Model Warm for Per-Step Model Routing in Agentic LLM Serving 

of the peak hour, and conversation traffic, which is steadier, leaves no whole-instance idle time in any window. 

Iterations have SLO slack even at peak. Whole-instance idleness disappears exactly when switches are slowest. A finer-grained resource remains: a continuous-batching iter-ation is dominated by memory-bound decode and finishes well within the time-per-output-token (TPOT) SLO of the requests it serves. At the peak hour, the median iteration uses about a quarter of the TPOT SLO, and 69–79% of the per-iteration latency budget is unused (Figure 3b). A prefill chunk added to such an iteration delays every decode in it (Agrawal et al., 2024b), but as long as the iteration stays within the slack of each request in flight, no request misses its SLO. This slack is the capacity S HADOW PREFILL harvests. 

## 3 DESIGN 

SHADOW PREFILL sits between the router and the serving engines of a model pair. For every routed call it creates or extends a shadow job on the model the router did not choose, and each engine runs shadow jobs as a lowest-priority work class. This section states the goal and the mechanisms to address the challenges: Shadow jobs ( [C4] , Section 3.1), har-vesting ( [C1] , [C2] , Section 3.2), Shadow KV management ([C3] , Section 3.3), and safety ( [C5] , Section 3.4). 

3.1 Goal and Shadow Jobs Goal. When a session switches from model A to model B

at call k+1 , the prompt of that call consists of the session’s history hk (all prompts and outputs through call k) plus the new input. S HADOW PREFILL aims to have hk resident in 

B’s prefix cache when call k+1 arrives, so that the switch call prefills only the new input, as a same-model call does. It may spend only capacity that would otherwise go unused (by harvesting idle capacity), and it must never delay a switch call or cause normal traffic to miss its SLO. 

Incremental shadow jobs. A shadow job for session s on model B records the prefix of h that B already holds and the tokens still missing. When call k arrives at A, the manager appends call k’s new input to the job immediately, and appends A’s output tokens once A generates them (output streaming). B therefore never re-prefills what it already has: after a switch back from B to A and forward again, the job covers only the delta. The shadow always trails the routed model by at least the output of the current call; the switch call prefills that tail itself as it would do at each switch. 

Sticky model placement. Each agentic session keeps a sticky instance per model (Agarwal et al., 2026), and the shadow job runs on the sticky instance of the other model. The router sends each call to the instance of the chosen model with the lowest estimated prefill completion time, counting only uncached tokens. A switch call therefore lands on the instance that holds its shadow, unless that instance is so busy that a cold prefill elsewhere would finish first. 

Ordering by switch likelihood (C4). The engine runs pend-ing shadow jobs in order of their predicted switch probability, estimated per task and current model from past sessions, so the capacity goes first to the sessions most likely to switch. Gating jobs below a probability threshold reduces waste further but loses switches the predictor misses; we evaluate it as the Predictive variant in Section 5. 

3.2 Harvesting Capacity Where shadow work runs. Each iteration of a continuous-batching engine schedules, in priority order, all running decodes, in-flight prefill chunks, and admissions from the waiting queue, under a token budget. SHADOW PREFILL 

adds shadow chunks last, and only if the waiting queue is empty and no admission was blocked by memory. 

Idle instances. When an instance has no other work, it runs shadow-only iterations. Each such iteration is capped at β

times the TPOT SLO ( β=0 .5), which bounds how long a newly arriving request waits behind it. 

SLO-slack controller (C1). At peak, instances are rarely idle, so S HADOW PREFILL piggybacks shadow chunks on normal iterations, sized by the latency slack of the requests in flight. The controller uses only what a production scheduler observes: arrival times, first-token times, and iteration counts. 3.3 Shadow KV Management A capped, evict-first class (C3). Shadow KV is useful only if it survives until the switch, but it must not displace the cache entries that make same-model calls fast. Shadow entries form their own cache class, limited to 25% of the KV pool. A shadow chunk may use free blocks or blocks of cache entries idle for more than 5 s. Eviction removes shadow entries before normal ones and is LRU within each class. Configuration sensitivity studies are in Section 5.5. 

Host-memory spill tier. SHADOW PREFILL spills evicted session entries, shadow and normal, to host DRAM and reloads them over PCIe when a call hits them, as KV offload-ing systems do for a single model (Gao et al., 2024; Liu et al., 2025). Reloading a prefix is far cheaper than recomputing it, so the tier keeps shadow work from being lost to HBM pressure; it also helps same-model calls whose prefixes were evicted, which we evaluate separately as the Host Tier variant (Section 5). Host tier is needed especially for long-context agents (e.g., coding (Liu et al., 2026b)): Gemma-7B uses full multi-head attention and stores 458 KB of KV per token, so a single 100K-token agent context fills most of its H100’s KV pool, and its shadow is evicted long before the switch. 

3.4 Safety and Fallback No regression by construction (C5). Shadow work never blocks a routed call or a normal request: it runs only when nothing is waiting, it is bounded per iteration by the budget above, and it is preempted at iteration granularity, so an arriving request waits at most one capped iteration. A switch call never waits for a shadow. If its shadow is partial, it uses the cached prefix and prefills the uncovered tail; if the shadow is absent or was evicted, it runs exactly as without SHADOW PREFILL . The price of a wrong prediction is the harvested capacity it consumed, plus the energy of that computation (Section 5.4). 

3.5 Prefill/Decode Disaggregation Extension 

PD disaggregation runs prefill and decode on separate in-stances and moves the KV between them (Patel et al., 2024; Qin et al., 2024). A switch there costs both a cold prefill on the target’s prefill (P) instances and a larger KV transfer to its decode (D) instance. S HADOW PREFILL runs shadow jobs on the session’s sticky P instance of the other model when its queue is empty and background requests have TTFT slack, in iterations of at most 0.1 s. P instances are provisioned for prefill-heavy peaks and idle often, so shadow work finds more capacity than in a colocated cluster. The sticky D instance of the other model then pulls the shadow KV in 4K-token pushes whenever its inbound link carries no normal transfer, into free decode memory that is reclaimed first. At the switch, the P instance prefills only the tail and the D instance receives only the tokens it lacks. 

## 4 IMPLEMENTATION 

Router and sessions. We build routed sessions from LLM-Router’s benchmark matrices (Feng et al., 2025) by replaying the accuracy-per-cost policy over each model pair (Table 3). A session builder grows each step’s prompt from the session history, the dataset input, and optionally sampled tool output; it compacts the history into a 1K-token summary when the context reaches the model’s window. 

Serving simulator. We implement on top of Vidur (Agrawal et al., 2024a), a high-fidelity LLM inference simulator, with additionally 2,700 lines of Python. The resulting simulator is a discrete-event model of a cluster of continuous-batching instances. Each iteration’s latency is grounded by a per-layer profiled model of kernels (GEMMs, prefill attention, decode attention, and tensor-parallel all-reduces) fitted to each model’s H100 operator profiles. Model instances run chunked prefill with a default 2,048-token budget and up to 256 sequences, reserve KV cache at admission, and maintain a prefix cache of session contexts and finished requests. 

vLLM prototype. We build a prototype to validate the core mechanism of S HADOW PREFILL in a real serving system. For each model pair, we run two vLLM (Kwon et al., 2023) instances, one per model, with prefix caching and priority scheduling enabled. A router selects the model for each call in an agentic session, and a router-side manager implements a request-level version of Harvest . ## 5 EVALUATION 

We evaluate S HADOW PREFILL through trace-driven simula-tion in this section and GPU testbed experiments in Section 6. 

5.1 Setup Model pairs and benchmarks. We simulate 22 model pairs: 5 on xRouteBench, 5 on FusionBench, 6 on Router-R1, and 6 on GHCP-coding (Table 1; full list in Table 3); the GPU testbed adds two SWE-bench pairs (Section 6). The simu-lated pairs span dense and MoE models from 7B to 141B parameters, same- and cross-family pairs, and the Qwen, Llama, Mistral, Gemma, GPT-OSS, and Granite families. The appendix shows all model pairs (Table 3 and Table 4). 

Production traffic. Each model runs on 4 instances, each using the smallest tensor-parallel degree among 1, 2, 4, and 8 H100 GPUs at which weights take at most half the HBM. Each instance serves normal traffic replayed from the Azure LLM inference conversation trace (Stojkovic et al., 2025) by default. Pools are provisioned for the trace’s peak hour: the normal-traffic rate is ρ=0 .7 of the capacity at which 90% of requests meet both SLOs at peak, and we run three one-hour windows (peak, median, and trough) at their relative trace load. The SLOs are TTFT ≤ max(1 s, 5× isolated prefill time ) and TPOT ≤ max(25 ms ,5× batch-1 decode time ).

5.4 Overheads and Disaggregation Token throughput. SHADOW PREFILL moves prefill work from the critical path into harvested idle capacity: un-der Harvest-SLO+Host , total prefill throughput, including shadow tokens, rises by 3.8% (Figure 8a), while the prefill throughput of routed and normal requests alone changes by -2.4%, because switch calls find their prefix cached. Decode throughput is unchanged. 

Energy and normal traffic. Shadow work runs on GPUs that are powered anyway, in slack that is mostly memory-bound, so energy per good request rises by only 0.4% under

Prefill/Decode disaggregation. On a disaggregated clus-ter, each model’s 4 instances split into prefill and decode instances, provisioned per trace for the same SLOs. Harvest-SLO ’s gain falls from 4.4% at ρ=0 .2 to 0.7% at

and Harvest-SLO+Host drops to 3.6%. At 120 s, shadows fit only into free memory, the switch-call hit rate falls from 72% to 54%, and Harvest-SLO+Host drops to 2.8%. ## 7 RELATED WORK 

Prefix caching and KV management. vLLM, SGLang, and CachedAttention reuse KV across requests that share a pre-fix (Kwon et al., 2023; Zheng et al., 2024; Gao et al., 2024); Mooncake, Pensieve, and LMCache extend the cache to host memory and remote storage (Qin et al., 2024; Yu et al., 2025; Liu et al., 2025). InferCept, KVFlow, and Continuum keep or prefetch a program’s KV across tool calls (Abhyankar et al., 2024; Pan et al., 2025; Li et al., 2025). All of them manage the cache of the model that produced it; SHADOW PREFILL 

builds a cache on a model that has not served the session. 

Across models, recent works translate one model’s KV into another’s (Liu et al., 2024; Fu et al., 2026; Dery et al., 2026; Heo et al., 2026), and ICaRus and PrefillShare train models to share a cache (Woo et al., 2026a;b). They require retraining and approximate the target’s KV while SHADOW PREFILL 

computes the exact KV (lossless). 

Harvesting and co-location. Harvest VMs and GPU co-location systems run low-priority work in spare capac-ity (Ambati et al., 2020; Han et al., 2022; Strati et al., 2024). ConServe co-serves offline batch jobs with online infer-ence (Qiao et al., 2026). Sarathi-Serve bounds iteration time with chunked prefill (Agrawal et al., 2024c). S HADOW PRE - 

> FILL

applies LLM inference harvesting uniquely to a new kind of work in agentic model routing. SHADOW PREFILL : Keeping Your Next Model Warm for Per-Step Model Routing in Agentic LLM Serving 

## 8 CONCLUSION 

We characterized the switch tax in per-step LLM routing and presented S HADOW PREFILL , a system that exploits idle GPU capacity to warm prefix caches on routed-to models without additional GPUs or compromising normal-traffic SLOs. Across 24 model pairs and five agentic benchmarks and traces, S HADOW PREFILL reduces switch-call latency by 8.5–21.4% and routed token cost by 22.5–46.1%.

## B SIMULATION DETAILS 

Deployments. Each model runs on the smallest tensor-parallel degree at which its weights take at most half of HBM: 7–12B models and GPT-OSS-20B on one H100; Gemma-2-27B, GPT-OSS-120B, and Granite-34B on two; Llama-3.x-70B and Mixtral-8x7B on four; Mixtral-8x22B and Qwen3-Next-80B-A3B on eight. 

Latency model in Vidur. An iteration contains prefill chunks ( q new tokens on c cached tokens) and decodes. Per layer, GEMMs take the maximum of compute and weight-read time; prefill attention adds compute and KV reads; decode attention adds KV reads and a per-sequence cost; tensor parallelism adds two all-reduces. MoE layers use active parameters for compute and total parameters for weight reads (Agrawal et al., 2024a). All operator latencies are grounded in measurements on H100 GPUs, providing high-fidelity estimates of prefill and decode execution times. 

Disaggregated cluster. Each model’s instances split into prefill and decode instances; the split (mostly 3P:1D) is the one with the highest SLO-compliant capacity for each model and normal-traffic trace. A prefill instance runs prefill-only iterations; KV moves to the decode instance, and the trans-fer and decode-queue wait count toward TPOT. A decode instance keeps a session’s context after each call, so the next transfer sends only the missing tokens. Load is set to ρ=0 .7 of each cluster’s own capacity, so colocated and disaggregated runs compare at the same relative load.

D.1 Serving Protocol Prototype. Each model uses one vLLM instance with prefix caching, chunked prefill, and priority scheduling (Table 4). After a call completes, the manager submits its prompt and response to the other model as lowest-priority shadow work with one output token. For non-append-only histories, it uses the next prompt’s prefix, capped at the completed prompt length. The destination computes its own KV, without cross-model transfer. Newer completed calls supersede pending shadows. Admission requires an empty destination waiting queue and permits one in-flight shadow per instance. KV-usage and SLO-based admission do not constrain these runs. The prototype omits per-iteration credit, the SLO-slack controller, evict-first shadow KV, and the host tier. Meanwhile, Oracle+Host grows from 10.0% to 14.6%, because more models mean more switches. The gap between the two comes from next-model prediction, which a router can close by exposing its scores for upcoming calls, or which an agent’s plan can supply when it fixes the model of the next steps ahead of time. 

What does it mean for the router? Switch-aware routers penalize switches (Zhang et al., 2026a;c), because a switch has so far cost a cold prefill. With S HADOW PREFILL , the cost of a switch depends on how much of the candidate’s prefix is warm, and the router can query that state and price each switch accordingly. A router that switches more freely gains accuracy (Section 5.3), and S HADOW PREFILL 

makes those switches cheaper: with frequent switches, 

Harvest-SLO+Host reduces LLM-call latency by up to 5.8% (Section C). Router and serving system can also cooperate in the other direction: the router’s switch probabilities can drive the ordering of shadow jobs, and a more accurate predictor lets a gate such as Predictive skip unlikely targets while missing fewer switches. 

Finer-grained model switching. SHADOW PREFILL targets routers that decide per LLM call. Systems that switch within a call, per token or per segment, such as speculative decod-ing (Leviathan et al., 2023; Chen et al., 2023a), speculative cascades (Narasimhan et al., 2025), and token-level rout-ing (Kwon et al., 2026), leave no gap between the decision and the next model’s use of the context. These systems keep both models’ KV current at every step by construction, and pay for it on the critical path of decoding. S HADOW PREFILL 

instead trails the routed model by the output of the current call and runs only in harvested slack, which suits decisions made once per call. Cross-model KV translation (Liu et al., 2024; Fu et al., 2026; Heo et al., 2026) could fill the remain-ing gap at a switch for models in the same family, at the cost of approximate rather than exact KV. 

When S HADOW PREFILL helps less. SHADOW PREFILL 

saves prefill, so its gain shrinks when prefill is a small part of a switch call. For targets above 50B, decoding dom-inates and switch-call latency falls by 3% (Section 5.5); doubling the tensor-parallel degree shortens prefill and lowers Harvest-SLO+Host ’s LLM-call gain to 3.5% (Sec-tion C). Long reasoning outputs, as from DeepSeek-R1, leave the target’s instances little slack to harvest. Rare switches leave little to warm: at about 0.5 switches per ses-sion, Harvest-SLO+Host ’s LLM-call gain is -0.2%. Under heavy normal traffic, the SLO-slack controller finds little capacity ( Harvest-SLO gives 0.7% at ρ=0 .9), and the host tier provides most of Harvest-SLO+Host ’s gain. 

Wasted work and energy. Shadow prefill is speculative: 63% of Harvest-SLO+Host ’s shadow tokens are never used, because the router decides only when the call arrives. On colocated clusters this work rides on iterations that run anyway, and energy per good request rises by 0.4%. On P/D-disaggregated clusters, shadow work wakes otherwise-idle prefill GPUs and raises energy by 11.5% (Section 5.4). Operators that cap power or bill energy can gate shadow work by switch probability, or limit it to the top-1 target, trading part of the latency gain for less waste.
