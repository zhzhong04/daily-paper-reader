# OSTINATO : Fast CPU–GPU MoE Inference for Local Agents via Resident Experts in Every Forward Pass 

Junning Zhu 1

## Abstract 

Language-model agents increasingly run on work-stations with a few consumer GPUs, where large mixture-of-experts (MoE) models keep part of their experts in host memory. With existing CPU– GPU engines, these agents get fast prefill or fast decode, not both: llama.cpp’s expert cache skips forward passes of more than 32 tokens to keep the experts of decode cached, so an agent waits 2.1– 2.8 s after each tool output, whereas its default layer placement shortens this wait but is 1.5–1.6 ×

slower in decode. Our key insight is that a short prefill touches too many distinct experts to upload, yet sends 84% of its expert activations ( routes ) to a stable set of experts that fits in GPU memory. We present O STINATO , a CPU–GPU MoE infer-ence engine that computes these experts on the GPUs in every forward pass without changing what the model computes. Short prefills split their routes, leaving fewer than one of a token’s six routed experts per layer to the CPU; long prefills upload each distinct cold expert once; and each decode step runs as one fixed-shape CUDA graph per GPU. On real coding and customer-service agent sessions with DeepSeek-V4-Flash on four RTX 4090D GPUs, O STINATO is the fastest en-gine in both phases and finishes every session sooner than all six baselines. Against llama.cpp and KTransformers, it cuts the median wait after a tool output by 22–55% and finishes sessions 1.4–2.5 × sooner.

Such methods compress experts (Zhou et al., 2025b), re-design or fine-tune the router so that consecutive tokens reuse experts (Zhou et al., 2025a; Zhu et al., 2026b), or reroute tokens toward experts that other tokens in a batch already load (Oncescu et al., 2026). While effective in reducing expert loads, these changes alter the tokens that the model generates, so each method has to re-establish quality on downstream benchmarks; FloE, for example, re-ports an average degradation of 4.4–7.6% on downstream tasks (Zhou et al., 2025b). For an agent, whose next tool call depends on every token it generates, these findings favor an inference engine that leaves the model’s computation un-changed, particularly when the agent acts without a person checking each step. An alternative line of work leaves the model unchanged, holding some experts in GPU memory and the rest in host memory (Kamahori et al., 2025; Cao et al., 2025; Chen et al., 2025; Zhong et al., 2025; The ggml authors, 2026). When a forward pass selects a host-resident expert, the CPU computes it, or its weights are uploaded over PCIe to a GPU, either on demand or ahead of time by a predictor (Hwang et al., 2024; Xue et al., 2024; Song et al., 2024a). To hide the cost of host-resident experts, existing engines overlap CPU and GPU computation (Chen et al., 2025; Yang et al., 2026a) or cache frequently used experts on the GPUs (am17an, 2026; spiritbuun, 2026). These engines speed up decode on consumer hardware, but agent sessions expose two mis-matches. First, the wait after each tool call is a short prefill, too short for uploading experts to pay off . Every agent framework turns a task into a session of requests, one after each tool output or user message: a held-out coding ses-sion in our traces sends 42 to 100 of them, and each request prefills only its newest tokens, a median of 249. Existing engines therefore keep these prefills away from the experts on their GPUs. The expert cache of llama.cpp (am17an, 2026), which ik llama.cpp (ikawrakow, 2026) ports, serves only forward passes of up to 32 tokens, on the premise that larger ones use most experts of a layer, and the cache of the tuned fork buun (spiritbuun, 2026) serves only decode. In a short prefill, these engines therefore leave the experts in their caches unused, and KTransformers (Chen et al., 2025) computes on the CPU every selected expert outside the 58 per layer that it keeps on the GPUs. On our coding sessions, these engines keep the agent waiting a median of 2.4–2.8 s for the first token after each tool output (Figure 1a). Second, 

existing engines make one phase of a turn fast at the expense of the other . Their designs and evaluations cen-ter on decode speed and single requests (Chen et al., 2025; Yu et al., 2026; Yang et al., 2026a), but agent turns gener-ate only a few hundred tokens after each prefill, so prefill takes 24–44% of the prefill and decode time of the engines that cache experts. Placing whole layers on the GPUs, as llama.cpp does by default, shortens these prefills but slows decode to 47.1 ms per output token, against 31.5 ms with its expert cache (Table 3). These mismatches raise the central question of this paper: 

How can a CPU–GPU engine shorten the wait after each tool call without slowing decode or altering the model’s outputs? 

Our key observation is that a short prefill looks unsuited to the GPU only when it is counted in distinct experts rather than in token–expert routes. Counted in experts , a prefill of a few hundred tokens touches many experts of each layer, too many to upload for so few tokens, and caches skip it so as not to evict the experts that decode uses. Counted in routes , the same prefill is concentrated: expert routing in agent sessions is skewed and stable across sessions, and the 44% of experts that development sessions route to most often receive 84.0% of the routes of held-out sessions. A GPU that keeps these experts resident therefore serves most of every forward pass, prefill and decode alike, without uploading or evicting anything. Building on this observation, we present O STINATO , a CPU–GPU MoE inference engine that computes the experts resident on the GPUs in every forward pass of an agent session. OSTINATO combines three techniques. First, cross-layer expert residency fills one pool per GPU, shared by its layers, with the experts that development sessions route to most often. A cost model calibrated inside the engine guides this choice and bounds its distance from the best static residency set by 0.15 ms per decode step. Second, size-dependent prefill paths serve a short prefill through a split path that computes its hot routes on the GPU and only its cold routes on the CPU, and a long prefill through an upload path that uploads each distinct cold expert once. Third, a decode graph per GPU computes the cold experts of a step on a resident CPU thread pool while the GPU computes the hot ones. All-zero slots ( zero slots ) take the place of cold experts, so the GPU’s tensor shapes stay fixed however many selected experts are hot, so all layers of a GPU replay as one CUDA graph, and GPU memory that decode leaves idle holds a few more experts. Ultimately, our design rethinks short prefills in hybrid MoE inference: it serves them from the experts that the GPUs already hold rather than from the CPU alone, so the GPU memory that hybrid engines devote to decode works in every turn. We implemented O STINATO in llama.cpp and evaluated it against six CPU–GPU engines, llama.cpp in its default layer placement and with its expert cache, ik llama.cpp, KTransformers, buun and FreeToken (Yang et al., 2026a), by replaying real coding (SWE) and customer-service ( τ 2-bench) agent sessions with DeepSeek-V4-Flash and Qwen3-235B-A22B on a workstation with four RTX 4090D GPUs. ## 2. Background and Motivation 

2.1. MoE Inference with Host-Resident Experts 

An MoE layer (Shazeer et al., 2017; Lepikhin et al., 2021) replaces the feed-forward network of a transformer block with a router and E routed experts, of which each token uses k, plus shared experts that every token uses. Attention, router and shared-expert weights are used by every token, so they reside in GPU memory and run on the GPU. Routed experts are used sparsely, so the experts that do not fit, which we call cold , stay in host memory, while the experts in GPU memory are hot . A forward pass runs the model once over a batch of tokens. If it selects a cold expert, the engine either computes the expert on the CPU from host memory or uploads its weights over PCIe so that a GPU computes it. Which of the two is cheaper depends on how many tokens of the forward pass use the expert: an upload costs the same for one token or for many, whereas the CPU’s cost grows with every token routed to the expert. An expert of DeepSeek-V4-Flash, for example, takes 13.4 MB in MXFP4 and 0.53 ms to upload over PCIe 4.0 on an idle bus, while our CPUs compute one token of it in about 0.18 ms. On an idle bus, an upload thus pays off only once about three tokens of the forward pass route to the expert. Engines built on llama.cpp (The ggml authors, 2026) choose between the two by the size of the forward pass: below an 

upload threshold , cold experts run on the CPU, and from the threshold on, the selected experts are uploaded. Ex-pert caches additionally keep frequently or recently used experts on the GPUs and admit new ones from decode steps and other small forward passes under a replacement pol-icy (am17an, 2026; spiritbuun, 2026). They serve only such small forward passes: the cache of llama.cpp skips any forward pass of more than 32 tokens, which it expects to use most experts of a layer and to evict the experts used in decode. Compared with whole-layer placement, expert caches decode faster because more of each step’s experts are already on the GPUs (31.5 against 47.1 ms per output token on our held-out SWE sessions). llama.cpp evaluates each forward pass as a computation graph and replays the GPU segments of decode steps as CUDA graphs (NVIDIA Corporation, 2026), which requires every step to keep the same operators and tensor shapes. 

2.2. Agent Sessions on Hybrid Engines 

Unlike single chat requests, agent sessions consist of many turns, each of which appends new messages or tool outputs to a long context, prefills them and generates a short response (Zhu et al., 2026a; Yuan et al., 2026). To examine the implications for hybrid engines, we replay software-engineering (SWE) sessions and τ 2-bench tasks (Section 4.1) with DeepSeek-V4-Flash on four RTX 4090D GPUs under the baselines of our evaluation. The results reveal that existing hybrid engines are ill-suited for agent sessions, primarily due to the following properties: 

Short prefills on the CPU. Because each turn reuses the previous turn’s KV cache, it prefills only its new tokens (a median of 249 per SWE turn and 118 per τ 2 turn), and three quarters of SWE turns prefill fewer than 512 tokens. Such forward passes are too large for the expert caches, which serve only forward passes of up to 32 tokens in llama.cpp and its port in ik llama.cpp and only decode in buun. With its upload threshold of 512 tokens, llama.cpp’s expert cache therefore computes all six experts that each token of a short prefill selects on the CPU, even those cached on the GPUs, 3OSTINATO : Fast CPU–GPU MoE Inference for Local Agents 

as buun does; KTransformers computes every selected ex-pert outside the 58 per layer that it keeps on the GPUs on the CPU. These four engines take a median of 2.36–2.78 s on SWE and 1.80–2.11 s on τ 2-bench to return the first token after a tool output (Table 3). 

One phase at a time. The engines trade the two phases of a turn against each other (Figure 6a and b). llama.cpp’s default layer placement keeps whole MoE layers on the GPUs, so in a short prefill only the layers left in host memory compute their experts on the CPU, and its median wait after a tool output is 1.66 s on SWE and 1.25 s on τ 2-bench. In decode, however, each of these layers computes all its selected experts on the CPU at every step. Over our held-out sessions, the three expert caches spend 42–58% more time in prefill than layer placement but 16–44% less in decode. 

Skewed, stable routing. Ranked by how often development sessions route to them, the top 44% of the experts receive 84.0% of the routes of held-out sessions, so the ranking carries over from one session to the next. Short prefills follow the same skew: although each touches many experts of a layer, the experts that O STINATO keeps on the GPUs serve 84% of its routes (Section 2.3). A set of experts chosen offline could thus serve most routes of every forward pass. These findings reveal a mismatch between existing hybrid engines and agent sessions: the GPU memory of each engine speeds up either the short prefills that the agent waits on or the decode steps that generate its responses, although one set of resident experts could serve both. 

2.3. From CPU-Bound to GPU-Served Prefill

(II) Uploads pay off only for large forward passes. Since an upload moves an expert’s 13.4 MB regardless of how few tokens use it, we swept the upload threshold on a de-velopment session, with buun as the engine. Its prefill time falls from 352.7 s with a threshold of 128 tokens and 329.2 s with 256 to 310.3 s with 512, and rises again to 323.6 s with 1,024. The forward passes that the lower thresholds move to the upload path are short prefills like the turn of Figure 2, so uploading their experts costs more than computing them on the CPU. A forward pass of 2,048 tokens, in contrast, touches 117 of a layer’s 143 cold experts, and one upload per distinct expert is cheaper. A short prefill should there-fore leave its cold experts to the CPU and a large one should upload them, which implies a single threshold on the size of a forward pass. 

(III) Decode can hide the CPU’s fixed cost. A decode step processes one token, so each layer selects only k experts, and a cold expert costs the CPU about 0.18 ms per route. Meanwhile, the GPU branch of a layer takes about 0.14 ms 4OSTINATO : Fast CPU–GPU MoE Inference for Local Agents 

regardless of how many hot experts it computes. The CPU can therefore compute a layer’s cold experts while the GPU computes the hot ones, which hides nearly all of the CPU’s fixed cost. Because the router’s output is the only input that both branches need, a decode step can keep the same shapes regardless of the routing and replay all layers of a GPU as one CUDA graph, which hands the cold experts to the CPU without a host-driven launch and wait in every layer. Short prefills reuse the same index tables in their split path. These observations motivate an execution design that uses the resident experts in every forward pass and sends each cold expert to the CPU or over PCIe by the size of the forward pass. 

## 3. Design of O STINATO 

3.1. System Overview 

OSTINATO works in two stages, offline residency planning and online execution, numbered as in Figure 3. 

Offline residency planning. Executed once before deploy-ment, this stage decides which experts stay on the GPUs (Figure 3a). O STINATO ranks the experts of every layer by how often development sessions route to them ( ❶). A capac-ity test then fixes the number of expert slots on each GPU: the longest development request, with the workload’s tool definitions, must complete while every GPU keeps a fixed margin free at its peak ( ❷). Finally, O STINATO fills each GPU’s slots with the highest-ranked experts of its layers, so the layers on a GPU share one expert pool and the number of slots that a layer receives follows its routing rather than a fixed quota. The resulting residency set is written to a file that the engine loads at start-up ( ❸). 

Online execution. At start-up, O STINATO copies the hot experts into the expert pool of each GPU and builds index tables that map every expert to a pool slot or to the CPU. Once the router selects the experts of a layer, the index tables split them into a GPU branch over the hot experts and a CPU branch over the cold experts ( ❹). In a decode step, a resident CPU thread pool computes the cold experts while the GPU computes the hot ones ( ❺), and a wait kernel joins the two branches before the GPU adds their outputs (❻). All layers on a GPU replay as one CUDA graph, and GPU memory that decode leaves unused holds a few more experts for later steps (Section 3.4). A prefill forward pass takes the split path or the upload path depending on its size (❼; Section 3.3). In every case, the layer’s output is the routing-weighted sum of all k selected experts, as in the original model.

Rule 2: compute a decode step’s cold experts on the CPU. 

Uploading a cold expert for the current token exposes its transfer (0.53 ms on an idle bus and up to 1.20 ms while the CPU reads host memory). The CPU branch, in contrast, runs beside the GPU branch and exposes about β per cold route. A decode step therefore computes its cold experts on the CPU. Uploading an expert for later steps is a separate decision, which pays when the CPU time that its later routes save exceeds the transfer that the GPU cannot hide. O S-

TINATO makes it only in GPU memory that decode would leave unused (Section 3.4), and the residency set itself stays fixed during the run. 

Rule 3: switch prefill paths once, by the size of the for-ward pass. An n-token prefill forward pass with r(n) cold routes can take one of two paths. The split path computes the hot routes on the GPU and the cold routes on the CPU, and the upload path uploads its u(n) distinct cold experts once and computes everything on the GPU. The CPU’s cost grows with the cold routes, whereas the upload cost grows with the distinct cold experts, which the experts of a layer bound: 

Proposition 3.2 (One switch between the prefill paths) . Let the routes of a prefill forward pass be stationary over its tokens, let ¯u(n) be the expected number of distinct cold experts that its first n tokens select, and let the expected cost difference between the split and the upload path be 

ϕ0 + ϕ1n − ϕ2 ¯u(n), with ϕ0 < 0, ϕ1 > 0 and ϕ2 > 0.Then there is an n∗ such that the split path is cheaper for every n < n ∗ and the upload path for every n > n ∗.

A single prefill threshold Np therefore suffices (Section 3.3; proof in Appendix B). 

3.3. Size-Dependent Prefill Paths Split path. A prefill forward pass with fewer than Np tokens takes the split path. As in decode, the CPU computes the cold routes from host memory and the GPU computes the hot routes from the pool, but the two branches run one after the other. The GPU thus serves the large majority of the routes of the forward pass from experts that it already holds, and nothing crosses the PCIe link. 

Upload path. A forward pass with Np or more tokens takes the upload path, whose cold branch is a GPU expert operator over a compact host tensor that holds only the layer’s cold experts. O STINATO translates each cold route to its expert in this tensor and each hot route to a zero slot (an all-zero expert that contributes nothing). The upload therefore copies only the distinct cold experts of the forward pass into a staging buffer. The GPU then computes the uploaded experts from the staging buffer and the hot experts from the pool, and hot experts are never uploaded again. 

Threshold. We set Np = 512 tokens, where the CPU and upload paths of llama.cpp cross on our machine (be-tween 512 and 1,024 tokens) and where buun prefills a 6OSTINATO : Fast CPU–GPU MoE Inference for Local Agents 

development session fastest (Section 2.3). A single path for all forward passes would be slow for one of the two kinds: uploads waste PCIe time on small forward passes, whose cold experts serve few tokens, whereas the CPU is far slower than one upload of the distinct cold experts of a large forward pass. 

3.4. Decode in One Graph per GPU Fixed shapes through zero slots. A CUDA graph replays fixed operators on fixed shapes, but the number of hot ex-perts that a token selects changes from step to step. Each GPU’s pool therefore reserves one zero slot for each of the 

k positions, and the GPU index table maps every cold expert to the zero slot of its position. The GPU branch thus always computes k distinct experts, and the graph keeps the same operators and shapes in every decode step, regardless of the routing. O STINATO builds on this fixed shape to capture all layers on a GPU as one CUDA graph. In each layer, the graph publishes the routing result and whether any selected expert is cold. For a layer with cold experts, it writes the to-ken’s activations and the cold expert IDs into a mapped host buffer, from which a resident CPU thread pool computes the CPU branch and writes the result back. A wait kernel in the graph blocks only until that result arrives, after which the GPU adds the two branches, and a layer whose experts are all hot skips the CPU entirely. The GPU branch and the shared expert run while the CPU computes, so a step pays only for the part of the CPU branch that the GPU work does not hide, as Rule 1 assumes. Zero slots occur only in layers with a cold route, where the CPU branch takes at least α + β = 0 .324 ms, more than twice Gℓ, so the GPU computes them within its wait for the CPU and they add no time to a decode step. 

Borrowed memory. The memory that the capacity test re-serves for the largest prefill forward pass lies unused while sessions decode, and O STINATO lends it to the cold experts that decode keeps computing on the CPU. Every CPU use raises an expert’s score, which decays over decode steps. A background thread uploads the highest-scored experts into free slots of the GPU that holds their layer, and once these slots are full, a newcomer replaces the lowest-scored borrowed expert only when it scores clearly higher. An up-loaded expert joins the GPU branch at a later token boundary, where the index tables of both branches switch together. A prefill forward pass returns all borrowed memory before it runs, so a borrowed expert serves only the decode of one request. Because the uploads overlap with the GPU’s work, the GPU waits for them about 0.01 ms per decode step, and the decode step becomes 1.4 ms shorter on SWE and 0.4 ms shorter on τ 2-bench (Section 4.5). 

Alternatives. Dispatching each cold expert from the host (Kamahori et al., 2025) adds a host operation per expert and prevents graph replay. SeqMoE keeps a fixed expert pool with lookup tables so that its decode loop can be cap-tured as a graph (Wang et al., 2026b). O STINATO adds a zero slot per position, a pool shared across layers, the prefill paths and the CPU branch inside the graph. 

3.5. Running Other MoE Models 

The residency planner, the capacity test, the index tables and both prefill paths work on the expert tensors of each layer, not on model-specific code. They therefore run Qwen3-235B-A22B, whose 94 MoE layers each route a token to 8 of 128 experts, without changes to the model code. Its Q4 K M experts store their projections in two quantization types, so the expert pool groups resident experts by their actual size in bytes. On Qwen3-235B-A22B, decode runs the two branches with llama.cpp’s per-segment CUDA graphs, so its results isolate the gains of the residency planner and the prefill paths on a second architecture. 

3.6. Implementation 

We prototype O STINATO on top of llama.cpp (The ggml authors, 2026) with CUDA 12.6 and keep llama.cpp’s na-tive expert operators for both branches. The two branches, the index tables, the zero slots, the decode graph and the borrowed memory add about 4.3K lines of C++ and CUDA to llama.cpp. The upload path builds on llama.cpp’s selec-tive upload, which copies only the experts that the routes of a forward pass reference. The residency planner, the capacity test and the selection of the borrowing parameters run offline. O STINATO pre-allocates the expert pool and the staging buffer of the upload path before it counts slots, so the pool never competes with prefill for memory at run time. On our machine, the borrowed memory holds 544 ex-pert slots across the four GPUs, and the background thread copies experts in chunks that alternate between the two PCIe root complexes. To keep a whole decode step replayable, the mapped buffers between each GPU and the CPU thread pool are allocated once at start-up and reused by every step.

4.1. Experimental Setup Models. We evaluate O STINATO on two publicly available MoE models from two families. Specifically, we include DeepSeek-V4-Flash (DeepSeek-AI, 2026b) (V4), on which we run the full method, and Qwen3-235B-A22B (Qwen Team, 2025) (Qwen3), on which we run the general resi-dency and prefill paths (Section 3.5). The two models differ in how many experts they have, how wide each expert is and how many layers hold them. Table 1 lists their main parameters. We serve the routed experts of V4 in its native MXFP4 format and those of Qwen3 in llama.cpp’s Q4 K M format, both on four GPUs. 

Workloads. To evaluate performance, we replay agent trajectories from two public collections (Table 2): Open-Hands (Wang et al., 2025) sessions that resolve SWE-rebench issues (Trofimova et al., 2025; Badertdinov et al., 2025) and τ 2-bench conversations (AgentSuite, 2026; Bar-res et al., 2026) in the airline, retail and telecom domains, each with its recorded tool outputs. All experiments serve one session at a time, representing the typical local deploy-ment of an agent. On V4, we replay all 13 held-out SWE sessions and 60 held-out τ 2-bench tasks; on Qwen3, we replay the same 60 tasks, whose trajectories Qwen3 itself generated. Development sessions choose the residency sets and thresholds, and held-out sessions are used only for eval-uation. Every engine is forced to emit the recorded tokens, so all systems receive and emit the same tokens (Pan et al., 2026). To isolate the effect of input length, we also prefill 128 to 1,024 new tokens after eight development prefixes and generate 128 tokens (Section 4.4). 

Hardware. We adopt a workstation with four RTX 4090D GPUs (24 GB each) on PCIe 4.0, two Intel Xeon Plat-inum 8358 CPUs (64 cores) and 512 GB of DDR4 memory as our testbed. All systems run on this machine, and its CPUs read host memory at 86–88 GB/s. 

Baselines. We compare O STINATO with six CPU–GPU MoE inference systems, each a distinct way of placing experts. All of them run on the same machine and pass the same capacity test, in which the longest development request must complete (Appendix C). (1) llama.cpp (lay-ers) (The ggml authors, 2026) maps each MoE layer as a whole to a GPU or to the CPU, and we let its automatic fit choose the layers. (2) llama.cpp expert cache (am17an, 2026) keeps experts in a GPU cache shared by the layers of each device and uploads missing experts on demand; we use the largest cache budget that passes the capacity test. (3) ik llama.cpp (ikawrakow, 2026) is a llama.cpp fork with its own CPU kernels and a GPU cache for host-resident experts (SamuelOliveirads, 2026), with the cache budget of 69,632 MiB chosen on development sessions. (4) buun (spir-itbuun, 2026) is a llama.cpp fork with a dynamic expert cache that admits experts by decaying access counts and is warmed with a routing profile of the development ses-sions; we use the upload threshold of 512 tokens chosen on a development session. (5) KTransformers (Chen et al., 2025; kvcache-ai, 2026) keeps a fixed number of experts per layer on the GPUs and computes the others on the CPU. We use its default uniform placement and the fastest of seven configurations on a development session, which keeps 58 experts per layer on the GPUs, and we replay it with a sepa-rate lean client because it serves a different HTTP interface. (6) FreeToken (Yang et al., 2026a), an edge-native MoE engine, runs on one GPU, so we compare it with a one-GPU configuration of O STINATO with the same 32 CPU cores. 

Evaluation Metrics. We use the total request time (the sum of the wall-clock times of all requests in a session) as our primary metric, and we also report the time to first token (TTFT) and the time per output token (TPOT). We report it for every turn that follows a tool output, measured at the client from sending the request that carries the tool output to receiving the first new token, and report the τ 2-bench turns that follow a user message separately. TPOT is the interval between the first and the last output token divided by the number of output tokens minus one. ## 5. Related Work 

MoE routing and expert locality. Recent open-weight MoE models route each token to a few of many fine-grained experts, such as 6 of 256 per layer in DeepSeek-V4-Flash and 8 of 128 in Qwen3-235B-A22B (DeepSeek-AI, 2026b; Yang et al., 2025). To make expert accesses local, Oracle-MoE trains a router so that consecutive tokens activate con-sistent experts (Zhou et al., 2025a), ReMoE fine-tunes only the gate of a trained model (Zhu et al., 2026b), OEA reroutes tokens toward experts that the batch already loads (Oncescu et al., 2026), and FloE compresses experts (Zhou et al., 2025b). O STINATO addresses the same cost without touch-ing the model: it exploits the skew that the unchanged router already shows across agent sessions, so it computes the orig-inal model and needs no accuracy evaluation. 

MoE inference with host-resident experts. MoE-Infinity, HOBBIT and Pre-gated MoE cache or prefetch experts on the GPU (Xue et al., 2024; Tang et al., 2024; Hwang et al., 2024), and ZipMoE compresses expert weights losslessly to cut I/O on edge devices (Yang et al., 2026b). Fiddler, MoE-Lightning, KTransformers, HybriMoE and FreeTo-ken split expert computation between the CPU and the GPU (Kamahori et al., 2025; Cao et al., 2025; Chen et al., 2025; Zhong et al., 2025; Yang et al., 2026a). llama.cpp offers whole-layer placement and an expert cache for host-resident experts (The ggml authors, 2026; am17an, 2026), and its fork buun adds a dynamic cache with decaying ac-cess counts (spiritbuun, 2026). OSTINATO differs from these engines in using its resident experts in every forward pass: its split path serves short prefills from GPU-resident experts, which existing caches leave to the CPU or to up-loads. KTransformers places shared experts on the GPU and routed experts on the CPU, and it fits the whole decode path of a token into one CUDA graph by issuing the CPU’s work through host callbacks (Chen et al., 2025). The decode graph of O STINATO also computes routed experts on the GPUs, whose selection changes with every token: zero slots keep their shapes fixed, and a wait kernel on the device joins the CPU branch. For dense LLMs, PowerInfer keeps frequently activated neurons on the GPU and computes the rest on the CPU (Song et al., 2024b); O STINATO answers the corresponding question for MoE models in both phases. Lossless compression (Yang et al., 2026b) is complementary to O STINATO : it lowers the cost of each transfer or host read, whereas O STINATO lowers how many expert computations the CPU and the PCIe link must serve. 

Serving LLMs with tool calls. InferCept decides for each paused request whether to keep, swap or recompute its KV cache (Abhyankar et al., 2024), and AugServe orders re-quests and adapts batch budgets to the states that tool calls create (Wang et al., 2026a). Cake computes part of a cached 12 OSTINATO : Fast CPU–GPU MoE Inference for Local Agents 

prefix on the GPU while loading the rest from storage (Jin et al., 2025), prefix caching avoids recomputing earlier turns (Kwon et al., 2023; Zheng et al., 2024; Gim et al., 2024), and DistServe places prefill and decode on different GPUs (Zhong et al., 2024). These systems reduce the work that a returning request needs, whereas O STINATO reduces the time that this work takes on a hybrid machine, and it reuses the KV cache of earlier turns as they do. 

## 6. Conclusion 

We presented O STINATO , a CPU–GPU MoE inference en-gine for agents on local workstations. Exploiting the skewed and stable routing of agent sessions, O STINATO keeps the experts that these sessions route to most often on the GPUs and computes them there in every forward pass. Short pre-fills split their routes between the GPU and the CPU, long prefills upload each cold expert once, and decode steps run as one CUDA graph per GPU, with a cost model calibrated inside the engine guiding these choices. On replayed coding and customer-service agent sessions, O STINATO spends less time in both prefill and decode than the four-GPU base-lines on DeepSeek-V4-Flash, and its residency and prefill paths alone shorten the sessions of Qwen3-235B-A22B, all without changing what the model computes.
