## 摘要
现代LLM智能体在持久化工作空间中运行，其累积历史可能超出GPU KV容量和模型原生上下文窗口。现有系统通常将较旧的上下文压缩为摘要或稍后作为文本检索，要么丢失细粒度的执行证据，要么反复预填充模型已处理过的内容。我们提出KVMem，一种KV上下文虚拟化系统，将溢出的工作空间历史作为分页KV状态保存在GPU内存、主机内存和NVMe中。KVMem使用轻量级的、模型原生的注意力空间索引来选择相关的历史块，并实现受模型原生上下文窗口限制的、查询相关的执行视图。在跨越长达一百万token历史的长上下文智能体基准测试（包括LongMemEval、MemoryAgentBench和AgentLongBench）上进行的大量评估表明，与压缩方法（处理上下文溢出的实际标准）相比，KVMem通常能实现更高的任务效用和更高的推理效率。在DeepSWE长上下文测试中，使用Qwen3.8-27B时，KVMem将仅使用压缩上下文管理的任务成功率从43.8%提高到48.4%。在我们本地部署评估中，KVMem在配备24GB RTX 5090笔记本电脑GPU的现成笔记本电脑上运行Qwen3.6/3.8-27B NVFP4与MTP，虚拟化高达1M token的智能体工作空间——是模型原生256K token上下文窗口的四倍。在单会话设置中，KVMem生成约50 tokens/s，为本地智能体执行提供交互响应性。更广泛地说，通过将可寻址工作空间大小与LLM的原生上下文窗口解耦，KVMem为实现工作空间可增长超过该窗口的长期运行智能体提供了实用途径。

## Abstract
Modern LLM agents operate in persistent workspaces whose accumulated history can exceed both GPU KV capacity and the model's native context window. Existing systems typically compact older context into summaries or retrieve it later as text, either losing fine-grained execution evidence or repeatedly prefilling content that the model has already processed. We present KVMem, a KV-context virtualization system that preserves overflowed workspace history as paged KV state across GPU memory, host memory, and NVMe. KVMem uses lightweight, model-native attention-space indexes to select relevant historical blocks and materializes a query-dependent execution view bounded by the model's native context window. Extensive evaluations on long-context agent benchmarks spanning histories up to one million tokens, including LongMemEval, MemoryAgentBench, and AgentLongBench, show that KVMem generally achieves higher task utility and greater inference efficiency than compaction-based approaches, the de facto standard for handling context overflow. In the DeepSWE long-context test with Qwen3.8-27B, KVMem improves task success from 43.8% with compaction-only context management to 48.4%.   In our local-deployment evaluation, KVMem runs Qwen3.6/3.8-27B NVFP4 with MTP on an off-the-shelf laptop equipped with a 24\,GB RTX 5090 Laptop GPU, virtualizing agent workspaces of up to 1M tokens-four times the model's native 256K-token context window. In a single-session setting, KVMem generates $\sim$50 tokens/s, providing interactive responsiveness for local agent execution. More broadly, by decoupling addressable workspace size from the LLM's native context window, KVMem provides a practical path toward long-running agents whose workspaces can grow beyond that window.

## 1. 核心问题与研究动机

现代LLM智能体（Agent）在持久化工作空间（workspace）中长时间运行，其积累的执行历史（用户指令、文件内容、工具输出、执行日志等）会快速增长并面临两个执行瓶颈：
- **GPU内存瓶颈**：即使历史总量不超模型原生上下文窗口，KV缓存也因与模型权重、运行时缓冲区等竞争有限的GPU显存而无法全部驻留；
- **上下文窗口瓶颈**：工作区累积历史本身可能超过模型原生上下文窗口（如Qwen3.6-27B原生窗口为256K tokens，而长上下文基准轨迹可达数百万tokens）。

现有上下文溢出管理均采用**以文本为中心的抽象**：
- **Compaction（压缩）**：将较早历史用摘要形式存储，存在「提前决定未来相关性」的固有问题。论文通过不可区分性论证说明：若两个不同历史 H1、H2 映射到相同压缩表示 C(H1)=C(H2)，则任何依赖两者差异的后续查询都无法从摘要中恢复答案——压缩本质上无法保证保留所有未来关键细节；
- **文本检索（如MemGPT、Mem0等）**：虽可部分恢复遗漏证据，但每个被检索的token都需要重新prefill，即模型重复计算已处理过的内容。文本检索的成本为 `T_text = T检索 + T_prefill(N_R)`，而若保留KV状态，则可表达为 `T_KV = T检索 + T加载 + T恢复`，前者始终包含一项目随检索量增长的重复prefill开销。

**核心洞察**：上下文溢出不等于必须丢失已算得的KV状态——历史内容被移出执行窗口之前已经完成了KV编码，唯一的不确定性仅是未来哪一部分会被再次需要。借鉴虚拟内存思想，应将**可寻址工作区大小**与**GPU物理驻留KV量**解耦。

## 2. 方法论：KVMem系统设计

### 2.1 整体架构

KVMem将已处理的工作区历史作为**分页KV块（KV blocks）**保存在GPU内存、主机内存与NVMe构成的多级存储中。每个KV块是检索评分、选择和搬运的基本单位（默认32个token）。在每个智能体步骤，仅物化一个**有界、查询相关的执行视图（execution view）**，并满足预算约束 `N(Qτ) + B块·|Rτ| ≤ min(B模型, BGPU)`。

三个抽象层面的区分是本工作的理论基础：**可寻址工作区** ≠ **模型可见执行视图** ≠ **GPU驻留KV集合**。

### 2.2 三大核心机制

#### (1) Step-Level Memory Scheduling（何时召回）
- 通过分析8个OpenHands SWE-bench Lite rollouts中相邻128-token滑窗的注意力KL散度，发现：**同一agent step内的相邻窗口KL均值仅0.070 bits，而跨step边界的窗口KL均值达2.59 bits（高出37.3×）**；
- 因此选择在每步prefill完成后、decode开始前，更新历史工作集一次；解码期间选定工作集保持不变。这实现了「回忆时机接近注意力变化点，同时避免频繁更新开销」。

#### (2) Query-Conditioned KV Retrieval（召回什么）
- **Mean-K索引构造**：每个KV块在每层、每个KV头上用「去RoPE位置编码后的K向量均值」作为紧凑表示：

  `k̄(l,b,g) = (1/|b|) Σ_{i∈b} k̃(l,i,g)`  （公式9）

- **查询条件化块评分**：当前查询的去位置编码query向量与所有候选块的Mean-K向量做缩放点积，跨候选块执行全局softmax归一化，公式为：

  `R_b = Σ_m mean_{l,h} [ softmax_{b'∈C}( q⊤_{l,m,h} · k̄_{l,b',g(h)} / √d ) ]_b`  （公式10）

- **稀疏性依据**：分析显示每个窗口平均覆盖103.1个历史块，但top-8块即捕获66.5%的历史注意力、top-16块捕获77.0%——不需要物化大部分工作区即可达到有效召回；
- 完整索引驻留主机内存，GPU仅以有界tile形式流式评分，GPU内存占用与索引总规模解耦。

#### (3) Tiered KV Management（如何召回）
- **双视图分离**：repository view跟踪每个块的物理副本位置（GPU页池/主机内存/NVMe）；execution view通过页表将非连续物理页映射为紧凑窗口中按时间序排列的逻辑位置，避免拷贝到密集缓存；
- **位置一致性（re-RoPE）**：原始RoPE编码的K仅在原位置有效；KVMem保存**位置无关Raw K**作为持久真源，块进入时在分配的逻辑位置apply RoPE，V则无需变换。已驻留GPU的块若位置变化，通过有界次数的增量re-RoPE复用（达到设定上限后从Raw K重建，以限制低精度GPU副本的数值误差累积）；
- **Proactive Stage-out**：prefill分块计算完成后，异步将已完成块的KV拷贝到主机内存（必要时继续持久化到NVMe），使stage-out移出工作集切换的关键路径；
- **Retrieval-Aware Hierarchical Reuse**：连续步骤间存在块的重叠。设保留块 R_t = W_t∩W_{t-1}、新入块 L_t = W_t\W_{t-1}、出块 E_t = W_{t-1}\W_t，实际物理需要stage-in的仅为 `L_physical(t) = W_t \ G_{t-1}`（G_{t-1}为仍驻留GPU页池的块）。主机内存准入/淘汰综合考虑最近检索与累积检索频率，避免高频召回块因短暂不活跃被降级到NVMe；
- **Packed & Pipelined Rematerialization**：将分散KV块收集到连续锁页缓冲区后批量传输到GPU staging buffer，GPU kernel再散落到目标页并施加RoPE。CPU gather（第n+1批）、H2D传输（第n批）、GPU scatter/re-RoPE（第n-1批）三阶段流水线重叠执行，用双缓冲和CUDA事件同步避免设备级同步。

### 2.4 实现：QW3引擎

因现有推理系统（vLLM、SGLang、LMCache、CacheBlend等）无法完整支持「每步变更、查询相关的非连续历史块召回与位置重映射」执行模型，作者自研了C++/CUDA原生推理引擎**QW3**作为KVMem的执行基座，支持连续批处理、前缀复用、MTP投机解码。基于QW3实现了增量Mean-K索引构建、主机驻留GPU-tile检索评分、异步分层移动、免拷贝执行视图组装等优化。

## 6. 主要结论与发现

1. **KVMem持续优于压缩与滑窗策略，并匹配/超越RAG增强压缩**：
   - LongMemEval-S：85.6% vs Full Context 86.6%（差距<1pt），远超Compact-only 45.6%和Sliding Window 26.8%；
   - AgentLongBench(≤256K)：60.87%，超过Full Context的59.54%——选择性召回部分缓解了长上下文性能衰减；
   - 超出256K原生窗口后：MemoryAgentBench(>256K) 40.99% vs Compact+RAG 34.80%；AgentLongBench(1M) 50.0% vs Compact+RAG 42.0%。

2. **效率优势巨大**：恢复延迟较Compact+RAG降低**11.4–53.8×**；不把检索文本再次prefill，故工作区增长不带来对应prefill增长。

3. **消费级设备可行性**：在24GB显存的RTX 5090 Laptop上支持1M token虚拟工作区（80K执行视图，模型原生窗口的4倍），保持约50 tokens/s单会话生成，同时匹配llama.cpp在同等显存下的执行视图上限。

4. **服务器端规模弹性**：工作区从256K扩展到10M tokens过程中GPU内存基本恒定（约34GB），额外占用主要落在主机内存（封顶64GB）与NVMe（至324GB）；端到端TTFT从0.43s升至1.60s，仍具交互可行性。

5. **DeepSWE完整轨迹实验**：Pass@1从43.8%提升至48.4%，Pass@4从81.3%提升至93.8%（15/16任务至少一次成功）；prefill时间减少55.1%（211.5s→95.0s），请求墙钟时间减少15.4%，端到端agent时间减少12.8%，解码token消耗减少18.7%——效率收益并非以更长输出为代价转移。

## 7. 方法优点

- **概念清晰且具系统性**：明确提出「可寻址工作区/模型可见执行视图/GPU驻留KV集合」三维区分，以虚拟内存视角统摄上下文溢出问题，理论框架有说服力；
- **以模型自身注意力空间做检索**：Mean-K索引直接提取自serving模型的K向量，而非依赖外部文本检索模型的分数，对齐了「模型实际会注意什么」这一目标；用公式（1）的不可区分性论证从理论上揭示了压缩方法保真度的固有边界；
- **工程优化体系完整**：proactive stage-out、GPU页复用、分层保留策略、packed+pipelined数据路径、re-RoPE位置重映射等，将朴素KV分页落地为实用系统，数据搬运开销被多级重叠显著隐藏；
- **通用性设计**：仅管理标准RoPE注意力层的KV，对模型代数（Qwen3.6→Qwen3.8）迁移无需改动机制，说明设计不依赖特定模型细节；
- **验证真实完整agent轨迹**：DeepSWE实验让策略实际影响推理与工具行为，而非仅重放固定历史，增加了结果的可信度。

## 8. 不足与局限

- **KV重用的保真度非数学等价**：历史KV原本在旧的因果上下文条件下计算，KVMem通过re-RoPE和查询重新prefill来恢复，但相似位置的历史token在不同上下文拼接下计算出的表征在理论上不会与全新计算完全一致；论文仅以效用指标近似验证；
- **检索遗漏风险仍存**：每步仅物化检索出的子集，任务关键块仍可能被漏检；论文自认资源允许时更大执行视图有利，但未探索检索覆盖率与Budget间的权衡曲线；
- **存储开销显著**：KV状态远大于其文本源，10M token工作区消耗约64GB主机内存+324GB NVMe+9.5GB检索索引，这是以存储换计算的经济性权衡，未做成本模型量化分析；
- **系统依赖自有引擎QW3**：无法透明叠加到黑盒LLM API或现有主流serving栈（vLLM、SGLang）之上，部署侵入性较高；多用户并发共享GPU/存储的工作区编排尚未涉及；
- **实验限制**：未提供传统意义上的逐组件消融研究；DeepSWE使用固定16任务且与公共轨迹的harness不对齐，严格受控对比性有限；论文日期标注2026年，部分基准与模型版本较新，可复现性有待检验。
