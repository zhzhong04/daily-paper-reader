## 摘要
重复的提示前缀在 LLM 服务工作负载中日益常见，出现在系统提示、模板化检索增强生成流水线、智能体框架和多轮对话中。vLLM 和 TensorRT-LLM 等现代推理运行时提供了跨请求复用先前计算的 KV 缓存状态的机制，但尚不清楚前缀复用何时能在当代加速器上实质性提升服务性能，以及其收益何时受调度、缓存粒度、并发或内存压力限制。本文提出 PrefixBench-H100，一个可复现的基准测试与测量框架，用于在单块 NVIDIA H100 上表征前缀复用。PrefixBench-H100 将受控合成轨迹与聊天式、检索式工作负载相结合，并在匹配的工作负载条件下评估两种广泛使用的 LLM 服务运行时。该基准测试改变共享前缀长度、后缀多样性、请求到达模式、并发度、输出长度和缓存配置，同时收集首 token 时间、token 间延迟、端到端延迟、吞吐量、缓存命中统计、GPU 内存使用以及选定的性能分析轨迹。PrefixBench-H100 的目标不是提出新的缓存算法，而是揭示面向 H100 级 LLM 服务的前缀复用实际运行包络。该研究识别出前缀复用能显著降低首 token 延迟的场景，以及缓存压力会侵蚀这些收益的场景，同时表明缓存有效性本身在很大程度上不受并发度和输出长度影响；剩余的跨运行时差异源于缓存之上，即调度层。

## Abstract
Repeated prompt prefixes are increasingly common in LLM serving workloads, appearing in system prompts, templated retrieval-augmented generation pipelines, agent frameworks, and multi-turn conversations. Modern inference runtimes such as vLLM and TensorRT-LLM provide mechanisms for reusing previously computed KV-cache state across requests, yet it remains unclear when prefix reuse materially improves serving performance on contemporary accelerators and when its benefits are limited by scheduling, cache granularity, concurrency, or memory pressure.   This paper presents PrefixBench-H100, a reproducible benchmark and measurement framework for characterizing prefix reuse on a single NVIDIA H100. PrefixBench-H100 combines controlled synthetic traces with chat-style and retrieval-style workloads, and evaluates two widely used LLM serving runtimes under matched workload conditions. The benchmark varies shared-prefix length, suffix diversity, request arrival pattern, concurrency, output length, and cache configuration, while collecting time-to-first-token, inter-token latency, end-to-end latency, throughput, cache-hit statistics, GPU memory usage, and selected profiling traces.   The goal of PrefixBench-H100 is not to introduce a new caching algorithm, but to expose the practical operating envelope of prefix reuse for H100-class LLM serving. The study identifies the regime where prefix reuse provides substantial first-token latency reductions and the regime where cache pressure erodes them, while showing that cache effectiveness itself is largely insensitive to concurrency and output length; the cross-runtime differences that remain arise above the cache, in the scheduling layer.

# PrefixBench-H100 论文总结

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：重复的提示前缀在 LLM 服务中极为普遍——系统提示、模板化 RAG 流水线、Agent 框架、多轮对话都会复用同一段前缀。vLLM 与 TensorRT-LLM 均已默认开启前缀缓存（prefix caching / block reuse），复用已预计算的 KV cache。
- **问题意识**：前缀缓存最初由 PagedAttention 在 A100 时代提出，其前提假设是"KV 显存是稀缺资源"。但到了 H100 NVL（94 GB HBM3）时代，这一假设被削弱，机制本身已跑在既有性能刻画之前。
- **核心追问**：论文不追问"前缀复用在 Hopper 上是否有效"，而是追问"当缓存层不再稀缺时，瓶颈迁移到了哪里"。
- **中心论点**：只要前缀工作集（prefix working set）能装进 KV 容量，跨运行时的主要差异就已经上移到缓存之上的**调度层**（scheduler）；一旦工作集超出 KV 容量，缓存重新成为约束，且对两个运行时同时成立。
- **整体含义**：这是一项**表征型（characterization）研究**，而非新系统/新算法构建。目标是为 H100 级 LLM 服务揭示前缀复用的"实际运行包络"，帮助研究者与运维者判断何时应优先做前缀复用，何时应转向调度调优或 chunked prefill 等其它优化。

## 2. 论文提出的方法论

### 2.1 核心思想
- 构建 **PrefixBench-H100**：一个可复现的基准与测量框架，让 vLLM 与 TensorRT-LLM 在**完全相同**的 OpenAI 兼容工作负载与请求调度下运行，从而把"前缀复用的内在收益"与"运行时实现差异"分离。

### 2.2 关键技术细节
- **统一入口**：两个运行时都通过 OpenAI 兼容的 `/v1/completions` 端点驱动，使用同一批 JSONL 工作负载文件，保证提示与调度一致。
- **单一异步负载驱动器**（`load_gen.py`，约 300 行，基于 aiohttp）：
  - 支持 **burst（一次性全发）** 与 **fixed-rate（定速到达）** 两种到达模式；定速模式第 i 个请求在 `i/QPS` 时刻释放（确定性间隔，非泊松）。
  - 记录每请求的 TTFT（以第一个非空流式 token 为计时点）、端到端延迟、输出 token 数、HTTP 错误。
  - 在每个 cell 前后抓取各运行时的 `/metrics`，以差分方式还原前缀缓存查询数、命中数、复用 KV block 数。
- **两类工作负载生成器**：
  - *合成重复前缀轨迹*：请求形式为 `⟨共享前缀⟩ ∘ ⟨唯一后缀⟩`，两段都按 Qwen2 tokenizer 精确构造为指定 token 数；可独立调节共享前缀长度、后缀长度、输出长度、不同前缀个数、请求数。保证前缀复用是唯一变量。
  - *真实 RAG 模板轨迹*：长系统提示 + 8 篇检索文档中均匀随机取一 + 8 个查询模板取一，用于验证合成结论的可迁移性。
- **缓存有效性归一化**：两个运行时的原生计数器结构不同（vLLM 是 block 粒度的 hit/query 计数；TensorRT-LLM 是每请求的 `usage.prompt_tokens_details.cached_tokens`）。论文将二者统一归一化为**"由缓存服务的输入 token 占比"**，并在离线用同一公式从原始日志计算，而非直接采信运行时自报的聚合值。
- **受控复用开关对照**：vLLM 用 `--no-enable-prefix-caching`，TensorRT-LLM 用 `enable_block_reuse: false`，作为复用收益的绝对锚点。
- **显存压力实验的变量隔离**：通过 `num_gpu_blocks_override=3520`（vLLM）与 `KvCacheConfig.max_tokens=56320`（TRT-LLM）人为限制 KV 容量，把"KV 容量"与"模型规模"这两个混淆变量解耦。

### 2.3 度量指标
- TTFT（p50/p95）、端到端延迟（p50/p95）、输出吞吐（tokens/s）、请求吞吐（req/s）、前缀缓存命中率、峰值 HBM 使用（从 Prometheus 端点抓取）、少量 Nsight Systems 轨迹（命中/未命中各一例）。
- 另有功耗采样：`nvidia-smi --query-gpu=power.draw` 以 4 Hz 采样，用于能量分析。

## 6. 主要结论与发现

### 6.1 复用收益的量级
- 8192 token 共享前缀下，开启复用带来 **5–6.5× 的 p50 TTFT 降低**（vLLM：345.1→53.0 ms，6.51×；TRT-LLM：306.1→58.2 ms，5.26×）。
- 两个运行时的缓存命中率**统计上等同**：在 1024/2048/4096/8192 前缀长度下均缓存了 65%/78%/87%/92% 的输入。
- 二者在顺序扫描下的 TTFT 曲线差距恒定约 **8 ms**，且在 pl=0（无前缀可缓存）时同样存在——说明差距来自缓存之上的固定每请求开销，而非缓存机制本身。

### 6.2 领导权随负载翻转（最核心发现）
- **Burst 到达、并发 32**：TTFT 领先权从 vLLM 翻转到 TensorRT-LLM，**2.4×**（vLLM 758.6 ms vs TRT 319.1 ms）。
- **定速到达 16 QPS**：领先权翻回 vLLM，在 **p95 上达 9.2×**（vLLM p95 约 22 ms，TRT 约 203 ms；TRT 的 p95/p50 自比为 7.1×）。
- 翻转**不能用缓存有效性解释**：命中率在 32× 并发跨度内只降不到 3 个百分点（两运行时均约 0.83–0.85）。
- vLLM 的计数器显示 burst 下排队延迟占比从 0.02% 升到 20.3%，而定速下始终低于 0.1 ms——指向调度层而非缓存层。
- (前缀长度, 并发) 平面上的领先权是一个**光滑曲面**而非单一阈值：在 (pl=8192, c=32) 角落，TRT-LLM 优势达 **5.75×**。

### 6.3 若干"零结果"与解耦发现
- **`tokens_per_block` 在 TRT-LLM PyTorch 后端上是无效旋钮**：{32,64,128} 在 9 个 cell 中 p50 TTFT 差异 <7 ms，命中率四位小数完全相同。
- **输出长度与前缀复用行为解耦**：{32,128,512} 输出长度下 p50 TTFT 变化 ≤1.2 ms（不到 3%），命中率三位小数一致（TRT 为 0.859）。
- **能量收益**：复用降低平均功耗 9–10%，缩短墙钟时间 5–6×，净能量/请求节省 **24%（TRT）与 31%（vLLM）**；按每天 100 万长前缀请求计，相当于每天数十 kWh。

### 6.4 缓存压力区
- 在 7B/94 GB 的工作点上，最大工作集（1.05M token）仍未撑满 KV 池（≥1.25M），因此"无驱逐"是算术上的预期结果而非经验发现。
- 用 32B 模型（KV 池缩至 79,280 token / 19.4 GB）或对 7B 人为限容（56,320 token），均可复现驱逐区：
  - 7B 限容后命中率从 68.2% 崩到 **3.6%**（两运行时小数点后两位完全一致），TTFT p50 回退 4.6–6.1×。
  - 32B 下工作集/容量比从 0.4× 升到 13.2×，命中率相对各自上限从 88.9%（0.4×）掉到 5.6%（13.2×）。
- **关键结论**：驱逐起始由**工作集与 KV 容量之比**决定，而非绝对模型规模；即使在压力区内，两运行时的缓存命中率仍只差 1–6 个百分点，**缓存平价（parity）在压力下依然成立**。

### 6.5 吞吐 vs 延迟的取舍
- 吞吐故事与 TTFT 相反：并发 32 时 vLLM 输出 1444 t/s，TRT-LLM 仅 523 t/s，**2.8× 优势**——恰是在 TRT-LLM 拥有 2.4× TTFT 优势的同一点上。

| 工作负载形态 | 推荐运行时 | 依据 |
|---|---|---|
| 长共享系统提示、顺序/交互式 | vLLM | 缓存等同，vLLM 每请求开销少约 8 ms |
| 突发短提示、关注 p50 TTFT | TRT-LLM（c≥16） | vLLM 在 burst 下 TTFT 膨胀快 2–3× |
| 定速稳态负载（RAG、Agent 循环） | vLLM | TRT 的 p95 在 1→16 QPS 间膨胀 9× |
| 吞吐最大化离线批处理 | vLLM | c=32 时 1444 vs 523 t/s |
| Block-size 调优（TRT-LLM） | 用默认 32 | {32,64,128} 无可检测差异 |

## 7. 优点

- **问题定位精准且有反直觉性**：把"缓存是否有效"重新表述为"缓存之上还剩什么差异"，并用三次负载切换（顺序→burst→定速）和两次领导权翻转来支撑，叙事说服力强。
- **测量方法论严谨**：
  - 跨运行时的缓存命中率做统一归一化，且离线用同一公式重算，不采信自报聚合值。
  - 变量隔离到位（合成轨迹精确 token 数、容量上限覆盖 vs 模型规模）。
  - 用"相对各自理论无驱逐上限的缺口"判定驱逐，逻辑自洽且可证伪。
- **诚实的自我限定**：明确指出 7B 上的"无驱逐"是算术结果而非经验发现；明确指出调度归因是最佳假设而非完整因果链；明确指出 p95 倍数依赖具体硬件。
- **鲁棒性检验成对且正交**：跨架构

- **鲁棒性检验成对且正交**：跨架构（Qwen2-7B 的 4 个 KV 头 vs Mistral-7B-Instruct-v0.3 的 8 个 KV 头）与跨规模（7B→32B）构成两个相互独立的泛化维度，且都复现了同一结论——缓存命中率平价、瓶颈上移至调度层，说明发现不是某一模型族的偶然。
- **工程可复现性高**：约 300 行异步驱动器、102 个逐 cell 原始 JSON、合并 CSV、全部绘图脚本与 `analysis.ipynb` 一并公开并附 DOI，且明确给出"单卡约 3 GPU 小时可全量复现"的成本，使该工作具备基准套件（benchmark suite）而非一次性论文的属性，后续可被他人扩展。
- **运维可操作性**：Table 7 把测量结论直接映射为按负载形态的选型建议，且每条建议都绑定到具体度量（p50 TTFT、p95 膨胀倍数、吞吐比值），避免了"看情况"式的空泛结论。

## 8. 不足与局限（客观评估）

- **硬件覆盖窄**：仅在单块 H100 NVL（94 GB）上测量，未验证 80 GB H100 PCIe/SXM、A100、H200 或消费级卡上的压力阈值与领导权翻转点是否漂移；作者本人也承认 p95 的倍数关系依赖具体硬件。
- **并行度单一**：全部为单 GPU 服务，未涉及张量并行/流水线并行下的前缀缓存与跨卡 KV 传输，因此结论无法直接外推到 70B 级以上、必须多卡部署的工作点。
- **到达过程过于理想**：定速到达采用零方差的等间隔释放，而非泊松或真实 trace 回放，稳态负载下的尾部延迟与队列行为可能被系统性低估，而"vLLM 在定速下 p95 领先"这一关键论点的强度因此打了折扣。
- **调度层归因非完全因果**：TensorRT-LLM 缺少与 vLLM 可比的调度器级计数器，论文对"差异来自调度层"的判断是"排除缓存 + CDF 形状 + 排队延迟占比"的证据链，属于最佳假设而非 instrumented 的因果证明；不同调度器内部实现（如 continuous batching 策略、抢占逻辑）未被拆解到组件级。
- **现代优化未纳入**：未考察 chunked prefill、FP8/INT8 KV cache、投机解码、多 LoRA、分离式（disaggregated）prefill/decode 等与前缀缓存的交互——而这些恰是当前生产栈的常见配置，可能改变"缓存之上还剩什么"的答案。
- **后端对比不完整**：TensorRT-LLM 的 legacy engine 后端只做了单 cell 对比，未重跑 burst 与 RAG sweep，因此"PyTorch 后端上 `tokens_per_block` 无效"这一零结果是否推广到 engine 后端尚不清楚。
- **正确性维度缺失**：论文聚焦性能，未验证开启/关闭前缀缓存时输出 token 序列是否逐位一致（尽管理论上应无损），也没有质量或一致性回归测试。
- **功耗粒度较粗**：4 Hz 的 `nvidia-smi` 采样对毫秒级 burst 峰值功耗不敏感，能量结论更适用于稳态长时窗，而非瞬时能效刻画。
- **真实 RAG 轨迹仍偏模板化**：8 篇文档均匀随机取一 + 8 个查询模板，共享前缀长度分布集中，未必反映真实检索文档长度长尾，因此"合成结论可迁移"的证据强度有限。

## 9. 对研究与实践的启示

- **认知框架的更新**：当 KV 容量不再稀缺时，前缀缓存的"有效性"已趋于跨运行时平价，研究焦点应从"缓存命中率"转向"缓存之上的每请求固定开销与调度策略"。论文用两次领导权翻转（burst 下 TRT 领先 2.4×、定速下 vLLM p95 领先 9.2×）把这一迁移具象化。
- **选型原则**：应以负载形态（到达模式、并发水平、目标指标是 p50 还是 p95、是否吞吐优先）而非"谁的缓存实现更好"来选型；同一对运行时在不同负载下会互换优劣，单点基准极易误导。
- **容量规划原则**：驱逐起始由"工作集/KV 容量比"决定而非绝对模型规模，因此把该比值作为一等配置参数纳入容量规划，比单纯关注模型参数量更有指导意义。
- **后续研究方向**：① 带调度器级 instrumentation 的因果归因研究；② 跨硬件代际（A100→H100→H200）与多卡并行下的阈值标定；③ 将 chunked prefill、FP8 KV、分离式架构等纳入同一受控基准，检验"调度层主导"结论是否稳健；④ 引入真实生产 trace 回放替代等间隔到达，以校准尾部延迟结论。

## 10. 一句话总评

这是一项**问题意识出色、测量纪律严谨、结论诚实自限的表征型研究**：它用受控基准证明前缀缓存在 H100 上已"商品化"为跨运行时平价，从而把性能竞争的战场清晰地推到缓存之上的调度层，并给出了可直接落地的负载—运行时选型表；其代价是硬件、并行度与流量真实性覆盖有限，使其结论更像"在明确定义包络内的可靠路标"，而非普适定律。
