## Abstract 

Agentic LLM workflows decide their execution paths at run-time. Downstream computation may be predictable, or may have run before, yet it cannot begin until the model or the user resolves the branch. We call this serialization the branch-resolution barrier . Caching alone does not hide it: the key that identifies a reusable result is not known until then. In this paper, we propose DynBranch, which makes an unresolved branch addressable before it resolves. Its stable 

coordinate lets candidate subgraphs run during resolution and completed subgraph results be reused across later re-quests. A two-level controller admits this work when its expected benefit exceeds the load price. DynBranch sits at the model-API boundary and requires no changes to agent harnesses or model execution engines. Across four agentic workloads with Qwen3-32B on 4 ×

H200 GPUs, DynBranch reduces mean latency by up to 32% over each workload’s strongest prior system and by 46–66% against a no-reuse floor, while preserving workflow results. The benefit persists across backbone families and on a com-modity Qwen3-8B/RTX 4090 deployment. 

## 1 Introduction 

LLM applications are moving from workflows whose model and tool calls are fixed before execution [38, 52] to agentic ones that decide each next step as they run, by the model or by the user [101, 104, 108]. Measured agent workloads show tens to hundreds of model and tool calls per task [55, 120], so these decision windows repeatedly enter the critical path. Downstream work waits on a choice the model has yet to decode: the handler a request needs, the sub-task a sub-agent runs, the entity a retrieval fetches. Each is typically followed by model inference. For example, a ReAct agent answering multi-hop questions decodes the entity it will search next [108], and coding agents such as Claude Code and Codex show both: they decode the next tool call, and at interactive decision points they wait for the user to pick from a short list of suggested actions [5, 63].

We call this serialization the branch-resolution barrier :downstream computation that may be predictable, or may have run before, waits for the model output or user choice that determines the branch. In measured coding, research, and scientific agents, 45–57% of end-to-end latency is down-stream time serialized after model output [88]. This creates two opportunities. Starting likely downstream computation before resolution can hide part of its latency on the first occurrence (Figure 1). Reusing a validated result can avoid that computation on later occurrences. Existing systems provide result caching [9, 94] and agent-level speculation [28, 34, 109] as separate mechanisms. Caches retain completed responses and operator results, while speculative agents consume or discard predicted work within the current request. Prefix caches reuse KV state [116], and dataflow schedulers overlap work once its inputs are known [38, 52, 89, 102]. These systems do not jointly support reusing a subgraph result across later re-quests, starting a branch before it resolves, and pricing that work against serving load. Each is hard in a different way. 

C1, shared-subgraph reuse : the unit that recurs is a sub-DAG rather than a whole request, and moving the boundary there must not weaken exact matching or freshness. C2, early

C3, load-priced admission : speculative work draws on the same slots and KV as the request it accelerates, so what helps at low load hurts at high load. In this paper, we propose DynBranch, which makes an unresolved branch addressable before it resolves (§3). For C1, it records a completed branch subgraph together with the input that produced it and the external reads it made. A later request consumes the entry only when its input matches exactly and those reads are still fresh; a write to any of them invalidates it. For C2, the workflow template provides a coordinate : the identity of a decision point in the template, such as the router stage of a routing workflow, known before the branch resolves in our target workloads (§5.6). Predicted candidate subgraphs run as fills during the resolution window; completed results can also serve later requests. Fills remain invisible until branch selection and an exact, fresh canonical (non-speculative) demand authorize their use, so wrong predictions cannot change workflow results. For C3, a two-level controller decides whether to generate candidates and whether to execute each fill, admitting either when expected benefit exceeds the load price over the fill’s execution horizon. That price reads the engine’s current decode and KV occupancy, so it rises as speculative and canonical work accumulate. We implement DynBranch at the model-API bound-ary between agent harnesses and unmodified SGLang or vLLM engines [39, 116], an interface that covers both framework-driven workflows [25, 41, 101] and text-based coding agents [5, 21, 63]. With Qwen3-32B on 4 × H200 GPUs, DynBranch reduces mean latency by up to 32% over each workload’s strongest prior system on the same GPUs and by 46–66% against a no-reuse floor, while preserving workflow results. With reuse disabled, early fill alone re-duces mean latency by 8 .5–34 .4% on model-driven paths and user-turn latency by 46 .6–47 .7% on HCI (§5.4). The ben-efit persists across backbone families and on a commodity Qwen3-8B/RTX 4090 deployment. We make three contributions: 

• We identify the branch-resolution barrier and quantify its cost on production traces and four agentic work-loads (§2). 

• We propose a branch-state abstraction connecting speculative execution with cross-request subgraph reuse, promoted on exact match and invalidated by writes (§3.2–§3.3). 

• We design a two-level online controller that prices candidate generation and fill execution against benefit and load, learning from delayed feedback (§3.4, §5.4– §5.5).

## 2 Background and Motivation 

An agentic workflow interleaves model calls, tool calls, and user turns, and at many steps the next one depends on the current step’s output: the model names the tool or sub-task to run, or the user picks among offered actions. We call each model or tool call, executed on its rendered input (the prompt or tool arguments after upstream outputs are substituted), a stage , and the stages downstream of a decision point its 

subgraph . Figure 2 narrows from all agent work to the part serialized behind such decisions, then to the part that can start before a decision resolves (C2) and the part a later request can reuse (C1), all drawn from capacity that canonical requests also need (C3). 

C1: shared-subgraph reuse. GPTCache and agentic plan caching match whole responses or plans [9, 74, 112], while SGLang, Pythia, PBKV, and KVFlow retain prefix-KV state but still execute the decode [64, 110, 115, 116]. Both anchor at the request boundary, at the whole request or its first token, so neither can name a sub-DAG that recurs inside requests differing elsewhere. Its retrieval and tool results also depend on external reads, so exact matching is not enough: writes to recorded dependencies must invalidate them (§3.2). 

C2: early fill during resolution. KVFlow, Pythia, and PBKV prefetch or retain prefix state for a declared or pre-dicted next stage [64, 110, 115], but the stage itself still runs only after resolution. Speculative Actions executes a pre-dicted API call early, SPAgent a search action [34, 109], DSP a chain of planning steps [28], and Speculative Interaction Agents dependent tool calls alongside model reasoning [32]. PASTE, the closest, isolates a predicted tool result until a matching authoritative invocation commits it [88]. All five, however, can use a speculative result only in the request that produced it: the result is checked against that request’s next step and used or discarded there, so even a correct result is lost when the request ends. C3: load-priced admission. Fills run on the same GPUs as the requests they accelerate, so each unused fill delays canonical traffic (Figure 5b), more so at high load [4]. PASTE, SPAgent, TurboSpec, and Nightjar limit speculative work under load [34, 48, 54, 88], but each scores a unit once, before it runs. A branch incurs two costs, running the predictor and then executing the admitted candidates, and whether either paid off is known only when the branch resolves, often seconds later. Admission therefore needs a cost that tracks current load and a benefit estimate corrected by these delayed outcomes (§3.4). 

What a workload must supply. First, the work needs an identity independent of runtime content, since conven-tional memoization names a result only once its inputs are known [9, 112]; a workflow template supplies one by nam-ing each decision point, though the model still produces the selection or tool arguments (§5.6). Second, the stage must be safe to run twice: no external side effects, same result for the same input and dependency versions. Greedy inference with batch-invariant kernels [31] over an immutable model and read-only retrieval over a versioned snapshot qualify; stages that sample or mutate external state run only after resolution (§3.3). §2.1 describes four workloads that meet both, and §2.2 measures what each challenge is worth on them. 

2.1 Dynamic Agentic Workloads 

Agentic workflows determine downstream steps at run-time [5, 101, 108], and the decisions are frequent and di-verse [56, 120]: agent sessions and tasks run 82–318 model steps [111, 120], and we measure 50 distinct paths in 52 requests, so every run opens tens to hundreds of resolution windows in which to speculate. 

A workload taxonomy. Dynamic branches vary along four dimensions that set the benefit of early execution and the life of its results: the resolution window (model decode or human wait), the candidate space (bounded or open vocabulary), the 

promotion semantics (one selected winner or multiple valid results), and the reuse horizon (within a chain, across turns, or across requests). Figure 3 places four workloads on them. 

Routing is a tool-use workflow over BFCL function calls [66], 

ReAct [108] a multi-hop question-answering agent [90, 106], 

Sub-Agent [101] an orchestrator that dispatches tasks to sub-agents, and HCI an assistant that offers actions and waits for the user to pick one [14, 22].

Recurrence concentrates in content sub-tasks. What a fill cannot hide, reuse removes outright when the same work is asked for twice. With speculation disabled, 12% of ReAct 

retrievals in a run and 26% of Sub-Agent sub-tasks across runs have byte-identical inputs, and recurrence increases as more requests arrive (Figure 5a): repeated MuSiQue [90] sub-topic mentions rise from 19% at 100 questions to 61% at 5 ,000. It appears outside our workloads too: our analysis of released SWE-agent and SWE-rebench trajectories [7, 104] finds 42– 45% of commands recurring verbatim within a repository. A production prefix-cache study reports 54–62% ideal hits [95]; that unit requires a shared prefix, while the retrievals and sub-tasks above recur in requests that differ elsewhere: the unit C1 must name. 

Speculation’s cost depends on load. A fill’s engine time pays off only if its result is used. Serving leaves capacity for it [65, 99]: over a day, GPUs leave ≈81% of streaming-multiprocessor (SM) time idle [26], decode leaves >50% of compute unused [73], and human thinking is 64% of coding-session wall-clock with idle gaps capped at an hour [120]. Fills still compete with canonical requests for decode slots and memory bandwidth; Figure 5b measures p50 latency for a fixed-shape 32B request as fills grow in number and context. At a fixed context length, 1–3 co-resident fills raise it by 4–6% and 48 by 53%; holding the count at 24 and growing each context from none to 4 ,500 words raises it from 11% to 145%, as the fills grow from 3% to 24% of the KV pool. Resident KV rises with both, which is why C3’s admission reads it as the measure of speculation in flight (§3.4).

3.1 System Overview 

DynBranch is a serving layer between agentic harnesses and model-serving engines, built from one interface and three parts. The candidate interface takes a branch coordinate and returns a ranked candidate list; which predictor sits behind it is a deployment choice (§3.3). Life of a request. Figure 6 follows a model-decided branch: its resolution window lets predicted downstream work run before the next stage is named. The predictor uses the branch

The gate prices each candidate and admits those whose expected benefit exceeds its load price ( 2 ); the admitted fills then run on the same engines as canonical traffic ( 3 ), concurrently with the branch-resolution decode. A completed fill remains an invisible shadow , a speculative result that serving paths cannot read ( 4 ). Branch resolution eliminates losers but does not authorize the survivor: only a subsequent canonical demand with the same exact reuse name can promote and consume it ( 5 ). This separation takes the serialized work off the critical path without exposing unchosen work. The confirmed entry then serves later exact matches ( 6 ) until a dependency write invalidates it ( 7 ). DynBranch treats reuse, overlap, and execution as separate decisions. C1: what may be reused? A subgraph, identified by its exact realized input and fresh dependencies (§3.2). 

C2: how can work run before resolution? A stable coordinate starts fills during the window; a matching canonical demand authorizes use (§3.3). C3: when should that work run? When its expected latency benefit exceeds its load-priced resource cost (§3.4).

Subgraph reuse names. Exact reuse follows the depen-dency closure captured by a rendered input, not a node’s graph position. A whole-response key needs the whole work-flow to repeat [9] and a prefix-region key an unchanged prefix [64, 116]. DynBranch instead makes the unit a self-contained subgraph, depending only on the upstream values entering its own rendered inputs, so it stays valid beyond an unrelated change. It records that subgraph with the real-ized input, output, external read-set, and provenance of one execution. Its reuse name combines a subgraph fingerprint with a hash of the realized input, covering the request fields that determine the output. C2 addresses work before reso-lution through the branch coordinate, which identifies an unresolved decision and therefore cannot authorize reuse. Freshness is maintained by a reverse index from external records to cached entries. A write invalidates direct depen-dents and any cached or engine-resident state that loses a valid producer; incomplete provenance conservatively ex-tends the cascade. Reads synchronize with invalidation, so concurrent or uncertain cases fall back to a miss. Writes may reduce reuse but cannot expose stale state; the cas-cade follows view-maintenance and lineage work [1, 11, 27]. Together, these checks make a hit replay one recorded exe-cution [61].

3.3 Early Fill During Resolution (C2) 

C2 must avoid two failures. The first is serial: downstream work that could have run inside the resolution window waits for it instead, and the obvious repair (publishing a result as soon as it completes) serves work no demand se-lected [82]. The second is cross-request: speculative decod-ing, speculative agents, and speculative tool systems bind validation and consumption to the request that authorized the work [28, 32, 43, 88, 109], so a result that survives its branch still dies with its request. C2 therefore decouples computation, selection, and authorization. 

Where candidates come from. Any predictor can sit be-hind the interface: a next-stage model over the coordinate’s

Speculative results and promotion. C2 speculates only on speculable stages, those the template declares safe to run twice (§2); unannotated, sampling, or externally mutating stages run only after resolution. Admission turns a candidate into a fill . Once the fill’s input renders, C1 derives the reuse name, and completion records that name, the result, and its read-set as a persistent shadow, visible to the gate’s per-branch record but unreadable by serving paths. A canonical demand resolves this lifecycle in two steps. First, selection settles the branch. For an exclusive branch, the resolved choice retains the matching candidate and aborts the losers’ in-flight fills in the engine, releasing their slots and KV and discarding their results; independent offers remain eligible, their shadows unreadable until an exact demand authorizes them or they expire. An ambiguous branch or choice promotes nothing. Second, authorization applies C1’s guards: the canonical reuse name must match the shadow’s, and its recorded read-set must remain fresh. Only then is the shadow atomically promoted and consumed: selection eliminates work, content and freshness serve it. If the matching fill is still running, the canonical demand waits a bounded interval and otherwise executes normally. Multi-stage fills are promoted stage by stage as canonical demands pass the same guards.

3.4 Load-Priced Admission (C3) 

DynBranch admits speculative work in two steps (Algo-rithm 1). For each branch, the generation gate (Action 0) decides whether running the predictor and expanding candi-dates is worth its fixed cost. If it opens, the fill gate (Action 1) admits a candidate only if the expected time it saves exceeds the expected delay it imposes on canonical requests at cur-rent load, re-pricing after each admission. The two are not one decision: generation itself costs time that no fill thresh-old can recover, and a cheap generation step can still reveal fills that are individually too costly. Predicting more actions raises the chance of covering the realized branch, but also creates work that may never be used [34, 58, 105, 109]. Admission must therefore protect canonical demand from those fills. Paying for an alternative before knowing whether it is needed is classical optimal search [97]; here the alternative is produced, not fetched, so its price moves with contention.

Admis-sion is the only point at which contention can be refused: a running fill holds its slots until it completes or its branch cancels it, so an instantaneous idle reading would underprice a multi-second fill. ## 4 Implementation 

Agentic harness integration. Framework-driven harnesses such as AutoGen [101], LangGraph [41], and AgentScope [25] attach to DynBranch through an HTTP interceptor that tags each model request with workflow_type_id , workflow_id ,and agent_id . Text-based coding-agent harnesses such as Claude Code [5], Codex [63], and DeepSeek Harness [21] normalize into the same arrival representation from their own wire protocols, so DynBranch depends on neither the agent loop nor the protocol. 

> 7

Serving integration. DynBranch hooks three lifecycle events on every normalized arrival: stage arrival, the open-ing of an unresolved branch, and the canonical request carrying its resolved selection. The hooks reuse the serving path’s existing queue, slot, and KV accounting, the same CSL manager, and the same terminal settlement path; canonical requests and speculative fills execute through the existing SGLang or vLLM executors [39, 116]. Disabling DynBranch bypasses the hooks and preserves the original semantics. 

## 5 Evaluation 

We evaluate end-to-end latency, completion, and tail (§5.2); how width, replicas, and depth trade GPU work for latency (§5.3); what reuse (C1), early fill (C2), and each admission gate contribute (§5.4); and how the system holds up under rising and bursty load (§5.5). Task accuracy is checked against the floor in every experiment. 

5.1 Experimental Setup Testbed. Our main testbed is a dedicated server with two AMD EPYC 9755 CPUs, 2.2 TiB of main memory, and four NVIDIA H200 NVL GPUs with 141 GiB of HBM each. Work-ers serve Qwen3-32B [103] unless stated otherwise, and a distilled Qwen3-0.6B drafts branch candidates. The commod-ity replication in Figure 8(c,d) uses four distributed worker nodes on vast.ai, each serving Qwen3-8B on one NVIDIA RTX 4090 with 24 GiB of device memory. 

Workloads. We instantiate the regimes in §2.1 with: 

• Routing : BFCL function-calling records [66], replayed with their handler choices and arguments. 

• ReAct : multi-hop questions from MuSiQue [90] over a local HotpotQA-derived retrieval corpus [106]. 

• Sub-Agent : MuSiQue-derived research sub-topics; the reuse-only run (Table 1) uses the same entity distribution. 

• HCI : menu-offer/user-pick pairs from Schema-Guided Dialogue [71], with paired, sampled think gaps between offer and selection [14, 22]; latency is measured on the user turn that follows the gap. 

Baselines. We compare five systems spanning completed-result reuse [94, 121], workflow scheduling, and agent-level speculation. InstCache [121] pre-populates an exact request cache from predicted instructions. Helium + [94] 1 combines cache-aware scheduling with exact operator-result reuse. Parrot [52] exposes workflow dataflow as semantic variables. DSP [28] tunes speculative-plan depth under a latency–cost objective. SPAgent [34] speculates the next search-agent action and retains it in an in-request buffer. 

Metrics. The reference throughout is a no-reuse floor : the same stack with speculation and cross-request reuse disabled.

5.2 End-to-End Comparison 

DynBranch achieves the lowest mean latency across all four workloads, both load levels, and both hardware configura-tions (Figure 8). On 32B/H200, it improves over each work-load’s strongest external baseline by 14–32% at low load. At load, the reductions are 15–31% on Routing , Sub-Agent , and 

HCI , and 6 .2% on ReAct . Across these cells, reductions against the no-reuse floor span 46–66%. Task accuracy tracks the floor in every experiment below: promotion is lossless by construction (§3.3). 

Early fill under load. C2 retains substantial benefit under load on Sub-Agent and HCI , reducing latency by 30% and 35% over C1-only, respectively; Routing gains 8 .6%. On open-vocabulary ReAct , the gain falls from 16 .0% at low load to 0.4% at load, while 53–55% of issued fills fail to match the resolved branch and are discarded at both points. The similar mismatch rates accompany different latency gains: under load the binding constraint is how much execution a fill can still hide, not how often the branch is guessed right (§5.5). 

Completion and tail latency. Every arm completes the offered load with zero runtime failures. Relative to the no-reuse floor on 32B/H200, DynBranch lowers p99 by 11–33% at load and 19–36% at low load on Routing , ReAct , and Sub-Agent ; HCI matches the floor at both points. 

Commodity replication. The benefit generalizes to the smaller-model, distributed deployment: with Qwen3-8B on four RTX 4090s, DynBranch lowers mean latency by 6 .9– 37 .6% relative to each cell’s strongest external baseline and 29 .6–54 .6% relative to its no-reuse floor (Figure 8c,d). C2 improves over C1-only in every cell.

5.4 Ablation Study 

C1 captures reuse across partially overlapping requests; C2 lowers latency even with cross-request reuse disabled. Both preserve task accuracy against their paired no-reuse floors. A final pair of experiments ablates the two admission gates. 

Reuse alone. With C2 disabled, DynBranch reduces mean latency on partial-overlap requests by 31%, matching Helium +’s 30% reduction; InstCache [121] gains only 7% (Ta-ble 1). The workload mixes exact repeats, shared sub-DAGs, and fresh negative controls; arms are paired by request id on cold-started stacks. Exact repeats reach the cache-hit path; fresh requests yield no reuse benefit. Across the mix, DynBranch reduces mean latency by 32 .2%, with zero unsafe splices. C1 thus captures reuse below the whole-request boundary while retaining write-cascade invalidation.

The baselines run their native admission, and DynBranch outperforms DSP [28] and SPAgent [34] through-out. These gains overlap with C1’s: some filled stages would also be served by reuse.

5.6 Limitations and Future Work 

The evaluated workflows use homogeneous serving models, stable branch coordinates before resolution, and side-effect-free speculative stages. Benefit depends on recurrence, pre-dictability, available overlap, and spare capacity. Extensions 

> 11

include templates from emitted plans [112], transactional isolation and cross-resource scheduling for stateful tools and heterogeneous multimodal pipelines [17, 89], and speculative units ranging from retrieval or prefill [96, 114] to branches. 

## 6 Related Work 

LLM state and result caches. Whole responses are cached under exact or semantic query matches [9, 45, 121], plan tem-plates are reused [112], prefix or chunk KV state is retained, blended, or routed [2, 16, 24, 64, 85, 107, 110, 115, 116], and tool outputs are memoized [10, 76, 92]. Continuum preserves KV state across tool-call pauses using tool-aware lifetimes and program-level scheduling [44]. These systems retain content or model state whose identity is already known. DynBranch instead produces work before the branch out-come exists, then promotes the exact selected result with its dependency provenance for later reuse. 

Reusable computation and freshness. Semantic caching and answering queries using views established sub-query reuse [19, 30]; derived state can be maintained incremen-tally [11, 29], as Noria, ReadySet, and Differential Dataflow do in dataflow systems [27, 57, 72]. Freshness scheduling and self-adjusting computation track when derived work remains valid [1, 40]. Adaptive query processing and multi-query optimization revise and share execution plans [6, 35, 78]. DynBranch adopts the same principle (reusable work needs an explicit dependency and freshness contract) for an LLM subgraph whose dependencies are external reads, not base tables. 

Agent-aware serving. Recent characterization finds hetero-geneous resources, long idle intervals, shifting bottlenecks, and cross-request tool redundancy in agentic workloads [15]. Agentix treats programs as first-class scheduling units [55], while a policy-driven agent runtime exposes observation, prediction, scoring, and action hooks between frameworks and engines, evaluating agent-aware KV prefetch and re-tention [113]. Murakkab configures workflow components across models and hardware under SLOs [17], and Dyserve adapts per-node model, verifier, and backend choices under load [69]. 

Workflow and dataflow optimization. Helium couples proactive caching with workflow scheduling, while Halo plans model residency for known DAGs [79, 94]. FlowMesh deduplicates operator work by content, and Lumilake merges identical intermediate nodes across known jobs [80, 87]. Ses-sion DAG and stage-pipeline systems make their inter-stage dependencies explicit to the scheduler [38, 52, 89]. Agentix, Alto, and Conveyor add program-aware preemption, nested-ancestry dataflow orchestration, and streamed tool/decode overlap [55, 70, 102]. DynBranch supplies a dependency not yet visible to the scheduler and returns the confirmed result to the same dataflow, so these techniques remain comple-mentary. 

Speculative agents and serving. Interactive Speculative Planning, dialogue-response prefetching, Speculative Ac-tions, DSP, SpecHop, SPORK, and SPEX predict future ac-tions, reasoning paths, or downstream work and verify the realized path [8, 28, 33, 59, 77, 109, 117]. Skim executes a site-template fast path and verifies its output before falling back to the full agent [100]; Sherlock instead overlaps a produced node’s verification with its downstream work [75]. Tool-oriented systems execute predicted calls [32, 88]; PASTE, SPAgent, IdleSpec, B-PASTE, and DualSpec gate them on confidence, utility, capacity, or semantic consistency [18, 34, 83, 88, 118]. PASTE is closest: beyond the hold-until-match of §2 it co-schedules tools with returning LLM ses-sions, but still consumes the confirmed result within its orig-inating request. Speculate-with-Memory carries predictor statistics and episodes across tasks [50], rather than persist-ing validated products. Token-level speculative decoding drafts and verifies individual tokens [13, 43, 49, 119], and serving systems adapt that draft work to load, batch, or bud-get [47, 48, 51, 53, 54]. A separate family lowers latency by changing what the model computes: routing to a cheaper model [62, 69], or bounding the reasoning budget, which can change the answer itself [42, 60]. DynBranch overlaps candidate subgraphs with resolving decode; completed re-sults serve later requests after exact matching and freshness checks. DynBranch reprices each branch at generation and every fill using live load and observed outcomes. 

## 7 Conclusion 

DynBranch removes the branch-resolution barrier by treat-ing an unresolved branch as serving state: a coordinate names candidate work before the branch resolves, an ex-act input match with fresh dependencies authorizes it af-terwards, and a two-level controller prices both against live load. Across four agentic workloads it cuts mean latency by up to 32% over the strongest prior system and by 46–66% against a no-reuse floor, with workflow results unchanged; with reuse disabled, early fill alone still removes 8 .5–47 .7%. The contract behind that result rests only on a named de-cision point and a stage safe to run twice, so it carries to workflows whose shape is decided at runtime, and priced ad-mission sustains it from idle to saturated load. Within those two requirements, predictors and pricing policies can evolve without weakening exact reuse or freshness.
