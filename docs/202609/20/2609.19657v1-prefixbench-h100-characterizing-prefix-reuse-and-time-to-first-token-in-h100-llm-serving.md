## 摘要
重复的提示前缀在 LLM 服务负载中日益常见，出现在系统提示、模板化检索增强生成流水线、智能体框架以及多轮对话中。vLLM 和 TensorRT-LLM 等现代推理运行时提供了跨请求复用先前计算的 KV 缓存状态的机制，但在当代加速器上，前缀复用何时能实质性提升服务性能、何时其收益又受调度、缓存粒度、并发或内存压力限制，仍不清楚。

本文提出 PrefixBench-H100，一个可复现的基准与测量框架，用于在单块 NVIDIA H100 上刻画前缀复用。PrefixBench-H100 将受控合成轨迹与聊天式和检索式负载相结合，并在匹配的负载条件下评估两种广泛使用的 LLM 服务运行时。该基准改变共享前缀长度、后缀多样性、请求到达模式、并发度、输出长度和缓存配置，同时收集首 token 时延、token 间延迟、端到端延迟、吞吐量、缓存命中统计、GPU 内存使用以及选定的性能分析轨迹。

PrefixBench-H100 的目标不是引入新的缓存算法，而是揭示 H100 级 LLM 服务中前缀复用的实际运行范围。该研究识别了前缀复用可显著降低首 token 时延的区域，以及缓存压力会侵蚀这些收益的区域，同时表明缓存有效性本身在很大程度上对并发度和输出长度不敏感；剩余跨运行时差异出现在缓存之上，即调度层。

## Abstract
Repeated prompt prefixes are increasingly common in LLM serving workloads, appearing in system prompts, templated retrieval-augmented generation pipelines, agent frameworks, and multi-turn conversations. Modern inference runtimes such as vLLM and TensorRT-LLM provide mechanisms for reusing previously computed KV-cache state across requests, yet it remains unclear when prefix reuse materially improves serving performance on contemporary accelerators and when its benefits are limited by scheduling, cache granularity, concurrency, or memory pressure.   This paper presents PrefixBench-H100, a reproducible benchmark and measurement framework for characterizing prefix reuse on a single NVIDIA H100. PrefixBench-H100 combines controlled synthetic traces with chat-style and retrieval-style workloads, and evaluates two widely used LLM serving runtimes under matched workload conditions. The benchmark varies shared-prefix length, suffix diversity, request arrival pattern, concurrency, output length, and cache configuration, while collecting time-to-first-token, inter-token latency, end-to-end latency, throughput, cache-hit statistics, GPU memory usage, and selected profiling traces.   The goal of PrefixBench-H100 is not to introduce a new caching algorithm, but to expose the practical operating envelope of prefix reuse for H100-class LLM serving. The study identifies the regime where prefix reuse provides substantial first-token latency reductions and the regime where cache pressure erodes them, while showing that cache effectiveness itself is largely insensitive to concurrency and output length; the cross-runtime differences that remain arise above the cache, in the scheduling layer.

# PrefixBench-H100 论文深度总结

## 一、核心问题与研究动机

- **背景变化**：前缀缓存（prefix caching）最初由 PagedAttention 提出，前提是 A100 时代 KV 显存稀缺。如今 vLLM 0.21 与 TensorRT-LLM 1.2.1 已在 H100 NVL（94 GB HBM3）上默认开启该功能，硬件假设已发生根本改变。
- **核心问题**：论文不问"前缀复用在 Hopper 上是否有效"，而问"缓存层不再稀缺后，瓶颈迁移到了哪里"。
- **中心论点**：当**前缀工作集能装入 KV 容量**时，跨运行时的主要性能差异已从缓存层上移到**缓存之上的调度层**。作者用三次"领先权翻转"来证明这一点：
  - 顺序复用场景下两运行时缓存效果几乎相同，绝对 TTFT 差距在整个前缀长度扫描中基本恒定（约 8 ms 的固定每请求开销）；
  - 突发到达、并发 32 时，p50 TTFT 领先者从 vLLM 翻转到 TensorRT-LLM（2.4×）；
  - 固定速率到达、16 QPS 时，领先者又翻回 vLLM（p95 TTFT 9.2×）。
- **边界条件**：该结论并非普适。一旦工作集超过 KV 容量，缓存重新成为瓶颈，且两个运行时同时受制。
- **定位**：这是一项**表征性（characterization）研究，而非系统构建**；目标是给出 H100 级 LLM 服务中前缀复用的可复现"操作包络"。

## 二、方法论

- **总体思路**：将 vLLM 与 TensorRT-LLM 当作**黑盒**，均使用官方推荐默认配置，通过同一套 OpenAI 兼容负载驱动，隔离"前缀复用本身"与"运行时实现差异"。
- **关键设计细节**：
  - 两个运行时均由同一个约 300 行的异步 Python 负载生成器（`load_gen.py`，基于 aiohttp）驱动，走 `/v1/completions` 端点，读取**相同的 JSONL 工作负载文件**，保证提示与请求时序完全一致。
  - 支持两种到达模式：**突发（burst，一次性全部发出）**与**固定速率（fixed-rate，请求 i 在 i/QPS 时刻释放）**。注意固定速率是**确定性等间隔**，非泊松过程。
  - **两类工作负载生成器**：
    - *合成重复前缀轨迹*：请求形如 ⟨共享前缀⟩∘⟨唯一后缀⟩，在 Qwen2 分词器下可精确控制 token 数；可独立调节共享前缀长度、后缀长度、输出长度、不同前缀数、请求数。
    - *真实 RAG 式模板轨迹*：长系统提示 + 8 篇随机检索文档之一 + 8 个查询模板之一，用于验证合成结论的可迁移性。
- **测量与统计口径**：
  - TTFT 以**第一个非空流式 token** 为计时点；同时记录端到端延迟、输出 token 数、HTTP 错误。
  - 每个 cell 前后抓取运行时 `/metrics`（Prometheus），以**增量**恢复前缀缓存查询数、命中数、复用 KV 块数。
  - **缓存命中率的归一化**：把两个结构不同的原生计数器统一为"由缓存服务的输入 token 比例"。vLLM 用 `prefix_cache_hits_total / prefix_cache_queries_total`（块单位相同，比值即 token 比例）；TensorRT-LLM 用累计 `usage.prompt_tokens_details.cached_tokens / prompt_tokens`。二者均在离线用同一公式从原始日志计算，而非信任运行时自报聚合值。
  - **理论无驱逐上界（ceiling）**：对一个从 np 个前缀均匀抽取、共 N 个请求的 cell，命中率上界为 **1 − np/N**（每个前缀至少必然 miss 一次）。论文以"每 cell 对比自身 ceiling"而非跨行直接比命中率，来把**驱逐效应**与**重访次数差异**分离开。
- **扫描维度**：前缀长度、后缀多样性、并发度、输出长度、缓存配置（共五个轴）。

## 三、实验设计

### 硬件与软件环境
- 单块 **NVIDIA H100 NVL**（94 GB HBM3），驱动 580.105.08，400 W 默认功耗墙；宿主机为 Azure Ubuntu 24.04 VM；启用 persistence mode。
- **vLLM 0.21.0** + PyTorch 2.11.0（CUDA 13.0）；**TensorRT-LLM 1.2.1** + PyTorch 2.9.1（CUDA 12.8）；两者装在隔离虚拟环境中避免依赖冲突。TensorRT-LLM 使用 **PyTorch 后端**（1.x 的文档默认），暴露与 TensorRT 后端相同的 `KvCacheConfig` 参数（`enable_block_reuse`、`tokens_per_block`）。
- **主模型**：Qwen/Qwen2-7B-Instruct（7.6B，BF16 权重，32K 上下文）。**辅助模型**：Qwen2.5-32B-Instruct（缓存压力实验）、Mistral-7B-Instruct-v0.3（跨架构验证）。
