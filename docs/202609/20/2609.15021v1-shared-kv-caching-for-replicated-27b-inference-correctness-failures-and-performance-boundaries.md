## 摘要
共享主机内存缓存可以在请求于推理副本之间迁移时避免重复预填充。其实用性既取决于状态传输是否正确，也取决于前缀局部性的损失程度。我们研究了两个单 GPU 的 27B vLLM 副本，它们共享一个 256 GiB 的 LMCache 池。在采用现有的 packed-page 补丁后，我们分离出一个 raw-pointer 回退路径，该路径遗漏了对当前 CUDA 流的依赖。受控字节测试在施加延迟时失败，而在恢复该依赖后通过；现有的混合分配器提供了一条可工作的部署路径。全池分配检查和服务回归完成了验证。一个四区块 OFF-ON-ON-OFF 对比在两个区块对内包含 768 个受测请求。在 128k 输入下，跨副本首个内容 token 时间中位数从 31.715 秒降至 0.605 秒；在 256k 下，从 92.047 秒降至 0.790 秒。在初始上下文为 32k 和 128k 时，交替副本的六轮合成会话分别提升约 35% 和 45%，而固定放置几乎没有收益。本工程案例研究识别了实用的验证步骤，以及共享缓存能够带来收益的局部性条件。

## Abstract
Shared host-memory caching can avoid repeated prefill when a request moves between inference replicas. Its usefulness depends on both correct state transfer and lost prefix locality. We study two single-GPU 27B vLLM replicas sharing a 256 GiB LMCache pool. After adopting an existing packed-page patch, we isolate a raw-pointer fallback that omits the dependency on the current CUDA stream. Controlled byte tests fail under an imposed delay and pass when the dependency is restored; the existing mixed allocator provides a working deployment path. Full-pool allocation checks and service regression complete the validation. A four-block OFF-ON-ON-OFF comparison contains 768 measured requests within two block pairs. Median cross-replica time to first content token falls from 31.715 to 0.605 seconds at 128k input and from 92.047 to 0.790 seconds at 256k. Six-turn synthetic sessions alternating replicas improve by approximately 35% and 45% at initial contexts of 32k and 128k, while fixed placement shows little benefit. This engineering case study identifies practical validation steps and the locality conditions in which shared caching pays off.

## 1. 核心问题与整体含义

- **背景**：多轮推理请求通常携带大量已在上一轮处理过的上下文。若请求被路由到原副本，可复用本地前缀状态；若迁移到另一副本，则该前缀需重新 prefill，代价高昂。
- **部署选择**：① 通过放置策略保持请求局部性；② 提供跨副本共享状态复用路径；③ 两者结合。
- **核心问题**：共享主机内存 KV 缓存（LMCache）看似可用时可能返回**错误状态**——HTTP 200 或命中计数器并不等于完整性校验；同时，"冷 vs 热"的对比容易掩盖一个竞争性基线——把会话留在原 GPU 上。
- **整体含义**：本文是一项**工程案例研究**，主张"先验证正确性，再测量性能"，并保留本地命中基线，从而明确共享缓存在何种局部性条件下真正带来收益。

## 2. 方法论

### 2.1 系统架构
- 单推理主机上部署**两个完整的 vLLM 副本**（各占一张 GPU，各自做 prefill + decode），共享一个 **256 GiB 主机内存 LMCache 服务**；网关仅做路由，不承担 KV 数据存储层。
- 每个副本保留自己的 GPU 前缀缓存；**非** prefill/decode 分离架构。
- 共享层：1,568-token chunk，四个 kernel group 归并为两个 object group，LRU 策略；两个实验臂均禁用原生 RAM offload。

### 2.2 混合状态与恢复边界
- "KV 缓存"此处涵盖**可在共同前缀边界恢复的混合解码状态**：full attention 贡献前置 K/V 页；Gated DeltaNet 贡献卷积态与循环态的边界快照。
- 补丁将整个循环页（卷积态 + 循环态 + padding）视为不透明可寻址字节；其 attention 形状视图**不**意味着 per-token K/V 或 INT8 量化。
- kernel group 0–2（1,568-token 窗口）→ object group 0；full-prefix attention kernel group 3 → object group 1。在 `align` 语义下，恢复需同时具备 attention 前缀块与对应循环快照，**仅命中 attention kernel group 不构成完整恢复**。

### 2.3 三类正确性修复（核心贡献）

**（a）packed-page 表示兼容性**
- 现象：跨副本响应返回乱码，但 HTTP 200 且外部命中 25,088 token。
- 根因：逻辑 full-attention 块由多个 packed kernel page 组成；原处理识别了 rank-5 attention 张量，却遗漏 rank-4 packed 表示，导致传输字节视图错误。
- 修复：采用上游 packed-subpage 补丁（commit `f180b9ff...`）。27B 场景下 1,568-token 逻辑块跨越 49 个 32-token 页。要求 **HND** 布局（NHD 启动因 kernel-page 数整除错误失败），属配置相关要求而非 LMCache 通性要求。

**（b）可复现的 stream 顺序性故障**
- 现象：表示修复 + 整池注册变通后，128k 服务仍失败。同一输入在 A 冷启/本地复用得到 `alpha=938639`；B 外部命中 127,008 token 却返回 `938624`，且 B 本地复用保留该错误；**新建 cache salt 强制零命中冷算后恢复正确**——将问题指向共享状态传输/复用。
- 根因：评测镜像缺少 LMCache CUDA-ops 扩展，走 PyTorch 回退；`lmcache_memcpy_async` 的 **raw-pointer 分支调用 `cudaMemcpy(..., cudaMemcpyDefault)` 时未传当前流**（`cudaMemcpyDefault` 是拷贝类型枚举，而非函数名）。PyTorch 流池使用 `cudaStreamNonBlocking`，非默认流被排除在 legacy 默认流的隐式同步之外，因而缺失生产者/消费者依赖。
- 受控字节探针（整数字节，非浮点/采样差异）：
  - 1 MiB D2H：延迟写入字节值 37，回退后主机读到旧值 0；
  - 1 MiB H2D：读取旧值 0，经回退覆盖为 53，消费者读到 53；
  - 每个探针报告 1,048,576 字节不匹配。
- 9 月 13 日补充对照（固定 pin 主机缓冲与 GPU 缓冲，仅变顺序机制）：两个独立进程在空闲的第三张 GPU 上，测试 4 KiB / 1 MiB / 16 MiB 双向对象，延迟为 0 或 10⁸ CUDA sleep cycles，每格 10 次试验。**raw 回退在 120 次延迟检查中全部失败、120 次无延迟检查全部通过**；三种修复（先等待前序流工作、在当前流上用 `cudaMemcpyAsync`、同流 tensor 拷贝）**720 次检查全部通过**。
- 分配器/helper 层面：单个 1 MiB `uint8` 对象，lazy 路径在 GPU 0 上 10/10 失败；mixed 路径在 GPU 0 与 GPU 1 上各 10/10 通过。
- 修复方式：显式设置 `--no-l1-use-lazy` 选用现有 mixed 分配器及其 tensor-copy 路径；**仅移除 lazy 正标志不够**，因为该 CLI 默认即为 lazy 分配。

**（c）全池 pinned 分配**
- 现象：小规模 mixed 探针可 pin 成功，但首次 256 GiB 服务分配回退到 pageable 内存。
- 分析：分配器请求 256 GiB + 4096 字节对齐；PyTorch 主机分配器的 2 的幂取整可能将其放大到 512 GiB。日志仅保留泛化分配失败，故**不能确立取整为唯一原因**。
- 修复：设 `PYTORCH_CUDA_ALLOC_CONF=pinned_max_round_threshold_mb:128` 限制大分配取整，且不缩小 LMCache 池。隔离进程中 274,877,911,040 字节分配 `is_pinned()=true`，耗时 38.973 s；正式服务池初始化约 42 s，无 pinned 回退告警。
- 强调：**pinning 与拷贝顺序是两件独立属性**；中间 pageable 阶段的计时不计入最终 ON/OFF 实验。

**（d）分层验证**（Table 2）
- packed 表示：兼容性测试通过；拷贝顺序控制：延迟 raw 120/120 失败，有序控制 720/720 通过；实际分配器/helper：lazy 10/10 失败，mixed 20/20 通过（跨两张 GPU）；中间服务阶段：207 条非预热精确答案请求通过（mixed/pageable 回归）；最终 pinned 服务阶段：57 条非预热精确答案请求通过；协议检查 11 项通过（工具调用与流式行为）。

## 4. 结果

### 4.1 正确性
- **修复前**：外部命中在 HTTP 200、命中计数正常的情况下返回错误状态；128k 场景下 `alpha=938624` vs 本地复用的 `938639`，且错误经共享层可"传染"至后续本地复用，直到强制冷算才恢复——说明故障发生在共享状态的传输/复用，而非计算本身。
- **修复后**：分层验证全部通过（packed 表示兼容性、拷贝顺序 720/720、实际分配器/helper 20/20 跨卡、中间服务阶段 207 条、最终 pinned 服务阶段 57 条、协议检查 11 项）。**在最终配置下，未再观察到"命中但错误"的样本。**

### 4.2 性能边界
- **相对冷启动**：外部命中在长上下文（32k 以上）显著降低 TTFT，因为省去了跨副本前缀的重新 prefill；收益随上下文长度增长。
- **相对本地命中**：这是关键对照。当请求本可路由回原副本时，共享层的外部命中**不优于**本地命中——本地命中无需经主机内存往返与状态恢复，时延更低。因此共享缓存的净收益只出现在**局部性被破坏**的场景（路由漂移、副本扩容/重启、跨会话前缀共享）。
- **命中代价结构**：即使命中，恢复也需同时具备 attention 前缀块与对应循环快照（`align` 语义），"仅命中 attention kernel group"不构成完整恢复，故有效命中率低于表面命中计数。
- **配置敏感性**：HND 布局为 27B packed-page 场景的配置要求；`--no-l1-use-lazy` 与 `PYTORCH_CUDA_ALLOC_CONF=pinned_max_round_threshold_mb:128` 是让正确性与 pinned 分配生效的必要条件，而非可选优化。

### 4.3 计时口径
- pinned 初始化约 42 s、隔离分配 274,877,911,040 字节耗时 38.973 s，均属**启动成本**，不计入 ON/OFF 的稳态对比；中间 pageable 阶段的计时同样被排除，以保证两臂可比。

## 5. 讨论

- **"可运行"不等于"正确"**：命中计数器与 HTTP 200 会掩盖状态完整性问题；正确性必须由端到端精确比对（而非计数）来确立。本文的三类故障（表示兼容、流顺序、分配回退）分属不同抽象层，说明正确性验证必须**分层**进行。
- **共享缓存的定位**：它不是本地命中的替代品，而是局部性失效时的**降级路径**。部署上应优先保证请求亲和性（放置策略），仅在亲和性不可得时使用共享复用。
- **竞争性基线不可省略**：若只对比"冷 vs 热"，会高估共享层的价值；保留"留在原 GPU"的基线，才能刻画收益的适用条件。
- **代价与边界**：主机内存池的容量（256 GiB）、chunk 粒度（1,568 token）与 LRU 策略共同决定命中窗口；pinning 与拷贝顺序是**两个独立属性**，需分别验证，任一缺失都可能表现为"看似命中却出错"或"分配悄悄回退"。

## 6. 局限性与适用边界

- 单主机、双副本、27B 规模，结论向更大副本数或跨主机共享的推广需额外验证。
- 评测镜像缺少 CUDA-ops 扩展时走 PyTorch 回退路径，故部分故障在装有官方扩展的环境中可能不出现；本文的修复对回退路径具针对性。
- 分配失败日志仅保留泛化信息，**取整放大不能确立为唯一原因**，pinned 修复的普适性有限。
- 工作负载为合成文件文本与受控多轮会话，未覆盖真实生产流量的分布多样性。

## 7. 结论

本文以工程案例研究的形式，给出了一条"先验证正确性、再测量性能、并保留本地命中基线"的方法论：在多副本 27B 推理中，共享 KV 缓存能在局部性失效时显著降低长上下文 TTFT，但其价值必须以**端到端精确正确性**为前提，以**本地命中**为对照来界定。三类修复——packed-page 表示兼容、流顺序显式化、全池 pinned 分配——分别对应表示层、并发层与内存层，缺一即可能退化为"命中但错误"或"静默回退"。
