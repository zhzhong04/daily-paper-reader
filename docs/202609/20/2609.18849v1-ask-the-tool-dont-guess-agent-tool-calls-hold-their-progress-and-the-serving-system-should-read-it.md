## 摘要
一个智能体请求会耗费大量实际时间等待工具，而其 KV 缓存全程占用 GPU 内存。服务系统通过猜测工具将运行多久来决定该缓存是保留、驱逐还是重新载入，猜测依据包括工具名称、其历史、调用前声明的时长，或引擎自身的占用情况。我们表明，任何在调用开始前固定的估计都无法知道其持续时间，而且这类估计甚至可能无法对调用进行排序。与此同时，正在运行的工具已经掌握答案，但智能体栈连同工具却让它保持沉默。我们提出，工具调用应在运行时显式报告其进度，并衡量实现这一点所需的代价。对四个公开智能体语料库的普查发现，一旦被揭示，大多数工具时间内都存在可读信号，且有两种强度：剩余工作量的比例，或接近结束的准确信号。一个测试框架在不改变智能体所见内容的情况下恢复该信号，且对智能体基准分数没有可测量的代价。在做出 KV 缓存决策的时刻，所报告的进度比已发表的最佳预测器准确数倍至一个数量级，并且在环境变化时仍保持准确。通过少量小提示接入生产引擎后，与 LRU 相比，它将工具调用后的 p90 首 token 时间（TTFT）分别降低 20.7%（仅 HBM）和 20.8%（HBM + DRAM），接近 oracle。服务系统不应猜测工具能够告诉它的信息。

## Abstract
An agentic request spends substantial wall-clock time waiting for tools, and its KV cache holds GPU memory the whole time. Serving systems decide whether that cache stays, leaves, or comes back by guessing how long the tool will run, from the tool's name, its history, a duration declared before the call, or the engine's own occupancy. We show that no estimate fixed before a call starts can know its duration, and such estimates may not even rank the calls. Meanwhile, the running tool already holds the answer, but the agent stack together with the tool silences it. We propose that tool calls report their progress explicitly while they run, and we measure what that takes. A census of four public agent corpora finds a readable signal in most tool time once it is revealed, in two strengths: a fraction of the work remaining, or an accurate signal that the end is near. A harness recovers it without changing what the agent sees, at no measurable cost to the agent's benchmark score. At the points where a KV cache decision is made, the reported progress is between several times and an order of magnitude more accurate than the best published predictors, and it stays accurate when the environment changes. Plugged into a production engine through a few small hints, it cuts the p90 time to first token (TTFT) after a tool call by 20.7% (HBM only) and 20.8% (HBM + DRAM) against LRU, close to an oracle. A serving system should not guess what its tools can tell it.

## 1. 核心问题与研究动机

- **背景**：智能体（agentic）请求在两次模型轮次之间要等待工具执行（shell 命令、构建、测试套件、安装、生成的脚本），其间 KV 缓存一直占用 GPU 显存。服务系统必须决定该缓存**保留、驱逐还是重新载入**。
- **现状（"猜"）**：现有系统只能靠调用前可得的信息猜测工具时长——工具名称、历史调用时长、调用前声明的 duration、引擎自身占用率等。论文把这些信号整理成一条"阶梯"（Table 1）：固定 TTL → 已耗时间外推 → 按工具统计 → 学习模型（名称+参数）→ 引擎侧占用观测 → 调用前声明时长。
- **核心论断一**：**任何在调用开始前固定的估计都无法知道真实时长，甚至无法对长调用正确排序**。长调用的时长由机器负载、沙箱邻居、远程 API 状态决定，命令行里看不到；作者把 leaderboard 记录的命令在空闲沙箱重放，同一命令快一个数量级（中位 0.12×）；加入竞争邻居后中位慢 3.83×；记录顺序与空闲重放顺序的 Kendall τ 分别为 −0.04 与 −0.07（即几乎无排序能力）。历史只有在"与当前环境匹配"时才有用，而同时满足"足够大"（如 Continuum 要求每工具约 100 次历史）与"同一负载下采集"的历史几乎不存在。
- **核心论断二**：**运行中的工具其实已经掌握答案，只是被"消音"了**。三层沉默：(1) 基础设施通过环境变量关闭 pip/tqdm 进度条；(2) agent 自己用 `| tail`、`-q`、重定向丢弃约 5/6 的工具时间输出；(3) agent 自己生成的脚本没有进度输出。
- **整体含义**：这是一个范式转换主张——把服务端从"隐式预测时长"改为"显式读取工具进度"，与数据库领域早已确立的结论（不执行查询的估计器误差无界，唯一可靠的进度指示是查询自身的工作计数）相呼应。

## 2. 方法论

### 2.1 核心思想
- 工具调用在**运行期间显式上报进度**，并随执行不断修订；服务端读取该报告来驱动 KV 缓存决策。
- 信号分两种强度：
  - **强信号（Strong）**：报告剩余工作量（分数，或"已知总数下的已完成计数"）。
  - **弱信号（Weak）**：只准确报告"接近结束"（stop signal），不给可信分数。
- 其余类别：**Negligible**（太短无需关心）、**Declared**（命令自带精确时长/上界，如 `sleep`、`timeout`）、**Unparsable**（无法解析，如长远程 API、等待人工反馈）。

### 2.2 架构：一次执行，两个消费者（Figure 6）
- **铁律**：agent 的观察不得改变。结果路径原样不动，进度经**独立的侧信道（side channel）**按 `call_id` 上报给服务端。
