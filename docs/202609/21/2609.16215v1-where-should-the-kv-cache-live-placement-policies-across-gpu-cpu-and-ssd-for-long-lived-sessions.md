## 摘要
GPU 高带宽内存稀缺且昂贵，而随着聊天、智能体循环和文档问答不断累积状态，KV 缓存会消耗其中很大一部分。Mooncake、LMCache、FlexGen、InfiniGen 和 AttentionStore 等系统利用 CPU DRAM 和 SSD 扩展 GPU 内存。更难的问题是：哪些块应属于哪个层级、何时迁移或逐出它们，以及预取是否有帮助。我们在一个涵盖 GPU HBM、CPU DRAM 和 SSD 的离散事件模拟器中研究这些选择，并以随机森林执行时间预测器进行校准。我们在聊天、智能体和文档问答工作负载上比较了最近使用（recency）、复用频率、预测复用，以及带预取前瞻的 EWMA 预测器。分层存储使每块 GPU 支持的并发会话数达到原来的 73.02 倍，并将每会话成本降至原来的 1/62.04。这些收益来自 1+8+64 的层级容量，而非放置策略。在我们的设置中，批大小为 1 时解码是计算受限的，因此放置几乎不影响吞吐量。它主要改变 PCIe 迁移流量和首 token 时间。对于聊天，最近使用产生的迁移流量比复用频率少 2.30 倍。复用频率在智能体和文档问答中表现最佳。现有的预测复用策略与最近使用逐字节相同，因此其面向智能体的推荐实际上就是最近使用。真正的 EWMA 预测器会改变行为，但在原本预期预测能帮助的工作负载上仍落后于复用频率。预取的收益不足以抵消其带宽成本。在策略与缓存大小的网格中，即使一个知晓未来请求的 oracle，在迁移流量上也从未优于不预取。针对特定工作负载的放置可以减少数据移动，但按当前实现，预测复用和预取建议并未得到支持。

## Abstract
GPU high bandwidth memory is scarce and expensive, and KV caches consume much of it as chats, agent loops, and document question answering accumulate state. Systems such as Mooncake, LMCache, FlexGen, InfiniGen, and AttentionStore extend GPU memory with CPU DRAM and SSD. The harder question is which blocks belong in each tier, when to move or evict them, and whether prefetching helps. We study these choices in a discrete event simulator spanning GPU HBM, CPU DRAM, and SSD, calibrated against a random forest execution time predictor. We compare recency, reuse frequency, predicted reuse, and an EWMA predictor with prefetch lookahead across chat, agent, and document question answering workloads. Tiering supports 73.02 times more concurrent sessions per GPU and lowers cost per session by 62.04 times. These gains come from tier capacities of 1 plus 8 plus 64, not placement policy. Decode is compute bound at batch size one in our setup, so placement barely affects throughput. It mainly changes PCIe migration traffic and time to first token. Recency produces 2.30 times less migration traffic than reuse frequency for chat. Reuse frequency performs best for agents and document question answering. The existing predicted reuse policy is byte identical to recency, making its agent recommendation effectively recency. A genuine EWMA predictor changes behavior but still ranks behind reuse frequency on the workloads prediction was expected to help. Prefetching does not justify its bandwidth cost. Across the policy and cache size grid, even an oracle with knowledge of future requests never beats no prefetch on migration traffic. Workload specific placement can reduce data movement, but the predicted reuse and prefetch recommendations are not supported as implemented.

## 1. 核心问题与整体含义（研究动机与背景）

- **资源稀缺性**：GPU 高带宽内存（HBM）是 LLM 服务中最稀缺、最昂贵的资源，而 KV 缓存是其最大消耗者——单个长上下文的 KV 已可与模型权重相当。
- **现实需求**：长时间聊天、Agent 工具循环、文档问答（RAG）等长生命周期会话会跨轮次累积 KV 状态，多并发场景下远超 HBM 容量。
- **现有应对**：要么每次恢复会话时重算 prefill（浪费算力与金钱），要么限制并发。更自然的思路是扩展内存层级：Mooncake、LMCache、FlexGen、InfiniGen、AttentionStore 等将 KV 溢出到廉价且容量更大的 CPU DRAM 与 SSD，在会话恢复时回取。
- **核心痛点**：**机制已基本解决，难的是"策略"**——哪些块放哪个层级、何时提升（promote）、降级（demote）、驱逐（evict）、预取（prefetch），以及策略如何随工作负载变化。层级间带宽/延迟差距巨大（HBM 比 SSD 快数百倍），错误放置要么浪费 HBM，要么在解码时因取盘而停顿。
- **整体含义**：论文把"放置策略本身"作为研究对象，试图给出一份"按工作负载选择策略"的实践指南，并验证业界路线图中关于"预测复用"和"预取"的建议是否成立。

## 2. 方法论：核心思想与关键技术细节

### 2.1 分层缓存模型
- KV 缓存以 **PagedAttention 固定块**为粒度，每个块驻留在三个层级之一：**GPU HBM（小、快、热）、CPU DRAM（中、温）、SSD（大、廉、冷）**。
- 设容量 $c_g \ll c_d \ll c_s$，带宽 $b_g \gg b_d \gg b_s$。放置策略即在容量约束下把每个活跃块映射到某个层级。

### 2.2 逐访问路径（Algorithm 1）
- 若块已在 HBM → 直接使用（命中）；
- 否则沿层级向上取回并提升至 HBM；
- 若 HBM 已满 → 将得分最低的块降级到 DRAM，DRAM 满则级联降级到 SSD；
- 预取：对预测即将使用的块提前上取，与计算重叠；
- 更新该块的策略得分 $s(b)$，记录命中层级与解码停顿。

### 2.3 三类放置策略族
1. **Recency（LRU 式分层）**：保留最近使用块在高层级；
2. **Reuse frequency（复用频率）**：保留被重新访问最频繁的块，偏向共享前缀；
3. **Predicted reuse（预测复用）**：以廉价预测器猜测下一轮会触及的块（InfiniGen 思路）；
4. **Predictive（EWMA 预测器）**：论文自行补充的"真正做预测"的策略，用 EWMA 估计下一次触及，经验证与 recency 行为不同。

### 2.4 预取机制
- 设定前瞻窗口（lookahead），在需要的解码步之前把块移到 HBM，用传输重叠计算；前瞻深度在 HBM 占用与停顿规避之间权衡，论文做了扫描。
- **关键建模选择**：在"带宽计费"模型下，投机预取与需求取回**共享同一条 PCIe 链路**并相互竞争。

### 2.5 成本模型
- 有效容量为 $c_g + c_d + c_s$，混合成本被廉价层级主导，因此分层可服务远超纯 HBM 的并发会话；
- 代价是未命中时的取回延迟，需由策略与预取保持在解码关键路径之外。

## 6. 主要结论与发现

1. **分层收益是容量收益，不是策略收益**：分层使单 GPU 并发会话数提升 **73.02×**、单会话成本下降 **62.04×**，该倍数恰好等于层级容量倍数（1+8+64 = 73），在整个比例扫描中稳定在 72.68×–73.22×，几乎与复用结构无关。
2. **Batch 1 下策略几乎不影响吞吐**：解码为算力受限，聊天吞吐恒为 1307.60 tok/s；策略真正控制的是 **PCIe 迁移流量与 TTFT**。
3. **工作负载决定胜者**：
   - 聊天：**recency（LRU）** 迁移流量 27.38 GB，比复用频率的 62.99 GB 少 **2.30×**，且 TTFT 更优；
   - Agent 与文档 QA：**复用频率**胜出，分别为 49.36 GB（1.60×）与 48.23 GB（1.63×）。
4. **"预测复用"名不副实**：现有 shipped 的 predicted-reuse 策略在**每个工作负载上都与 recency 逐字节相同**，因此"Agent 用预测复用"实际就是 recency，而 recency 在 Agent 上又略逊于复用频率。
5. **EWMA 预测器仍不敌复用频率**：论文补充的 predictive 策略确实与 recency 不同，但在 Agent（53.16 GB vs 49.36 GB）和文档 QA（48.45 GB vs 48.23 GB，近乎持平）上均列第二，在聊天上大幅落后（57.76 GB）；预测的价值仅出现在**一个很窄的中间缓存尺寸窗口**。
6. **预取不划算**：在带宽计费、投机与需求共享链路的模型下，因果预测器在**所有网格单元**中都未捕获 oracle 的正收益；即便 oracle 本身也在**超过一半**的单元中慢于不预取。
7. **成本–延迟前沿近乎垂直**：成本（每 1k 会话）是层级组成的纯函数，跨度 **8.38×**（\$45,493–\$381,287）；而 P99 TTFT 在整个跨度中最多只变化 **10.1%**。最优部署点是**偏 SSD 的廉价组合**（HBM/DRAM/SSD = 10/86/96）。
8. **深 SSD 的 SLO 表现**：加深 SSD 可最大化会话数（**10.77×**），但聊天与 Agent 在扫描范围内**从未满足** SLO；只有文档 QA 在 SSD 深度 64 处达标，且余量为 **0.000 ms**（恰好在线上），仍需支付 4.42 ms 平均停顿。
9. **DRAM 才是主力层**：赢家策略下，DRAM 承担了大部分溢出流量（聊天 61.87%、Agent 72.65%、文档 QA 68.48%），SSD 只是浅层后备（6.07%–8.80%），残余需重算的未命中率约 13.62%–14.15%。

## 7. 优点

- **清晰的"机制 vs 策略"分离**：明确指出容量/成本收益来自机制（挂载廉价层级），策略是二阶的带宽–延迟决策，避免了把机制收益误记为策略功劳。
- **诚实的证伪性研究**：不回避负面结果，用数据反驳了路线图中"预测复用 + 预取"的建议，并把证伪本身作为贡献报告。
- **代码级验证而非假设**：验证了 predicted_reuse 与 recency 逐字节相同、成本函数与工作负载/策略无关等关键论断。
- **预取建模严谨**：在**竞争链路上对投机取巧流量计费**，并引入 oracle 上界，说明"预取不划算"不是预测器太弱，而是带宽资源约束。
- **协议透明**：主动披露将聊天从单会话改为 6 并发会话的原因（单会话下驱逐顺序无关、策略无法区分），并把原始结果文件保留。
- **多维消融**：覆盖策略、块粒度、预取前瞻、缓存尺寸、层级组成、SSD 深度，并给出成本–延迟前沿这一部署导向的分析。

## 8. 不足与局限

- **合成工作负载偏差**：复用结构由生成器构造，天然有利于与之匹配的策略，策略间差距是**上界**，真实轨迹下会压缩甚至消失。
- **Batch size 1、单 GPU**：解码算力受限、取回停顿 <1% TPOT，导致放置与预取的价值被系统性低估；更大 batch 或更快解码内核下结论可能反转。
- **无真实硬件实验**：全部为离散事件模拟，缺乏真实 GPU/PCIe/SSD 的实测验证；预取结论也依赖"链路竞争"这一特定建模假设。
- **成本数字为假设值**：\$187.50/\$3.50/\$0.08 每 GB 来自默认配置而非市场报价，绝对金额不可直接引用。
- **停顿归因近似**：DRAM 与 SSD 的停顿份额按命中率分摊，模拟器未记录每个停顿毫秒的具体来源层级。
- **范围限定**：与 KV 量化、KV 驱逐等压缩技术正交但被固定，未考察组合效应；块粒度虽扫描但未与压缩联合优化。
- **预测器结论有限**：EWMA 仅在窄容量窗口获胜，作者承认"能广泛获胜的预测器仍是开放问题"。
- **会话数/成本为容量模型输出**：给定价格即精确，但代表性完全取决于价格假设。
