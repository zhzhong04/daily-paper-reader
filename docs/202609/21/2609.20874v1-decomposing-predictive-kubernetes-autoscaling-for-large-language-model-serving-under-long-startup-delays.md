## 摘要
部署在 Kubernetes 上的大语言模型（LLM）推理面临传统 Web 服务所没有的自动扩缩容挑战：新的服务副本需要两到十分钟才能启动，因为必须加载数 GB 的模型权重，这使得纯反应式扩缩容在结构上必然滞后。我们提出一个尖锐的问题：在预测式自动扩缩器的各组件中，哪些在如此长的执行延迟下才真正重要？我们通过将预测式自动扩缩容分解为四个因素——token 感知的需求跟踪、启动延迟前瞻、有界不确定性裕度以及被控对象状态观测——并在由 ServeGen 生成的源自生产环境的重尾工作负载上单独测量每个因素的贡献来回答这个问题。我们的主要发现是，一个简单的指数加权移动平均（EWMA）预测器，配合延迟感知前瞻和上置信界（UCB）裕度，就能获得大部分收益：在五个随机种子下，将首 token 时间（TTFT）服务等级目标（SLO）违规率从 53%（反应式、基于每秒查询数）降至 0.5%；仅前瞻一项就是最大的单一因素，带来 14× 的降低。卡尔曼滤波变体并不能稳定改善成本—SLO 权衡。受控实验分离出 token 粒度之所以必要的原因：在匹配吞吐量下，上下文长度通过键值（KV）缓存压力对 TTFT 的劣化远大于请求速率。最后，在真实 Kubernetes 集群（Qwen2.5-7B、A100、vLLM）上的验证证实了核心机制：相对于反应式 KEDA 扩缩容，延迟感知前瞻控制器将 TTFT 违规率从 63.5% 降至 3.7%。我们全程区分哪些发现特定于 Kubernetes 执行机制，哪些对 LLM 服务具有普适性。

## Abstract
Large language model (LLM) inference deployed on Kubernetes faces an autoscaling challenge that conventional web services do not: new serving replicas take two to ten minutes to start because multi-gigabyte model weights must be loaded, which makes purely reactive scaling structurally late. We ask a sharp question: among the components of a predictive autoscaler, which ones actually matter under such long actuation delays? We answer it by decomposing predictive autoscaling into four factors---token-aware demand tracking, startup-delay lookahead, a bounded uncertainty margin, and plant-state observation---and measuring each factor's contribution in isolation on production-derived heavy-tailed workloads generated by ServeGen. Our main finding is that a simple exponentially weighted moving average (EWMA) predictor with delay-aware lookahead and an upper confidence bound (UCB) margin captures most of the benefit, reducing time-to-first-token (TTFT) service-level-objective (SLO) violations from 53% (reactive, queries-per-second based) to 0.5% across five random seeds; lookahead alone is the single largest factor, a 14$\times$ reduction. Kalman filter variants do not consistently improve the cost--SLO tradeoff. Controlled experiments isolate the reason token granularity is necessary: context length, through key--value cache pressure, degrades TTFT far more than request rate at matched throughput. Finally, a validation on a real Kubernetes cluster (Qwen2.5-7B, A100, vLLM) confirms the central mechanism: a delay-aware lookahead controller cuts TTFT violations from 63.5\% to 3.7\% relative to reactive KEDA scaling. We distinguish throughout which findings are specific to Kubernetes actuation and which are general to LLM serving.

## 1. 核心问题与研究动机

- **背景**：LLM（GPT/Llama/Qwen 等）越来越多地以在线推理服务形式部署在 Kubernetes 集群上，自动扩缩容（调整服务副本数）比传统 Web 服务更难，原因有两类，作者全程刻意区分：
  - **LLM 服务本身的普适性问题**：负载不等于请求数。每个请求的输入（prompt）与输出（completion）token 数可变；推理分 prefill（计算受限，决定 TTFT）与 decode（显存带宽受限，决定 TPOT）两阶段；decode 期间需在 GPU 显存中保存所有活跃序列的 KV cache。4096 输入 token 的请求约消耗 256 token 请求的 16 倍 prefill 计算与 KV 缓存，而 QPS 指标把二者视为相同。**KV cache 而非 GPU 计算往往是真正的容量瓶颈**（vLLM 按空闲 block 数 gating 请求准入，计算可空闲而缓存满即阻塞）。
  - **Kubernetes 执行路径特有的问题**：启动新副本需拉取并加载 14–140 GB 权重（7B–70B）、初始化 CUDA 上下文、捕获执行图，耗时 **2–10 分钟**，比无状态 Web pod 的秒级启动慢数个数量级。这构成**延迟执行控制问题**：任何反应式策略都结构性滞后 ∆。
- **核心问题**：预测式自动扩缩器有很多部件（需求估计器、前瞻窗口、不确定性裕度、状态观测器、Kalman 滤波等），**哪些在长启动延迟下才真正重要？** 应投资复杂预测器，还是简单配方就够？作者认为此前没有受控的因素分解研究回答过这个问题。
- **整体含义**：厘清长启动延迟下真正起作用的组件，避免"攻击错误的问题部位"，并明确哪些结论是 K8s 特有、哪些对 LLM 服务普适。

## 2. 方法论

### 2.1 核心思想
实现**单一预测式扩缩容框架**，实例化为一组"每次只差一个设计因素"的变体，从而直接读出每个因素的贡献。四因素分解：
1. **Token 感知需求跟踪**（监测 prefill/decode token 速率而非 QPS）
2. **启动延迟前瞻**（预测 t+∆ 的需求而非反应当下）
3. **有界不确定性裕度**（按预测需求的上置信界而非点估计扩缩）
4. **被控对象状态观测**（除需求外还跟踪队列深度与 KV 缓存压力）

### 2.2 系统模型假设
- R 个同构副本，每副本为单 GPU 全模型（tensor-parallel-size=1）；prefill 与 decode **共置**（共享 KV cache 的连续批处理），不采用 DistServe/Splitwise 式分离部署（明确列为未来工作）。
- 负载均衡采用 **join-shortest-queue**，使各副本负载近似均衡，从而支撑"总需求 ÷ 单副本容量"的算术。
- 容量常数：单副本 prefill 吞吐 Cp=8000 tokens/s、decode 吞吐 Cd=500 tokens/s（由仿真器饱和点剖析并与 Vidur 硬件标定容量墙匹配，约 20 QPS/Llama-2-7B/A100），属部署相关输入，不做逐实验调参。
- 控制变量：以轮询间隔 T 观测总 prefill token 速率 pt、decode token 速率 dt、队列深度 qt、KV 缓存利用率 kt（均由 vLLM 以 Prometheus 指标导出）；单一动作变量为副本数 R；scale-up 受启动延迟 ∆ 约束。

### 2.3 四步算法流程
- **Step 1 需求估计**：每 T=15 s 由 vLLM 的 prompt tokens total 与 generation tokens total 计数器估计 pt、dt。
- **Step 2 延迟感知前瞻**：用后向差分斜率预测 t+∆ 的需求（∆ 为启动延迟，7B 模型在 A100 上典型 180 s）：
  - 斜率 ŝ = (p̂t − p̂t−T)/T，预测 p̂t+∆ = p̂t + ŝ·(∆ − T/2)，其中 ∆−T/2 修正项用于补偿斜率中心位于 t−T/2。前两个区间（t<2T）斜率未定义，取斜率 0，退化为反应式基线加裕度。
- **Step 3 有界不确定性裕度**：对每个需求维度 i∈{p,d}，按 UCB 扩缩：
  - d_ucb,i = x̂t+∆,i + β·σ_eff,i，其中 σ_eff,i = min(σi, γ·|x̂t+∆,i|)，默认 β=1.5、γ=0.8。
  - **上限截断（cap）是关键**：否则传播的不确定性随前瞻时长无界增长，在长 ∆ 下造成病态过度配置。EWMA-UCB 的 σi 来自预测平方误差的 EWMA；Kalman 变体来自跨前瞻传播的协方差。
- **Step 4 副本数计算**：R* = max(⌈d_ucb,p / Cp⌉, ⌈d_ucb,d / Cd⌉, R_min)。**扩容立即生效；缩容采用 300 s 稳定窗口**（遵循 HPA 惯例）。

### 2.4 变体设计（每行相对上一行只加一个因素）
- **Token-Reactive**：EWMA 跟踪 pt、dt，但按当前平滑需求扩缩，无前瞻、无裕度（隔离"token 感知"与"预测"）。
- **EWMA**：加入延迟感知前瞻（预测 t+∆），仅需求、无裕度（α=0.3，斜率由连续差分得到）。
- **EWMA-UCB**：加入有界裕度（σ 由平方误差 EWMA 得到）——尽管简单却捕获了大部分收益。
- **KF-4state**：用 Kalman 滤波替换 EWMA，状态 x=[pt, ṗt, dt, ḋt]ᵀ，常速模型（Fs=[[1,T],[0,1]]，Hs=[1,0]，prefill/decode 块对角），通过 Kalman 增益自适应信任观测与趋势，并给出标定 σ。
- **KF-6state**：状态扩展队列 qt 与 KV 压力 kt，转移行将队列增长耦合到 prefill 需求（增益 aq、bq）、KV 增长耦合到 decode 需求（ak、bk）。
- **Reactive-Plant**：观测 qt、kt 但不前瞻，阈值越界才扩缩（Chiron 式背压、无延迟补偿）。
