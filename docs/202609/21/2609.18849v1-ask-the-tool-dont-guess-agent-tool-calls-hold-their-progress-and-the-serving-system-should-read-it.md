## 摘要
智能体请求会花费大量实际时间等待工具，而其 KV 缓存全程占用 GPU 内存。服务系统通过猜测工具将运行多久来决定该缓存是保留、移出还是重新载入，猜测依据包括工具名称、其历史、调用前声明的时长，或引擎自身的占用情况。我们表明，任何在调用开始前固定的估计都无法知道其持续时间，而且这类估计甚至可能无法对调用进行排序。与此同时，正在运行的工具已经掌握答案，但智能体栈连同工具一起将其掩盖。我们提出，工具调用应在运行期间显式报告其进度，并衡量实现这一点需要什么代价。对四个公开智能体语料库的普查发现，一旦进度被揭示，大多数工具耗时中都存在可读信号，强度有两种：剩余工作量的比例，或表示即将结束的准确信号。一种测试框架可在不改变智能体所见内容的情况下恢复该信号，且对智能体基准得分没有可测量的代价。在做出 KV 缓存决策的时刻，所报告的进度比已发表的最佳预测器准确数倍到高一个数量级，并且在环境变化时仍保持准确。通过少量小提示接入生产引擎后，与 LRU 相比，它将工具调用后首 token 时间（TTFT）的 p90 降低了 20.7%（仅 HBM）和 20.8%（HBM + DRAM），接近 oracle。服务系统不应猜测其工具能够告知它的内容。

## Abstract
An agentic request spends substantial wall-clock time waiting for tools, and its KV cache holds GPU memory the whole time. Serving systems decide whether that cache stays, leaves, or comes back by guessing how long the tool will run, from the tool's name, its history, a duration declared before the call, or the engine's own occupancy. We show that no estimate fixed before a call starts can know its duration, and such estimates may not even rank the calls. Meanwhile, the running tool already holds the answer, but the agent stack together with the tool silences it. We propose that tool calls report their progress explicitly while they run, and we measure what that takes. A census of four public agent corpora finds a readable signal in most tool time once it is revealed, in two strengths: a fraction of the work remaining, or an accurate signal that the end is near. A harness recovers it without changing what the agent sees, at no measurable cost to the agent's benchmark score. At the points where a KV cache decision is made, the reported progress is between several times and an order of magnitude more accurate than the best published predictors, and it stays accurate when the environment changes. Plugged into a production engine through a few small hints, it cuts the p90 time to first token (TTFT) after a tool call by 20.7% (HBM only) and 20.8% (HBM + DRAM) against LRU, close to an oracle. A serving system should not guess what its tools can tell it.

# 论文总结：Ask the Tool, Don't Guess

## 1. 核心问题与整体含义

**研究动机与背景**

- **问题根源**：智能体（Agent）请求在等待工具执行时会耗费大量墙钟时间，而其 KV 缓存全程占用 GPU 显存却无人使用。服务系统必须在工具调用的"间隙"决定该缓存**保留、移出还是重新载入**。
- **现有做法的缺陷**：当前系统全部依赖"猜测"工具运行时长，依据包括工具名称、历史调用时长、调用前声明的时长、或引擎自身占用情况（表 1 的"时间信号阶梯"）。作者论证：**任何在调用开始前固定的估计都无法预知该次调用的真实时长，甚至无法对长调用进行正确排序**。
- **证据**：在 SWE-bench 排行榜运行中，不到 3% 的工具调用占据了近 2/3 的工具总时间（安装、构建、测试套件、生成脚本）；同一命令在空闲沙箱重放比记录时长快约一个数量级（中位 0.12×）；加入竞争邻居后多数调用慢数倍（中位 3.83×）；长调用在记录环境与空闲环境下的耗时排序几乎无相关性（Kendall τ 低至 -0.07）。
- **关键洞察**：正在运行的工具**已经掌握答案**，但智能体栈将其掩盖——mini-SWE-agent 的 harness 在工具启动前关闭进度条，智能体又把 5/6 的工具输出通过 `tail`、`-q`、重定向过滤掉。
- **整体含义**：服务系统不应猜测工具能告知的信息，而应让工具在运行期间**显式、可修订地报告进度**，并由服务端消费该信号来指导 KV 缓存决策。这一思想借鉴了数据库领域"唯一可靠的进度指标是查询自身的工作计数"的经典结论。

## 2. 方法论

### 2.1 核心思想

工具调用在运行期间通过**独立侧信道**（side channel）显式上报进度，而非在调用前隐式预测时长。信号分为两种强度：

- **强信号（Strong）**：报告剩余工作量的比例或计数（如 "20/66 个文件"）。
- **弱信号（Weak）**：仅准确报告"即将结束"（如最后单元标记、link 步骤、安装收尾标记）。

### 2.2 信号的来源与种类（五类）

| 类别 | 说明 |
|---|---|
| 强信号 | 报告剩余工作量，来源 A–D |
| 弱信号 | 仅报告接近结束 |
| Negligible | 调用太短，无需进度 |
| Declared | 命令自带时长声明（`sleep`、`timeout`） |
| Unparsable | 无法解析（远程 API、等待人工） |

强信号的四个来源：
- **A. 工具自身输出**：测试运行器的百分比列、pip 的包名列表。
- **B. 开关或 dry run**：verbose 标志、环境变量；难点在于计数器缺总量（用 dry run 或扩展列表补齐），或开关无法穿透隔离构建（改为观察磁盘上的目标文件）。
- **C. Hook/SDK**：工具向宿主暴露的进度钩子（如 LSP、MCP 的 progress notification），最干净但最罕见（采样中零命中）。
- **D. 智能体自写代码**：生成脚本时插入进度行，并做等价性校验。

### 2.3 关键设计规则与流程

**一条铁律**：不改变智能体所观察到的内容。结果路径（result path）完全不动，进度从第二条路径离开执行环境（图 6）。

**三层沉默与对应破解手段**：

1. **基础设施/智能体习惯层**：恢复被环境变量关闭的进度条并再次从智能体流中剥离；对 `tail`/重定向，把完整流复制到侧文件，智能体读到的字节与退出码不变。
2. **工具"需被正确询问"层**：用 dry run 求总量、加 verbose 标志并隐藏其输出、解析无换行的点号行（test runner）、在隔离构建中统计对象文件。
3. **智能体自写代码层**：生成时插入进度行，并对比原始/插桩脚本的输出与退出码。

**事件流统一**：每个事件包含 `call_id, work_done, total, phase, timestamp`；wrapper 有两层——解析输出、读取执行环境的磁盘足迹；两者经同一侧信道按 call_id 发送。设计要点包括：

- 计数超过总量时**撤回报告**并退回"无总量计数"，避免虚假 100% 告警。
- 多阶段调用按历史阶段占比**折叠成单一比例**（强信号），占比未知时只保留最后一条柱并报告其结束（弱信号）。
- 可扩展性三条路径：教会智能体开关与解析器、工具所有者暴露 hook（MCP）、后台自动扫描最耗时调用。

### 2.4 引擎侧集成

在 vLLM（开启 prefix caching）上增加少量原语：一条路由以早先响应 id 命名上下文，提供三个操作——`refresh`（无损移到驱逐队列安全端）、`release`（前移但保持可寻址）、`query`（报告驻留量）。调度器、驱逐规则与模型均不改动，无提示时行为与原来完全一致。控制器依据剩余时间估计做 keep/let-go/reload 决策，带 hysteresis。

### 2.5 防作弊机制

进度报告由租户可控内容产生，故服务端**不单独信任报告**：每会话从"事后被证明正确"的报告积累信用，引擎依据报告行动时消耗信用，工具返回发现报告错误时扣减。设两本账（保留显存、冒延迟风险）互相隔离，信用耗尽的会话按无信号方式服务。

## 6. 主要结论与发现

- **猜测注定失败**：调用前估计无法预知时长，也无法对长调用排序；历史只在收集环境与当前环境一致时有效，且同一负载下的足够历史"很少存在"。
- **信号广泛存在**：应用插桩后，强信号覆盖排行榜 38%、OpenHands 51%、自跑 48% 的工具时间；叠加弱信号后分别达 66%、59%、72%。
- **精度优势**：在 50% 处，进度流中位误差约为调用时长的 1/5，最佳历史预测器为 1/3；在 90% 处，进度流 <10%，最佳历史预测器 80%。
- **时效触发**：2 s 预算下约 1/4 运行能及时触发，0.5 s 预算下约 1/6，远优于基线；插桩脚本（迭代均匀）表现最佳。
- **环境鲁棒**：进度流不依赖历史，跨负载条件保持准确；唯一短板是"负载中途移除"场景（学习到的速率滞后，可用窗口化速率缓解）。
- **端到端收益**：p90 TTFT 相比 LRU 降低 **20.7%（仅 HBM）**、**20.8%（HBM+DRAM）**，接近 Oracle（27.7%/22.6%）；DRAM 重载量仅 6.0 GiB，而基线为 31–78 GiB；吞吐量略升。
- **收益随调用时长增长**：≥2 s 约 1/4，≥10 s 约 1/3（34.2%/35.3%），≥30 s 达 40%。
- **对智能体无代价**：side channel 不显著改变解题数、步数、token、工具时间与墙钟时间；de-suppressed 变体虽更侵入却并不提升信号占比，且改变退出码带来风险。
- **防撒谎可行**：撒谎仅使说谎者占用显存增加 6%，双账本机制回收其中 5%。

## 7. 优点

- **问题定位精准且具普遍性**：将"服务系统如何决定 KV 缓存去留"抽象为"剩余时间估计"问题，并指出这是跨所有现有系统（静态 TTL、elapsed、per-tool 统计、学习模型、引擎占用、声明时长）的共同盲点。
- **证据链完整**：从"长调用主导工具时间"→"调用前估计不可排序"→"环境决定时长"→"工具已持有答案但被沉默"层层递进，附真实 replay 数据。
- **方法设计克制且实用**：坚持"不改变智能体观察"这一铁律；统一事件流抽象清晰；对多阶段调用、超总量撤回、解析失败降级都有工程化处理。
- **首个语料库级普查**：给出强/弱信号、五种类型、四个来源的时间占比，填补了该领域空白。
- **实验客观**：为基线提供最佳历史、给出 Oracle 上界、跨环境与跨模型验证，并诚实报告 de-suppressed 变体的负面结果。
- **安全视角**：将工具报告视为**不可信输入**，设计信用账本，防止租户通过谎报进度放大资源占用，这是同类工作中少见的考量。
- **可扩展路径明确**：指出 MCP progress notification 已存在但缺少服务端消费者，呼吁工具主动暴露自身状态。

## 8. 不足与局限

**覆盖边界（作者自陈）**

- **部分工具调用无信息可读**：仅结束时才响应的远程 API、等待人工反馈的命令、首字节前卡住的下载——这是普查的边界。
- **部分信息无法解析**：未见过的输出格式、隐藏工作单元的构建系统、用自然语言报告的自写脚本，直到有对应解析器前均不可读；三条扩展路径只缩小集合、未闭合。
- **提取信号可能改变工具行为**：verbose 开关、dry run、插桩脚本都是对工具运行方式的改动，虽测得在噪声范围内，但每个新插桩都需重新测量；行为不一致的工具会破坏"智能体观察不变"的不变量。

**实验层面**

- 撒谎防护仅为**初步仿真**，规模有限，未给出完整的对抗性评估。
- Terminal-Bench 与 OTel 语料的时长来自作者沙箱 replay，可能与真实生产分布有偏差。
- 端到端评估基于**重放**（

而非真实生产流量）**，缺少真实多租户、多智能体并发争用下的验证；生产环境中缓存压力、请求到达分布与 SLO 违约代价都可能与实验设定不同。
- **端到端对比的是"预测器"而非"完整系统"**：基线多为已发表的时长估计方法，作者将其接入自己的决策框架，而非与 Continuum、CacheWise 等系统的完整实现（含其各自的缓存管理、调度与工程优化）正面对比，因此"20.7% 的 p90 TTFT 下降"更应理解为**信号质量的收益**，而非系统级胜负。
- **未覆盖异常与边界执行路径**：工具被超时杀死、进程挂起、OOM、被用户中断等情况下，进度语义如何失效、信用如何结算、缓存决策如何回退，文中讨论较少。
- **弱信号的表达能力有限**：弱信号只能说明"接近结束"，无法给出剩余时间量级，因而在 90% 决策点上的贡献天然受限；强/弱信号叠加虽把覆盖率提到 59%–72%，但仍有约三成工具时间落在可观测范围之外。
- **信用机制缺少对抗性分析**：仅给出初步仿真，未建模理性租户的策略性博弈、多租户串谋、信用恢复速率被利用等情形，也未讨论误判（工具因环境异常而"看起来撒谎"）对诚实租户的惩罚成本。
- **硬件与规模维度单一**：仅在单实例 4×H100 SXM 上评估，未涉及多副本路由、集群级缓存调度、跨节点 KV 迁移等现实部署问题。
- **落地成本未被量化**：解析器、wrapper、dry run、插桩与等价性校验都需要按工具族单独开发与维护；论文未给出"每新增一类工具需要多少工程量"以及生态改造成本与收益的边界条件。
- **未报告能耗与成本指标**：DRAM 重载量下降明显，但未换算为能耗、显存占用时间或单位 token 成本，削弱了经济性论证。

## 9. 总体评价与启示

**定位**：这是一篇**问题定义型 + 系统原型型**的工作。其最大价值不在于某个具体机制，而在于把"智能体服务系统如何管理 KV 缓存"重新表述为"剩余时间估计"问题，并证明该问题的答案**不在服务端，而在工具执行环境内部**。

**范式意义**：论文提出的"Ask the Tool, Don't Guess"实质上是在智能体栈中**新增一条契约**——工具不仅返回结果，还应（可选地）返回自身进度；而服务端从"结果消费者"升级为"进度消费者"。这与 MCP 已标准化的 progress notification 形成呼应：标准已存在，缺的是服务端消费者与工程化落地。

**方法论启示**：
- **信号优于模型**：当观测可行时，直接观测往往胜过任何基于历史的推断；历史方法失效的根源是环境不可迁移，而非算法不够强。
- **不变量优先**：坚持"不改变智能体所观察的内容"，使优化对上层完全透明，这是系统改动可被接受的前提。
- **信任边界要前置**：把工具报告视为不可信输入并配套信用账本，是把"性能优化"与"多租户安全"同时纳入设计的范例。
- **降级路径要显式**：解析失败、超总量、多阶段折叠、无信号回退到原行为——这类"不完美信号如何被安全使用"的工程处理，比理想情形下的精度数字更具参考价值。

**适用边界**：该方案最适合**长时间、可观测、自托管或可插桩的工具调用**（测试套件、构建、安装、批处理脚本），对短调用、黑盒远程 API、人工介入类操作收益有限。因此它更像一个**方向性框架**：随着工具生态主动暴露进度，其覆盖率与收益会自然增长，而非依赖服务端更聪明的猜测。

**一句话总结**：论文用充分的实测证据否定了"预测工具时长"的可行性，并给出了一条务实替代路径——让工具在运行中报告进度，由服务端据此管理 KV 缓存；其收益显著（p90 TTFT 降约 20%，接近 Oracle），代价是工具侧的可观测性改造，且这一代价正被现有协议标准逐步摊薄。
