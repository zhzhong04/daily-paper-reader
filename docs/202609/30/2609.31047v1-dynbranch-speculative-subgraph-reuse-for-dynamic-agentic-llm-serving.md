## 摘要
智能体式 LLM 工作流在运行时决定其执行路径。下游计算可能是可预测的，或者此前已经运行过，但在模型或用户解析该分支之前仍无法开始。我们将这种串行化称为分支解析屏障。仅靠缓存无法将其隐藏：用于标识可重用结果的键直到此时才可知。本文提出 DynBranch，使未解析的分支在解析之前就可被寻址。其稳定坐标允许候选子图在解析期间运行，并让已完成的子图结果在后续请求间复用。两级控制器在该工作的预期收益超过负载代价时接纳该工作。DynBranch 位于模型-API 边界，无需更改智能体框架或模型执行引擎。在 4 块 H200 GPU 上使用 Qwen3-32B 的四个智能体式工作负载中，DynBranch 相较于每个工作负载最强的先前系统，将平均延迟最多降低 32%；相较于无重用基线降低 46–66%，同时保持工作流结果不变。该收益在不同骨干模型系列以及消费级 Qwen3-8B/RTX 4090 部署上依然存在。

## Abstract
Agentic LLM workflows decide their execution paths at runtime. Downstream computation may be predictable, or may have run before, yet it cannot begin until the model or the user resolves the branch. We call this serialization the branch-resolution barrier. Caching alone does not hide it: the key that identifies a reusable result is not known until then. In this paper, we propose DynBranch, which makes an unresolved branch addressable before it resolves. Its stable coordinate lets candidate subgraphs run during resolution and completed subgraph results be reused across later requests. A two-level controller admits this work when its expected benefit exceeds the load price. DynBranch sits at the model-API boundary and requires no changes to agent harnesses or model execution engines. Across four agentic workloads with Qwen3-32B on 4x H200 GPUs, DynBranch reduces mean latency by up to 32% over each workload's strongest prior system and by 46-66% against a no-reuse floor, while preserving workflow results. The benefit persists across backbone families and on a commodity Qwen3-8B/RTX 4090 deployment.

## 1. 核心问题与研究背景

- **核心问题：分支解析屏障（branch-resolution barrier）**。智能体式 LLM 工作流在运行时才决定执行路径（由模型解码出下一步工具/子任务，或由用户在候选项中点选），下游计算虽可能可预测、甚至此前已运行过，却必须等待分支解析后才能启动，形成串行化瓶颈。
- **缓存无法直接解决**：识别可复用结果的键（key）在分支解析前并不存在，因此传统响应缓存、前缀 KV 缓存（SGLang、Pythia、PBKV、KVFlow 等）都无法隐藏这段延迟。
- **量化动机**：
  - 在编码、研究、科学类智能体中，**45–57% 的端到端延迟**是串行在模型输出之后的下游时间；任务含 82–318 个模型步；实测 52 个请求中出现 50 条不同路径。
  - 可重叠比例（overlap share）：Routing 0.26、Sub-Agent 0.32、ReAct 0.43，HCI 的后点击执行几乎完全可被思考窗口覆盖（≈1.00）。
  - 复用潜力：ReAct 中 12% 检索、Sub-Agent 中 26% 子任务具有逐字节相同输入；MuSiQue 重复子主题提及从 100 题的 19% 升到 5000 题的 61%；SWE-agent/SWE-rebench 轨迹中 42–45% 命令逐字重复；生产前缀缓存研究报告 54–62% 理想命中。
  - 空闲容量存在但会被挤占：日均约 81% SM 时间空闲、解码期 >50% 算力未用；但共驻 fill 会抬高 canonical 请求延迟（1–3 个 fill 抬升 4–6%，48 个抬升 53%；上下文增大时可达 145%）。
- **三大挑战**：
  - **C1 共享子图复用**：复现单元是请求内部/跨请求的子 DAG，而非整请求或前缀，且必须保持精确匹配与新鲜度。
  - **C2 解析期提前填充**：授权复用的"名字"在解析前不存在，但工作必须在解析前开始，且结果不能泄露给未被选中的分支。
  - **C3 按负载定价的准入**：投机工作与 canonical 请求争夺相同的槽位与 KV，低负载有益、高负载有害，且收益反馈存在数秒级延迟。

## 2. 方法论

### 2.1 核心思想

DynBranch 是位于 **智能体框架与模型服务引擎之间（模型-API 边界）** 的服务层，把"未解析的分支"本身当作服务状态来管理，将**复用（C1）、重叠执行（C2）、执行定价（C3）** 拆成三个独立决策，并统一到一个生命周期中。

### 2.2 关键技术细节

- **分支坐标（branch coordinate）**：工作流模板中决策点的稳定身份（如路由工作流的 router 阶段），在分支解析前即已知，用于在解析窗口内命名并启动候选子图。
- **复用名（reuse name）与新鲜度（C1）**：
  - 复用名 = 子图指纹（代码/模型/执行参数）+ 已实现输入哈希；键的是依赖闭包而非图位置。
  - 记录子图的实现输入、输出、外部读集（read-set）与来源；通过**外部记录到缓存条目的反向索引**维护新鲜度，任一写操作使直接依赖者及失去有效生产者的后代失效；读取与失效同步，不确定情形保守地回退为 miss。
  - 与整请求键、前缀键相比更粗（同精确性/新鲜度下服务 4/6 而非 0/6、2/6 个节点）。
- **影子（shadow）与提升（promotion）（C2）**：
  - fill 完成后作为**不可读的影子**存在，服务路径无法读取；仅当分支选择确定（淘汰失败者、取消其 in-flight fill）**且**出现精确、新鲜、非投机的 canonical 需求时，才原子地提升并消费。
  - **推测-规范等价性**：复用名覆盖指纹、完整渲染输入与参数集，新鲜度守卫保证依赖版本一致，确定性推出 $y_s = y_c$；满足**值等价（value equivalence）** 与**非干扰（non-interference）**，前置条件失败即视为 miss，投机只改变延迟不改变结果。
  - 多阶段 fill 按阶段逐级提升；仅对模板声明"可安全执行两次"的阶段投机。
- **候选来源**：任意预测器（下一阶段模型、检索排序器、小 draft LM 采样 N 次排序）；只用其排序，不校准分数，按 rank 的在线消费率替代。
