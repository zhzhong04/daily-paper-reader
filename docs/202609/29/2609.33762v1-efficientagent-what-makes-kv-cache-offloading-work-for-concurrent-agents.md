## 摘要
LLM 智能体在每一轮都会重新发送完整对话，而其中大部分已在上一轮处理过。服务系统通过缓存其键值（KV）状态来避免重新计算，并在 GPU 内存不足时将该状态卸载到主机内存。对智能体而言，卸载会带来不一致的结果：在相同的编码智能体工作负载上，它加速了一个部署，拖慢了另一个部署，而对第三个部署毫无影响，即使将 token 加载回来的成本比重新计算便宜数倍也是如此。原因在于，缓存状态必须存活到再次被使用。当一个智能体等待其工具时，服务器会处理所有其他智能体的上下文，因此只有当主机层保存了整个智能体池的可复用上下文时，某个智能体的前缀才会被复用，我们将该上下文称为复用工作集。较小的层会不断写入状态，而这些状态在任何人读取之前就被逐出。我们提出 EfficientAgent，它依据该工作集来确定主机层的容量并对其进行管理。一种栈距离模型根据智能体历史估计工作集，以确定主机层容量；其实验前做出的预测定位了卸载开始划算的容量点。当该层太小时，运行时策略会停止写入被逐出上下文的大规模回填，并继续扩展仍被缓存的前缀；当该层足够大时，则写入所有内容。在 SWE-bench Verified 编码智能体上，按估计工作集设置容量的主机层将重新计算的提示 token 减少了 93%，端到端时间减少了 39%。在较小的固定层下，该策略将重新计算减少了 35%；在较大的层下，它避免了因始终过滤写入而造成的 4.3 倍增加。在三种 GPU 类型和两个模型上，当 GPU 相对于每字节主机带宽的计算能力较低且主机层能容纳工作集时，卸载才会带来收益。代码见 https://github.com/KunmingSHAO/efficientagent_release。

## Abstract
LLM agents resend their whole conversation on every turn, and most of it was already processed on the previous turn. Serving systems avoid recomputing it by caching its key-value (KV) state and, when GPU memory runs out, by offloading that state to host memory. For agents, offloading gives inconsistent results: on the same coding-agent workload it speeds up one deployment, slows down another, and changes nothing on a third, even where loading a token back is several times cheaper than recomputing it. The reason is that cached state must survive until it is used again. While one agent waits for its tool, the server processes the contexts of all other agents, so an agent's prefix is reused only if the host tier holds the reusable context of the whole agent pool, which we call the reuse working set. A smaller tier keeps writing state that is evicted before anyone reads it. We present EfficientAgent, which sizes and manages the host tier by this working set. A stack-distance model estimates the working set from agent histories to size the host tier; its predictions, made before the experiments, located the capacity at which offloading starts to pay. When the tier is too small, a runtime policy stops writing large refills of evicted context and keeps extending prefixes that are still cached; when the tier is large enough, it writes everything. On SWE-bench Verified coding agents, a host tier sized to the estimated working set cuts recomputed prompt tokens by 93% and end-to-end time by 39%. With a small fixed tier, the policy cuts recomputation by 35%; with a large tier, it avoids the 4.3-fold increase caused by always filtering writes. Across three GPU types and two models, offloading pays off when the GPU has little compute per byte of host bandwidth and the host tier holds the working set. Code is available at https://github.com/KunmingSHAO/efficientagent_release.

# EfficientAgent 论文中文总结

## 1. 核心问题与整体含义

- **研究背景**：LLM 智能体（尤其是编码智能体）以闭环方式工作——模型读任务、调工具、读结果、再调模型。每次调用都会重新发送完整对话，而在 SWE-bench Verified 轨迹中，**98.1% 的提示 token 已在同一任务的前一次调用中处理过**。前缀缓存（复用已处理 token 的 KV 状态）可使编码智能体运行加速最高 **11.1 倍**。
- **核心矛盾**：当 GPU 显存不足时，KV 卸载到主机内存（host tier）本应总是有益的，但实测结果不一致——同一编码工作负载下，卸载在 RTX 3090 上加速、在 H800 上拖慢、在 H20 上无变化，即使 H20 上回载一个 token 比重新计算便宜 6 倍以上。
- **根本原因**：缓存状态必须**存活到再次被使用**。当一个智能体等待工具执行时，服务器会处理其他所有智能体的上下文，从而把较早的状态挤出缓存。作者提出**复用工作集（reuse working set）**概念：主机层必须能容纳整个智能体池的可复用上下文，前缀才可能被复用。较小的层会不断写入在被读取前就被逐出的状态。
- **整体含义**：卸载是否有收益取决于两个因素——**硬件**决定一次主机命中省多少（由每字节主机带宽对应的峰值算力决定），**工作集**决定是否命中。这为 KV 分层与调度提供了新的第一性输入量。

## 2. 方法论

### 核心思想
用**栈距离模型**从智能体历史估计复用工作集，据此配置主机层容量，并在运行时通过**容量条件写入准入（capacity-conditioned write admission）**决定哪些新 KV 写入主机层。

### 关键技术细节

- **KV 占用与硬件平衡**：每 rank 每 token 的 KV 字节数
  β_rank = 2·L·d·s·max(1, ⌈H_kv/TP⌉)
  例如 Qwen3-Coder-30B-A3B 在 TP8 下为 24 KiB/token/rank。

- **卸载收益比（OBR）**：衡量恢复缺失前缀相对重新计算的节省比例
  OBR(n) = 1 − T_load(n)/T_rec(n)
  H20 上长前缀 OBR ≥ 0.84；H800 因峰值算力/主机带宽比高 6.7–7.0 倍，OBR 显著下降。

- **栈距离存活条件**：在 LRU 引用模型下，已存 chunk 存活当且仅当
  D(k) < ⌊C / (b·β_rank)⌋
  其中 D(k) 为两次引用之间的不同 chunk 数（复用距离），C 为主机容量，b 为 chunk 大小。前缀恢复还要求从起点开始的**连续 chunk 覆盖**，并需减去 GPU 已驻留部分。

- **工作集尺度**：在积压池中
  b_Creuse ≈ (A − 1)·N̄·β_rank
  A 为活跃池大小，N̄ 为平均提示长度。两个压力比：γ_G = A·N̄/K_G（池上下文/GPU 容量），γ_H = b_Creuse/C_H（工作集/主机容量）。γ_H > 1 意味着主机层无法容纳复用工作集。

- **容量条件写入准入**：运行时估计 A 与 N̄，结合主机层"满且正在逐出"的反馈信号：
  pt = 1[b_Creuse > C_H] ∧ 1[tier full and evicting]
  save(r) = ¬pt ∧ (u > κ)
  即仅在压力下拒绝大规模回填（u 为新满 chunk 数，κ=8），压力消失则恢复全写。该规则为每请求常数时间开销。

- **命题 1（LRU 拒绝写入的安全性）**：若 LRU 层仅在复用距离 D ≥ K_H（或不再引用）的缺失处拒绝插入，则全准入下的所有命中仍会命中，且总命中不减少。这为缓存绕过/死块预测提供了 KV 前缀连续覆盖场景下的形式化依据。

## 3. 实验设计

- **数据集/场景**：SWE-bench Verified 真实 GitHub issue 编码任务；使用 OpenHands v0.56.0 + CodeActAgent。
- **模型**：Qwen3-Coder-30B-A3B-Instruct（MoE，BF16）与 Qwen2.5-Coder-32B-Instruct（稠密，BF16）。
- **服务栈**：vLLM 0.13.0 + 前缀缓存 + LMCache 0.3.12，chunk 大小 1,024 token。
- **回放方法**：**依赖保持回放（dependency-preserving replay）**——固定每次调用的提示 token ID 并约束解码复现记录的输出 token，同时保留记录的智能体/工具间隔时间，使不同策略在完全相同的工作量上可比。共 4,427 次模型调用、147.1M 提示 token。
- **对比方法**：
  - Recompute（仅 GPU 前缀缓存，基线）
  - Offload（LMCache 主机层，无写入准入）
  - Fixed write admission（对每个请求都过滤写入 + 去重）
  - Conditioned admission（容量条件准入）
- **变量扫描**：主机容量 3/4.5/5/10/20/40/80 GiB per rank；活跃池 A=8 vs A=16；GPU 显存分数 0.65–0.95；上下文折叠器对比。

## 6. 主要结论与发现

- **容量决定收益**：主机层从 5→20 GiB/rank，计算 prefill 从 76.7M 降到 5.3M token（**减少 93.1%**），makespan 从 209 降到 128 分钟（**降低 38.7%**）；5 GiB 层使 makespan 与重算持平（212 分钟）。转换点恰在 γ_H 跨越 1 处。
- **写入准入随容量反转**：5 GiB 下 fixed admission 减少重算 36%、makespan 10.8%；40 GiB 下反而使计算 prefill 增加 **4.3 倍**、makespan 增加 30.6%。容量条件准入在两侧均保持增益（5 GiB 减 35%，40 GiB 恢复 4.3 倍损失）。
- **栈距离预测定位转换点**：模型预测 20 GiB 时 prefill 5.19–5.78M，实测 5.28M；80 GiB 预测 5.19–5.31M，实测 5.29M。
- **并发改变工作集**：A 从 16 减到 8，工作集尺度从 11.4 降到 5.3 GiB，转换点随之左移；3 GiB 层即可减重算 65%。
- **硬件比例决定卸载是否有益**：低比例 GPU（RTX 3090 2.2K、H20 2.3K FLOP/byte）在命中存活时卸载获益（0.91、0.60）；H800（15.5K FLOP/byte）上所有卸载运行均变慢（1.08–1.87）。
- **makespan 跟随计算 prefill**：17 次运行中无论由何种干预产生，makespan 与计算 prefill 强相关。
- **上下文折叠的反直觉**：缩短输入 token 可能增加新 prefill——早期改写会重新哈希其后所有 chunk 的 key，prefix-hit 率从 96.5% 降到 50.8–60.9%。

## 7. 优点

- **问题洞察深刻**：将"主机命中价值"与"命中是否存在"两个因素清晰分离，指出并发智能体场景下工作集是决定性的新变量。
- **理论严谨**：基于 Denning 工作集模型与 Mattson 栈距离理论，并将其扩展到队列拉伸的复用距离、连续前缀覆盖与 GPU 驻留相减等新量；命题 1 给出了拒绝写入不损失命中的形式化保证。
- **预测先于实验**：栈距离模型在 10/20/80 GiB 运行之前给出预测，且预测与实际高度吻合，方法论可信度高。
- **实验设计公平**：依赖保持回放固定 token 工作量，策略差异仅来自服务决策；报告独立重复与完整测量表。
- **工程可用性强**：写入准入是每请求常数时间检查，参数预先固定；提供部署指南（Table 12）与开源代码。

## 8. 不足与局限

- **工作负载覆盖有限**：仅在 SWE-bench Verified 编码智能体上验证，其他类型智能体（如网页、多模态、长文档）与工具调用模式未评估。
- **工作集估计依赖假设**：Equation 5 假设积压池、上下文长度相近、弱共享前缀；对高度异构或强共享前缀的池，估计可能不准。
- **硬件覆盖偏向性**：H800 上卸载一律变慢的结论基于有限配置，但作者已将其归因于 FLOP/byte 比例并给出部署指南。
- **能耗未测量**：论文明确说明报告运行时与计算量而非能耗，因此能效层面的结论缺失。
- **上下文折叠实验规模较小**：仅在 8×RTX 3090 单一部署上比较三种冷凝器，缺乏跨硬件验证。
- **应用限制**：当 GPU 峰值算力/主机带宽比高（如 H800）时，卸载策略基本不适用；收益依赖主机内存预算充足到覆盖工作集。
