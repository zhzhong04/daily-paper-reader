## 摘要
共享主机内存缓存可以避免请求在推理副本之间迁移时重复进行预填充。其有用性取决于正确的状态传输和丢失的前缀局部性。我们研究了两个单GPU的27B vLLM副本共享一个256 GiB的LMCache池。在采用现有的打包页补丁后，我们隔离出一个原始指针回退，该回退省略了对当前CUDA流的依赖。受控字节测试在施加延迟时失败，并在恢复依赖后通过；现有的混合分配器提供了一条可用的部署路径。全池分配检查和服务回归完成了验证。四块OFF-ON-ON-OFF比较包含两个块对内的768个已测量请求。跨副本的首个内容token中位时间在128k输入下从31.715秒降至0.605秒，在256k输入下从92.047秒降至0.790秒。在初始上下文为32k和128k时，交替副本的六轮合成会话分别提升约35%和45%，而固定放置几乎没有收益。这个工程案例研究确定了实际验证步骤以及共享缓存能够带来收益的局部性条件。

## Abstract
Shared host-memory caching can avoid repeated prefill when a request moves between inference replicas. Its usefulness depends on both correct state transfer and lost prefix locality. We study two single-GPU 27B vLLM replicas sharing a 256 GiB LMCache pool. After adopting an existing packed-page patch, we isolate a raw-pointer fallback that omits the dependency on the current CUDA stream. Controlled byte tests fail under an imposed delay and pass when the dependency is restored; the existing mixed allocator provides a working deployment path. Full-pool allocation checks and service regression complete the validation. A four-block OFF-ON-ON-OFF comparison contains 768 measured requests within two block pairs. Median cross-replica time to first content token falls from 31.715 to 0.605 seconds at 128k input and from 92.047 to 0.790 seconds at 256k. Six-turn synthetic sessions alternating replicas improve by approximately 35% and 45% at initial contexts of 32k and 128k, while fixed placement shows little benefit. This engineering case study identifies practical validation steps and the locality conditions in which shared caching pays off.

## 一、论文的核心问题与整体含义

- **背景与动机**：多轮推理请求通常携带大量在先前轮次已处理过的上下文。当请求落在原副本时，可复用本地前缀状态（prefix state）；但一旦被调度到另一副本，就需要重新预填充（prefill）该前缀，造成显著的重复计算。
- **部署抉择**：由此产生三种工程选择——通过放置（placement）保持请求局部性、提供共享状态复用路径，或将两者结合。LMCache 提供了跨请求、跨推理引擎搬运与复用 KV 缓存（含混合解码状态）的机制。
- **两个核心关切**：
  - **正确性陷阱**：缓存可能"看起来在正常工作"却返回错误状态——HTTP 200 或命中计数器并不能作为完整性校验。
  - **基线陷阱**：令人印象深刻的"冷启动 vs 热缓存"对比可能掩盖了一个竞争性替代方案——把会话保留在原始 GPU 上（本地命中）。
- **整体含义**：论文是一篇工程案例研究，主张"先建立正确性、再测量性能，并保留本地命中基线"，最终给出共享缓存在复制式服务中真正划算的局部性条件。

## 二、方法论

### 核心思想
- 在两个单 GPU 的 27B vLLM 副本 + 一个共享 256 GiB 主机内存 LMCache 池的固定部署上，先诊断并修复状态传输路径的正确性缺陷，再做分离了"冷计算 / 本地复用 / 跨副本复用"的配对性能测量。
- 关键原则：**表示（representation）、拷贝顺序（ordering）、全量分配（full-size allocation）三类验证分层进行，最后才做服务级回归**。

### 系统配置
- 拓扑：外部网关 + 两个完整 vLLM 副本（各占一张 GPU，均执行 prefill 与 decode），二者连接同一个主机内存 LMCache 服务；各自保留独立的 GPU 前缀缓存。**不是** prefill/decode 分离，网关也不是 KV 数据存储层。
- 硬件：2× NVIDIA RTX PRO 6000 Blackwell Server Edition（每卡 97,887 MiB）、2× AMD EPYC 9455 48 核（192 逻辑 CPU、8 个 NUMA 节点）、驱动 610.57.04。
- 模型：Qwen3.8-27B-NVFP4；64 层 = 48 层 Gated DeltaNet + 16 层全注意力；hidden 5,120；全注意力 head dim 256、4 个 KV head。权重为压缩张量导出：FP8 大注意力/GDN 投影 + 层 0–62 的 NVFP4 MLP（无输入激活量化），末层 MLP 与 lm_head 保持 BF16。作者特别提醒"NVFP4"不等于全模型统一的 W4A4。
- 运行时：vLLM 0.28.0、LMCache 0.5.4、PyTorch 2.13.0+cu129；TP=1、FP8 KV、HND 布局、Mamba 对齐、开启前缀缓存；调度限制 8,192 batched tokens、64 序列、最大长度 1,010,000；每副本报告 1,262 块 / 1,957,941 可缓存 token。
- 共享层（仅 ON 臂）：256 GiB RAM、1,568-token 分块、四个 kernel group 归并为两个 object group、LRU；原生 RAM offload 在两侧均禁用。

### 关键技术细节与修复

- **混合状态的语义**：此处"KV 缓存"包含可在公共前缀边界恢复的混合解码状态——全注意力贡献前序 K/V 页，Gated DeltaNet 贡献卷积与循环状态的边界快照；vLLM 通过 Mamba cache 接口管理。补丁把整个循环页（含卷积状态、循环状态、padding）视为不透明可寻址字节，其"注意力形状视图"不意味着逐 token K/V 或 INT8 量化。在 `align` 恢复语义下，必须同时命中所需注意力前缀块与对应循环快照，单命中注意力 kernel group 不足以恢复完整混合状态。

- **故障一：打包页表示不兼容**
  - 首次跨副本响应在 HTTP 200、25,088 个外部命中 token 的情况下返回乱码。
  - 原因：一个逻辑全注意力块由多个打包 kernel 页组成；原处理识别 rank-5 注意力张量却遗漏了 rank-4 打包表示，导致传输字节视图错误。
  - 采用上游 packed-subpage 补丁（commit `f180b9ff...`）。在 27B 案例中，1,568-token 逻辑块跨越 49 个 32-token 页。
  - HND 是所评估的未修改补丁与 vLLM/FlashInfer 组合的**配置特定要求**（NHD 启动因 kernel 页数可整除性错误失败），并非 LMCache 的通用要求。

- **故障二：可复现的流顺序缺陷**
  - 表示修复后，128k 服务仍失败：相同输入在 A 上冷/本地复用得到 `alpha=938639`，B 外部命中 127,008 token 却返回 `938624`；新 cache salt 强制零命中冷计算后又恢复正确。
  - 机制：评估镜像缺少 LMCache CUDA-ops 扩展，走 PyTorch 回退路径；其裸指针 `lmcache_memcpy_async` 分支调用 `cudaMemcpy(..., cudaMemcpyDefault)` 时**未传入当前流参数**（`cudaMemcpyDefault` 是拷贝类型枚举而非函数名）。PyTorch 流池使用 `cudaStreamNonBlocking`，因此承载 gather/scatter 依赖的非默认流被排除在 legacy 默认流的隐式同步之外；拷贝在主机侧返回并不建立缺失的生产者/消费者依赖。
  - 探针证据：1 MiB D2H 探针先调度延迟写入字节 37，主机收到旧值 0；H2D 探针先读旧值 0，再经回退写入 53，消费者读到 53；每次报告 1,048,576 个不匹配字节——这是受控整数字节失败，与浮点或采样差异无关。
  - 统计：延迟条件下裸回退 120/120 失败，无延迟 120/120 通过；三种恢复顺序的控制（等待前序流工作、在当前流上用 `cudaMemcpyAsync`、同流张量拷贝）720/720 通过。
  - 修复路径：显式设置 `--no-l1-use-lazy` 选用现有 mixed allocator 及其张量拷贝路径（仅移除 lazy 正标志不够，因 CLI 默认即 lazy）。单对象探针中 lazy 在 GPU 0 上 10/10 失败，mixed 在 GPU 0 与 GPU 1 上各 10/10 通过。

- **故障三：全池 pinned 分配**
  - 小规模 mixed 探针可 pin 内存，但首次 256 GiB 服务分配回退到可分页内存。分配器请求 256 GiB + 4096 字节对齐，PyTorch 主机分配器的 2 的幂次舍入可能将其放大到 512 GiB。
