## 摘要
GPU 高带宽内存稀缺且昂贵，随着聊天、智能体循环和文档问答不断累积状态，KV 缓存会消耗其中很大一部分。Mooncake、LMCache、FlexGen、InfiniGen 和 AttentionStore 等系统利用 CPU DRAM 和 SSD 扩展 GPU 内存。更难的问题是：哪些块应属于哪一层级，何时移动或逐出它们，以及预取是否有帮助。我们在一个涵盖 GPU HBM、CPU DRAM 和 SSD 的离散事件模拟器中研究这些选择，并以随机森林执行时间预测器进行校准。我们在聊天、智能体和文档问答工作负载上比较了最近性、复用频率、预测复用以及带预取前瞻的 EWMA 预测器。分层存储使每 GPU 支持的并发会话数达到原来的 73.02 倍，并将每会话成本降至原来的 1/62.04。这些收益来自 1+8+64 的分层容量，而非放置策略。在我们的设置中，批大小为 1 时解码受计算限制，因此放置策略几乎不影响吞吐量。它主要改变 PCIe 迁移流量和首 token 时间。对于聊天，最近性产生的迁移流量仅为复用频率的 1/2.30。复用频率在智能体和文档问答中表现最佳。现有的预测复用策略与最近性逐字节相同，因此其针对智能体的推荐实际上就是最近性。真正的 EWMA 预测器会改变行为，但在预期预测能够帮助的工作负载上仍排名落后于复用频率。预取的收益不足以抵消其带宽成本。在策略和缓存大小的网格上，即使拥有未来请求知识的 oracle，在迁移流量方面也从未优于不预取。针对特定工作负载的放置可以减少数据移动，但按当前实现，预测复用和预取的建议并未得到支持。

## Abstract
GPU high bandwidth memory is scarce and expensive, and KV caches consume much of it as chats, agent loops, and document question answering accumulate state. Systems such as Mooncake, LMCache, FlexGen, InfiniGen, and AttentionStore extend GPU memory with CPU DRAM and SSD. The harder question is which blocks belong in each tier, when to move or evict them, and whether prefetching helps. We study these choices in a discrete event simulator spanning GPU HBM, CPU DRAM, and SSD, calibrated against a random forest execution time predictor. We compare recency, reuse frequency, predicted reuse, and an EWMA predictor with prefetch lookahead across chat, agent, and document question answering workloads. Tiering supports 73.02 times more concurrent sessions per GPU and lowers cost per session by 62.04 times. These gains come from tier capacities of 1 plus 8 plus 64, not placement policy. Decode is compute bound at batch size one in our setup, so placement barely affects throughput. It mainly changes PCIe migration traffic and time to first token. Recency produces 2.30 times less migration traffic than reuse frequency for chat. Reuse frequency performs best for agents and document question answering. The existing predicted reuse policy is byte identical to recency, making its agent recommendation effectively recency. A genuine EWMA predictor changes behavior but still ranks behind reuse frequency on the workloads prediction was expected to help. Prefetching does not justify its bandwidth cost. Across the policy and cache size grid, even an oracle with knowledge of future requests never beats no prefetch on migration traffic. Workload specific placement can reduce data movement, but the predicted reuse and prefetch recommendations are not supported as implemented.

# 论文总结：Where Should the KV Cache Live? Placement Policies Across GPU, CPU, and SSD for Long-Lived Sessions

## 1. 核心问题与整体含义

- **背景**：GPU HBM 是 LLM 服务中最稀缺、最昂贵的资源，而 KV cache 是其最大消费者。长对话、Agent 循环、重复文档问答等长期会话会不断累积 KV 状态，远超单卡 HBM 容量。
- **已有思路**：将 KV cache 分层扩展到 CPU DRAM 和 SSD，在会话恢复时取回，从而把 prefill 重算转化为缓存查找。Mooncake、LMCache、FlexGen、InfiniGen、AttentionStore 等已解决“机制”问题。
- **核心问题**：真正的难点是“策略”，即哪些 KV block 应放在哪一层、何时提升、降级、逐出和预取，以及最优策略如何随 workload 的复用结构变化。
- **整体含义**：论文将放置策略本身作为研究对象，构建可配置的三级缓存模拟器，系统比较 recency、复用频率、预测复用、EWMA 预测器及预取，并给出按 workload 区分的策略指南。结论强调：分层带来的容量与成本收益巨大，但主要来自容量倍数而非放置策略；放置策略主要影响 PCIe 迁移流量和 TTFT，而非 batch=1 下的吞吐。

## 2. 方法论

- **核心思想**：把 KV cache 视为固定大小 block 的集合，每个 block 驻留在 GPU HBM、CPU DRAM 或 SSD 三级之一；通过放置策略决定 block 的层级、提升、降级、逐出与预取。
- **系统建模**：
  - 三级容量满足 `c_g ≪ c_d ≪ c_s`，带宽满足 `b_g ≫ b_d ≫ b_s`。
  - 每个 token 的 decode 需要该层所有必需 block 位于 HBM；若不在 HBM，则必须沿层级向上取回，否则造成 decode stall。
  - 使用离散事件模拟器，并以随机森林执行时间预测器进行校准。
- **放置与逐出算法流程**：
  1. 对每个 block 维护一个策略分数 `s(b)`。
  2. 若 block 在 HBM，直接命中使用。
  3. 若不在 HBM，则从下层取回并提升到 HBM。
  4. 若 HBM 满，则把最低分 block 降级到 DRAM，必要时级联到 SSD。
  5. 根据预测的即将访问 block 执行预取。
  6. 更新 `s(b)`，记录命中层级和 decode stall。
- **策略族**：
  - **Recency / LRU 式分层**：保留最近使用的 block 在高层级。
  - **Reuse frequency**：保留被频繁复用的 block，偏向共享前缀。
  - **Predicted reuse**：廉价预测下一轮会访问哪些 block，类似 InfiniGen 思路。
  - **Predictive / EWMA**：论文额外加入的真正预测器，基于 EWMA 下一触达估计，证明其行为与 recency 不同。
- **预取机制**：使用 lookahead window 提前把未来 decode 步骤或恢复会话所需的 block 移到 HBM，以重叠传输和计算；论文扫描 lookahead 深度，并在“带宽计费”模型下让推测性取数与需求取数竞争同一链路。
- **成本模型**：有效容量为 `c_g + c_d + c_s`，混合成本由廉价层级主导；同时报告容量收益、成本收益与实测 stall，避免把内存节省误认为免费午餐。

## 6. 主要结论与发现

- **分层收益巨大，但来自容量而非策略**：
  - Tiering 使每 GPU 并发长期会话数提升 **73.02×**，每会话成本降低 **62.04×**。
  - 该倍数几乎等于 tier shape 的容量倍数 `1+8+64=73`，与 workload 复用结构基本无关。
- **Batch=1 下 decode 计算受限**：
  - 放置策略几乎不影响吞吐，chat 在不同策略下均为约 **1307.60 tok/s**。
  - 策略真正控制的是 **PCIe migration traffic** 和 **TTFT**。
- **策略胜负按 workload 分化**：
  - Chat：recency 最优，迁移流量 **27.38 GB**，比 reuse-frequency 的 **62.99 GB** 少 **2.30×**，TTFT 也更优。
  - Agent：reuse-frequency 最优，**49.36 GB**，比 recency 少 **1.60×**。
  - Document QA：reuse-frequency 最优，**48.23 GB**，比 recency 少 **1.63×**。
- **Predicted-reuse 建议不成立**：
  - 原 shipped predicted-reuse 策略与 recency **逐字节相同**，因此“agent loop 用 predicted-reuse”实际上就是 recency。
  - 新增的 genuine EWMA predictor 确实不同于 recency，但在 agent 和 document QA 上仍排第二：
    - Agent：53.16 GB vs reuse-frequency 49.36 GB。
    - Document QA：48.45 GB vs 48.23 GB，接近平局。
    - Chat：57.76 GB，明显落后。
  - 预测器仅在某个中间 cache size 的 agent 上取得第一，价值局限于窄容量窗口。
- **预取不抵带宽成本**：
  - 在带宽计费模型下，因果预测器在全部网格中都没有捕获到 oracle 的正收益份额。
  - 即使未来读取 oracle，在超过一半的单元格中也比不预取更慢。
  - 原因：竞争链路上，推测性取数会延迟正在等待的需求取数，移除的 stall 小于造成的延迟。
- **命中层级分布**：
  - DRAM 是主力层：chat 从 HBM 服务 **23.99%**、DRAM **61.87%**，SSD 为 **0.00%**。
  - Agent 从 DRAM 服务 **72.65%**；document QA **68.48%**。
  - SSD 更多是浅层后备，document QA 命中 **8.80%**，agent **6.07%**。
  - 需要重算的残余 miss 约 **13.62%–14.15%**。
- **延迟结构**：
  - 每 token 计算约 **13.2445 ms**，fetch stall 在 TPOT 中占比 **<1%**。
  - 分层取数在该规模下基本被计算隐藏，因此 TPOT 不是区分策略的好指标。
- **成本-延迟前沿近乎垂直**：
  - 固定预算 `T=192` blocks 下，成本跨度 **8.38×**，从约 **$45,493** 到 **$381,287 / 1k sessions**。
  - P99 TTFT 最多只移动其自身上限的 **10.1%**，多数组低于 1%。
  - 最便宜组成 HBM/DRAM/SSD 为 **10/86/96**，在全部 12 组中都是最便宜点，延迟代价几乎可忽略。
- **紧 HBM 下 SSD 深度**：
  - 固定 HBM=32、DRAM=64，SSD 加深可使 sessions/GPU 最大提升 **10.77×**，且各 workload 相同。
  - Chat 和 agent 在扫描范围内**从未满足** SLO。
  - Document QA 在 SSD 深度 **64** 首次满足 SLO，最深点 headroom 为 **0.000 ms**，仍支付平均 **4.42 ms** stall。

## 7. 优点

- **问题定位清晰**：明确区分“机制”与“策略”，把容量收益和策略收益分开，避免混淆。
- **负面结果诚实且系统**：没有强行支持原路线图，明确指出 predicted-reuse 与 recency 相同、prefetch 不划算。
- **代码级验证**：对“predicted-reuse ≡ recency”和“成本是组成纯函数”等关键结论做了代码验证，而非假设。
- **使用 oracle 上界**：预取实验引入未来读取 oracle，即使 oracle 也常不占优，增强了“预取不抵带宽”的结论。
- **协议透明**：主动披露单会话下策略不可区分，改用并发会话，并保留单会话结果。
- **覆盖成本-延迟前沿**：E11 和 E10 从部署角度给出 SSD-heavy 建议，并量化成本与 TTFT 的权衡。
- **指标选择合理**：在 batch=1 计算受限时，不只看吞吐，而看 migration traffic 和 TTFT，抓住了策略真正控制量。

## 8. 不足与局限

- **合成 workload 偏差**：策略比较基于合成生成器，其复用结构按构造有利于匹配策略；真实对话 trace 复用更低，策略差异会压缩，合成分离是上界。
- **Batch=1 与单 GPU 限制**：decode 计算受限，fetch stall <1% TPOT；更大 batch 或更快 decode kernel 下，stall 占比和放置/预取价值会上升，结论可能不通用。
- **未报告真实算力与硬件**：没有 GPU 型号、数量、训练/推理时长，实验可复现性和部署外推受限。
- **成本模型依赖假设价格**：HBM/DRAM/SSD 的 $187.50 / $3.50 / $0.08 per GB 来自 `cost_model.py` 默认值，非市场报价；成本-延迟前沿形状依赖价格比例。
- **stall 归因近似**：DRAM 与 SSD 的 decode stall 按命中率分摊，而非直接记录某层导致的 stalled 毫秒。
- **未与真实系统端到端对比**：没有与 Mooncake、LMCache、FlexGen、InfiniGen、AttentionStore 等真实实现做端到端 benchmark，模拟器结论需真实系统验证。
- **预取模型较强假设**：推测性取数与需求取数竞争同一链路，导致预取几乎总不划算；在有空闲带宽的系统中预取可能有益，论文也承认这一点。
- **预测器仍未解决**：EWMA 预测器只在窄容量窗口获胜，广泛有效的 predictor 仍是开放问题。
- **固定量化与逐出**：放置与 KV quantization、eviction 正交，但论文将其固定，未研究组合效应。
- **应用限制**：结论适用于 batch=1、长生命周期会话、三级存储场景；对高并发、低延迟 SLO 严格或带宽充裕的系统，策略选择可能不同。
