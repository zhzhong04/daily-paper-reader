## 摘要
与先前智能体服务系统针对的秒级工具调用暂停不同，智能体LLM请求在等待人工审批时可能被挂起数分钟甚至数小时。我们研究了挂起与恢复对GPU服务性能的影响，并制定了一种保留策略，在不确定的审批等待下平衡主动服务容量与未来重新计算的开销。核心矛盾十分严重，因为保留挂起的KV可以保持快速恢复，但可能消耗足够的GPU容量，使主动服务的有效吞吐降低41%；而驱逐KV则避免该驻留成本，但当请求返回时，恢复延迟会高出近10倍。我们围绕GPU机会成本开发了一个分级保留控制器，用统一的GPU时间成本来表示保存或重建挂起请求的KV状态所消耗的服务容量。在主机内存内，该控制器通过校准等待样本，在无限期保留和负载索引过期之间进行选择，无需对每个请求进行等待预测。在人工规模审批工作负载上，我们的控制器将主动请求的有效吞吐比vLLM基线提高23-51%，比MORI提高22-29%，比Continuum提高41-52%。

## Abstract
Unlike the seconds-scale tool-call pauses targeted by prior agent-serving systems, agentic LLM requests can be suspended for minutes or hours while waiting for human approval. We study how suspension and resumption affect GPU serving performance and develop a retention policy that balances active-serving capacity against future recomputation under uncertain approval waits. The central tension is severe because retaining suspended KV preserves fast resume but can consume enough GPU capacity to reduce active-serving goodput by 41%, while evicting it avoids that residency cost at the expense of nearly $10\times$ higher resume latency when the request returns. We develop a tiered retention controller around GPU opportunity cost, which expresses the serving capacity consumed by preserving or reconstructing a suspended request's KV state in a common GPU-time cost. Within host memory, the controller selects between indefinite retention and load-indexed expiration using calibration wait samples, without requiring per-request wait prediction. On human-scale approval workloads, our controller improves active-request goodput by 23-51% over the vLLM baselines, 22-29% over MORI, and 41-52% over Continuum.

## 1. 论文的核心问题与整体含义

- 论文聚焦 **LLM 智能体（agentic LLM）在等待人工审批（human approval）期间被挂起（suspend）的服务管理问题**。以往系统主要针对秒级 tool-call 暂停，但人工审批往往持续数分钟到数小时。
- 挂起请求虽然不产生 token，但其 **KV cache 仍占用资源**，形成关键矛盾：
  - 保留 KV：恢复快（66–75 ms），但会占用 GPU HBM/主机 DRAM，挤占活动请求的服务容量，在实验中造成 **41% 的 active-request goodput 下降**。
  - 驱逐 KV：释放容量，但恢复时需要重新计算，**resume TTFT 从 66–75 ms 升至 687–705 ms，约 10 倍**。
- 论文的核心目标是在“保留”与“释放”之间建立统一的、可量化的代价模型，并**在不预测单个请求等待时长的前提下**，自适应选择最优的 KV 保留策略，以平衡“服务容量”与“恢复延迟”。

## 2. 方法论

### 核心思想
- 提出用 **GPU opportunity cost（GPU 机会成本）** 统一衡量“保存”或“重建”挂起请求 KV 状态所消耗的 GPU 服务容量，计量单位为 GPU 时间。
- 不依赖逐请求的等待时长预测，而是：
  1. 校准平台相关的代价参数；
  2. 根据校准等待样本选择“无限期保留”或“负载索引过期”策略；
  3. 在实际服务中按固定策略执行。

### 保留状态的三层选择
- 状态 `j = 1/2/3` 分别表示：
  1. GPU HBM 保留；
  2. 主机 DRAM（host DRAM）保留；
  3. 丢弃并重算（recompute）。
- 成本模型为：
  \[
  C_j(\ell) = \alpha_j \ell + \beta_j
  \]
  - `α_j`：单位时间持有成本；
  - `β_j`：一次性恢复/重算成本。
- HBM 保留：`β1 = 0`；主机恢复有一次性成本 `β2`；丢弃则有重算成本 `β3`。

### 关键阈值与公式
- 未拥塞时：
  - HBM 与 DRAM 切换的盈亏平衡点：
    \[
    t_1 = \beta_2 / \alpha_1
    \]
  - HBM 与“丢弃+重算”的盈亏平衡点：
    \[
    t^* = \beta_3 / \alpha_1
    \]
- 主机内存拥塞时，通过 Little 定律和负载水平计算主机占用成本：
  - `C2`：主机 DRAM 能容纳的挂起上下文数量；
  - `Wref`：参考等待时长；
  - 饱和到达率：
    \[
    \lambda_{crit} = C_2 / W_{ref}
    \]
  - 负载相关的主机持有价格：
    \[
    \alpha_2(\lambda) = \max(0, \lambda - \lambda_{crit}) \cdot \beta_3 / C_2
    \]
  - 主机 DRAM 丢弃阈值：
    \[
    t_2(\lambda) =
    \begin{cases}
    \infty & \lambda \le \lambda_{crit} \\
    (\beta_3 - \beta_2)/\alpha_2(\lambda) & \lambda > \lambda_{crit}
    \end{cases}
    \]

### 控制器流程
- 请求挂起后，KV 先迁移到主机 DRAM（因为 `t1≈1s` 很短，在挂起时刻就应 offload）。
- 用独立校准样本在两种主机策略间“冻结”选择：
  1. `host-retain`（无限期保留）；
  2. `cpu_ttl(λ)`（超过 `t2(λ)` 后过期丢弃）。
- 实际服务时只需输入负载 `λ`，无需预测单个请求的等待时长。
- 平台校准仅需三个参数：`α1`、`β2`、`β3`。上述参数在不同硬件上变化显著，因此需要按平台重新测量。

## 3. 实验设计

### 数据与场景
- 使用 **τ²-bench** 的多轮工具使用智能体轨迹（retail 和 airline 场景）。
- 截取在首个“写操作”之前的轨迹作为 **approval-gated prefixes**，共 **2161 条**。
- 中位挂起上下文约为 8.4K tokens，其中约 3.0K 为私有 suffix（需要保存的状态），共享前缀可复用。
- 等待时长采用三种“人工尺度”分布，均值均为 1800 秒（30 分钟）：
  1. lognormal（σ=1）；
  2. exponential；
  3. mixture：短等待（指数，均值 60s，权重 0.5）与长等待的混合分布。

### 模型与系统
- 模型：Llama-3.1-70B，BF16，TP4。
- 基础平台：4×H100 NVL GPU + vLLM，主机内存预算 375–380 GB。
- 对比方法：
  - 未修改的 vLLM；
  - vLLM + host offload；
  - MORI（论文无公开实现，采用按论文策略的 **policy port**）；
  - Continuum（采用作者公开 fork，未包含论文中的 pause-duration estimator）。
- 评估指标：
  - active-request goodput（活动请求完成率）；
  - resume TTFT；
  - resume 时 KV 保留比例；
  - normalized recomputation 比例。

### 主要实验
- **驻留成本测量**：在并发活动请求下，人为设置 N=25–72 个挂起上下文，对比“stock vLLM”和“强制驻留”的 goodput 与恢复延迟。
- **端到端服务实验**：在 `2λ_crit` 负载下对比多系统的 goodput、KV 保留率和 resume TTFT。
- **控制器选择实验**：分析 `cpu_ttl(λ)` 相对 `host-retain` 何时更优，得到交叉点为 `P(W≤t*) = 0.39`。
- **负载扫描 replay**：在 `0.5–3×λ_crit` 的 12 个条件下，对比控制器与固定 TTL（10/30/60 分钟/无限期）的 GPU 机会成本。
- **跨平台校准**：在 H100 NVL、A100 SXM、L40S 上重复校准并检验策略排序稳定性。

## 6. 主要结论与发现

- **保留 KV 并非越久越好**：
  - 强制驻留可使 active-request goodput 下降高达 41%；
  - 驱逐可提升 goodput，但让 resume TTFT 从 66–75 ms 涨到约 700 ms（~10 倍）。
- **政策选择能够显著提升服务性能**：
  - 在 `2λ_crit` 的人工审批负载下，所提出的控制器比 vLLM 和 vLLM+offload 提升 **23–51%** 的 active-request goodput；
  - 比 MORI 提升 **22–29%**；
  - 比 Continuum 提升 **41–52%**。
- **保留比例高不等于系统更好**：
  - 在 mixture 等待分布上，MORI 保留了 21.9% 的 KV，高于本方法的 17.6%，但 goodput 反而更低（0.83 vs 1.07 req/s）。
- **负载感知的过期策略有时优于无限期保留**：
  - 在 lognormal 和 exponential 分布上应选择 host-retain；
  - 在 mixture 分布上应选择 `cpu_ttl(λ)`；
  - 交叉点约为 `P(W≤t*) = 0.39`。
- **策略无需逐负载重新调参**：
  - 在负载扫描 replay 中，校准后固定的控制器在大部分条件下均能与最优固定策略持平；
  - 在 mixture 工作负载的 `3λ_crit` 条件下，比最优固定策略还高 3.6% 效果。

## 7. 优点

- **问题选择具有现实意义**：人工审批暂停是真实 LLM 智能体场景中常见的服务形态，现有系统多只覆盖秒级 tool-call，本文填补了分钟/小时级场景的空白。
- **统一的成本建模**：GPU opportunity cost 将 HBM 保留、DRAM 保留、重算三者放在同一 GPU 时间尺度上比较，逻辑清晰、可解释性强。
- **无需逐请求预测等待时长**：对人工审批这种长尾且难预测的等待，选择“校准一次 + 负载驱动”的控制器是非常实用的设计。
- **平台校准而非固定死阈值**：阈值由 `α1、β2、β3` 推导，能随硬件能力、KV pool 大小而变化，方法可迁移到不同 GPU 平台。
- **实验设计相对严谨**：
  - 区分“stock vLLM 自动驱逐”与“强制驻留”两种状态；
  - 使用 victim exclusion 补丁控制驻留状态；
  - 先做并发度选择保证节点接近饱和，使代价可测量；
  - 使用校准样本和 held-out 测试分开策略选择与评估，减少偏差；
  - 对 MORI 与 Continuum 的不完整实现给予明确说明，诚实披露风险。

## 8. 不足与局限

- **对真实生产数据的覆盖不足**：
  - 等待时长全部是合成分布，审批结果来自模拟用户；
  - 没有真实大规模生产 trace 来验证跨越 `λ_crit` 的频率；
  - 论文本身也承认“尚未有真实 trace 显示部署中跨越 `λ_crit` 的频率”。
- **对比基线存在不对称性**：
  - MORI 没有公开实现，本论文使用的是策略移植（policy port）；
  - Continuum 使用的是第一作者公开 fork，缺少论文中的 pause-duration estimator，因此不是对 Continuum 论文完整系统的评估。
- **模型覆盖单一**：
  - 所有原型测量只用了 Llama-3.1-70B，没有验证其他模型规模/架构的泛化性。
- **控制器依赖配置化负载 λ 与周期性重校准**：
  - 实际生产环境中的在线负载估计、分布漂移等问题只被简单提及，没有深入解决。
- **主机容量 / 负载归一化可能影响结论显著性**：
  - 在低于 `λ_crit` 时，主机容量未饱和，拥塞驱动的保留决策基本不生效；
  - 只有把负载拉到 `2λ_crit` 时保留策略的差异才显著体现出来，因此结论的适用场景主要集中于“主机内存压力较大”的区间。
- **TTFT 侧重的公平性**：
  - 论文主要比较 active-request goodput，但对不同策略下的排队延迟、长尾延迟等 QoS 指标的讨论较弱。
- **缺少可复现代码与数据公开的完整说明**：
  - 没有提到是否完整开源构造的 controller 和 victim exclusion patch；这也限制了他人复现验证的便利性。
