## 摘要
长时任务大语言模型（LLM）智能体需要上下文组装：运行时必须决定在每个提示中包含什么内容、按什么顺序排列，以及在严格的上下文窗口预算和字节敏感的提示缓存下何时压缩历史记录。在生产级智能体系统中，这一逻辑分散在提示构建器、临时压缩例程、缓存破坏变通方案以及各提供商的适配层中。我们认为，上下文组装与关系数据库中的查询执行在结构上同构：两者都在硬预算下运行，利用分层缓存，并借助统计信息。我们在ContextPipe中采纳了这一原则：一个五阶段流水线（计划-绑定-优化-执行-反馈），由结构化数据源目录、确定性缓存感知优化器和EXPLAIN ANALYZE追踪提供支持。我们证明ContextPipe中的上下文是可审计、可重放且故障隔离的。使用SWE-bench Pro Qutebrowser子集的初步评估表明，与仅追加的上下文构建策略相比，ContextPipe将总令牌量减少了31%，LLM调用减少了23%，响应时间减少了9%，但代价是KV缓存命中率较低。

## Abstract
Long-horizon large language model (LLM) agents require context assembly: the runtime must decide what to include in each prompt, in what order, and when to compact history under a hard context-window budget and a byte-sensitive prompt cache. In production agentic systems, this logic is scattered across prompt builders, ad hoc compaction routines, cache-break workarounds, and per-provider shims. We argue that context assembly is structurally isomorphic to query execution in a relational database: both execute under a hard budget, exploit a tiered cache, and leverage statistics. We adopt this discipline in ContextPipe: a five-phase pipeline (Plan Bind Optimize Execute Feedback) backed by a structured data-source catalog, a deterministic cache-aware optimizer, and an EXPLAIN ANALYZE trace. We show that context in ContextPipe is auditable, replayable, and failure-isolated. A preliminary evaluation using the SWE-bench Pro Qutebrowser subset shows that, compared with the append-only context construction policy, ContextPipe reduces total token volume by 31%, LLM calls by 23%, and response time by 9%, at the cost of a lower KV cache-hit ratio.

# ContextPipe：面向长时任务智能体的数据库启发的上下文组装

## 1. 核心问题与整体含义（研究动机与背景）

- **核心问题**：长时程 LLM 智能体（Long-horizon LLM agents）运行在“接收用户消息 → 组装提示词 → 调用模型 → 解释回复/工具调用 → 执行工具 → 下一轮”的循环中。每一轮本质上是一个**请求组装问题**：运行时必须在上下文窗口硬预算下，决定提示中包含什么、以什么顺序排列、何时压缩历史。
- **现有痛处**：生产级智能体系统中，这一逻辑散落在各处的 prompt builders、临时压缩例程、cache-break 规避方案与各 provider 适配层中。系统中存在两个高风险决策：
  - **缓存字节稳定性约束**：自动前缀缓存（prefix caching）要求前缀字节一致，任何一字节改动都会使后续缓存失效并引发全量重算；
  - **顺序影响质量与成本**：长上下文模型对中间位置的注意力偏低（“Lost in the Middle”），顺序同时影响模型使用记忆的效果与缓存稳定性。
- **核心洞见**：上下文组装问题与关系数据库的查询执行**结构同构**——两者均运行在硬预算下、利用分层缓存、并依赖统计信息。因此可借用数据库领域半世纪以来沉淀的查询优化器、目录与执行追踪范式。

## 2. 方法论：核心思想与关键技术细节

### 2.1 架构：五阶段流水线

ContextPipe 将每一轮 LLM 调用建模为**一条五阶段流水线**：

- **Plan（纯函数）**：仅依据目录与统计数据，计算上下文压力并决定本轮的配置：
  - 上下文压力公式：
    - `Praw = Tused / Leff`
    - `Ppred = (Tused + Ro + Rt + Rs) / Leff`
    - `Ro` 为预期模型回复预留，`Rt` 为扩展思考预留，`Rs` 为工具 schema 增长预留；回复预留取**历史分布的百分位数**（稳态 p75、恢复期 p95），而非平均值，类似直方图基数估计。
  - 由压力水平选择压缩档位：`Normal → TrimSchemas → CompactHistory → AggressivePrune`；只允许升级、不可降级（gated escalation）。
- **Bind**：为各计划 section 并发获取具体内容（记忆检索、历史加载、工具 schema、技能加载、积累的新兴上下文等），是唯一执行外部 I/O 的阶段。
- **Optimize**：在预算内进行缓存对齐、压缩、溢出（spill）决策，输出可序列化的请求与追踪记录。限制在 `OptimizeLimits` 中显式声明。
- **Execute**：唯一向模型服务商发起请求的阶段；支持 EXPLAIN-only 模式（不发请求只出执行计划）。
- **Feedback**：记录实际输入/输出 token、缓存读/创建量、截断情况、缓存破碎归因；写 `PipelineStats` 供下轮 Plan 使用。

### 2.2 确定性缓存感知优化器

- **问题形式化**：在预算约束、锚定约束（Identity/Constraints 固定位置）、保护约束（Never 优先级 section 不可压缩）、配对约束（tool-call/tool-result 必须相邻）下选择 section 顺序 π、压缩掩码 μ 与缓存标记位置 M。
- **求解方法**：不追求效用最大化搜索，而是采用**固定确定性策略**：按缓存域波动性升序（Global < Session < None）排列 section（稳定标识符打破平局），即 **缓存感知有序放置（cache-aware ordered placement）**。
- **压缩阶梯**（每级受 OptimizeLimits 布尔门控，跳过时必须记录原因）：
  - TrimSchemas：裁剪本轮不太可能用到的工具 schema；
  - CompactHistory：清除最旧的工具结果并用占位符替代，受 max-clear-tokens 熔断器约束；超大结果**溢出到磁盘**并替换为 SpillReference（阈值 10,000 tokens，Identity/Constraints/WorkingMemory 不可溢出）；
  - AggressivePrune：额外删除最旧的整轮对话，至少保留 4 轮可删轮次，绝不删除系统消息。
- **不变量**：锚定与优先级保持、保护永不压缩内容、tool 配对与可恢复性、审计完整性、回放确定性、故障隔离等四条引理/三条性质——保证输出安全可序列化、可重放、故障后不污染统计。
- **算法复杂度**：排序 O(n log n)、压缩与序列化 O(n)，n≤30 个 section，开销相对单次 LLM 调用可忽略。

### 2.3 ContextSources 数据源目录

- 将数据源按**生命周期分为八层**（表 1），包括：Immutable（系统规则）、Latched（会话锁存）、Session（会话状态）、Per-turn、External、EmergentContext（涌现上下文）、Feedback 等。
- 重点强调两个新层：
  - **SessionLatches**：按首次触发惰性求值、随后冻结的会话级值（如 beta headers、provider 特性开关），用于防止缓存前缀漂移；
  - **EmergentContext**：将轮中后期发现（新技能、工具摘要、预取记忆）携带到下一轮；带 **TTL 守卫**（默认仅下轮消费一次）、**内容哈希去重**、列表大小上限三重安全机制。
- 每条目录项有固定 schema（层级、种类、缓存域、优先级、预估 token、绑定延迟、可恢复性、可否标记缓存等字段），类似关系数据库的 `information_schema`。

### 2.4 EXPLAIN ANALYZE 追踪

- 每个回合产生结构化 trace：EXPLAIN 部分展示压力分解、压缩档位、预计/实际 token 与缓存标记位置；ANALYZE 部分展示实际输入输出、缓存读/创建量与估计误差。
- 支持 8 条告警规则（缓存击穿、缓存冷启动、命中率回退、预测偏差 >20%、压缩级联、恢复循环等），使性能退化显性化而非静默劣化。

### 2.5 ForkPrefix：父子智能体缓存共享

- 捕获父智能体可缓存请求前缀的冻结快照（规范 wire bytes + 每工具 schema 哈希 + provider/模型身份 + thinking 配置），供子智能体首轮复用；支持 validate spawn 检查与侧查询 skip-cache-write 模式。

- trace 追踪可精确定位每次缓存命中率下降的具体原因（如 TrimSchemas 跨档造成的一次性 8% 命中率击穿后立即恢复）。

## 7. 优点与亮点

- **系统化类比数据库**：将上下文组装建模为查询执行问题，引入目录、优化器、追踪、统计储存等全套机制，填补了智能体上下文管理缺乏结构化理论框架的空白；
- **确定性 + 可审计**：非搜索式启发式优化器保证同输入同输出，配合 EXPLAIN ANALYZE 与跳过原因记录，支持影子发布、差异比对与故障后回放；
- **预测式压缩**：百分位数驱动的预测压力（而非反应式阈值触发）使请求在触发 prompt-too-long 错误前被压缩；
- **创新机制**：SessionLatches 将隐式状态显性化、EmergentContext 带 TTL/去重/上限三重安全守卫、ForkPrefix 支持父子智能体缓存复用；
- **故障隔离良好**：失败回合不污染统计桶、溢出写原子化、EmergentContext 仅成功时填充——重试无需特殊清理。

## 8. 不足与局限

- **实验规模有限**：仅 3/79 实例，单代码库（Qutebrowser）、单模型（DeepSeek-V4-Pro）、未披露 provider，外部效度差；作者将结尾质量对比定性为“探索性的平局”，缺乏统计功效的非劣效检验；
- **成本模型依赖性强**：token 计费与缓存价格比例显著影响结论（r<0.145 时 Structured 计费成本反而高于 Flat）；结论对不同 API 提供商的泛化能力未验证；
- **消融缺失**：四项核心机制消融（A1–A4）均未完成，无法独立归因每个设计的贡献；
- **缓存命中率下降风险**：压缩必然改变前缀字节，每次跨档都会造成一次性大缓存击穿；缓存命中率中位数下降约 9 个百分点，在高缓存价格环境下不可忽视；
