## Abstract 

Evaluating distributed LLM serving designs on physical clus-ters is costly. Yet existing simulators provide only subsets of the capabilities needed for realistic design exploration: state-ful closed-loop execution, timing prediction without pro-filing target hardware, and direct execution of unmodified serving benchmarks. We present ServeTwin, a closed-loop simulator that couples specification-driven analytical timing with a stateful serving loop. This coupling captures feedback among request completion, scheduling, queue state, and KV-cache evolution, including prefill–decode disaggregation and multi-turn agent workloads. ServeTwin avoids target-hardware operator profiling through iSTAGE, an analytical trace generator that derives per-iteration traces from model and engine specifications while representing ragged batches and discrete engine mechanisms such as CUDA-graph batch padding. It fur-ther decomposes execution time into component-owned throughput, scheduler, and runtime costs. This ownership lets unaffected parameters transfer across platforms and confines recalibration to changed hardware or software components. ServeTwin implements a vLLM-compatible interface and runs unmodified serving benchmarks. Against real deployments, it reproduces InferenceX’s steady-state throughput–interactivity frontier with a 3.6% mean error and predicts LMBenchmark’s multi-turn performance with a 9.9% error while tracking KV-cache evolution. Pre-silicon sweeps reveal that the preferred HBM bandwidth–capacity tradeoff reverses across workload states and that increasing concurrency shifts the bottleneck from memory bandwidth to scheduler and runtime overheads. Together, these capabil-ities enable practical exploration of distributed LLM serving systems before target hardware is available.

ServeTwin reconnects this severed feedback loop and re-solves these state failures, as illustrated in Figure 2. Running unmodified multi-turn benchmarks, it completes execution under deployment-equivalent KV budgets by properly stag-ing the waiting path. Each iteration, it constructs a batch mir-roring production LLM engines (e.g., vLLM, SGLang), strictly enforcing admission control, cross-worker KV transfers, and multi-turn states. To process this without empirical profiles, we introduce iSTAGE—extending STAGE [9] to translate the batch into a symbolic trace, calculating latency directly from hardware specifications. Feeding this precise timing back to advance the system state naturally dictates the next batch composition. Integrating an analytical model within a dynamic serving loop poses profound challenges. First, serving batches are inherently ragged; naïvely padding them to maximum di-mensions for analytical graphs overestimates execution time by up to 146 ×. Second, theoretical FLOPs and memory band-width cannot capture discrete runtime mechanisms (e.g., KV page walks, kernel launches) that heavily skew step latency. Finally, continuous end-to-end simulation demands excep-tionally lightweight trace generation. iSTAGE overcomes these hurdles through (1) statistics-preserving batch binding, (2) first-order modeling of discrete engine mechanisms, and (3) aggressive trace reuse. Despite this ex-treme runtime complexity where prior methods simply crash, ServeTwin successfully captures these transient dynamics within a 10% error margin. ## 2 Background and Motivation 

2.1 LLM Serving as a Stateful System 

LLM serving entails two distinct phases: prefill (processing prompts to generate a KV cache) and decode (iteratively generating tokens, expanding the cache). Modern engines dynamically reconstruct batches every iteration via contin-uous batching and chunked prefill, while leveraging prefix caching for history reuse. Crucially, execution is fundamen-tally state-dependent. A request is admitted only if sufficient KV memory exists; otherwise, it queues or preempts. Be-cause discrete runtime mechanisms often reshape physical execution (§3.5), simulators must explicitly track the dy-namic system state (e.g., KV occupancy) that governs batch composition, rather than merely counting requests. 

2.2 Prefill/Decode Disaggregation and KV Transfer 

Disaggregated architectures [12, 13, 22] isolate prefill and decode workers to prevent long prompts from stalling token generation. This necessitates transferring the KV cache be-tween workers. However, this handoff is not a static network delay. Production systems (e.g., Dynamo [11] with NIXL [10]) implement a pull mechanism where decode workers fetch KV blocks only when they have sufficient free capacity. If de-code memory is full, the cache remains staged on the prefill worker, creating upstream backpressure. Accurate simula-tion requires tracking this occupancy-coupled admission and the resulting capacity-driven dependencies (§3.3). 

2.3 Benchmarks Used in This Paper 

We validate ServeTwin using two distinct benchmarks. 

InferenceX [15] maps the steady-state balance between throughput and interactivity. We validate our simulator against the public hardware performance data published online by SemiAnalysis. 

LMBenchmark [8] captures dynamic, multi-turn behav-iors like admission pressure and transient delays. We vali-dated this by deploying an in-house DGX H100 with NVIDIA Dynamo and vLLM, directly matching ServeTwin’s behavior with physical telemetry data extracted via Prometheus and Grafana. 

2.4 Existing Simulation Approaches Serving Simulators. Tools like LLMServingSim [3, 4], Vidur [1], and AgentServeSim [14] model continuous batch-ing and scheduling but fundamentally rely on hardware-profiled latencies. Furthermore, they omit critical stateful semantics: LLMServingSim relies on open-loop trace replay that breaks multi-turn session dependencies, and mod-els prefill-to-decode disaggregation as an unconditional pipeline cut lacking staged-KV backpressure. Vidur and AgentServeSim similarly lack occupancy-coupled KV lifecy-cles. 

Analytical Models. GenZ [2] and LLMCompass [20] es-timate execution timings directly from hardware specifi-cations, enabling architectural exploration. However, they evaluate static workloads offline (i.e., snapshots), completely lacking the dynamic closed-loop scheduling required to iter-atively update batch compositions. 

STAGE. STAGE [9] synthesizes symbolic tensor graphs for distributed LLM workloads and includes an inference case study. Its abstraction, however, models prescribed work-load graphs rather than a stateful serving loop: it does not represent KV-cache lifecycles, queueing feedback, or the scheduler-generated ragged batches that change at every iter-ation. Adapting it for serving therefore requires the serving-specific mechanisms described in §3.5. 

2.5 Why Existing Serving Simulation Is Insufficient 

LLMServingSim represents prefill/decode disaggregation as a pipeline cut and has no state in which a completed pre-fill request can retain its KV on the producer while wait-ing for decode-side capacity. Figure 1 gives a motivating counterexample. ServeTwin runs the unmodified multi-turn benchmark and completes under the deployment-equivalent KV budget, while both LLMServingSim encodings abort when they attempt to allocate the decode-side KV without a staged waiting path. This is a semantic failure rather than an execution-time calibration error: all methods use the same calibrated compute profile.

3.2 Serving-State Simulation 

While the baseline scheduling logic builds upon LLMServ-ingSim [3, 4], we redesign its internal state management to achieve strict closed-loop fidelity. Through this redesign, ServeTwin models production systems like vLLM and SGLang, supporting continuous batching, chunked prefill, radix-tree prefix caching, and capacity-driven preemp-tion. To track these dynamics, we introduce a KV lifecycle registry featuring Dynamo-inspired pull-based handoffs (§2.2), occupancy-coupled admission, tiered memory, and a dedicated multi-turn session layer. Finally, iSTAGE and ASTRA-sim replace the legacy profile-based backend, en-abling fully spec-driven simulation. 

3.3 Disaggregated KV Lifecycle 

In ServeTwin, a request’s KV cache transitions through an explicit state machine (Figure 3), from initial allocation to eventual eviction or demotion. Unlike a simplistic pipeline cut, this lifecycle enforces two critical couplings. First, admis-sion is occupancy-coupled : decode-side memory saturation blocks admission, naturally inducing backpressure on the prefill queue. Second, KV transfer is strictly consumer-driven :staged KV awaits an explicit pull from the decode worker (modeling NIXL-style handoffs [10]). Decoding commences only upon full KV arrival or suffix recomputation, supporting both full and layer-wise transfers. 3.4 Multi-turn Sessions as Simulator State 

Unlike traditional trace-driven approaches that statically unroll conversations into independent requests, ServeTwin tracks multi-turn sessions as internal simulator state. A ses-sion issues a subsequent turn only after the preceding re-sponse is fully generated, reflecting strict inter-request de-pendencies and optional tool-execution delays. Because con-text accumulates continuously across rounds, the integrated prefix cache (§3.2) translates shared history into cache hits and minimal delta transfers. Furthermore, ServeTwin supports tiered KV memory man-agement: blocks evicted from HBM can be demoted to host memory and promoted back upon subsequent hits, with all data movement strictly constrained by the host-to-device in-terconnect bandwidth. Additionally, speculative decoding is analytically incorporated via a parameterized per-step accep-tance length. Collectively, these state-tracking mechanisms capture the workload semantics inherent to the multi-round agentic scenarios evaluated by LMBenchmark.

3.5 Spec-Driven Execution Modeling with iSTAGE 

While STAGE [9] provides foundational spec-driven graph synthesis for distributed LLM workloads, it does not model the dynamic serving state or KV-aware ragged batches pro-duced by a serving scheduler. To bridge this gap, we develop 

iSTAGE (Inference STAGE) , which extends and retargets this symbolic execution modeling specifically for serving. This enables accurate, profile-free timing evaluation based purely on hardware specifications. iSTAGE achieves modu-larity via configuration files rather than hardcoded backends. As summarized in Table 2, its templates support a wide spec-trum of modern architectural features. This breadth is es-sential for architectural exploration, as varying model struc-tures fundamentally shift system bottlenecks across compute, bandwidth, memory capacity, and communication. However, integrating these models into an iterative serv-ing loop introduces three unique challenges absent in train-ing simulations: (1) modeling irregular (ragged) batches with-out padding-induced cost distortions; (2) capturing discrete engine mechanisms that alter latency independently of the-oretical FLOPs/bytes; and (3) ensuring trace generation is lightweight enough for per-iteration execution. As illustrated in Figure 4, iSTAGE resolves these by replacing naïve rect-angular schemas with statistics-preserving batch binding and applying capture-size padding to reflect actual engine discreteness.

3.6 Component-Driven Latency Modeling 

Hardware specifications easily provide baseline times for compute and memory traffic. However, real-world execution includes complex overheads like host scheduling, KV cache traversal, and network startups. If a simulator lumps all these delays into a single, generic "overhead" constant, it cannot accurately predict performance when hardware or software configurations change. To address this, ServeTwin breaks down every overhead by its actual root cause—a principle we call component ownership .Every delay in our model must map to a specific system operation, scale based on clear variables (like request count or context length), and remain unchanged unless that specific operation changes. Consequently, the total time for each iteration is the sum of three distinct components:

Table 3 summarizes these costs and their system owners. To prevent these terms from becoming unjustified fitting parameters, ServeTwin enforces three strict rules: 1. Use specifications directly: Peak compute, mem-ory bandwidth, and engine capture lists are drawn strictly from hardware and software specifications, never from curve fitting. 2. Ground terms in observation: We introduce over-head terms exclusively when warranted by empirical scaling trends. For instance, a cost profile scaling with context length isolates KV-cache traversal, whereas an overhead persisting across hardware transitions signifies software-stack overheads. 3. Fix and reuse values: Calibrated parameters are frozen and consistently applied across all operating points and platforms, provided their underlying com-ponents remain unaltered. This breaks away from conventional practices—such as tuning a generic over-head percentage—that overfit a single scenario and fail to generalize. Separating these sources is critical for accuracy. For instance, on a high-batch H200 decode step, throughput physics takes 12.7 ms, but control and mechanism overheads add 11.1 ms—comprising nearly half the total time, not just a rounding error. By adhering to component ownership, ServeTwin makes falsifiable predictions: removing a term primarily affects the serving conditions it represents (§4.3), parameters transfer safely across platforms (§4.4), and swapping a component requires re-calibrating only its specific owner (§4.5).

• RQ1 (Attribution): When we remove one overhead term, does accuracy degrade where we expect it to (§4.3)?

4.3 Sensitivity Analysis of Cost Terms 

We conduct an ablation study to verify the necessity of the individual cost families in Table 3. By removing one term at a time, we evaluate whether prediction errors (reported as ab-solute percentage points, pp, in Figure 5) increase specifically under the serving conditions each term is designed to repre-sent. Omitting the GEMM utilization term increases prefill prediction error by 56 pp, showing that peak compute rates alone do not capture effective GEMM performance. Per-step host control: Removing this increases small-batch decode error by 47pp, demonstrating that CPU overhead remains sig-nificant even for small GPU batches. DPA synchronization: Removing this increases DPA-decode error by 40pp. Other terms (e.g., KV traversal, collective costs) similarly domi-nate prediction errors under their corresponding conditions. These results justify maintaining separate cost terms rather than using a generic, interchangeable correction factor, an approach that conceptually aligns with LIMINAL [5].

4.7 Simulation Efficiency 

Three forms of reuse cut trace-generation overhead. First, we generate each heavily repeated end-to-end trace expression once and reuse it. Second, rather than simulating individual layers, we exploit the layer-wise repetition of a Transformer to jump analytically to the end of all layer executions, a further 4 .9×. Third, a shape cache groups slightly varying tensor shapes (e.g., batch sizes or sequence lengths) into size-based buckets that share one entry, instead of caching every shape separately. Consequently, all experiments, including full calibration sweeps, execute deterministically on a single commodity CPU in minutes.

## 6 Conclusion 

ServeTwin predicts LLM serving performance by integrat-ing a KV-lifecycle state machine with a specification-driven analytical backend. Validated against independent public benchmarks, it achieves a 3 .6% mean error on InferenceX frontiers and reproduces queue and cache-reuse dynamics in multi-turn scenarios. By updating calibration parameters strictly based on architectural changes, ServeTwin success-fully transfers to new platforms, predicting GB200 NVL72 performance within a 2% margin. This capability allows ar-chitects to generate serving curves directly from pre-silicon specifications. Finally, our design studies demonstrate that hardware upgrade priorities must align with workload states and service targets.
