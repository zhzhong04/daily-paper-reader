## 摘要
LLM 智能体日益执行涉及多轮推理、工具使用和并行智能体的复杂工作流。高效服务需要跨两个具有互补信息的层次做出决策：智能体执行框架理解工作流依赖、上下文生命周期和执行目标，而推理引擎观察请求队列、KV 缓存状态、资源压力和执行能力。现有接口未能系统性地连接这些视图，限制了工作流感知的执行。HEAR 是一种面向智能体化 LLM 服务的双向 Harness–Engine 配对协议。HEAR 标准化了执行框架如何传达工作流意图与执行需求，以及推理引擎如何返回运行时状态、能力和结果。通过将协议语义与优化策略分离，HEAR 支持多种协调策略，而不改变工作流或模型语义。我们将 HEAR 实例化用于在线缓存感知的运行时协调，以及面向智能体角色的工作负载感知执行模式选择。在内存受限的并发服务下，跨越四个对话式与研究型智能体基准，HEAR 在 SCBench 上实现了 1.61 倍的批处理加速，并将首 token 时间中位数缩短了 2.23 倍。Mooncake 表明，工作流意图与实时引擎状态在不同负载状况下提供了互补收益。在 BrowseComp-Plus 和 DeepResearchBench 上，针对工作负载的配置分别带来了 1.23 倍和 2.45 倍的端到端加速，且未观察到任务质量下降。这些结果确立了 HEAR 作为高效智能体化 LLM 服务的可复用协调基底。

## Abstract
LLM agents increasingly execute complex workflows involving multi-turn reasoning, tool use, and parallel agents. Efficient serving requires decisions that span two layers with complementary information: the agent harness understands workflow dependencies, context lifecycles, and execution objectives, whereas the inference engine observes request queues, KV-cache state, resource pressure, and execution capabilities. Existing interfaces do not systematically connect these views, limiting workflow-aware execution.   HEAR, a bidirectional Harness--Engine Pairing protocol for agentic LLM serving. HEAR standardizes how the harness communicates workflow intent and execution requirements and how the engine returns runtime state, capabilities, and outcomes. By separating protocol semantics from optimization policies, HEAR supports diverse coordination strategies without changing workflow or model semantics. We instantiate HEAR for online cache-aware runtime coordination and workload-aware execution-mode selection for agent roles.   Across four conversational and research-agent benchmarks under memory-constrained, concurrent serving, HEAR achieves a $1.61\times$ batch speedup and reduces median time-to-first-token by $2.23\times$ on SCBench. Mooncake shows that workflow intent and live engine state provide complementary benefits across load regimes. On BrowseComp-Plus and DeepResearchBench, workload-specific configurations yield $1.23\times$ and $2.45\times$ end-to-end speedups, respectively, without observed task-quality degradation. These results establish HEAR as a reusable coordination substrate for efficient agentic LLM serving.

## 1. 核心问题与整体含义

- **研究背景**：LLM 智能体通过多轮规划、工具调用与并行协作执行复杂工作流，端到端效率不再仅取决于单次生成加速，而取决于跨工作流请求与可复用状态的协调。
- **核心矛盾**：执行决策所需信息被割裂在两层：
  - **Agent Harness（智能体执行框架）**：掌握工作流依赖、上下文生命周期、执行目标与角色语义；
  - **Inference Engine（推理引擎）**：掌握请求队列、KV-cache 驻留状态、资源压力与支持的执行模式。
- **具体表现**（论文 Figure 1 的动机示例）：
  - 引擎不知道上下文将被复用 → 在复用前一刻驱逐 KV，导致昂贵的重新 prefill；
  - Harness 不知道缓存驻留状态 → 在存在缓存可复用请求时先调度冷请求。
- **系统性缺口**：现有工作（KVFlow、Parrot、Pythia、PBKV、ConCUR 等）虽展示了工作流信息与运行时反馈的价值，但都各自定义跨层信号、控制语义与操作生命周期，**策略与特定 harness/引擎紧耦合，缺乏可复用的共享控制面抽象**，限制了可移植性与可组合性。
- **整体含义**：HEAR 旨在提供一种**协议层抽象**——标准化"两层之间交换什么、意味着什么、如何处理"，而把"交换哪些信息、采取什么动作"留给策略。它不改变工作流的任务选择逻辑，也不改变模型语义。

## 2. 方法论

### 2.1 核心思想
HEAR 是一个**双向 Harness–Engine 配对协议**，将协议语义与优化策略解耦，作为可复用的协调基底（coordination substrate）。每条交换消息都关联到具体的**请求、上下文版本或服务实例**。

### 2.2 四类语义消息（Message Categories）

| 方向 | 类别 | 代表性内容 |
|---|---|---|
| Harness → Engine | **Execution Description and Intent** | 智能体角色与阶段、工作流依赖与就绪状态、请求规模与输出上限、上下文生命周期、已知未来用途与显式标记的预测 |
| Harness → Engine | **Execution Requirements and Control** | 调度偏好与等待时间约束、缓存准备/保留/释放请求、允许或请求的执行配置与服务目标 |
| Engine → Harness | **State and Capabilities** | 可复用前缀范围与驻留层级、可分配容量、队列状态与资源压力、支持的控制与配置、校准或估计的执行成本 |
| Engine → Harness | **Execution Outcomes** | 推理与控制请求的状态（接受/完成/拒绝/不支持/失败）、实际配置与允许回退、缓存复用、延迟、资源消耗、重试与错误 |

### 2.3 四项关键语义区分（Interaction Semantics）

- **Intent vs. Control**：描述与预测只提供决策上下文，**只有显式控制请求才要求接收方行动**。例如"报告上下文 c 可能被复用"≠"请求保留或准备其 KV"。
- **Preference vs. Requirement**：偏好是尽力而为（best-effort）信号，要求约束合法执行；未满足的要求必须被拒绝或走显式允许的回退路径。
- **Observation vs. Guarantee**：状态与能力报告描述当前条件与支持的操作，**不预留资源、不保证未来可用**。
- **Acceptance vs. Completion**：接受仅表示操作被纳入处理，完成才确认预期效果已实现；被拒绝、不支持、失败是彼此不同的结果。

### 2.4 策略集成公式
联合信息决策：
$$d_i = \pi(h_i, s_j)$$
其中 $h_i$ 为决策点 $T_i$ 处的工作流与请求信息，$s_j$ 为最新的相关引擎更新，$\pi$ 选择执行安排或配置 $d_i$。由于两层独立演化，**$s_j$ 不必产生于 $T_i$**。

- 无引擎反馈时退化为 harness 本地决策 $d_i = \pi(h_i)$；
- 无工作流信息时引擎只能局限于请求本地状态。

### 2.5 两个策略实例（不同时间尺度）

**(1) Cache-Aware Runtime Coordination（在线策略，快速时间尺度）**
- Harness 提供：就绪请求 $\mathcal{R}_i$、上下文 $\mathcal{C}_i$、执行要求 $\mathcal{U}_i$（含等待保护）；
- 引擎返回：缓存可用性 $K_j$、队列状态 $Q_j$；
- 调度策略产出优先级分配 $p_i$，缓存与队列报告属于 State and Capabilities，优先级属于调度偏好，等待保护是强制要求；
- 具体做法：harness 顺序匹配可复用前缀块（遇首个缺失/被驱逐块即停止），统计 GPU/CPU 层级可复用前缀 token；可复用前缀覆盖 ≥50% 提示的请求为 **hot**，优先级为 `priority = −N_reuse`（可复用 KV 块数的负数），引擎按优先级值小者先执行，hot 请求内部按可复用前缀长度递减排序；
- **Guard-W**：请求等待超过 W 秒后被提升为受保护优先级，后续 cache-hot 请求不能再绕过；受保护请求按等待顺序排列；
- **Session-Aware**（KV 保留策略）：harness 从已完成会话维护会话返回概率 p，保留优先级 `r = p · e^(−idle/400)`，idle 为距上次请求完成的时长。

**(2) Capability-Aware Execution Configuration（粗粒度策略，慢时间尺度）**
- Harness 描述 $h_i$：智能体角色、工作流阶段、工作负载形态、执行目标、质量要求；
- 引擎视图 $s_j$：兼容执行模式及其测得的延迟、吞吐、KV 容量与稳定性画像；
- 候选空间：$\mathcal{C} = \{\text{vLLM}, \text{OmniKV}\} \times \{\text{vLLM}, \text{H2O}, \text{SnapKV}\}$（前者为 Main 侧，后者为 Reader/子智能体侧）；
- 在通过开发阶段质量与稳定性检查的配置中，选择器最小化 makespan：
$$d^{\text{config}}_i = \pi_E(h_i, s_j)$$
- 冻结映射：$d^*_{\text{BCP}} = (\text{vLLM}, \text{H2O})$，$d^*_{\text{DRB}} = (\text{OmniKV}, \text{H2O})$，在工作流初始化时由引擎加载，**运行时不做六臂搜索**，只做常数规模查表。

  - 策略与参数在正式评测前**冻结**，每个臂从独立初始化的服务状态开始，结果包含所有失败与重试；
  - 提供 Wilson 95% 置信区间与 paired bootstrap 区间；
  - 诚实报告了 Judge 环境的差异（部分臂在 RTX PRO 6000、部分在 H100 上评判），并指出单环境复评可进一步消除该差异。
- **局限**：部分结论（如 Mooncake 在 100% 负载下 Session-Aware + Cache-Aware + Guard 反而吞吐下降 0.89×）表明策略组合存在非单调行为，但论文未深入解释该退化机制。

## 6. 主要结论与发现

- **SCBench**：等待保护的缓存感知调度（Cache-Aware + Guard-40）相比 FCFS 实现 **1.61× 批完成加速**，中位 TTFT 降低 **2.23×**、P95 降低 **1.45×**、最大 TTFT 降低 **1.22×**，KV 复用率从 19.2% 提升至 66.1%（纯 Cache-Aware 可达 87.6% 但尾部延迟恶化）。
- **Mooncake**：**没有单一策略在所有负载下占优**——
  - 50% 负载：空闲期驱逐是复用损失主因，Session-Aware 最优（复用 19.5%→31.9%）；
  - 75% 负载：驱逐控制与执行顺序控制互补，Session-Aware + Cache-Aware + Guard 综合最佳（吞吐 121.0 vs FCFS 116.4）；
  - 100% 负载：Cache-Aware 在 P50、session 延迟与吞吐上更好（P50 TTFT 1.89×），Session-Aware 在尾部延迟与复用上更好。
- **BrowseComp-Plus**：选择 vLLM–H2O，wall time 从 5.69 降至 4.62 小时，**1.23× 加速**，Judge 准确率 46.63% vs 46.15%（无退化）。
- **DeepResearchBench**：选择 OmniKV–H2O，makespan 从 5.93 降至 2.42 小时，**2.45× 加速**，RACE 41.1% vs 40.6

**DeepResearchBench**：选择 OmniKV–H2O，makespan 从 5.93 降至 2.42 小时，**2.45× 加速**，RACE 41.1% vs 40.6%（+0.5 个百分点，无退化）。

**跨工作负载的共性结论**：
- **信息互补性成立**：harness 侧的上下文生命周期/依赖信息与引擎侧的缓存驻留/队列状态信息，任一单独使用都无法达到联合决策的效果；两者结合才使"何时驱逐、何时复用、以何顺序执行"的决策具备全局视野。
- **优化收益高度依赖工作负载形态**：对话式（SCBench、Mooncake）收益主要来自缓存复用与执行顺序；研究型智能体（BrowseComp-Plus、DeepResearchBench）收益主要来自执行配置选择与角色级资源分配，说明"哪类信号更重要"随场景迁移。
- **质量无退化**：所有策略与配置选择均未在 Judge 准确率或 RACE 分数上产生统计显著下降，表明协调优化并未以牺牲输出质量为代价。
- **策略非单调性**：Mooncake 100% 负载下 Session-Aware + Cache-Aware + Guard 组合的吞吐回退（0.89×）表明，不同时间尺度、不同目标的控制信号叠加可能产生冲突，协议只负责语义澄清与合法组合，不保证策略组合的最优性。

### 角色级归因与配对比较

- **角色级执行归因**：通过每次只替换一个角色（Main 侧或 Reader/子智能体侧）的执行模式，论文将端到端加速分解为两个来源。结果表明，在深度搜索与深度研究工作流中，**Reader/子智能体侧的配置选择贡献了主要加速**，这与其承担大量重复性检索/阅读调用、对 KV 压缩与批处理效率更敏感相符；Main 侧配置则更多影响长上下文推理的稳定性与延迟尾部。
- **配对质量比较**：采用 McNemar 检验（分类正确性）与配对 t 检验（连续指标），在各臂共享同一问题集的前提下比较质量差异；结果显示所选配置在效率提升的同时，质量差异落在噪声范围内，支持"效率增益不以质量为代价"的结论。
- **完整六臂明细**：论文给出了全部 6 种 Main×Reader 组合的效率与质量双维明细，使读者可以观察到"最优组合"并非全局唯一，而是依赖工作负载与硬件约束。

## 7. 讨论与启示

- **协议 vs. 策略的分层价值**：HEAR 的核心贡献不在于某个具体调度算法，而在于把"跨层信号应具备何种语义"从"具体系统如何实现优化"中剥离出来。这使得同一套消息语义可以支撑在线调度（毫秒级）与离线配置（会话级）两类完全不同时间尺度的策略，而无需为每种策略重新定义跨层契约。
- **可移植性与可组合性**：由于消息类别、语义区分与操作生命周期被标准化，harness 与引擎可以独立演化；新的 harness（如不同智能体框架）或新的引擎（如不同推理后端）只需实现协议端点，即可复用已有的策略生态，避免 KVFlow、Parrot 等工作中"策略与特定 harness/引擎紧耦合"的可移植性瓶颈。
- **"意图—控制"分离的工程意义**：显式区分 Intent 与 Control，使 harness 可以低成本地"告知"引擎未来可能的上下文复用，而不必立即触发保留动作；引擎据此可做保守的驱逐决策，同时保留在资源紧张时忽略该提示的自由。这种"软信号 + 硬控制"的双通道设计，是协议能在高负载下仍保持稳定的关键。
- **对系统设计的启示**：跨层协调的收益上限取决于信息质量而非信息数量；协议的语义澄清（Preference vs. Requirement、Observation vs. Guarantee、Acceptance vs. Completion）实质上是在为跨层决策划定责任边界，减少"误把观测当保证、误把偏好当约束"导致的调度抖动与资源错配。

## 8. 局限与未来工作

- **策略组合的非单调性尚未被充分解释**：如 Mooncake 100% 负载下多信号叠加导致吞吐回退，论文给出了现象但未给出机制层面的归因，未来需要更细粒度的信号冲突分析或自适应权重机制。
- **评测环境差异**：质量评判部分臂在 RTX PRO 6000、部分在 H100 上完成，虽被诚实报告，但单环境复评可进一步消除潜在偏差。
- **工作负载覆盖**：当前评测集中于对话式与研究型智能体两类负载，对更异构的混合工作流（如同时包含短对话、长文档、代码执行）覆盖有限。
- **协议实现开销**：控制面元数据处理虽被纳入端到端时间，但在极高 QPS 下协议端点的开销与扩展性仍待进一步验证。
- **策略生态**：论文给出了两个策略实例作为协议可行性的证明，但协议真正的价值取决于社区能否在其上构建多样化的可组合策略，这需要后续工作提供参考实现、接口规范与互操作性测试。

## 9. 总体评价

HEAR 是一篇以**协议抽象**为核心贡献的系统性工作：它没有提出某个单一的最优调度算法，而是识别出 LLM 智能体服务中"harness 与引擎信息割裂"这一结构性缺口，并通过四类语义消息、四项语义区分与统一的操作生命周期，为跨层协调提供了可复用、可移植、可组合的共享控制面。实验覆盖两个时间尺度、两类工作负载、多种对比策略，采用轨迹回放确保公平性，并诚实报告了质量与局限。其价值不仅在于 1.23×–2.45× 的端到端加速与无质量退化的实证，更在于为后续"策略与协议解耦"的研究与工程实践提供了一个可讨论、可扩展的基线抽象。
