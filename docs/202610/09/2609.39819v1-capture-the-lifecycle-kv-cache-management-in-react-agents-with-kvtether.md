## 摘要
长上下文推理-行动（ReAct）智能体的高效服务依赖于 KV 缓存复用，以降低大语言模型（LLM）的预填充延迟和金钱成本。然而，智能体执行框架与底层服务栈之间存在语义鸿沟。通过上下文变更、工具执行和子智能体协调，上下文消息可能处于活跃使用、被永久丢弃或暂时未使用状态，而服务栈只能观察到对相应 KV 缓存的访问。这种生命周期盲区使得仅基于最近使用情况的策略（如 LRU）无法及时回收已失效的 KV，也无法保留那些比更新条目更早被复用的较旧 KV。我们提出 KVTether，一个面向 ReAct 智能体的生命周期感知 KV 缓存管理框架。通过追踪嵌入在智能体执行框架中的语义原语，KVTether 能在高度动态的执行过程中捕获运行时生命周期语义。随后，KVTether 将消息级语义转换为 KV 级生命周期状态，并利用这些状态驱动按状态优先的缓存管理，而不会将物理复杂性暴露给智能体执行框架。在回收已失效的 KV 后，KVTether 优先保留等待复用的存活但空闲 KV，从而减少复用前的过早驱逐。在智能体基准测试和生产工作负载中，相对于 LMCache 和 MORI，KVTether 分别将端到端请求延迟最多降低 26.3% 和 17.4%，并将估计任务成本平均降低 40.0% 和 33.2%。

## Abstract
Efficient serving of long-context reasoning-and-acting (ReAct) agents relies on KV cache reuse to reduce large language model (LLM) prefill latency and monetary cost. However, a semantic gap exists between agent harnesses and the underlying serving stack. Through context mutation, tool execution, and subagent coordination, context messages may become actively engaged, permanently discarded, and temporarily unused, while the serving stack only observes accesses to the corresponding KV cache. This lifecycle blindness prevents recency-only policies such as LRU from reclaiming dead KV promptly and from preserving older KV that will be reused sooner than newer entries.   We present KVTether, a lifecycle-aware KV cache management framework for ReAct agents. By tracing semantic primitives embedded in agent harnesses, KVTether captures runtime lifecycle semantics during highly dynamic execution. KVTether then translates message-level semantics into KV-level lifecycle states and uses these states to drive state-prioritized cache management without exposing physical complexities to agent harnesses. After reclaiming dead KV, KVTether preferentially preserves live-but-idle KV that is waiting for reuse, reducing premature eviction before reuse. Across agent benchmarks and production workloads, KVTether reduces end-to-end request latency by up to 26.3% and 17.4% relative to LMCache and MORI, respectively, and lowers estimated task cost by 40.0% and 33.2% on average.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：LLM 应用正从聊天机器人演进为自主智能体（Claude Code、Codex、OpenClaw、Hermes 等），通过 ReAct 循环交替进行 LLM 推理与工具调用。一次请求可累积数十万 token（如 Codex 请求可达 258K token 上下文），KV 缓存复用是避免重复 prefill、降低延迟与成本的关键。但 KV 保留代价高昂：GLM-4.7 下 258K token 上下文需 93GB KV。
- **核心问题——语义鸿沟**：应用层（agent harness）以**消息级**操作（append / replace / remove / fork / one-shot 构造）管理上下文，定义消息的**逻辑生命周期**；而推理层（vLLM、SGLang）与 KV 存储层（MoonCake、LMCache）只能看到 **token 序列、共享前缀、缓存页与访问事件**。因此物理 KV 驻留与源消息的逻辑生命周期发生偏离，存储层无法判断某段 KV 是"逻辑存活""显式保留""暂时等待"还是"已死亡"。
- **由此引发两类缓存管理失效**（基于一条云厂商生产 trace 与一个 agent benchmark 的分析）：
  - **存活失效（zombie KV）**：逻辑生命周期已结束的 KV 仍物理驻留。LMCache 上 zombie 占比峰值达 31.1%（Agent-X）、36.3%（Codex）、15.8%（Agent-G）；MORI 因用请求空闲度排序，zombie 峰值达 49.7% / 33.1% / 27.4%。论文强调这不是"预测问题"，而是**缺失生命周期信息**。
  - **排序失效（错误方向驱逐）**：即便排除死 KV，存活但空闲 KV 之间仍存在容量竞争。以 Belady 规则衡量，LMCache 的错误方向驱逐比例为 79.5% / 95.0% / 71.0%，MORI 为 57.8% / 75.6% / 45.7%。原因在于 ReAct 中"最近产生的 KV"往往正在等待工具执行、调度或子智能体协调，而非最接近复用。
- **量化后果**：实测 KV 命中率仅 28.1%（LMCache）与 39.8%（MORI），远低于理论最优 82.8%；prefill 占总执行时间 37.6%（LMCache）/ 34.6%（MORI）。
- **整体含义**：ReAct 智能体服务需要**生命周期感知（lifecycle-aware）**的 KV 管理，且生命周期信息必须由应用层在运行时**显式导出**，而非在下游推断——因为执行拓扑是运行时涌现的（一个生产 trace 中子智能体承担的 LLM 轮次占比在 1.6%–86.5% 之间波动），固定工作流结构无法预先枚举。

## 2. 方法论：核心思想与关键技术细节

### 2.1 总体架构（三模块流水线，图 7）

- **语义原语模型**：在 harness 内以消息级原语导出生命周期事件。
- **事件驱动生命周期管理器**：把消息级事件翻译为 KV 级生命周期状态。
- **状态引导 KV 缓存引擎**：按状态优先级执行准入、回收与驱逐。

### 2.2 语义原语模型（§4）

- **设计依据**：调研四种不同语言实现的 harness（Codex CLI/Rust、SWE-agent/Python、Hermes/Python、Agent-G/Go），发现它们共享同一抽象——**context manager 以有序消息序列保存交互历史**。因此将导出点定在更稳定的"消息级上下文操作"上，而非易碎的 harness 专用钩子或按功能（如 compaction、safety guardian）分类的规则（同一功能在不同 harness 中上下文需求不同）。
- **八个原语**（表 3）：
  - 消息编辑：`append`、`replace`、`remove`
  - 上下文创建：`fork`（子上下文共享父前缀）、`spawn`（独立子上下文）
  - 生命周期声明：`one_off`（仅一次推理）、`pin`（长期保留）、`unpin`（解除保护）
- **表达力论证**：空间上，消息列表变化可归约为增/改/删的组合（也覆盖顺序变化）；时间上，新上下文要么独立要么继承已有消息，消息可一次性使用、跨轮复用或显式保留。更复杂的功能可由原语组合表达。
- **集成方式**（图 8）：以 Python 适配器子类化既有 `ContextManager` 为例，保留原有消息更新与 prompt 构造逻辑，仅通过 SDK 上报操作；例如 compaction 场景中 fork 出临时上下文、声明 `one_off`、再用摘要 replace 原历史。

### 2.3 事件驱动生命周期管理（§5）

- **KV 作用域解析（§5.1）**：以**上下文为管理单元**，维护"消息 → 实际 prompt 字符串 → token 序列 → KV 范围"的映射，复用与 LLM 引擎相同的 prompt 格式化与分词路径。
  - 多数事件按位置翻译；但 `remove`/`replace` 受**前缀依赖有效性**约束：修改上下文中间的消息会使缓存后缀失效（即使后续消息未变），故翻译为**后缀失效**，受影响 KV 进入 Expired。
  - 物理翻译受 **KV 存在性**门控：只有已参与过推理的消息才有实体化 token/KV；因此在推理边界施加更新，边界之间按程序顺序串行处理事件。
- **生命周期状态与迁移（图 9）**：为每个上下文中的每个消息版本维护状态——**Pinned、Active、Suspended、Expired、Temporary、Discarded**。
  - `append` → Active；某上下文 prefill 完成后其 Active 消息 → Suspended；下次请求前参与推理的普通消息重新激活；上下文终止 → 普通消息 Expired，Pinned 保持保护；`unpin` → 回到 Suspended，若上下文已终止则 Expired。
  - `remove`/`replace`：旧版本及其后续受影响后缀消息版本 → Expired，并记录新版本供后续请求使用。
  - `fork`：父子上下文各自独立维护继承消息的状态，任一侧的内容变更只影响自身。
  - `one_off`：将已有及后续追加消息标记为 Temporary（其独占 KV 绕过复用存储）。

### 2.4 状态引导 KV 缓存引擎（§6）

- **核心思路：先剔除"确定"的，再优化"不确定"的**。生命周期状态不仅决定驱逐顺序，更决定**准入时的默认动作顺序**。
- **算法 1（状态优先 KV 准入）**：
  1. 若到来 KV 为 Temporary → 直接绕过（不进入复用存储）；
  2. 计算缺口 Δ = size(r) − 空闲容量；
  3. 依次调用 `FreeByState`：先回收 **Expired**，再驱逐 **Suspended**，再回退到 **Active**；
  4. 若到来 KV 为 Pinned，则允许与 **Pinned** 竞争；
  5. Δ ≤ 0 时准入。
- **共享 KV 管理**：同一 token 的 KV 可能被多上下文的消息版本映射，取**最高优先级的映射状态**作为驱逐决策依据；仅当所有映射版本均 Discarded 时该 KV 才可回收（例如父上下文已 remove 但 fork 子上下文仍持有 Suspended 引用，则共享 KV 保持 Suspended）。
- **Suspended 层内的排序（§6.2）**：剔除确定性情况后，残余不确定性集中在"存活但空闲"层。传统 LRU 假设"最近访问者最接近复用"，但 ReAct 中恰恰相反——新写入 KV 常进入等待期。观测显示复用并不集中在最年轻年龄：Agent-G 有 43.1% 的复用发生在写回后 1–3 s，Codex 为 46.6% 在 3–6 s，Agent-X 为 87.5% 在 2–4 s。因此 KVTether 采用**MRU（最近使用者优先驱逐）**：在高压力下优先驱逐刚挂起的 KV，保留等待更久、更接近复用的条目。
- **重要限定**：作者明确其优势来自 ReAct 执行导致的**稳定方向性趋势**，而非精确的逐条下次使用时间预测；只要缓存事件的相对顺序保持（如 FIFO），该趋势在排队拉长时仍可操作。

### 2.5 实现（§7）

- **harness 内轻量框架**：同步记录原语调用以保序，异步按序导出事件，不阻塞关键路径。
- **服务端生命周期管理器**：Python 运行时，位于 harness 与底层服务栈之间；复刻 LLM 引擎的 prompt 格式化与分词以做消息到 KV 的独立翻译；在 LLM 调用上插入拦截，转发调用 ID 与上下文 ID 给缓存引擎。
- **多级缓存引擎**：横跨 GPU HBM、主机内存、远程内存；区分"全局生命周期控制"与"分层缓存副本"；原生引擎用 CUDA 做本地 GPU-CPU 搬运、MoonCake 做跨节点传输，并提供代理到 LMCache / MoonCake Store 的兼容路径。

## 3. 实验设计：数据集 / 场景、Benchmark 与对比方法

- **工作负载（3 个）**：
  - **Codex**：自部署的软件工程智能体（基于 Codex）运行 **TerminalBench**，采集轨迹，LLM 请求由 DeepSeek-V4-Pro 服务。
  - **Agent-X / Agent-G**：某大型云厂商部署的两个生产编码智能体，合计峰值超 **27,000 个活跃会话**，每个 agent 采集 **400 条轨迹**。
  - 请求特征跨度大：3–127 轮 LLM 调用、9K–374K prefill token

- 请求特征跨度大：3–127 轮 LLM 调用、9K–374K prefill token、单轮工具执行时长从毫秒级到数分钟级，且不同会话间的并发与到达模式高度非平稳。
- 所有工作负载均在**相同硬件与相同底层服务栈**上回放，以保证与 LMCache、MORI 等基线的可比性。

- **Benchmark 与评价维度**：
  - 主指标为 **KV 命中率（KV hit rate）**与 **prefill 占端到端执行时间的比例**，前者衡量缓存有效性，后者衡量其对延迟的实际影响。
  - 辅以 **TTFT / 端到端延迟、吞吐（tokens/s 或 requests/s）** 以及 **缓存占用与驱逐行为统计**。
  - 引入两个"失效"诊断指标以解释命中率差距：**zombie 占比**（逻辑已死亡但物理驻留的 KV 比例）与 **错误方向驱逐比例**（以 Belady 最优为参照，驱逐了"更接近复用"的条目所占比例）。

- **对比方法**：
  - **LMCache**：主流开源 KV 复用存储，基于前缀共享与 LRU 类策略。
  - **MORI**：以请求空闲度（idle-ness）排序的 KV 管理方案，代表"更贴近 agent 语义但仍不显式感知生命周期"的一类工作。
  - **理论最优（Belady / oracle）**：作为上界参照，用于量化剩余优化空间（论文报告理论最优命中率约 82.8%）。
  - 消融中进一步对比 **KVTether 去掉状态信息（退化为纯 MRU）**、**去掉 MRU（仅状态引导）** 等变体，以分离两类机制的贡献。

## 4. 主要实验结果与核心发现

- **命中率显著提升**：KVTether 将实测 KV 命中率从 LMCache 的 28.1%、MORI 的 39.8% 提升至接近理论最优区间，缩小了与 82.8% oracle 上界的大部分差距；在三个工作负载（Codex、Agent-X、Agent-G）上均保持一致的领先。
- **prefill 时间占比下降**：prefill 占总执行时间的比例由 37.6%（LMCache）/ 34.6%（MORI）显著降低，直接转化为端到端延迟与 GPU 计算量的节省。
- **zombie 与错误方向驱逐同时被抑制**：显式生命周期状态使 Expired/Temporary 类 KV 不再长期占用容量（缓解 zombie），MRU 排序则纠正了"最近写入最可能复用"的错误假设（缓解错误方向驱逐）。二者共同解释了命中率提升的来源。
- **共享 KV 与 fork 场景的正确性**：在多上下文共享前缀、fork 出临时上下文（如 compaction、safety guardian）的场景下，KVTether 未因共享 KV 的误回收而破坏后续复用，验证了"取最高优先级映射状态"这一规则的必要性。
- **消融结论**：仅靠状态信息或仅靠 MRU 都无法达到完整方案的效果，说明"先剔除确定性死亡/临时 KV，再在存活空闲层内做方向性排序"的两阶段设计是必要的；同时表明收益主要来自**结构性的生命周期信息**，而非对下一次访问的精确预测。
- **鲁棒性**：在请求排队拉长、并发波动等压力条件下，KVTether 的相对优势保持稳定，支持作者关于"稳定方向性趋势而非精确预测"的论断。

## 5. 贡献与创新点

- **问题识别**：首次系统刻画了 ReAct 智能体服务中应用层**消息级生命周期**与底层**KV 物理驻留**之间的**语义鸿沟**，并用生产 trace 量化了 zombie KV 与错误方向驱逐两类失效及其代价。
- **抽象设计**：提出**语义原语模型**（8 个消息级原语），在保持跨 harness 通用性的同时具备足够的表达力，覆盖增删改、fork/spawn 与 one-off/pin/unpin 等生命周期声明。
- **机制创新**：给出**事件驱动的生命周期状态机**（Pinned/Active/Suspended/Expired/Temporary/Discarded）与**状态引导的缓存引擎**（状态优先准入 + Suspended 层 MRU），并正确处理共享 KV 的多版本映射。
- **工程落地**：实现横跨 HBM、主机内存与远程内存的多级缓存引擎，兼容 LMCache / MoonCake，且导出路径不阻塞 harness 关键路径，具备生产可用性。

## 6. 局限性

- **依赖 harness 配合**：有效性以应用层愿意接入 SDK 并如实上报原语为前提；对无法修改的第三方 harness 需依赖适配或推断，可能退化。
- **MRU 的适用边界**：MRU 优势建立在 ReAct 执行导致的稳定方向性趋势上，对于非 ReAct、复用模式接近经典 LRU 假设的负载，该排序可能不再占优。
- **状态翻译开销与一致性**：服务端需复刻 LLM 引擎的 prompt 格式化与分词路径，一旦引擎侧模板或分词行为变化，翻译映射需同步维护，存在工程耦合风险。
- **评估范围**：实验集中于编码类智能体与特定模型/服务栈，尚未覆盖多模态、非编码或强多租户隔离等场景，泛化性有待更多验证。

## 7. 对后续研究的启示

- **生命周期信息应作为一等接口**：与其在下游用启发式猜测 KV 死活，不如在应用层显式声明，这一思路可推广到调度、批处理、卸载与跨节点迁移等更多决策点。
- **区分"确定性"与"不确定性"分层优化**：先用结构化信息剔除确定死亡/临时的对象，再对残余集合做方向性排序，是一种可复用的缓存治理范式。
- **重新审视 agent 场景下的经典假设**：LRU 等基于"近期访问≈近期复用"的假设在工具等待、子智能体协调等场景下可能系统性失效，值得在更多系统层（如调度器、内存管理）重新检验。
- **标准化潜力**：8 个原语有望演化为 agent 框架与推理引擎之间的通用生命周期协议，推动跨厂商的缓存互操作。
