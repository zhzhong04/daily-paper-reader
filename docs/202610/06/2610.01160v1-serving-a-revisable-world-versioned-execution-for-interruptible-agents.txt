ABSTRACT
LLM agents revise running tasks when users change instructions, tools fail, or new information changes a plan.
Today’s servers express a revision as aborting old requests and submitting replacements. Yet the old execution’s
buffered output and outstanding work must stop affecting the application, while completed KV state may still be
useful to its replacement. Handling these obligations separately can leave obsolete effects publishable and force
the successor to rebuild valid state.
We present RETIRE, a serving control-plane redesign around versioned execution. Requests own scheduling and
memory resources; execution versions own authority, the permission to publish output or install state for the
current execution. RETIRE first revokes obsolete work, then bounds its remaining execution and certifies the
completed prefix its successor can inherit. The successor runs from that state while isolated old resources are
reclaimed asynchronously. This unifies fast invalidation and selective preservation in one version transition.
We implement RETIRE in vLLM across output publication, GPU execution, KV handoff, tiered recovery, and
distributed and multi-tenant serving. Correctness experiments verify current-version output and valid state
inheritance across these paths. Combining invalidation with inheritance reduces revision-to-successor time-to-
first-token by a median 17.1% in controlled paired experiments. A replay of recorded coding-agent interruption
arrivals emits no obsolete output and keeps every final version progressing through repeated revisions. RETIRE
turns abort-and-restart into a coordinated handoff that stops obsolete work quickly and preserves useful work for
its successor.

INTRODUCTION
Consider a coding agent implementing an API change.
While the model is processing repository context, the user
asks it to keep the existing API and change only the imple-
mentation. The agent runtime replaces the plan. Output
buffered for the abandoned plan must no longer reach the
user, and its remaining model work has become obsolete.
Yet the repository context shared by both plans still has
value: its completed KV prefix can accelerate the revised
execution. One interruption therefore asks the server to stop
obsolete work and preserve useful work at the same time.
Such revisions are a normal part of agent execution. A tool
failure can invalidate a plan, and a fresh observation can
replace the assumptions behind ongoing reasoning. The
agent runtime chooses the response and constructs the re-
vised context. Here, authority means permission for output
or state updates to affect the application or the successor.
Once the runtime decides to replace live work, the server
must carry out one decision:

We call the replacement of a live execution an agent in-
terruption. Figure 1 shows the division of responsibility:

Requests allocate resources; versions determine author-
ity.
A request tells the server what to schedule and which
resources to account for. An execution version tells it which
results may still become visible. A scope groups the work
that the runtime replaces together, including multiple re-
quests when they belong to the same abandoned plan. Once
that plan is replaced, its requests can still own buffers and
GPU allocations even though their results have lost author-
ity. Conversely, their completed common-prefix state can
remain useful to the successor.

The request-centric serving stack couples these roles. It
admits, schedules, streams, and accounts for KV ownership
by request or sequence. PagedAttention makes the resource
unit concrete: each active sequence has a logical block table,
even when physical blocks are shared (Kwon et al., 2023).
Aborting a request changes its scheduling status, but the
revision also has to reach output already queued for delivery,
GPU work already issued, and state registered for reuse or
transfer. Caching and tiering extend those objects’ lifetimes
and increase the value of coordinating their handoff (Zheng
et al., 2024; Gao et al., 2024; Yu et al., 2025; Gao et al.,
2025; Qin et al., 2025).
A revision can pay twice.
Coarse abort-and-restart spends
time on work that has become obsolete, then repeats useful
work when the successor starts cold. Figure 2 shows the
two delays: waiting for the predecessor to reach a stopping
boundary, and rebuilding the shared prefix. Faster retirement
reduces the first delay; keeping a valid prefix reduces the
second. Reusing that prefix requires a writer and ownership
boundary so old work cannot subsequently alter it. The serv-
ing system must coordinate cancellation and preservation
around the same version decision.
The consequences appear at multiple boundaries in vLLM.
Across 18 request-abort trials, consumers receive 170 prede-
cessor tokens in aggregate after supersession. A long-prefill
replacement waits 3.21 seconds for the next server boundary.
State handoff adds a third obligation: selecting the com-
pleted prefix whose contents and ownership remain valid.
Together, these observations motivate a control plane that
makes one version decision govern publication, retirement,
and inheritance.
A versioned handoff.
We present RETIRE, a redesign of
the serving control plane around versioned execution. RE-
TIRE first makes obsolete work unable to publish new effects,
then hands its successor only state that satisfies the reuse
contract. Its organizing rule is revoke first, preserve sec-
ond. ADVANCE revokes the old version; FENCE bounds
its remaining work and closes writers; ALIGN certifies
the reusable prefix; RESUME launches the successor; and
RECLAIM releases isolated old resources asynchronously.
Reclamation stays off the successor’s critical path because
those resources no longer determine its output or state.
We implement this authority boundary throughout vLLM,
from output publication and GPU execution to KV instal-
lation, state transfer, and reclamation. The evaluation first
establishes correct publication, inheritance, and tenant isola-
tion. Combining fast invalidation with certified inheritance
then lowers paired revision-to-successor TTFT by a median
17.1% over native abort and cold restart. Under interven-
ing HBM churn, certified retention accelerates post-churn
recovery by up to 6.87×/5.07× on H100 PCIe/GB200.
Finally, replaying recorded coding-agent interruption bursts,
RETIRE publishes no obsolete output, advances every final
version, and delivers 5.53× the current-version output per
second of the best tested native quantum. Distributed and
co-tenant experiments extend the same boundary across
workers and shared resources. Versioned execution supports
both faster handoff and continued progress when another
revision arrives before cleanup ends.
This paper makes three contributions:
• Workload abstraction. We define revisable execution
through version transitions and characterize their pressure,
retirement horizon, reusable state, and scope width.
• Serving redesign. We separate request resource own-
ership from execution-version authority and coordinate
fast invalidation, certified inheritance, and asynchronous
reclamation in RETIRE.
• Implementation and evidence. We realize the design
across the vLLM serving lifecycle and establish cor-
rectness, faster recovery, and sustained progress under
recorded bursts, distributed execution, and tenant sharing.

Agents revise live work.
Benchmarks and control stud-
ies treat changing instructions, goals, and stop decisions
as recurring execution events (Wu et al., 2025; Rana et al.,
2025; Zou et al., 2026; Zhai et al., 2026; Khan, 2026). They
establish revision as a workload property: after new infor-
mation arrives, the runtime may select a replacement for
an already-running execution. The resulting decision must
reach the serving stack while old computation and output
are still in flight.
Servers carry work across time.
FastServe provides
iteration-level preemptive scheduling (Wu et al., 2026); In-
ferCept preserves state across intercepts (Abhyankar et al.,
2024); Agentix schedules agent programs (Luo et al., 2026).
Their scheduling decisions span turns, pauses, and persistent
state. Preemption retains the identity of paused work; revi-
sion is the complementary transition in which that identity
loses authority and a different successor may take over.
State outlives individual requests.
PagedAttention and
SGLang provide block and prefix sharing (Kwon et al., 2023;
Zheng et al., 2024). CachedAttention, Pensieve, HCache,
and Mooncake retain or restore conversational state across
memory tiers (Gao et al., 2024; Yu et al., 2025; Gao et al.,
2025; Qin et al., 2025), while Leyline proposes agentic KV
directives (Ma et al., 2026). This decoupling makes state
preservation valuable during revision, but matching tokens
or bytes alone cannot establish whether an in-flight writer
or transfer still belongs to the selected execution. Rollback
consistency exposes the same need to bound admissible
retained state (Zhang & Yang, 2026).
Versioned execution connects these developments through
one authority boundary. The runtime’s replacement decision
governs publication and retirement, and determines which
retained state the successor may adopt. RETIRE unifies
revocation, writer closure, state handoff, and asynchronous
reclamation in one lifecycle.
3
REVISABLE EXECUTION AS A SERVING
WORKLOAD
The coding-agent example has two execution versions: the
abandoned API change and the revised implementation
change. The runtime chooses between them; the server
must make that choice effective for every affected request
and state object. We define the serving event around this
transfer of authority.
Definition. An agent interruption at the serving
boundary replaces a runtime-selected scope at
execution version e with version e+1. Version
e loses permission to publish output or install
state; version e+1 runs from the revised context
supplied by the runtime.
3.1
The runtime selects the replacement
A scope is the work replaced together. It can contain one
model request, several requests for an abandoned branch,
or their distributed workers. An execution version is one
attempt to execute that scope. Other scopes in the same
batch keep their own authority. The runtime submits
SUPERSEDE(s, e, e+1, X′, C),
where s identifies the scope, e is its current version, e+1 is
the replacement, and X′ is the revised context. The execu-
tion contract C specifies when inherited state is acceptable,
including the numerical mode and required successor-output
equivalence against clean execution. After the switch, e+1
owns publication authority and can adopt certified prede-
cessor state. A pause retains the same authority; a terminal
cancellation has no successor.

3.3
The workload exposed to the server
The same transition can impose very different costs. Four
dimensions expose those costs to the server:
Revision pressure: arrival rate and burstiness. Another
correction may arrive before the previous version finishes
draining.
Retirement horizon: outstanding work before a safe
boundary. A long prefill or speculative step can delay its
replacement.
Successor overlap: state shared with the revised context.
A retained repository prefix can save most of a successor’s
prefill.
Scope width: requests, cache groups, transfers, and work-
ers replaced together. A distributed execution requires coor-
dinated closure.
These dimensions determine the value of finer execu-
tion boundaries, retained state, and coordinated retirement.
Across them, a successful transition has three outcomes:
1. Current output: revoked work cannot publish new ef-
fects.
2. Valid inheritance: the successor receives only state that
satisfies its execution contract.
3. Efficient handoff: useful work survives the switch, ob-
solete work leaves its critical path, and unrelated tenants
remain isolated.
The next section follows these obligations through a request-
centric server to show why resource lifetime and execution
authority need separate units.
4
FROM REQUEST-CENTRIC TO
VERSIONED SERVING
Return to the coding agent when the user changes the plan.
The runtime sends an abort for the model request represent-
ing the old plan. The scheduler can remove its future work,
but a token batch may already be waiting for a slow con-
sumer, a GPU step may still be processing the old context,
and completed repository-prefix blocks may be registered
in the cache. All belong to the abandoned execution, yet
they require different actions: suppress the output, bound
the computation, and preserve the useful prefix.
A request ID identifies resources; a version determines
whether their output or state may still affect the user or the
successor. Table 2 follows the decision through the stack.
Versioned serving makes the distinction explicit: requests
own schedulable work and allocations, while the current
scope version determines which effects can become visible.
A replacement can then revoke old publication before all
old resources are released, and inherit useful state without
keeping the predecessor authoritative.
Two costs on one critical path.
For a coarse abort fol-
lowed by cold prefill, the dominant sequential costs are the
predecessor’s remaining time to a server-visible boundary,
Ttail, and the successor’s full prefill, Tfull:
Tabort = Ttail + Tfull.
A versioned transition can replace that tail with time to a
bounded safe point, Tsafe, certify inherited state in Talign,
and prefill the remaining suffix in Tsuffix:
Tversioned = Tsafe + Talign + Tsuffix.
These decompositions expose the two levers: shorten obso-
lete work and avoid repeating valid work. When a native
prefix hit already removes recomputation, the remaining
opportunity lies in retirement and coordination. To com-
bine the levers, the server must control the following three
boundaries.
4.1
Obsolete results can escape
Removing a request from the scheduler does not retract to-
kens already queued between a worker, EngineCore, and a
slow consumer. Request completion and API publication
are different moments. The server must check the current ex-
ecution version again when delivering output, so a buffered
result from an abandoned plan cannot reach the application
after the switch.
4.2
Obsolete work can delay the replacement
Host-side cancellation cannot retract work already submit-
ted to a model worker. A long prefill, speculative step,

4.3
State handoff lacks versioned ownership
The common prompt prefix identifies candidate state for
reuse. A prefix cache can make its completed blocks avail-
able, while the transition needs a stable handoff: close pre-
decessor writers, retain the blocks until adoption, and val-
idate their ownership generation. A tiered transfer must
likewise be installed for the intended successor. Token posi-
tions, model and adapter configuration, cache layout, tenant,
and execution mode determine which state is compatible.
Rollback consistency makes the importance of bounding
retained state explicit (Zhang & Yang, 2026).
The server therefore needs both an eligibility decision and
a lifetime decision: which state may be inherited, and how
it remains available until the successor takes ownership. A
completed common prefix can be retained; an unfinished or
incompatible suffix must be recomputed. Releasing the old
request and later looking for a cache hit leaves this handoff
opportunistic: intervening requests may evict the blocks
before the successor arrives.
RETIRE connects these boundaries through one version life-
cycle. Revocation decides what may publish; writer closure
makes inheritance safe; certified handoff preserves useful
work; and isolation lets reclamation proceed after the suc-
cessor starts. Together they turn the two performance levers
into a coordinated serving transition.
5
RETIRE: A VERSIONED SERVING
CONTROL PLANE
RETIRE organizes serving around a simple rule: revoke first,
preserve second. The old plan immediately loses authority
to publish, while its useful state survives through an explicit
handoff. Resources are released after their last users finish;
only state the successor will consume must be ready before
it starts.
RETIRE assigns authority to (scope, version), with one
current version per runtime-selected scope. The implemen-
tation represents the version as a monotonically increasing
epoch. Each request, output frame, model step, and transfer
carries that identity, and publication checks it against the
scope’s current epoch. KV records also carry a generation
identifying an allocation’s ownership instance. Installation
checks that generation; writer fences and delayed recycling
protect the underlying pages.
5.1
Three guarantees across the serving lifecycle
RETIRE enforces three rules at the serving boundaries where
state becomes visible:
Current-version publication. Tokens, scheduler results,
and installed state are visible only if they belong to the
current scope epoch.
Versioned handoff. Predecessor state is consumed only
when its token prefix and execution configuration match, its
old writer is closed, and its ownership generation remains
valid. Otherwise the successor recomputes.
Retired-state isolation. Old work may finish, but it can-
not overwrite state owned by the successor or an unrelated
tenant.
Publication and isolation establish the switch; versioned
handoff recovers performance through safe inheritance. The
execution contract selects the required output comparison,
including batch-invariant execution when numerical equiva-
lence between cold and reused computation is required.
The two performance mechanisms share the same authority
boundary. FENCE shortens the predecessor tail and closes
writers; ALIGN uses that closure to separate the committed
common prefix from the obsolete suffix. If no reuse is
profitable, a cold successor bypasses physical pinning and
starts under an independent cache generation. If reuse is
profitable, only certified pages cross the version boundary.

5.3
Resume before reclamation
In the coding-agent example, the successor adopts the cer-
tified repository prefix and allocates fresh pages for its
changed suffix. Old suffix pages and buffered results are
unreachable from that successor. Their owners can drain
while the revised plan runs: old publication is revoked, and
old pages remain isolated until their writers finish.
The common prefix stays pinned until the successor adopts
it. Once adoption is verified, handoff pins are released and
the successor’s references keep those pages live. Only im-
mutable, writer-closed pages cross this boundary, allowing
preservation and cleanup to proceed under the same author-
ity decision.

A VERSIONED VLLM SERVING STACK
We implement RETIRE in vLLM 0.13.0 by carrying
(scope, epoch) through request admission, scheduling,
model execution, output publication, KV installation, and
memory transfer. Request IDs index local resources; the
scope epoch determines whether their results can become
visible.
Three changes enforce the lifecycle: publication gates reject
obsolete output, model safe points bound obsolete computa-
tion, and versioned KV ownership controls which state the
successor adopts.
6.1
Redesigning the execution lifecycle
Version-governed publication.
Every native request
maps to (scope, epoch). The server checks that authority
at scheduling and model completion, when output enters
the streaming queue, and again when the API consumer re-
ceives it. The delivery check rejects a frame whose version
was superseded while it waited in the queue.
Bounded retirement inside model execution.
An epoch
update reaches workers outside ordinary request traffic. A
safe point is a model boundary where the worker can stop
launching additional old-version work. Writer receipts es-
tablish the completed-state frontier, while KV and output
gates reject stale commits. Short decode steps already reach
model-step boundaries frequently. Long steps arm addi-
tional device predicates and bounded checks, avoiding per-
layer checking costs on short steps while shortening the tail
of a long prefill.
Versioned KV-cache transition.
FENCE snapshots the
predecessor block table before releasing its request and pins
its completed prefix. ALIGN finds the longest common
token prefix, limits it to the minimum writer-complete fron-
tier across participants, and rounds it to a block boundary
shared by every KV group. It then checks model and cache
configuration, tenant, generation, transfer identity, and nu-
merical mode. This produces the only prefix that may cross
the version boundary.
At RESUME, the successor table aliases those physical
HBM pages and allocates its changed suffix under e+1.
The old suffix loses cache reachability and is reclaimed
after its last writer; the shared prefix stays pinned through
adoption (Figure 4). Keeping this state in place avoids
copying, eviction, restoration, and recomputation. When
HBM capacity must be returned before the successor arrives,
the same certificate governs DRAM offload and restoration.
A failed certificate selects a cold, fresh-generation successor.
A restored object is installed only if its target version and
generation still match, rejecting transfers that complete after
their intended execution has been retired.
The contract extends across speculation, multiple KV
groups, memory tiers, tenants, and distributed participants;
their adapters and failure evidence appear in Appendix A.

EVALUATION
The evaluation follows the handoff from its guarantees to its
benefits. First, does the successor receive valid state while
obsolete effects are suppressed? Second, how much time is
saved by shortening old work and preserving useful state,
separately and together? Finally, can the same transition
sustain progress through recorded interruption bursts, dis-
tributed execution, and tenant sharing? Performance results
come from runs that pass the corresponding correctness
checks.

main and distributed paths; the state-handoff campaign re-

supplies heterogeneous KV groups and trace replay. Single-
GPU retirement paths use three pairs, active speculative
decode and distributed topologies use five, and state handoff
uses four paired quartets at each of nine pressure points per
platform. Co-tenant isolation uses three seeds.

Output, page digests, ownership generations, and participant
receipts thus validate one authority boundary across the
serving lifecycle. These accepted runs provide the basis for
measuring its performance.

We now move from one handoff to a sequence of revi-

and cache reuse.
This replay asks whether a transition that works once can

its predecessor has drained. Such bursts create chains of ver-

obsolete before emitting a token. Current-version goodput,

authority boundary.

8
IMPLICATIONS FOR REVISABLE
SERVING
Invalidation and preservation are complementary.
A
revision changes which work is useful, not just which re-
quest should run next. Fast invalidation stops spending
resources on the abandoned plan; inheritance reduces the
work required by its replacement. Their shared authority
boundary lets the server optimize both together. This is
the central consequence of treating revision as a serving
workload.
Authority spans objects with different lifetimes.
Out-
put queues, issued computation, and reusable state do not
finish together. A common version decision gives them one
logical boundary while allowing physical cleanup to pro-
ceed independently. Correctness depends on enforcing that
boundary wherever effects become visible, rather than on
making every object disappear at once.
Policies optimize within the invariant.
Revision pressure
changes the value of execution granularity and speculation;
prefix overlap and admission delay change the value of re-
tention. Schedulers and memory policies can respond to
these inputs while the same authority checks govern publi-
cation and handoff. Appendix A.2.2 explores this separation
through rate sweeps.
The runtime chooses; serving carries out the handoff.
The runtime selects the successor context and handles ex-
ternal actions. Serving determines when that successor can
run and which state it can inherit. This boundary lets agent
behavior evolve while publication, isolation, and efficient
handoff remain systems responsibilities.
9
CONCLUSION
Agent revisions invalidate executions but leave useful work
behind. RETIRE redesigns serving accordingly: requests
own resources, versions own authority, and one protocol
coordinates fast invalidation, certified inheritance, and asyn-
chronous reclamation. Combining invalidation and inheri-
tance reduces paired revision-to-successor TTFT by a me-
dian 17.1%. Recorded-burst replay emits no obsolete output
and advances 9/9 final versions; distributed and co-tenant
tests preserve the same authority boundary. Versioned exe-
cution makes a change of plan a coordinated handoff: retire
obsolete work and preserve useful state.

physical remapping checks pass in every trial.
