## 摘要
长上下文 LLM 智能体会累积交互历史，给 KV 缓存内存和注意力计算带来压力。尽管稀疏注意力降低了这些成本，但异构的缓存表示与工作流阻碍了与现有推理引擎的集成，而此前的稀疏服务抽象仅支持特定布局或工作流。我们提出 SparseEngine，一个从底层构建、稀疏优先的推理引擎，其共享生命周期契约让每种方法控制其 KV 表示与计算，同时与通用服务基础设施协调状态转换。SparseEngine 支持四大类共 15 种方法，并通过 Chain Cache 实现跨请求状态管理，Chain Cache 可从保留的历史中恢复 KV 驱逐方法；以及可控的 Prefix-Cache Pruning，可从选定的历史区域移除 KV，同时保留逻辑前缀匹配。在保持方法质量的同时，SparseEngine 在 KV 驱逐下实现超过 10 倍吞吐量提升，在相同并发下解码速度比 vLLM 快 2.5 倍以上，在智能体基准上实现超过 2 倍的端到端加速。代码可在 https://github.com/CURRENTF/SparseEngine 获取。

## Abstract
Long-context LLM agents accumulate interaction histories that strain KV-cache memory and attention computation. Although sparse attention reduces these costs, heterogeneous cache representations and workflows hinder integration with existing inference engines, while prior sparse-serving abstractions support only specific layouts or workflows. We present SparseEngine, a ground-up, sparse-first inference engine whose shared lifecycle contract lets each method control its KV representation and computation while coordinating state transitions with common serving infrastructure. SparseEngine supports 15 methods across four categories and enables cross-request state management through Chain Cache, which resumes KV-eviction methods from retained history, and controllable Prefix-Cache Pruning, which removes KV from selected history regions while preserving logical-prefix matching. While maintaining method quality, SparseEngine delivers over 10x higher throughput with KV eviction, over 2.5x faster decoding at matched concurrency than vLLM, and over 2x end-to-end speedup on agent benchmarks. The code is available at https://github.com/CURRENTF/SparseEngine.

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想：以"模型原生模块执行顺序"为锚的生命周期契约

- 不采用预定义工作流（如 SPIN 的 Index→Offload→Select→Retrieve→Attention），而是把不变式锚定在 **Transformer 的原生模块执行顺序**上，沿该顺序暴露细粒度钩子，让每个稀疏方法注册回调、自行组合计算工作流，**无需修改模型实现**（无需 LlamaSnapKV、Qwen3H2O 这类专用实现）。
- 契约由三部分组成：

### 2.2 三个组件

- **SparseController（细粒度生命周期钩子）**
  - 钩子覆盖 prefill 与 decode 两个阶段，扩展点包括：Step Preparation、Norm+QKV、Before Attention、After Attention、FFN/MoE+Residual、Layer-End、Step-End。
  - 由初始化时选定的 `SparseMethodRuntime` 实现方法特定回调，跨 prefill chunk、decode step、Transformer layer 组合打分、选择、状态更新操作。
  - 举例：`finish_step` 在 prefill 阶段支持 H2O 的分块驱逐与 SnapKV 在最后一个 prompt chunk 后的选择/驱逐；`build_decode_selection` 实现 Quest 的查询相关页选择；`on_layer_end` + `build_decode_selection` 使 OmniKV/DeltaKV 能跨后续层复用观测层索引。

- **CacheManager（方法自定制缓存管理）**
  - 拥有方法特定的状态与存储：定义 KV 表示、物理布局、位置映射，以及分配/写入/更新/释放操作，并维护持久化元数据。
  - 关键语义区分：**物理驱逐**（更新保留槽映射与上下文长度，把废弃槽归还分配器）vs **逻辑选择**（仅改变注意力读取哪些常驻条目）。
  - 例：SnapKV 压缩与 H2O 驱逐共同更新保留位置、方法统计与可用容量；KIVI 管理量化 KV 页、量化元数据与非量化残差区。

- **AttentionView（连接方法状态与注意力执行）**
  - 公式：`View_{ℓ,t} = BuildView(C_{ℓ,t}, I_{ℓ,t})`，`o_{ℓ,t} = Attention(q_{ℓ,t}, View_{ℓ,t})`，其中 `C` 为持久缓存状态，`I` 为被选中的 token/页标识。
  - CacheManager 依据状态与选择构造描述可访问数据及其物理布局的视图，交给兼容的注意力后端；底层状态可以是显式 KV 张量，也可以是 MLA 潜向量 + 位置状态 + 方法元数据。
  - Quest 视图含选中 KV 页，OmniKV 视图按跨层选择引用常驻 KV，DeltaKV 视图暴露按需重建的 KV。
  - 区分 prefill/decode 两类视图类型，配对物理载荷与请求索引、上下文长度、token-slot/页表坐标；重建槽在该层消费后释放，持久 KV 归 CacheManager 所有。
  - 支持 CUDA Graph：各组件提供地址稳定的缓冲区，step preparation 更新其中的槽映射、长度等可变输入。

### 2.3 调度接口

- **MemoryOracle**：调度器在 rank 0 查询方法特定的容量与预留需求。因为注意力预算不等于内存需求——Quest 可能只读少量页却保留完整缓存；驱逐方法在压缩前需临时持有 prompt KV；压缩方法需要重建空间。
- 准入公式：设 `B_j` 为资源 `j` 的剩余预算、`c_j(r)` 为请求 `r` 的预留成本，则仅当对每个上报资源 `j` 都有 `c_j(r) ≤ B_j` 时才准入，并在考虑下一请求前扣减。方法可上报多类资源（如 PyramidKV 逐层保留槽预算；DeltaKV 区分全注意力层、引用条目、保留原始 KV 并预留重建空间）。
- 每步还检查下一个 prefill chunk / decode token 的空间需求；用兼容性键把可共用同一 prefill 路径的请求分到同一批。

### 2.4 跨请求状态管理（Section 3.2）

- **Chain Cache（链式缓存）**
  - 问题：动态稀疏方法（Quest、OmniKV、NSA、DSA）保留完整 KV 历史，天然支持传统前缀缓存；而驱逐类方法（SnapKV、KVzip、H2O）丢弃条目，**违反常驻 KV 假设**。
  - 方案：`ChainCacheIndex` 把会话与其**保留的逐层 KV + 方法特定元数据 + 逻辑 token 前缀**关联。逻辑前缀在物理 KV 被移除后仍可用于匹配，续写只需 prefill 未处理的后缀，保留方法此前的缓存决策。
  - 每个会话有 `chain_id`；续写必须匹配指纹与确切的逻辑前缀边界（已处理边界排除尚未过模型的最后一个采样 token）。请求完成时链转入 idle 但 CacheManager 保留其 KV 与元数据；容量不足时按 LRU 回收。
  - 对 H2O/SnapKV 这类不同层保留不同位置、或需要 H2O 累积注意力分数的方法尤为关键。张量并行下由 driver 分发准入与牺牲计划，保证各 rank 状态转换一致。

- **Sparsity-Based Prefix-Cache Pruning（可控前缀缓存剪枝）**
  - 动机：智能体轨迹中不同区域（用户输入、工具结果、推理痕迹、输出）的 KV 效用不同，如工具响应在被摘要后价值下降。
  - 流程：应用提交完整 `token_ids` 序列与零基剪枝区间 `[L, R)`，定义 `𝒯 = {i | L ≤ i < R}`；打分策略（SnapKV 或 KVzip）在 `𝒯` 内选出保留位置并返回掩码；缓存管理器仅对无活跃引用/在途传输的 idle 块施加该掩码。
  - 形式化：设 `P` 为逻辑 token 前缀、`ℛ` 为有常驻 KV 的位置，保留选中位置 `ℐ ⊆ ℛ ∩ 𝒯` 得 `P' = P`，`ℛ' = (ℛ \ 𝒯) ∪ ℐ`。即释放被排除的物理槽但**保持逻辑前缀不变**，后续请求仍可匹配同一前缀而只复用保留的 KV。零预算即删除该区间全部 KV。
  - 剪枝后记录每个逻辑块内的保留偏移，并以剪枝记录标记受影响的续写使用压缩历史。
