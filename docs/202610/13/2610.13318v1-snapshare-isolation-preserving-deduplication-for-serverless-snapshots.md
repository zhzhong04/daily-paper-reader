## 摘要
无服务器计算的效率从根本上取决于函数的快速启动，而这一挑战正日益通过从虚拟机快照恢复来应对。然而，由于内容去重技术可能开启时序侧信道攻击，从而泄露敏感的租户数据，像 AWS Lambda 这样的生产平台转而强制在不同租户的快照之间实施严格的零共享隔离。这种隔离虽然安全，却阻碍了对公共基础设施组件进行去重，浪费了每个工作节点的缓存容量，并因低效的远程获取而加剧冷启动延迟。我们的特征分析表明，非敏感、可共享的基础设施约占典型快照内容的 70%，平均而言约占其工作集的 50%。我们提出 SnapShare，一种集群范围的快照管理系统，它协同设计存储与缓存，以在不损害敏感数据隔离的前提下利用这种共性。SnapShare 仅当快照页面的完整内容与来自提供商批准来源的页面内容匹配时，才将其归类为可共享；任何不匹配的内容都被视为隔离的私有内容。公共基础设施组件被选择性地去重，并固定在整个集群的工作节点上，而私有数据则保持严格隔离，并作为被跟踪工作集的一部分被主动获取，仅对工作集之外的页面回退到按需检索。作为 Knative 的扩展实现，SnapShare 相比传统的工作集和基于块的平台，将端到端尾部请求的减速降低了 10-29%。它还将远程存储需求降低了 39%，本地缓存占用降低了 38%，减少了网络检索负载，并将最坏情况下的获取延迟限制为原来的 1/10。

## Abstract
The efficiency of serverless computing fundamentally depends on rapid function startup, a challenge increasingly addressed by restoring from virtual machine snapshots. However, because content deduplication techniques can open timing-channel attacks that leak sensitive tenant data, production platforms like AWS Lambda instead enforce strict, zero-sharing isolation between snapshots of different tenants. While secure, this isolation precludes the deduplication of common infrastructure components, wasting per-worker cache capacity and exacerbating cold-start latency through inefficient remote fetching. Our characterization reveals that non-sensitive, shareable infrastructure accounts for roughly 70% of a typical snapshot's contents and, on average, about 50% of its working set.   We present SnapShare, a cluster-wide snapshot management system that co-designs storage and caching to exploit this commonality without compromising sensitive data isolation. SnapShare classifies a snapshot page as shareable only when its full content matches that of a page from a provider-approved source; any non-matching content is treated as isolated private content. Common infrastructure components are selectively deduplicated and pinned across the cluster's worker nodes, while private data remains strictly isolated and is eagerly fetched as part of the tracked working set, falling back to on-demand retrieval only for pages that fall outside it. Implemented as an extension to Knative, SnapShare reduces end-to-end tail request slowdowns by 10-29% compared to traditional working-set and chunk-based platforms. It also reduces remote storage requirements by 39% and local cache footprints by 38%, reducing network retrieval payloads and bounding worst-case fetch delays by 10x.
