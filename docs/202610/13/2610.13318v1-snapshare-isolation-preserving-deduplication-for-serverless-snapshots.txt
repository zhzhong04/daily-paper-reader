## Abstract 

The efficiency of serverless computing fundamentally de-pends on rapid function startup, a challenge increasingly ad-dressed by restoring from virtual machine snapshots. How-ever, because content deduplication techniques can open timing-channel attacks that leak sensitive tenant data, pro-duction platforms like AWS Lambda instead enforce strict, zero-sharing isolation between snapshots of different ten-ants. While secure, this isolation precludes the deduplication of common infrastructure components, wasting per-worker cache capacity and exacerbating cold-start latency through inefficient remote fetching. Our characterization reveals that non-sensitive, shareable infrastructure accounts for roughly 70% of a typical snapshot’s contents and, on average, about 50% of its working set. We present SnapShare, a cluster-wide snapshot manage-ment system that co-designs storage and caching to exploit this commonality without compromising sensitive data isola-tion. SnapShare classifies a snapshot page as shareable only when its full content matches that of a page from a provider-approved source; any non-matching content is treated as iso-lated private content. Common infrastructure components are selectively deduplicated and pinned across the cluster’s worker nodes, while private data remains strictly isolated and is eagerly fetched as part of the tracked working set, falling back to on-demand retrieval only for pages that fall outside it. Implemented as an extension to Knative, Snap-Share reduces end-to-end tail request slowdowns by 10–29% compared to traditional working-set and chunk-based plat-forms. ## 1 Introduction 

Serverless elasticity is limited by how fast function instances are created during workload changes [8]. Platforms such as AWS Lambda [6] accelerate function instance cold starts by restoring virtual machines from snapshots. As Figure 1 illustrates, workers cache snapshot chunks locally and fetch missing ones from remote storage. The capacity of this cache determines how much state can be reused during a cold start. However, snapshots of different functions contain duplicate copies of common infrastructure data found in popular con-tainer and base VM images. Duplicate snapshot data wastes remote storage and displaces useful state from worker caches, forcing more cold starts and remote state retrieval. Production platforms store VM snapshots encrypted in remote storage [6], but encryption alone does not prevent deduplication-induced disclosure: reusing a victim’s cached content can change an attacker’s retrieval time, revealing the presence of sensitive state or cryptographic keys [18, 42, 45, 50]. Production platforms thus take a conservative isolation approach that forces separate copies across secu-rity domains [3, 25], treating all snapshot state (including

• A classification-driven storage and cache co-design de-livering 39% lower remote-storage requirements and 38% smaller cache footprints than Sabre, with 10–29% lower aggregate tail request slowdown than safe baselines. Stor-age and cache footprints remain within 6% and 3% of un-safe fully deduplicated baseline, respectively. Even without container-image sharing, the system reduces cache foot-print by 31% relative to Sabre [31].

2.1 Duplication and Local Cache Efficiency 

Serverless platforms create new instances as demand grows. Functions are commonly deployed as container images and executed in lightweight VMs such as Firecracker [14], with image contents made available through the VM’s filesys-tem [1, 20]. A snapshot captures initialized guest memory and virtual disk state, avoiding repeated OS and application startup. As Figure 1 shows, the selected worker retrieves snapshot content through its local cache and fetches miss-ing state remotely. Local cache contains snapshot content organized in chunks, pages, or working sets [15, 47]. 2

In production platforms, upon a cold start, the system retrieves state in chunks [4, 16], potentially transferring un-accessed pages alongside accessed ones. REAP [47] and FaaS-nap [15] reduce this overhead by recording and coalescing 

working-set pages for eager retrieval. However, each tenant’s working set still contains duplicate copies of the same infras-tructure. Providers also limit snapshot-retrieval bandwidth to leave capacity for application traffic [3], making avoidable remote fetches particularly undesirable. Duplication consumes capacity in both remote storage and worker caches. Figure 4a compares storage of a sys-tem with no cross-snapshot deduplication against a system with unrestricted full deduplication: duplicate copies account for 43.9% of the nonzero page content. Full deduplication eliminates these copies but also shares private content; we use full deduplication as an unsafe oracle for estimating the capacity-saving opportunity, not as a deployable policy. On a worker, duplicate copies compete with other func-tions’ working sets for a fixed cache budget. As requests alter-nate among functions, admitting one working set can evict another despite their common content, causing repeated evic-tion and refetching. 2.2 The Measured Opportunity for Selective Sharing 

Using the same methodology (§4.1) as in Figure 2, we ex-amine recurrence within each source category by captur-ing page accesses using userfaultfd . The base snapshot is captured before adding the function image; rootfs and image references contain the corresponding filesystem con-tent. Unmatched content is labeled Rest ,3 independently of whether a page belongs to the working set or the lazy re-mainder. We classify content as ubiquitous if it appears in all tested functions, occasional if it appears in multiple but not all functions, or unique if it appears in only one. 2.3 Security Model for Snapshot Sharing 

Our security model focuses on confirming private snapshot content through cross-tenant deduplication. We trust the provider, its snapshot service, and its reference-approval policy. An adversarial tenant can execute arbitrary code in its own VM, influence its snapshot contents, and measure timing while co-located with a victim on the same worker. It cannot directly read victim memory or internal provider cache metadata. An attacker can place candidate content in its snapshot and use the timing difference between local reuse and remote retrieval to infer whether a victim populated a matching cache entry. Such confirmation-of-presence attacks [18, 42, 45, 50] motivate production restrictions on cross-domain memory sharing [19, 25, 40]. Encryption alone does not hide observable reuse. Private snapshot content must remain tenant-separated even when its bytes match; reuse by the owning function remains permitted. Our model permits disclosure of the pres-ence or use of approved content, which the operator must deem acceptable. Container-image sharing [20] motivates this boundary, but does not establish protection for arbi-trary guest-memory access patterns. Secrets embedded in approved artifacts and secret-dependent runtime accesses are outside the scope of this work and require exclusion or additional safeguards. We do not claim protection against all shared-hardware or resource-contention timing channels; conservative approval and private treatment by default are explicit assumptions. These observations motivate separating sharing eligibility from retrieval granularity. Approved infrastructure can be stored once and common components retained locally, while private content remains tenant-separated. Independently, working-set profiling determines which pages to retrieve eagerly. SnapShare carries these decisions through its storage layout, worker caches, and restoration path, with sharing eligibility governed by the provider’s policy.

## 3 SnapShare 

The characterization in §2.2 motivates co-designing stor-age and cache layouts that enable reuse of approved infras-tructure content, retain tenant identity for private content, and independently use working-set profiles to choose ea-ger rather than lazy retrieval. SnapShare incorporates these decisions through three design principles: 

• Content-Match Classification over Opaque Chunks: 

Rather than treating snapshot memory as an opaque blob, SnapShare compares each page’s complete content against provider-approved sources. Only exact matches are shared; all non-matches are private. 

• Selective Sharing: By decoupling the public data from the private state, SnapShare allows non-sensitive compo-nents to be aggressively deduplicated and pinned across worker nodes, while maintaining strict, function-exclusive isolation for sensitive components. 

• Integration with Profile-Guided Fetching: SnapShare incorporates working-set coalescing as in REAP [47] and FaaSnap [15] to retrieve entire working sets of pages effi-ciently at once, with individual 4 KB fetches on demand for the remainder. At a high level, SnapShare operates across both the con-trol plane and the data plane. In the control plane, an offline classifier partitions the snapshot data into two dimensions (Figure 6): exact content matches against provider-approved sources and access patterns. A page is Shared only if its complete content exactly matches a page from an approved source; every non-matching page is Private . Profiling identi-fies pages accessed during initialization and initial requests, as in prior works [15, 47], that are coalesced into Working-Sets that optimize retrieval; the remaining pages ( Lazy ) are fetched on-demand at the page-level granularity. In the data plane, this classification dictates the physical layout of both 

Remote Storage and the worker local caches (see Figure 7). During a cold start, the local Controller checks the cache for the shared components and orchestrates the targeted retrieval of the missing private components. A Page Fault Handler then utilizes userfaultfd (uffd ) to map both the cached shared state and the fetched private state into the VM’s memory, allowing execution to resume once the re-quired state is available.

To precisely capture the mem-ory access patterns, a local profiling agent monitors the VM’s guest memory using userfaultfd (uffd ). As the VM initial-izes the language runtime and loads the application code, every access to an unmapped memory page triggers a page fault, which the agent intercepts and logs. To record the working set for the profiling requests, the platform then routes a series of initial requests, such as developer-provided test payloads or synthetic health probes, to the running function [15, 47] The agent continues to trace all uffd faults during this request-serving window. The ag-gregate set of all pages faulted in during both the initializa-tion and the initial execution phases is explicitly recorded; these observed pages define the function’s profiled Working Set . Later requests may access additional pages, which are served on demand. Once recorded, the offline classifier computes an MD5 digest over each non-empty snapshot page and compares it with the digests of provider-approved reference pages, in-cluding the base snapshot and rootfs. The implementation uses equal MD5 digests as its page-content match criterion. Providers may also approve the exact contents of selected libraries or container images. The classification tests the snapshot page’s current contents, not which image origi-nally supplied it: only a page whose full content matches an approved source page is tagged Shared ; every unmatched page is tagged Private , including the pages initially supplied by a container image whose modified contents no longer match approved references. Second, pages accessed during the recording phase are tagged as the Working Set , while the unaccessed remainder is tagged as Lazy .

Working Sets for Eager Loading: Following prior profile-guided retrieval designs [47], the recorded working-set pages are coalesced into files that preserve their shared or private classification. Coalesced working-set transfers amortize re-trieval overhead without fetching surrounding pages merely because they share a chunk. The profile predicts which pages to load eagerly; accesses outside that profile use the lazy path. 

Lazy Pages for On-Demand Fetching: The pages that are not accessed during the recording phase are not coa-lesced. Instead, they are stored and managed at the granular-ity of individual 4 KB pages. Because these pages fall outside the predicted working set, they are fetched on demand if a post-restore page fault occurs, limiting transfer size without requiring the profile to cover every subsequent access. 

3.3 Co-designed Cache and Storage Layout 

To leverage the classifier output and effectively apply selec-tive sharing and dual-granularity fetching, SnapShare offers a co-designed storage and caching hierarchy (see Figure 7). Sharing eligibility is determined from snapshot-page con-tents before compression. On a cold start, the worker node overlaps transfer with decompression, so it must extract memory contents before loading them into guest memory. Compression changes the storage and transfer represen-tation, not a page’s shared/private ownership or working-set/lazy classification. 

3.3.1 Remote Storage. The centralized repository is split into Working Set Storage , holding the coalesced files for the restoration path, and Lazy Pages Storage , holding individual pages for lazy retrieval. Shared lazy pages use content-based identifiers to enable reuse across snapshots; identifying equal content must satisfy the classifier’s content matching con-tract. Private components, however, are indexed alongside their unique tenant and function version identifiers to guar-antee tenant-level isolation. In sum, the remote storage lay-out is logically divided into four distinct sections: Shared Working Sets, Private Working Sets, Shared Lazy Pages, and Private Lazy Pages. 

3.3.2 Worker Local Caches. On each worker node, the local cache mirrors the remote structure but is logically par-titioned based on content provenance. Crucially, SnapShare maps guest memory via userfaultfd (uffd ), hence the lo-cal cache operates entirely in user space. This architectural flexibility allows the local agent to implement a custom, provenance-aware caching/eviction policy: 

Shared partition: stores content approved for cross-tenant reuse. The controller pins common base-snapshot and rootfs components to retain their reuse across functions. In our measurements, this pinned base state occupies less than 1% of cache capacity; this is a workload-specific footprint, not a bound on an arbitrary approved registry. 

Private partition: stores every page that does not ex-actly match an approved source page, including sensitive, application-specific pages, and unapproved libraries. These pages remain strictly isolated per function. Private working sets are managed with LRU eviction under cache pressure, while pinned shared components remain resident. Sharing approval determines whether content may be reused across tenants; pinning separately determines which approved com-ponents are retained. 

3.3.3 Restoration Flow. During a cold start, the controller checks which shared and private working-set components are resident and retrieves the missing components from re-mote storage. The page-fault handler restores the working set from these cached files. Subsequent accesses outside the recorded working set trigger individual page fetches through the local cache, with remote retrieval on a miss. Shared con-tent remains eligible for cross-tenant reuse; private content retains its tenant identity throughout this path. 

3.4 Enforcing the Sharing Boundary 

Our security model (§2.3) defines the trusted provider, the attacker’s capabilities, and the permitted leakage. SnapShare enforces that boundary through hash-based matching against approved references and tenant-scoped identifiers for private content. Equal private pages are not reusable across tenants; approved pages may be shared per provider policy. Source approval does not establish that an artifact con-tains no secrets or that its run-time accesses are secret-independent. Components with these risks require exclu-sion or additional safeguards, consistent with §2.3. Screen-ing tools [26, 30, 51] may inform that policy, but are not protections established by the page classifier itself. We emphasize that SnapShare is intended for use by op-erators as a framework for defining dynamic policies that determine which components are safe to share. Operators

can revise the registry of approved reference content as their security assessment changes. If a newly disclosed vulner-ability makes a component’s presence sensitive, operators must withdraw its sharing eligibility. Enforcing that pol-icy requires handling existing cached copies and snapshot references as well as future classifications. A possible re-vocation procedure is to disable cross-tenant cache reuse for the affected content while regenerating snapshot meta-data to point to tenant-private copies. This procedure should close the possible timing channel attack nearly instanta-neously. We evaluate both image-sharing policies: SnapShare includes deduplication of container-image content, whereas SnapShare- excludes it, as the lower and upper bounds of possible policies. The most restrictive image-sharing pol-icy leads to only a 10% increase in cache size (§4.3.1); the tail-slowdown comparison appears in §4.2. These compar-isons quantify the performance cost of a stricter policy, not revocation correctness or latency. 

3.5 Implementation 

We implement SnapShare atop vHive [47], extending its Knative and Kubernetes infrastructure. Function sandboxes execute as Firecracker MicroVMs [14]. We bypass Knative’s standard container initialization, redirecting cold-starts di-rectly into our custom snapshot retrieval pipeline. 

Controller: We modify Knative’s Activator to intercept cold-start requests and route them to our custom node-level controller. Written in ∼3,000 lines of Go, the controller or-chestrates the control-plane restoration logic and executes the offline Classifier and the coalescer routine. The controller has no state that cannot be recovered from the global cluster state, making it easy to reconstruct after failures. 

Remote Storage: We build the centralized repository using MinIO. To optimize the high-throughput, small-I/O workload required for serving individual 4 KB pages, we format the underlying storage nodes with the XFS filesystem, which empirically outperformed standard ext4 in our small-object retrieval evaluations. We set up remote storage to provide ms-scale chunk retrieval latencies, comparable to datacenter/AZ-level storage tier used for snapshots in AWS Lambda [20]. We apply compression to all of the content in the remote storage to match the storage savings and network transfer performance to match state-of-the-art works [31]. 

Local Cache: The node-level cache runs as a user-space daemon managing NVMe drives. As designed in §3.3, the daemon explicitly pins shared components. Production en-vironments exhibit extremely low cardinality for the base state, 4 thus this pinned shared state consumes a negligible

Page Fault Handler: Implemented in ∼1,000 lines of Go, the handler interfaces with Firecracker’s userfaultfd API. During eager restoration, it supplies decompressed working-set page contents to guest memory. For lazy accesses, it resolves faulting guest addresses through the recipe metadata and obtains the required page through the cache or remote retrieval path. 

## 4 Evaluation 

We evaluate SnapShare to demonstrate that selective, struc-tural snapshot deduplication enables rapid serverless cold-starts without compromising tenant isolation. Our experi-ments focus on answering thee main questions. First, what is the end-to-end tail latency and local cache hit efficiency of-fered by SnapShare (§4.2)? Second, what is SnapShare’s stor-age impact and performance breakdown during a cold-start (§4.3)? Third, validate working set estimation and measure how sensitive is SnapShare to network bandwidth (§4.4)? 

4.1 Methodology 

Hardware and Software Setup: We evaluate SnapShare on a CloudLab [7] cluster comprising 10 c6620 bare-metal nodes, except for latency and footprint profiling experiments, which are performed on a single worker and a single MinIO node. Each node is equipped with a 28-core Intel Xeon Gold 5512U (Emerald Rapids) processor clocked at 2.1 GHz, 128 GB of DDR5 RAM, and a 780 GB NVMe SSD. To accurately mimic a multi-tenant production cloud environment—where network bandwidth must be strictly provisioned to guarantee perfor-mance for user logic—we throttle the 100 Gbps NICs to 10% (10 Gbps) for all snapshot state downloads, unless otherwise specified. For the compression comparison in §4.4.2, we use a phoenixNAP [12] s5.x6.c3.medium bare-metal instance equipped with a 24-core Intel Xeon 6527P processor clocked at 2.1 GHz with SMT disabled, four Intel IAA devices, 256 GB of DDR5 memory, and two 2 TB NVMe SSDs. Worker nodes run Ubuntu Linux 24.04 (kernel v6.8). The cluster infrastructure is orchestrated using vHive v1.8.1, with Knative v1.13 running on Kubernetes v1.29. Re-maining on-demand page faults are served as individual 4 KB granularity. 

• Full-Dedup: A system that employs full deduplication, representing prior works [36, 41] and estimating best-case performance. By construction, it does not satisfy our secu-rity model (§2.3), acting as an upper bound for performance.

4.5 Summary and Discussion 

SnapShare resolves the tension between rapid instantiation and strict tenant isolation. Selective global deduplication re-duces remote-storage requirements by 39% and local-cache requirements by 38% relative to Sabre . It reduces mean net-work retrieval volume by 56% and improves end-to-end tail slowdown by 10% over Sabre and 29% over Chunks .Unlocking these efficiencies requires acknowledging op-erational boundaries. While SnapShare’s offline profiling effectively coalesces working sets for idiomatic microser-vices, highly dynamic monoliths (e.g., JVM frameworks) may miss code paths during deployment-time probes, increasing on-demand remote fetches. This fragility can be mitigated in production via adaptive asynchronous profiling [4], which samples live page faults to seamlessly update working sets in the background without penalizing the critical path. Additionally, maximizing cache density necessitates a nu-anced threat model. SnapShare structurally isolates sensi-tive tenant data but accepts execution metadata leakage by permitting timing channels on globally deduplicated, non-sensitive infrastructure (e.g., the guest OS). While an adver-sary could in theory infer that a co-located victim is using a non-sensitive infrastructure component, this trade-off is necessary for microsecond-scale efficiency and mirrors the industry-accepted standard of deduplicating public container layers in multi-tenant public clouds [20]. 

## 5 Related Works 

Extensive research has focused on reducing serverless cold-starts. This section explores the main areas of prior work, highlighting the gap that SnapShare addresses. 

Optimizing the Execution Environment: A significant body of work has focused on minimizing serverless cold-starts by re-architecting the underlying execution environ-ment. This includes developing lean, serverless-tailored hy-pervisors such as Firecracker [14] and gVisor [9], which strip away unnecessary OS overhead to reduce boot times. Other approaches leverage specialized unikernels [34] or lightweight container runtimes like RunD [32] to further accelerate sandbox initialization. Alternatively, systems like Faasm [44] and Hydra [29] introduce concurrent sandboxes that execute multiple invocations within a single process to minimize isolation costs. However, across all of these exe-cution environments, memory snapshots have emerged as the mechanism of choice to bypass application-level initial-ization and further reduce cold-start latency. While these execution frameworks drastically reduce the time to provi-sion a sandbox, they do not resolve the cache efficiency issues and snapshot fetching overheads associated with managing massive application states. In sum, environment-level im-provements are orthogonal but complementary to the secure snapshot deduplication mechanism proposed by SnapShare. 

Optimizing Snapshot Restoration: Another line of work introduces various snapshot optimizations to accelerate state initialization by mitigating I/O bottlenecks during the restore process. Systems like REAP [47] coalesce memory work-ing sets to improve spatial locality during fetch operations, while FaaSnap [15] combines this with on-demand paging. Remote and local fork architectures, such as SEUSS [21], Cat-alyzer [24], AFaaS [22], and MITOSIS [49], similarly deliver memory pages on-demand to overlap function execution with data transfer. Additionally, Sabre [31] further optimizes the data movement pipeline through hardware-accelerated decompression, which we used in our evaluation §4.4.2. Cru-cially, to accelerate restoration, these systems inherently rely on duplicated state—either by maintaining warm in-stances for forking or by storing per-function working sets. SnapShare can directly improve the memory or storage re-quirements of such systems by deduplicating the common infrastructure without sacrificing sensitive state isolation. 

Snapshot Deduplication and Security: A third line of work optimizes the remote storage layer by deduplicating snapshot data. Because many serverless functions share com-mon base images, language runtimes, and libraries, their memory snapshots contain a large amount of redundant data. Systems such as SnapStore [36], SnapBPF [37], and TrEnv [28] capitalize on this redundancy by implementing chunk-based deduplication to minimize the storage footprint in the remote registry, enabling worker nodes to sparsely re-trieve only the necessary memory pages in a single, highly ef-ficient network I/O operation. However, traditional content-based deduplication is fundamentally unsafe in zero-trust, multi-tenant environments: memory deduplication can intro-duce cross-domain side channels that let a co-located tenant

confirm the presence of specific content [18, 45, 50]. Accord-ingly, production systems such as Firecracker recommend disabling memory deduplication when strong tenant isola-tion is required [25]. Other approaches retain deduplication while limiting cross-domain leakage, e.g., VUsion [35] and Slicedup [48], while later work revisits the security of same-domain deduplication [23]. Closer to our setting, CPC [33] coordinates a shared page cache across serverless functions, and UPM [39] propose user-guided page merging for server-less memory deduplication; both rely on functions or tenants to supply hints about which pages are safe to share. Snap-Share addresses this gap directly: it permits deduplication only when a page’s complete content exactly matches a page in a provider-approved source—without requiring tenant hints or attempting to infer historical provenance from the page content—thereby preventing private snapshot pages from ever being shared across tenants. 

## 6 Conclusion 

SnapShare selectively deduplicates only snapshot pages whose complete contents exactly match provider-approved infras-tructure sources, while strictly isolating all other, tenant-specific data as private. This conservative content-match rule enables high cache density and storage deduplication without sacrificing sensitive data isolation. Implemented as an extension to Knative, SnapShare reduces remote-storage requirements by 39% and local-cache footprints by 38% rela-tive to the tenant-isolated Sabre baseline, closely matching the efficiency of an idealized unsafe full-deduplication de-sign (within 6% and 3% for storage and cache, respectively). These savings translate into a 6.8 × reduction in cold-start fetch latency over chunk-based systems like AWS SnapStart, and a 10–29% reduction in end-to-end tail request slowdown relative to safe baselines.
