## Abstract 

Large-scale data-intensive workloads powered by iterative graph or machine learning processing have an insatiable demand for memory due to the continuous generation of new intermediate data. Although existing caching strategies strive to keep performance-critical data in memory, they often fail in practice because they are limited to node-local memory management and assume high node availability. In this paper, we introduce ShoreKeeper , a framework that max-imizes execution efficiency by treating cluster-wide mem-ory as a unified, elastic pool. ShoreKeeper employs a global optimization model that maps distributed dataflows into a single graph abstraction to minimize the recovery cost of data evicted from cache across the cluster. To handle mem-ory working sets and cluster capacities that fluctuate over time, ShoreKeeper employs a graph-pruning technique that permits the fast refinement of the caching plan. These opti-mizations allow ShoreKeeper to work seamlessly whether de-ployed on highly available VMs or cost-effective preemptible instances in the cloud. Our experiments show that Shore-Keeper consistently outperforms state-of-the-art systems. 

## 1 Introduction 

Numerous large-scale data-intensive workloads synthesize models to characterize intricate real-world phenomena. For example, structural graph analysis uncovers influential nodes based on the density and quality of their incoming connec-tions within massive networks [47]. Similarly, probabilistic forecasting or recommendation systems leverage various machine learning algorithms to identify latent relational pat-terns within vast datasets [13, 36, 37]. Such workloads rely on iterative model refinement, with more iterations leading to a higher model accuracy [16, 24, 32, 42]. Modern distributed processing frameworks typically express this refinement pro-cess using a dataflow-based execution model [14, 25, 29, 69] that expands incrementally as new computational iterations are initiated and generate downstream data blocks .In-memory caching is vital for iterative data processing because it eliminates recovery costs for intermediate data blocks accessed across iterations. However, such computa-tions constantly inflate the volume of intermediate data as they progress through the dataflow, often straining available memory resources [18, 57]. When faced with memory short-age, an effective caching strategy must navigate a complex trade-off between the execution gains of retaining individual data blocks and the recovery costs—via recomputation or disk I/O—incurred if those blocks are evicted. Earlier caching policies such as least reference count (LRC) [67] and most reference distance (MRD) [48] bypass this complexity simply by exploiting block dependency information exposed in the dataflow. A more recent system, Blaze [57], accounts not only for dynamic access patterns, but also for the size and expected recovery cost of each block. With this informa-tion, each compute node independently prioritizes caching of intermediate data that is more costly to retrieve at each iteration boundary. While effective at the individual node level, prior meth-ods fall short of optimizing caching decisions in diverse distributed settings. In this work, we design and implement 

ShoreKeeper , a generic cost-aware caching system that works effectively for various deployment scenarios at scale. Specif-ically, we address two critical challenges: 

• Recovery cost imbalance. Despite the efforts of system schedulers to load balance across the cluster [12, 70], new blocks generated by concurrent tasks across nodes are often non-uniform in size and computation time. Such imbalance occurs even when nodes execute the dataflow with an iden-tical sequence of operations, due to factors like varying data filtering ratios or skewed key compositions after group-by-key operations [39, 51]. This poses two issues for node-level memory management. (1) Some nodes may saturate their memory capacity earlier than others, triggering premature block evictions while free space remains available on remote nodes. (2) Even when no such free space exists, local evic-tion decisions can lead to the loss of blocks that are globally expensive to recover. Without a cluster-wide view, nodes cannot coordinate caching decisions to prioritize high-cost blocks across the entire fleet. 

• Resource preemption. To leverage scalability and ease of maintenance, data analytics workloads often run in public clouds [6, 26, 43], using options ranging from on-demand virtual machines (VMs) to preemptible instances [5, 27, 44]. ShoreKeeper addresses these issues by introducing a global, cluster-level cost optimization framework aimed at minimiz-ing application execution time subject to the time-varying

At its core, the system executes a mixed integer linear programming (MILP) solver that determines not only which data blocks to keep in memory (caching), as prior cost-aware systems do, but also where each data block should reside across the cluster (placement). ShoreKeeper treats every executor as a candi-date location and precisely weighs the gain of retaining a partition against the cost of evicting resident data at the destination. To explore such plans, ShoreKeeper transforms the distributed dataflows across compute nodes into a sin-gle unified computational graph that captures cluster-level recovery costs and accounts for cross-node transfer latency. 

ShoreKeeper applies a dataflow pruning algorithm to keep MILP solving tractable. It prunes the optimization scope to only those blocks relevant to upcoming iterations in a near-future window, reducing decision latency to under 4 secs in our experiments. This latency is low enough to invoke the solver on-the-fly for intermediate data blocks produced at every iteration at scale. For blocks designated for another node, ShoreKeeper performs cross-node transfers in the back-ground, using only the network capacity that foreground computation leaves idle. 

ShoreKeeper ’s strategy for preemptible instances exploits cloud-native preemption events to dynamically refine its caching plan under reduced cluster capacity. Most cloud providers issue preemption alarms with predefined grace periods (e.g., 30 secs in Google Cloud). Upon receiving an alarm, ShoreKeeper re-triggers its solver to quickly migrate critical blocks from nodes slated for reclamation within the grace period. However, preemption alarms can occasion-ally be missed in practice [9, 59]. To handle such misses, 

ShoreKeeper periodically replicates a minimal set of blocks produced by time-consuming shuffle communication. We build ShoreKeeper atop Apache Spark 3.3.2 [70] and evaluate it against state-of-the-art in-memory caching [48, 57, 67] and storage-based checkpoint systems [55] over four benchmarks. With on-demand instances, ShoreKeeper achieves up to 6.11 × speedup over cost-agnostic caching methods and up to 2.05 × over Blaze [57], with the largest gains on workloads with the highest cross-executor imbalance. With preemptible instances, the performance gap widens further: 

ShoreKeeper achieves up to 2.87 × speedup over Blaze com-bined with Spark’s Decommissioner [10], as cost-aware evac-uation and proactive replication protect high-cost partitions. 

## 2 Caching for Iterative Dataflow Execution 

Distributed processing frameworks typically express the dataflow of iterative, data-intensive computations as a di-rected acyclic graph (DAG) [17, 33, 70]. Fig. 1 illustrates a simplified PageRank [47] DAG on Apache Spark [69, 70] as an example. In this DAG, vertices represent intermediate data blocks termed resilient distributed datasets (RDDs), and edges represent the transformations that derive downstream RDDs from upstream ones. An iteration corresponds to a sin-gle data-processing job, the unit of scheduling across cluster resources. Each job is divided into stages with boundaries defined by shuffle operators (e.g., group-by-key, join) that redistribute data across the network by element key. Within a stage, each RDD is partitioned and processed in parallel by tasks across distributed processes termed executors , each with a fixed memory allocation. As shown in Fig. 1, this DAG structure repeats across iterations, with each job consuming the output partitions of its predecessors, making effective caching critical for performance. When memory is full, cached partitions are either spilled to disk or discarded. While a spilled partition is restored via disk I/O, recovering a discarded partition requires recomput-ing it from the lineage, which is the recorded sequence of transformations starting from the source datasets [69]. The 2cost of recomputation depends on the memory-residency state of every partition along its lineage [48, 57, 67]. For instance, R49 in Fig. 1 depends on multiple upstream parti-tions: R47 from the same iteration and R37 from the previous one. If both are in memory, recovering R49 requires a single transformation. If both have been discarded, the executor must recursively recompute all missing partitions along the entire path back to the original input. This cascading recom-putation significantly amplifies the total recovery cost for a single cache miss by orders of magnitude. 

Cost-Aware Caching. Heuristic-based schemes, ranging from classic Least Recently Used (LRU) [70] to dependency-aware policies such as Least Reference Count (LRC) [67] and Most Reference Distance (MRD) [48], establish caching priorities based on historical usage patterns or partition de-pendencies in the DAG. However, none of these policies account for the actual recovery costs associated with future accesses to evicted partitions. Cost-aware caching methods address this gap by explicitly modeling the recovery cost of each partition when making eviction decisions. 3.1 Recovery cost imbalance 

Iterative workloads often process data with non-uniform distributions. In graph workloads, for instance, a small frac-tion of vertices may account for a disproportionate share of edges. Offline partitioning methods address this prior to execution: vertex-cut partitioning [23] distributes edges evenly across executors by replicating high-degree vertices, and GraphX [24] minimizes the number of such replicas. Together, these strategies yield nearly balanced per-executor partition sizes at the start of execution. However, the initial balance does not always persist as execution progresses. The variation in memory arises from runtime factors (e.g., selective filtering, aggregation fan-in, and shuffle redistribution) [38, 39, 51] that offline partitioning methods cannot anticipate. Because each operator consumes the output of a preceding stage or iteration, uneven partition sizes propagate into uneven computation times, even though every executor applies the same sequence of operations. As iterations unfold, new intermediate states accumu-late and add memory pressure. In distributed cloud settings, evicted partitions from executors under such high pressure have an opportunity to be migrated to a remote executor’s spare memory, stored in local disk or discarded so they can be recomputed when needed. Persisting a partition or discard-ing it are favorable options if caching in a remote executor for later retrieval can result in high network transfer costs. On the other hand, processing partitions on the same execu-tor can result in compute hotspots. Since the overall iteration time is bound by the slowest executor, such bottlenecks can significantly impact the job completion time. Our key insight is that end-to-end job completion time de-pends on these factors: (1) cost of task computation running on executors, (2) caching strategy which identifies important partitions incurring high recomputation cost (if discarded) or disk access cost (if persisted), and (3) remote fetching cost based on the distribution of dependent partitions across ex-ecutors. These factors are inter-dependent and impact each other. This creates an opportunity: executors with lower iteration time and recovery cost can absorb partitions from heavier peers to reduce iteration time.

Impact of Node Departure and Arrival. When a compute instance departs, all in-memory cached partitions accumu-lated over multiple iterations on that node are lost, forcing recovery through lineage recomputation or disk I/O under reduced cluster capacity. The performance impact of this loss is highly sensitive to when it occurs. As iterations pro-ceed and more intermediate data accumulates, the recovery lineage grows deeper, leading to a steady increase in com-pletion time for later preemptions (Fig. 5a). Losing a single instance during the final iteration increases completion time by 30–50% for the workloads evaluated in Fig. 5b. When a new instance joins, it provides no immediate caching benefit by default because cache population is lazily coupled with tasks subsequently scheduled on that node. To 4our knowledge, no mechanism exists to proactively redis-tribute cached partitions across the enlarged instance pool. 

Cloud-Native Support. To mitigate preemption impacts, cloud providers issue interruption alarms with a brief grace period (e.g., 2 mins on AWS, 30 secs on Google Cloud). Man-aged services such as AWS EMR [7] and Google Cloud Dat-aproc [26] leverage these alarms to trigger graceful decom-missioning, aiming to safely offload stateful data before a node departs. The Spark Node Decommissioner [10] exem-plifies this approach: upon receiving an alarm, the departing executor migrates cached partitions to surviving peers. How-ever, it selects partitions at random (oblivious to recovery costs), and the total volume is strictly constrained by the idle memory available in peers. In practice, such headroom is rarely sufficient, as executor memory is often heavily con-sumed by intermediate data accumulated across iterations. Preemption alarms are not always guaranteed in prac-tice [9, 59]. Unalarmed departures bypass decommissioning entirely, causing the loss of all cached data on the affected node. However, our traces show an extremely low alarm miss rate (0.3%), indicating that periodic checkpointing to persistent storage (e.g., AWS EBS) [55, 74] is impractical for such rare events, given its substantial overhead [54, 60] (see Fig. 9a). This motivates a lightweight, proactive approach tailored to rare alarm misses. 

## 4 ShoreKeeper Overview 

ShoreKeeper is a cost-aware caching system that manages aggregate memory across on-demand VMs or preemptible instances as a unified pool 1. ShoreKeeper has the following design goals to overcome the limitations identified in §3. 

• Cost-aware cluster-wide placement. To mitigate severe imbalance in recovery costs across executors, ShoreKeeper 

must place each partition on the executor that minimizes cluster-wide recovery cost, rather than confining it to its origin. ShoreKeeper schedules cross-executor transfers carefully to avoid interference with foreground network operations. 

• Cost-aware preemption handling. On receiving a pre-emption alarm, ShoreKeeper must prioritize the migration of partitions with high recovery costs over random ones. These migrations are executed within rigid grace periods while minimizing performance damage on peer nodes even under significant memory pressure. 

• Fast planning. Caching and placement decisions must quickly respond to frequently changing workload memory states and cluster capacity. ShoreKeeper aims to compute plans within seconds to keep up with typical iteration times and rigid grace periods imposed by cloud providers. 

• Alarm miss handling. ShoreKeeper employs minimal in-memory replication to handle rare alarm misses. This

4.1 Design Overview 

While features specific to resource preemptions (e.g., cost-aware migration and replication) are inactive on stable on-demand VMs, ShoreKeeper provides a unified solution rather than fragmented fixes. ShoreKeeper further simplifies its operations through a clean separation of planning and exe-cution. 

Unified Planner (§5). ShoreKeeper orchestrates caching, placement, and replication through a unified optimization framework. It maintains accurate cost estimates via a cost model informed by both offline and online profiling, and solves a mixed integer linear programming (MILP) to de-rive the cluster-wide plan. ShoreKeeper jointly determines 

whether to cache a partition, where to place it, and whether 

to replicate it, rather than treating these decisions in iso-lation. The solver considers every executor as a candidate location for every partition while incorporating the transfer cost into the placement decision. When placing a partition on a non-origin executor, ShoreKeeper weighs the gain of retaining that partition against the cost of evicting resident data at the destination. 

Runtime Manager (§6). ShoreKeeper invokes the planner (1) at periodic iteration boundaries, (2) upon preemption alarms, and (3) when a new executor joins the cluster. The Runtime Manager translates each new plan into per-executor actions. It diffs each new plan against the current placement, so only partitions whose placement changes are transferred. These transfers run asynchronously, batched per destination, and consume only the network capacity that foreground execution (e.g., shuffle stages) leaves idle. On receiving a preemption alarm, ShoreKeeper migrates partitions in de-scending order of recovery cost, transferring as much critical data as possible within the grace period.

## 5 Unified Planner 

As established in §4, ShoreKeeper solves a cluster-wide cache placement problem using a single MILP. This section details the three components of ShoreKeeper ’s planning pipeline: input profiling, cost modeling, and solver design. 

5.1 Profiling 

The solver can only produce an optimal plan if it operates on accurate cost estimates, but partition sizes, computation times, and cluster composition all shift during execution. 

ShoreKeeper combines offline profiling to initialize these estimates with online profiling to keep them up to date. 

Offline Profiling. Before execution begins, ShoreKeeper 

performs a dry-run on a minimal input to initialize all three state structures, similar to Blaze. The dry-run measures initial partition sizes and computation times to populate 

Cache State , and extracts the RDD lineage graph by cap-turing the code path of the iterative computation to popu-late Cost Graph . Separately, ShoreKeeper runs a bandwidth benchmark to obtain the initial pairwise network bandwidth 

BW 𝑛 (𝑒, 𝑒 ′), per-executor disk bandwidth BW 𝑑 (𝑒 ), and memory capacity 𝐶 𝑒 , which together initialize Cluster State .

Online Profiling. ShoreKeeper continuously updates all three state structures during execution. Cache State and Cost Graph are updated continuously during execution while Clus-ter State is updated on composition changes: node departures and arrivals trigger an immediate bandwidth benchmark so the solver incorporates the new cluster composition into the next plan.

5.3 Solver Design 

The solver’s goal is to minimize the aggregate recovery cost of partitions globally, i.e., across all executors. As discussed in §3.1, high recovery cost amplifies the memory and compute overhead on each executor when an eviction occurs. Minimiz-ing the recovery cost reduces the resource overhead of han-dling the eviction of structurally important partitions, and addresses a critical bottleneck when locality-aware sched-ulers direct tasks to executors with most data. Scheduler decisions are not considered by the solver so that Shore-Keeper is broadly applicable to the class of locality-aware data analytic schedulers, without requiring specific sched-uling policies to be modeled as they can vary across imple-mentations. Doing so introduces the challenge of scheduler drift , i.e., solver’s cost estimates can drift from actual runtime costs when the scheduler assigns tasks differently. Such drift does not impact ShoreKeeper ’s optimization decisions in a homogeneous resource setting. We design ShoreKeeper as a scheduler-agnostic caching layer, so it can be integrated with existing locality-aware schedulers without changing their task-assignment policies or modeling scheduler-specific deci-sions. The solver therefore determines the caching plan that minimizes aggregate recovery cost alone, subject to memory and placement constraints. The caching plan still prioritizes structurally important partitions whose high recovery cost persists regardless of scheduling outcome. ## 6 Runtime Manager 

The Unified Planner determines the cache placement plan, while the Runtime Manager determines how and when that plan is enforced. When the Planner produces a new caching plan, the Runtime Manager diffs it against the most recent plan and sends each executor the partition-level actions it must apply: evict, migrate, or replicate. Only partitions whose state changes appear in these directives. In response, executors report the sizes, computation times, and residency states of newly created partitions to the Runtime Manager at every stage completion, in order to keep Cache State and Cost Graph up to date. This stage-level granularity is a deliberate choice: per-task reporting would incur a round-trip for every partition, while per-iteration reporting would prevent the Planner from reacting promptly to mid-iteration composition changes such as preemptions. §7 describes two execution mechanics of these directives: lazy memory release and par-tition transfer optimization. This section focuses on how the Runtime Manager adapts the caching plan to executor arrivals, preemption alarms, and unalarmed departures. 

Executor Arrival. By default, a newly joined executor pro-vides no immediate caching benefit because its memory is empty and cache population is lazily coupled with tasks scheduled on that node. ShoreKeeper instead proactively profiles the new executor’s network and disk throughput, updates Cluster State , and re-invokes the solver with the expanded executor set. The updated plan can redistribute partitions from memory-constrained executors to the new node, exploiting the additional capacity immediately rather than waiting for task placement to populate the cache. 

Preemption Alarm. The grace period between a preemp-tion alarm and instance reclamation varies across cloud providers, and not all cached partitions can be migrated in time. Upon receiving an alarm, ShoreKeeper re-invokes the solver with Eq. 6 to account for the departing executor. Once the Runtime Manager identifies the partitions to mi-grate, ShoreKeeper evacuates them in descending order of solver-estimated recovery cost. Unlike prior cost-agnostic schemes such as the Spark Node Decommissioner, which migrate partitions in arbitrary order, this ordering ensures that the most expensive data is transferred first regardless of when the instance is reclaimed. Partitions computed during the grace period also enter the evacuation queue as they be-come available. Any shuffle partition that cannot be migrated in time remains available through proactive replication, if enabled. 

Unalarmed Departure. When an executor departs without an alarm, no evacuation is possible and all locally cached data is lost. If proactive replication is enabled, shuffle par-titions survive through replicas already residing on other executors. ShoreKeeper exposes this replication as a user option, since unalarmed departures are rare. Otherwise, all lost partitions are recovered through lineage recomputation when a subsequent task requires them. As with an alarmed departure, the Runtime Manager re-invokes the solver at the next iteration boundary with the reduced executor set to produce an updated plan. 

## 7 ShoreKeeper Implementation 

ShoreKeeper is implemented on top of Apache Spark 3.3.2 by modifying approximately 8k lines in the storage and schedul-ing subsystems. On the master, ShoreKeeper RpcEndpoint 

coordinates cluster-wide caching decisions and maintains 

RDDJobDag , which tracks RDD dependencies, job-to-stage mappings, and partition-level metrics collected from all ex-ecutors. Executors report partition sizes and computation costs to the master via asynchronous RPC messages, and 

RDDJobDag aggregates these reports into per-partition cost estimates for the solver. On each executor, ShoreKeeper Manager 

intercepts caching and eviction decisions within BlockManager 

through a pluggable CostPolicy interface, which maps solver outputs to per-partition actions: cache, disk, transfer, or evict. When a solver result is available, ShoreKeeper Manager 

consults the placement map to determine whether a parti-tion belongs on the local executor; otherwise, it falls back to reuse-based autocaching. Partition migration and replication use Spark’s BlockTransferService , with the solver’s per-partition replication factor determining the number of repli-cas. On a preemption signal, the master marks the alarmed 8executor, removes it from the active set, triggers the solver under the updated configuration, and broadcasts the new plan to surviving executors via RPC. The ShoreKeeper solver runs as a standalone Python pro-cess using Gurobi 11.0.3 [30], communicating with the JVM master through named pipes in JSON format. The master serializes the compressed DAG, per-executor memory ca-pacities, and measured bandwidth metadata to the pipe, and the solver formulates the MILP and writes back the block-to-executor assignment. 

Lazy Memory Release. When generating a caching plan, the solver considers both resident partitions and new parti-tions to be produced in the next iteration. Because new parti-tions materialize progressively, eagerly reclaiming memory for partitions already transferred to remote executors would leave local memory underutilized. ShoreKeeper therefore marks such partitions as removable and defers reclamation until the executor’s memory is exhausted. Once memory is full, the executor frees removable partitions in ascending order of recovery cost. 

Partition Transfer Optimization. ShoreKeeper performs partition transfers through three mechanisms: asynchronous transfer, batching, and pipelining. Each executor buffers par-titions targeting the same remote executor and flushes them in batches once the buffer is full to reduce per-transfer over-head. It further pipelines transfers across all destinations, as the CPU overhead of asynchronous transfers is low. Since the shuffle stage saturates network bandwidth with all-to-all communications, remote transfers pause until it completes. Replication follows the same mechanism, except that the sender retains its copy permanently. 

## 8 Evaluation 

8.1 Experimental Setup Environment. Unless specified otherwise, we deploy Shore-Keeper on 11 r5n.2xlarge AWS EC2 instances (8 vCPUs, 64 GB memory, 512 GB gp3 SSD, up to 25 Gbps network), with one master and ten worker nodes hosting 20 executors of 25 GB memory each. We use Spark’s default memory man-agement settings [11], under which execution and caching dynamically share a single memory region of 318 GB in aggregate. For the full-disaggregation comparison in §8.5, we keep executor CPU and execution memory allocations identical across both configurations. For full-disaggregation setting, we use Amazon S3 [8] to hold cached data in dedicated cloud object storage. This setting uses five m6in.16xlarge work-ers with 256 GiB of memory each, while ShoreKeeper uses five r6in.16xlarge workers with 256 GiB for execution memory, and 256 GiB for storage memory (i.e., for caching) each. Both instance types provide 64 vCPUs and 100 Gbps network. Each worker runs four 8-core executors. 

Benchmarks. We evaluate four benchmarks spanning graph analytics and machine learning, selected from those evalu-ated in [57]. PageRank (PR) iteratively propagates influ-ence scores across a graph, producing a deep lineage and the largest working set among our benchmarks: each itera-tion references about 400 GB of intermediate partitions, 1.3 ×

the aggregate cache. Connected Components (CC) identi-fies disjoint subgraphs of mutually reachable vertices on the same input graph. It shares PR’s iterative structure but con-verges in fewer iterations, producing shorter lineage chains and a working set of 276–383 GB per iteration. Both operate on a 54 GB synthetic graph that contains 25 million vertices (SparkBench [41]). Logistic Regression (LR) optimizes bi-nary classification coefficients on a 118 GB click-log dataset (HiBench [31]). Its computational graph is compact, and its working set stays close to the dataset size and fits within the cache. SVD++ performs collaborative filtering on synthetic ratings from 15M users across 1.5M items (25 GB). Its work-ing set (264–384 GB) is smaller than PR’s, but each partition carries high recovery cost from heavier serialization. In PR, CC, and SVD++, the cache is thus full throughout the iterations and 47–75% of cached partitions are evicted before a job completes. 

Baselines. We compare ShoreKeeper against five baselines categorized into three groups: heuristic-based caching (LRU, LRC [67], and MRD [48]), cost-aware caching (Blaze [57]) and in-storage checkpointing (Flint [55]). 

• LRU is the default caching strategy in vanilla Spark that relies on manual annotations for caching decisions, follow-ing the standard Apache Spark GraphX [24] and Spark ML-lib [42] implementations for the corresponding benchmarks. 

• LRC and MRD are representative cost-agnostic policies. LRC (Least Reference Count) evicts partitions with the fewest references in the compute graph. MRD (Most Reference Dis-tance) evicts partitions farthest from their next access and prefetches upcoming data. 

• Flint is a checkpointing-based system that periodically persists frontier partitions, the latest outputs at the leading edge of the lineage, to network-attached block storage. 

• Blaze is a recovery cost-aware caching system that solves a per-executor ILP for caching decisions (Eq. 3). All baselines are implemented in the same Spark engine for a fair comparison. Except for Flint, none of the baselines support preemption handling. We thus build two additional preemption-aware baselines: (1) Blaze+D , which integrates the Spark Node Decommissioner [10] into Blaze to migrate randomly selected cached blocks to surviving peers on a pre-emption alarm, and (2) Blaze+DF , which further adds Flint’s periodic checkpointing atop Blaze+D for durable replication.

## 9 Discussions 

Profiling Overhead. Offline profiling provides initial esti-mates that ShoreKeeper refines online during execution. Its startup cost amortizes across long iterative jobs but can mat-ter for short jobs. Sampling or reusing profiles from similar workloads could reduce this cost. 

Deployment Scenarios. When all instances are simulta-neously reclaimed in a purely preemptible cluster, Shore-Keeper falls back to full recomputation from the original input. A simple remedy is to provision a small number of on-demand nodes alongside preemptible ones, a configuration that ShoreKeeper handles without modification. For a clus-ter with on-demand instances, node departures can occur through hardware failures or autoscaling, which resemble un-alarmed and alarmed departures, respectively. ShoreKeeper 

covers both cases through the same Runtime Manager mech-anisms. 

Generality. ShoreKeeper requires three properties from the backend: intermediate data materialized as immutable par-titions, a dependency graph over those partitions, and the ability to recompute a lost partition from its ancestors. En-gines that satisfy these properties (e.g., Flink [17], Ray [45], and Dask [52]) could serve as a backend with modest engi-neering effort, as each component of ShoreKeeper operates on this abstraction. Extending beyond iterative workloads is harder: iteration boundaries bound the solver’s scope to the next iteration, and without them it must reason over the entire dataflow at once.

## 10 Related Work 

Distributed Memory Management. Memory disaggre-gation enables applications to access remote memory over the network. FaRM [20] and soNUMA [46] expose cluster memory as an explicit shared address space over RDMA for low-latency access. Infiniswap [28] and Fastswap [4] har-vest idle remote memory through RDMA-backed paging. AIFM [53] and Semeru [61] integrate far memory manage-ment into application runtimes to hide far-memory access latency. Carbink [73] features fault tolerance through era-sure coding and ownership migration. These systems treat remote memory as an extension of local memory, whereas 

ShoreKeeper manages intermediate data placement across dynamically changing cluster nodes to reduce recovery cost. 

Adapting to Resource Changes. Several systems adapt computation or its state to changing cloud resources. Pado [65] schedules critical tasks on reserved instances while offload-ing elastic work to preemptible ones, and ExoSphere [56] manages portfolios of heterogeneous transient instances to optimize availability and cost. Accordion [71] changes the parallelism of an analytical query during execution and rebuilds partitioned state as resources change. BigQuery’s distributed shuffle [2] separates shuffle data from compute workers, while POLARIS [1] separates compute from state by externalizing the assignment of data cells to nodes, en-abling partial query restart and online resize. On-demand state separation [62] implements task migration without costly periodic checkpointing by extracting and transferring operator state and execution progress only when migration is triggered. These systems reconfigure execution state to survive resource changes, but treat all state as equally worth preserving. ShoreKeeper instead decides which reusable data partitions to retain based on their lineage-aware recovery costs. 

Checkpoint-Based Recovery. Besides Flint [55], several systems persist intermediate state to stable storage to survive failures or instance revocations, including TR-Spark [64], SpotOn [58], Tachyon [40], and cost-based approaches [19, 54, 60, 74]. These systems trade storage and I/O cost for bounded recovery time, whereas ShoreKeeper retains inter-mediate data in memory, optimizing caching, placement, and replication as cluster capacity changes. 12 External Storage and Analytical Caching. A separate line of work moves analytical data and state off compute workers. Among analytical caches, Crystal [21] places a cache next to compute and stores predicate-defined regions of base data to reduce reads from remote cloud storage, and AnyBlob [22] retrieves base data from cloud object stores through a down-load path integrated with the query engine. Among disag-gregated stores, Pocket [35] provides job-scoped ephemeral storage, Locus [49] spreads serverless shuffle data across object storage and a fast storage tier, and Jiffy [34] leases fine-grained far memory to serverless tasks. Tachyon [40], later renamed Alluxio, uses storage-level lineage for high-throughput writes and recovery while exposing a shared file layer to compute frameworks such as Spark [3]. These sys-tems change where data resides and how it is accessed, while 

ShoreKeeper decides which reusable partitions to retain as executor capacity changes. The two operate at different lay-ers of the caching stack and can be combined. 

## 11 Conclusion 

Workload analysis reveals that managing recovery costs across executors in the cloud for iterative workloads is essen-tial for reducing execution time. ShoreKeeper addresses two intrinsic challenges: recovery cost imbalance across execu-tors and resource preemption, making it applicable across diverse cloud deployment scenarios. Its design follows a clean separation of planning and execution, where the plan-ner uses MILP to holistically balance caching benefits against eviction costs across all in-memory partitions in the cluster.
