## 摘要
LLM 智能体越来越多地执行涉及多轮推理、工具使用和并行智能体的复杂工作流。高效服务需要跨越两个具有互补信息的层次做出决策：智能体框架理解工作流依赖、上下文生命周期和执行目标，而推理引擎则观察请求队列、KV 缓存状态、资源压力和执行能力。现有接口未能系统性地连接这些视图，限制了工作流感知的执行。HEAR 是一种面向智能体式 LLM 服务的双向 Harness--Engine Pairing 协议。HEAR 标准化了 harness 如何传达工作流意图与执行需求，以及引擎如何返回运行时状态、能力和结果。通过将协议语义与优化策略分离，HEAR 支持多样化的协调策略，而无需改变工作流或模型语义。我们将 HEAR 实例化用于在线缓存感知的运行时协调，以及针对智能体角色的负载感知执行模式选择。在内存受限的并发服务场景下，在四个对话和研究智能体基准上，HEAR 在 SCBench 上实现了 1.61 倍的批处理加速，并将首 token 时间中位数缩短至原来的 1/2.23。Mooncake 表明，工作流意图与实时引擎状态在不同负载情形下提供互补收益。在 BrowseComp-Plus 和 DeepResearchBench 上，针对特定工作负载的配置分别带来了 1.23 倍和 2.45 倍的端到端加速，且未观察到任务质量下降。这些结果确立了 HEAR 作为高效智能体式 LLM 服务的可复用协调基座。

## Abstract
LLM agents increasingly execute complex workflows involving multi-turn reasoning, tool use, and parallel agents. Efficient serving requires decisions that span two layers with complementary information: the agent harness understands workflow dependencies, context lifecycles, and execution objectives, whereas the inference engine observes request queues, KV-cache state, resource pressure, and execution capabilities. Existing interfaces do not systematically connect these views, limiting workflow-aware execution.   HEAR, a bidirectional Harness--Engine Pairing protocol for agentic LLM serving. HEAR standardizes how the harness communicates workflow intent and execution requirements and how the engine returns runtime state, capabilities, and outcomes. By separating protocol semantics from optimization policies, HEAR supports diverse coordination strategies without changing workflow or model semantics. We instantiate HEAR for online cache-aware runtime coordination and workload-aware execution-mode selection for agent roles.   Across four conversational and research-agent benchmarks under memory-constrained, concurrent serving, HEAR achieves a $1.61\times$ batch speedup and reduces median time-to-first-token by $2.23\times$ on SCBench. Mooncake shows that workflow intent and live engine state provide complementary benefits across load regimes. On BrowseComp-Plus and DeepResearchBench, workload-specific configurations yield $1.23\times$ and $2.45\times$ end-to-end speedups, respectively, without observed task-quality degradation. These results establish HEAR as a reusable coordination substrate for efficient agentic LLM serving.

## 二、方法论

### 2.1 核心思想

- HEAR = **双向 Harness–Engine Pairing 协议**，是控制面（control-plane）协议而非数据面协议。
- **职责划分**：harness 管工作流语义（角色、依赖、就绪性、上下文生命周期）；engine 管模型执行（队列、KV 缓存、服务资源）。协议只协调"被工作流选定的请求如何被服务"，**不改变任务选择逻辑、不放松依赖、不修改模型语义**。
- **语义与策略解耦**：协议定义"交换是什么、如何被处理"；策略定义"交换什么信息、采取什么动作"。
- 每次交换都关联到具体的 **request / context version / serving instance**，从而把工作流需求与引擎状态及结果绑定。

### 2.2 四类语义消息（Table 1）

| 方向 | 类别 | 代表内容 |
|---|---|---|
| Harness → Engine | **Execution Description and Intent** | 角色与阶段、工作流依赖与就绪性、请求规模与输出上限、上下文生命周期、已知/显式标注的未来复用 |
| Harness → Engine | **Execution Requirements and Control** | 调度偏好与等待时间约束、缓存准备/保留/释放请求、允许或请求的执行配置与服务目标 |
| Engine → Harness | **State and Capabilities** | 可复用前缀范围与驻留层级、可分配容量、队列状态、资源压力、支持的控制与配置、校准/估计的执行成本 |
| Engine → Harness | **Execution Outcomes** | 推理与控制请求的状态（accepted/completed/rejected/unsupported/failed）、实际配置与允许的 fallback、缓存复用、延迟、资源消耗、重试与错误 |

- 类别定义的是**语义角色而非报文格式**；单次交换可含多个类别，实现可只暴露其支持的子集（通过 capability 上报让 harness 发现）。

### 2.3 四条交互语义区分（Table 2）

- **Intent vs. Control**：描述/预测只提供决策上下文，**只有显式控制请求才要求对方行动**（"报告 c 会被复用" ≠ "要求保留 c 的 KV"）。
- **Preference vs. Requirement**：偏好是 best-effort；需求约束合法执行，未满足必须**拒绝或走显式允许的 fallback**（如优先级提示不能覆盖强制保护条件）。
- **Observation vs. Guarantee**：状态/能力报告只描述观察到的条件与支持的操作，**不预留资源、不保证未来可用**。
- **Acceptance vs. Completion**：acceptance 表示被接纳处理，completion 表示声明的效果已实现；rejected / unsupported / failed 需与二者区分。

> 作用：防止策略把描述当命令、把观察当预留、把已接纳当已完成，使后续决策依赖**已实现的效果**而非对先前控制的假设。

### 2.4 策略集成公式（文字说明）

- 联合信息决策：\(d_i = \pi(h_i, s_j)\)
  - \(h_i\)：决策点 \(T_i\) 时可用的工作流与请求信息；
  - \(s_j\)：最近一次相关引擎更新（\(j\) 与 \(i\) 异步，两层独立演化，故 \(s_j\) 未必在 \(T_i\) 产生）；
  - \(\pi\) 选择执行安排或配置 \(d_i\)。
- 退化情形：无引擎反馈 → \(d_i = \pi(h_i)\)（仅框架本地决策）；无工作流信息 → 引擎仅限请求本地状态。
- 策略可运行在任一层：本地执行或通过控制消息下发。已有策略（PBKV 的预取、Pythia 的调度）**预测器与优化规则不变，仅通过适配器暴露所需描述、观察与控制**。

### 2.5 两个互补的实例化策略（不同时间尺度）

**(A) Cache-Aware Runtime Coordination（在线，毫秒/秒级）**
- 实例化：\(h_i = (\mathcal{R}_i, \mathcal{C}_i, \mathcal{U}_i)\)（就绪请求、上下文、含等待保护的执行需求）；\(s_j = (K_j, Q_j)\)（缓存可用性、队列状态）。
- 调度输出：\(d_i = \pi_{\text{sched}}(h_i, s_j) = (\boldsymbol{p}_i, \mathcal{U}_i)\)，即优先级分配 + 需求约束。
- 具体实现细节：
  - 从前缀起始处顺序匹配可复用 block，遇到第一个缺失/被驱逐的 block 即停止；分别统计 GPU 与 CPU 层的可复用前缀 token。
  - **Hot/Cold 判定**：可复用前缀 ≥ 50% prompt 为 hot；hot 请求优先级 = \(-N_{\text{reuse}}\)（可复用 block 数的负值），数值越小越先执行，hot 之间按可复用前缀长度降序。
  - **Guard-\(W\) 等待保护**：harness 在固定时刻下发；等待超过 \(W\) 秒的请求被提升为 protected 优先级，后续 cache-hot 请求不能绕过，protected 请求间按等待顺序。SCBench 评测 \(W \in \{40, 60\}\) s，Mooncake 用 \(W=40\) s。
  - **Session-Aware（KV 保留策略）**：harness 从已完成会话统计会话返回概率 \(p\)，保留优先级 \(r = p \cdot e^{-\text{idle}/400}\)，idle 为距上次请求完成的时间；只更新自已完成会话，不使用当前 replay 的未来信息。该估计**显式标注为描述性 intent 而非保留要求**。

**(B) Capability-Aware Execution Configuration（离线冻结映射，粗粒度）**
- harness 描述 \(h_i\)：角色、工作流阶段、负载形态、执行目标、质量要求；引擎 \(s_j\)：兼容执行模式及其延迟、吞吐、KV 容量、稳定性画像。
- 候选空间：\(\mathcal{C} = \{\text{vLLM}, \text{OmniKV}\} \times \{\text{vLLM}, \text{H2O}, \text{SnapKV}\}\)（前者为 Main 侧模式，后者为 Reader/子智能体侧模式）。
- 选择器在通过开发期质量与稳定性检查的配置中最小化 makespan：
  - \(\tilde{d} = \arg\min_{d \in \mathcal{C}_{\text{valid}}} T_{\text{dev}}(d)\)（程序化推荐）→ 人工/脚本核验执行日志与质量稳定性摘要 → 冻结为 \(d^*\)。
  - 冻结结果：\(d^*_{\text{BCP}} = (\text{vLLM}, \text{H2O})\)，\(d^*_{\text{DRB}} = (\text{OmniKV}, \text{H2O})\)。
- 运行时：初始化时加载版本化配置文件，逐请求做**常数规模查表**，不搜索六臂空间；记录请求与实际模式及 completion/failure/fallback。

**(C) 协议开销核算（Table 7）**
- HEAR 只增加控制面元数据处理（KV 状态更新、调度决策、角色-模式查表、结果上报），**不引入额外模型层或 per-token GPU 算子**；OmniKV/H2O/SnapKV 的计算属于执行模式而非协议本身。
- 上述在线路径**计入正式端到端时间**；画像校准、筛选、排序、核验为离线开发阶段，不计入。

## 三、实验设计

### 3.1 数据集 / 场景与 Benchmark

| 策略族 | Benchmark | 负载构造 | 模型与硬件 |
|---|---|---|---|
| 缓存感知运行时协调 | **SCBench**（KV-cache 中心的长上下文分析） | 原始数据无时间戳，构造闭环多轮：Poisson 会话到达 + 思考时间 \(\mathcal{N}(5,1)\) s | Qwen3-8B，单张 RTX PRO 6000，96 GiB L2 KV cache |

| 能力感知执行配置 | **DeepResearchBench** | 100 个实例/臂，Main–Sub-Agent 架构 | 同上 |

### 3.2 对比方法与基线

- **缓存感知协调**（SCBench / Mooncake）：FCFS（vLLM 默认调度）、Cache-Aware（受 KVFlow 启发）、Cache-Aware + Guard-\(W\)（\(W=40/60\)）、Session-Aware（受 Pythia/PBKV 预测引导方法启发）、Session-Aware + Cache-Aware + Guard。
- **能力感知配置**：六臂全组合 \(\{\)vLLM, OmniKV\(\} \times \{\)vLLM, H2O, SnapKV\(\}\)，主对比基线为 vLLM–vLLM。
- **公平性控制**：同模型、同输入、同 prompt、同工作流与工具预算、同硬件；策略与参数在评测前冻结；每臂独立初始化服务状态；结果包含全部失败与重试；缓存感知实验采用**轨迹录制-重放**，确保各策略看到相同到达时间、长度、前缀，差异仅来自调度与缓存管理。

### 3.3 评价指标

- 效率：TTFT（P50/P95/Max）、批完成时间 / session 时间 / makespan、吞吐、端到端 P95 延迟、KV 复用率、GPU KV 池占用、KV 恢复量、等待请求数。
- 质量：BrowseComp-Plus 用 Judge Accuracy + 检索召回 + 引用精度/召回；DeepResearchBench 用官方无参考 RACE 评测（综合、洞见、指令遵循、可读性四维）。
- 统计：Wilson 95% CI、配对 McNemar 检验、配对 t 检验、percentile bootstrap CI。
