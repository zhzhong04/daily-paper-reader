## Abstract 

Large language model (LLM) serving is increasingly domi-nated by agentic workloads, in which agents and their sub-agents accumulate context as KV cache across many requests, consuming substantial memory. High-bandwidth flash (HBF) is a promising solution, providing an order of magnitude greater capacity at HBM-class read bandwidth, but its finite write endurance is the key limiting factor. Our key insight is that KV cache should be placed across HBM and HBF by its lifetime. Placing shorter-lived data in HBM lets HBM absorb more of an agent run’s writes and sends less of them to HBF. As the lifetime of KV cache in agentic serving is dictated by the harness, the program that orchestrates the agents, we analyze its behavior and identify three axes along which life-time diverges, temporal, structural, and inter-worker. Guided by these observations, we present Lachesis, a lifetime-aware KV cache placement layer between the agent harness and the serving engine. At write time, it places each segment in HBM or HBF according to its lifetime, and frees its blocks once the segment is no longer read. In trace-driven simulation, Lachesis extends HBF lifetime by 1.19–3.13 × over HBM-first placement, reaching 3.3–12.2 device-years. Even under con-tinuous 24 ×7 operation at the full load a tight SLO admits, HBF outlasts its five-year warranty on the multi-agent trace. 

## 1 Introduction 

LLM serving is shifting toward agentic workloads, in which an agent works on a single user task over many LLM re-quests and spawns sub-agents that run concurrently along-side it [55]. Whereas a conventional request holds one con-text for the duration of one request, an agent holds the con-text it has accumulated so far in the session as KV cache, and that KV cache can stay live well beyond the request that wrote it, in some cases until the session ends (Figure 1, top left). Together with the sub-agents a session spawns, this longer lifetime pushes the volume of KV cache live at one time far beyond that of conventional serving. The pressure this KV cache puts on an accelerator’s high-bandwidth mem-ory (HBM) forces a deployment to add accelerators or serve fewer sessions at once, either of which raises the hardware cost of a served request [14, 23, 41]. High-bandwidth flash (HBF) is emerging as a promising class of memory for LLM inference, offering an order of mag-nitude greater capacity than HBM with HBM-class sequen-tial read bandwidth [38]. That capacity absorbs the added pressure and brings the cost of a served request back down. The key limiting factor for HBF, however, is write endurance. NAND flash tolerates only a finite number of program/erase (P/E) cycles, so a DRAM-like role that absorbs a large vol-ume of writes can wear it out in a fraction of HBF’s required service life. Early HBF designs therefore confine HBF to read-only data such as model weights and shared-prefix KV caches [14, 20, 29]. As KV caches are a dominant source of serving-time memory pressure in agentic and large-batch workloads [25, 26, 36], recent works extend HBF to dynam-ically generated KV cache and select what to write to it, mainly by its read-to-write ratio [23, 33, 47]. Unlike prior work, which selects KV cache for HBF by its read-to-write ratio [23], we select it by its lifetime. When HBF is used alongside HBM, every KV block a session writes lands in one of the two tiers, and only the bytes that land in HBF spend endurance. HBF therefore lasts longer the more of a session’s writes HBM absorbs. The volume HBM absorbs over a period is its capacity multiplied by the number of times each block is reclaimed when the KV cache it holds is discarded. Placing shorter-lived KV blocks in HBM therefore lets HBM absorb more of a session’s writes and sends less of them to HBF, which requires knowing a block’s lifetime before it is written. In agentic serving, KV lifetime is set by the agent harness, the program that orchestrates the session [5, 24, 37, 46], so we analyze how the harness manages it. ## 2 Background and Motivation 

2.1 Agent Serving Intensifies the Capacity Wall 

Agentic serving is increasingly constrained by a memory-capacity wall , pushing up the cost of serving each request. The pressure grows from two sides, the model footprint and the KV cache. The model footprint has grown faster than per-accelerator HBM capacity, requiring more accelerators simply to host a model [14, 41]. The other side is the KV cache, which grows with the context each session accumu-lates. An agent session accumulates context by repeating the reason-act-observe loop of a ReAct-style agent until the task is done (Figure 2(a), top). Each pass is a round , a single LLM request, and it appends all three to the context every later round must read [52, 55]. A session divides into turns , one per user message, and a turn holds one or more rounds. An observation is sized by the environment rather than by a person, so a source file or a command’s output enters the con-text whole. The peak context lengths of agentic workloads are 29 × larger than those of conventional chatbot workloads (Figure 2(b)). A multi-agent session holds more than one such context at a time (Figure 2(a), bottom). A lead agent carries the user’s task and delegates a subtask to a sub-agent , which runs its own rounds in a context of its own and returns a result [4, 5, 21]. The session therefore occupies the lead agent’s context and one more for every sub-agent running under it. Many such sessions are served at once, and each holds its accumulated context in HBM. Deployments must either spread each request across more accelerators or reduce the number of concurrently resident contexts, both of which increase the hardware cost per served request [14, 23, 41]. HBF is therefore a promising alternative to HBM, and Fig-ure 3 shows two architectures explored by prior works that directly integrate HBF with accelerators. Daisy-chained de-signs connect HBF stacks behind HBM, allowing HBF traffic to reach the accelerator through the HBM stacks (Figure 3(a)) [14]. Co-located designs instead attach HBF directly along-side the accelerator (Figure 3(b)) [23, 41]. When accessing HBF-resident data in co-located designs, the accelerator can utilize the aggregate memory bandwidth of all stacks through direct and inter-stack paths [3, 20]. Prior works have addressed the main performance lim-itations of HBF, which are outside the scope of this work [14, 20, 29, 47]. First, HBF read latency is orders of magni-tude higher than HBM. LLM inference exposes predictable sequential accesses that enable aggressive prefetching to hide this latency. Second, sustaining HBF’s peak read band-width requires accessing many flash planes in parallel; prior work achieves this through plane-balanced data layouts. The remaining obstacle to using HBF in LLM serving is the limited write endurance. Because NAND supports only a finite number of P/E cycles, prior HBF designs have largely focused on read-only state that is written once and then repeatedly read [38]. Designs such as H3 place model weights and precomputed KV cache in HBF while retaining online-generated KV in HBM [14, 20, 29]. For agentic serving, however, the generated KV becomes the dominant capacity bottleneck, making write endurance a first-order challenge. Unlike model weights, whose foot-print is fixed once the model is loaded, generated KV grows with context length and the number of resident sessions (Fig-ure 2(b)). Fully exploiting HBF, therefore, requires placing the generated KV in HBF [23, 41]. The KV cache is generally well suited to NAND flash. Each entry is written once during prefill or decode and then repeatedly read by subsequent attention steps [22]. But short-lived KV with little reuse can nonetheless quickly exhaust write endurance [41]. 

2.3 Why Agent Sessions Require Lifetime-Aware KV Cache Placement 

Although Kyung et al. propose placing the KV cache with a high read-to-write ratio in HBF [23], this criterion does not directly apply to agentic serving. They show that output length largely determines the read-to-write ratio because longer generation reuses the KV cache across more decode steps. This relationship holds for stateless requests, where all KV is created and consumed within a single request and therefore shares the request’s lifetime. Agent sessions are stateful, however, and different parts of their context can remain useful for different lengths of time. The harness may discard some context while retaining the rest for later turns or subtasks. We call a group of tokens that share the same lifetime a context segment .

## 3 Context-Lifetime Analysis for Agent Serving 

3.1 Analysis Overview 

Table 1 summarizes the three characterization axes that arise in agentic serving, where each axis separates short-lived from long-lived context segments. Along the temporal axis, reasoning context is discarded at the turn end, and the re-maining reasoning-stripped context merges with the session context (§3.3). Similarly, along the structural axis, sub-agent context excluding the result is discarded at the sub-agent return (§3.4). The discarded segment is a short-lived context segment, and what survives the boundary is a long-lived context segment. Along the inter-worker axis, the class is constant and worker segments differ in lifetime by when each worker returns (§3.5). The harness fixes a segment’s class before the segment is written, so the lifetime is known at the write. The first two splits are deterministic, fixed at the turn end and at sub-agent spawn. The last split, worker lifetime, is predictable from the metadata the harness records when it spawns each worker. A reactive policy such as least-recently-used (LRU) cannot assign the class before observing subsequent accesses and would require migration to correct the placement later. 

3.2 Methodology 

We isolate the turn end and sub-agent return in two execu-tion regimes, each configured so that only the context bound-ary under study can close a read window (Table 2). A lifetime difference measured in a regime is therefore attributable to that regime’s boundary. The temporal regime runs on Harbor [15] and the structural regime on AOrchestra, which builds each sub-agent from an explicit ⟨Instruction, Context, Tools, Model ⟩ specification at spawn [37]. We call that specification the spawn record , from which §3.5 ranks worker lifetimes. No harness records segments, so they are recovered from a per-request trace. The trace records the exactly matched input-prefix length and the cache read SGLang reports [58]. A segment’s read window closes where the segment stops appearing in the context that later requests reuse, or at the end of the session if no boundary closes it. Rematerialization produces a new segment, not an in-place rewrite, so each segment is materialized once with its own write volume. The primary metric, normalized context lifetime, is how long a segment must remain readable on a fixed reference clock rather than on server wall time:

3.3 Temporal Axis: Reasoning-Content Stripping 

Along the temporal axis, reasoning determines how long a context segment remains live. Across multiple rounds within a turn, the harness accumulates reasoning context across tool calls along with non-reasoning context [9, 32]. The ac-cumulated context is read throughout the later rounds in the same turn [55]. When the turn ends as the next user mes-sage arrives, the harness discards the reasoning context, the reasoning-laden context segment, and only the remaining reasoning-stripped context segment from the previous turn is passed to the new turn [31]. Figure 4(a) shows that the reasoning-stripped context seg-ment outlives the reasoning-laden context segment by a median ratio of 7.6–17.2 × across all domains. The reasoning-stripped context segment is retained across multiple con-secutive turns, while the reasoning-laden context segment is retained only during the single turn that generates the context. The lifetime distributions of the two segments are clearly separated: a separability, the probability that a ran-dom reasoning-stripped context segment outlives a random reasoning-laden context segment, is 0.96–0.99. Placing short-lived reasoning-laden context segment in HBF is particularly costly because it is much larger than the reasoning-stripped context segment. Of the tokens written by a turn, 66–83% belong to the reasoning-laden context segment (Figure 4(b)). These tokens consume extensive HBF P/E cycles even though the harness soon discards them at the next turn end. The same write budget can instead retain many smaller, long-lived contexts in HBF. 

Takeaway 1 

• The reasoning-laden context segment is short-lived yet holds 66–83% of the tokens a turn writes, while the reasoning-stripped context segment that replaces it is long-lived. 

• HBM should hold the short-lived context seg-ment and HBF the long-lived context segment. 3.4 Structural Axis: Lead-Agent/Sub-Agent Isolation 

In multi-agent sessions, the lead-agent context is retained longer than the context created for each delegated subtask. The lead agent delegates a subtask to a sub-agent, which executes the task in a separate context. When the sub-agent returns, only its result is merged into the lead-agent segment, while the remaining sub-agent segment is discarded. This separation is by design of the multi-agent execution model, not an optimization specific to one harness [4, 5, 21, 24, 30]. The predictor reads the spawn record’s instruction, context and tool list, together with where the spawn falls in the session; we call that set the worker’s spawn signal .The predictor is a linear model over that signal, fitted by ridge regression and read only for the order it induces. Each element enters the model as a length, an indicator per tool, a session position, or a hashed bag of its words. A single predictor serves all five benchmarks. The predicted ranking orders workers by lifetime at Kendall’s 𝜏 of 0.53, a metric that scores the order alone. The predictor is scored by five-fold cross-validation that keeps all workers of a session in the same fold, so no worker is scored against training data from its own session. ## 4 Lachesis Design 

Based on the three axes of §3, we present Lachesis, a lifetime-aware KV cache placement layer that decides which KV reaches HBF before a segment is written. As Figure 8 shows, Lachesis lies between an agent harness such as the Open-Hands SDK, AOrchestra or Claude Code [5, 37, 46] and a serving engine such as vLLM or SGLang [22, 58]. Lachesis receives three things from the harness, the id of the segment that each LLM request extends, the spawn record written at each sub-agent spawn, and the context boundary that closes a segment. It holds three components, a deterministic path that reads the segment class that the harness fixes on the temporal and structural axes, a predictive path that ranks workers by a lifetime predicted at spawn on the inter-worker axis, and a segment table that carries one row for each live segment. It reaches the serving engine as two calls, one that allocates a block in a named tier and one that frees the blocks of a closed segment. Its placement covers KV only, leaving §2.2’s read-only mapping for model weights unchanged and activations in HBM. The deterministic path places the short-lived context seg-ment in HBM and the long-lived context segment in HBF, by the segment class that the harness fixes. In a single-agent session, the harness reports one context boundary, the turn end (§3.3). Until it arrives, every request extends the turn’s reasoning-laden context segment, which Lachesis places in HBM. At the boundary, the harness discards that segment and materializes the reasoning-stripped context segment that carries into the next turn, which Lachesis places in HBF. The spawn separates the sub-agent segment from the lead-agent segment, so from that point Lachesis places what the sub-agent writes in HBM and what the lead agent writes in HBF. Of the two sub-agent roles, only the reviewer, whose segments are the shorter-lived, takes that placement unconditionally; a worker is admitted by the predictive path. The predictive path ranks the workers of every session that the node serves by a lifetime predicted at their spawn, and admits the first 𝑘 to HBM, allocating the rest in HBF. In a multi-agent session, every worker’s segment carries the same class, because no context boundary separates one from another (§3.5). They all close at sub-agent return and differ only in when that return comes, so the deterministic path cannot distinguish them. At each worker spawn, Lachesis scores that worker’s segment from its spawn signal, and the segment’s place in the ranking decides its memory tier. A reviewer is spawned only after the worker that it reviews, so Lachesis reserves HBM capacity for reviewers before it counts 𝑘 . 𝑘 is determined by HBM’s free capacity rather than set as a parameter, so a fuller HBM admits fewer workers. Only a worker’s rank among the predictions is consumed, never a lifetime, so the predictor must recover the order rather than estimate how long a worker’s segment lives.

Scoring the signal is one evaluation of a linear model, so it adds no delay before the worker starts. Every memory tier decision is made in Lachesis, which holds one segment table row for each live segment. The row is keyed by the segment id and gives the segment class, the context boundary that closes it, and the engine’s own identifiers for the KV blocks that it holds. Lachesis adds a row at a segment’s first write and records in it the id of every block it allocates for that segment. When the harness reports the boundary that a row names, Lachesis frees that row’s blocks and removes the row. The table’s size is proportional to the number of blocks live at any moment. Lachesis names the tier for every block it places, so it tracks how much KV each tier holds. The engine executes those decisions without representing a lifetime. Lachesis reaches the engine as two calls that it issues itself, and neither names a turn, a sub-agent, or rea-soning content. alloc(tier) draws one KV block from the named tier’s free list, and free([block ids]) returns the blocks that a closed segment held, each to the free list it came from. That second call fires at a context boundary, not after the inactivity that a recency policy waits for [45]. A deployed engine keeps a single free block list. Supporting a heterogeneous memory costs it one free list per tier, an HBM list and an HBF list, and nothing else. A block’s tier is therefore the free list it was drawn from. When HBM’s free list is empty, the allocation is served from the HBF free list. 

## 5 Evaluation 

5.1 Implementation 

We implement Lachesis on a simulated serving engine and two-tier memory, and replay real agent traces through it. Frontier supplies the engine [11]: a scheduler and request queue, a KV-cache manager with a block-hash prefix cache, memory capacity expressed as a KV-block budget, and con-text that grows per round. LLMSimulator supplies the hard-ware [1], with the HBF extension prior work used [23, 41]: compiled operator kernels and roofline memory pricing. Its memory system holds KV in both tiers and prices each read against the bandwidth of the tier it is served from. KV bound for HBF is buffered across the decoder layers and flushed once at the end of the decode step, so HBF’s write bandwidth prices that flush rather than any decoder layer. The two meet at the operator-cost call, where the engine passes an opera-tor’s shape and its KV length and receives its execution time on the device. Its workload generator now replays an agent run as per-request rows that name the segment each request extends. Its KV allocator now keeps a free list per tier and serves the two calls of §4. 

5.2 Experimental Setup Testbed. Lachesis is evaluated at the decode node of a prefill– decode disaggregated deployment [10, 34, 59], where the HBF-equipped GPUs reside [23, 41]. Four GPU-memory con-figurations split the eight stack slots of the GPU used by Son et al. [41] between HBM and HBF, 1/7, 2/6, 3/5 and 4/4. A fifth is H3’s daisy chain, labelled 8/8* [14]. The two tiers have the same read bandwidth and differ only in write bandwidth. The traces are replayed against two models, Llama-4-Maverick and Qwen3-235B-A22B. Each is served across eight GPUs, its attention by data parallelism and its experts by expert parallelism. Every configuration is run at two SLOs on the multi-agent trace, both with a 2 s time to first token (TTFT) [42, 50]. They differ in the 99th-percentile time per output token (TPOT), a tight 60 ms and a loose 100 ms [6, 42]. The single-agent traces are run at the tight SLO alone. 

Workloads. Three replay traces are built from the ses-sions of §3.2 (Table 2). The temporal regime supplies the two single-agent traces, 𝜏 3-bench and BFCLv4, and the structural regime’s five benchmarks are mixed into one multi-agent trace. The multi-agent trace is collected twice, once as the harness records it and once with the reviewer disabled, and every result below is read on the first unless it names the second (§5.4). The evaluation uses the latency model of §3.2, and both of its terms are taken from prior serving work. No benchmark records when a user replies, so user delay is sampled from a log-normal with median 120 s [12, 49, 54], and tool-call latency from a published measurement for each tool class (Appendix B). 

Baseline. Lachesis is compared against HBM-first place-ment, which places a KV block in HBM whenever HBM has a free block and in HBF otherwise. It is the placement an engine performs without Lachesis. 

Metric. HBF lifetime is the time HBF’s P/E budget lasts at the mean rate at which KV is written to it, excluding the one write that loads the model weights. Each cell tolerates 100,000 P/E cycles at SLC density [41], over 512 GB of flash per stack [38]. KV blocks are written whole and in order, so garbage collection and wear leveling move few blocks and write amplification is 1.02, the value prior work adopts [16, 23]. Lifetime is measured once the write traffic has settled. A device must outlast its five-year warranty.

## 7 Conclusion 

This paper presents Lachesis, a lifetime-aware KV cache placement layer for agent serving across HBM and HBF. We find that the context an agent session accumulates divides at harness-defined context boundaries into context segments whose lifetimes differ along three axes, temporal, structural and inter-worker, and that each lifetime is knowable before its segment is written. Lachesis places each segment on the tier its lifetime implies, along a deterministic path that reads the segment class the harness fixes and a predictive path that ranks worker segments at spawn. In trace-driven simulation, Lachesis extends HBF lifetime by 1.19–3.13 × over HBM-first placement, and HBF outlasts a five-year warranty on the multi-agent trace at a tight SLO even under 24 ×7 operation.
