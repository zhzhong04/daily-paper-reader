## Abstract 

LLM agents increasingly execute complex workflows involving multi-turn reasoning, tool use, and parallel agents. Efficient serving requires decisions that span two layers with complementary information: the agent harness understands workflow dependencies, context lifecycles, and execution objectives, whereas the inference engine observes request queues, KV-cache state, resource pressure, and execution capabilities. Existing interfaces do not systematically connect these views, limiting workflow-aware execution. We propose HEAR , a bidirectional Harness–Engine pAiRing protocol 

for agentic LLM serving. HEAR standardizes how the harness communicates workflow intent and execution requirements and how the engine returns runtime state, capabilities, and outcomes. By separating protocol semantics from optimization policies, HEAR supports diverse coordination strategies without changing workflow or model semantics. We instantiate HEAR for online cache-aware runtime coordination and workload-aware execution-mode selection for agent roles. Across four conversational and research-agent benchmarks under memory-constrained, concurrent serving, HEAR achieves a 1.61 × batch speedup and reduces median time-to-first-token by 2.23 × on SCBench. Mooncake shows that workflow intent and live engine state provide complementary benefits across load regimes. On BrowseComp-Plus and DeepResearchBench, workload-specific configurations yield 1.23 × and 2.45 × end-to-end speedups, respectively, without observed task-quality degradation. These results establish HEAR as a reusable coordination substrate for efficient agentic LLM serving.

## 1 Introduction 

LLM agents tackle complex tasks through multi-round planning, tool use, and collaboration [27, 28]. Unlike a single generation, these applications execute workflows of interdependent model calls with evolving contexts. An agent harness orchestrates the workflow, maintains context, and manages tool interactions, whereas an inference engine, such as vLLM [11] or SGLang [34], performs model execution, request batching, and KV-cache management. This coordination is difficult because the information needed for execution decisions is split across the two layers. The harness knows request dependencies, context lifecycles, and application objectives, while the engine observes cache residency, request queues, resource pressure, and supported execution modes [4, 20]. Neither view is sufficient in isolation. As illustrated in Figure 1, an engine unaware of future context use may evict KV state immediately before it is needed, forcing costly re-prefilling. Conversely, a harness unaware of cache residency may schedule a cold request before a cache-reusable one, even when both are ready and can be legally reordered. The same information gap affects execution configuration: selecting an appropriate inference mode requires matching harness-visible workload characteristics and objectives with engine-side efficiency, capacity, and quality trade-offs. Effective coordination thus requires a bidirectional interface through which both layers can exchange information and carry out joint decisions. Prior work demonstrates the value of workflow information and runtime feedback for agentic serving [4, 9, 15, 20, 30, 31]. These efforts reveal a more fundamental systems gap: agentic LLM serving lacks a shared control-plane abstraction that connects workflow semantics with runtime execution state. Consequently, individual optimizations must define their own cross-layer signals, control semantics, and operation lifecycles, tightly coupling policies to particular harnesses and inference engines and limiting their portability and composition. To address this missing abstraction, we introduce HEAR , a bidirectional Harness-Engine pAiRing protocol 

for agentic LLM serving. HEAR associates each exchange with the relevant request, context version, or serving instance and organizes communication into four semantic categories. The harness provides Execution Description and Intent and Execution Requirements and Control ; the engine returns State and Capabilities and 

Execution Outcomes . HEAR further defines message force and operation lifecycle by distinguishing description from instruction, preference from requirement, observation from guarantee, and acceptance from completion. Coordination policies determine what information to exchange and what actions to take, whereas HEAR defines what those exchanges mean and how they should be handled. The protocol coordinates how requests from an existing workflow are served without changing the workflow’s task-selection logic or the model’s semantics. We demonstrate the generality of HEAR through two complementary policies operating at different timescales. 

Cache-Aware Runtime Coordination is an online policy that combines harness-provided waiting constraints and future-reuse intent with engine-reported KV residency and queue state to coordinate request ordering and cache retention. Role-specific inference configuration is a coarser-grained policy that maps agent roles and their input–output and concurrency characteristics to engine-supported inference modes using measured efficiency, capacity, and quality profiles. The two policies use the same interaction contract to answer distinct execution questions: which ready request should run next and how requests from each workflow role should be executed .We systematically evaluate HEAR across four conversational and research-agent benchmarks under memory-constrained, concurrent serving. HEAR exposes complementary information that neither layer can exploit alone. On SCBench [13], waiting-protected cache-aware scheduling achieves a 1.61 × batch speedup while reducing median and P95 time-to-first-token by 2.23 × and 1.45 ×, respectively. Mooncake [21] shows that future-reuse intent improves cache retention, but must be conditioned on live engine state to remain beneficial under overload. On BrowseComp-Plus [5] and DeepResearchBench [7], workload-specific role configurations deliver 1.23 × and 2.45 × end-to-end speedups, respectively, without observed degradation in task quality. 2Together, these results show that harness intent and engine feedback are complementary, workload-dependent signals for execution coordination. Our contributions are summarized as follows: • We introduce HEAR , a bidirectional Harness-Engine protocol that associates cross-layer exchanges with requests and contexts, organizes them into four semantic categories, and defines their message force and operation lifecycle. • We instantiate two execution-level coordination policies , online cache-aware runtime coordination and role-specific inference configuration, showing how a common interaction contract supports both runtime scheduling and cache decisions and coarser-grained execution-mode selection. • Through controlled evaluations on SCBench, Mooncake, BrowseComp-Plus, and DeepResearchBench, we show that combining harness intent with engine state improves conversational-serving efficiency and yields 1.23 ×–2.45 × end-to-end speedups for research-agent workflows without observed degradation in task quality. 

## 2 Related Work 

Agent Harnesses and Workflow Orchestration. Agent harnesses such as AutoGen [27], AgentScope [8], LangGraph [24], and Deep Agents [3] support multi-agent communication, stateful control flow, model invocation, context management, and tool use. LangGraph represents dynamic workflows as stateful graphs, while Deep Agents adds planning and subagent delegation. These frameworks determine what agents execute and when model calls become ready, but lack direct access to runtime conditions independently managed by inference engines, including request queues, batching, KV-cache residency, and resource pressure. HEAR 

bridges this boundary by conveying workflow intent and requirements to the engine and returning engine state and execution outcomes to the harness. 

LLM Inference Systems. LLM inference systems improve request-level efficiency through continuous batching [29], chunked prefill [2], and prefill-decode disaggregation [35]. KV-cache optimizations include PagedAttention for flexible allocation and sharing in vLLM [11], RadixAttention for prefix reuse in SGLang [34], asynchronous multi-tier loading and prefetching in LMCache [16, 25], and selective retention, dynamic context selection, or compression in H 2O, SnapKV, OmniKV, and KIVI [10, 14, 17, 32]. These systems provide engine-side mechanisms but do not define how workflow semantics reach the engine or how runtime state and outcomes return to the harness. Rather than replacing their schedulers, cache managers, or execution modes, HEAR provides a bidirectional contract for communicating context lifecycles, future reuse, and execution requirements; discovering engine capabilities; requesting supported operations; and observing their outcomes. 

Cross-Layer Coordination for Agentic Serving. Recent systems combine application structure with runtime feedback for targeted optimizations. Parrot exposes inter-request dependencies, while Agentix prioritizes calls from program history [15, 18]. KVFlow uses workflow structure for retention and prefetching, whereas PBKV predicts dynamic agent invocations [20, 33]. InferCept and Continuum preserve KV state across external-operation pauses [1, 12], while CONCUR controls concurrency using cache pressure [4]. Broader systems include Helium’s query-plan-based caching and scheduling [26], Pythia’s predictability-driven caching, scheduling, and autoscaling [30], Pie’s application-defined inferlets for generation and KV management [9], and an intermediate policy runtime providing shared identities and observation, scoring, prediction, and action primitives [31]. These designs couple cross-layer signals to particular policies or execution substrates. 

HEAR instead standardizes the bidirectional interaction contract between an existing harness and engine without prescribing policies, relocating application logic, or adding a runtime tier. It associates workflow descriptions and controls with requests and contexts, returns engine state, capabilities, and outcomes, and defines message force and operation lifecycle. ## 3 The HEAR Protocol 

HEAR is a bidirectional execution-coordination protocol between an agent harness and an inference engine. It defines what cross-layer messages mean and how they are handled, while leaving individual policies to decide what information to exchange and what actions to take. Figure 2 summarizes the protocol and illustrates how repeated exchanges can coordinate a dynamic workflow as both workflow progress and engine conditions evolve. 

3.1 Scope and Execution Model 

The harness and engine retain distinct responsibilities: the harness manages workflow semantics, i.e., agent roles, dependencies, readiness, and context lifecycles, while the engine manages model execution, request queues, KV caches, and serving resources. HEAR connects these views to coordinate request ordering and admission, cache preparation and retention, and supported execution configurations. It governs how 

workflow-selected requests are served without changing task selection, relaxing dependencies, or modifying model semantics. Workflows may evolve dynamically without being known in advance, and each exchange identifies its associated request, context version, or serving instance, linking workflow requirements to the corresponding engine state and outcomes. 

Illustrative Trace. Figure 2 (right) tracks four agents across decision points 𝑇 0–𝑇 4. At 𝑇 0, the harness queries the current requests of agents A–D, and the engine reports resident KV state for A and C. As agents execute, pause, finish, or create new work, the harness enforces request validity and dependencies, while engine feedback informs admission, ordering, resumption, and KV preparation. This trace illustrates one HEAR-enabled policy rather than a protocol-mandated sequence.

State and Capabilities support decision making, whereas outcomes describe realized effects. The categories specify semantic roles rather than packet formats. A single exchange may contain information from multiple categories, and an implementation may expose only the categories and fields it supports. Capability reports allow the harness to discover this supported subset instead of assuming that every engine implements every control. 

3.3 Interaction Semantics 

Message categories identify the purpose of an exchange but do not determine its force or lifecycle. HEAR therefore defines four additional distinctions, summarized in Table 2. 

Intent vs. Control. Descriptions and predictions provide decision context; only explicit control requests ask the receiver to act. For example, reporting that a context is likely to be reused does not itself request that the engine retain or prepare its KV state. 

Preference vs. Requirement. Preferences are best-effort signals, whereas requirements constrain valid execution. Thus, a cache-aware priority may reorder ready requests but cannot violate workflow dependencies or waiting-time protection; an unsatisfied requirement must be rejected or handled through an explicitly permitted fallback.

The corresponding outcome must distinguish acceptance, completion, rejection, lack of support, and execution failure. Together, these distinctions prevent policies from treating descriptions as commands, observations as reservations, or accepted operations as completed ones. Later decisions can therefore depend on realized engine effects rather than assumptions about previously issued controls. 

3.4 Policy Integration 

Joint-Information Policy. HEAR separates the protocol from the policies that use it. Orchestration methods such as Conductor and Puppeteer derive decisions from task and agent state [6, 19], but application-side information alone does not reveal runtime conditions such as request-level cache residency or queue pressure. HEAR makes these engine-side signals available alongside workflow information, enabling policies to condition execution decisions on both views. We express this joint-information decision as:

## 4 Experiments 

4.1 Experimental Setup 

We evaluate HEAR on two execution decisions that combine harness workflow information with engine state. 

Cache-aware runtime coordination uses rapidly changing cache and queue state to control request ordering and KV retention, evaluated on a controlled closed-loop SCBench workload [13] and a production-derived Mooncake trace [21]. Capability-aware execution configuration combines workload descriptions with engine capability profiles to select role-specific inference modes, evaluated on BrowseComp-Plus [5] and DeepResearchBench [7] using benchmark-specific workflows built on a common LangGraph harness. All policies preserve the original task-selection logic and workflow dependencies. Within each setting, all methods use identical models, inputs, prompts, workflow and tool budgets, and hardware. Policies and method-specific parameters are frozen before evaluation, each arm starts from an independently initialized serving state, and reported results include all failures and retries. We assess end-to-end efficiency and task quality, using request-, token-, and cache-level measurements for attribution. Implementation details and complete results are provided in Appendices A and B.

4.4 Cross-Policy Takeaway 

The two policy families instantiate HEAR at different timescales: cache-aware coordination combines dynamic cache and queue state with harness intent and requirements to control request ordering and KV retention, while capability-aware configuration combines stable engine profiles with workload descriptions and objectives to select inference modes. Both follow Equation 1, since neither layer alone has sufficient information. Across conversational and research-agent workloads, decisions adapt to the workload while the HEAR interface and workflow semantics remain unchanged, demonstrating a common bidirectional contract for workload-specific policies. 10 5 Conclusions 

We introduce HEAR , a bidirectional Harness–Engine protocol that connects workflow intent and requirements with engine state, capabilities, and outcomes while preserving workflow and model semantics. We instantiate HEAR for cache-aware runtime coordination and role-specific inference configuration. On SCBench, waiting-protected cache-aware scheduling achieves a 1.61 × batch speedup while improving median and tail TTFT. Mooncake further shows that future-use-aware retention must account for live queue state under overload. On BrowseComp-Plus and DeepResearchBench, workload-specific role configurations yield 1.23 × and 2.45 ×

end-to-end speedups, respectively, without observed degradation in task quality. These results establish HEAR as a reusable, policy-independent substrate for workload-adaptive coordination across the Harness-Engine boundary, with its benefits determined by the information and controls exposed by the serving stack.

A.2 Cache-Aware Runtime Coordination Settings 

Benchmark Construction and Fair Replay. For both benchmarks, the formal evaluation follows a trajectory recording and replay procedure. We first execute and record a complete trajectory, including request arrival times, input and output lengths, session/turn relationships, and prefix information. For SCBench [13], the original data contain multi-turn interactions but do not provide real user request timestamps. We construct each sample as an independent session and use a Poisson process to simulate initial session arrivals. Except for the coordination policy being compared, all experiments use the same replay trajectory, model configuration, cache capacity, and other serving parameters. 

Coordination and Session-Aware KV Retention. Cache-Aware orders ready requests according to the KV-residency view maintained by the harness. For each request, the harness matches reusable prefix blocks sequentially from the beginning of the prompt. Matching stops at the first missing or evicted block, since 15 subsequent blocks cannot independently form a reusable prefix. The harness separately counts reusable prefix tokens in the GPU and CPU tiers. A request is classified as hot if reusable prefixes cover at least 50% of the prompt, and cold otherwise. Cold requests retain the default priority, while the priority of a hot request is defined as the negative number of reusable KV blocks: priority = −𝑁 reuse ,

where 𝑁 reuse denotes the number of reusable KV blocks. Because the engine schedules requests with smaller priority values first, hot requests are executed before cold requests, and hot requests are further ordered by decreasing reusable-prefix length. The residency view reflects the cache state currently observed by the harness and does not constitute a residency guarantee; when a request actually executes, the engine rechecks the reusable content against the current cache state. Guard is submitted by the harness to the engine at fixed times and supports subsequent updates. Once a request has waited longer than the threshold 𝑊 , the engine promotes it to a protected priority so that later cache-hot requests can no longer bypass it. Protected requests are still ordered according to their waiting order. Session-Aware is independent of the request-scheduling priority above and acts only on KV-cache eviction order. The harness maintains a session-return probability 𝑝 by continuously summarizing completed conversations and their subsequent return behavior, and uses this statistic to provide a continuation estimate for the current session. The estimate is updated only from completed conversations and does not use future information from the current replay. After a request completes, the engine records the corresponding context’s 𝑝 and completion time and computes its retention priority as 

𝑟 = 𝑝 · 𝑒 −idle /400 .

Here, idle denotes the time elapsed since the context’s most recent request completed. Contexts that are more likely to return and have been accessed more recently receive higher retention priority, while the priority gradually decays as idle time increases. 

A.3 Protocol Cost Accounting 

HEAR adds control-plane metadata processing rather than model-side computation. It does not introduce additional model layers or per-token GPU operators; its online work consists of state updates, object lookups, policy-input construction, control handling, and execution-outcome reporting. The computation introduced by OmniKV, H 2O, or SnapKV belongs to the corresponding execution mode rather than to the protocol itself. For cache-aware coordination, Engine KV events update a Harness-maintained residency directory. At each scheduling point, the Harness queries reusable prefix blocks, constructs scheduling preferences, and attaches the applicable waiting requirement. The Engine applies these controls and reports the realized execution order, cache reuse, retries, and errors. For capability-aware configuration, candidate profiling, filtering, ranking, and verification occur during offline development. The online path loads the frozen role-to-mode mapping once at workflow initialization and performs a constant-size lookup when dispatching each model request.
