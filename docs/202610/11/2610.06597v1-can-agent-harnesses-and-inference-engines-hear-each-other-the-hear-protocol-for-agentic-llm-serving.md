## 摘要
LLM 智能体越来越多地执行复杂工作流，涉及多轮推理、工具使用和并行智能体。高效服务需要跨越两个具有互补信息的层面进行决策：智能体框架理解工作流依赖、上下文生命周期和执行目标，而推理引擎则观测请求队列、KV 缓存状态、资源压力和执行能力。现有接口未能系统性地连接这些视角，限制了工作流感知的执行。HEAR 是一种面向智能体化 LLM 服务的双向 Harness–Engine 配对协议。HEAR 标准化了框架如何传达工作流意图与执行需求，以及引擎如何返回运行时状态、能力和结果。通过将协议语义与优化策略分离，HEAR 支持多样化的协调策略，而无需改变工作流或模型语义。我们将 HEAR 实例化用于在线缓存感知的运行时协调，以及针对智能体角色的工作负载感知执行模式选择。在内存受限的并发服务下，跨四个对话与研究智能体基准测试，HEAR 在 SCBench 上实现了 1.61 倍的批处理加速，并将首 token 中位时间缩短了 2.23 倍。Mooncake 表明，工作流意图与实时引擎状态在不同负载状况下提供互补收益。在 BrowseComp-Plus 和 DeepResearchBench 上，针对工作负载的配置分别带来 1.23 倍和 2.45 倍的端到端加速，且未观察到任务质量下降。这些结果确立了 HEAR 作为高效智能体化 LLM 服务的可复用协调基座。

## Abstract
LLM agents increasingly execute complex workflows involving multi-turn reasoning, tool use, and parallel agents. Efficient serving requires decisions that span two layers with complementary information: the agent harness understands workflow dependencies, context lifecycles, and execution objectives, whereas the inference engine observes request queues, KV-cache state, resource pressure, and execution capabilities. Existing interfaces do not systematically connect these views, limiting workflow-aware execution.   HEAR, a bidirectional Harness--Engine Pairing protocol for agentic LLM serving. HEAR standardizes how the harness communicates workflow intent and execution requirements and how the engine returns runtime state, capabilities, and outcomes. By separating protocol semantics from optimization policies, HEAR supports diverse coordination strategies without changing workflow or model semantics. We instantiate HEAR for online cache-aware runtime coordination and workload-aware execution-mode selection for agent roles.   Across four conversational and research-agent benchmarks under memory-constrained, concurrent serving, HEAR achieves a $1.61\times$ batch speedup and reduces median time-to-first-token by $2.23\times$ on SCBench. Mooncake shows that workflow intent and live engine state provide complementary benefits across load regimes. On BrowseComp-Plus and DeepResearchBench, workload-specific configurations yield $1.23\times$ and $2.45\times$ end-to-end speedups, respectively, without observed task-quality degradation. These results establish HEAR as a reusable coordination substrate for efficient agentic LLM serving.

## 一、核心问题与研究动机

- **背景**：LLM 智能体（agent）通过多轮规划、工具调用和多智能体协作完成复杂任务，其执行本质上是**由多个相互依赖的模型调用组成的工作流**，而非单次生成。
- **双层信息割裂**：
  - **Agent Harness（框架层）**：掌握工作流依赖、上下文生命周期、执行目标、请求就绪状态。
  - **Inference Engine（引擎层，如 vLLM/SGLang）**：掌握请求队列、KV 缓存驻留状态、资源压力、可支持的执行模式。
- **割裂带来的实际代价**（图 1 例子）：
  - 引擎不知道上下文即将被复用，可能在复用前一刻驱逐 KV 状态，导致代价高昂的重新 prefill；
  - 框架不知道缓存驻留情况，可能先调度一个冷请求，而忽略了可复用缓存的热请求。
- **现有工作的不足**：已有系统（Parrot、KVFlow、PBKV、Pythia、Pie、CONCUR 等）虽结合了工作流信息与运行时反馈，但各自定义跨层信号、控制语义与操作生命周期，**策略与特定框架/引擎紧耦合**，缺乏一个共享的控制平面抽象，可移植性与可组合性差。
- **论文目标**：提出 **HEAR**（Harness–Engine pAiRing），一个**双向、协议语义与优化策略解耦**的协调基座，在不改变工作流语义和模型语义的前提下，实现工作流感知的 LLM 服务。

## 二、方法论

### 1. 核心思想
- HEAR 定义跨层消息的**含义**与**处理方式**，但不规定具体策略；策略决定"交换什么信息、采取什么动作"。
- 每条交换都与具体请求、上下文版本或服务实例绑定，支持动态演进的工作流。
- 协议**不改变**任务选择逻辑、不放松依赖关系、不修改模型语义，仅协调"已由工作流选定的请求如何被服务"。

### 2. 四类语义消息（表 1）
- **Harness → Engine**：
  - *Execution Description and Intent*：智能体角色与阶段、工作流依赖与就绪状态、请求规模与输出上限、上下文生命周期、已知/预测的未来复用。
  - *Execution Requirements and Control*：调度偏好与等待时间约束、缓存准备/保留/释放请求、允许或请求的执行配置与服务目标。
- **Engine → Harness**：
  - *State and Capabilities*：可复用前缀范围与驻留层级、可分配容量、队列状态、资源压力、支持的控件与配置、校准/估计的执行代价。
  - *Execution Outcomes*：推理与控制请求的状态（接受/完成/拒绝/不支持/失败）、实际配置、允许的回退、缓存复用、延迟、资源消耗、重试与错误。

### 3. 四条交互语义区分（表 2）
- **Intent vs. Control**：描述/预测仅提供决策背景；只有显式控制请求才要求对方行动。
- **Preference vs. Requirement**：偏好是尽力而为信号；需求约束合法执行，未满足必须被拒绝或走显式允许的回退路径。
- **Observation vs. Guarantee**：状态与能力报告不预留资源、不保证未来可用性。
- **Acceptance vs. Completion**：接受 ≠ 完成，需区分接受、完成、拒绝、不支持、失败。

### 4. 策略整合公式
- 联合信息决策：`d_i = π(h_i, s_j)`
  - `h_i`：决策点 T_i 处可用的工作流与请求信息；
  - `s_j`：最新的相关引擎更新（j 与 i 可异步，因两层独立演进）；
  - `π`：选择执行安排或配置。
- 无引擎反馈时退化为 `d_i = π(h_i)`；无工作流信息时引擎仅能做请求局部决策。
- HEAR 兼容已有策略（如 PBKV、Pythia），只需通过适配器暴露所需的描述、观测与控制。

### 5. 两个策略实例（不同时间尺度）
- **缓存感知运行时协调（在线）**：`h_i = (ℛ_i, 𝒞_i, 𝒰_i)`，`s_j = (K_j, Q_j)`；策略输出优先级 `d_i = (p_i, 𝒰_i)`，其中等待保护是强制需求。包含 Cache-Aware、Cache-Aware+Guard-W、Session-Aware。
- **角色特定推理配置（粗粒度）**：候选空间 `𝒞 = {vLLM, OmniKV} × {vLLM, H2O, SnapKV}`，离线校准、过滤、排序、验证并冻结映射 `d*_BCP = (vLLM, H2O)`、`d*_DRB = (OmniKV, H2O)`，运行时仅做常量级查表。

## 六、主要结论与发现

- **SCBench**：Cache-Aware 将 KV 复用率从 19.2% 提升至 87.6%，中位 TTFT 从 63.1s 降至 4.6s；加入 Guard-40 后实现 **1.61× 批处理加速**，中位/P95 TTFT 分别改善 **2.23×/1.45×**，同时保留缓存收益。
- **Mooncake**：最优策略随负载变化——50% 负载下 Session-Aware 主导（复用率 19.5%→31.9%）；75% 下组合策略最佳；100% 下 Cache-Aware 在 P50/吞吐上更优，Session-Aware 在尾延迟与复用上更优。**无单一策略在所有负载下占优**，说明意图与实时状态是互补信号。
- **BrowseComp-Plus**：vLLM–H2O 实现 **1.23×** 端到端加速（5.69h→4.62h），Judge 准确率 46.63% vs 46.15%。
- **DeepResearchBench**：OmniKV–H2O 实现 **2.45×** 加速（5.93h→2.42h），RACE 41.1% vs 40.6%。
- **角色级归因**：Reader/子智能体侧选 H2O 收益最大（延迟降低 5.60×/7.22×，prefill 减少 76.2%，缓存复用 6.2%→80.3%）；Main 侧偏好依工作负载而定（短输出偏好 vLLM，长解码偏好 OmniKV）。
- **固定映射代价**：统一使用 OmniKV–H2O 会使 BrowseComp-Plus 墙钟时间增加 7.8%；统一使用 vLLM–H2O 会使 DeepResearchBench makespan 增加 14.0%。
- **总体**：协议接口与工作流语义保持不变，而决策可随工作负载自适应，验证 HEAR 是**可复用、策略无关的协调基座**。

## 七、优点

- **抽象层次清晰**：将"协议语义"与"优化策略"彻底解耦，跨层信号有统一含义与生命周期定义（意图/控制、偏好/需求、观测/保证、接受/完成），显著提升可移植性与可组合性。
- **双向设计**：同时规范 harness→engine 与 engine→harness 两个方向，弥补了以往单向或策略内嵌信号的缺陷。
- **兼容已有工作**：明确说明 PBKV、Pythia 等只需适配器即可复用其预测器与优化规则，定位为"语义基座"而非替代品。
- **实验严谨性**：轨迹回放保证公平负载、参数冻结、含全部失败重试、报告置信区间与配对统计检验、完整六臂结果置于附录。
- **跨尺度验证**：同一契约同时支撑在线毫秒级调度决策与离线粗粒度执行模式选择，证明抽象具有通用性。
- **工程细节完备**：附录给出协议成本核算（表 7）、执行模式参数（表 8、9）、SnapKV prefill 准入控制等实现细节，可复现性较好。

## 八、不足与局限

- **执行模式覆盖有限**：候选空间仅 2×3（vLLM/OmniKV × vLLM/H2O/SnapKV），未涵盖更多引擎（如 SGLang、LMCache）或更多稀疏/量化方法。
- **引擎与框架单一**：仅基于一种 LangGraph 框架与 SparseEngine/vLLM 组合验证，跨框架、跨引擎的通用性缺乏直接实证。
- **Judge 环境不一致**：BrowseComp-Plus 不同 arm 在不同 GPU 上评测，作者承认存在环境差异；DeepResearchBench 初始高并发 Judge 存在 provider 错误需重评。
- **质量评估样本有限**：DeepResearchBench 仅 89 个实例有全部 arm 的有效 RACE 分数；配对质量差异（+0.48%、+0.51%）统计上不显著（p=1.000、p=0.278），"无质量下降"结论的统计效力有限。
- **算力信息不透明**：未披露 GPU 总数、累计机时、能耗或成本，难以评估部署经济性。
