## 摘要
LLM 智能体每一轮都会重新发送其完整对话，而其中大部分已在上一轮处理过。服务系统通过缓存其键值（KV）状态来避免重新计算；当 GPU 内存耗尽时，则将该状态卸载到主机内存。对于智能体而言，卸载会带来不一致的结果：在相同的编程智能体工作负载上，它加速了一种部署，拖慢了另一种部署，而在第三种部署上毫无变化，即便将 token 加载回来的成本比重新计算便宜数倍。原因在于，缓存状态必须存活到再次被使用之时。当一个智能体等待其工具时，服务器会处理所有其他智能体的上下文，因此只有当主机层级能够容纳整个智能体池的可复用上下文（我们称之为复用工作集）时，该智能体的前缀才会被复用。较小的层级会不断写入状态，但这些状态在任何人读取之前就被逐出。我们提出 EfficientAgent，它依据该工作集来确定主机层级的容量并进行管理。一个栈距离模型根据智能体历史估计工作集，以确定主机层级的容量；其实验前做出的预测定位了卸载开始带来收益的容量点。当层级过小时，一种运行时策略会停止写入被逐出上下文的大量重新填充，并继续扩展仍被缓存的前缀；当层级足够大时，它会写入所有内容。在 SWE-bench Verified 编程智能体上，按估计工作集确定容量的主机层级将重新计算的提示 token 减少了 93%，端到端时间减少了 39%。在小型固定层级下，该策略将重新计算减少了 35%；在大型层级下，它避免了因总是过滤写入而导致的 4.3 倍增长。在三种 GPU 类型和两种模型上，当 GPU 每字节主机带宽对应的计算量较少，且主机层级能容纳工作集时，卸载才会带来收益。代码见 https://github.com/KunmingSHAO/efficientagent_release。

## Abstract
LLM agents resend their whole conversation on every turn, and most of it was already processed on the previous turn. Serving systems avoid recomputing it by caching its key-value (KV) state and, when GPU memory runs out, by offloading that state to host memory. For agents, offloading gives inconsistent results: on the same coding-agent workload it speeds up one deployment, slows down another, and changes nothing on a third, even where loading a token back is several times cheaper than recomputing it. The reason is that cached state must survive until it is used again. While one agent waits for its tool, the server processes the contexts of all other agents, so an agent's prefix is reused only if the host tier holds the reusable context of the whole agent pool, which we call the reuse working set. A smaller tier keeps writing state that is evicted before anyone reads it. We present EfficientAgent, which sizes and manages the host tier by this working set. A stack-distance model estimates the working set from agent histories to size the host tier; its predictions, made before the experiments, located the capacity at which offloading starts to pay. When the tier is too small, a runtime policy stops writing large refills of evicted context and keeps extending prefixes that are still cached; when the tier is large enough, it writes everything. On SWE-bench Verified coding agents, a host tier sized to the estimated working set cuts recomputed prompt tokens by 93% and end-to-end time by 39%. With a small fixed tier, the policy cuts recomputation by 35%; with a large tier, it avoids the 4.3-fold increase caused by always filtering writes. Across three GPU types and two models, offloading pays off when the GPU has little compute per byte of host bandwidth and the host tier holds the working set. Code is available at https://github.com/KunmingSHAO/efficientagent_release.

# EfficientAgent 论文总结

## 1. 核心问题与研究动机

- **背景**：LLM 智能体（如编程智能体）以循环方式工作——模型读取任务、调用工具（如运行测试）、读取结果、再次调用模型。每一轮调用都会重发整个对话历史。在 SWE-bench Verified 的真实编程智能体轨迹中，**98.1% 的 prompt token 在上一轮调用中已经处理过**。
- **核心问题**：通过 KV 缓存复用已处理状态是降低智能体服务成本的主要手段；当 GPU 显存不足时，将 KV 状态卸载到 CPU 主机内存。但卸载效果**极不一致**：在同一编程智能体负载上，卸载让 RTX 3090 变快、让 H800 变慢、让 H20 无变化，即便在 H20 上加载一个 token 比重新计算便宜 6 倍以上。
- **根本原因**：缓存状态必须**存活到再次被使用之时**。当一个智能体等待工具执行时，服务器会处理其他所有智能体的上下文，这些上下文会把较早的状态挤出缓存。作者将整个智能体池需要保留的可复用上下文称为**复用工作集（reuse working set）**。
- **关键量化观察**：在 5 GiB 主机层下，等待其他智能体使同一智能体两轮之间的间隔中位数拉长到 9.0 秒（是其自身调用间隔的 14 倍）；97.3% 的新 KV 会在任务下一次调用中再次出现，但 **79.2% 写入主机层的 KV 块在下一次调用前就被逐出**并被迫重算。
- **整体含义**：卸载是否有效由两个独立因素决定——**硬件**决定一次主机命中省下多少计算（由每字节主机带宽对应的峰值算力决定），**工作集**决定命中是否存在。现有系统按 token 逐条决策（能加载就加载、新算就存），忽略了第二个因素。

## 2. 方法论

### 2.1 核心思想
用**复用工作集**统一决定主机层的**容量**与**写入策略**：容量按工作集估计配置；运行时按工作集与容量的关系决定是否准入新写入。

### 2.2 关键技术细节

- **卸载收益比（OBR）**：衡量恢复一个缺失前缀能省下多少重算时间。
  - `T_rec(n) = n·t_pf`（重算时间），`T_load(n) = n·β_rank/B_eff_H2D + τ_load`（加载时间）
  - `OBR(n) = 1 − T_load(n)/T_rec(n)`
  - H20 上恢复中位数 0.86 μs/token/rank，而预填至少 5.6 μs/token，故长前缀 OBR ≥ 0.84；固定模型下该下界随每字节主机带宽算力上升而下降。
- **栈距离模型**：每个 KV 块由内容键标识，`D(k)` 为两次引用之间被引用的不同块数。在容量 C、块大小 b token、LRU 全相联模型下，块存活条件为 `D(k) < ⌊C/(b·β_rank)⌋`。
- **前缀覆盖约束**：可用覆盖是从前缀起点开始的**连续命中段**（consecutive run），而非孤立命中；模型计算主机前缀覆盖后减去 GPU 常驻部分。
- **工作集尺度**：在积压池中，`b·C_reuse ≈ (A−1)·N̄·β_rank`（A 为活跃池大小，N̄ 为平均 prompt 长度）。
- **压力比**：`γ_G = A·N̄/K_G`（池上下文 / GPU KV 容量），`γ_H = b·C_reuse/C_H`（工作集 / 主机容量）。`γ_G > 1` 提供卸载机会，`γ_H > 1` 意味着主机层无法容纳复用内容。
- **容量条件写入准入（核心运行时策略）**：
  - `p_t = 1[b·C_reuse > C_H] ∧ 1[层已满且正在逐出]`
  - `save(r) = ¬(p_t ∧ u > κ)`，其中 `u` 是请求新需要的满块数，`κ` 为写入阈值。
  - 压力成立时，只保存对已常驻前缀的**增量扩展**，拒绝大的**重新填充**（已逐出的上下文）；压力解除时写入全部。每次请求仅一次常数时间检查。
  - 对照端点：`p_t ≡ 0` 为无写入准入的 offload，`p_t ≡ 1` 为固定写入准入（对所有请求过滤）。
- **命题 1（LRU 性质）**：若 LRU 层只在未命中且该块下次复用距离 `D ≥ K_H`（或不再被引用）时拒绝插入，则所有在完全准入下命中的引用在受限策略下仍会命中，且每个块的命中数不降。该性质形式化了处理器缓存中的缓存绕过、死块预测等原理。
- **实现载体**：构建在 **LMCache**（vLLM 的 KV 缓存层）之上；主机层分块 1,024 token，sha256_cbor 哈希；遥测每秒发布一次层占用与逐出量；去重在每个 GPU worker 每次拷贝前执行。

### 2.3 三个贡献
1. 并发智能体服务模型：分离"命中的价值"与"命中是否发生"，按工作集定容并**在部署前预测更多主机内存何时不再有帮助**。
2. 工作集感知的 LMCache 准入机制：常数时间规则 + LRU 命题。
3. 两个测量工具（缓存稳定 prompt 长度、依赖保持重放）及其发现。

## 6. 主要结论与发现

1. **容量转折点存在且可预测**：从 5 到 20 GiB/rank，计算预填从 76.7M 降到 5.3M token（−93.1%），makespan 从 209 降到 128 分钟（−38.7%）；5 GiB 层相比重算毫无改善（212 分钟）。转折发生在 `γ_H` 越过 1 处（工作集估计 11.4 GiB/rank）。
2. **栈距离预测成功定位转折**：运行前预测 20 GiB 下 5.19–5.78M token、80 GiB 下 5.19–5.31M token，实测 5.28M 和 5.29M。
3. **写入准入的效果随容量反转**：
   - 5 GiB 下，固定过滤把计算预填从 76.7M 降到 48.9M（−36%），makespan 降 10.8%。
   - 40 GiB 下，固定过滤反而把计算预填抬高 4.3 倍（5.3M → 22.8M），makespan 增加 30.6%。
   - 容量条件准入在两侧都跟随更优策略：5 GiB 降 35%，40 GiB 避免损失（相对固定过滤降 4.3 倍）。
4. **并发度改变工作集**：A 从 16 减到 8，工作集尺度从 11.4 降到 5.3 GiB/rank，转折点随之左移（3 GiB 层已能恢复前缀）。
5. **硬件比例决定卸载方向**：RTX 3090（2.2K FLOP/byte）与 H20（2.3K）在命中存活时卸载有收益（H20 达 0.60×，RTX 3090 达 0.91/0.92×）；H800（15.5K，高 6.7–7.0 倍）所有 1.08–1.87× 的运行都变慢。
6. **makespan 跟随计算预填**：无论由何种干预造成，17 次运行中 makespan 与计算预填单调对应。
7. **前缀缓存的独立价值**：仅 GPU 前缀缓存就使 RTX 3090 智能体运行快 11.1 倍、2×H800 快 2.19

倍（子集实验）。
8. **GPU 内存比例的耦合效应**：在 8 × H800（内存比例 0.20）上，缩小 GPU KV 容量会同时抬高 `γ_G`（增加卸载机会）与 `γ_H`（加剧主机层压力），因此单纯调整 GPU 内存分配并不能替代主机层容量与准入策略的联合配置。
9. **延迟分布而非均值**：前缀命中主要消除的是长尾中的长预填，因此队列延迟与抢占次数的下降幅度大于平均每 token 延迟的变化；这也解释了为何 makespan 的改善与计算预填量高度一致，而与吞吐的瞬时波动关系较弱。

## 7. 讨论与部署启示

- **卸载不是"更多内存即更好"的单调问题**：论文给出的判据是两条独立条件同时成立才有效——(i) 硬件上 `OBR` 足够高（每字节主机带宽对应的峰值算力低，如 RTX 3090、H20），(ii) 工作集能容纳在主机层内（`γ_H ≤ 1` 或接近）。任一条不满足，卸载要么无收益，要么因逐出-重算循环而变成负收益（H800 上 1.08–1.87× 的减速）。
- **容量规划应先于策略调优**：作者建议以 `b·C_reuse ≈ (A−1)·N̄·β_rank` 估计复用工作集，并据此选择主机层容量；当无法满足时，宁可不做主机卸载，也不要做"半容纳"的卸载。
- **写入准入是容量不足时的必要补偿**：当 `γ_H > 1`，LRU 层会持续逐出尚未复用的块，此时"少写、只写增量"能显著降低无效的 H2D/D2H 流量与重算量；当 `γ_H < 1`，过滤写入反而阻止了未来命中的建立，因此策略必须随压力状态切换，而不能固定。
- **对系统的含义**：该结论与处理器缓存中的缓存绕过（cache bypassing）、死块预测思想同源，说明智能体 KV 缓存管理可以复用经典存储层次的分析工具（栈距离、复用距离分布），只是需要把"前缀覆盖必须连续"这一约束显式纳入。
- **对模型与框架的含义**：工作集尺度与 `N̄`（平均 prompt 长度）、`A`（并发智能体数）成正比，因此长上下文智能体与高并发池会更快触及主机层天花板；减少历史重发（如结构化摘要、工具输出压缩）既降低 `γ_G` 也降低 `γ_H`，与本文的缓存策略互补而非替代。

## 8. 局限性与未来工作

- **负载单一**：仅在 SWE-bench Verified + OpenHands/CodeActAgent 上评估，工具调用模式相对规整（读文件、跑测试、编辑）。其他形态（多轮检索、浏览器操作、长文档问答）的复用距离分布可能不同，`γ_H` 转折点的可迁移性未验证。
- **模型同源**：两个模型均为 Qwen 系列，MoE 与稠密各一，但架构多样性有限；不同 KV 布局、量化方案、MLA/GQA 变体会改变 `β_rank`，进而改变 OBR 下界。
- **理论假设**：栈距离模型假设 LRU 全相联与固定块大小，实际 LMCache 的分块、哈希去重与多 worker 并发拷贝会引入近似误差；命题 1 的成立依赖于"拒绝条件严格基于下次复用距离"，实现中该距离只能通过遥测近似观测。
- **硬件覆盖**：H800 的负收益结论基于少量配置（2 卡 TP2、8 卡低内存比例），未覆盖 NVLink、PCIe 代际、主机内存带宽差异等变量；H20 与 RTX 3090 的收益幅度也依赖具体主机内存配置。
- **未评估**：能耗、成本货币化、多租户公平性、缓存安全（跨租户前缀泄漏）以及写入策略与调度（批处理、优先级）的交互均未展开。
- **未来方向**：把工作集估计从"运行前一次估计"扩展为在线自适应；将准入决策与请求调度、GPU 显存分配联合优化；在更多负载与模型上验证 OBR–工作集二维判据的普适性。

## 9. 总体评价

- **贡献定位清晰**：论文没有提出新的推理算法，而是把一个被普遍误解的经验现象（卸载时快时慢）拆解为两个可独立测量、可独立预测的因素——"命中值多少"（硬件）与"命中是否存在"（工作集），并给出可操作的容量公式与常数时间运行时规则。
- **方法论严谨**：用依赖保持重放固定 token 工作量，使不同策略可在同一负载上逐 token 对比；用栈距离模型在运行前给出预测，再与实测对照，避免了"先跑后解释"的常见问题。
- **结论具有反直觉性且被数据支持**：固定写入过滤在 40 GiB 下使计算预填升高 4.3 倍，而容量条件准入在 5 GiB 与 40 GiB 两侧都跟随更优策略，这一"随容量反转"的现象是本文最有价值的实证发现。
- **实用性强**：规则简单（每请求一次常数时间检查）、可直接构建在 LMCache 之上，部署者只需知道 `A`、`N̄` 与主机带宽即可估算是否值得开主机层。
- **主要不足**：评估负载与模型偏窄，理论模型与实际实现的偏差未做量化敏感性分析，跨硬件结论的样本量偏小；若能在更多智能体形态与更宽的硬件谱系上复现 OBR–工作集判据，本文的结论将从"一个负载上的规律"上升为"服务系统的设计原则"。
