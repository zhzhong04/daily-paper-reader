## 摘要
多 LoRA 智能体系统通过共享一个公共骨干模型，实现了高效的角色专业化。然而，每个智能体都会重复处理不断增长的共享轨迹，并构建自己的 KV 缓存，这在长时程任务中引入了大量内存与计算冗余。现有的 KV 缓存共享方法可以减少这种重复预填充，但它们要么需要额外训练或架构约束，要么仍保留大量模型计算。此外，直接复用缓存会使当前智能体依赖于前一个智能体适配器生成的缓存状态，从而削弱其自身 LoRA 所编码的角色特定行为。我们提出 PReCache，一种无需训练的 KV 缓存共享框架，包含两种设计，即 PreLRShared 和 ReBaseShared；它们共享使用预训练权重计算的基础缓存，并预计算紧凑的、智能体特定的低秩（LR）缓存。为消除重复预填充，PreLRShared 在首次处理共享上下文时预计算每个智能体的 LR 缓存，使当前智能体能够使用自己的 LR 缓存，而无需重新处理先前智能体已处理过的上下文。为提高共享准确性，ReBaseShared 从无适配器的隐藏状态重建共享基础缓存，减少由前一个智能体的适配表示所造成的剩余误差。为最小化其重建开销，我们提出两种分别面向单流推理与并发服务的推理方案，分别在每个智能体回合之后或与其执行同时进行相同重建。在多个模型和智能体基准上，与不使用 KV 缓存共享的推理相比，PreLRShared 实现了最高 3.1 倍的 TTFT 加速和 2.3 倍的每请求吞吐量提升。在评估的缓存共享方法中，ReBaseShared 总体上最好地保持了准确性，相较于不使用缓存共享的推理，平均仅下降 1.1 个百分点。

## Abstract
Multi-LoRA agent systems enable efficient role specialization by sharing a common backbone model. However, each agent repeatedly processes the growing shared trajectory and constructs its own KV cache, introducing substantial memory and computation redundancy in long-horizon tasks. Existing KV cache sharing methods reduce this repeated prefill, but they either require additional training or architectural constraints or retain substantial model computation. Moreover, direct cache reuse causes the current agent to rely on cache states generated by the previous agent's adapter, weakening the role-specific behavior encoded by its own LoRA. We present PReCache, a training-free KV cache sharing framework with two designs, namely PreLRShared and ReBaseShared, that share the base cache computed using the pretrained weights and precompute a compact agent-specific low-rank (LR) cache. To remove repeated prefill, PreLRShared precomputes each agent's LR cache when the shared context is first processed, allowing the current agent to use its own LR cache without reprocessing context processed by previous agents. To improve sharing accuracy, ReBaseShared reconstructs the shared base cache from adapter-free hidden states, reducing the remaining error caused by the previous agent's adapted representation. To minimize its reconstruction cost, we propose two inference schemes tailored to single-stream inference and concurrent serving, performing the same reconstruction after each agent's turn or alongside its execution, respectively. Across multiple models and agent benchmarks, PreLRShared achieves up to a 3.1x TTFT speedup and a 2.3x improvement in per-request throughput over inference without KV cache sharing. ReBaseShared best preserves accuracy overall among the evaluated cache-sharing methods, with an average drop of only 1.1 points relative to inference without cache sharing.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：多 LoRA 智能体系统通过共享一个预训练骨干模型、为每个角色挂载轻量 LoRA 适配器，实现低成本的角色专业化，广泛用于规划、行动、反思等协作式长程任务。
- **核心问题**：尽管骨干共享，每个智能体仍需**独立重复处理不断增长的共享轨迹**（用户请求、检索信息、工具观测、前序智能体输出），并各自构建一份 KV 缓存，导致：
  - **计算冗余**：每个智能体都要对已处理过的上下文重复做 full-length prefill；
  - **内存冗余**：随轨迹变长，各智能体需维护独立的全维 KV 缓存。
- **现有方法局限**：
  - 选择性重计算（DroidSpeak、CacheBlend、RelayCaching）需按比例重算层/Token，精度与效率难以兼得；
  - 偏差校正类方法针对前缀差异，在多 LoRA 前缀匹配场景下退化为 FullShared，缺乏适配器特定校正；
  - LRAgent 的 BaseShared 虽分解出基础缓存与低秩缓存，但仍需当前智能体对累积上下文做完整骨干前向以构建自身 LR 缓存，重复预填几乎未减少；
  - BaseLRShared 需共享 LoRA 下投影，不兼容已有适配器。
- **整体含义**：PReCache 旨在**免训练、不改架构**的前提下，同时降低 KV 缓存内存占用与重复预填计算，并保留各 LoRA 智能体的角色特定行为。

## 2. 方法论

### 2.1 核心思想
- 将适配后的投影输出分解为**共享基础贡献**与**智能体特定的低秩（LR）贡献**：
  - `Y_i = X_{i,adpt} W_0 + (X_{i,adpt} A_i) B_i`
  - 其中 `W_0` 为冻结骨干权重，`A_i ∈ R^{d_in×r}`、`B_i ∈ R^{r×d_out}` 为第 i 个智能体的 LoRA 权重，`r ≪ d_in, d_out`。
- 共享基础缓存 `X_{i,adpt} W_0`，为每个智能体维护紧凑的 rank-r LR 缓存 `X_{i,adpt} A_i`。

### 2.2 PreLRShared：LR 缓存预计算
- **关键操作**：当某段共享上下文**首次**被处理时，对产生的隐藏态 `X_{i,adpt}` 应用**所有**智能体的下投影 `A_k`（k=1…N），一次性构造全部智能体的 LR 缓存。
- **效果**：后续智能体 j 只需复用共享基础缓存与自身预计算的 LR 缓存，**仅对新增上下文 L_C 做适配骨干计算**，无需重新处理累积轨迹 L_P。
- 将原本 full-dim 的骨干重复前向替换为轻量的 rank-r 下投影。

### 2.3 ReBaseShared：中性基础缓存重建
- **动机观察**：共享基础缓存若由前一个智能体的适配隐藏态构建，仍残留前序适配器影响；而由**无适配器隐藏态**构建的“中性基础缓存”更接近当前智能体自身会构建的基础缓存。
- **做法**：禁用 LoRA 适配器处理共享上下文，得到 `X_neut`，构造中性基础缓存 `X_neut W_0`；同时用同一批无适配器隐藏态为其他智能体预计算 LR 缓存。
- **理论条件**（附录 A.1）：定义 `Δ_i = C_i − C_neut`、`Δ_j = C_j − C_neut`，令 `ρ = ‖Δ_i‖/‖Δ_j‖`，`cosθ` 为二者余弦相似度，则前序缓存与中性缓存的相对误差比：
  - `Γ_err = √(1 + ρ² − 2ρ cosθ)`
  - 当 `ρ ≥ 2cosθ`（即 `Γ_err ≥ 1`）时，中性基础缓存相对误差更低。附录 A.2 在 LLaMA-3.1-8B 与 Ministral-8B 上逐层验证该条件成立。

### 2.4 两种推理调度
- **Lazy Prefill（LP）**：当前智能体回合内只跑适配路径；解码结束后，用无适配器骨干对新增上下文 L_C 做一次连续 prefill，扩展中性基础缓存。适合**单流边缘推理**，重建不计入下一智能体的 TTFT。
- **Double Batching（DB）**：在 prefill 与 decoding 阶段同时调度适配路径与无适配器路径，共享同一 token 位置但维护独立 KV 视图；适配路径不影响当前生成。适合**并发服务**，避免单独重建 prefill 造成排队延迟。
- 两种调度产生逻辑等价的缓存状态，仅重建时机不同。

## 6. 主要结论与发现

- **精度**：ReBaseShared 在所有评估方法中总体精度最优，相对 NonShared 平均仅下降 **1.1 个百分点**，与 BaseShared 相当，但消除了其大部分重复预填；PreLRShared 平均下降 1.0–3.3 个百分点，仍优于或接近选择性重计算基线。
- **效率**：
  - PreLRShared 单流 TTFT 最高加速 **3.1×**，每请求吞吐最高提升 **2.3×**；在 66.4k token 时 TTFT 仍接近 FullShared（相差 17% 以内）。
  - ReBaseShared LP 最高 TTFT 加速 **3.0×**、吞吐提升 **1.6×**。
  - 并发服务下，PreLRShared 与 ReBaseShared DB 分别比 NonShared 提升 1.6× 与 1.3× 吞吐，并在高负载下保持更低 TTFT。
- **内存**：在 66.4k token 时，PreLRShared/ReBaseShared 峰值内存接近 FullShared（差距 ≤2%），比选择性重计算基线低 **17–23%**。
- **调度差异**：单流场景 LP 优于 DB；并发场景 DB 优于 LP，二者缓存状态逻辑等价。
- **扩展性**：智能体数从 N=4 增至 N=8 时，PReCache 的 TTFT 仅增 3–7%、内存增 1–2%，远优于 NonShared/BaseShared/选择性重计算的 20–53% 增幅。

## 7. 优点

- **免训练、无架构约束**：直接支持已有不同下投影权重的 LoRA 适配器，不需额外训练或改造模型结构。
- **双设计互补**：PreLRShared 解决重复预填，ReBaseShared 进一步降低前序适配器依赖，兼顾效率与精度。
- **理论支撑**：给出中性基础缓存更优的解析条件（ρ ≥ 2cosθ），并在两个骨干上逐层实证验证。
- **调度适配场景**：LP 与 DB 分别针对单流边缘与并发服务优化，工程实用性较强。
- **实验严谨**：受控轨迹 + 自然轨迹双轨评估，20 次重复运行报告标准差，消融覆盖 rank、投影配置、智能体数量、调度方式，基线设置统一。
- **内存与计算双重收益**：LR 缓存 rank-r 使内存接近 FullShared，同时显著减少 full-dim 计算。

## 8. 不足与局限

- **任务与模型覆盖有限**：仅评测 HotpotQA 与 ScienceQA 两个问答基准、两个 8B 级模型，未覆盖更大模型、多模态或非问答类智能体任务。
- **依赖角色特定 LoRA 训练轨迹**：主实验要求具备各角色 LoRA 训练数据，对无此类轨迹的通用多 LoRA 场景泛化性未充分验证。
- **精度提升存在组间差异**：ReBaseShared 虽平均最优，但个别难度组（如 Ministral 的 ScienceQA Easy、LLaMA 的 ScienceQA Hard）表现低于 NonShared 或 PreLRShared。
- **训练资源未披露**：LoRA 微调的 GPU 数量、时长与总成本未说明，复现成本不透明。
- **QKVO 场景开销增加**：当 key 投影也被适配时，key 侧 LR 缓存需在 RoPE 前展开，Flash-LoRA-Attention 的关联重排不直接适用，带来额外计算开销。
- **基线排除 BaseLRShared**：因架构约束被排除对比，缺少与该类共享下投影方案的直接比较。
- **重建路径的双重计算**：ReBaseShared 需额外一次无适配器前向，虽通过 LP/DB 调度缓解，但仍带来一定吞吐损失（相对 PreLRShared）。
