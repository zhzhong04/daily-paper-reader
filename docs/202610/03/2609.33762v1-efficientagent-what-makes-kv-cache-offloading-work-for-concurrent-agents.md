## 摘要
LLM 智能体在每一轮都会重新发送其完整对话，而其中大部分内容在上一轮已经处理过。服务系统通过缓存其键值（KV）状态来避免重新计算，并在 GPU 内存耗尽时将该状态卸载到主机内存。对智能体而言，卸载带来的结果并不一致：在相同的编码智能体工作负载上，它加速了一个部署，拖慢了另一个部署，而对第三个则毫无改变，即使将 token 加载回来比重新计算便宜数倍。原因在于，缓存状态必须存活到再次被使用。当一个智能体等待其工具时，服务器会处理所有其他智能体的上下文，因此只有当主机层保存了整个智能体池的可复用上下文时，一个智能体的前缀才会被复用；我们称之为复用工作集。较小的层级会不断写入在任何人读取之前就已被逐出的状态。我们提出 EfficientAgent，它根据该工作集来确定主机层的容量并进行管理。一种栈距离模型根据智能体历史估计工作集，以确定主机层容量；其实验前做出的预测定位了卸载开始产生收益的容量。当层级过小时，运行时策略停止写入已被逐出上下文的大量重新填充，并继续扩展仍被缓存的前缀；当层级足够大时，则写入所有内容。在 SWE-bench Verified 编码智能体上，按估计工作集确定容量的主机层将重新计算的提示 token 减少了 93%，端到端时间减少了 39%。在使用小型固定层级时，该策略将重计算减少 35%；在使用大型层级时，它避免了因始终过滤写入而导致的 4.3 倍增长。在三种 GPU 类型和两个模型上，当 GPU 每字节主机带宽对应的计算量很少，且主机层能够容纳工作集时，卸载才会带来收益。代码见 https://github.com/KunmingSHAO/efficientagent_release。

## Abstract
LLM agents resend their whole conversation on every turn, and most of it was already processed on the previous turn. Serving systems avoid recomputing it by caching its key-value (KV) state and, when GPU memory runs out, by offloading that state to host memory. For agents, offloading gives inconsistent results: on the same coding-agent workload it speeds up one deployment, slows down another, and changes nothing on a third, even where loading a token back is several times cheaper than recomputing it. The reason is that cached state must survive until it is used again. While one agent waits for its tool, the server processes the contexts of all other agents, so an agent's prefix is reused only if the host tier holds the reusable context of the whole agent pool, which we call the reuse working set. A smaller tier keeps writing state that is evicted before anyone reads it. We present EfficientAgent, which sizes and manages the host tier by this working set. A stack-distance model estimates the working set from agent histories to size the host tier; its predictions, made before the experiments, located the capacity at which offloading starts to pay. When the tier is too small, a runtime policy stops writing large refills of evicted context and keeps extending prefixes that are still cached; when the tier is large enough, it writes everything. On SWE-bench Verified coding agents, a host tier sized to the estimated working set cuts recomputed prompt tokens by 93% and end-to-end time by 39%. With a small fixed tier, the policy cuts recomputation by 35%; with a large tier, it avoids the 4.3-fold increase caused by always filtering writes. Across three GPU types and two models, offloading pays off when the GPU has little compute per byte of host bandwidth and the host tier holds the working set. Code is available at https://github.com/KunmingSHAO/efficientagent_release.

## 1. 核心问题与整体含义（研究动机与背景）

- **LLM 编码智能体天然重复计算**：智能体每轮都重发完整对话。在 SWE-bench Verified 的编码智能体轨迹中，**98.1% 的 prompt token 已在同一任务上一轮处理过**。仅靠前缀缓存（prefix caching）就能让编码智能体运行最高加速 **11.1×**。
- **KV 卸载收益不一致**：GPU 显存不足时，系统将 KV 状态卸载到 CPU 主机内存，按“回读比重算便宜就回读”的直觉，卸载应总是有益。但同一编码智能体负载下：
  - RTX 3090 上加速；
  - H800 上变慢；
  - H20 上几乎无变化——即使 H20 上加载一个 token 比重算便宜 **6 倍以上**。
- **根因：缓存状态必须存活到再次被使用**。一个智能体等待工具执行时，服务器会处理其他所有智能体的请求，这些上下文会把旧状态逐出缓存。
  - 5 GiB 主机层下，一个智能体两轮之间的中位间隔被拉长到 **9.0 秒**，是其自身调用间隔的 **14 倍**；
  - 一次调用新增 KV 的 **97.3%** 会在任务下一轮再次出现，但 **79.2%** 写入主机层的 KV 块在下一轮前已被逐出，只能重算。
- **核心概念：复用工作集（reuse working set）**。一个智能体的前缀要被复用，主机层必须容纳**整个智能体池**的可复用上下文。工作集随智能体数量和上下文长度增长。
- **两个决定性因素**：
  1. **硬件**：一次主机命中有多值钱，取决于 GPU 的“每字节主机带宽对应的峰值算力”；
  2. **工作集**：是否存在命中，取决于主机层能否装下复用工作集。
- **整体含义**：KV 卸载是否划算，不能只看单 token 的回读/重算成本比，还必须看并发智能体池的复用工作集与主机层容量的关系。论文为并发智能体的 KV 分层提供了容量规划与运行时写入控制依据。

## 2. 方法论：核心思想、关键技术细节与算法流程

### 2.1 核心思想

- 用**栈距离（stack-distance）模型**从智能体历史中估计复用工作集，据此：
  - **部署前定容**：预测不同主机层容量下的重算量，定位“卸载开始产生收益”的容量转变点；
  - **运行时准入控制**：根据工作集是否超过主机层，决定“写入全部新 KV”还是“只扩展仍被缓存的前缀、拒绝大量 refill”。

### 2.2 关键量化模型

- **KV 足迹**：每个 rank 每 token 的 KV 字节数为  
  `β_rank = 2 · L · d · s · max(1, ⌈H_kv / TP⌉)`。  
  例如 Qwen3-Coder-30B-A3B-Instruct 在 TP8 下为 24 KiB/token/rank。
- **卸载收益比（OBR）**：恢复 n 个 token 的前缀相对于重算节省的时间比例：
  - `T_rec(n) = n · t_pf`
  - `T_load(n) = n · β_rank / B_eff_H2D + τ_load`
  - `OBR(n) = 1 − T_load(n) / T_rec(n)`  
  H20 上长前缀的 OBR 至少为 **0.84**；OBR 随 GPU 峰值算力/主机链路字节比升高而下降。
- **栈距离存活条件**：KV 块由依赖整个前缀的内容键标识；`D(k)` 为两次引用同一块之间出现的不同块数。在容量 C 字节、块大小 b token 的全相联 LRU 模型下，块存活当  
  `D(k) < ⌊C / (b · β_rank)⌋`。
- **前缀覆盖约束**：可恢复覆盖必须是**从前缀开头开始的连续块序列**；主机前缀覆盖减去 GPU 常驻部分，才是真正有用的恢复量。
- **工作集规模近似**：在积压池中，`A` 个智能体上下文长度相近（均值 `N̄`）时，  
  `bC_reuse ≈ (A − 1) · N̄ · β_rank`。
- **两个压力比**：
  - `γ_G = A · N̄ / K_G`：池上下文 / GPU KV 容量；`γ_G > 1` 才有卸载机会；
  - `γ_H = bC_reuse / C_H`：工作集 / 主机容量；`γ_H > 1` 表示主机层装不下复用工作集。
