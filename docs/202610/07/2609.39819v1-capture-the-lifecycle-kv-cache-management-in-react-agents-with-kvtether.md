## 摘要
长上下文推理与行动（ReAct）智能体的高效服务依赖于 KV 缓存复用，以降低大语言模型（LLM）预填充延迟和经济成本。然而，智能体执行框架与底层服务栈之间存在语义鸿沟。通过上下文变更、工具执行和子智能体协调，上下文消息可能处于活跃参与、被永久丢弃或暂时未使用状态，而服务栈只能观察到对相应 KV 缓存的访问。这种生命周期盲区使得仅基于新近性的策略（如 LRU）无法及时回收失效 KV，也无法保留那些会比更新条目更早被复用的较旧 KV。我们提出 KVTether，一个面向 ReAct 智能体的生命周期感知 KV 缓存管理框架。通过追踪嵌入在智能体执行框架中的语义原语，KVTether 在高动态执行过程中捕捉运行时生命周期语义。KVTether 随后将消息级语义转换为 KV 级生命周期状态，并利用这些状态驱动按状态优先的缓存管理，而无需向智能体执行框架暴露物理复杂性。在回收失效 KV 后，KVTether 优先保留正在等待复用的存活但空闲 KV，减少复用前的过早驱逐。在智能体基准测试和生产工作负载中，相对于 LMCache 和 MORI，KVTether 将端到端请求延迟分别最多降低 26.3% 和 17.4%，并将估计任务成本平均降低 40.0% 和 33.2%。

## Abstract
Efficient serving of long-context reasoning-and-acting (ReAct) agents relies on KV cache reuse to reduce large language model (LLM) prefill latency and monetary cost. However, a semantic gap exists between agent harnesses and the underlying serving stack. Through context mutation, tool execution, and subagent coordination, context messages may become actively engaged, permanently discarded, and temporarily unused, while the serving stack only observes accesses to the corresponding KV cache. This lifecycle blindness prevents recency-only policies such as LRU from reclaiming dead KV promptly and from preserving older KV that will be reused sooner than newer entries.   We present KVTether, a lifecycle-aware KV cache management framework for ReAct agents. By tracing semantic primitives embedded in agent harnesses, KVTether captures runtime lifecycle semantics during highly dynamic execution. KVTether then translates message-level semantics into KV-level lifecycle states and uses these states to drive state-prioritized cache management without exposing physical complexities to agent harnesses. After reclaiming dead KV, KVTether preferentially preserves live-but-idle KV that is waiting for reuse, reducing premature eviction before reuse. Across agent benchmarks and production workloads, KVTether reduces end-to-end request latency by up to 26.3% and 17.4% relative to LMCache and MORI, respectively, and lowers estimated task cost by 40.0% and 33.2% on average.

# KVTether 论文结构化总结

## 1. 核心问题与整体含义（研究动机与背景）

- **背景趋势**：LLM 应用正从聊天机器人演进为自主智能体（Claude Code、Codex、OpenClaw、Hermes 等），它们通过 ReAct 循环交替进行 LLM 推理与工具调用。单个请求可累积数十万 token（如 Codex 请求可达 258K token），对应 GLM-4.7 下高达 93GB 的 KV 缓存，KV 复用成为降低 prefill 延迟与成本的关键。
- **核心问题——语义鸿沟（Semantic Gap）**：
  - 应用层（agent harness）通过消息级操作（append、replace、remove、fork、one-shot 构造）管理上下文，定义消息的**逻辑生命周期**；
  - 底层服务栈（vLLM、SGLang、LMCache、MoonCake Store）只观察到缓存页、共享前缀与访问事件，**无法分辨 KV 是逻辑存活、显式保留、暂时等待还是已死**。
- **两种由生命周期盲区导致的缓存失效**：
  - **活性失效（僵尸 KV 驻留）**：压缩子智能体用摘要替换长历史后，被丢弃的历史与一次性上下文逻辑上已死，但其 KV 仍驻留至被动驱逐。重放显示僵尸 KV 最高占 LMCache 容量的 **36.3%**（MORI 下最高达 49.7%）。
  - **排序失效（错误方向驱逐）**：LRU 认为最近使用的 KV 最接近复用，但 ReAct 中新产生的 KV 常进入等待工具/子智能体/调度的阶段。跨三种负载，LRU 的 **71.0%–95.0%** 驱逐为“错误方向”（被换入的 KV 比被换出的 KV 更晚被复用）。
- **整体含义**：生命周期语义无法从下游推断，必须由 harness 在运行时显式导出；而现有工作（语义无关的 KV 基座、基于预定义工作流的 KV 管理、基于预测的策略）都无法覆盖“harness → cache”的完整生命周期路径。

## 2. 方法论

### 2.1 核心思想
将消息级生命周期语义从 harness 导出，翻译为 KV 级生命周期状态，并以**状态优先**的方式驱动缓存准入、回收与驱逐；把不确定性收窄到“存活但空闲（suspended）”这一层后再做排序优化，而不依赖精确的复用时刻预测。

### 2.2 三大模块

**（1）语义原语模型（Semantic Primitive Model）**
- 选择 **消息级上下文操作** 作为稳定抽象（而非按子智能体功能分类，因为同一功能在不同 harness 中上下文需求不同）。
- 提供 8 个原语：
  - 消息编辑：`append`、`replace`、`remove`
  - 上下文创建：`fork`（子上下文共享父前缀）、`spawn`（独立子上下文）
  - 生命周期声明：`one_off`（仅一次推理）、`pin`（长期保留）、`unpin`（解除保护）
- 表达力覆盖空间演化（增/改/删/序变）与时间需求（一次性、跨轮复用、显式保留）；复杂功能可由原语组合表达。集成方式为子类化既有 `ContextManager`，不暴露 token/KV 物理细节。

**（2）事件驱动生命周期管理器（Event-Driven Lifecycle Manager）**
- **KV 范围解析**：以 context 为管理单元，维护消息→token/KV 范围映射；遵循与推理引擎相同的 prompt 格式化与分词路径。
  - 消息级事件按位置平移；`remove`/`replace` 因**前缀依赖有效性**导致缓存后缀失效，映射为后缀失效；
  - 受 **KV 存在性** 约束，仅在推理边界应用 token/KV 更新，推理间按程序顺序串行处理事件。
- **生命周期状态**（针对每个 context 中每个消息版本）：
  - `Pinned`：显式长期/临时保护；
  - `Active`：新追加或正在参与 LLM 请求；
  - `Suspended`：LLM 开始解码后转入（存活但空闲）；
  - `Discarded/Expired`：生命周期终结；`Temporary`：一次性上下文，其独占 KV 绕过复用存储。
- **运行时迁移**：context spawn/fork 时开始监控；prefill 完成将 Active→Suspended，下轮请求前再激活；context 终止时普通消息→Expired，Pinned 保留保护；`unpin` 回退到 Suspended 或 Expired；`fork` 后父子状态独立演化。
- **共享 KV 管理**：为每个 token 的 KV 聚合跨 context 的所有消息版本状态，取**最高优先级状态**用于驱逐决策；仅当所有映射版本均 Discarded 时才可回收。

**（3）状态引导的 KV 缓存引擎（State-Guided KV Cache Engine）**
- **状态优先准入算法（Algorithm 1，FreeByState）** 按顺序：
  1. 若到达 KV 为 `Temporary` → 直接 bypass，不进入复用存储；
  2. 先回收 `Expired` KV；
  3. 再驱逐 `Suspended` KV；
  4. 再回退到 `Active` KV；
  5. 若到达 KV 为 `Pinned`，才与 `Pinned` KV 竞争；
  6. 若 Δ≤0，则准入。
- **Suspended 层内采用 MRU（most-recently-used）而非 LRU**：
  - 观察依据：复用并不集中在最年轻年龄，而是聚集在写回后数秒——Agent-G 中 43.1% 在 1–3s，Codex 中 46.6% 在 3–6s，Agent-X 中 87.5% 在 2–4s；
  - 因此高压下优先驱逐“刚挂起”的 KV，保留已等待更久、更接近复用的 KV；
  - 强调该设计依赖 ReAct 执行诱导的**稳定方向性趋势**，而非精确的逐项预测。

### 2.3 实现要点
- harness 侧同步记录原语调用（保持顺序）、异步导出事件（不在关键路径）；服务端 Python 生命周期管理器复现推理引擎的 prompt 格式化与分词，并在 LLM 调用前传递 call ID 与 context ID。
- 分离**全局生命周期控制**（是否留在可复用 KV 空间）与**分层缓存**（某层是否保留快速副本）；支持 GPU HBM / 主机内存 / 远程内存多级缓存，兼容 LMCache、MoonCake Store 等后端。

## 3. 实验设计

- **数据集 / 场景**（3 种 ReAct 负载）：
  - **Codex**：自部署的软件工程智能体，运行 TerminalBench 任务，LLM 请求由 DeepSeek-V4-Pro 服务；
  - **Agent-X / Agent-G**：某大型云厂商部署的两个生产级编码智能体轨迹，各 400 条任务，合计峰值超 27,000 活跃会话；
  - 单请求特征：3–127 轮 LLM、9K–374K prefill token、3–134 GB KV、1–47 种工具类型、子智能体 LLM 轮次占比 1.6%–86.5%。
- **Benchmark / 评估方式**：在真实三节点集群上重放轨迹，按记录的每轮输入 token 数构造随机 prompt，精确匹配可复用前缀长度；用等待记录时长模拟工具调用以消除工具执行时间波动；保留消息边界、前缀共享、fork 继承与后缀失效；每轨迹 5 个 RPS 点、泊松到达。
- **对比方法**：
  - **LMCache (LMC)**：基于页访问新近度的 LRU 驱逐；
  - **MORI**：按“相对空闲度”（近期工具调用时间占比）排序的 agent-aware 基线，含两层准入控制。
- **评估指标**：KV 缓存命中率、累计 prefill 时间、端到端延迟、平均任务定价（按 DeepSeek-V4-Pro 峰值费率 $0.044/$1.32/$3.96 每百万 cache-hit 输入 / cache-miss 输入 / 输出 token 估算）。
- **消融设置**：
  - `KVTether w/o LT`：关闭生命周期追踪与状态优先管理，保留 MRU；
  - `KVTether w/o RO`：保留生命周期追踪与状态优先级，但在 Suspended 层用 LRU 替代 MRU。

## 6. 主要结论与发现

- **命中率**：KVTether 相对 LMCache 与 MORI 平均绝对命中率提升 **33.3% 与 24.5%**，最高提升 47.8% 与 36.4%；高负载下退化更平缓（Agent-X 最高负载时 LMCache 10.2%、MORI 35.7%，KVTether 达 49.5%）。
- **性能与成本**：prefill 时间平均降低 29.2% 与 23.3%（最高 41.2% / 33.2%）；端到端延迟平均降低 16.5% 与 12.4%（最高 **26.3% / 17.4%**）；估算任务成本平均降低 **40.0% / 33.2%**（最高 53.6% / 44.1%）。延迟收益小于 prefill 收益，因解码仍不可避免。
- **消融结论**：
  - 仅改驱逐顺序不够：无生命周期追踪时 MRU 平均命中率低 25.6%，甚至可能劣于 LRU 的 LMCache（Codex 最低 RPS 下 20.8% vs 36.1%），僵尸页平均占 21.4%–38.5%；
  - 仅回收死 KV 不够：w/o RO 的错误方向驱逐率仍达 65.6%–92.3%，KVTether 降至 25.7%–38.7%。
- **可落地性**：集成到 6 个 harness 仅需 **26–216 行代码**/harness（上下文管理器 14–162 行 + 语义函数 12–54 行），运行时开销可忽略。

## 7. 局限性与批判性讨论

- **对 harness 显式集成的强依赖**：KVTether 的核心前提是应用层能够调用语义原语并导出事件。对于闭源、不可修改或跨组织的 agent harness，这一前提可能不成立；此时只能退化为基于访问模式的启发式管理，无法获得生命周期语义带来的收益。
- **原语模型的覆盖边界**：8 个消息级原语在本文覆盖的 ReAct 负载中表达力充分，但未来 agent 可能出现更复杂的上下文演化，例如细粒度 token 级编辑、多分支合并、跨会话长期记忆注入、动态权限过滤等。消息级抽象可能无法精确表达这些场景，导致生命周期状态误判或过度保守。
- **状态聚合的保守性**：共享 KV 按 token 聚合跨 context 消息版本状态并取最高优先级，虽然保证安全，但可能使某些实际已死或可回收的 KV 因残留高优先级映射而延迟回收，尤其在 fork 频繁、父子状态长期分化的场景中可能损失部分容量效率。
- **MRU 策略的负载依赖性**：Suspended 层采用 MRU 而非 LRU，依赖 ReAct 执行中“复用集中在写回后数秒”的方向性趋势。若工作负载变为长思考、长工具调用、批量离线推理或非 ReAct 交互模式，该趋势可能减弱甚至反转，MRU 的收益不再成立，需要重新校准或自适应切换策略。
- **事件同步与推理边界的约束**：为遵守 KV 存在性约束，token/KV 更新仅在推理边界应用，事件按程序顺序串行处理。这在极高并发或异步工具调用密集的场景下可能引入事件排队与状态滞后，影响驱逐决策的实时性。
- **重放实验的保真度限制**：如第 5 节所述，轨迹重放使用随机 prompt 匹配 token 数、模拟工具调用等待，且部分生产轨迹为离线日志重建。真实 prompt 的语义分布、工具执行抖动、网络与调度竞争可能改变缓存访问模式，结论的绝对数值需谨慎外推。
- **成本与部署假设**：成本估算基于特定模型费率与特定硬件配置（GB200、MoonCake 传输引擎），不同云厂商、不同模型、不同缓存后端下的性价比可能差异较大。跨节点 KV 传输开销、主机内存带宽瓶颈、多租户隔离成本也未充分展开。
- **安全、隐私与公平性**：生命周期管理器需要感知消息内容边界与上下文关系，可能接触敏感元数据；在多租户环境中，共享 KV 的优先级聚合与驱逐策略是否会导致信息侧信道或资源不公平，仍需进一步审视。

## 8. 总体评价与结论

KVTether 抓住了 LLM agent 服务中一个真实且日益尖锐的矛盾：应用层以消息为单位管理逻辑上下文，而缓存层只看到物理 KV 页与访问事件。论文没有停留在“预测下一次复用”的精度竞赛上，而是将问题重新定义为**生命周期语义的显式导出与状态优先管理**，把不确定性收窄到“存活但空闲”这一层，再在该层内利用 ReAct 负载的稳定方向性做排序优化。

从方法上看，语义原语模型、事件驱动生命周期管理器与状态引导缓存引擎三者分工清晰：原语提供稳定抽象，管理器维护消息到 KV 范围的映射与状态迁移，缓存引擎按状态优先级决定准入与驱逐。实现上保持对推理引擎与缓存后端的低侵入性，支持多级缓存，并在 6 个 harness 上验证了仅需 26–216 行代码即可集成。

实验层面，论文在 3 种 ReAct 负载、15 个 RPS 设置下与 LMCache、MORI 对比，并做了两个关键消融。主要发现具有一致性：仅改驱逐顺序不够，仅回收死 KV 也不够，二者必须结合；KVTether 在命中率、prefill 时间、端到端延迟与任务成本上均取得显著且随负载升高更明显的优势。尽管重放保真度、原语覆盖边界与 MRU 的负载依赖性构成主要局限，但论文为“agent-native”推理系统提供了一个可落地、可扩展的方向：让应用层生命周期语义成为缓存管理的头等输入，而非事后从访问模式中猜测。
