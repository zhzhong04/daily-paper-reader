## 摘要
长上下文 LLM 智能体积累的交互历史会给 KV 缓存内存和注意力计算带来压力。尽管稀疏注意力降低了这些开销，但异构的缓存表示与工作流阻碍了其与现有推理引擎的集成，而此前的稀疏服务抽象仅支持特定布局或工作流。我们提出 SparseEngine，一个从底层构建、以稀疏优先的推理引擎，其共享生命周期契约使每种方法都能控制自身的 KV 表示与计算，同时与通用服务基础设施协调状态转换。SparseEngine 支持四大类共 15 种方法，并通过 Chain Cache 实现跨请求状态管理：Chain Cache 可从保留的历史中恢复 KV 驱逐方法；以及可控的 Prefix-Cache Pruning，可在保留逻辑前缀匹配的同时，从选定的历史区域中移除 KV。在保持方法质量的同时，SparseEngine 借助 KV 驱逐实现超过 10 倍的吞吐量提升，在相同并发下解码速度比 vLLM 快 2.5 倍以上，并在智能体基准测试上实现超过 2 倍的端到端加速。代码见 https://github.com/CURRENTF/SparseEngine。

## Abstract
Long-context LLM agents accumulate interaction histories that strain KV-cache memory and attention computation. Although sparse attention reduces these costs, heterogeneous cache representations and workflows hinder integration with existing inference engines, while prior sparse-serving abstractions support only specific layouts or workflows. We present SparseEngine, a ground-up, sparse-first inference engine whose shared lifecycle contract lets each method control its KV representation and computation while coordinating state transitions with common serving infrastructure. SparseEngine supports 15 methods across four categories and enables cross-request state management through Chain Cache, which resumes KV-eviction methods from retained history, and controllable Prefix-Cache Pruning, which removes KV from selected history regions while preserving logical-prefix matching. While maintaining method quality, SparseEngine delivers over 10x higher throughput with KV eviction, over 2.5x faster decoding at matched concurrency than vLLM, and over 2x end-to-end speedup on agent benchmarks. The code is available at https://github.com/CURRENTF/SparseEngine.

## 2. 方法论：核心思想与关键技术

### 2.1 核心思想

- **稀疏优先、从底层构建**：引擎锚定于一个不变量——**模型原生模块执行顺序**；通过沿此顺序暴露细粒度钩子，让每种方法注册回调、组合自己的计算工作流，而**无需修改模型实现**（不需要 LlamaSnapKV 或 Qwen3H2O 这类定制模型）。
- **三大组件构成生命周期契约**：
  1. **SparseController 中的细粒度生命周期钩子**；
  2. **方法定制的 CacheManager**；
  3. **连接方法状态与注意力执行的 AttentionView**。

### 2.2 关键技术细节

- **细粒度钩子**：覆盖 prefill 与 decode 两个阶段，在**注意力前/后**、**每层结束**、**每步结束**提供扩展点。`SparseMethodRuntime` 在初始化时选定并实现方法特定回调，这些回调跨 prefill 分块、decode 步、Transformer 层组合打分、选择与状态更新操作。
  - prefill 阶段 `finish_step` 支持 H2O 的分块驱逐（基于累积注意力分数）与 SnapKV 在最后一个 prompt 分块后的选择与驱逐，同时**保持 chunked prefill**；
  - decode 阶段 `build_decode_selection` 执行 Quest 的查询相关页选择，`finish_step` 更新 H2O 累积分数并执行在线驱逐；
  - `on_layer_end` + `build_decode_selection` 组合使 OmniKV、DeltaKV 能跨后续层复用观测层索引。
- **方法定制的 CacheManager**：拥有方法特定的状态与存储，定义 KV 表示、物理布局、位置映射以及分配/写入/更新/释放操作，并维护与 KV 状态对应的持久元数据。
  - 区分**物理驱逐**（更新保留槽映射与上下文长度，把丢弃槽归还分配器）与**逻辑选择**（仅改变注意力读取哪些常驻条目）；
  - 示例：SnapKV 压缩与 H2O 驱逐联合更新保留位置、方法统计与可用容量；OmniKV 对常驻 KV 施加跨层选择；KIVI 管理量化 KV 页、量化元数据与非量化残差区。
- **AttentionView**：把方法持有的缓存表示连接到注意力执行，公式为
  - `View_{ℓ,t} = BuildView(C_{ℓ,t}, I_{ℓ,t})`
  - `o_{ℓ,t} = Attention(q_{ℓ,t}, View_{ℓ,t})`
  - 其中 `C_{ℓ,t}` 是持久缓存状态，`I_{ℓ,t}` 标识被选中的 token 或页。视图描述可访问数据及其物理布局，底层状态可为显式 KV 张量或 MLA 潜向量与位置状态加方法元数据；支持对选中、压缩、量化或临时重建的 KV 做注意力，而持久状态管理仍归 CacheManager。
- **执行概览**：调度器按 prefill 分块处理 prompt，再将采样 token 回馈做下一步 decode；向 MemoryOracle 查询方法特定的容量与预留需求，并在各 GPU rank 间协调执行。
- **CUDA Graph 支持**：缓存管理器、方法运行时与注意力实现提供地址在重放期间保持稳定的缓冲区；step preparation 更新槽映射、长度等可变输入；图与布局兼容性在配置执行路径时检查。

### 2.3 扩展的稀疏状态管理

- **Chain Cache（跨轮次复用被驱逐方法的压缩状态）**：
  - 传统 radix 前缀缓存假设 KV 完整常驻；驱逐类方法（SnapKV、KVzip、H2O）丢弃条目会破坏该假设。
  - `ChainCacheIndex` 把会话与其逐层保留 KV、方法元数据、逻辑 token 前缀关联；**逻辑前缀仍可用于匹配，即使部分物理 KV 已被移除**。
  - 每个会话获得 `chain_id`；续接请求必须匹配此前处理过的逻辑前缀（但不要求每个匹配 token 都有常驻 KV）；请求完成后 chain 转为 idle，CacheManager 保留逐层 KV 与元数据；匹配的续接重新挂载该状态，仅 prefill 未处理的后缀。
  - 容量不足时按 **LRU 顺序**回收 idle chain 及其状态。对 H2O/SnapKV 这类**不同层保留不同 token 位置**、或需要持久统计（如 H2O 累积注意力分数）的方法尤为重要。
- **可控 Prefix-Cache Pruning**：
  - 应用提交完整 `token_ids` 序列与剪枝区间 `[L, R)`，定义目标集合 `T = {i | L ≤ i < R}`；打分策略（SnapKV、KVzip）在 `T` 内选出保留位置并返回掩码；缓存管理器仅对**无活跃引用或在途传输的 idle 块**施加该掩码。
  - 设 `P` 为逻辑 token 前缀、`R` 为有常驻 KV 的位置，保留 `I ⊆ R ∩ T` 后：
    - `P' = P`（逻辑前缀不变）
    - `R' = (R \ T) ∪ I`（物理槽被释放）
  - 后续请求仍能匹配同一前缀，但只复用其保留的 KV；图 4 示例为对 `[L,R)`（L=4, R=12）做 KVzip 选择。

  - 复现材料完整：开源代码 + 附录 B/C 的接口、缓存机制、评测协议、硬件配置与超参。
- **不足/可商榷之处**：
  - 端到端服务性能主要依赖轨迹重放与专用 Gasai trace，**真实在线多租户负载**（突发流量、混合长短请求）的验证相对有限。
  - 跨会话复用（Chain Cache）的核心收益在 H2O/SnapKV 等"逐层保留不同位置"的方法上最突出，但对**无状态或层间一致保留**的方法收益可能被高估，论文对该边界的讨论不够显式。
  - 部分方法（如 FP8 KV、TurboQuant）与量化硬件特性强相关，结论在不同 GPU 代际（H100 vs 4090/5090）间的可迁移性需读者自行判断。
  - 未报告训练时长——这对推理引擎合理，但也意味着无法评估方法自身的**离线校准/统计预热**开销。

## 6. 主要结论与发现

- **抽象边界的重新划定是可行的**：把接口从"特定缓存布局/工作流"上移到"统一的方法生命周期契约"（细粒度钩子 + 定制 CacheManager + AttentionView），能在**同一引擎**中容纳 15 种异构稀疏方法，而无需为每种方法定制模型实现。
- **性能优势**：在方法匹配的公平对比中，SparseEngine+Quest 相比 Vortex 提升 **1.24×**、相比 HiSparse 提升 **1.55×**；SparseEngine+SnapKV 相比 Tangram 提升 **1.55×**，说明统一抽象并未以牺牲性能为代价。
- **质量保持**：在 LongBench V1/V2、AIME 2024、SWE-Bench Lite、Claw-Eval 上，各稀疏方法在 SparseEngine 中的表现与官方实现相当，表明引擎化封装不引入额外的精度损失。
- **有状态推理需要新的缓存语义**：传统 radix 前缀缓存假设 KV 完整常驻，与驱逐类方法冲突；Chain Cache 通过"逻辑前缀可匹配、物理 KV 可缺失"的关联机制解决了这一问题，并支持按 LRU 回收 idle chain。
- **可控前缀剪枝可行**：应用可指定 `[L, R)` 剪枝区间，由打分策略在区间内选择保留位置，缓存管理器只对 idle 块施加掩码，逻辑前缀 `P` 不变而物理保留集合 `R' = (R \ T) ∪ I`，从而在释放物理槽的同时维持前缀匹配能力。
- **CUDA Graph 与稀疏执行可兼容**：通过稳定地址缓冲区 + 每步更新可变输入（槽映射、长度）的设计，稀疏方法在重放期间不会破坏图捕获。

## 7. 局限与未来方向（基于论文的客观推断）

- **抽象层级的权衡**：细粒度钩子虽通用，但每引入一种新方法仍需实现 `SparseMethodRuntime` 回调与配套 CacheManager，方法开发者的**心智负担**与引擎核心的耦合度需持续观察。
- **状态管理的复杂度**：Chain Cache 需要跨请求持久化逐层 KV、方法元数据与逻辑前缀，元数据规模与匹配开销在**超长会话、超多并发**下的可扩展性值得进一步量化。
- **硬件异质性**：结论覆盖 H100/H20/RTX PRO 6000/4090/5090，但不同代际的显存带宽、量化指令支持差异可能影响各方法的相对排名，论文未给出跨代际的系统性对照。
- **潜在方向**：将生命周期契约进一步标准化为可插拔的"方法 SDK"；把 MemoryOracle 扩展为支持跨请求的容量博弈/公平调度；探索 Chain Cache 与分布式 KV 存储（如分离式 prefill/decode 架构）的结合。

## 8. 总体评价

SparseEngine 的贡献不在于提出新的稀疏算法，而在于**重新定义了稀疏推理引擎的抽象边界**：以"模型原生模块执行顺序"为锚点，通过生命周期钩子、方法定制 CacheManager 与 AttentionView 三者构成的契约，把异构稀疏方法的**状态管理与计算控制**从共享服务基础设施中解耦出来。实验在方法覆盖广度（15 种方法、14 种模型变体、四类注意力结构）、评价维度（质量 + 系统效率）与公平性设计（原始实现基线 + 抽象匹配对手）上均较为扎实，并开源了完整复现材料。其核心局限在于真实在线负载验证相对有限、跨会话状态管理的规模化开销尚待量化。总体而言，论文为"有状态 LLM 智能体时代"的推理引擎设计提供了一个有说服力的抽象范式与工程验证。
