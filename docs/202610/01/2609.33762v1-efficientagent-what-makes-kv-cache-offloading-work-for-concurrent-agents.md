## 摘要
LLM 智能体每一轮都会重新发送其完整对话，而其中大部分内容在上一轮已经处理过。服务系统通过缓存其键值（KV）状态来避免重计算，并在 GPU 内存耗尽时将该状态卸载到主机内存。对于智能体而言，卸载带来的结果并不一致：在相同的编码智能体工作负载上，它加速了某个部署，却减慢了另一个部署，而对第三个部署毫无影响，即使将 token 加载回来的成本比重新计算便宜数倍也是如此。原因在于，缓存状态必须一直保留到再次被使用。当一个智能体等待其工具时，服务器会处理所有其他智能体的上下文，因此，只有当主机层保存整个智能体池的可复用上下文时，某个智能体的前缀才会被复用；我们将这一可复用上下文称为复用工作集。较小的层级会不断写入状态，而这些状态在任何人读取之前就被逐出。我们提出 EfficientAgent，它依据该工作集来确定主机层容量并进行管理。一个栈距离模型根据智能体历史估计工作集，以确定主机层容量；其在实验前做出的预测定位了卸载开始产生收益的容量点。当该层过小时，运行时策略会停止写入已被逐出上下文的大规模重新填充，并继续扩展仍被缓存的前缀；当该层足够大时，它则写入所有内容。在 SWE-bench Verified 编码智能体上，将主机层容量设置为估计工作集大小，可将重新计算的提示 token 减少 93%，并将端到端时间减少 39%。在较小的固定层容量下，该策略将重计算减少 35%；在较大层容量下，它避免了因始终过滤写入而导致的 4.3 倍增加。在三种 GPU 类型和两种模型上，当 GPU 每字节主机带宽对应的计算量很少，且主机层能容纳工作集时，卸载才会带来收益。代码见 https://github.com/KunmingSHAO/efficientagent_release。

## Abstract
LLM agents resend their whole conversation on every turn, and most of it was already processed on the previous turn. Serving systems avoid recomputing it by caching its key-value (KV) state and, when GPU memory runs out, by offloading that state to host memory. For agents, offloading gives inconsistent results: on the same coding-agent workload it speeds up one deployment, slows down another, and changes nothing on a third, even where loading a token back is several times cheaper than recomputing it. The reason is that cached state must survive until it is used again. While one agent waits for its tool, the server processes the contexts of all other agents, so an agent's prefix is reused only if the host tier holds the reusable context of the whole agent pool, which we call the reuse working set. A smaller tier keeps writing state that is evicted before anyone reads it. We present EfficientAgent, which sizes and manages the host tier by this working set. A stack-distance model estimates the working set from agent histories to size the host tier; its predictions, made before the experiments, located the capacity at which offloading starts to pay. When the tier is too small, a runtime policy stops writing large refills of evicted context and keeps extending prefixes that are still cached; when the tier is large enough, it writes everything. On SWE-bench Verified coding agents, a host tier sized to the estimated working set cuts recomputed prompt tokens by 93% and end-to-end time by 39%. With a small fixed tier, the policy cuts recomputation by 35%; with a large tier, it avoids the 4.3-fold increase caused by always filtering writes. Across three GPU types and two models, offloading pays off when the GPU has little compute per byte of host bandwidth and the host tier holds the working set. Code is available at https://github.com/KunmingSHAO/efficientagent_release.

# EfficientAgent 论文总结

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：LLM 编码智能体以循环方式工作——读取任务、调用工具（如运行测试）、读取结果、再次调用模型。每一次调用都会重新发送到目前为止的完整对话。在 SWE-bench Verified 的轨迹中，**98.1% 的 prompt token 在上一轮已经处理过**。因此，复用这些已处理内容是低成本服务智能体的关键手段：仅前缀缓存就能让编码智能体运行加速最多 **11.1 倍**。
- **核心问题**：当 GPU 显存不足以容纳所有智能体上下文时，系统会将 KV 状态卸载到 CPU 主机内存（host tier），并在后续 prompt 需要时再加载回来。按逐 token 的直觉判断（加载比重算便宜就卸载），卸载"应该总是有益"。但事实并非如此：
  - 同一编码智能体负载下，卸载在 **RTX 3090 上加速**、在 **H800 上变慢**、在 **H20 上无变化**——即使 H20 上加载一个 token 比重算快 6 倍以上。
- **根本原因**：缓存状态必须**存活到被再次使用**。当一个智能体等待工具执行时，服务器会处理所有其他智能体的请求，它们的上下文会把旧状态挤出缓存。在 5 GiB 主机层下，智能体两次调用之间的间隔中位数被拉长到 9.0 秒（是其自身间隔的 14 倍）；**79.2% 写入主机层的 KV 块在被下次读取前就被逐出**，只能重算。
- **关键概念——复用工作集（reuse working set）**：一个智能体的前缀要被复用，主机层必须保存**整个智能体池**的可复用上下文。该工作集随智能体数量和上下文长度增长，约等于 $(A-1)\bar{N}\beta_{rank}$。
- **两个决定性因素**：
  1. **硬件**：决定一次主机命中能节省多少——跨 GPU 表现为"峰值算力 / 每字节主机带宽"之比。
  2. **工作集**：决定是否真的存在命中——若主机层小于工作集，写入的状态在读取前就被逐出，卸载纯属浪费。

## 2. 方法论

### 2.1 核心思想
EfficientAgent 用**复用工作集**同时解决两个问题：**定容**（主机层该多大）与**准入**（哪些新 KV 该写入主机层）。

### 2.2 关键技术细节

- **栈距离（stack distance）模型估计工作集**：
  - 每个 KV 块由依赖整个前缀的内容键标识；定义复用距离 $D(k)$ 为两次引用之间被引用的**不同**块数。
  - 在容量 $C$ 字节、块大小 $b$ token 的全相联 LRU 模型中，块存活条件为 $D(k) < \lfloor C/(b\beta_{rank}) \rfloor$。
  - 前缀恢复有**结构性约束**：可用覆盖必须是从前缀起点开始的**连续块序列**，需扣除 GPU 常驻部分。
  - 积压池（backlogged pool）下工作集规模估算为 $bC_{reuse} \approx (A-1)\bar{N}\beta_{rank}$。
  - 两个压力比：$\gamma_G = A\bar{N}/K_G$（池上下文 / GPU KV 容量，>1 表示有卸载机会）、$\gamma_H = bC_{reuse}/C_H$（工作集 / 主机容量，>1 表示主机层装不下）。
  - 该模型**在实验前**预测出容量转变点（如 H20 上 5→20 GiB 之间）。

- **卸载收益比（OBR）**：
  $$OBR(n) = 1 - \frac{n\beta_{rank}/B^{eff}_{H2D} + \tau_{load}}{n \cdot t_{pf}}$$
  - 衡量"恢复缺失前缀所节省的重算时间比例"，将**命中的价值**与**命中是否存在**分离。
  - H20 上长前缀的 OBR 至少 0.84。

- **容量条件写入准入（capacity-conditioned write admission）**：
  - 压力信号：$p_t = \mathbb{1}[bC_{reuse} > C_H] \wedge \mathbb{1}[\text{tier full and evicting}]$（需两个条件同时成立）。
  - 写入规则：`save(r) = ¬p_t ∧ (u > κ)`，其中 $u$ 是请求需要的**新满块数**，$\kappa$ 是写入阈值（固定为 8）。
  - 直觉：**压力下**只保留对仍被缓存前缀的增量扩展，拒绝大规模"重新填充"（已被逐出的上下文）；**压力解除后**恢复写入全部。
  - 每个请求仅需一次常数时间检查；参数在准入运行前固定。

- **理论支撑（命题 1）**：在 LRU 参考模型下，若仅在"复用距离 $D \geq K_H$ 或不再引用"的缺失处拒绝插入，则**所有在全量准入下命中的引用仍然命中**，且各块与总命中数不减少。这为"缓存旁路/死块预测"原则提供了面向连续前缀覆盖的 KV 层形式化。

- **两个测量工具**：
  - **缓存稳定 prompt 长度（cache-stable prompt length）**：从上次调用起未改变、可复用的 token 数上界。由于缓存键哈希整个前文，**早期一次改写会使后续所有块的键失效**。
  - **依赖保持回放（dependency-preserving replay）**：固定每个调用的 token 与输出，仅让服务决策影响排队与任务交错，实现 token 级可比。

## 6. 主要结论与发现

1. **主机容量决定有效恢复**：5→20 GiB/rank，computed prefill 从 76.7M 降到 5.3M（**−93.1%**），makespan 从 209 降到 128 分钟（**−38.7%**）。5 GiB 层使 makespan 与纯重算持平（212 分钟）。转变点恰在 $\gamma_H$ 跨过 1 处。
2. **并发改变工作集**：池从 16 减到 8，工作集规模从 11.4 降到 5.3 GiB，转变点随之左移；3 GiB 与 4.5 GiB 层已能显著恢复前缀。
3. **写入准入随容量转变而符号反转**：
   - 5 GiB 下，固定过滤写入减少 36% 重算、10.8% makespan；
   - 40 GiB 下，固定过滤写入使重算**增加 4.3 倍**、makespan 增加 30.6%；
   - **容量条件准入在两侧都保持收益**（5 GiB 下重算 −35%、makespan −10.4%；40 GiB 下重算 −4.3 倍、makespan −23.1%）。
4. **makespan 跟随 computed prefill**：跨所有干预（不同策略、不同容量），makespan 与重算量单调对应。
5. **硬件比值决定卸载是否划算**：RTX 3090（2.2K FLOP/byte）与 H20（2.3K）属于低比值设计，命中存活时卸载获益（H20 覆盖工作集时 makespan 为重算的 **0.60**）；H800（15.5K）在所有测得的运行中卸载都变慢（1.08–1.87 倍）。
6. **上下文折叠的陷阱**：由于 KV 键依赖完整前缀，**早期改写会使后续所有块失效**。三种折叠器把前缀命中率从 96.5% 降到 51–61%，且都延长了单实例推理时间。因此上下文编辑应同时以"缓存稳定长度"来评判。

## 7. 优点

- **问题定位精准**：识别出"卸载效果不一致"这一真实且反直觉的现象，并给出简洁有力的解释（缓存存活 vs. 工作集）。
- **理论与系统结合**：将操作系统工作集/栈距离理论（Denning 1968；Mattson 1970）迁移到智能体 KV 层，并补充了**连续前缀覆盖**与 **GPU 常驻扣除**等新量，命题 1 给出了 LRU 下拒绝写入不损失命中的严格证明。
- **预测先于实验**：栈距离模型在部署前定位容量转变点，且与实测吻合（20 GiB 预测 5.19–5.78M vs 实测 5.28M）。
- **策略自适应**：容量条件准入优雅地统一了两个极端（全写 vs 全过滤），按请求逐次选择，代价为常数时间。
- **可复现性强**：依赖保持回放使不同策略在完全相同 token 工作下可比；代码开源；附录极其详尽（含全部运行记录、参数敏感性、参考流分析）。
- **实用工具产出**："缓存稳定 prompt 长度"与"依赖保持回放"对智能体训练/评估流水线的 KV 容量规划有直接价值。

## 8. 不足与局限

- **模型与负载覆盖有限**：仅两个 Qwen-Coder 模型、单一基准（SWE-bench Verified）、单一智能体框架（OpenHands/CodeActAgent）。是否适用于其他智能体形态（如多工具、长链推理、非编码任务）尚不明确。
- **回放而非纯在线**：核心对比依赖依赖保持回放（固定 token 与输出），虽保留真实模型执行，但**无法反映自由生成下任务质量的变化**；在线运行仅 H20 两次（A=16），样本偏少。
- **能耗未测量**：作者明确说明只报告运行时与计算量，未测量实际能耗，这削弱了对"效率"的完整评价。
- **硬件结论的外推风险**：H800 上"卸载总是变慢"的结论基于 6.7–7.0 倍的算力/带宽比，但未来 GPU（更高算力或更高带宽）的归属需重新验证；论文给出的部署指南是经验性的。
- **策略参数依赖**：工作集估计依赖对 $A$ 与 $\bar{N}$ 的滑动窗口估计（60 秒活动窗口、最近 256 次首查），在负载剧烈波动或上下文长度高度异质时可能失真；$\kappa$、$\theta$ 等参数虽做了敏感性分析，但仍是固定值。
- **对上下文编辑方法的评判偏保守**：论文指出折叠会降低前缀命中率，但未进一步给出"如何在减少 token 与保持缓存稳定长度之间做最优权衡"的具体算法。
- **未涉及多租户/共享前缀场景**：工作集模型假设各智能体上下文可比且共享较弱；强共享前缀或跨任务缓存复用的情形未充分讨论。
