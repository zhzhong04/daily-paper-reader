## 摘要
大语言模型（LLM）服务正日益由智能体工作负载主导。在这些工作负载中，智能体及其子智能体会在多次请求间以 KV 缓存的形式累积上下文，从而消耗大量内存。高带宽闪存（HBF）是一种有前景的解决方案，它能在 HBM 级读取带宽下提供高一个数量级的容量，但其有限的写入耐久性是关键限制因素。我们的核心洞见是：KV 缓存应根据其生命周期在 HBM 与 HBF 之间进行放置。将生命周期较短的数据放在 HBM 中，可让 HBM 吸收智能体运行中更多的写入，并减少发送到 HBF 的写入量。由于智能体服务中 KV 缓存的生命周期由 harness（编排智能体的程序）决定，我们分析其行为，并识别出生命周期出现差异的三个维度：时间性、结构性和工作进程间。基于这些观察，我们提出 Lachesis，一个位于智能体 harness 与服务引擎之间的生命周期感知 KV 缓存放置层。在写入时，它根据每个段的生命周期将其放置到 HBM 或 HBF，并在该段不再被读取后释放其块。在轨迹驱动仿真中，Lachesis 将 HBF 寿命相较 HBM 优先放置延长 1.19–3.13 倍，达到 3.3–12.2 设备年。即使在严格 SLO 所允许的满负载下连续 24x7 运行，在多智能体轨迹上 HBF 仍能超过其五年保修期。

## Abstract
Large language model (LLM) serving is increasingly dominated by agentic workloads, in which agents and their sub-agents accumulate context as KV cache across many requests, consuming substantial memory. High-bandwidth flash (HBF) is a promising solution, providing an order of magnitude greater capacity at HBM-class read bandwidth, but its finite write endurance is the key limiting factor. Our key insight is that KV cache should be placed across HBM and HBF by its lifetime. Placing shorter-lived data in HBM lets HBM absorb more of an agent run's writes and sends less of them to HBF. As the lifetime of KV cache in agentic serving is dictated by the harness, the program that orchestrates the agents, we analyze its behavior and identify three axes along which lifetime diverges, temporal, structural, and inter-worker. Guided by these observations, we present Lachesis, a lifetime-aware KV cache placement layer between the agent harness and the serving engine. At write time, it places each segment in HBM or HBF according to its lifetime, and frees its blocks once the segment is no longer read. In trace-driven simulation, Lachesis extends HBF lifetime by 1.19-3.13x over HBM-first placement, reaching 3.3-12.2 device-years. Even under continuous 24x7 operation at the full load a tight SLO admits, HBF outlasts its five-year warranty on the multi-agent trace.

# Lachesis 论文总结

## 1. 核心问题与研究背景

- **趋势转变**：LLM 服务正从无状态请求转向**智能体（agentic）工作负载**。智能体在一次用户任务中跨越多次 LLM 请求累积上下文，并派生子智能体（sub-agent）并发执行。
- **内存容量墙**：传统请求的 KV 缓存随请求结束即释放；而智能体会话的 KV 缓存可存活到会话结束，且每个子智能体各持有独立上下文。智能体工作负载的峰值上下文长度比传统聊天负载大 **29 倍**，HBM 容量成为主要瓶颈，推高单请求硬件成本。
- **HBF 的机会与限制**：高带宽闪存（HBF）可提供约一个数量级的容量提升，并具备 HBM 级顺序读带宽，但其**写入耐久性（P/E 循环）有限**是首要限制。
- **已有工作的不足**：早期 HBF 设计仅放置只读数据（模型权重、预计算 KV）；近期工作按**读写比**选择生成的 KV 写入 HBF。但该标准针对无状态请求，不适用于**有状态**的智能体会话——会话中不同上下文段的有效期差异极大。
- **核心洞见**：KV 缓存应**按生命周期**在 HBM 与 HBF 之间放置。短命数据放 HBM，可让 HBM 吸收更多写入、减少到达 HBF 的写入量；而智能体服务中 KV 生命周期由 **agent harness**（编排智能体的程序）决定。

## 2. 方法论

### 2.1 核心思想
- 在 **agent harness 与 serving engine 之间**插入生命周期感知的 KV 缓存放置层 Lachesis。
- 在**写入时**即决定每个上下文段（context segment）的层级归属，而非事后迁移；段生命周期结束时立即释放其块。
- 段定义为**共享同一生命周期的一组 token**；其生命周期由 harness 在**上下文边界**（context boundary）处固定。

### 2.2 三个生命周期差异轴（分析基础）
- **时间轴（Temporal）**：轮次（turn）结束时 harness 剥离推理内容（reasoning）。reasoning-laden 段短命但占该轮写入 token 的 **66–83%**；reasoning-stripped 段寿命长 **7.6–17.2×**。边界确定、写入前可知。
- **结构轴（Structural）**：子智能体返回时其段被丢弃，仅结果并入 lead agent。lead-agent 段寿命长 **4.0–6.1×**（相对 worker）、**4.7–38.3×**（相对 reviewer）。边界确定、spawn 时可知。lead-agent 段有 **71–88%** 的生命周期处于未被读取的等待状态，故**读写比不能代理生命周期**。
- **跨 worker 轴（Inter-worker）**：同属 sub-agent 类的 worker 之间无上下文边界，寿命从 p10 到 p90 相差 **3.7–23.6×**，写入量相差 **2.8–22.5×**，二者 Kendall τ 为 0.51–0.72。完成时间不可预知，但**相对顺序可在 spawn 时预测**。

### 2.3 两条放置路径
- **确定性路径**（时间轴 + 结构轴）：按 harness 固定的段类别放置——短命段（reasoning-laden、sub-agent）优先 HBM，长命段（reasoning-stripped、lead agent）放 HBF。reviewer 因段更短，无条件放 HBM。
- **预测路径**（跨 worker 轴）：在 worker spawn 时，用 **spawn record**（instruction、context、tool list、会话位置等构成的 spawn signal）预测其生命周期排名；**最短者优先准入 HBM**，其余放 HBF。准入数量 **k 由 HBM 空闲容量动态决定**，非固定参数；并为 reviewer 预留 HBM 容量。
- **预测器**：基于 spawn signal 的**岭回归线性模型**（特征为长度、工具指示、会话位置、词袋哈希），单一模型服务全部 5 个 benchmark，仅消费排名顺序而非寿命数值；Kendall τ 为 0.53，单次评分无额外延迟。

### 2.4 系统实现与公式
- **段表（Segment Table）**：每个活跃段一行，记录 segment id、段类别、关闭边界、KV 块 id，大小与活跃块数成正比。
- **引擎接口仅两个调用**：`alloc(tier)` 从指定层空闲列表分配一个块；`free([block ids])` 在边界释放该段全部块（按来源归还对应层）。引擎无需表示生命周期概念，仅需每层一个空闲列表。
- **寿命度量公式**：
  - `T_norm(s) = G_dec(s)·TPOT_ref + N_obs(s)·TTFT_ref + Λ_tool(s) + Λ_user(s)`，在固定参考时钟（TPOT_ref=0.2s，TTFT_ref=1.0s）下归一化，去除 batching、负载与排队影响。
  - 读写比 `ρ_R/W(s) = V_R(s) / V_W(s)`，其中 `V_W(s) = N_W(s)·V_token_KV`，`V_R(s)` 按解码步累计。
- **放置范围**：仅 KV 缓存；模型权重仍按只读映射，激活保留在 HBM。

## 3. 实验设计

- **实现方式**：在**模拟服务引擎 + 两层内存系统**上回放真实 agent trace。引擎用 Frontier（调度器、请求队列、带块哈希前缀缓存的 KV 管理器、按轮增长的上下文），硬件用 LLMSimulator（含 HBF 扩展：编译算子内核与 roofline 内存定价）。面向**预填充–解码分离部署的解码节点**。
- **GPU 内存配置**：将 8 个栈槽在 HBM/HBF 间划分，共 4 种：**1/7、2/6、3/5、4/4**；第五种为 H3 的菊花链 **8/8\***（不牺牲 flash 栈）。两层读带宽相同，仅写带宽不同。
- **模型**：**Llama-4-Maverick** 与 **Qwen3-235B-A22B**，各跨 8 GPU（attention 数据并行、experts 专家并行）。
- **SLO**：TTFT 均为 2s；99 分位 TPOT 分紧（60ms）与松（100ms）两档；单智能体 trace 仅在紧 SLO 下运行。
- **数据集 / 场景**：
  - 单智能体（时间轴）：**τ³-bench**（airline/retail/telecom/banking）与 **BFCLv4**（base/long-context）。
  - 多智能体（结构轴）：**AppWorld、DeepSearchQA、SWE-bench Verified、TerminalBench、WebArena** 混合为一条 trace，并分别采集**含/不含 reviewer** 两个版本。
  - 用户延迟按对数正态采样（中位 120s），工具调用延迟按各类工具的已发表测量建模（指数分布）。
- **对比方法**：**HBM-first placement**（HBM 有空闲块就放 HBM，否则放 HBF），即无 Lachesis 时引擎的默认行为。
- **指标**：HBF 寿命（设备年），按 KV 平均写入速率消耗 P/E 预算计算；假设 SLC 密度下 100,000 P/E、每栈 512GB、写放大 1.02；以**五年保修**为合格线。
