## 摘要
LLM 智能体越来越多地执行涉及多轮推理、工具使用和并行智能体的复杂工作流。高效服务需要跨越两个具有互补信息的层次进行决策：智能体执行框架理解工作流依赖、上下文生命周期和执行目标，而推理引擎则观测请求队列、KV 缓存状态、资源压力和执行能力。现有接口未能系统地连接这些视角，限制了工作流感知的执行。HEAR 是一种面向智能体化 LLM 服务的双向“执行框架—引擎”配对协议。HEAR 标准化了执行框架如何传达工作流意图和执行需求，以及引擎如何返回运行时状态、能力和结果。通过将协议语义与优化策略分离，HEAR 支持多样化的协调策略，同时不改变工作流或模型语义。我们为在线缓存感知的运行时协调以及面向智能体角色的工作负载感知执行模式选择实例化了 HEAR。在内存受限的并发服务下，在四个对话式和研究型智能体基准测试中，HEAR 在 SCBench 上实现了 1.61 倍的批处理加速，并将首 token 时间中位数缩短了 2.23 倍。Mooncake 表明，工作流意图与实时引擎状态在不同负载区间下提供互补收益。在 BrowseComp-Plus 和 DeepResearchBench 上，特定工作负载的配置分别带来 1.23 倍和 2.45 倍的端到端加速，且未观察到任务质量下降。这些结果确立了 HEAR 作为高效智能体化 LLM 服务的可复用协调基础。

## Abstract
LLM agents increasingly execute complex workflows involving multi-turn reasoning, tool use, and parallel agents. Efficient serving requires decisions that span two layers with complementary information: the agent harness understands workflow dependencies, context lifecycles, and execution objectives, whereas the inference engine observes request queues, KV-cache state, resource pressure, and execution capabilities. Existing interfaces do not systematically connect these views, limiting workflow-aware execution.   HEAR, a bidirectional Harness--Engine Pairing protocol for agentic LLM serving. HEAR standardizes how the harness communicates workflow intent and execution requirements and how the engine returns runtime state, capabilities, and outcomes. By separating protocol semantics from optimization policies, HEAR supports diverse coordination strategies without changing workflow or model semantics. We instantiate HEAR for online cache-aware runtime coordination and workload-aware execution-mode selection for agent roles.   Across four conversational and research-agent benchmarks under memory-constrained, concurrent serving, HEAR achieves a $1.61\times$ batch speedup and reduces median time-to-first-token by $2.23\times$ on SCBench. Mooncake shows that workflow intent and live engine state provide complementary benefits across load regimes. On BrowseComp-Plus and DeepResearchBench, workload-specific configurations yield $1.23\times$ and $2.45\times$ end-to-end speedups, respectively, without observed task-quality degradation. These results establish HEAR as a reusable coordination substrate for efficient agentic LLM serving.

  - **Agent Harness**：掌握工作流依赖、上下文生命周期、执行目标、请求就绪状态。
  - **Inference Engine**：掌握请求队列、KV 缓存驻留、资源压力、批处理与执行模式能力。
- **现有问题**：已有接口没有系统连接两种视角，导致引擎可能过早驱逐即将复用的 KV，或 harness 调度冷请求而绕过缓存可复用请求；跨层优化往往与特定 harness/engine 强耦合，难以移植和组合。
- **整体含义**：论文提出 **HEAR**，即面向智能体化 LLM 服务的双向 **Harness–Engine pAiRing** 协议，试图提供可复用的协调基底，在不改变工作流选择逻辑和模型语义的前提下，连接工作流意图与运行时执行状态。

## 2. 方法论

- **核心思想**：将“协议语义”与“优化策略”分离。HEAR 规定跨层消息的含义、力度和生命周期，但不规定具体调度、缓存或配置算法。
- **双向消息类别**：
  - **Harness → Engine**：
    - *Execution Description and Intent*：角色、阶段、依赖、就绪状态、请求规模、上下文生命周期、未来复用意图/预测。
    - *Execution Requirements and Control*：调度偏好与约束、等待时间保护、缓存准备/保留/释放请求、允许或请求的执行配置。
  - **Engine → Harness**：
    - *State and Capabilities*：可复用前缀范围、驻留层级、可分配容量、队列状态、资源压力、支持的控制与配置、估计成本。
    - *Execution Outcomes*：请求状态、实际执行配置、缓存复用、延迟、资源消耗、重试与错误。
- **四组关键语义区分**：
  - **Intent vs. Control**：描述/预测只是决策上下文；只有显式控制请求才要求对方行动。
  - **Preference vs. Requirement**：偏好是尽力而为；要求约束合法执行，未满足需拒绝或走允许的 fallback。
  - **Observation vs. Guarantee**：状态和能力报告不预留资源、不保证未来可用。
  - **Acceptance vs. Completion**：接受表示已进入处理，完成才表示效果已实现；拒绝、不支持、失败需区分。
- **联合信息决策公式**：
  - \(d_i = \pi(h_i, s_j)\)
  - 其中 \(h_i\) 是 harness 侧工作流与请求信息，\(s_j\) 是引擎最新相关状态，\(\pi\) 选择执行安排或配置。
  - 没有引擎反馈时退化为 harness 本地决策 \(d_i = \pi(h_i)\)；没有工作流信息时引擎只能做请求局部决策。
- **策略实例一：Cache-Aware Runtime Coordination**
  - 用于在线请求排序与 KV 保留。
  - 定义 \(h_i=(R_i,C_i,U_i)\)，\(s_j=(K_j,Q_j)\)，调度输出 \(d_i=(p_i,U_i)\)。
  - 根据引擎 KV 驻留反馈识别可复用前缀；若可复用前缀覆盖至少 50% prompt，则视为 hot。
  - hot 请求优先级定义为 \(priority=-N_{reuse}\)，即复用块越多优先级越高。
  - **Guard-W**：若请求等待超过 \(W\) 秒，则提升为保护优先级，防止冷请求被无限绕过。
  - **Session-Aware**：估计会话继续概率 \(p\)，保留优先级 \(r=p\cdot e^{-idle/400}\)，越可能返回且越近期访问的上下文越倾向保留。
- **策略实例二：Capability-Aware Execution Configuration**
  - 用于角色级推理模式选择。
  - 候选空间：\(\mathcal{C}=\{vLLM, OmniKV\}\times\{vLLM,H2O,SnapKV\}\)，分别对应 Main 侧与 Reader/子智能体侧模式。
  - 在开发阶段过滤质量/稳定性不合格配置，再最小化 makespan。
  - 冻结映射：BrowseComp-Plus 选 \((vLLM,H2O)\)；DeepResearchBench 选 \((OmniKV,H2O)\)。
