# CACHE ENGINEERING FOR AGENTS 

Tianyu Fu ∗ 1, Ruoxi Wang ∗1, Zihan Min ∗1, Zhongqi Ren 1, Zhihao Li 1,Tengxuan Liu 1, Shengxu Mu 1, Hanling Zhang 2, Yu Wang †11Tsinghua University 2The Chinese University of Hong Kong 

## ABSTRACT 

Large Language Model (LLM) agents can handle increasingly complex tasks, nav-igating long trajectories of observations and actions. As these trajectories grow, key-value (KV) cache I/O and storage become the dominant cost. Trajectories can also exceed the LLM’s maximum context length, requiring control over ac-tive cache growth. Prior work uses context engineering to reduce cache size by trimming or summarizing history. However, modifying the trajectory prefix invali-dates subsequent cached states and triggers costly re-prefilling of retained context. Task accuracy can also suffer when too little context is retained to limit re-prefill costs. We propose cache engineering as a new scheme. It allows agents to directly control their active KV cache without modifying the trajectory or re-prefilling re-tained context. Specifically, agents can proactively use drop to exclude selected cache from future attention and repos to adjust retained keys’ position encod-ings. We formalize these cache operations and identify history dependence as a serving challenge: identical token sequences can yield different cache states un-der different cache operation sequences, making prefix matching insufficient for correct cache reuse. Thus, we co-design the AKV serving engine. It provides a stateless interface compatible with existing serving APIs, while internally manag-ing stateful cache reuse, eviction, and restoration. Experiments show that a tool-response rolling-drop cache policy improves average benchmark scores by 1.7 points and reduces average cost by 27.7%, compared with conventional threshold-triggered summarization. With AKV, it achieves up to 1.2× the output through-put and a 1.5× speedup in P95 request latency. Recursive self-improvement of cache policies further reduces cost by 7.1% over expert design. Our code is at 

https://github.com/thu-nics/AKV .

## 1 INTRODUCTION 

Large Language Model (LLM) agents are capable of increasingly long-horizon tasks. Agents are generally composed of an LLM for reasoning and tool calling, and a harness that orchestrates tool execution and context. Through repeated reasoning, tool use, and environment interactions, they can carry out complex work spanning hundreds of rounds (Ye et al., 2025; Liu et al., 2025b). As agent trajectories grow longer, Key-Value (KV) cache growth poses challenges to both inference cost and task accuracy. In terms of cost, retaining and repeatedly accessing accumulated KV caches incur substantial storage and I/O overhead (Wu et al., 2026; Anthropic, 2026). As shown in Fig-ure 13, KV cache reads take up 82.4% of the total API cost. In terms of task accuracy, agents can suffer severe degradation if either the number of attended KV states or their positional range exceeds what LLM handles reliably (Hsieh et al., 2024; Chen et al., 2026b; Zhou et al., 2025). Therefore, it requires delicate control over the active KV cache for efficient and reliable agent execution. Prior work reduces the growing cache via context engineering , typically by trimming or summariz-ing historical messages. While older messages are often less useful, editing them changes the trajec-tory prefix, invalidates subsequent KV states, and triggers re-prefill. The earlier the edit, the more retained trajectory suffix that must be re-prefilled. In this paper, we introduce cache engineering , a new scheme for agents to directly control their active KV cache. As shown in Figure 1, instead of modifying the text trajectory, it excludes only selected KV entries from future attention, and reuses all retained KV states without re-prefill. This allows agents to incrementally drop older KV entries while retaining more suffix KV within a given cost budget. To support this control, alongside the usual append operation that adds KV states for new tokens, we introduce two additional cache operations. Drop removes selected KV entries from future attention, and repos adjusts the positions encoded in retained keys. Throughout execution, the LLM and harness choose when and how to apply these operations, repeatedly interleaving them with append to shape the active cache. This programmable control also enables agents to search, evaluate, and refine cache engineering strategies through recursive self-improvement (RSI). However, the history-dependent nature of cache engineering challenges current LLM serving sys-tems. With standard KV caching, the token prefix fully determines the cached states (Kwon et al., 2023; Zheng et al., 2024). In contrast, the same token prefix and retained positions can result in different cache states under different cache operation histories. As shown in Figure 5, trajectories 

① and ② both retain KV entries for B and C, but C’s KV is computed with attention to A only in 

①, due to the different ordering of drop and append operations. The serving system must therefore account for both token and cache operation histories to correctly track or reuse cache states. Thus, we co-design AKV, a user-friendly and efficient serving system for cache engineering. It pro-vides a stateless interface compatible with existing API-based serving, while handling the complex-ity of stateful cache management internally. Agents simply submit messages as usual, accompanied by cache operation instructions, without tracking which KV states remain resident on the server. The system uses an extended radix tree for correct reuse and timely eviction of history-dependent cache states, while segment-batch attention efficiently reconstructs missing states in a single prefill pass. AKV turns the theoretical efficiency potential of cache engineering into lower wall-clock latency and higher throughput for real-world agent workloads. • Cache engineering formulation. We formalize cache engineering through explicit cache operations and their trajectories, providing a clear and deterministic description of history-dependent cache states. This formulation also provides a programmable interface for agents to define and refine their own cache engineering strategies. • Serving system for cache engineering. We propose the first serving system that allows agents to directly control their caches, which were previously managed solely by the sys-tem. We co-design a stateless interface, an extended radix tree, and segment-batch attention to support efficient cache reuse, eviction, and restoration. • Improving efficiency and benchmark performance. Across three LLMs and four agent benchmarks, a simple tool-response rolling-drop cache policy reduces average cost by 2Preprint version 27.7% and improves average benchmark scores by 1.7 points, compared with conventional threshold-triggered summarization. With AKV server, this translates to 1.18 × the output throughput and a 1.51 × speedup in P95 request latency. An RSI-based policy additionally reduces cost by 7.1% on held-out tasks. 

## 2 RELATED WORK 

Agent context engineering . At the text level, context engineering summarizes or trims interaction histories to reduce cost and enable agents to work beyond the LLM’s context window. Existing methods trigger summarization through heuristics (Wu et al., 2025) or agent decisions (Ye et al., 2025; Sun et al., 2025). Further work improves summary quality through reinforcement learning (Lu et al., 2025) or by optimizing compression guidelines (Kang et al., 2025). To avoid the cost and complexity of summarization, trimming methods (Lindenbauer et al., 2025; Zhang et al., 2026) directly remove less relevant context. However, editing earlier context requires re-prefilling the retained suffix, creating a dilemma between re-prefill cost and information retention. 

KV cache compression, eviction, and reuse . At the cache level, prior work reduces cache size or approximately reuses existing states to lower storage, access, and computation costs. Compression 

methods use low-rank representations (Liu et al., 2024a; Wang et al., 2024a), quantization (Liu et al., 2024b; 2026b), or aggregation (Fu et al., 2025b; Wang et al., 2024b) to represent cached entries more compactly. Eviction methods typically rely on low-level signals such as token positions (Xiao et al., 2024) or attention-based importance (Zhang et al., 2023; Li et al., 2024; Fu et al., 2025a; Yang et al., 2026) to remove less useful cache entries. Reuse methods adapt cached states to different positions or context prefixes through position encoding adjustments (Gao et al., 2024; Ma et al., 2026; Ordonez & Parnell, 2026) or partial recomputation (Wang et al., 2025). Our work focuses on eviction and reuse, enabling high-level eviction decisions by agents and harnesses, while providing a practical serving engine for efficient cross-request reuse and isolation. We discuss concurrent agent-oriented eviction work in Appendix A.5. 

KV cache management in serving systems . Beyond algorithmic designs, previous works also ex-plore system optimizations for efficient cache storage, sharing, and request scheduling. Existing systems use prefix caching to share KV states across requests with common prefixes while preserv-ing equivalence to full prefill (Zheng et al., 2024; Ye et al., 2024). For agent workloads, recent systems batch context edits to reduce cache invalidation (Xu et al., 2026) or overlap re-prefill with ongoing execution to hide its latency (Pan et al., 2026). For cache engineering, it additionally re-quires tracking cache operation histories, since identical token prefixes can produce different states under different operations.

Context engineering modifies the logical token sequence through trimming or summarization. In contrast, cache engineering directly modifies the active cache through cache operations, while keep-ing the logical token sequence unchanged. 3.2 DESIGN MOTIVATION 

The design of cache engineering stems from our thinking about three key questions: why direct cache modification is needed, which parts of the cache to retain, and how to manage its encoding positions. We discuss the motivations and empirical evidence guiding our design decisions below. 

Why modify the cache directly . Cache engineering alleviates the dilemma between re-prefill cost and task accuracy in context engineering. We evaluate GPT-OSS-120B on the first 100 BCP tasks, with four trials per task and at most 100 agent rounds. Trim-based context engineering (retain-ing only the latest 12 rounds of tool responses) costs 1.85 × as much as the full-context baseline. Summary-based context engineering (48k threshold) reduces cost by about 7% but lowers accuracy by 5 percentage points (Figure 3). In contrast, directly dropping older tool-response cache can reuse the remaining cache, simultaneously improving accuracy and reducing cost (Figure 3). The retained cache may also preserve information from dropped history used in its computation (Xiao et al., 2024; Fu et al., 2026; Zou et al., 2025), as shown in Figure 1. 

Which parts of the cache to retain . Cache selection should reflect message roles, recency, and task needs, beyond token-level importance heuristics. Figure 2 shows that older tokens receive less attention than recent ones, and tool responses receive less attention than assistant messages at comparable relative positions. We therefore use tool-response rolling drop as our primary example, retaining cache for all reasoning and recent tool responses while dropping older tool-response cache. We later explore alternative policies, including RSI-based cache engineering. 

How to manage position encodings . By default, position encoding indices grow with the logical trajectory, even as the cache is reduced. Dropping cache neither changes retained position encodings nor resets the next token’s position index, so indices can reach the model’s limit even with a small cache. We decouple position encoding indices from logical indices and cache size, using a separate cache operation to reposition cached keys with RoPE rotations (Su et al., 2023) without re-prefill. 3.3 CACHE OPERATIONS

Append . Operation append is the standard cache update in LLM inference. It processes a new token xt+1 conditioned on the active cache and appends its cache entry Ct+1 :

append( xt+1 ) : C ← [C; Ct+1 ]. (3) We represent C as a sequence of KV entries ordered by their logical indices, where [·; ·] denotes concatenation. The token may come from the prompt, a tool response, or model generation. Position encoding indices start at zero and advance by one after each append; repos can reset the next index. 

Drop . Operation drop removes selected KV states from subsequent attention, while leaving the retained states, their position encodings, and the logical token sequence unchanged (Figure 1): 

drop( P ) : C ← C \ { Ci : i ∈ P }, (4) where P is the set of active logical token indices selected for dropping, and \ denotes cache removal, preserving the order of retained entries. Note that drop does not change the position encoding indices used by subsequent append operations. 

Repos . Operation repos updates cached keys’ position encodings in logical token order, and resets the position index for subsequent append operations. With r retained cache entries, their posi-tion indices become 0, . . . , r − 1, and the next appended token uses index r. For rotary position embeddings (RoPE) (Su et al., 2023), we move a cached key K from position index p to q by 

K ← R(q)R(p)−1K, (5) where R(p) is the rotation matrix at position p. Cached values remain unchanged. These operations define the cache visible to attention at the algorithmic level. The serving system handles physical storage, eviction, and reuse of cache separately in Section 4. 3.4 CACHE OPERATION SEQUENCE

## 4 AKV S ERVING SYSTEM 

AKV follows the principle of stateless interface, stateful serving . Agents control the cache used in subsequent attention by specifying cache operations (Section 4.1), while the server handles physical cache reuse, eviction, and restoration internally (Section 4.2). 4.1 SERVING INTERFACE 

The serving interface must keep each request’s output distribution independent of physical cache residency and other requests’ cache operations. For example, drop must affect only the issuing request’s attention, leaving other requests’ output distributions unchanged even when they share the same prefix cache. Each request must also fully describe the cache states it uses, without relying on physical cache retained from previous turns. This allows the server to fully restore missing cache states if memory pressure causes eviction between turns. To meet these requirements, AKV extends the standard LLM serving API to specify both token and cache operation histories. As shown in Figure 6, the existing messages field provides the full log-ical token sequence, while the optional cache field specifies drop and repos operation sequence using an operate-after grammar. Note that all entries in messages implicitly specify append op-erations. Each key in drop identifies the message index after which to apply the operation; its value lists the message indices whose cache is dropped. The reposition field lists the message indices after which to apply repos . Message indices are zero-based, and drop precedes repos when both occur at the same message boundary. For multi-round agent workloads, clients extend the message and cache operation histories after each round, following the standard LLM serving workflow. 4.2 CACHE STATE MANAGEMENT 

4.2.1 DESIGN OBJECTIVES AND CHALLENGES 

AKV aims to preserve three key properties of conventional LLM serving systems: (1) reusing cached states if and only if they are equivalent to the required states, (2) evicting unused cache states without compromising request isolation, and (3) restoring evicted cache states within one prefill pass. Serving systems face three corresponding challenges in preserving these properties when supporting cache engineering: (1) Token prefixes alone no longer determine cache states, so ordinary prefix matching can incorrectly reuse states from different cache operation histories (Figure 5(b)). (2) KV cache dropped by one request may still be needed by another, so evicting it without accounting for other requests can cause unnecessary recomputation or violate request isolation. (3) Ordinary causal prefill cannot reproduce cache states resulting from drops and repositions, while replaying the operation history requires multiple forward passes. AKV addresses these three challenges with an extended radix tree, drop-aware eviction, and segment-batch attention, respectively. 4.2.2 DROP -AWARE CACHE MANAGEMENT

When a request invokes drop , AKV inserts a drop node ∆ at the trigger point along the request’s path, recording the logical token indices whose cache is dropped. Evict with drop-awareness . AKV uses drop information to reclaim unused cache before requests finish. A cache entry becomes evictable only when no ongoing computation or restoration needs it. For example, in Figure 5, A’s cache can be freed once both requests ① and ② drop it, even as they continue generating D. Eviction frees the physical storage but leaves the tree node as an empty placeholder, keeping cached descendants accessible through prefix matching. Among evictable cache entries, AKV prioritizes evicting dropped cache over cache from completed requests, since the latter is more likely to be reused in the next round. 

Restore with segment-batch attention . AKV uses segment-batch attention to restore missing cache states in a single prefill pass. At each layer, queries are split at drop trigger points, and each segment attends causally to its own tokens and to active cache from earlier segments. Note that dropped cache is excluded from later segments but remains available to earlier segments that originally used it, as shown in Figure 10. Only attention is segmented, while the FFN processes the full sequence as one batch. This avoids repeating FFN weight reads, a major source of memory traffic, for each segment. 4.2.3 REPOSITION -AWARE CACHE MANAGEMENT 

While drop leaves retained cache unchanged, repos efficiently modifies its keys’ position encodings. Different requests may therefore need the same cache with different position encodings. Restoration must also reproduce the encodings used at each stage of computation. 

Reuse with key rotation . AKV reuses cache after repos by copying cached states and rotating keys, without recomputing hidden states. In Figure 8(c), request 2 copies B and C from positions 1 and 2 to positions 0 and 1, while request 1 continues using the original B. In the radix tree, these copies form a new branch with updated position indices and a reposition node after C. Prefix matching checks both token and operation histories: matching position indices allow direct reuse, while differing indices require key rotation. Appendix A.1.2 explains why reposition nodes are necessary and details the matching rules and position transformations. 

Evict positional versions independently . AKV evicts each position encoding versions indepen-dently, when it is no longer in use by any ongoing computation or restoration. For example, in Figure 8(c), the original B remains in use by Request 1, while the original C becomes evictable. 

Restore with temporary KV versions . AKV extends segment-batch attention so each segment uses the position encodings from its original computation. Queries are also split at repos trigger points. ## 5 EXPERIMENT 

5.1 SETUP 

Baselines . We compare AKV with two context engineering baselines that summarize accumu-lated history, following common practice in agent harnesses (Anthropic, n.d.; OpenAI, n.d.). Stan-dard uses a higher, model-specific summarization threshold: 96K tokens for GPT-OSS-120B and MiniMax-M2.7, and 192K tokens for MiroThinker-1.7-Mini. Text Engineering uses the same sum-marization policy with a lower threshold of 48K tokens across all models. For AKV, we use a tool-response rolling-drop policy that retains the KV states of the latest 12 tool responses. Its repos 

threshold matches Standard’s summarization threshold for each model. 

Models and benchmarks . We evaluate AKV across MiniMax-M2.7 (Chen et al., 2026a), GPT-OSS-120B (Agarwal et al., 2025), and MiroThinker-1.7-Mini (Team et al., 2026) LLMs. GPT-OSS-120B is evaluated with high reasoning effort, while MiniMax-M2.7 and MiroThinker-1.7-Mini are evaluated in thinking mode. The benchmarks cover various long-horizon agentic tasks, including BrowseComp-Plus (Chen et al., 2025) (BCP), xbench-DeepSearch-2510 (xbench, 2025) (xbench-DS), and the text-only 103-task validation subset of GAIA (Mialon et al., 2023) (GAIA-Text) for deep research, and SWE-Verified (OpenAI, 2024) for software engineering. Benchmark setup de-tails are provided in Appendix A.2.1. 

Metrics . We report success rate and mean per-task API cost for the main agent and its context-summary calls, in US cents unless otherwise specified. Costs are computed from active input and generated output tokens using Groq’s rates (Groq, n.d.) for GPT-OSS-120B and MiniMax’s official rates for MiniMax-M2.7. For MiroThinker-1.7-Mini, we use the official rates of its base model, Qwen3-30B-A3B (Yang et al., 2025). Detailed token prices are listed in Table 6. We additionally charge each token repos by AKV at the cache-hit rate, deliberately overestimating the cost of key rotation for a conservative comparison. For serving efficiency, we report request latency, time to first token (TTFT), and time per output token (TPOT), together with input and output throughput. 

Serving configuration . Baselines run on SGLang (Zheng et al., 2024), which is also the base serving system of AKV. Serving experiments use eight NVIDIA A800-80GB GPUs: four for prefill and four for decode, with tensor parallelism of four. Since A800 GPU lacks native MXFP4 support, all LLM weights are set to BF16. Further details are in Appendix A.1.3. 5.2 PERFORMANCE

## 6 CONCLUSION 

We introduce cache engineering, enabling agents to directly manage active KV states while reusing retained caches without recomputation. We co-design the AKV serving system to support cache engineering through a stateless interface, an extended radix tree, and segment-batch attention for ef-ficient cache reuse, eviction, and restoration. Across agent benchmarks, cache engineering improves average task performance while reducing inference costs, with AKV translating these efficiency gains into higher serving throughput and lower latency. 

Limitations . Further exploration of cache engineering strategies, training agents under this scheme, and extending serving support to linear attention models remain future work. 10 Preprint version

A.1.2 REPOSITION SCHEME 

Design objective . Reposition-aware cache management must distinguish positional versions while reusing their shared computational states. We therefore first identify directly reusable caches via exact matching, then use retrigger matching to find prefixes that are reusable via positional transfor-mation, avoiding unnecessary hidden-state recomputation. 

Token-node representation . Each token node is represented as T (x, p ), where x is the token ID and p is the position currently encoded in its cached K. The position label describes the stored cache, not necessarily the position at which the token was originally computed. For example, C is initially computed at position 2 in all three trajectories in Figure 11. After repos , trajectories 1 and 3 use 

(C, 0) , while trajectory 2 uses (C, 1) . Operation nodes along the path preserve the operation history that governs computation. 

Why position labels and reposition nodes are needed .Position labels distinguish cache representations that cannot be used interchangeably. For example, 

C has the same original computation history in trajectories 1 and 2, but is repositioned to 0 and 1, respectively. Its K encodings therefore differ and require positional transformation before reuse. Reposition nodes distinguish states that share final positions but arise from different computations. Trajectories 1 and 3 both drop B after ABC , but trajectory 3 executes RC before computing D.15 Preprint version When D is computed, the positions of A, C, and D are respectively (0 , 2, 3) and (0 , 1, 2) . The relative distance between D and A changes, while that between D and C remains unchanged, po-tentially producing different hidden states and KV entries for D. Both trajectories subsequently drop 

A and execute RD to move C and D to positions 0 and 1. This later transformation cannot erase the computational difference already established in D. The path must therefore retain RC before D to prevent incorrect reuse of D and subsequent cached states. 

Exact and retrigger matching . Exact matching compares all token-node fields: 

T (x, p ) ≡ T (x′, p ′) ⇐⇒ x = x′ ∧ p = p′,

and requires identical operation nodes and their parameters. Retrigger matching ignores only stored position encoding indices while preserving all operation records: 

ϕ(T (x, p )) = T (x), ϕ(∆ P ) = ∆ P, ϕ(R) = R. 

Two prefixes are history-compatible if their projections are identical. The system initializes the result with the longest valid exact prefix, then searches compatible branches from the root. A candidate replaces the current result only if it is valid and matches a strictly longer prefix, preserving exact matches in a tie. Retrigger matching stops at the first token or operation mismatch. Selected source caches are copied and positionally transformed as needed before use. 

Correctness of retrigger matching . Under fixed model and position encoding configurations and exact arithmetic, identical projected prefixes preserve the token and operation history preceding each token’s original computation. They therefore produce the same hidden states and unrotated KV content. Repos operations applied afterward change only K’s positional representation, allowing a source version s to be transformed into a target version t as 

Kt = R(pt)R(ps)−1Ks, Vt = Vs,

without recomputing hidden states. Preserving operation nodes prevents this transformation from crossing a divergence in computa-tional history. For example, trajectories 1 and 3 disagree at RC before D, so retrigger matching cannot reuse D across them. Finite-precision transformations may introduce rounding error; this correctness argument does not require bitwise equivalence to recomputation. A.1.3 SERVING CONFIGURATION

after X.A.1.4 WORKLOAD REPLAY AND EVALUATION PROTOCOL 

Task selection . To emulate realistic long-horizon agent workloads with substantial accumulated context, we select the 80 SWE-bench Verified tasks with the largest context lengths in trajectories, without any summary operation. These tasks reflect the difficulty of tasks in long-context reasoning. We rank tasks by this peak length and shuffle the selected tasks with a fixed seed. All methods use the same tasks and ordering. Each method replays trajectories collected under its own context/cache engineering policy, so the number of turns and the output budgets may differ between methods. 

Trajectory replay . For each turn, we reconstruct the output token budget from the complete recorded message history, including reasoning and tool-call content, after subtracting the genera-tion prefix already present in the input. We use temperature 0 and ignore eos=True to generate the prescribed number of tokens. The newly generated assistant response is retained in the history for subsequent turns, while tool responses are replayed from the recorded trajectory rather than re-executing the tools. Recorded terminal inputs without an available assistant response are excluded from replay. 

Concurrency and measurement windows . We maintain C client task concurrency and execute turns sequentially within each task. The task-count target for each measurement window is max(3 ×

C, 30) ; measurements include requests from supplemental tasks used to maintain concurrency. For AKV at C ∈ { 14 , 16 }, we truncate the archived runs at the completion of the first 30 tasks in completion order, counting all requests within the resulting window rather than only requests from those 30 completed tasks. For Standard at large concurrency, KV cache capacity pressure causes repeated prefill, resulting in severe serving degradation. We therefore report these two runs over a fixed one-hour window, with some requests still unfinished at the cutoff. 17 Preprint version A.2 EXPERIMENTAL DETAILS

A.5 ADDITIONAL RELATED WORKS 

Concurrent works . Concurrent work adapts KV eviction to the changing attention needs of agent trajectories. AgentKV (Liu et al., 2026a) scores KV entries using query buffers from different exe-cution phases, retaining information that recency-based scoring can miss. IntentKV (Li et al., 2026) combines cross-turn query memory with learned importance estimates to preserve useful history under limited KV budgets. SideQuest (Kariyappa & Suh, 2026) explores model-directed retention through an auxiliary reasoning branch that identifies stale tool results and issues cache-deletion com-mands, but its current strategy is limited to tool responses, and its serving integration is tailored to this specific eviction workflow. Context Language Models (CLMs) (Shao et al., 2026) primarily study model-driven context management, treating the live context as an editable file and learning how to maintain it. CLM also introduces Suffix Cache Reuse to preserve unchanged downstream KV states after text edits. Its serving support centers on session-local reuse: relocated states remain in private buffers outside the shared radix cache, without a unified mechanism for indexing, manag-ing, and recovering these history-dependent states. AKV addresses these serving concerns directly by exposing policy-independent cache operations through a stateless interface and uses an extended radix tree to track both tokens and cache operation histories, integrating retained states into shared cache reuse, memory management, and recovery. 21
