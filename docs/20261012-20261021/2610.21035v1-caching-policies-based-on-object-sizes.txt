# Caching Policies based on Object Sizes 

## Ridwanul Hasan Tanvir and George Kesidis 

Computer Science & Engineering Dept, Electrical Engineering Dept Pennsylvania State University University Park, PA, 16802, USA 

{rpt5409,gik2}@psu.edu 

Abstract 

We evaluate eviction policies that consider the lengths of the objects being cached for different cache sizes (cost) and different workloads. Workloads include the Independent Reference Model and real-world production traces. In particular, hybrid policies are considered for segmented caches. A working-set approximation is developed for SIEVE as well as its length-aware extension. 

Keywords: cache replacement, variable-length objects, size-aware caching, SIEVE, working-set approxima-tion 

# 1 Introduction 

Cache replacement is often described as choosing which resident object to evict. For variable-length objects, a caching policy also decides how much byte capacity remains for other objects. Admitting one large object may require evicting hundreds of smaller objects, each of which may be very useful for serving requests in the near future. This setting is common in web caches where objects may range from small metadata records to videos, images, and software artifacts [33, 7]. The variation in object size is not confined to one cache or one workload. Studies of large-scale Content Distribution Networks (CDNs) and in-memory caches report substantial diversity in both object sizes and access patterns [10, 44, 7]. This matters because replacement policies operate under a byte constraint even when their state is organized around objects. AdaptSize, for example, showed that size-aware admission can substantially change the object hit rate of a CDN cache [10], while the LHD policy explicitly accounts for the expected number of hits relative to the space consumed by an object [5]. In both systems, object size directly affects which objects the cache should keep. Consider a cache that serves small API responses, thumbnails, HTML fragments, small images, videos, and software images from the same byte budget. In one production trace we consider, the median object is tens of kilobytes (kB), while the largest object is gigabytes (GB). A single 2GB object can occupy the space of roughly fifty thousand 40kB objects. If a size-oblivious policy admits and protects that large object after one reference, it may evict many small objects that would have served later requests, i.e., those evictions become backend cache misses. The cache may still serve nearly the same byte volume, but it serves fewer requests. The size-aware policies in this paper are designed to avoid this outcome: they retain many small reusable objects unless a large object has shown stronger evidence of current reuse. The value of size awareness is workload dependent. It is most useful when the objects competing for cache space are both popular and heterogeneous in size, and when their aggregate footprint is larger than the cache budget. If the currently popular objects all fit in the cache, or if the popular objects have nearly equal sizes, a size-oblivious policy loses little by ignoring size. The difficult case is the “middle” one: popular objects overlap in time, compete for the same bytes, and vary enough in size that protecting one large object can displace many smaller objects with comparable current-reuse evidence. There is, however, no universal rule that smaller objects should receive higher priority. The appropriate treatment of size depends on what the cache is intended to optimize. A request-oriented cache may benefit from retaining more objects that are likely to be requested again, whereas a bandwidth-oriented cache 1arXiv:2610.21035v1 [cs.PF] 15 Oct 2026 may place greater value on retaining large objects. A particular application using a cache may also attach different costs or importance to different objects. Thus, size is a signal used by the replacement policy; it does not by itself define the objective. In this paper we evaluate the policies from the cache’s point of view using conventional object and byte hit rates, rather than assuming an application-specific weighting of objects. This said, we consider different cases of cache capacities as a signal for the cost of the cache, noting that cache users may have Service-Level Objectives (SLOs, in terms of hit rates) which they trade off with capacity-dependent cost as may be specified in a Service-Level Agreement (SLA) of the cache. An operator can state the design goal in several ways. One objective is to minimize cache capacity while meeting a target hit rate: min B subject to H ≥ H⋆. Another possible objective fixes the available byte budget and asks for the highest hit rate: max H subject to B ≤ B⋆. A third possible objective combines performance and resource cost directly: max H − λB , where λ > 0 is the operator’s price for resident capacity. Generally non-convex utility formulations of these kinds have been used for cache design and cache policies [16, 32]. The symbol H can denote object hit rate, byte hit rate, or an application-defined utility-weighted hit rate. Our mechanisms instantiate the object-hit-oriented choice: all other reuse evidence being equal, a shorter object receives more retention priority because the same byte budget can hold more such objects. A different deployment could reverse or reshape this preference. For example, a cache for large media objects, software images, or costly-to-restore data may prefer to protect larger objects under the same framework. This paper focuses on object hit rate. Object hit rate measures the fraction of requests served from cache, and it is the natural metric when backend request load is the bottleneck. Byte hit rate is also important, but it measures a different objective. A cache that keeps many small popular objects can serve many more requests while moving about the same number of bytes. We therefore optimize for object hit rate and check byte hit rate separately. We also report policy computational overhead, since replacement logic consumes CPU and metadata bandwidth and can limit cache throughput [18, 35], even though its cost may be partly hidden by (pipelined with) the I/O overhead needed to fetch or move large objects. Prior size-aware designs intervene at different points in cache management. AdaptSize uses object size at admission time and adapts the admission rule as the workload changes [10]. LHD instead estimates the expected hits obtained per unit of cache space and uses that estimate to guide replacement [5]. Both approaches demonstrate that size can be useful when the objective is request hit rate, but they introduce mechanisms specifically designed for size-aware admission or ranking. We ask a narrower question: how much of this benefit can be obtained by adding a small, causal, size-dependent decision to replacement policies that already have their own notions of recency, reuse, admission, and promotion? We start with Sieve , a FIFO-like policy that uses one visited bit and an eviction hand [47]. We then apply the same size signal inside three common blended families: 2Q, ARC, and S3-FIFO. In every case, the policy sees only past requests and current object sizes. It does not use future reuse, offline labels, or an oracle. The evaluation follows the same point of view. Rather than selecting one cache size and declaring a winner, we compare policies across byte budgets and ask how object hit rate changes with the amount of cache memory allocated. This exposes the performance–capacity tradeoff that a cache operator faces when provisioning memory [38]. The synthetic traces then isolate one part of that tradeoff by holding the request process fixed while increasing the coefficient of variation of object sizes. 

Sieve is a natural starting point because its replacement state is small. A hit records reuse by setting a visited bit, while the ordering of resident objects is left unchanged until the eviction hand examines them [47]. The same work also showed that Sieve can serve as a replacement primitive inside policies such as 2Q and ARC, rather than only as a standalone cache policy. Canonical Sieve , however, gives the same replacement state to objects of different sizes. This leaves a direct question for variable-length caches: whether size can be incorporated without giving up the simple state and deferred eviction decisions that make Sieve attractive. A deployed cache should not need a new cache architecture to obtain a basic size signal. We therefore keep the mechanisms close to their parent policies, which also lets us measure the effect of the size signal directly. A second question is whether the resulting behavior admits a useful analytical description. Characteristic-time and working-set approximations have provided a tractable way to reason about cache occupancy and hit probability for policies such as LRU under the Independent Reference Model (IRM) [13, 20, 28, 22, 21, 19]. 

Sieve does not maintain an LRU stack: objects remain in insertion order, and eviction is determined by 2successive examinations of the hand. In particular, the first examination after admission is different from subsequent examinations of an object that has already survived one examination. We therefore examine whether these two stages can be represented by separate characteristic times, and whether the resulting approximation can be adapted from an object-count constraint to the byte-capacity constraint of a variable-length cache. This paper makes the following contributions. • We describe two new causal size-aware variants to Sieve (Section 2.4). Mean-Threshold grants extra protection below the running mean object size, while Dual-Threshold separates small, medium, and large objects using the running mean. On the production traces, Dual-Threshold increases object hit rate by up to 27 .7% over canonical Sieve .• We evaluate size-aware policies across production and synthetic traces, including LRU-MIN (reported as LRU !), Dual-Threshold Sieve (reported as Sieve !), and new size-aware segmented versions of 2Q, ARC, and S3-FIFO (Section 2.7). The hybridized Sieve -based policies give the best object hit rate most often: 2Q-SIEVE ! on the META traces and ARC-SIEVE ! on the synthetic traces. • We compare cache-eviction policies in terms of hit rate versus cache-memory size rather than at a single fixed cache size. This is the performance–cost tradeoff seen from a user’s point of view. • We develop a new working-set approximation for Sieve under the IRM (Section 6 and Appendix E). The model uses two examination times and handles variable-length objects by replacing the unit-capacity equation with a byte-weighted one. This paper is organized as follows. Section 2 introduces the cache model, size-aware replacement mech-anisms, and the policies evaluated in the paper. Section 3 describes the traces, metrics, and experimental setup. Sections 4–5 present the empirical results, Section 6 develops the working-set approximation, and Sections 7 and 8 discuss implications and conclude. 

# 2 Background and Size-Aware Cache Replacement 

## 2.1 Cache Model and Evaluation Objectives 

A content cache stores objects so that subsequent requests can be served without accessing a slower backend, such as a remote origin server, a lower cache tier, or persistent storage. Modern web and storage caches serve workloads with many distinct objects, skewed request popularities, and substantial variation in object sizes [7, 44, 10]. A cache therefore has to decide not only which objects have sufficient evidence of reuse, but also how to allocate a finite byte budget among objects that may occupy very different amounts of memory. Let the resident cache capacity be B bytes. A request at time t is for object xt whose size is Lxt bytes. A request is a hit if xt is resident when the request arrives and a miss otherwise. On a miss, the requested object may be admitted to the cache; if there is insufficient free space, the replacement policy evicts one or more resident objects. Objects with Lxt > B cannot be admitted and are treated as forced misses. We distinguish resident objects from policy metadata. A resident entry contains the cached payload together with the metadata needed by the replacement policy. A ghost entry records the identity of a recently evicted object but does not retain its payload. A request to a ghost entry is therefore still a miss. The ghost hit nevertheless provides causal evidence that the evicted object has returned, and several segmented policies use this information when making subsequent admission, promotion, or partitioning decisions [26, 29, 45]. As in the original definitions of these policies, ghost memory is relatively small and is typically not counted toward the resident byte capacity B.We evaluate two conventional cache metrics. In particular, retaining several frequently requested small objects may increase object hit rate without producing a corresponding increase in byte hit rate. Object size does not, by itself, determine the value of an object. An application may prefer smaller objects, larger objects, or may assign application-specific values to individual objects. Such preferences could be represented by a weighted hit-rate objective or by a different size-dependent retention rule. We do not assume a universal ordering of objects by size. Instead, this paper uses conventional object hit rate as its primary metric and evaluates byte hit rate separately. The size-aware mechanisms studied below instantiate one particular retention rule—additional protection for objects below an online size threshold—and evaluate its consequences under these cache-side metrics. 

## 2.2 Replacement Policies and Object Size 

Classical cache-replacement policies infer future usefulness from recency, frequency, or combinations of the two. LRU orders objects by their most recent access, while policies such as LRU-K, 2Q, ARC, CAR, LIRS, and CLOCK-Pro retain additional history or organize objects into multiple regions to distinguish short-term recency from stronger evidence of reuse [34, 26, 29, 3, 25, 24]. More recent policies have shown that substantially simpler FIFO-like structures can also obtain strong hit-rate performance. S3-FIFO uses FIFO queues, lightweight counters, and ghost history [45], while Sieve combines insertion order with one visited bit and an eviction hand [47]. Such CLOCK-like policies can show performance cliffs, where added capacity has little effect until a workload-dependent threshold is crossed [15]; Wang et al. analyze a randomized SIEVE/CLOCK variant with multiple access bits per object that addresses this behavior [39]. Variable-length objects change the replacement problem because resident objects consume unequal por-tions of the cache. For equal-sized objects, an eviction releases one cache slot. For variable-length objects, the number of objects that must be removed depends on the sizes of both the incoming and resident objects. The offline optimum is therefore no longer characterized by the usual equal-size form of Belady’s rule, and optimal caching with variable object sizes is substantially more difficult [6, 8]. Even the equal-size optimum requires dedicated tools to compute on large traces [23]. Prior work incorporates size at several different points in cache management. GreedyDual-Size combines object size with retrieval cost in the replacement priority [12, 46]. AdaptSize uses size to control admission while retaining LRU as the underlying eviction policy [10]. LHD estimates the expected utility of an object relative to the cache space and time that it occupies [5]. Other approaches modify LRU itself so that victim selection depends jointly on recency, size, or reference count [40, 1, 14]. These approaches show that size helps, but each adds it through a different mechanism. Learning-based policies take another route and train a model online to choose eviction victims: LRB approximates Belady’s rule for CDN caches [37], and GL-Cache learns eviction decisions for groups of similar objects [43]. A separate line of work treats caching as online learning and gives regret guarantees against adversarial request sequences [11, 27, 31]. Our study is complementary: it evaluates simple eviction rules empirically under a byte budget. We ask whether size can be introduced into a simple replacement primitive without replacing the sur-rounding cache architecture. The mechanisms are causal: decisions use only object sizes and request history observed up to the current time. They do not use future requests, oracle reuse distances, or offline phase labels. This allows the effect of the size signal to be studied separately from changes to admission, ghost management, or promotion logic. 

## 2.3 Canonical Sieve 

By canonical Sieve we mean the original, size-agnostic Sieve policy [47], which gives every object the same replacement state regardless of its size. It keeps resident objects in insertion order with one visited bit per object. A hit only sets the bit. When space is needed, an eviction hand scans from older to newer objects, clears the bits that are set, and evicts the first object whose bit is zero. The hit path is therefore constant time, and the consequence of a hit is decided only when the hand later examines the object; the size-aware variants below change retention at this point. ## 2.5 Established Size-Aware Policies 

We also compare against three established size-aware policies: LRU-MIN [40], AdaptSize [10], and LHD [5]. We chose them because each adds object size at a different point in cache management. LRU-MIN changes victim selection: it evicts the least recently used object among those at least as large as the incoming object. AdaptSize changes admission: it admits a missed object of size s with probability e−s/c and tunes c online. LHD ranks resident objects by their estimated hits per unit of cache space and time and evicts the lowest. We use these policies without modification and report LRU-MIN as LRU !. Appendix A.2 describes them in detail. 

## 2.6 Segmented and Blended Cache Policies 

Many replacement policies separate newly admitted objects, in a cold region, from objects that have shown stronger evidence of reuse, in a hot region, and several keep ghost histories of recently evicted objects: a ghost hit is still a miss, but it shows that the object returned after eviction. We build on three such policies, 2Q [26], ARC [29], and S3-FIFO [45]. Sieve can also manage one resident region inside such a policy [47]; we call the results blended policies, namely 2Q-SIEVE, ARC-SIEVE, and S3-FIFO-SIEVE. In each, the parent policy keeps its admission path, ghost histories, partitioning rule, and promotion semantics, and only its protected region is managed by Sieve . How to divide an LRU cache among request classes has also been analyzed directly [36]. Appendix A.3 describes the parent policies and the blended construction, and Table 5 there summarizes their structure.

## 3.3 Cache Sizes and Metrics 

Cache sizes are fixed byte budgets. We use 0 .01%, 0 .1%, 1%, 5%, 10%, 20%, and 30% of each trace’s total object size. Object sizes are read directly from the trace records. Records whose size is unknown are skipped by every policy. The oracle next-access field of the production records is never passed to any policy, so no evaluated online policy can use future reuse. The largest cache sizes, 20% and 30% of the total object size, are larger than those usually studied. They may be realistic for edge or near-edge caches that serve real-time applications, such as virtual or augmented reality, where the data must be close to the user when it is requested. Also, 20%–30% still represents significant savings considering the cost of edge versus remote cloud storage. We evaluate policies in terms of object hit rate and average runtime per request (cache policy overhead), noting the latter may be pipelined with object I/O overhead. Byte hit rate performance is given in the Appendix.

## 4.2 Runtime and Byte Hit Rate 

Figure 3 reports whole-trace policy time for the three META traces at the 10% cache size. We use this replay time as a measure of replacement-policy overhead: it is the wall-clock time required by the simulator per request to apply the policy logic, not an end-to-end storage or network latency. Lower values mean less controller CPU and metadata work. The size-aware policies add one running mean update and a small token calculation to the Sieve path, so they are slower than canonical Sieve in this replay engine; nevertheless, the absolute times remain in the hundreds of nanoseconds per request. The full META timing table, including the 30% cache size, is in Appendix C. In a deployed cache, this eviction overhead can be pipelined with the memory or disk I/O that moves object payloads. That I/O can be substantial for very large objects, so part of the extra policy time may be hidden rather than added to request latency. Byte hit rate measures the fraction of requested bytes served from cache. It reflects the efficiency of cache capacity usage. It is difficult to discriminate different cache-eviction policies according to this criterion, see Figure 12 in Appendix C. Prior work such as AdaptSize also reports no noticeable difference in disk-cache byte hit rate [10].

## 4.4 Why the Size-Aware Rule Helps 

Canonical Sieve treats the first hit to a small object and the first hit to a large object identically. Under a byte budget this can be costly: a large object with weak reuse evidence can displace many smaller objects that would each have served later requests. Mean-Threshold changes this by giving below-mean objects one additional hand pass. Dual-Threshold adds a second correction for the far tail by withholding hit-based protection from objects at least twice the running mean size. Both rules are local. The policy observes object sizes as requests arrive and changes only the amount of retention credit assigned when objects are inserted, hit, and examined by the hand.

# 7 Discussion 

Why a running-mean threshold works. The (causal) mean-threshold rule uses no future information and adds little state. It works because very large objects make the mean object size much larger than the median on the META traces (right-skewed size distribution). The rule therefore protects most objects while withholding protection from the few very large objects that consume disproportionate cache capacity. The threshold automatically adapts to the workload. When object sizes vary widely above their mean, the mean moves far above the median and the benefit is larger. When object-size variance is low, the mean and median nearly coincide and the benefit fades. The policy does not need a trace-specific threshold. 

Object and byte objectives differ. The size rule raises object hit rate because it caches more small reused objects. A small object and a large object count equally for object hit rate but not for byte hit rate, and byte traffic on the production traces we used is dominated by very large objects. Reclaiming space from weakly reused large objects therefore adds many request hits while barely changing the byte hit rate. This suits caches limited by request load; a cache limited by bandwidth would need a rule that values bytes directly. The direction of the size preference follows from the cache-eviction objective. All other qualities being equal, the shorter object receives higher retention priority because we evaluate request hits under a byte budget. An operator optimizing byte hit rate, retrieval costs, or application value could choose a different priority function ψ(j, ℓ j ), which assigns a retention priority to object j of size ℓj . For example, a media cache may value retaining a large object because a miss consumes substantial downstream bandwidth, while a metadata cache may value retaining many small objects because each hit avoids a backend lookup. The algorithms would then change the direction or shape of the size rule while preserving the same causal structure. 

Heavier tails give larger gains. The gains are largest on the META traces, where the largest 1% of objects hold more than half of the total object size, and smallest on WIKI TRACE, where the tail is lighter. The top-1% share is only a rough guide: META TRACE 3 has a slightly smaller share than META TRACE 1 but a larger gain. The working-set model gives the same intuition: under a byte constraint, reducing the occupancy of a few very large objects can free capacity for many small objects. Why the hybridized size-aware Sieve-based policies perform best. In 2Q-SIEVE !, ARC-SIEVE !,and S3-FIFO-SIEVE !, the segmented parent policy supplies reuse filtering through its admission path, res-ident regions, and ghost history. Size-aware Sieve then decides how much protection each of these objects receives under the byte budget. Standalone Sieve ! has no ghost history to keep one-hit objects out, while the size-aware 2Q !, ARC !, and S3-FIFO ! keep their LRU or FIFO protected regions. Combining the two gives the highest object hit rates we measured. For a cache where serving more requests is the primary objective and object sizes have a heavy tail, we therefore recommend adding a running-mean size token to the Sieve -managed protected region of a segmented cache. The change is small. It preserves FIFO-style replacement without reordering on hits and gives consistently strong object hit rates across the measured workloads. 

More retention tokens. Two retention tokens do not give the highest hit rate this mechanism can reach. 

Sieve -K8 (Table 13) allows up to eight tokens per resident object. At the 10% cache size it improves object hit rate over canonical Sieve by 8 .3%–27 .0% on the META traces and by 27 .3%–94 .6% on the synthetic traces, and over Dual-Threshold by 0 .8%–2 .8% on the META traces and by 16 .5%–25 .8% on the synthetic traces. On WIKI TRACE, where the size tail is lighter, the additional tokens give essentially no further gain over Dual-Threshold. The extra tokens help most on the synthetic traces, and most of all on the two lognormal traces, which have the largest relative size dispersion. Wang et al. [39] analyze a related design, a randomized SIEVE/CLOCK variant with multiple access bits per object; combining multiple bits with size-dependent credit is left for future work. 

Limitations. Our experiments do not evaluate admission control, fetch-delay effects, TTL policies [2, 4], or latency-aware allocation of cache space across backends [9]. Cache sizes are percentages of each trace’s total object size, so equal percentages do not mean equal byte capacities across traces. The results also do not claim that object hit rate is always the right objective. Some deployments are limited by egress bandwidth or storage-device throughput. Those settings need either a byte-hit objective or a utility function that jointly values requests and bytes. # 8 Conclusion 

With variable-length objects, the number of bytes stored in a cache and the number of requests it serves are no longer proportional. A cache that aims for object hit rate should therefore not protect a large object and a small object in the same way after the same weak reuse evidence. A causal running-mean size rule can correct this with little additional state. In standalone Sieve , Dual-Threshold raises object hit rate by up to 27 .7% over canonical Sieve on the production traces. Hybridized with 2Q, ARC, and S3-FIFO, the same rule gives our strongest policies. Size-aware 2Q-SIEVE achieves the highest object hit rate for almost all cache sizes across the production traces. It incurs lower policy overhead than the established size-aware policies LHD, LRU-MIN, and AdaptSize across all measured configurations. Size-aware ARC-SIEVE achieves the highest object hit rate on the synthetic traces. The rule keeps Sieve simple, fits inside existing segmented caches, and admits a working-set approximation for variable-length objects. The direction of the size preference follows from the cache-eviction objective, and an operator who values bytes rather than requests can reverse it within the same framework. 17 020 40 60 Object hit rate (%)

## A.1 Canonical Sieve 

Sieve keeps resident objects in insertion order and associates one visited bit with each resident object [47]. Let Qt = ( q1, q 2, . . . , q m) denote the resident ordering at time t, from oldest to newest, and let vx ∈ { 0, 1}

be the visited bit of resident object x. A miss inserts the requested object at the newest end with vx = 0. A hit changes only the bit, 

vx ← 1, (9) and leaves the resident order unchanged. Thus the hit path is constant time and does not perform an LRU-style move. When additional bytes are needed, an eviction hand scans residents from older to newer entries. If the hand finds an object with vx = 0, that object is removed. If it finds vx = 1, the bit is cleared and the hand advances: 

vx ← 0 and the hand advances. (10) The first zero-bit object encountered by the scan is the victim. Since newly inserted objects have vx = 0, an object admitted after a miss receives no retention credit unless it is requested again before the hand reaches it.

This deferred use of the hit signal is the key property we exploit. Sieve records reuse immediately, but the replacement consequence of that reuse is resolved only when the hand later examines the object. ## A.2 Established Size-Aware Policies 

LRU-MIN LRU-MIN was introduced for Web proxy caches containing variable-sized documents. When an incoming object of size S must be admitted, the policy first asks whether any resident object of size at least S can be removed. If so, it chooses the least-recently-used object among that eligible set. If not, the threshold is relaxed to S/ 2, then S/ 4, and so on until a victim can be selected. LRU-MIN therefore preserves the recency principle within each eligible size class, but it uses the incoming object’s size to avoid freeing space through a long sequence of small evictions. In Section 5, we report this LRU-family size-aware baseline as LRU !.

AdaptSize AdaptSize is a size-aware admission policy for content-delivery caches. On a miss for object i,with size si, the object is admitted with probability 

pi(c) = exp( −si/c ), (11) 22 where c is the admission parameter. ## A.3 Segmented and Blended Cache Policies 

Many replacement policies separate newly admitted objects from objects that have accumulated stronger evidence of reuse. We refer to these regions as cold and hot , respectively. Cold and hot describe their functional roles rather than a particular data structure: a region may be managed by FIFO, LRU, Sieve ,or another replacement primitive. This separation provides a reuse filter. A newly observed object is initially given limited protection; only after satisfying the parent policy’s promotion rule does it enter the hot region. Several policies also retain ghost histories for recently evicted objects. Because ghosts contain metadata rather than payload, a ghost hit is a miss, but it provides evidence that the object returned after eviction. The parent policies differ primarily in how this evidence is collected and how it changes admission, promotion, or the division of resident capacity. How to divide an LRU cache among request classes has also been analyzed directly [36]. 

2Q 2Q separates recent arrivals from objects that demonstrate reuse using three structures [26]: a resident FIFO queue for recently admitted objects, a nonresident ghost history for objects evicted from that queue, and an LRU queue for objects receiving longer-term protection. A previously unseen object enters the FIFO region. A hit while the object is still resident there does not immediately move it to the protected queue. If the object is evicted and subsequently requested while its identifier remains in the ghost history, the returning object is admitted to the protected LRU queue. The ghost therefore distinguishes a second access separated by eviction from a short burst of references while the object is still resident. 23 ARC ARC maintains two resident LRU lists and two corresponding ghost lists [29]. One resident list represents objects seen recently, while the other represents objects with stronger repeated-reference evidence. Their ghost histories record objects recently evicted from the two resident lists. A hit in the recency ghost history indicates that the recency side was too small; a hit in the frequency ghost history provides evidence in the opposite direction. ARC uses these events to adapt the target division between the two resident lists online. Thus, unlike a cache with a fixed cold/hot partition, ARC changes its preferred balance between recency and frequency as the request stream evolves. 

S3-FIFO S3-FIFO uses FIFO structures rather than LRU lists [45]. A small resident FIFO region filters newly admitted objects, a larger resident FIFO region protects objects with stronger reuse evidence, and a FIFO ghost queue records recently evicted identifiers. Hits update a small reuse counter without changing FIFO order. When an object reaches the eviction end of the small region, the counter determines whether the object is promoted or evicted to the ghost queue. A subsequent request to a ghosted object admits the returning object with stronger protection. In the main FIFO region, counter-based reinsertion gives reused objects additional opportunities to remain resident without requiring LRU-style movement on every hit. 

Sieve-based blended variants. Sieve can also be used as a replacement primitive inside an existing segmented policy [47]. We call such constructions blended policies: the parent policy retains its admission path, ghost histories, partitioning rule, and promotion semantics, but one resident replacement component is managed by Sieve instead of the parent’s original primitive. In 2Q-SIEVE, the FIFO admission region and ghost-hit rule of 2Q are unchanged, while the protected LRU queue is replaced by Sieve . ARC-SIEVE retains ARC’s ghost histories and adaptive target split but uses Sieve for replacement in its protected, frequency-oriented resident region. S3-FIFO-SIEVE retains S3-FIFO’s small FIFO filter and ghost behavior while managing its protected region using Sieve . This construction is useful experimentally because the parent policy’s reuse evidence remains fixed while the local eviction mechanism changes. # E Sieve Working-Set Approximation Details 

This appendix gives the full working-set approximation (WSA) derivation and validation. Figure 14 compares the WSA predictions with empirical Sieve replays for the measured popularities of META TRACE 1, and Figures 15 and 16 compare them for Zipf-popularity unit-size and variable-length objects at N = 10 6 and 

N = 10 7.

Sieve keeps (equal-sized) objects in FIFO insertion order and uses one visited bit per object together with an eviction hand. On a cache hit, the object’s visited bit is set to one; the object is not moved and the hand does not advance. On a miss, if an eviction is needed, the hand examines objects in order of a circular cache. A visited object is kept in place and if its bit is set to one then its bit is cleared to zero and the hand continues. The first object whose bit is zero is evicted. The missed object is then inserted at the FIFO head with visited bit zero. Thus a newly inserted object can be evicted the first time the hand reaches it if it has not been hit. Sieve also defines a logical examination clock and shows that inter-examination times depend on queue position [47]. This suggests that a WSA for Sieve should be based on hand examinations rather than on LRU recency alone.
