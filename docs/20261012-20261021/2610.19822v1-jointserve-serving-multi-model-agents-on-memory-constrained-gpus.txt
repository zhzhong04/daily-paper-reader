# JointServe: Serving Multi-Model Agents on Memory-Constrained GPUs 

## Daijin Hu 

Beihang University daijinhu@buaa.edu.cn 

## Abstract 

LLM agents are evolving from a single model calling tools to planners that orchestrate multiple expert models whose capabilities live in distinct weights. This shift breaks a hidden assumption of today’s serving systems—that the working set of models fits in GPU memory. On the memory-constrained GPUs typical of private and edge deployments, naive whole-model swapping serializes weight transfer with computation and, without host-backed KV restoration, discards session state at a switch. We present JointServe, a serving system that treats weight shards and KV blocks as residency objects competing for one unified memory budget. JointServe exploits three struc-tural properties of agent workloads—directed calls, gapped execution, and dual-state residency—to prepare models be-fore they are called: an intent signal parsed from the caller’s own output stream triggers prefetch during generation, par-tial k* residency reduces switching to incremental layers, and a preemptive transfer scheduler protects live-session KV with a guaranteed bandwidth share. A carve-out control step adjusts the weight/KV allocation as workload demands change. Evaluations show that JointServe reduces session com-pletion time by 21.7% over the strongest whole-model swap baseline and stays usable in a crash regime where every whole-model swap baseline fails to finish (a 46 × gap). On replayed SWE-bench, 𝜏 -bench, and OSWorld traces, it cuts session completion time by up to 49% and lifts SLO attain-ment from 2.8–24.5% to 76.8–100%. 

Keywords: Large Language Model Serving, Multi-Model Agents, GPU Memory Management, KV Cache

A recurring archi-tecture has emerged from these systems: a general-purpose 

planner model orchestrates a pool of domain-specialized ex-pert models [36], invoking an expert much as earlier agents invoked an external tool [31, 34, 41]. Serving these workloads therefore means serving many models on demand, not one model well. Serving an expert pool requires memory for both model weights and the state of active agent sessions. Private, edge, and shared-GPU deployments typically offer one or two 80 GB-class accelerators, while the combined weights of even a modest expert pool overflow a single GPU. Session state compounds the pressure: as an agent task deepens, the key– value (KV) cache of each session grows with every turn, so weights and KV blocks contend, physically and unavoidably, for the same bytes of HBM. The cost of this contention lands on two user-visible metrics that we use throughout the paper: time to first token (TTFT), which governs the interactivity of each model call, and session completion time (SCT), the wall-clock duration of an entire agent task. The core challenge is not raw capacity; it is deciding which bytes should reside in scarce memory, and when they should move .

What happens when the planner calls an expert that is not resident? In a naive whole-model swap path, the serving stack must first make room in HBM, and then the entire weight footprint of the target model streams in before prefill can begin. This is a load-all barrier : until the last layer is in place, the first token cannot be produced (Figure 1(a)). Loading is not the only tax. When the session later switches back to a model whose KV blocks were evicted to make room without a host copy, that state is gone, and the context must be re-prefilled from scratch. A single cross-model call there-fore pays twice: once in serial weight transfer on the way out, and once in KV recompute on the way back. The first tax alone reaches second scale on current hardware and grows linearly with model size, with the GPU idle throughout; we quantify both taxes precisely in §2. These costs characterize the naive path in Figure 1(a): weights move at whole-model granularity, and evicted KV is not preserved for fast restora-tion. Prior work addresses different parts of this trade-off. Whole-model loading and session-aware placement reduce switch and return costs. ServerlessLLM [11] accelerates checkpoint load-ing. Talaria [28] routes continuations using model residency, KV locality, and instance pressure; soft reservations, host-restorable KV, and staged weights preserve session continu-ity across model switches. Talaria’s cold pool still switches at model granularity. JointServe instead selects resident weight layer groups and KV blocks within one constrained GPU and prefetches missing groups before a named call. Quan-tized co-residency (Figure 1(b)) removes swaps by shrinking weights [6, 8, 16, 35, 46], but merely relocates the contention: the bytes freed by quantization are reclaimed by growing KV, the scheme fails outright when even compressed weights do not fit, and it carries accuracy risk. Same-family compression 

shares a base model across adapters or deltas [5, 7, 14, 37, 53], an assumption that breaks in heterogeneous expert ecosys-tems whose architectures, vocabularies, and tokenizers differ. 

Passive caching , from LRU eviction to prefix reuse [58], de-cides what to keep from past reference statistics alone; blind to which model comes next, it discards the call-graph pri-ors that agent workloads expose for free. These approaches improve different scheduling and memory costs, but leave open how one memory-constrained GPU should jointly se-lect weight shards and session KV as demand changes. This paper tackles exactly one question: under a single GPU’s tight memory budget, which bytes, weight shards or KV blocks, should reside, when should they move, and on whose signal? Our goal is to have both: the capacity headroom of aggressive swapping and the interactivity of full residency, without paying for one with the other. Talaria uses session-aware placement and admission across serving instances [28]. JointServe instead manages weight shards and KV blocks within one constrained GPU, using the caller’s named target to move bytes ahead of demand. Two insights make this possible. First, residency is one problem, not two. Weight shards and KV blocks compete for the same memory pool, so we model both as residency objects under a single budget with explicit restore costs, and show that a fixed partition can become infeasible under the measured crash budget. Second, agent call structure supplies signals that passive statistics cannot. A planner reveals its target model while it is still generating the tool call, tool execution leaves idle gaps between calls, and 96.4–99.9% prefix reuse makes preserved KV state highly valuable. Together these observa-tions turn the question of when to move from a prediction problem into a read-off problem. JointServe occupies a point that complements, rather than competes with, recent serving systems. BlitzScale [56] scales model instances at the cluster level; Pensieve, HCache, and MORI [12, 45, 54] tier the KV state of a single model across the memory hierarchy; NanoFlow [61] overlaps compute, memory, and communication within an operator pipeline; and DeltaZip [53] compresses families of same-base fine-tunes. JointServe manages the unified residency of heteroge-neous weights and KV within a single instance .Concretely, this paper makes three contributions. 

• Unified residency formulation and adaptive split. 

We formulate weight shards and KV blocks as same-domain residents of a single memory budget under an explicit cost model 𝑐 𝑖 = 𝛼 + 𝑠 /BW + 𝑟 (𝑛 ), use a carve-out step to adapt the split during serving, and prove a (1 − 𝜀 ) recovery-value approximation for one selection snapshot of independent, additive objects. 

• Caller-generation proactive prefetching. We ex-tract agent call-graph semantics into residency sig-nals. The planner’s streaming tool-call header deter-ministically identifies the target model, moving the swap window from after request arrival to the caller’s generation phase and tool gaps; a preemptive, chunk-granular transfer scheduler with a 𝜅 -floor bandwidth share keeps weight movement from starving KV restora-tion of live sessions. 

• Partial-shard streaming hot-swap and dual-state KV tiering. Each of 𝑁 heterogeneous models keeps an analytically derived resident shard of 𝑘 ∗ layers with per-group readiness checks, so a swap streams only the remaining 𝐿 − 𝑘 ∗ layers; the evaluated prototype switches by in-place overwrite, and a dual-state KV tier substitutes host-RAM reload for GPU recompute at a 20 × cost advantage. We implement JointServe on top of SGLang [58] and eval-uate it across a range of real-world traces and datasets. Com-pared with the strongest whole-model swap baseline, JointServe reduces SCT by 21.7% in the tight memory regime, stays fea-sible in a crash regime where every whole-model swap base-line fails to finish (a 46 × gap), and on real agent traces lifts SLO attainment from 2.8–24.5% to 76.8–100% while cutting SCT by up to 49%.

## 2 Background and Motivation 

2.1 Model-as-Tool Agents and Serving Preliminaries 

Multi-agent systems increasingly follow a model-as-tool ar-chitecture: a general-purpose planner model decomposes a task, streams intermediate reasoning, and invokes domain 

experts through tool calls, which execute on the tool’s output and resume planning. Software-engineering agents call a coding model behind a fixed agent–computer interface [49], and multi-agent systems cast planning, implementation, and review as roles played by different models [13, 32]. The ex-pert pool assembled this way is genuinely heterogeneous, for three recurring reasons. Domain experts are fine-tuned from different base models and released independently; mul-timodal experts, such as vision or code models, carry their own architectures, vocabularies, and tokenizers; and legacy models remain in service long after their training stacks are retired. Expert heterogeneity matters to a serving sys-tem: it rules out sharing a single base weight across the pool, which precludes adapter- and delta-based co-residency schemes. Recent agent-serving systems schedule program structure and call dependencies well, but they assume that every model an agent may invoke stays resident at some serving endpoint [21, 27]. JointServe starts where that as-sumption breaks. Serving engines such as vLLM and SGLang process each request in two phases [17, 58]. Prefill consumes the prompt in one forward pass and materializes its key–value (KV) state, which the engine caches in HBM as paged blocks; decode 

then generates tokens autoregressively, reusing that state at every step. Unlike request-level latency models in the serving literature [1, 30, 43, 59], which separate queuing from execu-tion, a cross-model call must also pay for memory movement. A cross-model call traverses four latency components,

2.2 Why Not Swap Whole Models Faster? 

The most direct response to capacity pressure is to reduce switching cost. ServerlessLLM [11] accelerates checkpoint loading, while Talaria [28] stages model weights across cold-pool switches and preserves host-restorable session KV. These methods reduce exposed transfer and recovery time. A con-ventional whole-model reload, however, admits prefill only after the target weights are ready. When the weights have not been staged, moving the whole target model remains on the first-token path. JointServe instead keeps a startup prefix resident and streams later layer groups as execution proceeds. Figure 2 quantifies the tax. Swapping in a 7B FP16 expert (15.2 GB) at the full 24 GB/s host-to-device bandwidth costs 0.63 s with the GPU producing nothing, and the serial swap plus prefill reaches 0.74 s of TTFT; both grow linearly with model size. The default engine reload path, which stops the instance, streams the full checkpoint off NVMe into host memory, copies it over PCIe into HBM, and re-initializes the runtime before serving resumes, is two orders of magnitude worse at 67.76 s for a 7B model: it serializes disk reads, host-to-device copies, and engine re-initialization, overlapping none of them with compute and serving no layer before the last one lands.

2.3 Why Not Shrink Models to Co-Reside? 

A second family of designs avoids swapping altogether by making the weights small enough that the whole pool fits at once: quantize every expert to four bits, or share one base model across many adapters [10, 22, 37, 53]. Shrinking the weights, however, merely relocates the contention rather than removing it. Figure 5(a) makes the arithmetic concrete at a 32 GB effective budget. A whole-model swapper locks 15.2 GB for one FP16 expert and leaves 16.8 GB for KV; the INT4 co-resident scheme locks 21.1 GB for all five experts and leaves only 10.9 GB for KV. Compression has pinned more bytes in weights that may sit idle for whole stretches of a session, and the space left to the state that grows without bound shrinks. Nor does accuracy come for free: low-bit quantization degrades mathematical and code competence, a cost documented in the quantization literature [10, 22]. Adapter- and delta-based sharing is bounded by an even earlier constraint: it presumes a shared base model, which the heterogeneous expert pool does not have.

2.4 How Does Session-Aware Routing Differ? 

Talaria [28] treats agent continuations as stateful. Its router weighs model residency, KV locality, and instance pressure; soft reservations preserve likely return affinity, while instance-local host KV can be restored across model switches. Cold-pool instances time-share multiple models and stage weights, so Talaria neither requires a full replica of every model nor discards session KV at each switch. Its main decisions con-cern where and when a session runs in a serverless pool. JointServe addresses a complementary decision within one memory-constrained GPU: which layer-group weight shards and session KV blocks share HBM, and which missing groups to prefetch using the caller’s intent. The two policies act at different scheduling levels; their integration is outside this paper’s evaluation. Whole-model staging, compression, and session-aware routing address transfer, weight footprint, and cross-instance continuity, respectively; JointServe instead selects weight shards and KV blocks jointly within one GPU and combines this with intent-driven prefetch and partial residency (§3). 

O3: Eviction is not destruction. Across four traces, prefix reuse is 96–100%; at the SWE-bench median context, host KV reload takes 0.05 s versus 2.64 s for re-prefill, making host RAM a useful second residency tier.

## 4 JointServe System Design 

JointServe turns the residency selection of §3 into trans-fers and execution through the architecture in Figure 9. The Request Scheduler, Residency Manager, and Signal Engine form the serving-control layer, which produces versioned residency plans. The GPU Worker and Transfer Scheduler ex-ecute those plans across shared HBM and host memory. This separation lets the residency policy operate independently of the loading back end. Executing a residency plan requires making room for the next model while preserving the state of in-flight sessions. The Residency Manager tracks the selected target separately from the objects ready for execution. Within the shared HBM budget, the Transfer Scheduler overlaps weight load-ing with KV movement where dependencies permit and reserves bandwidth for live-session KV traffic. The GPU Worker begins prefill once the startup layer groups and re-quired session KV are resident, while later groups stream in alongside computation. Per-group ready events enforce the remaining dependencies, allowing execution to begin before the full model arrives.

4.2 Executing Residency Plans 

A plan is a differential, not a re-derivation: Algorithm 1 hands the Residency Manager a target residency set, its per-type quotas, and a diff of actions, release or offload displaced objects and load selected ones (Figure 9, steps 3–6). Execution rests on one identity and one registry: every object keeps its model or session key end to end, and the host side registers a read-only weight bank plus a host KV store keyed by model. Commit is a three-step protocol: the delta is dispatched, with evictions and offloads running in parallel with loads and restores (steps 4–6). The Transfer Scheduler reports startup readiness once the groups needed to begin execution are resident (step 7), and the manager atomically switches the residency mapping and hands control back to the Request Scheduler (steps 8–9). Target set and ready set are tracked as distinct states: a new mapping is never committed before reclamation finishes and the target copies are in place, and the protected set of §3.1 is as unevictable here as it was in selection. If a plan is infeasible or capacity falls short, the old mapping is retained and the request returns to the decision layer, the runtime counterpart of the CapacityShortfall branch of Algorithm 1. The plan determines which objects move; the Transfer Scheduler determines their order. Per-group ready events from the runtime establish when the startup prefix and re-quired session state can be used. Remaining groups must arrive by their first use; otherwise, execution waits on the corresponding ready event. These execution checks preserve the selected target while tracking which parts are ready. 

4.3 Preemptive Transfer Scheduler 

Three traffic classes share one host-to-device channel: target-model prefetch, the streaming shard refill of §4.4, and back-ground KV offload and restore. Left unordered, a gigabyte-scale weight burst would starve the KV restoration of ses-sions already in service. The scheduler enforces a static priority order, target prefetch above pipeline shard stream above background KV, and chunks weight transfers at layer-group granularity so a higher-priority transfer preempts an in-flight one at chunk boundaries. A 𝜅 -floor, 15% of link bandwidth by default, re-serves a minimum share for the KV traffic of live sessions: a lower bound on what KV restoration receives, not an up-per bound on what weights may use when the channel is otherwise idle. Per-task readiness reports aggregate into the transfer status of step 7 in Figure 9. The scheduler only or-ders the deltas that §4.2 hands down and never alters the target set. Its priority input comes from the Signal Engine, whose intent marks the highest level, so signal, decision, and transfer depend on one another in a single direction.

Layer-granular loading is an established lineage: PipeSwitch [3] pipelines one model’s layers over PCIe for context switching, ZeRO-Inference [2] streams a single oversized model from CPU or NVMe memory, and 𝜆 Scale [55] and BlitzScale [56] amortize loading across a cluster. All four move the layers of one model, or share one model’s loading cost across in-stances. None keeps several heterogeneous models partially resident in one memory pool and reassembles the working set per call. The two directions are orthogonal and compose: a single instance can run the 𝑘 ∗-prefix scheme here while the cluster layer reuses a multicast loading path. 

## 5 Implementation 

JointServe is implemented on SGLang [58]: the system core is about 1.5K lines of Python. Three hook groups form the integration surface. submit_plan(target, delta) hands the runtime one versioned residency plan: a target set plus the release, offload, load, and restore actions that reach it. 

ready_event reports one layer group’s copy completion to the commit protocol. kv_load and kv_offload move session KV between the HBM and host tiers, and the intent tap observes the engine’s output stream without rerouting it. The shard loader reads layer groups from a pinned, read-only host weight bank and copies them host-to-device on a dedicated stream that overlaps compute; page-locked stag-ing keeps the copy at link rate, and the per-group events aggregate into the startup-readiness report that the commit protocol of §4.2 waits on. Two residency managers, one for weight shards and one for KV blocks, hold the residency maps keyed by model and session. The stock reload path re-reads a full checkpoint from disk and admits execution only after the entire state dict is resident, so JointServe bypasses the engine loader and writes weight buffers directly from host memory. The Signal Engine, Residency Manager, and Transfer Sched-uler run as asynchronous threads that consume only the output-stream tap and engine heartbeats, never the request critical path. Plan deltas execute concurrently, and only the final mapping switch is serialized. Priorities and the 𝜅 -floor are chunked queues inside the transfer channel, and preemp-tion happens at chunk boundaries. Amortized control-plane overhead stays below 0.1% of a decode step (§6). 

## 6 Evaluation 

We evaluate the full JointServe implementation against five baselines on synthetic and real agent workloads. Three re-sults summarize the chapter: 

• Across memory budgets, JointServe cuts median session completion time (SCT) by 21.7% against the strongest whole-model baseline in the tight regime, and remains feasible at a crash budget where every whole-model base-line stalls past the measurement window. 

• On real agent traces, JointServe raises SLO attainment on 

𝜏 -bench from 24.5% to 100% and cuts SWE-bench SCT by 49.1%. 

• The mechanism itself is fast: a streaming hot-swap changes the resident expert in 1.83 s where an engine reload takes 67.76 s (37 ×), and the control plane amortizes to under 0.1% of a decode step.

6.2 Baselines 

Our System uses the five baselines: 

vLLM [17] restarts the engine on every model switch, the naive path. 

SGLang [58] re-reads weights from NVMe and hot-reloads them without a restart, with HiCache-style LRU tiering for KV state; this is the default path of a mainstream serving framework. 

ServerlessLLM [11] is the fastest published loading stack; we configure it at its official 23 GB/s loading bandwidth and additionally compare against an idealized host-resident vari-ant that pays only the H2D transfer, which serves as an optimistic upper bound for the whole-model family. 

INT4-CoResident keeps 4-bit weights of all experts resi-dent and never swaps, the compression-only route. 

INT4-Swap combines 4-bit weights with whole-model swap, the naive combination of the two routes. We report JointServe in two forms: JointServe (FP16, lossless) and JointServe-INT4 (sharding composed with quantization). 

6.3 Evaluation Metrics SCT is the primary metric: how long a user waits for a whole agent task. TTFT captures interactivity at the request level, and SLO attainment converts it to a production-readiness number: the fraction of requests with TTFT under 5 s, a threshold in line with what interactive agent workloads tol-erate. Stall decomposition attributes per-request waiting to three sources, weight-switch, KV-reload, and KV-recompute, following the latency anatomy of a cross-model call. Model-switch count exposes behavior directly: whether partial residency eliminates switching altogether. 

6.4 End-to-End Results JointServe dominates across all pressure regimes (Fig. 10). In the tight regime ( 𝑏 =0.4, 24 GB usable), JointServe com-pletes the median session in 516 s, reducing SCT by 21.7– 72.9% over the stronger swapping baselines and by 15 × over vLLM. The advantage comes from spending the scarce bytes on high-value objects rather than on whichever whole model happens to be resident. In the crash regime ( 𝑏 =0.2, 8 GB us-able), every baseline that must place a whole model does not finish within the 35,000 s measurement window; JointServe, which needs only a 𝑘 ∗ shard per active model, completes in 758 s, a 46 × gap against the least-affected baseline’s truncated reading. When capacity is ample ( 𝑏 =1.0), JointServe still reduces SCT by 37.5% relative to ServerlessLLM, while matching INT4-CoResident, for which all weights already fit in HBM. This convergence is expected: once residency ceases to be a constraint, there is little room for sharding to improve capacity utilization. In contrast, SGLang remains 8.3 × slower than JointServe even at full HBM capacity, indicating that its bottleneck lies in the storage-backed reload path rather than in HBM capacity itself. 

Quantization composes with, and does not replace, sharding. At 7B under the tight budget, quantizing a whole-model swap reduces transfer cost but retains the whole-model loading barrier; JointServe-INT4 remains about 21% faster than INT4-Swap. As the budget increases, the two con-verge to within 2%, since both configurations can keep their working sets resident. The distinction grows with model size: at 32B, JointServe-INT4 is 2.3 × faster than the best fea-sible alternative in the tight regime. Under the crash budget, FP16 sharding and INT4 whole-model swapping both cross the capacity limit, while JointServe-INT4 remains feasible at both 14B and 32B. Thus, quantization lowers the cost of movement, whereas sharding removes the whole-model ca-pacity requirement; combining the two is the only evaluated configuration that remains robust as model size grows.

## 7 Discussion 

Capacity determines gains and feasibility. At loose bud-gets, compute saturates and residency policies converge; at 

𝑏 =0.4, JointServe saves 21.7% of session time; at the crash budget, whole-model baselines do not finish within the mea-surement window. SGLang still has 8.3 × JointServe’s median SCT at full capacity because its storage-backed reload cost remains. 

Gap structure shifts the benefit. Switch-bound SWE-bench mainly gains completion time, 𝜏 -bench gains interac-tivity, and OSWorld’s long tool gaps hide much of the transfer. Intent-driven prefetch reduces exposed stall, so end-to-end gains depend on the baseline’s critical path. 

Adaptive allocation preserves feasibility. The control mechanisms are super-additive: nearly neutral individually but decisive together. Shifting capacity between weights and KV fits working sets that a fixed split cannot hold at the crash budget. Steady-state speed alone understates this benefit. 

## 8 Related Work 

Model and request placement. ServerlessLLM [11] speeds load-ing; BlitzScale [56] loads layers for autoscaling. Talaria [28] routes by residency, KV locality, and pressure, preserving return continuity through soft reservations, mid-slot admis-sion, host-restorable KV, and staged weights. MuxServe and Llumnix [9, 39] multiplex or schedule instances. JointServe selects weight shards and KV blocks inside one GPU, retains startup prefixes, and streams missing groups. 

KV and model families. Pensieve and HCache [12, 54] pre-serve or restore KV; MORI [45] moves it during idle windows. CacheBlend [50] reuses KV; CacheGen [25] compresses and streams it. InfiniGen, H 2O, StreamingLLM, SnapKV, and PyramidKV [4, 18, 20, 47, 57] manage long-context KV, and KIVI [26] quantizes it. AWQ and GPTQ [10, 22] compress weights; S-LoRA and Punica [5, 37] serve shared-base adapters; DeltaZip [53] compresses fine-tuned deltas. JointServe in-stead jointly allocates distinct-expert weights and session KV. 

Agent execution. Parrot and Autellix [21, 27] expose or schedule agent structure; NanoFlow [61] overlaps pipeline operations. JointServe prefetches the named expert before request arrival; their combination remains untested. 

## 9 Limitations and Future Work 

JointServe serves heterogeneous, full-parameter experts on memory-constrained GPU; shared-base experts better suit adapters. Intent extraction assumes that tool-call headers are visible in the caller’s output stream, as in structured function calling. The residency objective estimates reuse and recovery cost over a decision window. The measured gains depend on transfer bandwidth, prefill cost, and available overlap, so their magnitude may differ on other hardware or agent traces. Future work can pair cluster replica counts with per-instance residency, use intermediate activations as a third KV recovery source between host reload and recompute, and adapt the currently fixed selection precision and re-solving cadence to observed estimation error. 

## 10 Conclusion 

Serving multi-model agents on a memory-constrained GPU forces weights and KV state to compete for the same bytes. JointServe treats that competition as one scheduling problem. A unified residency formulation values weight shards and KV blocks on a single recovery-cost scale; signals read from the agent’s own output stream move bytes before requests exist; and a sharded runtime swaps an expert in 1.83 s where a full reload takes 67.76 s. Across memory budgets and three real agent workloads, this keeps sessions interactive where whole-model systems stall, and keeps them feasible where those systems cannot run at all. As agents assemble ever more specialized models onto fixed hardware, we believe residency, not raw capacity, becomes the resource worth scheduling.
