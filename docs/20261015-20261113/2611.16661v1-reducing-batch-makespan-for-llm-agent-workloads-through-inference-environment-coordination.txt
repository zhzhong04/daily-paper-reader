Reducing Batch Makespan for LLM Agent Workloads
through Inference–Environment Coordination
Wei Feng, Meiling Chen, Boxiao Chen, Lu Liu, Bin Zi, Libin Ye, Xingyu Lu∗, Lei Xu,
Jun Zhou
Ling Team, Ant Group
∗Corresponding author
Efficient batch execution of agent tasks is critical to LLM training and development work-
flows, including benchmark evaluation, synthetic-data generation, and RL rollouts. Since
these tasks alternate between LLM inference and environment interaction, we present coor-
dinated optimizations to reduce batch makespan, the time required to complete all tasks
in a batch. For hybrid LLMs, a workload-based resource model guides GPU-memory allo-
cation between key-value (KV) cache and recurrent state and provides a reference sample
concurrency to exploit parallelism while limiting recomputation. Trajectory-aware routing
and scheduling promote cache reuse while balancing worker load. Under constrained
environment capacity, we decouple sample admission from environment execution and
introduce Chain-Advancing Action Scheduling (CAAS), which prioritizes long chains using
observed progress to shorten the batch tail. Controlled replay combines actual inference
with recorded environment responses and durations for ablations of individual optimiza-
tions. Live evaluations with Ling-3.0-Flash and Ling-3.1-Flash on the BFCL, SWE-bench
Multilingual, WideSearch, and MCP-Atlas benchmarks demonstrate makespan reductions
of 10.4%–65.0%, while evaluation scores remain aligned. Furthermore, these methods have
been successfully applied to training and evaluation workflows for the Ling-3.x model
series, accelerating the model-development cycle.

Introduction
The training and development of agentic LLMs rely on workflows such as benchmark evaluation,
synthetic-data generation, and RL rollouts. Repeated across model-development iterations, these
workflows often execute agent tasks in batches, with downstream stages awaiting the entire batch.
Batch completion time therefore affects development efficiency, motivating our focus on reducing
batch makespan, the time required to complete all tasks in a batch, rather than the request-level
latency typically optimized in conventional serving, such as time to first token (TTFT) and time per
output token (TPOT) (Kwon et al., 2023).
We refer to an agentic task instance as a sample and its complete execution as a trajectory. Figure 1
illustrates how a batch of such trajectories is executed, each alternating between LLM inference
and environment interaction. Tasks are admitted under a sample-concurrency limit, and their
inference requests are routed to workers and ordered by local schedulers. Actions produced by the
model are queued as environment jobs and dispatched under an execution limit. Model responses
and environment results are appended to the task’s context before the next inference turn. A final

Successive requests within a trajectory share growing input prefixes, creating opportunities for
cache reuse. Hybrid models such as Ling-3.0-Flash (Ling Team, 2026a), Qwen3.8-Max (Qwen Team,
2026), and Kimi K3 (Kimi Team, 2026) require both KV cache and recurrent state for cross-turn
reuse. For a given model, KV-cache memory grows with the number of cached tokens, whereas
each recurrent state has a fixed size. Thus, longer contexts increase KV-cache demand per trajectory,
while admitting more concurrent trajectories requires retaining more recurrent states as well as
their associated KV cache. SGLang manages these states in separate pools within a shared cache-
memory budget. If a default or empirically chosen allocation ratio does not accurately reflect
the target workload’s cache-demand characteristics, one pool can be exhausted while substantial
capacity remains unused in the other. This imbalance limits the number of trajectories whose caches
can be retained together. Our workload-aware capacity model quantifies the target workload’s
recurrent-state and KV-cache requirements to balance memory allocation between the two pools
at deployment and provide a reference sample concurrency, enabling greater parallelism while
preserving cross-turn cache reuse. The resulting allocation remains fixed during inference serving.
Even with suitable allocation, reuse depends on where and when requests execute. With multiple
inference workers, keeping a trajectory’s requests on the same worker favors reuse, but strict affinity
can concentrate load and lengthen queues. Even on a worker holding reusable state, a request
can wait long enough for that state to be evicted. In addition, model responses and environment
results accumulate across turns, potentially producing very long agent contexts. Identifying
cache-reuse opportunities through token-prefix matching can then incur substantial computational
overhead. To reduce this overhead, we use a shared trajectory label to identify requests from the
same trajectory at low cost, giving the router an affinity key and letting the worker screen waiting
requests before querying the prefix cache for scheduling priority. We implement this approach
through two complementary methods. Load-bounded consistent hashing (LBCH) routing uses the
labels to preserve cross-turn worker affinity while accounting for worker load. Routing-prefix (RP)
2


scheduling uses them to prioritize requests from recently served trajectories and promote timely
cache reuse at low scheduling cost.
Environment resources may also be constrained by CPU budgets or external-service quotas.
A single sample-concurrency limit, as used in the agent implementations of MCP-Atlas and
τ3-bench (Bandi et al., 2026; Shi et al., 2026), couples the two stages. When the environment sup-
ports less concurrency than the inference service, raising this shared limit to keep inference busy
can overload environment execution. Conversely, lowering it to protect the environment can leave
inference workers without ready requests while active samples await environment-interaction
results. We therefore decouple sample admission from environment execution, allowing more
samples to remain active while an independent execution limit protects the environment. This
improves stage overlap but also makes environment-side queuing more likely as more admitted
samples submit jobs to the limited execution slots. Their dispatch order determines when each
trajectory can resume inference. Repeated waits can defer a long trajectory’s later stages until most
other samples have finished, leaving few ready inference requests and prolonging the batch tail.
When multiple environment jobs await execution, Chain-Advancing Action Scheduling (CAAS)
uses observed progress to prioritize those from potentially long trajectories. This aims to expose
their subsequent stages sooner and shorten the batch tail without requiring knowledge of remaining
trajectory lengths.
Our contributions are summarized as follows.
1. Workload-based and trajectory-aware inference optimization. A hybrid-cache capacity model
guides allocation and sample concurrency, complemented by LBCH routing for affinity–load
balance and routing-prefix scheduling for timely cross-turn reuse.
2. Inference–environment coordination. Independent sample and environment concurrency
controls improve stage overlap, while CAAS effectively advances long execution chains to
shorten the batch tail.
3. Controlled replay and live end-to-end validation. Trace-driven replay combines actual inference
with recorded environment responses and durations for controlled comparisons and ablations.
Live evaluations with Ling-3.0-Flash and Ling-3.1-Flash across four well-known benchmarks
demonstrate substantial reductions in batch makespan, while evaluation scores remain aligned
(Section 5.4). The proposed methods are also applied in Ling-3.x model development, where
batched agent workloads such as benchmark evaluation, synthetic-data generation, and RL
rollouts play a key role. By accelerating these workloads, the methods substantially improve
overall development efficiency.
The remainder of this paper presents the methods and experimental evaluations supporting these
contributions. Section 2 reviews related work. Sections 3 and 4 present inference-side optimizations
and inference–environment coordination, respectively. Section 5 evaluates the proposed methods
through controlled replay and live execution. Section 6 discusses future directions, and Section 7
concludes the paper.

Related Work
Prefix caching. Prefix caching avoids repeated computation over shared prompt prefixes. Serving
systems support prefix reuse through mechanisms such as SGLang’s RadixAttention (Zheng et al.,
2024) and vLLM’s automatic prefix caching (vLLM Project, 2026). Mooncake, Tutti, and CacheFlow
extend cache management across distributed or multi-tier settings (Qin et al., 2024; Qiu et al., 2026;
Nian et al., 2026). Li et al. (2026) survey these broader cache-management techniques. BatchLLM
3


exploits globally available prefix structure and throughput-oriented batching for large inference
batches (Zheng et al., 2026), whereas we target cross-turn reuse within agent trajectories.
Cache management for hybrid LLMs. Cache reuse in hybrid LLMs requires retaining both KV
cache and recurrent state. AVMP manages separate KV-cache and state-space-model (SSM) state
pools through a unified virtual page table (Nguyen, 2026). It can transfer capacity between pools at
runtime when allocation fails in one pool and the other has enough spare capacity. Marconi selects
recurrent states for caching based on their reuse potential and guides eviction using recency and
computation saved relative to the combined footprint of the KV cache and recurrent state (Pan
et al., 2025). Our workload-aware capacity model uses trajectory profiles to select a static partition
of the cache budget and a reference sample concurrency before serving, with the goal of increasing
joint trajectory-cache residency.
Cache-aware routing and scheduling. Preble uses global prefix-cache information and computa-
tion estimates to route requests across workers (Srivatsa et al., 2024). Its local scheduler groups
requests by the fraction of cached prompt tokens and selects requests from each group to form a
batch, assigning larger shares to higher-priority groups. DualMap hashes a prompt prefix to two
candidate workers and uses a time-to-first-token (TTFT) service-level objective to balance affinity
and load (Yuan et al., 2026). PEEK maintains an incremental radix tree over pending requests to
identify shared prefixes even before they are cached (Xie et al., 2026). It uses these relationships to
schedule prefix-sharing requests and protect cache entries needed by queued requests. These meth-
ods use prompt-prefix information to guide routing or scheduling. In contrast, our LBCH routing
and RP scheduling use trajectory labels to identify and exploit potential cache-reuse opportunities.
Agent-aware inference scheduling. Autellix schedules LLM calls using observed program-level
attained service and uses program locality in cross-engine routing (Luo et al., 2025). Helium
represents workflows as query plans and optimizes workflow makespan through rewriting, caching,
and cost-based scheduling (Wadlom et al., 2026). SAGA uses predicted workflow structure for
cache management and workflow-level scheduling (Guo et al., 2026). ConServe uses observable
conversation state to place the first-turn prefill and maintains decoder affinity across turns (Ding
et al., 2026). RP links successive turns of an agent trajectory through shared labels and recent
serving activity, without tracking program-level attained service or requiring workflow graphs.
Environment-aware serving and action scheduling. SAGA uses expected tool-call durations to
guide cache retention (Guo et al., 2026), while MORI uses relative tool-call idleness to guide cache
placement across GPU and CPU memory (Xia et al., 2026). Both use environment behavior to
inform inference-side cache decisions. ARL-Tangram directly schedules external actions, using
first-come, first-served (FCFS) to select candidates and elastic resource allocation to reduce the sum
of action completion times (Xiao et al., 2026). We instead order pending environment jobs under a
fixed execution limit with separate sample admission. CAAS uses observed trajectory progress to
advance long execution chains and shorten the batch tail without changing individual job service
times.

Optimizing Inference Efficiency
This section presents our methods for improving inference efficiency, which are implemented in
SGLang (Zheng et al., 2024). We first examine cache allocation for hybrid models, then present
cross-worker routing and in-worker scheduling to improve cross-turn reuse.

3.1
Workload-Aware Hybrid-Cache Allocation
Hybrid models such as Ling-3.0-Flash (Ling Team, 2026a) combine Multi-head Latent Attention
(MLA) with Kimi Delta Attention (KDA), requiring KV cache and recurrent state, respectively.
Each inference worker maintains separate pools for these states within a shared cache-memory
budget. Cache reuse requires both types of state for the reused prefix to remain available, so the
more constrained pool limits how many trajectories can retain reusable state.
KV-cache demand grows with cached context length, whereas recurrent state occupies a fixed
number of slots per request. As a trajectory extends its prefix, the latest reusable recurrent state
summarizes that prefix and supports subsequent computation without retaining states from earlier
turns. We therefore retain one recurrent state per trajectory, keeping its recurrent-state memory
requirement fixed as the number of turns increases.
At low sample concurrency, performance is relatively insensitive to the cache ratio when both
pools have sufficient capacity. Higher concurrency can shorten makespan, but also increases cache
demand, so an imbalanced allocation can cause eviction and recomputation that offset parallelism
gains. We therefore use a workload-aware capacity model to guide cache allocation and sample
concurrency, aiming to sustain high cross-turn reuse while increasing parallelism.
Model development often involves repeated execution of batched agent workloads, including
benchmark evaluation, synthetic-data generation, and RL rollouts, across successive checkpoints.
For similar task distributions, the mean context length often changes little between nearby check-
points, allowing historical trajectory profiles to provide reusable estimates for guiding cache
allocation and sample concurrency.

3.2
Cross-Worker Trajectory-Aware Routing
We consider a distributed inference deployment comprising a gateway and multiple homogeneous
workers. Each worker is a model-serving replica that independently schedules its assigned inference
requests and maintains its own device-local KV-cache and recurrent-state pools. The gateway
routes each inference turn to one of these workers. We focus on worker-local cache reuse without
6


cross-worker cache transfer, so a later turn can reuse its trajectory cache only on the worker that
currently holds the corresponding cached state.
Routing decisions based solely on load balancing may send successive turns of the same trajectory
to different workers, missing opportunities for cache reuse. Conversely, prioritizing trajectory
affinity without considering worker load can concentrate requests on a few workers. Requests may
then queue at these workers while others remain idle, reducing overall inference efficiency. We
adapt consistent hashing with bounded loads (Mirrokni et al., 2016) to per-turn inference routing.

wait in the worker’s queue long enough for its trajectory’s cached state to be evicted. When

prefix-matching overhead.

The label set A records recent batch admissions, not GPU cache residency. Its LRU updates are
independent of GPU cache eviction, so labels and cached state can become inconsistent in two ways.
First, a label may remain in A after the corresponding cached state has been evicted. If eviction
occurs before the prefix lookup, the resulting hit length may be short or zero, potentially lowering
the request’s rank within the first tier. If eviction occurs after the lookup, the stored hit length may
become stale because subsequent priority calculations reuse it without another lookup. Second, a
label may be removed from A while corresponding cached state remains on the worker: removing
a label does not evict that state. A request with this label skips the priority-related prefix lookup
and enters the second tier, potentially missing an opportunity to prioritize reuse of the remaining
cached state.
The capacity CA therefore controls label coverage, not GPU cache allocation. Larger sets offer
more reuse opportunities at higher prefix-query cost, while smaller sets reduce this cost but may
miss reuse opportunities. We use CA = ⌊C(ˆr; D)⌋as a model-informed default, matching the set
capacity to the estimated number of trajectories whose KV cache and recurrent state one worker
can retain under the selected cache ratio. Section 5.2.2 evaluates whether this RP design preserves
cache reuse and limits priority-calculation cost under cache pressure.
3.4
Integration with SGLang
At deployment, we apply the selected cache ratio ˆr through SGLang’s native mamba_full_memory_-
ratio parameter. Since each trajectory requires only its latest reusable recurrent state, as explained
in Section 3.1, we use SGLang’s native path-based Mamba-state eviction with mamba_max_states_-
per_path=1 to prune older states as the trajectory advances. We add LBCH as a routing policy in
SGLang’s router and RP as a scheduling policy in each worker. Both policies use the same trajectory
label carried as request metadata. LBCH selects a worker using this label and in-flight request
counts. RP reorders the waiting queue while reusing SGLang’s existing prefix-cache lookup and
resource-constrained batch builder. Sample admission remains controlled by the agent execution
layer, as described in Section 4.

Chain-Advancing Action Scheduling

which can increase queueing for environment jobs. Their dispatch order determines which trajectory
resumes inference next. In practice, a few long trajectories often prolong batch completion after

and advance potentially long trajectories earlier through environment-job scheduling to shorten
batch makespan.

potentially long trajectories and prioritizes deeper chains within each arrival band. This allows
subsequent stages to be revealed and executed sooner and reduces the risk that long chains are
left to dominate batch completion. Arrival bands prevent returning trajectories from repeatedly
overtaking shallower jobs waiting in earlier bands, as can happen under depth-only ordering.
Section 5.3 shows that CAAS reduces batch tail and makespan over FCFS after capacity separation.
5
Experimental Evaluation
Our evaluation examines how the proposed optimizations reduce batch makespan, both individu-
ally and in combination. Section 5.1 first describes the replay framework and experimental setup.
Using controlled replay, we evaluate how cache allocation, sample concurrency, scheduling, and
routing affect inference efficiency (Section 5.2), and isolate the effects of capacity separation and
CAAS under constrained environment capacity (Section 5.3). Live experiments then evaluate their
combined effects across models of different sizes (Section 5.4).
5.1
Controlled Replay Framework and Setup
Real-world environment interactions vary with network conditions, provider load, rate limits,
retries, and response drift, making repeatable comparisons across system configurations difficult.
To support controlled comparisons, we combine actual model inference with recorded environ-
ment responses and service durations from historical agent trajectories. Replay runs within each
comparison use the same initial messages, stage sequences, per-turn target output lengths, and
recorded environment responses and durations.
Figure 2 illustrates the turn-by-turn replay of a trajectory. At each inference turn, the input consists
of the initial user message followed, in execution order, by model responses generated in preceding
replay turns and recorded environment responses released earlier in the replay. A deployed
SGLang service performs actual inference, generating the same number of output tokens as the
corresponding historical turn. If an environment stage follows, the trajectory waits for an available
execution slot and then pauses for the recorded job duration. The framework subsequently appends
the recorded environment response to the context, making the next inference turn ready.
No environment actions execute during replay. Stage dependencies and environment durations
remain fixed, while inference latency and cache reuse arise from actual serving. The replay timeline
includes measured inference times, recorded environment durations, and queueing delays under
the selected admission limits, execution capacity, and scheduling policies. Batch makespan is the
elapsed time until all trajectories complete. Replay therefore measures execution efficiency rather
than semantic correctness, as generated text need not reproduce the recorded action.
All replay experiments use Ling-3.0-Flash with thinking enabled, served by SGLang on H20 GPUs
with four-way tensor parallelism (TP4) per worker. The model combines KDA and Multi-head
Latent Attention layers at a 5:1 ratio with a sparse MoE backbone (Ling Team, 2026a). Inference-
only replay covers SWE-bench Multilingual (SWE) (Khandpur et al., 2025), BFCL-v4 (BFCL) (Patil
et al., 2025), and WideSearch (Wong et al., 2025), bypassing environment durations and capacity
limits. Coordination replay uses MCP-Atlas (Bandi et al., 2026) with recorded environment stages.
Within each replay comparison, we keep the checkpoint, sampling parameters, workload, hardware
budget, submission order, and target output lengths fixed. Appendix A.1 provides the inference-
only replay workload details.

Cache allocation and admission operating point
We evaluate the joint effect of cache allocation and sample admission on a single TP4 worker with
FCFS scheduling. Using Equation 6, we obtain rbal = 0.09 for SWE, rbal = 2.26 for BFCL, and

859, and 98, respectively. We perform a grid search over cache ratios and sample-concurrency limits
around these model-derived reference points. Figure 3 summarizes the resulting makespans.
Joint operating region.
Under FCFS scheduling, the model-derived operating points yield
makespans close to the best measured values across all three workloads, leaving only modest
room for further improvement through local search. The analytical capacity model abstracts away
allocation granularity and runtime fragmentation. Nevertheless, these results show that it provides
a simple yet effective heuristic for jointly selecting the cache ratio and sample concurrency by
accounting for trajectory token footprints and the number of trajectories that can remain resident.
The sweeps around the model-derived operating points show that the benefit of increasing con-
currency depends on the cache ratio. At a fixed ratio, raising concurrency from below Cref can

cache reuse to explain these trends.
Cache reuse and the cost of excess concurrency. This limited sensitivity at low concurrency is
consistent with both cache pools having sufficient capacity to retain reusable state across a broad

consistent with earlier release of subsequent inference work.

during the current run. These gains come from changing job dispatch order, not service times.

allocation, scheduling, and routing in preserving cache reuse at higher concurrency and reducing
batch makespan. The latency measurements further clarify how these batch-level gains relate
to individual request performance. Compared with the concurrency-matched Baseline-2, Opt
reduces TTFT by 24.9% and 50.2%, and TPOT by 51.1% and 40.2%, for Ling-3.0-Flash and Ling-3.1-

makespan, reflecting the distinction between batch efficiency and per-request latency. Appendix A.3
provides a detailed analysis of the SWE results.

the batch much earlier while taking longer to complete its final 5%, so L5 alone should not be used
to compare overall execution efficiency across different admission policies.

the baseline and optimized configurations, indicating that the efficiency gains do not come at the
expense of response quality.
6
Discussion and Future Work
Although this work focuses on batch makespan in LLM training and development workflows,
its underlying principles may extend to other agent workloads. For example, in personal-agent
services, workload-aware cache allocation, RP scheduling, and LBCH routing could preserve
cross-turn reuse while supporting concurrent users. These mechanisms could reduce prefix recom-
putation and shorten the prefill component of TTFT. Reducing redundant prefill may also help
reduce TPOT by leaving more capacity for ongoing decoding. Separating sample admission from
environment-execution capacity could let ready trajectories use GPUs while others wait for tools
or external services. In workflows with parallel subagents, the chain-advancing principle behind
CAAS could inform tool-job scheduling to advance subagents that delay downstream aggregation
or overall task completion.
Many directions remain for improving agent trajectory execution efficiency and further reduc-
ing makespan. These include extending workload-aware cache allocation and trajectory-aware
scheduling to hierarchical caching while accounting for cache capacity and transfer costs, and
investigating cache eviction policies for hybrid models in agent workloads. Another important
direction is makespan optimization subject to application service-level objectives (SLOs), such as
TTFT and TPOT targets, which is relevant to datacenters seeking to improve task throughput while
meeting user-facing latency requirements.

7
Conclusion
We present coordinated inference and environment optimizations to reduce batch makespan
for multi-turn agents served by hybrid LLMs. A workload-aware capacity model guides cache
allocation and sample concurrency, while RP and LBCH promote timely cross-turn reuse at low
scheduling cost and balance trajectory affinity with worker load. Under constrained environment
resources, capacity separation improves inference–environment overlap, and CAAS advances long
execution chains to shorten the batch tail. Controlled replay evaluates individual mechanisms, while
live experiments with Ling-3.0-Flash and Ling-3.1-Flash demonstrate batch makespan reductions of
10.4%–65.0% across four well-established benchmarks without compromising model performance.
Their successful application in developing the Ling-3.x model series demonstrates the practical
value of these optimizations in improving model-development efficiency.
