Recompute or Restore? Host-Tier KV for Multi-Model Agent Workflows
on a Static-Graph NPU Serving Stack
Sungwon Woo
Seyeon Kim∗
Abstract
Agent workflows issue dependent model calls that share
long context prefixes, so serving them efficiently depends
on reusing the key-value (KV) cache of those prefixes.
On accelerators that compile model graphs ahead of time,
however, the device KV budget is fixed, and prefixes
evicted under load must be recomputed. Restoring them
from host memory avoids this recomputation, but the
transfer occupies the same engine thread as prefill and
decode, so its benefit is not guaranteed. In this paper, we
study when restoring beats recomputing on a commercial
static-graph neural processing unit (NPU) stack (Rebel-
lions ATOM+, vllm-rbln 0.10.2) that serves a Qwen3-8B
planner on two cards and a Qwen3-0.6B executor on
one. We first show that repeated prefill dominates plan-
ner work when default serving collapses: 89.5% of the
executed planner prompt tokens had been materialized
before. We then build a synchronous host-DRAM tier
on the runtime’s public KV copy calls, together with a
scheduler-aware event model whose predictions are frozen
before each test cohort. Experimental results show that
the host tier raises workflow service-level objective (SLO)
attainment from 22.8% to 100% and from 9.4% to 99.8%
in the two tested overload conditions, and endpoint con-
firmation on two new seeds supports conservative load
gains of 11.8% (chain) and 18.2% (fork), while mixed
and bursty workloads remain seed-sensitive. The frozen
model predicts median and 99th-percentile (P99) latency
within its 15% tolerance in all 24 common-load conditions,
including the 16–18% P99 increase that the tier causes
for fork workflows, but it misorders three policy contrasts
and overestimates the benefit of a cheaper store path
(11% predicted against 3.1% measured). The trade-off
therefore depends on runtime scheduling and transfer
cost as well as cache capacity.

Introduction
Agent workflows execute small programs of large lan-
guage model (LLM) calls. A planner reads a task and
a shared document, executors handle sub-steps, and an
answer step reads the accumulated context again. Be-
cause consecutive calls share long prefixes, caching the

key-value (KV) state of those prefixes [4, 14] keeps such
workloads affordable, and recent agent-serving systems
schedule around it [5, 7, 8, 2, 3].
Serving these workflows on an accelerator that compiles
model graphs ahead of time raises a different problem. On
such a neural processing unit (NPU), the model graphs
and the KV budget are fixed at compile time, so the device
cache has a fixed size and the vendor runtime owns the
KV layout. When the prefixes of completed requests
are evicted, later calls must recompute them. A host-
memory tier that keeps those prefixes is a known remedy
on GPUs [6, 12, 10], and the NPU vendor documents a
CPU offload path for a newer software stack [9].
However, two questions remain open before a host tier
can be relied on in such a stack.
First, it is unclear
which work actually dominates when serving collapses
under overload, and therefore how much a host tier can
remove. Second, restoration has a cost of its own: storing
a prefix takes time on the same engine thread that runs
decode, and restoring it takes time before the next call
can run. Whether restoring beats recomputing for a given
workload is thus a quantitative question that depends on
how the engine schedules prefill, decode, and transfers.
To answer these questions, we present a measurement
study with prospective validation on one pinned serv-
ing stack, a Rebellions ATOM+ NPU server that runs
a Qwen3-8B planner and a Qwen3-0.6B executor. The
study rests on two components: (i) a host-tier KV bridge
that connects vLLM’s offloading manager to the runtime-
owned KV layout and restores evicted prefixes from host
DRAM, and (ii) a scheduler-aware discrete-event model
that is calibrated on one seed and whose predictions are
frozen before each test cohort. The paper does not pro-
pose a new cache or tiering design. Instead, it measures
what restoration recovers, what it costs, and how far
these effects can be predicted in advance.
Experimental results show that redundant prefill is the
dominant work under overload and that restoring it is
effective. In a collapsed run with default serving, 89.5%
of the executed planner prompt tokens had been material-
ized before, and the host tier raises workflow service-level
objective (SLO) attainment from 22.8% to 100% and
from 9.4% to 99.8% in two overload conditions. Endpoint
confirmation on two new seeds supports conservative load
gains of 11.8% for chain and 18.2% for fork workflows.

• We identify the work that dominates an overload

Background and Motivation
This section describes how a static-graph NPU serves
agent workflows and then examines, on a collapsed run,
which work a host tier would have to remove.
2.1
Serving Agent Workflows on a
Static-Graph NPU
An agent workflow is a small directed acyclic graph (DAG)
of dependent model calls that share long prompt prefixes.
On the stack we study (§4.1), each model is compiled with
a fixed KV budget. The default, which we call KV32, is
the SDK’s automatic value of 32K tokens per model, and
a 64K planner budget (KV64) is used only in the first
two cohorts of Table 1. Decode graphs exist for batch
sizes 1, 2, and 4, whereas prefill runs one request at a
time in fixed 128-token chunks. A long uncached prompt
therefore runs as consecutive 128-token calls without
returning control to the scheduler. The runtime owns
the KV layout and exposes it only through copy calls.
Consequently, when the prefix of a completed request is
evicted, a later call that needs it must recompute it.
2.2
Redundant Prefill Under Overload
To determine what a host tier could recover, we first exam-
ine which work dominates when default serving collapses.
We added an observer to the vLLM engine that records,
for every request, its scheduling, the runtime calls it took
part in, and the blocks allocated to and evicted from it.
In two 48-workflow pairs with the observer on and off, no
records were lost, outputs matched the uninstrumented
server for 192 of 192 requests, and P99 rose by 1.4% and
6.6%; a later check closed the remaining gap between
metadata assignment and runtime completion.

under stock serving at 0.55 workflows/s, a run that col-
lapsed (§4.1 defines the workloads and policies). In this

2.3
Cost of Restoring from Host
Memory
A host tier removes this recomputation, but it adds work
of its own.
On this stack, the copies that move KV
between the device and host memory occupy the same
engine thread that runs prefill and decode, so a store
delays the other requests on that engine and a restore
delays the next call. As a result, cache capacity alone
does not determine whether restoration pays off. In the
host-capacity sweep of §4.2, a tier that holds the whole
reused set still meets the SLO for only 84.1% of workflows
at the higher arrival rate. This motivates a model that
represents engine scheduling explicitly (§3.3).
3
System Design
To answer the two questions above, we build a host tier
for the runtime-owned KV of this stack and a model that
predicts its serving behavior. As illustrated in Figure 2,
the design consists of two components: a host-tier KV
bridge that keeps evicted planner prefixes in host DRAM
and restores them on demand (§3.2), and a scheduler-
aware discrete-event model whose predictions are frozen
before each test cohort (§3.3). The remainder of this
section first gives an overview of the serving path (§3.1)
and then describes each component.
3.1
Overview
Figure 2 shows the serving path with a chain workflow
as the dependency example; replayed prompts are fixed.
Admitted workflows send requests to two engines, a plan-
ner that runs with tensor parallelism (TP) over two cards
and an executor that runs on a third, and the two engines
can overlap in time. On the planner, restore, prefill, and
store occupy the same engine thread as decode. Let Hh
and Hl denote the usable host and local prefix lengths of
a request. When Hh > Hl, the full host prefix is restored
before the remaining prefill. Missing host entries are
stored after prefill, and incomplete stores are invisible to
lookups. Both transfers are conditional: a restore runs
only when Hh > Hl, and a store runs only for missing
host entries. Separately from serving, the event model
uses the frozen trace and a calibration on seed 701 to
make predictions that are fixed before each test cohort.
For the store-cost test, only its store coefficient is changed,
using the isolated store measurement taken before the

serving runs.
Serving policies.
We compare the following serving
policies throughout the paper. B0 is stock serving. F6
caps active workflows at six and in-flight requests at four
per role, admitted in first-in, first-out (FIFO) order. The
suffix +host adds the host tier of §3.2 to either policy;
from §3.3 on, the host arm is F6+host. Comparing F6
with F6+host holds admission fixed, whereas comparing
B0 with F6+host changes both admission and restore.
3.2
Host-Tier KV Restoration
The host tier keeps the KV of evicted planner prefixes
in host DRAM and copies it back to the device when a
later request can reuse it.
Transfer path.
The runtime exposes KV only through
copy calls (get kv cache and set kv cache) on its own
layout. We mapped the host-visible layout of the serving
graph for both TP shards and connected it to vLLM’s
offloading interface. During serving, prefixes are stored
and restored in 128-token slots. A single 2,048-token
copy aborted, whereas 512-token copies passed a separate
round-trip check and are used only in §4.5.
Ordering contracts.
From vLLM’s least-recently-used
(LRU) offloading manager [10], we reuse host-block pin-
ning during loads and the store-publication rule that
keeps incomplete stores invisible to lookups. Two parts
are our own: the mapping from vLLM’s slots to the
runtime’s opaque TP payload, and the link to the run-
ner’s synchronous execution boundary. The worker-local
bridge reserves device mappings through the scheduler
and advances the optimum runner’s input past the re-
stored prefix only after both TP payloads have been
written. The bridge is synchronous and specific to the
single-process executor, and stores run after prefill.
Correctness.
Logits computed from restored KV were
bitwise equal to the original on two cards, and restored
KV was bitwise equal to recomputed KV for the same
graph and input. A 2,048-token round trip took about
165 ms in a microbenchmark outside serving.
3.3
Scheduler-Aware Model
The second component predicts the serving behavior of a
policy before it is run. We first explain why the model
must simulate the engine queues and then describe its
rules, calibration, and use.
Why occupancy is an output.
Our first capacity
forecast replayed the cache to predict host hit rates and
combined them with mean call costs. In the host-capacity
sweep of §4.2, hit rates were right within 1.5 percentage
points at all eight points.
Without the tier, the pre-
dicted completion rate was 0.5808 workflows/s against
0.5880 measured (finite-run throughput including drain).
With the tier, however, the completion rate was under-
predicted by 16–17% with 9 and 18 GiB at 0.80 work-
flows/s, beyond the 15% tolerance. Per-call decode time
stayed at 35.6–36.9 ms while the average number of to-
kens per decode call rose from 2.6 to 3.3–3.7 under load,
which accounts for part of the residual. A model that
fixes occupancy cannot follow this change.
Event model.
We model the vendor scheduler with a
reduced discrete-event simulation. Each role has a FIFO
request queue, at most four running requests, and one
busy flag, and the two role engines can overlap. B0 admits
workflows without a client cap, whereas F6 admits six
workflows and four requests per role. From here on, the
candidate is F6 with the 36 GiB host tier (F6+host); B0
with the tier alone is not carried forward. Dependencies
and tool delays release subsequent nodes, and equal-time
events execute in insertion order.
An idle engine first tries to allocate the oldest waiting
request. If allocation succeeds and a running slot is free,
it serves that request’s entire remaining prefill before
any decode. Otherwise, it decodes one token for every
running request. Prefill costs the required number of
128-token calls plus one wrapper and dispatch overhead,
and decode cost is looked up by role and active request
count. Batch occupancy therefore follows the simulated
queues rather than an assumed function of load.
Cache model.
The cache model reuses the installed
outer-block mapping, search, and eviction code, with a
reduced inner-block model. A planner-only host directory
tracks prefix residency in LRU order. A restore uses the
full host prefix when it exceeds local coverage. Restore,
prefill, and store occupy the same engine, and new host
entries become visible only at completion. These are
timing and metadata operations; no tensors or model
outputs are simulated.
Calibration.
We pool eight calibration runs: four work-
load families, each with B0 and F6+36 GiB, all at seed
701. Each has 480 measured and 32 warmup workflows.
Successful call spans provide mean runtime costs, wrap-
per residuals, and dispatch gaps. Response-token counts
provide role/node/context length distributions, capped
by the request budget. In the calibration run, every re-
sponse reached its budget, so each of these distributions
is a single value. No held-out timings or output lengths
enter calibration, and costs include host-side execution.
We fit no end-to-end latency correction and do not pre-
scribe decode occupancy. In the in-sample check, the final
calibration still underpredicts fork-B0 P99 by 16.0%.

Frozen predictions.
The model and coefficients re-

the store-cost test, only the store coefficient is scaled,
by the ratio measured in the isolated store test, before
the serving runs.
Endpoint predictions use the same
finite-window judge as measurements, but simulate nei-

4
Performance Evaluation
We evaluate the host tier and the frozen model on the
ATOM+ testbed. After describing the setup (§4.1), we
examine overload recovery (§4.2), latency and policy rank-
ing at common load (§4.3), serving capacity (§4.4), and
a change to the store cost (§4.5).
4.1
Evaluation Setup
Testbed.
All runs use Rebellions ATOM+ (RBLN-
CA22) cards with KMD 3.0.0, compiler and optimum-
rbln 0.10.2, and vllm-rbln 0.10.2.post2.
The planner,
Qwen3-8B [13] in bf16, runs with tensor parallelism over
two cards, and the executor, Qwen3-0.6B, runs on a third.
Workloads.
We replay synthetic workflow DAGs with
fixed inputs. A chain workflow consists of a planner plan,
an executor step after a 0.1 s tool delay, and a planner
answer, with generation budgets of 32 tokens each and
512-token shared prefixes drawn from a pool of 64. A
fork workflow consists of a planner plan with a 32-token
budget, two parallel executor branches with 128-token
budgets after a 1 s tool delay, and a planner answer with
a 64-token budget, with 2,048-token prefixes drawn from
a pool of 128. Budgets are maximum generation lengths,
and requests stop at the natural end of sequence. We also
use mixed (50/50 chain and fork) and mixed-burst (mixed
with arrivals at twice the mean rate for 15 s and two-thirds
of it for 45 s in every 60 s cycle). Arrivals are open loop.
Generated outputs do not change later prompts, so the
replay measures serving behavior and does not assess
agent quality. A 50,000-workflow dataset in the same
four profiles, together with the trace generator, is publicly
available [11].
Metrics.
The SLOs are 30 s per chain workflow and
120 s per fork workflow. SLO attainment uses all offered
workflows, latency quantiles use completed workflows, and
throughput counts successful completions over elapsed
time including drain. Errors are always reported.

4.5
Store-Path Optimization
Finally, we test the explanation of the fork tail loss. If the
loss came from synchronous stores, making stores cheaper
should remove it. The model supports this hypothesis:
setting the store cost to zero brought fork P99 back to
the level without the tier, while setting the restore cost
to zero did not change it. In the measured runs, the host
arm’s P99 was 9.9 s in the first half and 6.8–7.3 s in the
second, consistent with a burst of initial stores.
Pooled store path.
Timers added during the capacity
screen split store time into a copy from the device (40–
42%) and host-side packing (55–57%). We then built an
alternative store path, A0 (the existing path is current):
a 36 GiB pool of fixed slots allocated and touched before
measurement and reused after eviction, copies of 512
instead of 128 tokens, and packing straight into pool
slots. When the pool is exhausted, the stock skip-store
behavior is kept and counted. Pool setup took 7.8 s at
server start.
Isolated gates.
Before the serving runs, we tested A0
in two isolated settings, which Figure 6 labels the op gate
and the HTTP gate. On a fixed 2,048-token source, all
correctness controls passed (byte equality, continuation,
poison and load-pin checks, and 21 serialized HTTP
requests with restore and identical outputs). In the op
gate, the foreground store time fell from 119.7 to 74.1 ms
(ratio 0.620, 30 of 30 pairs). In the HTTP gate, where
the steps were timed separately, the copy fell from 68.9 to
23.4 ms and packing from 95.9 to 44.2 ms per 2,048 tokens
(store 170.4 to 72.9 ms). The copy gain matches a per-call
overhead: the same 2,048 tokens took 70.6 ms in 128-
token calls and 23.8 ms in 512-token calls. Preallocation,
buffer reuse, and the copy routine changed together, so
we cannot separate their shares of the packing gain. A
CPU microbenchmark on another server showed a 3.5×
packing gain from preallocated output buffers alone, but
we do not carry that number over.
Serving panel.
The serving panel is fork at 0.36 work-
flows/s on seeds 704 and 705, with four runs per arm
in crossover order. Predictions were frozen after the op
gate by scaling only the store coefficient by the gate ratio.
Every run passed, and every metric was within tolerance.
However, the arithmetic mean of the four run-level P99
values per arm fell from 9.83 to 9.53 s (−3.1%; −3.7% and
−2.5% by seed), while the model predicted 9.66–9.68 to
8.58–8.67 s (−11.2% and −10.4%). The model was close
for the current path (errors 1.4–2.3%) and consistently
optimistic for the new one (10.2–10.7%; Figure 6d).

Interleaving prefill.
Long prefills already run as 128-
token chunks, so we asked whether decode steps could be
placed between them. The installed scheduler admits one
prefill at a time and gives it the engine, and the runner re-
jects mixed prefill and decode batches. The runtime itself
allowed alternating 128-token prefill calls of one request
with decode calls of another, with bitwise-identical logits
in three repetitions. In the model, interleaving at 128,
256, or 512 tokens with zero switching cost gave fork P99
of 10.34, 9.93, and 9.80 s against 9.66 s, because faster
decode for running requests delays new requests’ prefill.
Because the same model overpredicted the A0 benefit,
this result is only weak evidence about the hardware, and
we did not pursue a scheduler change.
5
Discussion
Scope of the measurements.
We measured one ven-
dor stack, one SDK version, and one fixed heterogeneous
placement. The DAGs are synthetic with fixed inputs:
outputs do not change later prompts, so agent semantics,
tool choice, and execution paths are not validated. The
planner’s unique reuse set (36 GiB) fits the largest host
tier we used; the 9/18/36 GiB sweep shows what happens
10


when it does not. Host DRAM use exceeds the payload:
the anonymous-memory peak was about 85 GiB in one
cohort, and the pool of §4.5 is resident from server start.
Measurement limitations.
Energy is gross board
power over a fixed offered window (§4.1), and host CPU
and DRAM energy were not measured. Output differ-
ences are counted per request and not attributed to a
cause. The measurement client changed between cohorts
as described in §4.1. The simulator executes the installed
SDK’s block-management code, so it is specific to this
SDK version.
6
Related Work
Host-tier KV.
LMCache [6] keeps KV outside the
engine and moves it between tiers. SGLang HiCache [12]
separates host and device layouts, overlaps transfers, and
chooses write policies. vLLM’s offloading connector and
LRU manager [10] define the not-ready, pin, and publish
rules we reuse. InferCept [1] studies whether to preserve,
discard, or swap context during tool calls and pipelines
its swaps.
Vendor offloading.
The 0.12 documentation of Re-
bellions describes an offloading path based on LMCache.
The separate lmcache-rbln package supplies the device-
specific integration, and public vllm-rbln code registers
and re-exports its connector. The documented path re-
quires the vllm model implementation and KV tensors on
the RBLN device, and supports host-memory and direct-
NVMe tiers [9]. Our measurements use the pinned 0.10.2
optimum path, whose runtime owns the KV allocation.
We bridge its public get/set interface to vLLM’s offload-
ing machinery so that this older runtime can be measured
with a synchronous host-DRAM tier. We did not evaluate
the vendor connector, and whether our numbers transfer
to it is untested.
Agent serving.
Several systems schedule or cache by
program structure, including Parrot [5], Autellix [7], and
KVFlow [8]. CONCUR [2] and ThunderAgent [3] control
admission to avoid thrashing, and our F6 policy is a
fixed cap of that kind. In contrast to these systems, our
study adds measurements on a static-graph stack: what
work a collapse consists of, what restoring it costs in
the foreground, and how well a model fixed in advance
predicted the result.
7
Conclusion
In the two tested overload conditions, a host tier replaced
repeated planner prefill with KV restoration and recov-
ered most or all offered workflows. Separate endpoint
confirmations supported conservative load gains for chain
and fork, while mixed and burst endpoints remained
seed-sensitive. At common load, the host tier improved
median latency but worsened the fork tail.
A frozen
model anticipated several of these effects, yet it misor-
dered three policy contrasts and overpredicted the benefit
of cheaper stores. The measured trade-off depends on
runtime scheduling and transfer cost as well as cache
capacity.

Model Specification and

A.1
Inputs, Queues, and Completion
The input is the frozen tokenized DAG trace: arrival
offsets, role assignments, dependencies, tool delays, gen-
eration limits and workflow SLOs. Subsequent prompts
are fixed by this trace; generated text does not change
them. The event heap is ordered by time and then a
monotonically increasing insertion counter. Each simula-
tion uses random seed 1701. It first drains 32 warmup
workflows, retains both cache states, and starts measured
arrivals 7.2 s later, which approximates the client’s 6 s
wait and 1.2 s initial telemetry interval.
Workflows enter a FIFO admission queue. B0 has no
client-side workflow or role cap. F6 permits six active
workflows and four in-flight requests per role; excess re-
quests wait FIFO. Both policies use engines with at most
four running requests. Ready nodes are visited in trace
order. Their output lengths are drawn when dependencies
become ready, then a send event is scheduled after the
declared tool delay. A node completion releases its role
slot before making dependent nodes ready. A workflow
completion releases its admission slot. Engine comple-
tions defer these callbacks to same-time events, so they
cannot interrupt a partially processed completion.
The planner and executor have independent busy flags.
A busy engine does nothing when pumped. An idle engine
attempts prefill only for its oldest waiting request, and
only if fewer than four requests are running and cache
allocation succeeds. It does not bypass an unallocatable
head request. If that attempt fails, it decodes the cur-
rent running set. Prefill produces the first output token;
each decode completion adds one token to each member
of the captured batch. Finished requests release their
native allocation. A decode allocation that would require
preemption is reported as an error, as are deadlock and
exceeding a 100,000 s simulation limit.
A.2
Cache State and Publication
Each role has 256 inner blocks of 128 tokens and eight
outer blocks of 4,096 tokens, with maximum model length
8,192 and four sequences.
We execute the preserved
0.10.2 outer-block mapping, search and FIFO eviction
implementation. Unused tensor allocation and logging
imports are stubbed, and the rest of the scheduler is not
executed. The reduced inner model maintains a FIFO
free-ID queue and a directory that can contain duplicate
hashes. Allocation removes old hash entries for reused
IDs and installs complete prompt-block metadata before
local lookup. Lookup selects the preceding duplicate,
then asks the vendor outer manager for usable cached
lengths. Release returns inner IDs in reverse allocation
order. Decode also reserves the vendor dummy block.
These details matter: logical token capacity alone does
not determine a local hit.
Prompt hashes are chained SHA-256 digests of compact
JSON token blocks. Only ⌊(P −1)/128⌋complete blocks
are hashed for a prompt of P tokens; one query token
remains to compute.
Generated-token blocks receive
no reusable hashes.
The model thus ignores content-
dependent reuse after the prompt.

A.4
Event-Loop Pseudocode
The following specifies the reduced engine. Cache alloca-
tion and publication follow the rules above; all times use
the coefficients just defined.
1. Pop the earliest event, breaking ties by insertion number.
Advance time and execute its callback.
2. On workflow arrival, enqueue FIFO. Admit while the
policy’s flow cap allows. For newly ready nodes, draw a
length and schedule send after the tool delay.
3. On send, enqueue at the role cap if necessary; otherwise
append to that engine’s FIFO queue and pump it.
4. Pump: if busy, return.
If a running slot is free, try
allocating the oldest waiting request. On success, move
it to running, compute Hl, Hh, m, R, S, mark busy, and
schedule prefill completion after Dprefill. Return.

5. Otherwise, if requests are running, extend their native
allocations and obtain the dummy block. Capture this

6. Prefill completion: publish missing host keys, set the

7. Release requests that reach their sampled length. Queue

Freezes and Finite-Window Scoring
Common load.
The source, calibration JSON, cache
snapshot, RNG seed, traces, 24 conditions and predictions
were hashed before inference. These cover four families,
three policies and seeds 702/703, each with 1,200 mea-
sured and 32 warmup workflows. Rates are 0.72 for chain,
0.36 for fork and 0.44 for mixed/burst. Per-arm latency
error is (ˆy −y)/y, with frozen absolute tolerance 0.15;
SLO tolerance is 0.05. Policy deltas are scored separately.
No measured held-out length, batch occupancy, cache
hit or completion order enters a prediction. The client
I/O repair preceded measured data and did not change
predictions; its effect relative to the calibration client is
not modeled.
Predicted workflow latency is completion time minus
its scheduled release, including admission wait. P50 and
P99 use linear interpolation between sorted observations.
Completion throughput is the measured workflow count
divided by the interval from the first measured arrival
to the final completion, including drain. SLO counts all
measured workflows. Board energy is outside the model.
Endpoints.
The simulator, cache model and calibra-
tion JSON are byte-identical to those of the common-load
predictor. The screen chooses endpoints; before confir-
mation, both endpoints of all 12 brackets, their traces,
seeds 712/713, 48-run order and predictions are frozen.
Runs have at least 1,200 workflows and 1,800 s of ar-
rivals. Predicted completion records are passed to the
same judge used for measured records. Simulation release
times are reconstructed as completion minus latency, and
every simulated completion is marked successful. This
predicts a finite-window outcome under the model, not a
timeout-aware capacity limit.
For N offered workflows and declared arrival window T,
the judge requires zero request/workflow errors, at least
0.99 SLO attainment in each workflow class, and bounded
backlog and drain. It samples released-minus-finished
workflows at 141 evenly spaced points in [0.2T, 0.9T];
bursts instead use 60-second cycle boundaries in that
interval. Fewer than five samples are inconclusive. With
mq = max(1, ⌊nq/7⌋), it compares the mean of the last
mq backlog samples to the first mq. This growth and
the least-squares slope multiplied by T must each be
at most max(6, 0.01N). Drain after T must be at most
max(20 s, 0.03T). Invalid IDs, clocks or instrumentation
are inconclusive. Missing completions after a measured
hard timeout fail; the model has no such timeout mecha-
nism. Numerical errors use |y −ˆy|/ˆy with tolerance 0.15,
and SLO tolerance 0.05, separately from the pass/fail
call.

Limits.
Mean costs omit rare stalls, request failures,
timeout/abort recovery and preemption. The model does
not simulate tensor arithmetic, transport queues, output-
dependent hashes or scheduling effects from semantic
branching. The same judge cannot restore these missing
mechanisms. We report numerical fit, policy direction
and endpoint classification separately; none of them is a
confidence interval or a proof of stationary stability.
