## Abstract 

Long-context LLM serving for agentic, coding, and document work-loads reuses prefixes whose key-value (KV) cache outgrows GPU and host memory, putting storage I/O on the critical path of the inference step for retrieving prefixes. A single node-local NVMe absorbs all retrievals, while the parallel file system or cloud file store that nodes already mount carries almost no inference traffic. We cast prefix retrieval as aggregate-bandwidth scheduling across these tiers and present KVStream , a KV cache engine that batches a step’s reads, defers writes behind the forward pass, replicates each chunk on every tier, and lets each tier adaptively claim the next unread chunks once it is free. Our performance model shows this routing attains the aggregate-bandwidth bound without prediction or tuning, whereas any static split misses it by a margin that grows as per-tier bandwidths drift or fluctuate. It also predicts that the time-to-first-token (TTFT) gain grows with load, as faster retrieval drains the queue, and disappears when host memory or arrival order keeps reuse in cache. Plugged into LMCache and evaluated on four models, six datasets, and up to 128 GPUs, KVStream re-trieves within 5% of the bound, delivers up to 1.49 × higher offline throughput than LMCache, and lowers mean TTFT by up to 6.1 ×

under bursty arrivals. 

## Keywords 

Large Intermediate States of Transformer Models, Multi-path I/O Concurrency, Hierarchical Memory Management, I/O and Inference Performance Modelling. 

## 1 Introduction 

Large language models (LLMs) now serve long-running agentic, coding, and document-analysis workloads that process tens to hun-dreds of thousands of tokens per request [18, 23, 35, 65]. The at-tention keys and values of every token, the KV cache, must be retained for all later tokens, so the KV cache grows with context length and dominates GPU memory. Requests frequently share long prefixes, such as system prompts, documents, code repositories, and the growing history of multi-turn and agentic sessions. The KV of prefixes are cached for later reuses, avoiding recomputations whose cost grows with model depth and quadratically with prefix length [10, 29, 38, 46, 55]. The set of unique prefixes that will be reused, the working set ,rarely fits on the GPU due to limited capacity. As new prefill and decode tokens need memory for their KV states, the inference engine evicts cached prefixes under policies such as LRU, LFU, or workflow-aware schemes [31, 43, 44, 70]. KV cache connectors such as LMCache and Mooncake [10, 46] extend GPU capacity to slower but large memory and storage tiers, from which the prefix KVs are retrieved when later requests reuse them. Therefore, storage-backed prefix caching trades expensive GPU recomputation for I/O, and in this paper we characaterize, model, and accelerate the I/O bounds for faster inferencing. 

Motivation for Storage-Tier Offloading of KV Cache . Realis-tic long-context workloads have working sets (unique KV prefixes) far larger than GPU and host memory. On our testbeds (§ 6.1), four GPUs leave about 140 GB for KV after the model weights. Each node has 512 GB of host DRAM, 1.6–3.2 × its GPU memory, similar to cloud GPU instances such as AWS p4 , p5 , and the new Nvidia-B300-based p6 [2–4]. Figure 1 shows the working sets of three document datasets and two online production traces (detailed in § 6.1). Even though grouped-query attention (GQA) [1] already compacts the KV of every model, the working set of a 14B model (0.5–1 TB) is 3.3–7.2 × the GPU KV budget, and at 110B it reaches ∼2 TB, up to 6.3 × the host-memory KV cache of a node. We observe that the memory footprint of unique KV prefixes grows with model size due to more layers and attention heads. As a consequence, for the same dataset, the 14B model can hold the KV cache of larger number of prefix chunks than the 110B model. We next see in Figure 2, for the LooGLE dataset, that despite disk reads being slow (6.2–13GB/s, Table 2), utilizing LMCache [10] to store and fetch the offloaded prefixes is up to 2.2 × faster then recom-puting on H100 GPUs. This is because recomputation scales with model depth while retrieval scales only with the bytes moved. Fur-thermore, although each dataset’s unique KV amounts to at most a few TBs (Figure 1), serving the entire dataset reads 5–32 TB for 32B and 70B models, as shown in Figure 3. This read amplification is be-cause eviction from the faster tiers (due to staleness) forces prefixes to be read again and again for reuse as the requests arrive in arbi-trary order (from multiple users and concurrent sessions [38]). Limitations of the State of the Art . Existing systems take three directions to acclerate such prefix-reuse heavy workloads, and none systematically charaterizes and remove storage reads from the critical path once the working set (unique KV footprint) spills beyond the GPU and host memory (§ 2). KV cache connectors such as LMCache, Mooncake, and NVIDIA Dynamo’s KV block manager [10, 41, 46] extend the engine’s cache with host memory and storage, but they read each matched chunk of each request in the batch in serial, non-overlapped fashion (detailed in § 3). Compression, token eviction, and selective restoration [32, 36, 69] shrink each prefix by a constant factor, typically at the cost of accu-racy. Modern GQA and MLA-based architecture already perform in-model KV compression, shrinking the KV sizes by 5–8 × compared to standard multi-head attention for our evaluated models outlined in Table 3. Despite this with, as observed in Figure 1, the working set size (Unique KV prefix footprint) still spills beyond the GPU and CPU memory. Therefore, despite newer architectures, supporting large 1M+ context lengths (common for agentic workflows) for mul-tiple concurrent users still requires memory capacity beyond what the GPU and CPU offer. Efforts such as Nvidia GDS [40], Deepseek 3FS [8], IBM storage scale [25], and Mooncake [46], provide GPU-and/or filesystem-vendor specific optimizations, or proposing mem-ory pooling capabilities for distributed KV caching, but do not design or model the I/O bounds of KV retrieval from multiple stor-age tiers on HPC systems. Lastly, KV reuse-aware schedulers such as HotPrefix [34], PEEK [63], Preble [52], and Bidaw [24] hide the storage retrieval overheads by shuffle the order of the requests to hide the storage retrieval overheads, which dishonors the arrival and/or priority order, and fails to accelerate if the prefix reuse order is not known apriori, which is typically the case for online serving. 

Key Insight and Contributions . In this work, we leverage the insight the HPC and cloud datacenters are typically connected to fast remote storage such as a parallel file system (PFS) [42] or AWS FSX [5], which can supplement additional storage bandwidth but remains idle during inferencing. To this end, we design KVStream ,which utilizes the I/O bandwidth of multiple storage tiers in par-allel to accelerate prefix KV retrievals during inferences. We take a model-backed approach and cast prefix retrieval over heteroge-neous storage tiers as an aggregate-bandwidth scheduling problem: within an iteration, the fastest that any engine can retrieve the prefixes it needs is set by the combined read bandwidth of the tiers it can read in parallel, the classic bound for dividing work among parallel servers [56]. KVStream approaches this bound with adap-tive multi-path completion-driven routing and lands within 5% of it. Our contributions are: (1) Characterization and gap analysis. On two HPC testbeds, we show that storage-backed prefix retrieval is serialized, dominates step time, leaves the PFS bandwidth idle, and suffers read/write interference and heavy-tailed latency on the local and remote storage devices; and that host memory capacity, arrival order, and arrival rate decide whether it matters and how much (§ 3). (2) Design and implementation of KVStream . We propose four mechanisms: step-level batched retrieval, deferred writes, multi-path replication, and completion-driven meet-in-the-middle routing, in a standalone C++ io_uring engine that plugs into LMCache and transparently serves inference engines such as vLLM and SGLang (§ 4). (3) Performance model of iteration breakdown and I/O bounds. 

We decompose an iteration into retrieval, compute, and write; ap-ply the classic aggregate-bandwidth bound of parallel servers to multi-tier retrieval; derive the penalty that a static split NVMe:PFS pays when the per-tier bandwidths deviate from it. We also ex-plain the queueing delay and TTFT as functions of arrival order, arrival rate, host memory, and input and output lengths. We validate it with kvsim , a trace-driven simulator that we release (§ 5). (4) Evaluation in offline and online serving. With four models (14B–110B), six datasets, and two testbeds at up to 128 GPUs, 

KVStream delivers up to 1.49 × higher offline throughput than LMCache (3.22 × over recomputation); for online real-world traces KVStream lowers mean TTFT by up to 6.1 × under bursty arrivals. We also characterize where KVStream gains little or loses: its speedup over LMCache is 0.98–1.05 × when host mem-ory or the arrival order keeps reuse in cache, and 0.81 × when reuse is sparse (§ 6,§ 7). 

Scope and Limitations of Our Approach . KVStream targets long-context workloads, such as agentic, coding, and document-analysis serving, whose unique prefix KVs spill beyond GPU and host memory and are reused heavily (81–96% of prompt tokens hit a cached prefix in our datasets and traces). For workloads with small working sets, such as short conversations [60], or with sparse reuse, storage leaves the critical path and the benefit of any storage-tier optimization [24, 27, 28, 34, 40, 43, 46, 49], including ours, erodes (§ 5.3 states the conditions). Capacity is rarely the issue on multi-terabyte storage tiers: each tier independently evicts its chunks based on LRU when it nears its configured limit, and an evicted prefix is recomputed or fetched from alternate tier if it is requested again. The extra writes nevertheless cost coordination and bandwidth even when they are deferred off the read path, and when they cannot drain behind the forward pass they slow the iteration. If parallel reads do not recover more than replication costs, KVStream is slower than single-tier offloading: 0.98 × when host memory holds the working set (§ 6.5), and 0.81 × at 4% reuse (§ 6.2). KVStream needs at least two storage tiers to realize its benefit; with one, it reduces to batched retrieval with deferred writes. KVStream coordinates nothing across nodes: each node routes its own reads, so nodes that share the PFS adapt independently (§ 6.6). Cross-node coordination, cross-node KV sharing, and prefill-decode disaggregation are orthogonal, and § 7 discusses how they compose with KVStream .

## 2 Background and Problem Formulation 

KV caching across the memory hierarchy . Inference engines manage the KV cache in fixed-size blocks: vLLM’s PagedAttention allocates it in pages to avoid fragmentation, and SGLang’s RadixAt-tention and vLLM’s automatic prefix caching index cached blocks by their token prefix, so that a new request reuses the longest cached prefix [31, 57, 70]; CacheBlend extends reuse to cached chunks that are not prefixes [66]. FlexGen offloaded KV beyond the GPU for throughput-oriented inference [51]. Today, connectors such as LM-Cache [10] extend the engine’s prefix cache with host memory and storage, as CachedAttention does for multi-turn conversations [15], Mooncake and NVIDIA Dynamo’s KV block manager pool DRAM and SSDs across nodes for disaggregated prefill and decode [41, 46], and characterization studies of production traces and offloading stacks document both the reuse that makes it worthwhile to utilize storage tiers and the I/O that it generates [38, 49, 59]. On a prefix hit, these connectors read each matched chunk from the fastest tier that holds it and serve the requests of a step one after another. 

Reducing and accelerating storage reads . Compression and quantization [36, 53], token eviction [62, 69], and selective or partial restoration [16, 32] shrink a prefix by a constant factor (3.5–4.3 × for CacheGen), sometimes at a cost in accuracy. Architectures already build in much of this saving: GQA leaves 5–8 × fewer KV heads in the models we evaluate, and multi-head latent attention cuts the KV cache of DeepSeek-V2 by 93.3% [1, 11]. Compression shrinks the spill but does not remove it, and it composes with our approach (§ 7). Storage backends make one tier faster: 3FS serves KV from RDMA-attached SSDs [8], GPUDirect Storage and NIXL move KV without host copies [39, 40], py-kvcache and BiDAW drives NVMe with io_uring and preloads the blocks of waiting requests [24, 28], and IBM Storage Scale and Dynamo add shared storage as a further tier [25, 41]. None reads a step’s prefixes from several tiers at once. Reuse-aware schedulers, such as SGLang’s longest-prefix-match (LPM) policy, Preble, BiDAW, and PEEK, run requests that share a prefix while its KV is hot [24, 52, 63, 70], and smarter eviction and promotion keep hot prefixes in the faster tiers [34, 43, 44]. Reordering may work for offline batches running without arrival or scheduling priorities, but online serving must respect arrival order, and better eviction helps only while the working set between reuses is not much larger than memory (detailed in § 5.1). 

The store and retrieve path . A connector such as LMCache splits each request’s KV into chunks of 256 tokens by default and keeps one file per chunk and tensor-parallel rank on storage (Fig-ure 4(c)). Its store path copies newly computed chunks from the GPU to a host buffer and flushes them to storage asynchronously, so that later requests sharing the prefix can reuse them. Its retrieve path runs when the engine schedules the next step. The engine matches each request’s prompt against the cached prefixes; matched chunks resident on the GPU need no transfer, chunks in host memory are copied to the GPU, and chunks only on storage are read into host memory and then copied. The forward pass cannot start on any tensor-parallel rank until all matched chunks of the batch are on its GPU, and the flushes of step 𝑖 overlap the reads of step 𝑖 +1 on the same devices.

## 3 Gap Analysis and Observations 

We characterize storage-backed prefix retrieval in LMCache [10], the state-of-the-art KV connector, on the testbeds and workloads of § 6.1, offline (closed loop, throughput) and online (open-loop arrivals, TTFT). Observations O1–O4 concern how fast retrieval moves bytes; O5 and O6 concern whether storage retrieval matters for a given workload and deployment, and how much. 

O1: Prefix retrieval is serialized request by request . LM-Cache retrieves a step’s prefixes in a strictly sequential, per-request pipeline: for each request, all matched chunks are read from storage into host memory and copied to the GPU before the retrieval of the next request begins. Figure 5 shows an Nsight Systems trace of one step that batches seven requests on a 70B model. The storage reads of each request take 600–1300 ms, the next request waits for them, and the step spends 4.7 s retrieving. NVMe controllers reach peak throughput only at high queue depths, when many I/O operations are in flight simultaneously [20, 64]. Issuing chunks one request at a time and alternating control between disk-to-host and host-to-device transfers, results in two limitations (a) the pipeline keeps the queue shallow and prevents the controller from exploiting its internal parallelism across channels and dies; and (b) it keeps hier-archical interconnects idle, i.e., when host-to-device link is used, the disk-to-host channel remains idle. Because the forward pass waits for the KV of every request, finishing one request early gains nothing; only the arrival of the step’s last chunk matters. 

O2: Prefix retrieval dominates step time . Figure 6 decomposes the processing time of the CPU-only baseline, which keeps KV only in GPU and host memory and recomputes evicted prefixes, and of LMCache, which offloads them to NVMe, for four model sizes, each with a different KV footprint per token (Table 3). Because of the read amplification of Figure 3, retrieval dominates LMCache’s time at every size, accounting for 80–88% of it. Even so, LMCache matches CPU-only at 14B and finishes up to 2.2 × sooner at larger models, where CPU-only, which must recompute every evicted prefix, spends far longer in its again computing and repeatedly storing it. Since retrieval is the major fraction of the total serving time, accelerating it speeds up inferences. O3: Second-tier bandwidth sits idle while the local device suffers read/write interference . To measure the bandwidth avail-able to KV offloading, we run an io_uring MPI microbenchmark that mirrors the inference pattern: four ranks, matching the tensor-parallel degree, issue O_DIRECT chunk reads and writes, one file per chunk, in isolation and concurrently (Figure 7). Two observa-tions follow. First, in isolation the node-local NVMe reads only 2.2 × (Testbed-1) and 3.2 × (Testbed-2) faster than the PFS, which is shared by all compute nodes. Yet during inference the PFS carries no traffic beyond model loading, so its bandwidth is available for free. On cloud providers, fast storage tiers such as AWS FSx [5] support tens of GB/s of throughput cheaper than GPUs, making inferences both faster and cheaper than using more GPUs for re-computations. Second, when one device serves reads and writes together, as interleaved retrieval and flushing force it to, the two interfere: 1 TB of concurrent reads and writes (512 GB each) takes 6% longer on Testbed-1 and 27% longer on Testbed-2 than running them in isolation. The read bandwidth a device delivers during inference therefore depends on what else it is doing, and a division of reads across devices computed from their isolated bandwidths is mis-sized for the concurrency in which inference runs. 

O4: Per-chunk latency is heavy-tailed and per-tier band-width fluctuates . Even a well-chosen division of reads meets un-stable per-chunk latency, especially on the shared PFS. On Testbed-2 with four ranks (Figure 8), isolated NVMe reads have a p50 of 123 ms and a p99 of 216 ms; under concurrent reads and writes the p99 reaches 898 ms, 7.3 × the isolated median, and PFS reads show a p99 of 795 ms against a 102 ms median. The tails have different origins: write amplification and garbage collection on the NVMe [20, 64], and cluster-wide contention on the PFS (Figure 4(a)) [17, 68]. To-gether with the tensor-parallel ranks that contend for reads and writes on the NVMe, they make the chunk retrieval latency and bandwidth fluctuate across different inference steps, making static split of prefixes across storage tiers suboptimal (detailed in § 5). 

O5: Host memory relative to the working set decides whether storage is on the critical path . Whether storage reads happen at all depends on how much KV is touched between two uses of a prefix compared with how much host memory holds. Figure 9 varies host memory per rank while the 32B model serves two online production traces (§ 6.1): Qwen-Coder and Chutes at their medium arrival rates (50% of times vLLM’s scheduling queue was idle, and requests didn’t have to wait, detailed in § 6.1). On Qwen-Coder, with sessions interleaved round-robin, the KV touched between reuses far exceeds host memory: doubling it from 40 to 80 GB per rank changes the storage read volume by less than 1% (1428.3 to 1428.2 GB per rank), and LMCache’s mean TTFT stays between 0.76 and 0.90 s. On Chutes, the same doubling brings almost every reuse within memory: storage reads fall by 98.6% (1412 to 20 GB per rank), and LMCache’s mean TTFT falls 3.5 ×, from 8.13 to 2.32 s. This analysis demonstrates two sub-observations: (a) when the working set between reuses is large (beyond host memory capacity), and only faster storage retrieval can; and (b) When it fits in the faster tiers, storage leaves the critical path, and no storage-side optimization (e.g., BiDAW [24], 3FS [8], PyKVCache [28], etc.), ours included, can accelerate the workload. Appendix A.3 adds KVStream to this sweep (Figure 35). 

O6: Arrival/Scheduling order and arrival rate shape both the demand and the queue . Figure 10 (left) serves the same Qwen-Coder trace with the 32B model at a high arrival rate (2.4 req/s, § 6.1), with the same output lengths and host memory (80 GB per rank), in three arrival orders. In the cache-friendly order of the source trace (similar to BiDAW [24], SGLang’s LPM, PEEK [63], and PyKV-Cache [28]), consecutive turns of a session arrive close together: the median reuse distance, the KV touched between two uses of a chunk, is 13 GB per rank, far below host memory (80 GB/rank), because of which only 291.3 GB (instead of 1692 GB) per rank is read from storage, leading to LMCache’s mean TTFT of 0.42 s. In-terleaving whole sessions at random (representative of real-world multi-session concurrent serving [38]), with turn/request order per-session preserved, raises the median reuse distance to 67 GB and storage reads to 1300 GB per rank, leading to mean TTFT of 1.61 s. And finaly, interleaving them round-robin (giving each concurrent session fair/equal priority) raises it to 278 GB and 1692 GB per rank, leading to 42.8 s mean TTFT. Takeaways . O1–O4 expose losses that a storage engine can recover: retrieval is serialized per request (O1) and dominates the step (O2), the PFS bandwidth sits idle while the local device suffers read/write interference (O3), and per-tier bandwidth fluctuates with heavy tails (O4). O5 and O6 lie outside any storage engine’s control: host memory, arrival/scheduling order, and arrival rate decide how much of the working set reaches storage and how many requests wait behind each read, and therefore how much a faster storage read path can speed up the inference. 

## 4 KVStream System Design and Implementation 

KVStream minimizes the retrieval term 𝑇 ret  

> 𝑖

that dominates each step (O2) under three design goals: it serves batches in the order the engine schedules them, without reordering requests to suit its cache; it predicts nothing about future demand or bandwidth; and it needs no tuning at run time. Four I/O mechanisms address the gaps of § 3: M1 pools a step’s storage reads (O1), M2 keeps writes off the devices while a step reads (O3), M3 replicates every chunk on every tier to use the idle PFS (O2, O3), and M4 routes each read by completion rather than by a fixed split (O4). 

## 4.1 KVStream ’s I/O Mechanisms 

M1: Parallel, batched prefix retrieval . A forward pass batches many requests to keep the GPU busy and cannot begin until the prefixes of all of them are on the GPU. KVStream therefore treats a step’s storage reads as one pool rather than as a sequence of per-request pipelines (O1). It classifies the matched chunks of all re-quests by where they reside, submits every storage-resident chunk into one parallel I/O queue, and drains it with a single completion loop. Pooling is what makes the remaining mechanisms possible: the pool can be divided among tiers, and a tier that finishes early can take more of it. Pooling also simplifies I/O management in three ways. Buffers are allocated in bulk, removing the per-request block-management and scheduling overhead that a one-at-a-time pipeline pays repeatedly. One completion-drain loop serves all requests, so reads finish in any order without per-request synchronization. And host-to-device transfers pipeline naturally: each chunk ships to the GPU as soon as it arrives, overlapping the PCIe transfer with the remaining storage reads instead of alternating between the two. 

M2: Deferred writes . The KV generated in a step must be per-sisted for future reuse. Under tensor parallelism, all ranks finish together and flush their KV at once, competing for write bandwidth. Meanwhile, the next step needs a different set of prefixes read back, and those reads are on the critical path. Letting the writes run against these reads delays retrieval, and read/write interference amplifies the delay (O3, Figure 4(c)). KVStream prioritizes reads and defers writes: new KV is buffered in host memory and flushed during the following forward pass, when the devices are otherwise idle for reads. A retrieval is always followed by a forward pass that leaves such an idle window, and the window is usually long enough for a step’s writes to drain. Deferral moves writes in time but does not remove them: every chunk is still written, and a flush that outlasts the forward pass overlaps the next step’s reads. § 5.3 states when this happens, and § 6.5 measures how often. 

M3: Multi-path replication . When requests arrive in an order the server does not control, which chunks a step will need cannot be predicted, so any placement that commits each chunk to one tier risks loading too much of a step’s demand onto one tier and too little onto another, and the bandwidth each tier will deliver at read time is unknown as well (O4). Rather than guess, KVStream 

writes each chunk to every tier. Storage capacity is plentiful relative to the working set, and because writes are deferred behind the forward pass, the second copy normally stays off the read path; it still consumes write bandwidth, which § 5.3 weighs against the read bandwidth it unlocks. Replication gives the engine full flexibility: any part of any prefix can be read from whichever tier is free, which enables the routing below and lets a step draw on the aggregate, otherwise idle bandwidth of all tiers (O3). The scheme is not specific to NVMe and PFS; any further tier, such as CXL-attached memory or a second NVMe, adds read bandwidth with no placement or migration policy to maintain. 

M4: Completion-driven meet-in-the-middle routing . Repli-cation lets KVStream read any part of any prefix from any tier, which it exploits with a meet-in-the-middle strategy. For two tiers, it reads the beginning of a prefix from the NVMe and the end from the PFS, in batches of 𝑚 chunks, and lets the two directions meet in the middle, as Cake does between loading and recomputing KV [27]. A tier that finishes its batch immediately pulls the next outstanding chunks, so a faster or momentarily less contended tier advances its cursor further and takes on more work. This has four consequences: each tier stays saturated, since neither waits on the other; the sched-uling and polling overhead of reaping many small one-by-one reads is avoided; tail latency is masked, because both tiers rarely stall at once, so the healthy tier absorbs the stragglers of O4; and no bandwidth measurement, prediction, or interleaving schedule is needed, since the engine adapts purely by completion. The cursors need not synchronize at the meeting point: a small overlap re-reads a few chunks into the same host buffer, and because the content is identical, the first arrival makes the chunk GPU-ready while the redundant read completes harmlessly. § 5.2 shows that this routing attains the aggregate-bandwidth bound.

## 4.3 Implementation 

KVStream ’s I/O engine is a standalone C++ library with no CUDA dependency, so it carries over to other GPU architectures. It is-sues asynchronous O_DIRECT reads and writes through Linux’s 

io_uring , with separate rings for reads and writes, so that waiting on one never stalls the other. A nanobind binding exposes it to Python with zero-copy buffers. KVStream plugs into LMCache [10] as a storage backend: the adapter between LMCache and the infer-ence engine calls KVStream ’s batch-level API at the start of each it-eration, during prefix matching. The engine keeps using LMCache’s existing interface, so vLLM [31] and other engines that integrate LMCache get multi-tier retrieval, completion-driven routing, and deferred writes without code changes. In SGLang [70], KVStream 

is a storage backend of the hierarchical cache (HiCache). There it writes synchronously and does not overlap retrieval, because HiCache reuses a host page as soon as a write returns and finishes or abandons a prefetch before it schedules the request.

## 5.3 End-to-End Gains and Losses 

Equations 3–6 concern a single step. However, in real-world deploy-ments serving continuous stream of requests, the effective overall savings or overheads achieved by KVStream (or other storage-tier optimizations) depend on the following. 

Service time . Routing a step’s reads over both tiers instead single tier reduces retrieval from 𝐷 𝑖 /𝑏 0 (𝑖 ) to 𝐷 𝑖 /( 𝑏 0 (𝑖 ) + 𝑏 1 (𝑖 )) , that is, by a fraction 1 −𝜑 (𝑖 ) of the single-tier’s retrieval time. However, since a step’s time 𝑇 𝑖 is composed of both 𝑇 ret and the time for forward pass 

𝑇 fwd (Equation 1), the gain of step 𝑖 is capped by retrieval’s share of the step (Amdahl’s law [7]): large when retrieval dominates, as in O2, and negligible when most matched prefixes come from memory or when long outputs or decodes stretch 𝑇 fwd . In offline serving, the engine is saturated and throughput is inversely proportional to step time, so a closed-loop run measures this capacity gain. 

Queueing . In online serving, a request’s TTFT is its own step time plus the time it waits in the scheduling queue for previous requests to complete. Faster retrieval therefore helps twice: the batch that retrieves finishes sooner, and the queue behind it drains faster, so every waiting request starts sooner. At low load, the TTFT gain is the per-request saving due to faster retrievals, which is small; however, at moderate or higher loads, when baseline approaches experience saturation due to slower storage reads, faster draining of waiting queue with KVStream accumulates the TTFT gains across all batches, accelerating real-time serving.

## 6.4 Attaining the Aggregate-Bandwidth Bound 

In the next series of experiments, we test the two predictions of § 5.2: if completion-driven routing attains the aggregate-bandwidth bound 𝑇 𝑖 (Eq. 3), and if a static split pays the penalty of Equa-tion 6, which grows with the mismatch between its share 𝑔 and the bandwidth share 𝜑 (𝑖 ) (Eq. 4). We use 17 runs of the 32B model on LooGLE on Testbed-2, and for every step, kvsim computes the bound and 𝜑 (𝑖 ) (Eq. 4) from the run’s per-tier byte and time counters. On a quiet file system, four static placements put 60–90% of each prefix’s chunks on the NVMe. A static placement controls where chunks go, not where reads go: host memory serves the initial chunks of many prefix chain which reside on the NVMe, so the NVMe serves a smaller share 𝑔 of the storage demand: 27–74% instead of 60–90% which are stored on it. We first check the model run by run in Figure 20: Equation 5 predicts the gap of every static run within 3%, and KVStream ’s runs sit within 4.3% of the bound. The model thus explains the retrieval time of both policies, so the gap to the bound is a faithful measure of what each policy loses. Next, Figure 21 sweeps the static share 𝑔 on the quiet file system. As Equation 6 predicts, the gap is V-shaped in 𝑔 : it is smallest (8.0%) when 𝑔 matches the mean bandwidth share ( ≈ 0.55), and it grows on either side, up to 67.7%. Even the best static split pays, because 

𝜑 (𝑖 ) moves from step to step on a quiet file system too (O4), and a fixed 𝑔 matches it only on average. KVStream has no share to tune, since completion-driven routing sets its split as reads complete, and it stays at the bound. End to end, KVStream ’s throughput is 4.6% above that of the best static split and 24.8% above that of the worst, so even a well-tuned static split leaves throughput on the table. For next experiments, a co-located fio job adds periodic, bursty, or steady traffic on the PFS, representative of other jobs sharing it. Figure 22 shows that this traffic widens the spread of 𝜑 (𝑖 ) (Eq. 4) and, for steady traffic, shifts its mean from 0.55 to 0.62, away from the static split’s fixed 𝑔 = 0.55. The static gap thus grows with the mean mismatch |𝜑 (𝑖 ) − 𝑔 |, from 8.0% on the quiet file system to 11.8–23.6%, whereas KVStream stays within 4.3% of the bound under every pattern, because completion-driven routing rebalances the tiers at every step without monitoring their bandwidths (§ 4.1, M4). ## 6.5 Demand and Write Cost: Host Memory and Arrival Order 

In the next series of experiments, we test Equation 2, which predicts the storage demand from the reuse distance 𝑑 and the cache capacity 

𝑀 , by varying host memory (40, 60, and 80 GB per rank) on the three online traces. Figure 23 shows that the prediction tracks the measured storage reads across all of them, from 20 to 2410 GB per rank (correlation 0.998). One rule produces three shapes, depending on where the reuse distances lie relative to 𝑀 . On Qwen-Coder, they lie far beyond every memory size (median 278 GB per rank), so reads stay flat at 1428 GB per rank, and only faster retrieval helps. On SWE-bench, most session turns recur beyond the largest memory size, so reads decline only gradually (17% from 40 to 80 GB). On Chutes, the reuse distances straddle the memory sizes, so storage reads drastically reduce– 70 × from 40 to 80 GB. The same rule holds across arrival orders: at the same memory, Qwen-Coder reads 5.8 × more in round-robin order than in its cache-friendly order, and Equation 2 predicts each order within 26%. More host memory therefore takes disk I/O off the critical path only when a workload’s reuse distances straddle it, while long, interleaved sessions keep spilling. Appendix A.3, Figure 35 extends this evaluation. Replication, in contrast, writes every new chunk to both tiers, so its write volume is fixed by the workload (e.g., 1100 GB per rank for Qwen-Coder in every order), while its read benefit scales with the demand above. Figure 24 therefore plots the TTFT speedup against the storage reads relative to the replicated writes. In both workloads, the speedup follows this ratio, as § 5.3 predicts. On Qwen-Coder, moving from the cache-friendly to the random and round-robin orders raises reads from 0.27 to 1.18 and 1.54 of the writes, and the speedup from 1.05 × to 1.95 × and 3.12 × (per order in Appendix A, Figure 36). On Chutes, more host memory lowers reads from 3.6 to 0.05 of the writes, and the speedup falls from 1.71 × to 0.98 ×.Multi-tier replication thus pays when storage reads dominate the replicated writes, the regime of interleaved multi-session serving that respects arrival order, and it stays within 2% of single-tier offloading when the working set fits in host memory. Deferred writes keep most of this write traffic off the read path (§ 4.1, M2). On LooGLE, SWE-bench, and Chutes at 40–60 GB, writes overlap only 10–14% of the NVMe’s read time, because each forward pass is long enough to drain the step’s writes (§ 5.3). Qwen-Coder’s short prompts leave less time, so its writes overlap 28–50% of the NVMe’s read time. Figure 25 shows why order decides whether this cost pays: each tier writes 0.19 GB/s per rank in both orders, whereas reads peak at 1.27 GB/s in round-robin order and at only 0.21 GB/s in the cache-friendly order, where the writes nearly match the reads they serve. Figure 37 follows the round-robin run over time: the writes are exactly replicated, and the PFS serves close to its share of the read bandwidth (Appendix A.3). 

## 6.6 Scaling and Ablations 

In the next series of evaluations, we scale KVStream out with data parallelism (DP) from 4 to 32 Testbed-2 nodes (16 to 128 GPUs) on NarrativeQA, where every replica has its own NVMe but all repli-cas share the PFS, the highest PFS concurrency in our evaluation. 

KVStream keeps a 1.23–1.36 × throughput advantage over LMCache (which operates on local NVMes, running in embarassingly parallel fashion, unaffected by other replicas) at every scale (Figure 26), because each replica adapts to the contention on its own: at any iteration, some replicas read more than 50% of their chunks from the PFS while others read less than 20% (Figure 27), without any coordination across nodes. Tail latency stays stable as well (Fig-ure 28): KVStream ’s p90 step time stays near 2.7 s at every scale, against 4.0 s for LMCache at 4 nodes, and even its p99 at 32 nodes remains 1.4 × below LMCache’s. Offline, batched retrieval (M1) and deferred writes (M2) change throughput by less than 1%, because a single NVMe caps the read bandwidth however its reads and writes are scheduled (O1, O3). Other second tiers . Equation 3 depends only on bandwidth, so any tier on a path independent of the node-local NVMe can serve as the second tier: a managed file system or object store attached to a cloud instance [5, 6], remote NVMe, or CXL-attached memory. The added tier need not be as fast as the first, since completion-driven routing lets a slower tier simply claim fewer chunks. Its write path, however, must keep up with the replicated writes to beat single-tier systems (§ 5.3). 

Many nodes . Each node routes its own reads by completion, so nodes that share the PFS adapt without coordination: a node that finds the PFS congested reads more from its NVMe, which keeps 

KVStream ’s advantage at up to 128 GPUs (§ 6.6). Coordination could still save capacity and writes, for example by keeping one shared PFS copy of a prefix that several nodes reuse (particularly useful when dynamically scaling nodes up/down), which we leave to future work. 

KV compression . Compressing KV by a factor 𝑟 divides both the reused volume and every reuse distance by 𝑟 , so in Equation 2 it acts like 𝑟 times less volume and 𝑟 times more memory: 𝐷 𝑟 =

(𝑉 /𝑟 ) · Pr [𝑑 > 𝑟𝑀 ]. Compression thus removes the demand of workloads whose reuse distances sit near memory capacity, but not the spill of long agentic and coding sessions whose working sets exceed memory by more than 𝑟 : 100 resumable 128K-token sessions of a 70B model still need about 500 GB of KV after 8 ×

compression, more than the 320 GB of host memory our nodes devote to KV. Compression and KVStream therefore compose: the former shrinks what spills from memory, and the latter reads the spill at the aggregate bandwidth of multiple storage tiers. 

Request reordering . Reuse-aware schedulers [24, 52, 63, 70] lower the demand of Equation 2 by moving the serving order to-ward a cache-friendly one, and KVStream lowers the time per byte of whatever demand remains. Where the order is free, as in offline batches, the two compose, although in our cache-friendly order (similar schedule to BiDAW [24]– which lack public implemen-tation) which such reordering approaches use, some KV reaches storage and a second tier adds little (§ 6.5). Where it is not free to shuffle requests, as in online serving under per-request latency objectives or in multi-turn sessions whose turns depend on earlier outputs, the arrivals set the demand, and only the read path can be made faster. 

Disaggregated prefill and decode . Disaggregated serving runs prefill and decode on separate instances and moves KV between them through pooled memory and the network [14, 22, 46, 58, 71]. It changes where KV is produced and consumed, not how a prefix comes back from storage, so KVStream ’s routing extends directly: a prefill step can read from the storage tiers or memory of both the prefill and the decode node as well as from the PFS, adding the bandwidth of each independent path to Equation 3. 

## 8 Conclusions 

Once prefix KV outgrows GPU and host memory, storage bandwidth governs long-context LLM serving, yet the parallel file system or cloud file store that nodes already mount sits idle. We cast prefix retrieval as aggregate-bandwidth scheduling over the the available storage tiers. KVStream batches a step’s reads, defers writes behind the forward pass, replicates every chunk on every tier, and routes each read by completion. Our performance model shows that this attains the aggregate-bandwidth bound for any per-tier bandwidths, whereas any static split loses as the bandwidths drift or fluctuate, and that the end-to-end gain grows with the storage demand left by memory, arrival order, and with the load queued behind each read. In our evaluation on up to 128 GPUs, KVStream retrieves within 5% of the aggregate bandwidth bound, delivers up to 1.49 ×

higher throughput than LMCache for offline/batched workloads, and lowers mean TTFT by up to 6.1 × under bursty arrivals. Future work will reduce the replicated writes and add object stores as bandwidth sources.

## A Additional Experimental Results 

This appendix backs claims of the evaluation, and the body cites each figure where it makes the claim: Appendix A.1 extends § 6.2, Appendix A.2 extends § 6.3, and Appendix A.3 extends § 6.5. Setups follow § 6.1: online runs serve the 32B model on one Testbed-2 node, and offline runs serve LooGLE on one Testbed-1 node, all with TP=4. 

## A.1 Online Serving 

SLO attainment on the production traces . Figure 29 extends Figure 11 to Qwen-Coder and Chutes at the medium and high arrival rates (Chutes with 40 GB of host memory per rank). At the medium rate, the two systems’ curves nearly coincide: on Qwen-Coder, their median TTFTs differ by only 1.14 ×, yet 3.35 × fewer requests miss a 5 s SLO with KVStream . At the high rate, more requests wait behind each retrieval, and KVStream ’s curve lies well above LMCache’s on both traces: the gain concentrates in the queued requests, as § 5.3 predicts. 

Retrieval versus queueing on Chutes . Figure 30 repeats the decomposition of Figure 13 on Chutes. Per request, KVStream re-trieves about 1.3 × faster at every rate, while the gap in requests in flight widens with the rate, so the queue, not the per-request saving, carries the speedup from 1.23 × to 2.01 × (§ 5.3). 

A second serving engine . Figure 31 repeats the SWE-bench comparison of Figure 11 in SGLang and in vLLM, each with three storage backends. As HiCache’s storage backend (§ 4.3), KVStream 

lowers SGLang’s mean TTFT 1.57 × against HiCache’s file backend and 1.22 × against Mooncake, although HiCache makes it write syn-chronously, without the deferred writes of M2. In vLLM, KVStream 

has the lowest mean, p50, and p90 TTFT of the three backends, so the gain carries over to a second engine (MR-B.1). 

## A.2 Offline Throughput 

Where the time goes . Figure 32 adds KVStream to the break-down of Figure 6 (O2) into the retrieve, compute, and store phases of Equation 1. LMCache and KVStream spend nearly the same com-pute and store time at every model size, so the gain lies entirely in retrieval (§ 6.3): at 70B, KVStream serves LooGLE in 25 minutes, against 37 for LMCache and 64 for CPU-only. Replication adds no visible store time offline, because each forward pass is long enough for the deferred writes (M2) to drain. 

Same demand, faster reads . Figure 33 shows which tier serves the matched chunks. LMCache and KVStream serve nearly the same shares from the GPU, host memory, and storage at every model size, so they face the same storage demand 𝐷 (Equation 2), and 

KVStream wins by reading it at the combined bandwidth of both tiers (Equation 3, Figure 18). The storage share grows from about a third at 14B to about 60% at 70B and 110B, the first of the two reasons why the gain grows with model size (§ 6.3). 

Host memory offline . Figure 34 raises host memory, the ca-pacity 𝑀 of Equation 2, from 60 to 100 GB per rank for the 32B model. Storage reads fall from 2,832 to 1,856 GB per rank and every approach speeds up, but LooGLE keeps spilling at every size, so 

KVStream ’s advantage over LMCache stays at 1.37–1.41 ×. Chutes, whose reuse distances straddle host memory, behaves differently (Appendix A.3). 

## A.3 Storage Demand and Write Cost 

Host memory online . Figure 35 adds KVStream to the sweep of Figure 9 (O5), with the measured reads of Figure 23 in brackets. On Chutes, the reads fall from 1412 to 20 GB per rank and the speedup with them, from 1.71 × to 0.98 × (Figure 24): once memory holds the working set, the replicated writes have no reads to offset them (§ 5.3).
