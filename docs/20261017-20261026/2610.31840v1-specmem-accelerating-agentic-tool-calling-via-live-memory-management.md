## 摘要
工具调用智能体大多针对准确性进行优化；然而在部署中，其日益增长的成本在于延迟：每次工具调用都以自回归方式解码。推测解码可在不改变输出的情况下加速，而检索到的历史调用在真实使用中能形成强草稿，因为每个用户的行为往往重复。然而现有系统要么不保留跨会话记忆，要么只构建一次草稿存储且从不更新。我们提出 SpecMem，一种在整个部署过程中保持活跃并受管理的工具调用记忆：经校验的调用会在线写回带 LRU 淘汰的有界每用户存储，副作用门控会推迟不可逆调用，直到校验确认。在由三个开放权重模型服务的多会话、多用户查询流上，冻结存储的接受率会持续下降，而 SpecMem 能保持：平均接受 token 数存在 27% 差距（各基准上为 +11% 到 +34%，反映存储构建后有多少新工作到来），实际耗时加速最高达 1.74 倍。消融实验将收益几乎完全归因于保持存储活跃；本地每用户作用域不增加接受率，但封堵了一条实测的跨用户泄漏通道；而基于声明的副作用而非检索置信度进行门控，才是消除不可逆错误的关键。

## Abstract
Tool-calling agents are mostly optimized for accuracy; in deployment, however, their growing cost is latency: every tool call is decoded autoregressively. Speculative decoding accelerates this without changing the output, and retrieved past calls make strong drafts under real use, where each user's behavior tends to repeat. Yet existing systems keep no cross-session memory, or build the draft store once and never update it. We propose SpecMem, a tool-call memory kept alive and managed throughout deployment: verified calls are written back online into bounded per-user stores with LRU eviction, and a side-effect gate defers irreversible calls until verification confirms. On multi-session, multi-user query streams served by three open-weight models, a frozen store steadily loses acceptance while SpecMem holds it: a 27% gap in mean accepted tokens (+11% to +34% across benchmarks, tracking how much novel work arrives after the store is built) and up to 1.74x wall-clock speedup. Ablations attribute the gain almost entirely to keeping the store live; local per-user scoping adds no acceptance but closes a measured cross-user leakage channel, and gating on declared side effects, rather than on retrieval confidence, is what eliminates irreversible mistakes.

# SPECMEM 论文深度总结

## 一、核心问题与整体含义

- **背景**：LLM 智能体越来越多地通过工具调用来完成任务（API 查询、搜索、操作软件），现有研究主要聚焦“准确性”（选对工具、给对参数），但在实际部署中真正持续增长的成本是**延迟**——每一次工具调用都要自回归逐 token 解码，导致智能体在交互场景中不可用。
- **技术切口**：投机解码（speculative decoding）可以在不改变输出分布的前提下加速，其收益取决于草稿被接受的比例。由于工具调用高度模板化、且每个用户的行为往往重复（查天气、查同一支股票、把昨天的查询换个日期重跑），**从记忆中检索到的历史相似调用是极强的草稿来源**。
- **现有工作的缺口**：
  - 多数智能体投机工作只在任务内上下文里做投机，**不保留跨会话记忆**，用完即弃；
  - 最接近的工作 ToolSpec 虽然用历史调用库做检索草稿并报告 3.5–4.2× 加速，但其存储是**构建一次后冻结**的：不写入、不淘汰、全局共享，且其附录明确把“记忆管理”留给未来工作。
- **核心论点**：真正需要研究的不是“静态存储能否加速”，而是**在长期、多用户、行为漂移的部署中，工具调用记忆应当如何被持续管理**。作者把这一问题形式化为一个“生命周期”问题，包含三个耦合子问题：
  - **lifecycle（生命周期）**：调用跨会话累积，存储必须有界且保持新鲜；
  - **scope（作用域）**：全局共享 vs. 每用户独立，决定“谁的调用能出现在谁的草稿里”；
  - **side effects（副作用）**：工具会作用于真实世界，草稿在验证前执行可能提交不可逆操作。

## 二、方法论

### 2.1 总体框架

SpecMem 是位于投机解码器之后的一套**活的工具调用记忆**，由三部分组成：(1) 把单轮基准扩展为多用户多会话流的构造方法；(2) 带在线写回、有界淘汰、本地作用域的草稿存储；(3) 控制草稿能否在验证前执行的副作用门控。

### 2.2 数据构造：从单轮基准到部署场景

- 把基准任务划分给 U 个模拟用户（用户间任务不相交）；
- 每个用户的任务被重新发行为**有序会话**上的查询；
- 每次重复都对任务的**数值参数做扰动**，因此用户的查询“结构重复但不逐字重复”；
- Session 0 为所有 arm 的冷启动；每个用户有一部分任务**只在后续会话首次出现**，保证 warmup 之后仍有新工作到来；
- 该构造与基准无关、对所有 arm 完全一致，因此不会偏袒任何一方。

### 2.3 检索式草稿

- 每个用户拥有一个以 user id 为键的有序映射，存放 `(embed(query), canonical_call)` 对；
- 草稿时对输入查询做嵌入，按**余弦相似度**取该用户最近邻；若相似度超过阈值 **τ = 0.35**，返回该调用作为草稿并将其提升为最近使用（MRU）；
- **回退链**：用户存储为空或相似度过低（冷启动）→ 回退到由群体历史播种的小型共享存储 → 最后回退到**仅 schema 的骨架**（工具名 + 参数占位符），该骨架的 token 是任何正确调用都必须共享的前缀。

### 2.4 在线写回与有界淘汰

- 每次调用**验证完成后**，SpecMem 把确认后的调用以其查询嵌入为键写入发起用户的存储；
- **写回是无条件的**：无论草稿被接受多少，目标模型都会完整产出输出，而确认后的调用是关于用户当前行为的最新证据；
- 每个用户存储容量上限 **C = 48**（全规模实验），溢出时按 **LRU 淘汰**（LFU 为可替换方案）；
- 由此，“作用域（本地 vs. 全局）”与“生命周期（有界+淘汰）”成为 SpecMem 与冻结全局存储的本质区别变量。

### 2.5 副作用门控

- **问题**：投机执行会在验证完成前运行草稿工具。对只读工具，错误投机只是浪费算力；对 `transfer_funds`、`drop_table` 等有外部可见副作用的工具，则会在验证拒绝之前就**提交了伤害**。
- **关键概念澄清**：相关性质**不是幂等性**——幂等操作仍可能有害（误删文件两次与一次结果相同，但误删本身就是损失），而名义上非幂等的调用在事务或 dry-run 中可能安全。真正要判断的是：**在验证前执行是否会提交不可恢复、外部可见的效应**。
- **实现**：在每个工具声明式 schema 中打上 `safe_to_speculate` 标志（只读/无副作用/可事务缓冲或可补偿者为 true，不可逆副作用者为 false，无论是否幂等）；**schema 级门控**只允许被标记为安全的草稿投机执行，其余仍照常起草与验证，但**执行推迟到验证确认之后**。
- **错误代价度量**：给每个不安全工具赋予严重度 σ(t) ∈ [1,10]（安全工具 σ=0），策略的错误代价定义为所有错误不可逆投机执行上的 Σσ(t)。比较三种策略：朴素执行（执行所有被接受的草稿）、置信度门控（仅当相似度 > τ_c 才执行不安全草稿）、副作用门控。
- **代价**：门控只推迟执行、不影响起草；代价是放弃对不安全草稿的投机执行（包括其中正确的那些）。

| **τ²-bench（live 多轮）** | 全部 278 任务，覆盖 airline / retail / telecom 三域；服务模型作为 agent，**GPT-4.1 作为实时用户模拟器**，状态与目标均为 on-policy；产出 1,753 个决策点，3 个流构造 seed |
| **ToolSpec 的四个基准**（墙钟对比） | API-Bank、ToolAlpaca、BFCL v4、ToolBench（OpenBMB 版），统一走相同的每用户/会话构造（10 任务/用户，12 会话，3 seed） |

### 3.2 服务模型

- **gpt-oss-120b**（MoE，120B 总参、约 5B 激活，MXFP4）为主模型，sglang 服务；
- **gemma-4-31B-it**（30.7B dense）；
- **Nemotron-3-Super-120B**（hybrid-SSM，120B 总参、12B 激活），vLLM 服务；
- 查询嵌入使用 **all-MiniLM-L6-v2**（22M 参数，CPU 运行）。

### 3.3 对比方法（arm）

- **No memory（schema-only 草稿）**：下界；
- **Static datastore（ToolSpec 风格）**：单一全局存储在 warmup 期间填充后冻结，永不写入、永不淘汰；
- **SpecMem（local + live + evict）**：本文方法；
- **消融 arm**：Global live+evict（作为归因对照，非部署候选）、Local live unbounded、Ours；
- **Live token-match 基线**：用 SuffixDecoding 式精确 token 匹配替换嵌入检索，同 footprint；
- **门控策略对比**：naive spec-exec、confidence gate、side-effect gate。

### 3.4 指标

- **MAT（mean accepted tokens）**：草稿与目标输出之间的 token 级最长公共前缀均值；
- **accepted fraction**：目标流中被接受的 token 比例；
- **exact rate**：草稿与目标完全一致的比例；
- 评分前对调用做 canonical 化（键排序），使接受度反映语义一致而非线格式噪声；
- 墙钟加速为**真实外部投机循环 + serving-stack 计时器**测得，取 p50；
- 用配对 bootstrap 给出置信区间。

### 5.1 实验组数概览

- **主实验**：BFCL（3 seed）+ Seal-Tools（3 seed）+ τ²-bench（3 域 × 3 seed），共 3 个数据集族；
- **跨模型复现**：3 个开放权重模型（MoE / dense / hybrid-SSM），完整协议重跑；
- **墙钟实验**：ToolSpec 的 4 个基准 × 3 seed，外加 1→32 并发下的吞吐测量；
- **消融**：4 个 arm（frozen / global-live-evict / local-live-unbounded / ours）在同一目标流上重放，3 seed；

- **门控仿真**：400 次调用流 × 5 seed，14 个不安全工具 + 7 个安全工具，不安全调用注入率 0.45，并按原始计数与三级严重度映射做稳健性检验。

### 5.2 充分性与公平性评估

- **公平性设计较强**：所有 arm 共享同一目标模型、同一嵌入器、同一查询流、同一 harness，目标输出每个查询只解码一次且与 arm 无关，因此 arm 之间只差“检索到的草稿”；
- ToolSpec 在自有 harness 内**按其组件重实现**（置信度门控检索 + schema-aware FSM 代理），并验证重实现与静态代理在墙钟上完全等价（MAT 差 ≤0.04），说明差距不是弱基线造成的；
- 作者**主动声明绝对加速不可跨论文比较**（服务模型、服务栈、外部投机循环的客户端开销、BFCL v4 vs. v2 均不同），只主张表内对照有效——这是很克制的处理；
- **归因严谨**：live global arm 作为“归因对照”把 liveness 与 scope 分离；并额外证明收益不是检索器造成的（token-match 基线也能复现）；
- **局限**：用户与会话是合成的，不是真实日志；τ²-bench 每个任务只生成一条规范轨迹（单 trial）；拒答查询被对称剔除，结论只适用于“模型确实发起工具调用”的子population。

## 六、主要结论与发现

1. **存活性（liveness）几乎独自承担全部接受率收益**：BFCL 上 SpecMem 达 19.96 MAT vs. 冻结存储 15.70（+27% 相对，+4.26 绝对），无记忆基线仅 5.92；配对 bootstrap 给出 +3.73 MAT（95% CI [3.37, 4.10]），每个用户、每个会话均为正，仅 5.8% 的重复任务为负。
2. **冻结存储随时间退化，活存储保持**：Session 1 两者几乎持平（约 21 MAT），此后冻结存储跌入 13.5–14.9 区间，SpecMem 稳定在 18.9–21.5，到最终会话差距扩大到 **+46%**；τ²-bench 上冻结存储从约 31 MAT 退到 20–25 带，SpecMem 保持 27–32，优势从约 1% 增至峰值约 37%。
3. **差距随“冻结后新工作比例”缩放**：
