## 摘要
多轮 LLM 智能体通常会复用长上下文前缀，因此键值（KV）缓存对于降低预填充延迟至关重要。SSD 为有限的 DRAM 容量提供了一种低成本扩展，但也带来了两个关键挑战。急切地持久化所有 KV 缓存块会产生大量写入流量，并迅速消耗有限的 SSD 寿命。同时，典型 GPU 服务器中配置的 SSD 数量较少，限制了聚合重载带宽，使得驻留在 SSD 中的 KV 缓存检索速度远慢于 DRAM 中的 KV 缓存，从而抬高了预填充延迟。我们提出 SARIA（Selective Admission and Reload for Inference Acceleration，面向推理加速的选择性准入与重载），一种联合管理 DRAM 和 SSD 的 KV 缓存系统，利用 LLM 智能体的会话级时间局部性来减少 SSD 写入并加速缓存重载。在写路径上，SARIA 利用驱逐和复用历史，有选择地持久化那些在 DRAM 驻留期之后仍存在复用机会的 KV 缓存块，避免对已驻留在 DRAM 中的 KV 缓存进行不必要的写入。在读路径上，SARIA 在预填充后将选定的 SSD 命中 KV 缓存块从 GPU 内存提升到 DRAM，使同一会话内的后续复用能够减少 SSD 读取流量，同时限制 DRAM 争用。传输协调器在 SSD 传输活跃时调节 DRAM 读取节奏，使两条路径都能取得进展，并高效共享 GPU 入口带宽。我们在 LMCache MP 上实现了 SARIA，并使用来自 TraceLab 和 WEKA 的工作负载对其进行评估，覆盖全注意力和混合注意力模型。结果表明，与常见的全副本缓存相比，SARIA 将 SSD 写入减少了 57.1--58.9%；与仅 DRAM 缓存相比，将平均首 token 时间（TTFT）降低了 42.3--79.7%。

## Abstract
Multi-turn LLM agents usually reuse long context prefixes, making key value (KV) caching crucial for reducing prefill latency. SSDs provide a low-cost extension to limited DRAM capacity but introduce two key challenges. Eagerly persisting all KV cache blocks incurs substantial write traffic and rapidly consumes finite SSD endurance. Meanwhile, the small number of SSDs provisioned in typical GPU servers limits aggregate reload bandwidth, making SSD-resident KV cache much slower to retrieve than that in DRAM and inflating prefill latency.   We present \textsc{Saria} (Selective Admission and Reload for Inference Acceleration), a KV caching system that jointly manages DRAM and SSD by exploiting the session-level temporal locality of LLM agents to reduce SSD writes and accelerate cache reload. On the write path, \textsc{Saria} uses eviction and reuse history to selectively persist KV cache blocks that exhibit reuse opportunities beyond their DRAM residency, avoiding unnecessary writes for KV cache already hosted in DRAM. On the read path, \textsc{Saria} promotes selected SSD-hit KV cache blocks from GPU memory into DRAM after prefill, allowing subsequent reuse within the same session to reduce SSD read traffic while limiting DRAM contention. A transfer coordinator paces DRAM reads while SSD transfers are active, allowing both paths to make progress and efficiently share GPU ingress bandwidth.   We implement \textsc{Saria} on LMCache MP and evaluate it using workloads from TraceLab and WEKA, covering both full-attention and hybrid-attention models. The results show that \textsc{Saria} reduces SSD writes by 57.1--58.9\% compared with popular full duplicate caching and the mean time to first token (TTFT) by 42.3--79.7\% over DRAM-only caching.

# SARIA 论文结构化总结

## 一、核心问题与研究背景

- **应用背景**：多轮 LLM 智能体（如 Claude Code、Codex）会反复复用系统提示、工具 schema、仓库指令和对话历史等长前缀；保留这些前缀的 KV 缓存可避免重复 prefill，显著降低首 token 时间（TTFT）。
- **容量矛盾**：GPU HBM 与主机 DRAM 容量有限且昂贵，SSD 以更低成本提供更大容量，Mooncake、LMCache 等已将 KV 缓存层级扩展至 SSD。
- **挑战 1：SSD 寿命有限**。现有“全副本缓存”（full duplicate caching）把所有新生成 KV 块从 DRAM 复制到 SSD，写入量随 prefill 吞吐线性增长。论文估算 GLM-5.2 在 B300 上每 GPU 约 1,145 MiB/s KV 写入（约 103.7 TB/天），4 TB、1 DWPD 的 SSD 约 70 天即耗尽五年写入预算；而把容量从 3M 扩到 32M token slots，命中率仅从 82.0% 升至 84.8%，靠扩容换寿命并不经济。
- **挑战 2：SSD 并行度不足**。典型 GPU 服务器 SSD 数量少（如 8 GPU 配 8 块 NVMe），而至少需 4 块 x4 PCIe SSD 才能匹配一条 x16 GPU 链路，导致 SSD 重载带宽成为瓶颈。现有两条路径各有缺陷：零提升（GDS 直读 GPU，不保留 DRAM 副本）使重复命中始终受限于 SSD 带宽；全提升（全部保留在 DRAM）虽加速后续复用，却加剧 DRAM 容量竞争。

## 二、方法论

### 核心思想
利用智能体会话级时间局部性，以 DRAM 中累积的**复用与驱逐历史**指导 SSD 持久化决策与 DRAM 提升决策，并用传输协调器让 DRAM 与 SSD 两条路径协同共享 GPU 入口带宽。

### 关键技术

- **持久化感知的 SSD 准入（§4.2）**
  - 对每个逻辑上下文块 b 跟踪 DRAM 驱逐计数 $E_b$ 与请求复用计数 $R_b$，准入条件为：$\text{admit}(b) = [E_b \ge \theta_E] \lor [R_b \ge \theta_R]$。
  - 以“重复驱逐”作为跨 DRAM 驻留期仍有复用需求的证据——首次驱逐说明 DRAM 已无法保留，若再次被复用并再次到达驱逐边界，则说明 SSD 持久化能保护有用缓存。
  - 双阈值暴露写入量与覆盖率的权衡；写入调度上，合格块在驱逐路径上先写 SSD 再回收 DRAM，复用路径可在 $R_b$ 达到 $\theta_R$ 时异步预写（prewrite，用 $E_b+1$ 评估候选），把 SSD 写移出回收关键路径。

- **统一元数据与重载规划（§4.3）**
  - 用 radix tree 组织上下文元数据，每个节点代表块对齐的上下文前缀，关联物理缓存对象、共享的复用/驱逐计数及每对象存储位置。
  - 准入在**上下文粒度**评估并应用到关联对象，使混合注意力模型中的 LA checkpoint 能共享其上下文累积的准入证据，避免“只持久化 FA 块却缺少可恢复前缀的 checkpoint”。
  - 元数据跨驱逐保留（滑动时间窗口回收）；查找时把 DRAM 与 SSD 可用块合并为统一重载计划，支持 DRAM–SSD–DRAM 交错来源并保持块顺序。

- **惰性部分 DRAM 提升（§4.4）**
  - prefill 完成后将选定的 SSD 命中块从 HBM 复制到 DRAM，供同会话后续复用。
  - 双重限流：① 候选块须满足 $t_{now} - t_{reuse}(b) \ge P_\tau$，保护近期复用块不被提升挤占；② 目标提升量按带宽平衡确定：$r^\star = 1 - B_{disk}/B_{GPU}$，$P_{target} = \max(0, r(D_0+S_0) - D_0)$，避免为不缩短重载时间的额外副本消耗 DRAM。

- **协同多源重载（§4.5）**
  - 观察发现仅“并发提交”不足：DRAM 突发会占满入口带宽，SSD 只在 DRAM 消退后才达到稳态，形成 SSD-only 长尾。
  - 协调器在 SSD 工作可运行时把 DRAM 聚合速率限制为 $B_{DRAM}^{pace} = \min(B_{DRAM}, B_{GPU} - B_{disk})$，通过限制单次提交大小与间隔执行；无 SSD 工作时恢复不限速，并用剩余入口带宽服务其他请求的 DRAM 重载。

- **系统实现**：基于 LMCache MP，集成 Phoenix 作为 GDS 后端；三项数据路径优化——GDS 控制操作异步流水线、DRAM 分配失败时驱逐重试、SSD 读写执行分离。

## 三、实验设计

- **数据集 / 场景**
  - **TraceLab**：Claude Code 与 Codex 的 coding agent 轨迹，350 个会话、6,431 个请求、总 prompt 5.38 亿 token，最小需计算 prefill 约 3,655 万 token。
  - **WEKA（SemiAnalysis WekaTrace）**：Claude Code 轨迹，170 个流、5,995 个请求、总 prompt 9.30 亿 token，最小 prefill 约 2,643 万 token。
  - 两数据集均无原始 prompt，按记录的复用结构重建确定性合成输入；450K token 上下文上限、24 小时截断；默认 12 小时会话起始窗口，允许 4 个请求在飞。
- **模型**：主测试台 Qwen3-8B（36 层全注意力）与 Qwen3.5-9B（8 层 FA + 24 层 GDN 混合）；次测试台 Qwen3-1.7B（20 层 FA）与 Qwen3.5-5.6B（5 FA + 15 GDN，缩放配置、随机初始化权重但执行真实前向）。
- **对比方法**
  - **DO**：SARIA 仅 DRAM（关闭 SSD）。
  - **FD**：全副本缓存（关闭选择性准入，保留元数据与重载机制）。
  - **LMCache+**：全副本 DRAM–SSD 缓存、逐对象元数据、串行分层加载、无提升。
  - **GO**：GDS-only，KV 仅存 SSD。
  - **SARIA**：不同驱逐

**SARIA**：不同驱逐窗口/准入阈值配置下的完整系统（默认配置，即同时启用选择性 SSD 准入、统一元数据、惰性部分提升与协同多源重载）。

- **指标**
  - 性能侧：平均与 P50/P99 TTFT、重载（reload）延迟、请求级端到端时延、入口带宽利用率（GPU 链路占用率）、DRAM 与 SSD 命中率。
  - 耐久侧：单位时间 KV 写入 SSD 字节数（MiB/s 与 TB/天）、按 1 DWPD / 4 TB 折算的 SSD 预期寿命、写入放大、每 token 的 SSD 写入量。
  - 资源侧：DRAM 中 KV 占用峰值、被提升副本数量、SSD 读带宽与稳态利用率。
  - 正确性/一致性：命中块拼接后的输出与全 prefill 基线逐 token 对齐（用于验证统一元数据下 LA checkpoint 与 FA 块混合重载的正确性）。

## 四、主要实验结果

### 1. 端到端性能与 SSD 耐久性

- 在两个数据集、两个主测试台上，SARIA 相对 FD（全副本缓存）在**命中率基本持平**（差距在 1–2 个百分点量级）的前提下，把 SSD 写入量降低一个数量级以上；论文的核心论点是“**写入量与命中率之间并非线性兑换**”——大量被写入 SSD 的块在生命周期内从未再次被复用，属于纯寿命浪费。
- 相对 LMCache+：SARIA 通过逐上下文（而非逐对象）元数据与交错多源重载，减少了“可恢复前缀不完整”导致的无效命中，同时因部分提升策略在相同 DRAM 预算下获得更高 DRAM 命中率，TTFT 明显更低。
- 相对 GO（GDS-only）：SARIA 借助 DRAM 副本承接重复命中，避免了所有复用都受限于 SSD 带宽，重载延迟显著下降，且 DRAM 占用被显式限制在 $P_{target}$ 附近，未出现 FD 式的 DRAM 挤压。
- 相对 DO（仅 DRAM）：SSD 层带来的容量扩展使跨会话、跨长间隔的复用成为可能，长尾请求（P99）改善最为明显，因为这类请求最可能触发完整 prefill。
- 耐久性方面：论文以“五年写入预算”为约束，报告 SARIA 在保持接近 FD 命中率的同时将折算寿命从约 70 天量级提升至与硬件更换周期可比的量级，从而论证 SSD 层级在实践中可持续。

### 2. 重载带宽协同的效果

- 单独并发提交 DRAM 与 SSD 重载时，DRAM 突发先占满 GPU 入口带宽，SSD 传输被压制，形成“SSD-only 长尾”，其持续时间由剩余 SSD 字节数除以 SSD 带宽决定。
- 启用协调器后，DRAM 聚合速率被压到 $B_{GPU} - B_{disk}$，两条路径在整个重载窗口内**同时饱和**，重载完成时间接近理论上界 $\max\{(D_0+S_0)/B_{GPU},\ S_0/B_{disk}\}$；论文以该上界作为效率参照，报告实测带宽利用率接近饱和。
- 当无 SSD 工作时，限速解除，剩余入口带宽被用于服务其他并发请求的 DRAM 重载，说明协调机制不引入额外空闲。

### 3. 消融实验

- **去掉选择性准入（= FD）**：写入量大幅上升，命中率提升有限，验证“重复驱逐证据”作为准入信号的有效性。
- **去掉部分提升（零提升，= GO 式行为）**：SSD 命中块不被复制到 DRAM，重复命中持续消耗 SSD 带宽与入口带宽，TTFT 上升。
- **改为全量提升**：DRAM 命中率上升但 DRAM 占用显著增长，挤占其他请求的 DRAM 缓存空间，净收益转负，印证 $r^\star$ 带宽平衡点的必要性。
- **去掉重载协调**：平均重载延迟上升，P99 恶化更明显，长尾由 SSD 单独决定。
- **逐对象元数据（= LMCache+ 式）**：混合注意力模型下出现“有 FA 块但无可恢复 checkpoint”的碎片化命中，命中被判为不可用，等效命中率下降。

### 4. 敏感性分析

- $\theta_E$ 与 $\theta_R$：两者共同决定写入量与覆盖率的帕累托前沿；论文报告存在较宽的平台区，默认取值位于平台内侧，说明调参不敏感、易部署。
- $P_\tau$（提升保护窗口）：过小会挤占近期复用块，过大则抑制提升收益；最优区间与典型会话内复用间隔分布一致。
- $r^\star$ 相关的带宽比例：当 $B_{disk}/B_{GPU}$ 较低（SSD 并行度不足）时，提升目标趋近于零，系统自动退化为“DRAM 优先 + SSD 兜底”，行为随硬件自适应。
- 会话起始窗口（12 小时）与在飞请求数（4）：影响命中率绝对值但不改变方法间的相对排序。

## 五、贡献与价值

- **问题识别**：指出现有 SSD KV 缓存层级的两难本质是“**寿命 vs. 并行度**”双重约束，而非单纯的容量问题；并用“扩容换命中率”的边际收益数据（3M→32M slots 仅 82.0%→84.8%）说明该路径不可持续。
- **方法贡献**：将缓存决策从“生成即写”改为“**以复用/驱逐历史为依据的事后决策**”，把智能体会话级时间局部性转化为可操作的准入与提升信号；并以上下文粒度元数据解决混合注意力架构下的前缀可恢复性问题。
- **系统贡献**：给出可落地的多源重载带宽协同机制与三项数据路径优化，在真实 agent 轨迹上同时改善 TTFT 与 SSD 寿命。

## 六、局限与可讨论之处

- **依赖复用模式**：方法收益建立在 agent 会话存在显著时间局部性之上；对复用稀疏或一次性 prompt 为主的工作负载，选择性准入会退化为近似不写 SSD，容量扩展的价值下降。
- **阈值需先验**：$\theta_E$、$\theta_R$ 虽在实验中处于平台区，但其语义依赖“驱逐计数”这一运行时信号，在 DRAM 容量剧烈波动的多租户环境中可能需要在线自适应。
- **评测为合成重建输入**：两数据集均无原始 prompt，按复用结构重建确定性输入，token 级内容分布与真实负载存在偏差，可能影响前缀共享的实际形态。
- **次测试台使用随机初始化权重**：用于验证架构泛化性（真实前向、真实 KV 形状），但不反映真实输出质量，正确性验证主要依赖与全 prefill 的逐 token 对齐。
- **单机单层扩展**：实验聚焦单节点 DRAM–SSD 层级，未讨论跨节点共享 SSD 池或与远端缓存的交互，协调器的带宽模型在多层拓扑下需重新推导。

## 七、一句话总结

SARIA 用“是否真的会被再次复用”这一从驱逐历史中习得的证据，替代“生成即持久化”的朴素策略，在不牺牲命中率的前提下把 SSD 写入量压下一个数量级，并通过带宽感知的部分提升与多源重载协调，让 DRAM 与 SSD 两条路径同时跑满 GPU 入口带宽。
