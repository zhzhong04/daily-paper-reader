# SARIA: Persistence-Aware KV Caching with Coordinated DRAM–SSD Reload for LLM Agents 

Hui Li 1, Qihui Zhou 2, Xiao Yan 3, Shumeng Zhang 4, Zijie Dai 1

Zequn Gong 2, Mingcong Song 2, Guoping Long 2, Hongjie Si 2, James Cheng 11The Chinese University of Hong Kong 2Huawei 3Wuhan University 4Xiamen University 

Abstract 

Multi-turn LLM agents usually reuse long context prefixes, making key value (KV) caching crucial for reducing prefill latency. SSDs provide a low-cost extension to limited DRAM capacity but introduce two key challenges. Eagerly persist-ing all KV cache blocks incurs substantial write traffic and rapidly consumes finite SSD endurance. Meanwhile, the small number of SSDs provisioned in typical GPU servers limits aggregate reload bandwidth, making SSD-resident KV cache much slower to retrieve than that in DRAM and inflating prefill latency. We present S ARIA (Selective Admission and Reload for Inference Acceleration), a KV caching system that jointly manages DRAM and SSD by exploiting the session-level temporal locality of LLM agents to reduce SSD writes and ac-celerate cache reload. On the write path, S ARIA uses eviction and reuse history to selectively persist KV cache blocks that exhibit reuse opportunities beyond their DRAM residency, avoiding unnecessary writes for KV cache already hosted in DRAM. On the read path, S ARIA promotes selected SSD-hit KV cache blocks from GPU memory into DRAM after prefill, allowing subsequent reuse within the same session to reduce SSD read traffic while limiting DRAM contention. A trans-fer coordinator paces DRAM reads while SSD transfers are active, allowing both paths to make progress and efficiently share GPU ingress bandwidth. We implement S ARIA on LMCache MP and evaluate it using workloads from TraceLab and WEKA, covering both full-attention and hybrid-attention models. The results show that S ARIA reduces SSD writes by 57.1–58.9% compared with popular full duplicate caching and the mean time to first token (TTFT) by 42.3–79.7% over DRAM-only caching.

Challenge 1: Finite SSD endurance . SSDs can only sus-tain a finite cumulative write volume before exhausting their rated endurance budget [16]. Existing systems duplicate all 1arXiv:2610.31169v1 [cs.OS] 22 Oct 2026 newly generated KV blocks from DRAM to SSD, which we call full duplicate caching . As such, write traffic scales with the model’s KV footprint and prefill throughput. For exam-ple, vLLM reports 12,963 prefill tokens/s per GPU for GLM-5.2 with 8K-token inputs on B300 GPUs [5]. At this rate, each GPU would generate approximately 1,145 MiB/s of KV writes, or 103.7 TB/day. A 4-TB SSD rated at one drive write per day (DWPD) would consume its five-year write budget in about 70 days of continuous operation. Increasing SSD capacity provides a larger write budget, but the capacity needed for endurance can far exceed that needed for caching. For Figure 1, we replay 350 TraceLab sessions following the setup described in §5.1. Increasing the cache size from 3M token slots to 32M token slots (the capacity required for five-year endurance) only boosts cache hit rate from 82.0% to 84.8%. As such, using larger SSDs is not economical in terms of the performance gain. 

Challenge 2: Limited SSD parallelism . The number of SSDs on GPU servers is usually too small to match GPU ingress bandwidth. For example, AWS’s p5.48xlarge provides 8 H100 GPUs and 8 local NVMe devices [1], whereas at least 4 x4 PCIe SSDs are needed to match one x16 GPU link at the same PCIe generation [18]. Adding more drives consumes bays and PCIe resources and increases cost. With limited device parallelism, SSD bandwidth remains a bottleneck when reloading the cached prefixes. Existing SSD-based KV cache systems adopt two reload paths. The first fetches SSD-resident KV cache directly into GPU memory via GDS [8, 19]. Since this path bypasses DRAM, DRAM copies are not created for SSD hits, a be-havior we refer to as zero promotion . Repeated SSD hits therefore remain bound by SSD bandwidth. The second path loads SSD-resident KV cache into DRAM before transferring it to the GPU [28]. These systems retain all reloaded blocks in DRAM for subsequent reuse, which we refer to as full pro-motion . Although these copies reduce subsequent SSD reads, the promoted KV cache blocks compete with other active sessions for DRAM. 

Our System S ARIA . To tackle the two challenges, we present SARIA (Selective Admission and Reload for Inference Accel-eration), a DRAM–SSD KV caching system for agent work-loads. The central idea is to guide SSD persistence and promo-tion using session reuse history. S ARIA ’s persistence-aware SSD admission preserves KV cache blocks whose reuse ex-tends beyond DRAM residency, while lazy partial DRAM pro-motion and coordinated multi-source reload combine GDS reads with DRAM replicas to accelerate subsequent reloads. Together, they reduce SSD writes and reload latency under limited SSD capacity and parallelism. To account for finite SSD endurance, S ARIA uses repeated DRAM evictions as evidence that a block needs SSD per-sistence. This is because requests within the same session often reuse KV cache blocks while they remain in DRAM, but contention from other active sessions or long inter-request intervals can evict these blocks before they are reused. There-fore, repeatedly evicted KV cache blocks have high potential for reuse after DRAM eviction. We also persist exceptionally popular KV cache blocks (based on their reuse counts) be-fore they are evicted. S ARIA allows users to trade off SSD write volume against cache coverage by configuring eviction and reuse-count thresholds (§4.2). S ARIA further designs uni-fied context metadata to support both classical full-attention models and emerging hybrid-attention models and plans valid prefix reloads from both DRAM and SSD (§4.3). To tackle limited SSD parallelism, S ARIA combines di-rect GDS reloads with lazy partial promotion to accelerate subsequent cache reuse. After a request reloads SSD-hit KV cache into GPU memory through GDS and completes prefill, lazy promotion copies some SSD-hit blocks from HBM into DRAM. We choose a promotion ratio so that DRAM and SSD can fully utilize the GPU’s ingress bandwidth while avoiding DRAM capacity competition. Subsequent requests can then reload different portions of the KV cache from DRAM and SSD concurrently to reduce SSD traffic (§4.4). Loading KV cache concurrently from both DRAM and SSD requires careful coordination for good performance. We observe that DRAM transfers can consume most of the GPU ingress bandwidth and leave a long SSD-only completion tail. As such, S ARIA ’s coordinator paces DRAM transfers while GDS is active and only restores full DRAM bandwidth after SSD transfer finishes. To fully utilize GPU ingress bandwidth, SARIA also uses the residual GPU ingress bandwidth to serve DRAM reloads for other requests (§4.5). We implement S ARIA on LMCache MP and evaluate it us-ing TraceLab and WEKA workloads, covering full-attention and hybrid models and single- and dual-SSD configurations. The results show that the selective admission of S ARIA re-duces SSD write volume by 57.1–58.9% compared with the full duplicate baseline. The mean TTFT is also reduced by 42.3–79.7% over DRAM-only caching. The ablation study shows that partial promotion, tier overlap, and coordination together reduce the cache reload time by 26.7–31.9% for requests in the slowest quartile. 2 Background and Challenges 2.1 Hierarchical KV Caching 

KV caching allows later requests to restore cached prefixes and prefill only unmatched suffixes. CachedAttention [9], Mooncake [22], and LMCache [3] extend the KV cache from GPU memory to host DRAM and SSD. DRAM provides fast reloads, while SSD extends capacity. SSD reloads either stage through DRAM or use direct I/O such as SPIN [2] and GPUDi-rect Storage (GDS) [18]. The GDS paths in FlexKV [8] and Dynamo KVBM [19] reload SSD blocks without retaining DRAM copies ( zero promotion ); HiCache’s DRAM-staged path supports full promotion , retaining all reloaded blocks for subsequent requests [28]. Tutti shows that SSD caching can approach DRAM-backed performance with sufficient SSD parallelism and optimized I/O [23]. Different model architectures impose different require-ments on KV cache access and reuse. Full-attention (FA) KV can be reused at any matched prefix boundary. Hybrid models combining FA with recurrent layers, such as linear attention (LA), also require a checkpoint at that boundary because later states cannot generally be rolled back [11, 20]. Their access patterns therefore differ: FA blocks can serve prefix hits ending at different positions, while a recurrent checkpoint is accessed when computation resumes at its spe-cific boundary.

2.3 Limited SSD Reload Bandwidth 

Approaching the GPU’s PCIe ingress bandwidth with SSD-backed KV reload requires multiple drives operating in par-allel. A typical NVMe SSD uses an x4 PCIe link, while a PCIe-attached GPU typically uses x16. At the same PCIe generation, at least four typical x4 NVMe SSDs must operate in parallel to match one x16 GPU link [18]. Dense GPU servers commonly provide fewer drives than needed to match aggregate GPU ingress bandwidth. 3 Observations and Motivations 

To characterize session-level KV reuse under cache pressure, we analyze the same 350 reconstructed TraceLab sessions used in our evaluation [31, 43], averaging 18.4 requests per session and 83.7K prompt tokens per request. Section 5.1 describes workload construction; Table 2 summarizes the 24-hour replay. To avoid distorting multi-turn arrival patterns by scaling inter-turn times [35], we preserve each session’s request se-quence and inter-request intervals, varying only session start times. We place starts within 12-, 4-, and 2-hour windows, denoted lower, medium, and higher load, respectively. Shorter windows make more active session contexts compete for the same DRAM capacity, raising cache pressure without chang-ing within-session reuse timing. 

3.1 KV Reuse under Cache Pressure 

We observe that requests within an agent session often reuse overlapping context over short intervals. Such temporal local-ity allows DRAM to serve much of the reuse as long as the corresponding KV cache remains resident. We therefore ex-amine how cache pressure affects the role of SSD persistence, focusing on how much reusable KV cache can already be served from DRAM and how often an SSD copy is actually read after being written. To quantify these effects, we simulate full duplicate caching under the three load settings. We model a 100 GB DRAM cache for GLM-5.2 using approximately 2.2 million token slots, based on its FP8 KV footprint. 3.2 DRAM Competition under Full Promotion 

The session-level temporal locality observed above also cre-ates an opportunity on the reload path. After an SSD-resident block is reloaded through GDS, retaining a copy in DRAM can accelerate subsequent reuse by reducing reliance on lim-ited SSD bandwidth. However, promoted replicas consume additional DRAM capacity and compete with the KV cache of active sessions. We therefore examine whether promoting more SSD-hit KV cache always reduces transfer time as cache pressure increases. We compare zero, half, and full promotion under the three load settings, holding the workload and all other cache set-tings fixed within each setting. Transfer times are measured under ideal overlap between DRAM and SSD transfers, with GDS bandwidth set to half the GPU-ingress bandwidth. Half promotion uses a fixed target of 50% DRAM coverage of the currently reused prefix: it creates only enough replicas to reach that target, counting blocks already in DRAM. Figure 4 reports mean request transfer time and the mean times for 4the slowest 10% and 5% of requests, denoted P10 and P5, respectively. Both half and full promotion reduce mean transfer time relative to zero promotion, but full promotion does not con-sistently improve on half promotion. Under lower load, both achieve a mean of approximately 78 ms, with similar P5 times of 226 ms for half promotion and 229 ms for full promotion. The tail gap widens as load increases: under medium load, half promotion reduces P5 from 256 to 244 ms; under higher load, it reduces P10 from 252 to 231 ms and P5 from 310 to 277 ms, while also lowering the mean from 81 to 78 ms. Thus, full promotion retains much of the average benefit but delivers smaller tail improvements at higher load than half promotion. The additional replicas also increase DRAM replacement. In the 2-hour replay, cumulative DRAM block evictions rise from 59,589 with zero promotion to 97,097 with half pro-motion and 175,314 with full promotion. More aggressive promotion therefore creates more replicas but also evicts more resident KV cache blocks, potentially removing reusable blocks before their next access. Together with the transfer-time results, these counts indicate that limiting promotion can alleviate DRAM competition and improve tail transfer performance under cache pressure. 

Observation 2. Session-level temporal locality makes DRAM promotion beneficial, but aggressive promotion intensifies DRAM competition under cache pressure. Reducing the pro-motion ratio can alleviate this competition and improve tail transfer latency. 

4 SARIA 4.1 System Overview 

SARIA manages a hierarchical DRAM–SSD KV cache for serving agent workloads under limited SSD endurance and reload bandwidth. It selectively persists KV cache using reuse and eviction history accumulated in DRAM, and maintains context metadata to apply admission consistently across hy-brid KV types and recover prefixes distributed across storage tiers. When a request reloads SSD-backed KV cache, lazy partial promotion creates selected DRAM replicas for subse-quent reuse, with the promotion volume jointly determined by the reuse recency of DRAM eviction candidates and the DRAM-to-SSD bandwidth ratio. A coordinator schedules the resulting DRAM and GDS transfers to efficiently share GPU ingress bandwidth. Figure 5 illustrates how S ARIA manages KV cache through-out a request’s lifecycle. 4.2 Persistence-Aware SSD Admission 

Every SSD write consumes a finite endurance budget, even if the persisted KV cache is never read from SSD (§2.2). Observation 1 (§3.1) shows that DRAM supplies most cached reuse under normal load and many eagerly persisted copies provide no read benefit: in the reference replay, 82.5% of SSD writes under full duplicate caching receive no subsequent SSD read. This motivates an admission filter that defers SSD persistence while DRAM serves reuse and seeks evidence that retaining the KV cache beyond its DRAM residency would be beneficial. A natural admission signal is request popularity. HiCache, for example, uses access counts to filter HBM-to-DRAM backups [28], but does not make a separate admission decision for SSD endurance. For predominantly session-private agent context, however, these counts largely describe reuse within a session and do not reflect the DRAM competition from other sessions. Increased competition from other active sessions can shorten a block’s DRAM residency even when its own access pattern remains unchanged. 4.3 Unified Metadata and Reload Planning 

Applying admission independently to physical blocks can leave a hybrid model without the KV cache needed to recover a context prefix. Full-attention (FA) KV through a position c

remains useful when later requests extend beyond c, whereas a linear-attention (LA) recurrent state at c is reused as a check-point at that particular boundary [11, 20]. These components can therefore accumulate different access and eviction histo-ries despite representing the same context position. Indepen-dent admission may therefore persist FA blocks without the LA checkpoint needed to reuse that prefix. Selective persis-tence and independent replacement also distribute reusable blocks across DRAM and SSD, producing interleaved sources such as DRAM–SSD–DRAM. Recovery must therefore es-tablish a valid prefix boundary and assign a source to every cache object required at that boundary. SARIA organizes context metadata in a radix tree, follow-ing the prefix organization used in HiCache and Unified Radix Cache [11, 28]. Each node represents a block-aligned context prefix and associates its physical cache objects with shared reuse and eviction counts and per-object storage locations. 4.4 Lazy Partial DRAM Promotion 

Limited SSD parallelism constrains GDS reload bandwidth (§2.3). Observation 2 (§3.2) shows that promotion reduces mean transfer time but increases competition for DRAM ca-pacity. Limiting the promotion ratio can ease this competi-tion and reduce tail transfer latency. S ARIA therefore creates DRAM replicas on demand while limiting their volume. Af-ter a request reloads KV cache from SSD through GDS and completes prefill, S ARIA copies selected SSD-hit blocks from HBM into DRAM (Figure 8). If these replicas remain resident, subsequent requests can reuse them from DRAM instead of repeatedly relying on the bandwidth-limited SSD path. SARIA limits the DRAM competition introduced by promo-tion along two dimensions. First, it avoids displacing recently reused KV cache blocks in DRAM merely to accommodate promoted replicas. The actual promotion volume is fur-ther bounded by the eviction-candidate filter above, allowing SARIA to balance reload bandwidth against current DRAM contention. 

4.5 Coordinated Multi-Source Reload 

The source balance in §4.4 assumes that DRAM and GDS make progress concurrently. However, we find that simply enabling overlap does not ensure concurrent progress. Fig-ure 16 shows that SSD traffic remains low during the initial DRAM burst and reaches its sustained rate only after DRAM traffic subsides. A disk-only completion tail therefore persists despite concurrent submission, leaving GPU ingress underuti-lized. SARIA therefore coordinates the two sources by pacing DRAM traffic while GDS work is active. The coordinator consumes each request’s reload plan from §4.3, tracks its remaining DRAM and SSD work, and shares a per-GPU ingress budget across concurrent traffic. Let BDRAM denote the standalone DRAM reload bandwidth. While SSD work is runnable, S ARIA limits the aggregate DRAM rate to approxi-mately 

Bpace DRAM = min (BDRAM , BGPU − Bdisk ) , (4) reserving sufficient ingress bandwidth for GDS to sustain 

Bdisk . The coordinator enforces this rate by bounding individ-ual DRAM submissions and spacing them according to the 7Req A Req B Req A Req A+B Req C Req C Req B Figure 9: Illustration of multi-source reload with and without transfer coordination. available budget. When no SSD work is runnable, DRAM returns to its unthrottled path. Figure 9 illustrates the coordinated schedule. Once Request A finishes its DRAM portion, residual ingress advances the DRAM-only Request B while A continues reading from SSD. When A’s SSD transfer finishes, B uses the full DRAM rate. Request C overlaps its DRAM and SSD transfers; after its SSD portion completes, its remaining DRAM work also runs at full rate. The coordinator is configured using estimated DRAM, GDS, and GPU-ingress bandwidths. Inaccurate settings can cause bandwidth underutilization or transfer contention, de-grading reload performance. When GDS alone saturates GPU ingress bandwidth, coordination offers no benefit and its over-head may reduce performance.

6 Related Work 

KV cache management. SGLang [42] organizes reusable prefixes with radix trees, while HiCache [28] further uses access counts to filter HBM-to-DRAM backups. Unified Radix Cache [11] extends prefix management to hybrid-attention models, and Marconi [20] introduces checkpoint-aware caching for recurrent states. SAECache [7] uses evic-tion feedback to estimate token reuse value. These techniques improve cache organization and admission within memory hi-erarchies, but do not explicitly address SSD endurance. S ARIA 

instead uses reuse and eviction history across DRAM residen-cies to determine which KV cache blocks warrant persistence on SSD. 

SSD-backed KV caching. Mooncake [17, 22], LMCache [3], and CachedAttention [9] extend KV caching beyond GPU memory using host DRAM and SSDs. HiCache reloads SSD-resident KV cache through DRAM and supports full pro-motion, whereas FlexKV [8] and Dynamo KVBM [19] use GDS to reload SSD hits directly into GPU memory without DRAM promotion. Tutti [23] exploits SSD parallelism and an optimized I/O stack to approach DRAM-backed cache performance. Unified KV Pooling [13] partitions KV cache according to device bandwidth, while HiFC [12] combines GDS with pseudo-SLC regions. Strata [36] and Swarm [33] improve storage I/O scheduling and multi-SSD placement. In contrast, S ARIA targets deployments with limited SSD en-durance and parallelism, using partial DRAM promotion and coordinated mixed-source reloads to reduce dependence on the bandwidth-limited SSD path without excessive DRAM competition. 

SSD Admission and Write Endurance. Flashield [6] re-duces flash writes by admitting general-purpose key–value objects based on their observed reads and updates, while CacheSack [37] and Baleen [34] similarly optimize flash-cache admission. These policies target general storage work-loads rather than the session-level reuse structure of agent serving. S ARIA exploits this structure by distinguishing reuse already covered within a DRAM residency from reuse that ex-tends across DRAM residencies. Repeated eviction and reuse therefore provide an admission signal that reflects both ses-sion reuse and cache competition, complemented by a reuse threshold for highly popular prefixes. 

7 Conclusions 

SSD-backed KV caching faces two practical challenges: ex-cessive writes rapidly consume SSD endurance, while limited SSD parallelism constrains reload bandwidth. We present SARIA , a hierarchical KV caching system that addresses these challenges through Persistence-Aware SSD Admission , which uses reuse and eviction history to avoid unnecessary SSD writes; Lazy Partial DRAM Promotion , which retains selected SSD-hit KV cache blocks in DRAM for subsequent reuse while limiting DRAM competition; and coordinated multi-source reload, which schedules DRAM and GDS transfers to efficiently share GPU ingress bandwidth. Across TraceLab-derived workloads and both full-attention and hybrid-attention models, S ARIA reduces SSD writes by 57.1–58.9% compared with full duplicate caching while reducing mean TTFT by 42.3–79.7% compared with DRAM-only caching.
