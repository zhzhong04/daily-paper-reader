Abstract 

Tool-calling agents are mostly optimized for accuracy; in deployment, however, their grow-ing cost is latency: every tool call is decoded autoregressively. Speculative decoding accel-erates this without changing the output, and re-trieved past calls make strong drafts under real use, where each user’s behavior tends to repeat. Yet existing systems keep no cross-session memory, or build the draft store once and never update it. We propose S PEC MEM , a tool-call memory kept alive and managed throughout de-ployment: verified calls are written back online into bounded per-user stores with LRU eviction, and a side-effect gate defers irreversible calls until verification confirms. On multi-session, multi-user query streams served by three open-weight models, a frozen store steadily loses acceptance while S PEC MEM holds it: a 27% 

gap in mean accepted tokens ( +11% to +34% 

across benchmarks, tracking how much novel work arrives after the store is built) and up to 

1.74 × wall-clock speedup. Ablations attribute the gain almost entirely to keeping the store live; local per-user scoping adds no acceptance but closes a measured cross-user leakage chan-nel, and gating on declared side effects, rather than on retrieval confidence, is what eliminates irreversible mistakes. 

1 Introduction 

LLM agents increasingly act through tool calls: querying APIs, searching, and operating software on a user’s behalf (Qin et al., 2023; Yan et al., 2024). Most work on such agents targets accuracy :choosing the right tool with the right arguments (Li et al., 2023; Tang et al., 2023). In deployment, however, the cost that grows is latency : every call is decoded autoregressively, and an agent that pauses between steps is impractical for interactive use, however accurate it is. This paper is about making tool-calling agents faster without affecting what they output. A growing line of work targets exactly this ef-ficiency. Speculative decoding lets a cheap draft be verified by the target model, so the output is unchanged and the speedup rests on how often the draft is right (Leviathan et al., 2023; Chen et al., 2023). Moving from general decoding to agentic flows, speculation has been applied to the next tool call, its arguments, or the following observation (Sui et al., 2026; Saberi et al., 2026; Hooper et al., 2026; Chung et al., 2026), and to repeated output patterns cached across requests (Oliaro et al., 2025). Tool calls are highly templated, so among draft sources, a similar past call retrieved from memory 

is especially likely to be right. The scenario that matters in practice is tool call-ing under real use: an agent serves many users over a long horizon, and each user’s behavior tends to repeat, asking for the weather, checking the same stock, or re-running yesterday’s query with today’s date. Whether this recurrence can make agentic tool calling faster is the problem we focus on. The closest work is T OOL SPEC (Xia et al., 2026), which retrieves similar past calls from a datastore as drafts and reports large speedups. Its store, however, is built once and then frozen (never updating, never evicting, and shared globally across users), so the recurrence a returning user keeps supplying is never reused (Figure 1). A gap therefore remains between static stores and an agent that stays efficient in this evolving scenario. To close this gap, we propose S PEC MEM , a tool-call memory that is kept alive and managed throughout deployment. Managing such a memory raises three coupled problems. Because calls accu-mulate across sessions, the store must stay bounded yet fresh as the user behavior drifts ( lifecycle ). Be-cause the agent serves many users, retrieval must draw either on one shared global store or on each user’s own history, a choice that decides whose calls can appear in whose drafts ( scope ). 2 Related Work 

Speculative decoding for tool-calling agents. 

Draft-then-verify decoding accelerates inference without changing the output distribution (Leviathan et al., 2023; Chen et al., 2023); drafts can come from self-drafting heads (Cai et al., 2024; Li et al., 2024b,a), parallel decoding (Fu et al., 2024), or, most relevant here, from retrieval : REST veri-fies recurring n-grams from a datastore (He et al., 2024) and S UFFIX DECODING grows an online suf-2fix cache (Oliaro et al., 2025), which we adopt as a live token-match baseline (§5.1); see Xia et al. (2024) for a survey. Retrieval drafting suits agents because tool calls are highly templated and recur-rent (Yao et al., 2022; Schick et al., 2023; Qin et al., 2023; Liu et al., 2024a), the repetition a memory exploits. Closest in spirit, online speculative decod-ing (Liu et al., 2024b) fine-tunes a neural drafter under distribution shift; we ask the same liveness question for retrieval stores, where staying live is a write-back, not a training loop. A concen-trated 2024–2026 wave then speculates over agent actions: the next tool call (Sui et al., 2026), tool ob-servations (Saberi et al., 2026), on-device (Chung et al., 2026), concurrent I/O overlap (Hooper et al., 2026), and forked, beam, and multimodal variants (Bai et al., 2026; Song, 2026; Huang et al., 2026). But none keep a persistent cross-session memory :each speculates from within-task context and dis-cards it. 

The closest prior datastore, and its gap. The closest prior system to ours is T OOL SPEC (Xia et al., 2026), which maintains a historical tool-call datastore retrieved by embedding similarity with a schema-aware FSM and reports 3.5–4.2×

speedups. Its evaluation store, however, is fixed and globally shared, with no online write-back, eviction, or gating of side-effecting tools; its ap-pendix explicitly leaves memory management to future work. S PEC MEM targets exactly this gap, treating the store as a lifecycle and evaluating the cross-session dynamics that a fixed store cannot sustain. 

Agent memory, caching, and tool safety. Agent memory systems keep bounded, updated, user-scoped stores (MemGPT (Packer et al., 2023), MemoryBank (Zhong et al., 2023), Generative Agents (Park et al., 2023), Reflexion (Shinn et al., 2023), A-MEM (Xu et al., 2025), Agent Workflow Memory (Wang et al., 2024)), but for knowledge or skill recall, not speculative drafts; semantic caches like GPTCache (Bang, 2023) evict for response reuse , where a stale hit costs correctness rather than acceptance. On tool-use safety, ToolEmu (Ruan et al., 2023), R-Judge (Yuan et al., 2024), ToolSword (Ye et al., 2024), and GuardAgent (Xi-ang et al., 2024) document that tool-use risk is real and graded , and speculative-execution engines buffer side effects until commit (Nightingale et al., 2005). Yet the systems above uniformly assume tools are safe to execute speculatively (Ghost Tool Calls (Mohammadi et al., 2026) gates privacy , a complementary axis); this motivates our severity-weighted cost of being wrong and the hard gate (§5.2). 

3 Methodology 

Our methodology consists of three components: (1) data construction extending single-shot tool-calling benchmarks into the multi-user, multi-session scenario we target (§3.2); (2) S PEC MEM , a tool-call memory maintained as a managed lifecy-cle behind a speculative decoder (§3.3); and (3) a 

side-effect gate governing when a drafted call may execute before verification (§3.4). 

3.1 Preliminaries 

Speculative decoding lets a cheap source propose a draft that the target model verifies in one forward pass, accepting the longest correct token prefix and re-decoding from the first mismatch (Leviathan et al., 2023; Chen et al., 2023); the output is un-changed, so the speedup depends only on how much of the draft is accepted. In tool calling the draft is a candidate call, and a similar past call re-trieved from a datastore makes a strong one (Xia et al., 2026). Our setting is a deployment in which a fixed served model serves many users over many sessions; the object of study is the datastore: how it is scoped, updated, bounded, and gated as user behavior evolves. 

3.2 Extending benchmarks to the deployment scenario 

Public tool-calling benchmarks are single-shot pools of one-off tasks with no notion of users or time, so we extend them into multi-user, multi-session query streams. Benchmark tasks are parti-tioned across U simulated users; each user’s tasks are then re-issued as queries over ordered sessions, and every recurrence perturbs the task’s numeric argument values, so a user’s queries repeat in struc-ture but not verbatim. Session 0 is a cold start for every arm, and part of each user’s tasks first appear only in later sessions, so novel work keeps arriv-ing after warmup. The construction is benchmark-agnostic (we instantiate it on BFCL and Seal-Tools, §4.1) and identical across arms, so it cannot favor any one of them (synthetic structure: §6). 

3.3 SPEC MEM : live memory management 

Given this scenario, S PEC MEM maintains the draft store as a managed lifecycle rather than a static 3index (Figure 1). 

Retrieval-based drafting. Each user owns a store: an ordered map keyed by user id, holding 

(embed (query ), canonical_call ) pairs from that user’s history. At draft time, S PEC MEM embeds the incoming query and retrieves the user’s nearest entry by cosine similarity; if the similarity clears 

τ =0 .35 , the stored call is returned as the draft and promoted to most recently used. If the user’s store is empty or too dissimilar (the cold-start case), SPEC MEM backs off to a small shared store seeded from population history, and finally to a schema-only skeleton (tool name plus argument placehold-ers), whose tokens any correct call to that schema must share as a prefix. 

Online write-back and bounded eviction. Af-ter every verified call, S PEC MEM inserts the con-firmed call, keyed by its query embedding, into the issuing user’s store. Write-back is unconditional: the target’s output is produced in full regardless of how much of the draft was accepted, and the confirmed call is the freshest evidence of the user’s current behavior. Each user’s store is bounded at capacity C (48 in full-scale runs); on overflow the least recently used entry is evicted (LFU is a drop-in alternative). Store scope (local per-user keying vs. global) and lifecycle (bounded and evicting) are thus the variables that distinguish S PEC MEM from a frozen global store. 

3.4 Gating speculative execution of side-effecting tools 

Speculative execution hides tool latency by run-ning the drafted tool before verification completes. For a read-only tool a wrong speculation wastes work; for a tool with externally visible side effects (transfer_funds , drop_table , . . . ) it commits harm that verification then rejects too late. We emphasize that the relevant property is not idempo-tency: an idempotent operation can still be harm-ful (deleting a file twice yields the same state as deleting it once, but a wrongly drafted deletion is still a loss), and a nominally non-idempotent call can be safe inside a transaction or dry run. The property that matters is whether executing the call before verification can commit an unrecoverable, externally visible effect. We therefore tag each tool with a safe_to_speculate flag as part of its declared schema: true for read-only or side-effect-free calls and for calls whose effects are transac-tionally buffered or compensatable, false for irre-versible side-effecting calls, whether idempotent or not. We then apply a schema-level side-effect gate : only flagged-safe drafts may be speculatively executed; all others are still drafted and verified speculatively, but execution is deferred until ver-ification confirms. Call-dependent cases (e.g. a payment that is safe only when an idempotency key is supplied) need a per-call ternary gate, which strictly dominates the binary flag (§6). 

Cost of being wrong. A raw count treats moving money and sending a duplicate message alike, so we score each unsafe tool with a severity σ(t) ∈

[1 , 10] (σ=0 if safe to speculate). A policy’s cost of being wrong is P σ(t) over its wrong irreversible speculative executions. We compare naive (execute every accepted draft), a confidence gate (execute an unsafe draft only above a similarity threshold 

τc, plausible but insufficient), and our side-effect gate . The gate defers only execution, not drafting: speculation on safe calls is unaffected; the cost is forgoing speculative execution on unsafe drafts, including correct ones (quantified in §5.2). 

4 Experiments 

4.1 Experimental setup Data. We instantiate the construction of §3.2 on the BFCL v4 simple/multiple/parallel pool (Yan et al., 2024). Each of 40 simulated users is as-signed 15 benchmark tasks, disjoint across users. Session 0 (warmup) issues 8 of each user’s tasks once; the remaining 7 first appear spread across sessions 1–11, so novel work keeps arriving after warmup. Each of sessions 1–11 issues 6 queries per user, drawn from the tasks seen so far and weighted toward recently arrived ones, with nu-meric argument values perturbed on every recur-rence. This yields 2,960 queries per seed ( 8,880 

over 3 seeds); queries the model declines are ex-cluded from all arms symmetrically, leaving 6,814 

scored post-warmup queries per arm (full account-ing in Appendix A.1). We use BFCL’s single-turn categories because our accept unit is one drafted call scored against one target call; §5.4 repeats the protocol on Seal-Tools. 

Models. All experiments serve gpt-oss-120b 

(OpenAI, 2025), an open-weight, natively tool-calling mixture-of-experts model ( ∼5B active of 

120 B total parameters), served with sglang on one NVIDIA H200 behind an OpenAI-compatible end-point; query embeddings use all-MiniLM-L6-v2 .4Each unique query is answered once by the served model with greedy decoding. Compute budget, licenses, and package versions are given in Ap-pendix B. We will release the harness, stream gen-erator, and raw result files. 

Baselines. Two draft sources serve as baselines, sharing S PEC MEM ’s target model, embedder, and query stream; we refer to the three compared policies as arms . No memory drafts the schema-only skeleton, the lower bound. Static datastore 

(T OOL SPEC -style) retrieves by cosine similarity from one global store populated during warmup and then frozen (it never ingests and never evicts), matching T OOL SPEC ’s evaluation setting. 

Metrics. The payoff of a draft is its longest com-mon token prefix with what the target would emit (§3.1). We decode the target’s tool-call stream once per query (arm-independent) and score each arm’s draft by token-level LCP, reporting mean accepted tokens (MAT) , the accepted fraction of the target stream, and the exact rate (draft identical to tar-get). Calls are canonicalized (sorted keys) before scoring, so acceptance reflects semantic agreement rather than wire-format noise. MAT is a controlled proxy , distinct from two related measurements: (a) wire-format token acceptance in a deployed de-coder, which additionally depends on a trained drafter’s distribution, tokenization, and acceptance sampling (§6); and (b) the wall-clock speedups of the real external speculative loop in §4.3, reported separately. MAT is always measured against the served model’s greedy output; the arms differ only in the draft they retrieve.

5 Analysis 

5.1 Ablation: attributing the gain 

SPEC MEM differs from the frozen store in three respects: it remains live (continuing to ingest af-ter warmup), it scopes the store locally per user, and it evicts . The aggregate gap alone cannot at-tribute the gain among these factors, so we toggle each independently across four arms replayed on a shared target stream, using the same three stream seeds as the headline run (Table 3). The live global 

arm serves as an attribution control rather than a deployment candidate: it separates liveness from store scope and measures the cross-user leakage of a shared store. 2

The decomposition is stable across all three seeds: keeping the store live accounts for essen-tially the entire gain. A global store that keeps growing and evicting but is shared by all users, at the same total footprint, already reaches 20 .06 

MAT, covering the full gap to the frozen store. Adding per-user partitioning then changes MAT by −0.15 and eviction by −0.05 , both negative in every seed. Nor is the gain an artifact of the

Note that the full configuration is therefore not the acceptance-optimal point: the live global arm is slightly higher ( 20 .06 vs. 19 .91 ). We neverthe-less recommend the local, evicting configuration: a global store serves one user drafts from another user’s history, and local scoping obtains isolation at a cost of only ∼0.15 MAT (quantified below). Although local scoping and eviction do not im-prove acceptance, they are what make a live store deployable. Eviction bounds growth: a capacity sweep shows that the headline capacity of 48 costs only 0.04 –0.05 MAT relative to an unbounded store, and acceptance degrades materially only be-low a capacity of about 32 at this stream’s ∼74 

queries per user. Partitioning provides isolation: re-playing the live global store, we find that 14 –68% 

of drafts served to a user were written by a different 

user (rising with task overlap), a cross-user draft-provenance rate that a deployment keeping users’ histories separate would want at zero (cf. Moham-madi et al., 2026). A per-user store removes this channel by construction, at ∼0 acceptance cost in our disjoint-user regime. Local retrieval adds no acceptance in the headline stream because dis-joint users already route each query to their own calls, so we also constructed the regime where it plausibly could win: users sharing tasks but hold-ing fixed, user-specific argument realizations. Even there the live global store is marginally better (local costs 1.3–7.2% MAT as overlap rises). Embedding retrieval already routes most queries to the right user’s entries, so the case for partitioning rests on isolation, not accuracy. Six further sweeps confirm the picture. With ar-gument perturbation turned off, the frozen store still loses 29% to novel tasks arriving after the freeze. Five randomized data constructions pre-serve the direction, with liveness carrying 100 –

104% of the gap. Session-reset and TTL arms at-tribute about three quarters of the win to genuine cross-session memory. A warmup-budget sweep shrinks the gap to ∼2% once warmup covers ev-ery task, confirming that the decay reflects post-warmup novelty rather than an inadequate warmup. We do not claim that real query streams necessar-ily drift this way; our claim is that a frozen store degrades when post-warmup arrival and recurrence are present. Finally, the decomposition replicates on gemma-4-31B-it , where the live global arm re-covers 4.00 of the 4.04 MAT gap, so the finding holds on both a mixture-of-experts and a dense model. In summary, liveness accounts for the ac-ceptance gain, while local scope and eviction pro-vide isolation and boundedness. 

5.2 Side-effect gating for speculative execution 

We next evaluate speculative execution of tools with irreversible side effects: executing a drafted call before verification completes commits its side effect even if the draft is subsequently rejected, and we quantify this cost under three gating poli-cies. The experiment is reported once: the gate decides from each tool’s declared annotation, not the LLM’s output, so its numbers are model-independent (§5.3). The registry contains 14 side-effecting tools marked unsafe to speculate, span-ning money movement, data loss, security, infras-tructure, and communication, each with an author-assigned ordinal severity σ ∈ [1 , 10] , plus 7 safe tools ( σ=0 ). Naively executing every accepted draft incurs a weighted cost of 800 from 124 wrong irreversible execu-tions. 40 bad actions, including maximum-severity ones. The reason is that retrieval confidence and side-effect safety are orthogonal: a stale draft can re-main highly similar to the query yet be wrong. The side-effect gate’s zero cost, by contrast, holds by construction (refusing to execute unsafe tools triv-ially commits no harm), so the experiment’s value is quantifying the price of that refusal against the harm confidence gating admits: the gate defers the ∼41 correct unsafe drafts per stream to post-verification execution while keeping all ∼214 safe speculations. 5.3 Generalization across served models 

A single target model cannot tell us whether the gap reflects the memory policy or an ar-tifact of gpt-oss-120b . We therefore repeat the identical full-scale protocol (same harness, stream, arms, and seeds) on two additional open-weight, natively tool-calling models, each mea-sured against its own greedy output with its own tokenizer: gemma-4-31B-it , a dense 30 .7B model served with sglang, and Nemotron-3-Super-120B ,a hybrid-SSM model ( 12 B active of 120 B total) served with vLLM. The three models span ven-dor, scale, architecture, quantization, and tool-call serialization format. Per-model gating numbers are not re-measured: the side-effect gate keys off each tool’s declared annotation rather than the LLM that drafted the call, so its numbers are identical across served models by construction. Every model reproduces the same holds-versus-degrades dynamics, with a +27 –29% post-warmup gap and a +45 –48% final-session gap. De-cline rates differ by model ( ∼18% /8% /2% of unique queries for gpt-oss /Nemotron/ gemma ); each model’s declined queries are excluded from its arms symmetrically. Since the gap reproduces within two points across models that share none of these axes, we conclude it is a property of the mem-ory lifecycle rather than of any one target model.

6 Conclusion 

We studied how persistent tool-call memory for speculative agents should be managed in long-lived, multi-user deployments: online write-back sustains acceptance as the stream evolves, local scope and eviction provide isolation and boundedness, and future systems should keep draft stores live and gate speculative execution on declared side effects, not retrieval confidence. 8Limitations 

Simulated repetition structure. Our users and sessions are synthetic: benchmark tasks partitioned across simulated users with numeric-variant per-turbation, not organic logs. The gap’s magni-tude therefore depends on how much users repeat their tools and how much novel work arrives af-ter warmup, a dependence we measure directly (§5.1); its direction is robust across seeds, drift rates, data constructions, and benchmarks. We sur-veyed public candidates for real per-user, multi-session tool-call traces (LMSYS-Chat-1M, Wild-Chat, ToolBench, API-Bank, and the TraceLab agent traces) and none provide per-user session structure together with the query and argument content our accept metric needs; un-redacted multi-session agent telemetry remains the decisive test. 

Metric and integration scope. MAT scores one retrieved draft per query against the served model’s greedy output over canonicalized calls; it omits the multi-turn-selection and irrelevance categories some benchmarks also test, and absolute values are not comparable to trained drafters (Li et al., 2024b). Wall-clock speedups use a faithful external specula-tive loop with real serving-stack timers rather than an engine-integrated hook. The retrieval thresh-old τ =0 .35 and the single embedder are fixed, not swept, and the dynamics are confirmed on three open-weight model families but not on deployed proprietary agents. 

Side-effect gate scope. The gate relies on cor-rect per-tool safe_to_speculate annotations and treats side-effect safety as binary; on call-dependent tools a per-call ternary gate strictly dom-inates and is the natural refinement. Rollback, com-pensating actions, and learned idempotency infer-ence are open directions. 

Ethical Considerations 

Persistent memory and speculative execution for tool-calling agents introduce privacy and opera-tional safety risks. A globally shared memory may expose one user’s interaction history through drafts retrieved for another user, motivating our use of per-user memory partitioning. Incorrect specula-tive execution may also trigger irreversible actions before verification completes; S PEC MEM there-fore defers tools declared unsafe to speculate until verification is complete. These protections still depend on correct tool annotations and should be complemented in deployment by access control, auditing, sandboxing, and human confirmation for high-impact actions. Our experiments use public benchmarks and simulated users rather than real user logs.

A.1 Stream details Query accounting. Session 0 (warmup) issues each user’s 8 warmup tasks exactly once; ses-sions 1–11 issue 6 queries each, so one seed con-tributes 40 ×(8+11 ×6) = 2 ,960 queries and three seeds give 8,880 . Exact repeats and perturbation collisions leave 5,535 unique query strings (BFCL; 

5,088 on Seal-Tools), each answered once by the served model with greedy decoding; no target is fabricated. The model declines a tool call on 982 

unique queries (BFCL; 238 on Seal-Tools); those are excluded from all arms symmetrically, leav-ing n=6 ,814 (BFCL) and n=7 ,592 (Seal-Tools) scored post-warmup queries per arm. Session 0 is a cold start for every arm, so all headline compar-isons are on sessions 1–11. ( exact_rate ≈0 for the no-memory arm is expected: a schema-only draft matches a concrete call only when that call takes no arguments (never on BFCL, 0.7% on Seal-Tools).) 

Arrival schedule. Warmup covers half of each user’s task set ( 8 of 15 tasks, warmup_frac =0.5). Post-warmup sessions draw each user’s queries from their full task set with unwarmed (novel) tasks weighted 3:1 over warmed ones, spreading first appearances across sessions 1–11 (arrival = spread ); burst and late alternatives, and warmup fractions up to 1.0, were additionally swept (stable in direction throughout). The head-line gap should be read at this operating point: as the warmup sweep shows, it shrinks to ∼2% when warmup covers every task. 

Scope of exclusions. Declined queries are removed from all arms symmetrically, so com-parisons are internally valid but conclusions ap-ply to the subpopulation of queries on which the served model issues a tool call at all ( 82% of unique queries for gpt-oss on BFCL, 95% on Seal-Tools). 

τ 2-bench trace generation. For the live τ 2-bench experiments (§5.4), one canonical trace is generated per task and served model (a single trial): the served model acts as the agent against a live GPT-4.1 user simulator, and the 278 tasks yield 

1,753 post-warmup decision points. All memory arms then replay the same trace, so arms differ only in the draft they retrieve; multiple trials would alter the success statistics of the underlying benchmark but not this within-trace acceptance comparison. The seeds reported there are stream-construction seeds for the replay, which reuses cached targets. 

Pool choice. The disjoint-per-user design needs users × tasks = 600 distinct examples, hence 600 

of BFCL’s 800 -task simple/multiple/parallel pool. We restrict to the single-turn categories because our accept unit is one drafted call scored against one target call; BFCL’s multi-turn and irrelevance-detection categories evaluate dialogue-level tool selection, which this protocol does not measure (§6).
