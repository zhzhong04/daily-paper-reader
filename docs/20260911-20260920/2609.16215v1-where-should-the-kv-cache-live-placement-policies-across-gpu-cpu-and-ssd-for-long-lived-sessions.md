## 摘要
GPU 高带宽内存稀缺且昂贵，而随着聊天、智能体循环和文档问答不断累积状态，KV 缓存会消耗其中很大一部分。Mooncake、LMCache、FlexGen、InfiniGen 和 AttentionStore 等系统利用 CPU DRAM 和 SSD 扩展 GPU 内存。更难的问题是：哪些块应属于各层级、何时移动或逐出它们，以及预取是否有帮助。我们在一个涵盖 GPU HBM、CPU DRAM 和 SSD 的离散事件模拟器中研究这些选择，并以随机森林执行时间预测器进行校准。我们在聊天、智能体和文档问答工作负载上比较了最近使用、重用频率、预测重用，以及带预取前瞻的 EWMA 预测器。分层支持每 GPU 并发会话数提高 73.02 倍，并将每会话成本降低 62.04 倍。这些收益来自 1 加 8 加 64 的层级容量，而非放置策略。在我们的设置中，批大小为一时解码是计算受限的，因此放置几乎不影响吞吐量。它主要改变 PCIe 迁移流量和首 token 时间。对于聊天，最近使用产生的迁移流量比重用频率少 2.30 倍。重用频率在智能体和文档问答中表现最佳。现有的预测重用策略与最近使用逐字节完全相同，使其针对智能体的推荐实际上等同于最近使用。真正的 EWMA 预测器会改变行为，但在预测本应帮助的工作负载上仍排名低于重用频率。预取无法证明其带宽成本合理。在策略与缓存大小的网格上，即使拥有未来请求知识的预言机也从未在迁移流量上优于不预取。工作负载特定的放置可以减少数据移动，但预测重用和预取建议按当前实现并不受支持。

## Abstract
GPU high bandwidth memory is scarce and expensive, and KV caches consume much of it as chats, agent loops, and document question answering accumulate state. Systems such as Mooncake, LMCache, FlexGen, InfiniGen, and AttentionStore extend GPU memory with CPU DRAM and SSD. The harder question is which blocks belong in each tier, when to move or evict them, and whether prefetching helps. We study these choices in a discrete event simulator spanning GPU HBM, CPU DRAM, and SSD, calibrated against a random forest execution time predictor. We compare recency, reuse frequency, predicted reuse, and an EWMA predictor with prefetch lookahead across chat, agent, and document question answering workloads. Tiering supports 73.02 times more concurrent sessions per GPU and lowers cost per session by 62.04 times. These gains come from tier capacities of 1 plus 8 plus 64, not placement policy. Decode is compute bound at batch size one in our setup, so placement barely affects throughput. It mainly changes PCIe migration traffic and time to first token. Recency produces 2.30 times less migration traffic than reuse frequency for chat. Reuse frequency performs best for agents and document question answering. The existing predicted reuse policy is byte identical to recency, making its agent recommendation effectively recency. A genuine EWMA predictor changes behavior but still ranks behind reuse frequency on the workloads prediction was expected to help. Prefetching does not justify its bandwidth cost. Across the policy and cache size grid, even an oracle with knowledge of future requests never beats no prefetch on migration traffic. Workload specific placement can reduce data movement, but the predicted reuse and prefetch recommendations are not supported as implemented.

# 论文总结：KV 缓存应该放在哪里？——面向长期存活会话的 GPU、CPU 与 SSD 放置策略

## 1. 核心问题与整体含义（研究动机与背景）

- **核心资源矛盾**：GPU HBM 是 LLM 服务中最稀缺、最昂贵的资源，而 KV cache 是其最大消费者。长聊天、Agent 循环、重复文档问答等长期存活会话会持续累积 KV 状态，并需跨轮保持可达。
- **现有机制已较成熟**：Mooncake、LMCache、FlexGen、InfiniGen、AttentionStore 等系统已将 KV 块扩展到 CPU DRAM 与 SSD，把“恢复会话时重新 prefill”转化为“缓存查找”。
- **真正难点是策略而非机制**：哪些 KV 块应放在哪一层、何时提升/降级/逐出/预取，以及最佳策略如何随工作负载变化，仍缺少系统研究。
- **整体含义**：论文将“放置策略”本身作为研究对象，在 GPU HBM、CPU DRAM、SSD 三层结构上做受控比较，试图给出按工作负载划分的策略指南，并检验“预测重用 + 预取”这类常见建议是否成立。

## 2. 方法论：核心思想、关键技术细节与算法流程

- **核心思想**：构建一个可配置的三层 KV cache 放置层，在离散事件模拟器中比较不同放置、提升、逐出和预取策略，并将模拟器校准到随机森林执行时间预测器。
- **缓存结构**：
  - KV cache 被划分为固定大小的块，沿用 PagedAttention 的 block 粒度。
  - 每个块驻留在 GPU HBM、CPU DRAM 或 SSD 之一。
  - 三层容量满足 \(c_g \ll c_d \ll c_s\)，带宽满足 \(b_g \gg b_d \gg b_s\)。
  - 单层上下文长度 \(T\) 的缓存规模约为 \(2LHdT\) 个标量。
- **放置与迁移算法（Algorithm 1 文字流程）**：
  - 若块已在 HBM，直接使用，记为命中。
  - 若未命中，则从下层逐级向上取回，并提升到 HBM。
  - 若 HBM 已满，将得分最低的 HBM 块降级到 DRAM；DRAM 满时再级联降级到 SSD。
  - 对预测即将使用的块进行预取，提前取到 HBM。
  - 更新块得分，记录命中层级与是否造成解码停顿。
- **策略族**：
  - **近期性 / LRU**：保留最近使用的块在高位。
  - **重用频率**：保留被频繁重新访问的块，偏向共享前缀。
  - **预测重用**：廉价预测下一轮会访问哪些块，思路类似 InfiniGen。
  - **真正 EWMA 预测器**：基于指数加权移动平均的 next-touch 预测，作者额外加入以检验“近期上下文可预测”的前提。
- **预取机制**：使用 lookahead 窗口，把未来解码步或恢复会话所需的块提前搬到 HBM，以重叠传输与计算；lookahead 深度可扫描。
- **成本模型**：
  - 有效容量为 \(c_g + c_d + c_s\)，混合成本由廉价层主导。
  - 代价是未命中时的取回延迟，需要靠策略与预取避免进入解码关键路径。
  - 论文同时报告容量/成本收益与实测停顿，避免把内存节省误认为免费。

## 6. 主要结论与发现

- **机制收益巨大但来自容量，而非策略**：
  - 三层化使每 GPU 并发长会话数提升 **73.02×**，每会话成本降低 **62.04×**。
  - 该倍数基本等于层级容量倍数 \(1+8+64=73\)，跨工作负载和策略近似不变。
- **策略主要影响 PCIe 迁移流量与 TTFT，而非吞吐**：
  - batch size 1 下解码计算受限，吞吐对策略几乎不敏感，聊天约为 1307.60 tok/s。
  - 放置策略实际控制的是迁移字节数和首 token 延迟。
- **按工作负载的策略指南**：
  - **并发聊天**：近期性/LRU 最佳，迁移流量 27.38 GB，比重用频率的 62.99 GB 少 **2.30×**，TTFT 也更好。
  - **单个孤立长聊天**：所有逐出策略逐字节相同，廉价 LRU 默认正确，容量是唯一杠杆。
  - **Agent 与文档问答**：重用频率最佳；Agent 为 49.36 GB，比对照少 **1.60×**；文档问答为 48.23 GB，少 **1.63×**。
- **“预测重用”建议不成立**：
  - 已实现的 predicted-reuse 与 recency/LRU **逐字节完全相同**，因此“Agent 用预测重用”实质就是“用近期性”。
  - 额外加入的真正 EWMA 预测器 `predictive` 在 Agent 上为 53.16 GB，仍输给重用频率的 49.36 GB；在文档问答上为 48.45 GB，与 48.23 GB 接近但未胜；在聊天上明显落后。
  - 预测只在某个狭窄缓存
