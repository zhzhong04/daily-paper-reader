## 摘要
一个智能体请求会花费大量实际时间等待工具，而其 KV 缓存在整个等待期间占用 GPU 显存。服务系统决定该缓存是保留、驱逐还是重新载入，其依据是猜测工具将运行多久——根据工具名称、历史记录、调用前声明的时长，或引擎自身的占用情况。我们表明，任何在调用开始前固定的估计都无法知晓其持续时间，而且这类估计甚至可能无法对调用进行排序。与此同时，正在运行的工具已经握有答案，但智能体栈连同工具却将其沉默。我们提出，工具调用应在运行期间显式报告其进度，并衡量了实现这一点所需的条件。对四个公开智能体语料库的普查发现，一旦进度被揭示，大多数工具时间内都存在可读信号，其强度分为两种：剩余工作量的比例，或表明即将结束的准确信号。一个测试框架在不改变智能体所见内容的情况下恢复该信号，且对智能体的基准分数没有可测量的代价。在做出 KV 缓存决策的时刻，所报告的进度比已发表的最佳预测器准确数倍到高一个数量级，并且在环境变化时仍保持准确。通过少量小型提示接入生产引擎后，与 LRU 相比，它将工具调用后的 p90 首 token 时间（TTFT）降低 20.7%（仅 HBM）和 20.8%（HBM + DRAM），接近预言机水平。服务系统不应去猜工具能够告诉它的东西。

## Abstract
An agentic request spends substantial wall-clock time waiting for tools, and its KV cache holds GPU memory the whole time. Serving systems decide whether that cache stays, leaves, or comes back by guessing how long the tool will run, from the tool's name, its history, a duration declared before the call, or the engine's own occupancy. We show that no estimate fixed before a call starts can know its duration, and such estimates may not even rank the calls. Meanwhile, the running tool already holds the answer, but the agent stack together with the tool silences it. We propose that tool calls report their progress explicitly while they run, and we measure what that takes. A census of four public agent corpora finds a readable signal in most tool time once it is revealed, in two strengths: a fraction of the work remaining, or an accurate signal that the end is near. A harness recovers it without changing what the agent sees, at no measurable cost to the agent's benchmark score. At the points where a KV cache decision is made, the reported progress is between several times and an order of magnitude more accurate than the best published predictors, and it stays accurate when the environment changes. Plugged into a production engine through a few small hints, it cuts the p90 time to first token (TTFT) after a tool call by 20.7% (HBM only) and 20.8% (HBM + DRAM) against LRU, close to an oracle. A serving system should not guess what its tools can tell it.

## 1. 核心问题与整体含义（研究动机与背景）

- **问题背景**：智能体（agent）请求在等待工具（tool）执行时会消耗大量 wall-clock 时间，而其 KV cache 在此期间持续占用 GPU 显存。服务系统必须在工具调用期间决定：该请求的 KV cache 是保留、驱逐，还是稍后重新载入。

- **现有做法的缺陷**：
  - 当前服务系统只能**在调用前猜测**工具时长，依据包括：工具名称、历史调用时长、调用前声明的时长、引擎自身占用率等。
  - 论文指出：**任何在调用开始前固定的估计都无法知晓该调用的真实持续时间**，甚至无法对长调用进行正确排序。
  - 长调用的时长由机器负载、沙箱邻居、远程 API 状态等外部因素决定，这些信息在命令行中完全不可见。
  - 历史数据只有在**与当前运行环境匹配**时才有用，而同时满足“足够大”和“同一负载下采集”的历史几乎不存在。

- **核心洞察**：
  - 等待时间高度集中在少数长调用上（SWE-bench 榜单中不到 3% 的调用占据近三分之二的工具时间）。
  - **正在运行的工具本身已经掌握答案**，但智能体栈（harness + agent）主动将其“沉默”：环境变量关闭进度条、agent 用 `tail`/`-q`/重定向丢弃输出。
  - 数据库领域早有类似结论：不执行查询的估计器误差无界，唯一可靠的进度指标是查询自身已完成的工作量计数。

- **整体含义**：服务系统不应“猜”工具能告诉它的东西；工具调用应在运行中显式、可修订地上报进度，服务系统应读取该信号来指导 KV cache 决策。

## 2. 方法论

### 2.1 核心思想

- 用**工具运行中显式上报的进度流**替代调用前预测的固定时长。
- 进度信号分为两种强度：
  - **强信号**：报告剩余工作量的比例（如已完成 40/66 个文件）。
  - **弱信号**：仅准确报告“即将结束”（如最后一个单元或链接阶段即将开始）。
- 设计原则：**智能体的观测结果不得改变**。结果路径保持原样，进度通过独立的**侧信道（side channel）** 传给服务系统。

### 2.2 三层沉默与破解方式

| 层次 | 沉默来源 | 破解方式 |
|---|---|---|
| 第 1 层 | 基础设施关闭进度条；agent 用 `tail`、`-q`、重定向截断输出 | 重新启用进度条，并从 agent 读取流中剥离；将完整流复制到侧文件；`tail` 仍读到相同末行，文件与退出码不变 |
| 第 2 层 | 工具需要特定开关才输出进度（如 verbose flag），或缺少总数 | 代 agent 询问并保留答案在侧信道；先跑 dry run 获取总数；无法传开关时改从磁盘观察（如目标文件逐个出现） |
| 第 3 层 | agent 自己生成的脚本没有进度输出 | 在生成时让模型加入进度行；对比原始与插桩脚本的输出和退出码，并验证基准分数不变 |

### 2.3 信号分类（五种类型）

- **强信号**（来自四个来源）：
  - **A**：工具自身输出（如 pytest 的百分比列、pip 的包名）。
  - **B**：工具已有开关或 dry run（verbose flag、`--progress-bar raw`）。
  - **C**：工具向宿主暴露的钩子/SDK（最干净但最稀有，样本中未发现使用）。
  - **D**：agent 自己生成的代码，在生成时插入进度行。
- **弱信号**：多阶段构建（`make` 风格）的最后单元标记；下载（如 `pip install`）的最后阶段公告。
- **可忽略**：过短无需进度的调用，可在调用前从命令文本高精度识别。
- **声明时长**：`sleep`、`timeout` 等自带精确或上界时长。
- **不可解析**：长时间远程 API 调用、等待人工反馈的命令。

### 2.4 事件流与包装器设计

- 包装器位于执行器与工具进程之间，原样透传工具字节，侧路产生事件。
- 每个事件统一格式：**call id、已完成工作量、总数（若已知）、阶段、时间戳**。
- 两层事件源：
  1. **输出层**：解析工具打印的计数器、百分比；注册表识别常见工具；通用解析器兜底；shim 让进度条库输出结构化行。
  2. **磁盘层**：读取执行环境中的文件痕迹（如编译产物逐个出现、下载大小、测试收集计数）。
- **可信性处理**：
  - 计数器超过总数时撤回报告，降级为无总数计数，避免误报。
  - 多阶段调用按历史阶段权重折叠为单一分数；权重未知时仅保留最后阶段作为弱信号。
- **扩展路径**：教 agent 使用开关、工具方暴露钩子（如 MCP progress notification）、harness 自动扫描高频工具并添加规则。

### 2.5 服务引擎集成

- 在 vLLM 上增加少量原语（几百行代码）：
  - `refresh`：将驻留块移到驱逐队列安全端（零成本）。
  - `release`：移到队首但保持可寻址。
  - `query`：报告驻留比例。
- 控制器逻辑：
  - 仅 HBM：当报告剩余时间低于 keep 阈值时刷新上下文。
  - HBM + DRAM：增加迟滞，估计值远超阈值后停止刷新；在预测返回前一个 lead time 刷新并预取。
- **信任机制**：进度报告来自租户可控内容，视为不可信输入。每个 session 通过正确报告赚取信用，引擎依据报告行动时消耗信用，报告被证伪时扣费；设置内存保留与延迟风险两个独立账本，无信用时回退到无信号服务。

## 6. 主要结论与发现

- **长调用主导工具时间**：不到 3% 的调用占据近 2/3 工具时间。
- **调用前估计不可靠**：同一命令在空闲沙箱中快一个数量级；争用使多数调用慢数倍；长调用排序在录制环境与空闲环境之间无相关性（Kendall τ ≈ -0.04 至 -0.07）。
- **工具确实持有信号**：应用插桩后，强信号覆盖榜单工具时间的 38%、OpenHands 的 51%、自采的 48%；加入弱信号后升至 66%、59%、72%。
- **精度优势显著**：
  - 调用 50% 处，进度流中位误差约为调用时长的 1/5，最佳历史预测器约 1/3。
  - 调用 90% 处，进度流中位误差 <10%，最佳历史预测器约 80%。
  - 环境变化下进度流保持准确，历史预测器在混合历史下近结束时差一个数量级。
- **端到端收益**：
  - 仅 HBM：p90 TTFT 较 LRU 降低 **20.7%**，吞吐量 +2.2%；oracle 降低 27.7%。
  - HBM + DRAM：p90 TTFT 降低 **20.8%**，DRAM 重载仅 6.0 GiB（LRU 为 31.1 GiB，部分预测器达 77.7 GiB）。
  - 调用越长收益越大：≥10s 的调用平均 TTFT 降低约 34%–35%，≥30s 达 40%。
- **覆盖而非精度是当前瓶颈**：给未覆盖阶段真值可恢复 oracle 收益的 63%，给已覆盖阶段真值仅恢复 17%。
- **说谎影响有限**：信用机制下说谎者多占 6% 内存，双账本追回其中 5%；最坏情况只是失去收益，诚实会话不受影响。
- **Harness 对 agent 无显著代价**：解决任务数、步数、token、工具时间、wall time 均无显著变化。

## 7. 优点

- **问题定义精准**：抓住 agent 服务系统中“工具等待期 KV cache 管理”这一真实痛点，并给出反直觉但有力的论断——预测不如读取。
- **系统化普查**：首次对 agent 工具调用的进度信息进行语料库规模统计，提出“两种强度、五种类型、四个来源”的分类框架。
- **无侵入设计**：严格保证 agent 观测字节不变，通过侧信道传递信号，并用基准分数验证无代价，工程上可落地。
- **端到端验证**：不局限于离线精度，在真实 vLLM + H100 上验证 TTFT 和吞吐收益，并给出 oracle 上界。
- **鲁棒性考量**：覆盖多种负载变化、历史来源、基础模型和内存配置，证明信号不依赖环境。
- **安全性思考**：将工具报告视为不可信输入，设计信用账本机制，兼顾多租户场景下的激励与公平。
- **与数据库领域类比**：将“查询进度估计”的经典结论迁移到 LLM 服务系统，理论视角有深度。

## 8. 不足与局限

- **覆盖边界**：
  - 部分工具调用本身无信息可读：仅在结束时返回的远程 API、等待人工反馈的命令、首字节前卡住的下载。
  - 部分信息无法解析：未见过的输出格式、隐藏单元的构建系统、用自然语言报告的脚本。
- **插桩可能改变工具行为**：开关、dry run、插桩脚本均是对工具运行方式的改变；虽然实测在噪声范围内，但每个新仪器都需重新验证，verbose flag 下行为不同的工具会破坏不变量。
- **实验覆盖偏差**：
  - 部分语料（Terminal-Bench、OTel）依赖重放获取时长，可能与真实生产分布有偏差。
  - 说谎者信用机制仅为**初步模拟**，未在大规模多租户环境中验证。
  - 跨模型实验显示，不同模型抑制输出的程度不同，信号恢复比例从约 1/3 到 1/2 不等，存在模型依赖性。
- **应用限制**：
  - 需要工具方、harness 方、服务引擎三方协同改造；生产部署需处理侧信道敏感性问题（进度流可能泄露租户工作负载结构）。
  - 信用账本中的“谁为误判买单”是策略选择而非技术必然，涉及公平性权衡。
  - 当前引擎补丁仅针对 vLLM，其他引擎需另行适配。
- **精度并非万能**：在负载中途移除的场景下，进度流因速率在负载下习得而短暂高估剩余时间，需窗口化速率缓解。
