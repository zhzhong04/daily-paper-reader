## 摘要
重复的提示前缀在 LLM 服务负载中日益常见，出现在系统提示、模板化检索增强生成流水线、智能体框架和多轮对话中。vLLM 和 TensorRT-LLM 等现代推理运行时提供了跨请求复用已计算 KV 缓存状态的机制，但在当代加速器上，前缀复用何时能实质性提升服务性能、何时其收益受调度、缓存粒度、并发或内存压力限制，仍不清楚。本文提出 PrefixBench-H100，一个可复现的基准测试与测量框架，用于在单块 NVIDIA H100 上刻画前缀复用。PrefixBench-H100 将受控合成轨迹与聊天式、检索式负载相结合，并在匹配的负载条件下评估两种广泛使用的 LLM 服务运行时。该基准变化共享前缀长度、后缀多样性、请求到达模式、并发度、输出长度和缓存配置，同时采集首 token 延迟、token 间延迟、端到端延迟、吞吐量、缓存命中统计、GPU 内存使用以及选定的性能分析轨迹。PrefixBench-H100 的目标不是引入新的缓存算法，而是揭示面向 H100 级 LLM 服务的前缀复用的实际运行边界。该研究识别出前缀复用能显著降低首 token 延迟的情形，以及缓存压力侵蚀这些收益的情形，同时表明缓存有效性本身对并发度和输出长度基本不敏感；剩余的跨运行时差异源于缓存之上，即调度层。

## Abstract
Repeated prompt prefixes are increasingly common in LLM serving workloads, appearing in system prompts, templated retrieval-augmented generation pipelines, agent frameworks, and multi-turn conversations. Modern inference runtimes such as vLLM and TensorRT-LLM provide mechanisms for reusing previously computed KV-cache state across requests, yet it remains unclear when prefix reuse materially improves serving performance on contemporary accelerators and when its benefits are limited by scheduling, cache granularity, concurrency, or memory pressure.   This paper presents PrefixBench-H100, a reproducible benchmark and measurement framework for characterizing prefix reuse on a single NVIDIA H100. PrefixBench-H100 combines controlled synthetic traces with chat-style and retrieval-style workloads, and evaluates two widely used LLM serving runtimes under matched workload conditions. The benchmark varies shared-prefix length, suffix diversity, request arrival pattern, concurrency, output length, and cache configuration, while collecting time-to-first-token, inter-token latency, end-to-end latency, throughput, cache-hit statistics, GPU memory usage, and selected profiling traces.   The goal of PrefixBench-H100 is not to introduce a new caching algorithm, but to expose the practical operating envelope of prefix reuse for H100-class LLM serving. The study identifies the regime where prefix reuse provides substantial first-token latency reductions and the regime where cache pressure erodes them, while showing that cache effectiveness itself is largely insensitive to concurrency and output length; the cross-runtime differences that remain arise above the cache, in the scheduling layer.

# PrefixBench-H100 论文详细总结

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：重复提示前缀在现代 LLM 服务负载中极为普遍，广泛出现于系统提示（system prompt）、模板化 RAG 流水线、Agent 框架以及多轮对话中。vLLM 与 TensorRT-LLM 等推理运行时均提供了跨请求复用已计算 KV 缓存状态的机制（如 vLLM 的 `--enable-prefix-caching`、TensorRT-LLM 的 `KvCacheConfig.enable_block_reuse`）。
- **核心问题**：前缀缓存最早由 PagedAttention 在 A100 时代提出，其前提假设是 KV 显存稀缺。然而在 94 GB HBM3 的 H100 NVL 上，这一假设已发生根本变化。作者要回答的不是"前缀复用是否有效"，而是**当缓存层不再稀缺时，瓶颈转移到了哪里**。
- **整体含义**：论文的核心论点在于——在 H100 NVL 上，只要前缀工作集（working set）能装进 KV 容量，**跨运行时的主要差异已从缓存层迁移到缓存之上的调度层（scheduler）**。这意味着运维者不应再纠结于缓存机制本身，而应关注调度与到达模式。
- **研究定位**：这是一项**测量与刻画（characterization）工作**，而非系统构建或新算法提出，目标是为 H100 级 LLM 服务提供前缀复用的实际运行包络（operating envelope）。

## 2. 方法论：核心思想与关键技术细节

- **核心思想**：通过一个统一的、可复现的基准框架，将 vLLM 与 TensorRT-LLM 置于**完全相同的 OpenAI 兼容负载**下进行黑盒对比，从而将前缀复用的内在收益与运行时实现差异分离开来。
- **硬件/软件隔离**：两个运行时分别安装在独立的 Python 虚拟环境中，避免依赖冲突；均以出厂默认推荐配置运行，不做源码修改。
- **统一负载驱动**：
  - 单一异步 Python 驱动（`load_gen.py`，约 300 行，基于 `aiohttp`），同时驱动两个运行时的 `/v1/completions` 端点。
  - 支持 **burst（一次性全发）** 与 **fixed-rate（固定速率）** 两种到达模式，固定速率下第 i 个请求在 `i/QPS` 时刻释放。
  - 逐请求记录 TTFT（首个非空流式 token）、端到端延迟、输出 token 数与 HTTP 错误。
- **指标采集**：
  - 每单元前后抓取运行时的 `/metrics`（Prometheus 端点），恢复前缀缓存查询、命中、复用 KV 块的增量。
  - vLLM 命中率 = `prefix_cache_hits_total / prefix_cache_queries_total`（块级，因单位相同即为 token 比例）。
  - TensorRT-LLM 命中率 = 累计 `usage.prompt_tokens_details.cached_tokens / 累计 prompt_tokens`。
  - 两者归一化为同一量：**从缓存提供的输入 token 比例**。
- **五轴扫描空间**：前缀长度、后缀多样性、并发度、输出长度、缓存配置。
- **四组主扫描**：
  1. **顺序复用**：并发 1，前缀长度 ∈ {0, 512, 2048, 4096, 8192}，建立 TTFT 上界收益。
  2. **突发并发**：前缀固定 4096，并发 ∈ {1, 4, 8, 16, 32}，每单元 100 请求。
  3. **块大小消融**：TensorRT-LLM 的 `tokens_per_block` ∈ {32, 64, 128}。
  4. **真实 RAG**：固定速率 {1, 4, 8, 16} QPS，模板生成器。
- **受控对比**：reuse-on/reuse-off 对照锚定禁用前缀缓存的绝对成本；容量封顶实验（`num_gpu_blocks_override`、`KvCacheConfig.max_tokens`）隔离 KV 容量这一变量。

## 6. 主要结论与发现

- **复用收益量级**：在 8192-token 共享前缀、并发 1 时，前缀复用带来 **5–6.5× TTFT 降低**（vLLM 6.51×，TensorRT-LLM 5.26×），reuse-off 的 TTFT 随前缀长度近线性增长，reuse-on 则近乎平坦。
- **缓存有效性跨运行时基本一致**：两者在 1024/2048/4096/8192 前缀下分别缓存 65%/78%/87%/92% 的输入，命中率在 32× 并发范围内仅下降 <3 个百分点（约 83–85%），且**对并发度与输出长度基本不敏感**。
- **跨运行时差距来自缓存之上**：vLLM 曲线整体低约 8 ms，但该差距在 pl=0（无共享前缀）时已存在，说明是**每请求固定开销**，而非缓存行为差异。
- **TTFT 领导权随负载翻转（核心发现）**：
  - **突发到达 c=32**：TensorRT-LLM 的 p50 TTFT 比 vLLM 低 **2.4×**（319 ms vs. 759 ms）。
  - **固定速率 16 QPS**：vLLM 的 p95 TTFT 比 TensorRT-LLM 低 **9.2×**（22 ms vs. 203 ms）。
  - 两种到达模式给出两个相反的排名，均归因于调度层而非缓存层。
- **`tokens_per_block` 消融为零结果**：在 TensorRT-LLM PyTorch 后端上，{32, 64, 128} 三档在任意并发下 TTFT 差异 <7 ms，命中率完全一致，文档所述"复用粒度 vs. 内核效率"权衡已不可检测。
- **缓存压力由工作集/容量比主导**：7B/94 GB 下无法打破缓存；换 32B 或封顶 KV 池后，命中率从 68.2% 崩至 3.6%（两运行时完全一致），p50 TTFT 回归 4.6–6.1×，且**两个运行时的命中率在压力下仍保持 1–6 个百分点的同步**。
- **吞吐量故事与 TTFT 相反**：c=32 时 vLLM 达 1444 t/s，TensorRT-LLM 仅 523 t/s（**2.8× 差距**），即最小化 p50 TTFT 的运行时并非吞吐量最优的运行时。
- **能耗收益**：复用使平均功耗下降 9–10%，结合 5–6× 墙钟时间缩短，每请求能耗节省 **24%（TRT-LLM）到 31%（vLLM）**。
- **跨模型泛化**：Mistral-7B 上复现了突发场景的领导权翻转（2.1×，vs. Qwen2 的 2.4×），命中率在 c=1 时精确一致（85%），说明结论是运行时 × H100 的属性，而非 Qwen2 架构特有。

## 7. 优点（方法或实验设计亮点）

- **公平的头对头对比设计**：单一 OpenAI 兼容负载驱动 + 相同 JSONL 工作负载，使两个运行时面对完全一致的 prompt 与调度，最大程度消除对比偏差。
- **可复现性强**：公开完整 artifact（负载生成器、测量脚本、原始结果、绘图模板、无需 GPU 的复现 notebook），并明确给出 3 GPU 小时的复现成本。
- **指标归一化严谨**：针对两个运行时结构迥异的原生缓存计数器，设计
