## 摘要
共享主机内存缓存可以在请求于推理副本之间迁移时避免重复 prefill。其有效性取决于正确的状态传输以及前缀局部性的丢失。我们研究了两个单 GPU 的 27B vLLM 副本，它们共享一个 256 GiB 的 LMCache 池。在采用现有的打包页补丁后，我们隔离出一个裸指针回退路径，该路径省略了对当前 CUDA 流的依赖。受控字节测试在施加延迟时失败，而在恢复该依赖后通过；现有的混合分配器提供了一条可用的部署路径。全池分配检查和服务回归完成了验证。一个四区块 OFF-ON-ON-OFF 对比在两个区块对中包含 768 个实测请求。在 128k 输入下，跨副本首个内容 token 的时间中位数从 31.715 秒降至 0.605 秒；在 256k 输入下，从 92.047 秒降至 0.790 秒。在初始上下文为 32k 和 128k 时，交替副本的六轮合成会话分别提升约 35% 和 45%，而固定放置几乎没有收益。本工程案例研究识别了实用的验证步骤，以及共享缓存能够带来收益的局部性条件。

## Abstract
Shared host-memory caching can avoid repeated prefill when a request moves between inference replicas. Its usefulness depends on both correct state transfer and lost prefix locality. We study two single-GPU 27B vLLM replicas sharing a 256 GiB LMCache pool. After adopting an existing packed-page patch, we isolate a raw-pointer fallback that omits the dependency on the current CUDA stream. Controlled byte tests fail under an imposed delay and pass when the dependency is restored; the existing mixed allocator provides a working deployment path. Full-pool allocation checks and service regression complete the validation. A four-block OFF-ON-ON-OFF comparison contains 768 measured requests within two block pairs. Median cross-replica time to first content token falls from 31.715 to 0.605 seconds at 128k input and from 92.047 to 0.790 seconds at 256k. Six-turn synthetic sessions alternating replicas improve by approximately 35% and 45% at initial contexts of 32k and 128k, while fixed placement shows little benefit. This engineering case study identifies practical validation steps and the locality conditions in which shared caching pays off.

## 1. 核心问题与整体含义

- **背景**：多轮推理请求通常携带大量已在先前轮次处理过的上下文。若请求留在原副本，可复用本地前缀状态；但一旦被路由到另一副本，就需要重新预填充（prefill）整个长前缀，造成高昂延迟。
- **部署抉择**：在实际服务中面临三种选择——通过请求放置（placement）保持对话局部性、提供共享状态复用路径、或两者结合。
- **两个核心问题**：
  - 如何验证共享 KV 状态转移路径的正确性？
  - 其性能收益与"把对话保留在原 GPU 上"这一竞争性替代方案相比如何？
- **两个动机性观察**：
  - 缓存可能"看似可用却返回错误状态"——HTTP 200 或命中计数器并不构成完整性检查。
  - 令人印象深刻的"冷 vs 热"对比会掩盖更优的替代方案（保留在原 GPU），因此评估必须保留本地命中基线。
- **整体含义**：这是一篇工程案例研究，强调"先建立正确性、再测量性能"，并指出共享缓存的收益高度依赖前缀局部性条件。

## 2. 方法论

### 2.1 核心思想

- 在同一推理主机上部署两个完整的单 GPU vLLM 副本（各占一张 GPU，均执行 prefill 与 decode），各自保留本地 GPU 前缀缓存，同时共同连接一个 256 GiB 主机内存 LMCache 服务。
- 该架构**不是** prefill/decode 分离，网关也不充当 KV 数据存储层；LMCache 仅提供缓存转移与复用机制。
- 采用分层验证：表示（representation）→ 排序（ordering）→ 全量分配（allocation）→ 服务结果（service outcome）。

### 2.2 正确性故障定位与修复

- **打包页兼容性修复**：
  - 初次跨副本响应虽返回 HTTP 200 和 25,088 个外部命中 token，却产生损坏文本。
  - 根因：一个逻辑 full-attention 块包含多个打包 kernel 页，原实现识别 rank-5 attention 张量但遗漏 rank-4 打包表示，导致转移字节视图错误。
  - 修复：采用上游 packed-subpage 补丁（commit `f180b9ff…`），无额外本地源码修改；1,568-token 逻辑块跨 49 个 32-token 页。
  - HND 布局是评测中该补丁与 vLLM/FlashInfer 组合的必需配置（NHD 启动因 kernel-page-count 整除错误失败），但这是配置特定要求，非 LMCache 通用要求。

- **CUDA stream 排序故障（核心发现）**：
  - 现象：相同 token 输入在 A 上冷计算或本地复用得到 `alpha=938639`；B 外部命中 127,008 token 却返回 `938624`，且 B 本地复用保留该错误；换新 cache salt 强制零命中冷计算后恢复正常。
  - 根因：评测镜像缺少 LMCache CUDA-ops 扩展，走 PyTorch 回退路径；`lmcache_memcpy_async` 的裸指针分支调用 `cudaMemcpy(..., cudaMemcpyDefault)` 时**未传入当前 stream**，而 `cudaMemcpyDefault` 是拷贝类型枚举而非函数名；PyTorch stream 池使用 `cudaStreamNonBlocking`，非默认流被排除在 legacy default-stream 隐式同步之外，导致生产者/消费者依赖缺失。
  - 字节探针：1 MiB D2H 探针调度延迟写入值 37，回退路径后主机收到旧值 0；H2D 探针类似，消费者读到 53；每个探针报告 1,048,576 个不匹配字节。
  - 补充控制（9 月 13 日，固定 pin 内存与 GPU 缓冲，仅变排序机制；4 KiB / 1 MiB / 16 MiB，双向，0 或 10⁸ CUDA sleep cycles，每格 10 次）：裸回退在全部 120 个延迟检查中失败、120 个非延迟检查通过；三种控制（等待前序流工作、`cudaMemcpyAsync` 当前流、同流 tensor 拷贝）通过全部 720 项检查。
  - 实际分配器/helper 层：lazy 路径在 GPU 0 上 10/10 失败；mixed 路径在 GPU 0 和 GPU 1 上各 10/10 通过。
  - 修复：显式设置 `--no-l1-use-lazy` 以选择 mixed 分配器及其 tensor-copy 路径；仅移除 lazy 正向标志不够，因为 CLI 默认即为 lazy。

- **全池 pinned 分配**：
  - 首次 256 GiB 服务分配回退到 pageable 内存。
