## 摘要
AI编码代理（如GitHub Copilot、Claude Code和Codex）将多步LLM推理与工具执行交织在一起，形成了不同于聊天机器人的工作负载。我们基于2026年6月的采样GitHub Copilot轨迹（涵盖320万用户、1300万会话、7.61亿次LLM调用和95万亿个词元）对这类工作负载进行了首次生产规模表征。我们的分析揭示了独特的工作负载特性及其对系统的关键影响。例如，代理式编码会话由稀疏的用户发起回合组成，每个回合展开为一个自主的代理循环，其中LLM调用几乎总是与工具执行耦合。这种结构使得回合内的KV缓存命中率平均可达90%，但在回合边界处降至55%，并且在模型切换或上下文压缩等事件后会被大幅失效。观测到多样化的流程和用户行为，其词元消耗、时间跨度和工具调用具有可变性和长尾分布。我们强调了快速代理周转时间与回合边界处长达数分钟的用户空闲期之间的差异，并设计了一个轻量级空闲时间预测器，可捕获总空闲时间的86%至90%，从而为高效资源编排的主动决策提供支持。这些发现对现有LLM服务系统的假设提出了挑战，并为代理原生基础设施提供了经验基础。

## Abstract
AI coding agents like GitHub Copilot, Claude Code, and Codex interleave multi-step LLM inference with tool execution, creating a workload different from chatbots. We present the first production-scale characterization of this workload using sampled GitHub Copilot traces from June 2026, comprising 3.2M users, 13M sessions, 761M LLM calls, and 95T tokens.   Our analysis reveals distinctive workload properties with important systems implications. For example, agentic coding sessions consist of sparse user-initiated turns, each unfolding into an autonomous agent loop of LLM calls almost always coupled with tool execution. This structure yields KV cache hit rates averaging 90% within a turn, but falling to 55\% across turn boundaries and drastically invalidated after events like model switches or context compaction. Diverse workflows and user behaviors are observed with variable and long-tailed token consumption, time span, and tool calls. We highlight the difference between quick agentic turnaround times and the minutes-long user idle periods at turn boundaries, and design a lightweight idle-time predictor that captures 86-90\% of total idle time, enabling proactive decisions for efficient resource orchestration. These findings challenge assumptions underlying current LLM-serving systems and provide an empirical foundation for agent-native infrastructure.

- **执行结构**：代理会话呈现 87% 代理自主发起的 LLM 调用；LLM 调用与工具调用近 1:1 严格耦合；并行度低（中位数 1.15，P90=1.4），主要集中在回合中段的读操作批次。

- **空闲预测器有效**：在时间流逝后准确率衰减的情况下，仍能持续捕获总空闲时间的 86–90%，可作为 LLM 服务 API 层的 keep-alive 调度信号。

- **预测器设计精巧**：用生存曲线替代点估计预测，提供了灵活的操作点选择，且推导的闭合条件概率更新方式代价极低；模型小、推理快，适合生产部署。
- **识别出多个此前未被量化的关键事件**：如上下文压缩对缓存的全新破坏性、模型切换的缓存灾难性失效、工具失败的算力放大效应，为后续系统设计提供了新的方向。
- **诚实披露局限性**：明确说明无质量信号、无服务器端视角、工作负载快速演化等局限，增强了结论的可信度。

### 8. 不足与局限

- **无任务质量信号**：未收集 prompt/response 内容，无法将资源效率与任务完成质量关联，无法回答"资源消耗是否带来更好的产出"这一关键问题。
- **单一平台偏差**：数据仅来自 GitHub Copilot（虽然具有代表性），工作负载特征未必完全适用于 Claude Code、Codex 等其他编码代理的部署形态。
- **地理覆盖有限**：数据仅覆盖美国区域，最多三个时区，全球其他地区（如 APAC、欧洲）的开发行为可能不同，导致工作负载特征的普遍性受限。
- **无服务器端视角**：缺乏 GPU 利用率、队列深度、批大小和内存压力等服务器端数据，只能从客户端观察推断系统优化方向，无法做端到端的闭环验证。
- **工作负载快速演化**：模型、工具和代理策略每周都在变化，虽然作者声称 2026 年 1-6 月特征一致，但这一结论对未来是否适用仍存疑。
- **KV 缓存观察为客户端推断**：缓存命中率是从客户端观测推断的，未直接观测服务端的替换策略和缓存状态；文中"2-10分钟命中率悬崖"虽被推断为时间基准淘汰策略的痕迹，但无法验证该机制。
- **预测器精度局限**：随着预测时间窗口拉长（30 分钟），准确率和 F1 明显衰减（降至 25–43%），虽捕获总空闲时间稳定，但精确的长时间空闲预测仍是未解难题。
